# Порядок развития базы знаний

## Проверка существующих ответов

Наличие ответа определяется парсером и не является отметкой проверки. Полная техническая проверка базы пока не проведена.

Сначала проверяйте материалы с высоким риском ошибки: lifetime/UB, memory model, atomics, MMIO/DMA, безопасность, нормативные утверждения LTE/NR. В каждом ответе проверяйте:

- Указаны язык, версия стандарта, реализация и платформа там, где поведение зависит от них.
- Источник подтверждает конкретное утверждение; ссылка на главную страницу не заменяет раздел документации.
- Пример компилируется в заявленном окружении; ожидаемый результат и ограничения объяснены.
- Требования стандарта отделены от типичного поведения реализации и рекомендаций автора.
- Повтор вопроса раскрывает новый аспект или явно используется для повторения.

Фиксируйте результат проверки вместе с конкретным вопросом: статус «проверен», дата, версия и ссылка на подтверждение. Пока таких метаданных нет, не отображайте пользователю знак технической верификации.

## Следующие этапы продукта

- Поиск по текстам вопросов через отдельный загружаемый индекс; не добавлять полные ответы в стартовый каталог.
- Метаданные сложности, предварительных знаний и технической проверки; перенос прогресса при изменении ID.
- Интервальное повторение с датой следующей проверки; текущая отметка «Повторить» ещё не задаёт расписание.
- Отдельные измерения стартовой загрузки, первой темы и длинного ответа на телефоне и медленной сети.
- При подтверждённой проблеме памяти — ограничение кэша тем; при дорогой загрузке — деление крупных тем.

Готовый сквозной учебный проект должен включать исходники, тесты, описание нагрузки, результаты измерений и объяснение компромиссов. Перечень вопросов не заменяет эту практику.
