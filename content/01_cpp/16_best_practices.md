# Best_practices


## Лёгкий уровень


1. Что обычно понимают под best practices в C++?

   **Ответ:** Это набор проверенных индустрией и стандартами подходов, идиом и соглашений (например, RAII, использование `std::string_view`, соблюдение const-correctness), которые снижают вероятность багов, утечек ресурсов и делают код безопасным и предсказуемым.
   **Пример:**
   ```cpp
   // Следуя best practice: RAII вместо ручного управления
   auto file = std::make_unique<std::ifstream>("data.txt");

   ```


   **Типичная ошибка:** Считать, что best practices — это догмы, которые нужно применять без учета контекста (например, экстремальной оптимизации под специфичное "железо").
   **Источник:** [C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)

2. Почему best practices важны даже для «рабочего» кода?

   **Ответ:** Код, который просто выдает нужный результат сегодня, может содержать скрытое неопределенное поведение (UB), гонки данных или утечки памяти, которые проявятся позже под нагрузкой или на другой платформе.
   **Пример:**
   ```cpp
   // Возвращает висячий указатель; его разыменование после возврата — UB:
   int* get_val() { int x = 42; return &x; }

   ```


   **Типичная ошибка:** Полагать, что отсутствие сбоя при локальном запуске гарантирует корректность программы.
   **Источник:** [SEI CERT C++ Coding Standard](https://wiki.sei.cmu.edu/confluence/pages/viewpage.action?pageId=88046682)

3. Почему «код компилируется» ещё не означает «код хороший»?

   **Ответ:** Компилятор проверяет синтаксис и правила типизации, но не логику бизнес-требований, отсутствие утечек, читаемость, устойчивость к исключениям и производительность.
   **Пример:**
   ```cpp
   // Компилируется без ошибок, но содержит логический баг
   bool is_valid(int x) { return x = 5; } // присваивание вместо сравнения

   ```


   **Типичная ошибка:** Игнорировать предупреждения компилятора (`-Wall -Wextra`), опираясь только на нулевой код возврата сборки.
   **Источник:** [C++ Core Guidelines: Per.1](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#per1-dont-optimize-without-reason)

4. Что важнее в долгосрочной перспективе: написать быстро или написать поддерживаемо?

   **Ответ:** В долгосрочной перспективе критически важна поддерживаемость, так как фаза сопровождения, рефакторинга и адаптации кода может составлять значительную часть работы над проектом.
   **Пример:** Модульная архитектура с чистыми интерфейсами позволяет внедрять новые фичи за часы, тогда как монолитный «быстрокод» требует переписывания с нуля через полгода.
   **Типичная ошибка:** Жертвовать модульностью и тестами ради сиюминутного дедлайна, накапливая критический технический долг.
   **Источник:** [Code Complete (Steve McConnell)](https://en.wikipedia.org/wiki/Code_Complete)

5. Почему читаемость кода считается неотъемлемой частью качества программы?

   **Ответ:** Читаемый код снижает когнитивную нагрузку на разработчика, упрощает поиск дефектов при код-ревью и уменьшает риск внести регрессионную ошибку при доработке.
   **Пример:**
   ```cpp
   // Читаемо и выразительно
   if (user.has_active_subscription()) { /* ... */ }

   ```


   **Типичная ошибка:** Писать код «под компилятор», превращая выражения в нечитаемые однострочники.
   **Источник:** [C++ Core Guidelines: P.1](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#p1-express-ideas-directly-in-code)

6. Что такое maintainability (сопровождаемость/поддерживаемость)?

   **Ответ:** Это характеристика кода, отражающая, насколько легко разработчикам находить и исправлять ошибки, внедрять новую функциональность и адаптировать систему без риска поломать существующее поведение.
   **Пример:** Класс с высокой поддерживаемостью имеет одну ответственность и изолирован тестами, поэтому его изменение не ломает соседние модули.
   **Типичная ошибка:** Оценивать качество системы только по текущей скорости работы, полностью игнорируя трудозатраты на внесение изменений.
   **Источник:** [ISO/IEC 25010 Software Quality Model](https://iso25000.com/index.php/en/iso-25000-standards/iso-25010)

7. Почему разработчики читают код чаще, чем пишут его?

   **Ответ:** Чтобы написать одну строчку корректного кода, программист должен изучить контекст вызовов, контракты смежных функций, модели данных и зависимости проекта.
   **Пример:** При исправлении бага на 1 строчку разработчик нередко прослеживает стек вызовов через десяток файлов.
   **Типичная ошибка:** Писать код быстро ради ускорения ввода символов, игнорируя то, сколько времени потребуется коллегам на его расшифровку.
   **Источник:** [Clean Code (Robert C. Martin)](https://www.oreilly.com/library/view/clean-code-a/9780136083238/)

8. Что такое self-documenting code (самодокументируемый код)?

   **Ответ:** Это код, чье назначение и логика понятны непосредственно из структуры, сигнатур функций, системы типов и названий идентификаторов без обращения к внешним комментариям.
   **Пример:**
   ```cpp
   // Смысл понятен без комментариев:
   if (connection.is_timed_out()) {
       connection.reconnect();
   }

   ```


   **Типичная ошибка:** Полагать, что самодокументируемый код отменяет необходимость документирования архитектурных решений («почему было сделано именно так»).
   **Источник:** [Refactoring: Improving the Design of Existing Code (Martin Fowler)](https://refactoring.com/)

9. Почему хорошие имена важны не меньше правильной логики?

   **Ответ:** Неудачные имена дезинформируют разработчика, порождая ложные предположения о поведении сущностей, что приводит к багам быстрее, чем ошибки в синтаксисе.
   **Пример:** Функция с именем `check_validity()` не должна внутри себя скрытно модифицировать или сбрасывать состояние объекта.
   **Типичная ошибка:** Использовать общие названия (`data`, `temp`, `info`, `process()`) для ключевых структур предметной области.
   **Источник:** [Google C++ Style Guide: Naming](https://google.github.io/styleguide/cppguide.html#Naming)

10. Какими свойствами обычно обладает хорошее имя переменной?

   **Ответ:** Хорошее имя отражает суть данных (намерение), однозначно трактуется в контексте задачи, легко произносится при коммуникации и согласуется с общим стилем проекта.
   **Пример:**
   ```cpp
   const size_t max_retry_attempts = 3; // Ясно назначение и единица измерения

   ```


   **Типичная ошибка:** Добавление устаревшей венгерской нотации (`iCount`, `pBuffer`) там, где тип гарантируется компилятором.
   **Источник:** [C++ Core Guidelines: NL.1](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#nl1-dont-say-in-comments-what-can-be-clearly-stated-in-code)

11. Почему имя `count` лучше, чем `x`, если оно отражает смысл?

   **Ответ:** Имя `count` передает семантику количественного показателя, исключая предположения о том, что переменная хранит координаты, коэффициент или произвольный дескриптор.
   **Пример:**
   ```cpp
   // count говорит само за себя:
   for (size_t count = 0; count < buffer.size(); ++count) { /* ... */ }

   ```


   **Типичная ошибка:** Оставлять временные однобуквенные имена из чернового кода в финальном pull request.
   **Источник:** [Clean Code (Robert C. Martin)](https://www.oreilly.com/library/view/clean-code-a/9780136083238/)

12. Когда короткие имена переменных всё же уместны?

   **Ответ:** Короткие имена уместны в предельно узких областях видимости (локальные счетчики циклов `i`, `j`, координаты `x`, `y`, параметры тривиальных лямбд или шаблонные параметры `T`).
   **Пример:**
   ```cpp
   for (int i = 0; i < n; ++i) { /* 2 строки кода */ }

   ```


   **Типичная ошибка:** Использование однобуквенных идентификаторов для полей классов или долгоживущих глобальных/статических переменных.
   **Источник:** [Google C++ Style Guide: Variable Names](https://google.github.io/styleguide/cppguide.html#Variable_Names)

13. Почему единый стиль именования важен в командном проекте?

   **Ответ:** Он позволяет мгновенно отличать типы данных от переменных, функций, констант и макросов, избавляя разработчика от необходимости постоянно переходить к объявлениям.
   **Пример:** Принятый стиль `CamelCase` для типов и `snake_case` для функций сразу разделяет вызов конструктора и вызов функции.
   **Типичная ошибка:** Смешивание нескольких стилей в рамках одного файла или модуля (`getUserName()` рядом с `set_user_age()`).
   **Источник:** [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html)

14. Что такое consistency (согласованность) в кодовой базе?

   **Ответ:** Это свойство проекта, при котором схожие задачи решаются одинаковыми паттернами, архитектурными подходами и правилами форматирования во всех его модулях.
   **Пример:** Если обработка ошибок в проекте построена на `std::expected` или кодах ошибок, новые компоненты не должны спонтанно переходить на выброс исключений без согласования с командой.
   **Типичная ошибка:** Создание собственного уникального микро-фреймворка внутри отдельного подкаталога чужого репозитория.
   **Источник:** [C++ Core Guidelines: Introduction](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#in-introduction)

15. Почему единообразие в проекте часто важнее личных предпочтений разработчика?

   **Ответ:** Общая однородность снижает friction (трение) при чтении и перемещении между модулями: команда тратит время на логику продукта, а не на визуальный парсинг чужих персональных стилей.
   **Пример:** Следование командному правилу ставить открывающую фигурную скобку на той же или новой строке устраняет споры на код-ревью.
   **Типичная ошибка:** Переформатирование целых файлов чужого авторства под свои личные привычки при исправлении локального бага.
   **Источник:** [Google C++ Style Guide: Formatting](https://google.github.io/styleguide/cppguide.html#Formatting)

16. Что такое code style guide (руководство по стилю кода)?

   **Ответ:** Это задокументированный свод правил и соглашений команды, регламентирующий форматирование, соглашения об именах, допустимые конструкции языка и запрещенные практики.
   **Пример:** Правило style guide: «Всегда помечать конструкторы с одним аргументом ключевым словом `explicit`».
   **Типичная ошибка:** Составление огромного руководства без автоматизации его проверки через линтеры и форматтеры (`clang-format`, `clang-tidy`).
   **Источник:** [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html)

17. Почему проекту нужен общий стиль, даже если компилятор языка его не требует?

   **Ответ:** Компилятору безразличны отступы и правила именования, но они критичны для людей: стандартизация исключает когнитивный шум, упрощает `diff` в системе контроля версий и автоматизирует ревью.
   **Пример:** `clang-format` исключает конфликты слияния (merge conflicts), вызванные расстановкой лишних пробелов разными редакторами.
   **Типичная ошибка:** Вести субъективные дебаты о форматировании на pull request вместо делегирования проверки CI-пайплайну.
   **Источник:** [ClangFormat Documentation](https://clang.llvm.org/docs/ClangFormat.html)

18. Почему использование «магических чисел» считается плохой практикой?

   **Ответ:** Числовые литералы без имени скрывают смысл заложенного в них коэффициента или лимита, а при необходимости изменить значение приходится вручную искать и заменять дубликаты по всему проекту.
   **Пример:**
   ```cpp
   // Плохо: что означает 86400?
   if (elapsed > 86400) { /* ... */ }

   ```


   **Типичная ошибка:** Полагать, что очевидные для автора числа (например, размер буфера или таймаут) будут так же понятны любому другому человеку через год.
   **Источник:** [C++ Core Guidelines: ES.45](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#es45-avoid-magic-constants-use-symbolic-constants)

19. Что такое magic number (магическое число)?

   **Ответ:** Это жестко зашитый в логику программы числовой литерал, смысл, происхождение и назначение которого не ясны без детального исследования контекста.
   **Пример:** Вызов функции вида `apply_discount(price, 0.15);`, где `0.15` не вынесено в понятную именованную сущность вроде `default_seasonal_discount`.
   **Типичная ошибка:** Оставлять такие числа внутри сложных математических условий без пояснений или физических размерностей.
   **Источник:** [Clean Code (Robert C. Martin)](https://www.oreilly.com/library/view/clean-code-a/9780136083238/)

20. Чем именованная константа лучше литерала, разбросанного по кодовой базе?

   **Ответ:** Именованная константа дает числу документальное имя, фиксирует единую точку изменения при переконфигурации и позволяет компилятору контролировать строгую типизацию.
   **Пример:**
   ```cpp
   // Хорошо: одна точка модификации и понятный смысл
   constexpr size_t max_buffer_capacity = 1024;

   ```


   **Типичная ошибка:** Использование устаревшего макроса `#define MAX_BUFFER 1024` вместо безопасного `constexpr` с контролем области видимости и типа.
   **Источник:** [C++ Core Guidelines: Con.1](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#con1-by-default-make-objects-immutable)

21. Почему комментарий не должен компенсировать неудачно подобранное имя?

   **Ответ:** Комментарии имеют свойство устаревать при модификации кода, в то время как выразительное имя само по себе актуализирует смысл сущности прямо в точке использования.
   **Пример:**
   ```cpp
   // Плохо:
   int d; // прошедшее время в днях
   // Хорошо:
   int elapsed_time_days;

   ```


   **Типичная ошибка:** Написание объясняющих комментариев к аббревиатурам вместо прямого переименования переменной.
   **Источник:** [Clean Code: Chapter 4 (Robert C. Martin)](https://www.oreilly.com/library/view/clean-code-a/9780136083238/)

22. В каких случаях комментарий в коде действительно необходим?

   **Ответ:** Комментарий необходим для объяснения нетривиальных бизнес-причин («почему так сделано»), ссылок на баг-трекеры, описания сложных математических алгоритмов, нестандартных оптимизаций или ограничений внешних API.
   **Пример:**
   ```cpp
   // Выравнивание по 64 байтам для предотвращения false sharing между потоками
   alignas(64) std::atomic<int> counter;

   ```


   **Типичная ошибка:** Дублирование очевидного действия: `++i; // инкрементируем i`.
   **Источник:** [C++ Core Guidelines: NL.1](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#nl1-dont-say-in-comments-what-can-be-clearly-stated-in-code)

23. Почему комментарий, пересказывающий «что делает код», часто хуже самого кода?

   **Ответ:** Он дублирует код и создает двойную нагрузку при поддержке. Когда логика меняется, такой комментарий забывают обновить, и он начинает вводить читающего в заблуждение.
   **Пример:**
   ```cpp
   // Проверяем, что соединение открыто (а код на самом деле проверяет закрытие!)
   if (!conn.is_open()) { return; }

   ```


   **Типичная ошибка:** Трата сил на пересказ стандартных инструкций языка русским или английским текстом.
   **Источник:** [C++ Core Guidelines: NL.2](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#nl2-hang-comments-on-the-language-concepts-they-refer-to)

24. В каких ситуациях полезнее пояснять комментарием причину («почему»), а не само действие («что»)?

   **Ответ:** Это необходимо, когда решение выглядит нестандартно, обходит неочевидный баг платформы/драйвера или вызвано внешними юридическими/бизнесовыми ограничениями, которые невозможно выразить синтаксисом C++.
   **Пример:**
   ```cpp
   // Спим 10мс: обход известного бага прошивки v1.2 устройства,
   // иначе сбрасывается буфер приема (см. тикет #4021)
   std::this_thread::sleep_for(10ms);

   ```


   **Типичная ошибка:** Оставлять неочевидные костыли без объяснения контекста, из-за чего следующий разработчик их удаляет при рефакторинге и возвращает баг.
   **Источник:** [Clean Code (Robert C. Martin)](https://www.oreilly.com/library/view/clean-code-a/9780136083238/)

25. Почему чрезмерно «умный» и компактный код считается плохой практикой?

   **Ответ:** Плотный код, перегруженный побитовыми хаками, шаблонными трюками или тернарными операторами в несколько уровней, крайне сложен для отладки, ревью и дальнейшей поддержки другими людьми.
   **Пример:**
   ```cpp
   // Излишне "умно":
   a ^= b ^= a ^= b;
   // Просто и понятно:
   std::swap(a, b);

   ```


   **Типичная ошибка:** Попытка доказать собственную квалификацию через намеренное усложнение кода там, где достаточно стандартной функции.
   **Источник:** [C++ Core Guidelines: P.2](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#p2-write-in-iso-standard-c)

26. В чём заключается суть принципа KISS в программировании?

   **Ответ:** Принцип KISS (Keep It Simple, Stupid) утверждает, что система работает надежнее всего, если она остается максимально простой, без введения преждевременных абстракций, фабрик и уровней косвенности.
   **Пример:** Использование прямого вызова свободной функции вместо конструирования иерархии абстрактных фабрик ради одного сценария.
   **Типичная ошибка:** Проектирование сложнейшей системы плагинов и наследования для функциональности, которая гарантированно не будет расширяться.
   **Источник:** [The Art of Unix Programming (Eric S. Raymond)](https://www.google.com/search?q=http%3A%2F%2Fwww.catb.org%2F~esr%2Fwritings%2Ftaoup%2Fhtml%2Fch01s06.html)

27. Что означает идиома «make the common case simple»?

   **Ответ:** Интерфейс библиотеки или класса должен быть спроектирован так, чтобы типовые, часто встречающиеся задачи решались минимальным и очевидным кодом, а редкие сценарии оставались возможными, но требовали дополнительных настроек.
   **Пример:** `std::vector` позволяет просто вызывать `push_back()`, не заставляя пользователя вручную аллоцировать память и управлять `std::allocator_traits` для базовых случаев.
   **Типичная ошибка:** Вынуждать пользователя передавать десяток параметров по умолчанию в конструктор ради самого частого сценария использования.
   **Источник:** [C++ Core Guidelines: I.1](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#i1-make-interfaces-explicit)

28. Почему простые решения часто превосходят «изящные», но сложные архитектурные конструкции?

   **Ответ:** Простые решения содержат меньше состояний и граничных случаев, легче поддаются модульному тестированию, оптимизируются компилятором без сюрпризов и понятны любому члену команды с первого взгляда.
   **Пример:** Простой линейный массив `std::vector` с линейным поиском для малого количества элементов работает в разы быстрее и надежнее сложного самобалансирующегося дерева.
   **Типичная ошибка:** Усложнение архитектуры из перфекционизма и желания применить все известные паттерны проектирования GoF сразу.
   **Источник:** [A Philosophy of Software Design (John Ousterhout)](https://web.stanford.edu/~ouster/cgi-bin/book.php)

29. Что такое code smell (запах кода)?

   **Ответ:** Это характерный признак в исходном коде программы (например, огромный метод, дублирование, длинный список параметров), который не является синтаксической ошибкой, но указывает на глубокие проблемы в архитектуре или дизайне.
   **Пример:** Метод класса на 500 строк с 10 аргументами — классический code smell, сигнализирующий о нарушении SRP.
   **Типичная ошибка:** Игнорирование запахов кода до тех пор, пока они не приведут к критическим багам под нагрузкой.
   **Источник:** [Refactoring: Improving the Design of Existing Code (Martin Fowler)](https://refactoring.com/)

30. Почему дублирование кода считается одним из самых критичных code smells?

   **Ответ:** При исправлении ошибки или изменении бизнес-логики в одном месте дубликат в другой части кодовой базы неизбежно забудут обновить, что гарантированно приведет к рассинхронизации поведения и багам.
   **Пример:** Дублирование логики валидации email-адреса в пяти разных контроллерах приводит к разным правилам проверки на фронте и бэкенде.
   **Типичная ошибка:** Копирование блока кода через Copy-Paste с последующим мелким изменением переменных («Copy-Paste programming»).
   **Источник:** [The Pragmatic Programmer (Andy Hunt, Dave Thomas)](https://pragprog.com/titles/tpp20/the-pragmatic-programmer-20th-anniversary-edition/)

31. Что такое принцип DRY (Don't Repeat Yourself)?

   **Ответ:** Это принцип разработки, требующий, чтобы каждый фрагмент знания или логики имел единственное, непротиворечивое и авторитетное представление в рамках всей системы.
   **Пример:**
   ```cpp
   // Вынесение общей математики в отдельную функцию
   double calculate_vat(double price) { return price * 0.20; }

   ```


   **Типичная ошибка:** Восприятие DRY исключительно как запрета на совпадение двух строчек кода, без учета совпадения бизнес-смысла.
   **Источник:** [The Pragmatic Programmer](https://pragprog.com/titles/tpp20/the-pragmatic-programmer-20th-anniversary-edition/)

32. В каких случаях слепое следование DRY может принести вред архитектуре?

   **Ответ:** Когда разные части системы случайно похожи визуально, но изменяются по совершенно разным бизнес-причинам; их искусственное объединение создает сильную связность (coupling) между несвязанными доменами.
   **Пример:** Объединение валидации логина пользователя и валидации промокода в одну общую функцию только потому, что обе проверяют длину строки.
   **Типичная ошибка:** Создание монструозных обобщенных функций с множеством флагов (`if (is_admin) ... else ...`) ради избежания повторения 2–3 строчек.
   **Источник:** [A Philosophy of Software Design (John Ousterhout)](https://web.stanford.edu/~ouster/cgi-bin/book.php)

33. Что характеризует понятный и качественный интерфейс функции?

   **Ответ:** Понятный интерфейс явно выражает намерения через типизированные аргументы, минимизирует побочные эффекты, защищен от ошибочной передачи аргументов перепутанных типов и возвращает ожидаемый результат.
   **Пример:**
   ```cpp
   // Понятный интерфейс с использованием strong types:
   void set_timeout(std::chrono::milliseconds ms);
   // Вместо двусмысленного: void set_timeout(int t);

   ```


   **Типичная ошибка:** Прием множества `bool`-флагов подряд: `draw_window(true, false, true, false);`, где невозможно понять назначение без документации.
   **Источник:** [C++ Core Guidelines: I.4](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#i4-make-interfaces-strongly-typed)

34. Почему функция должна решать ровно одну понятную задачу?

   **Ответ:** Функцию с одной задачей легко назвать понятным именем, ее тривиально покрыть модульными тестами, она не содержит скрытых сайд-эффектов и пригодна для повторного использования в других контекстах.
   **Пример:** Разделение чтения файла и парсинга JSON на две отдельные функции: `read_file_to_string()` и `parse_json()`.
   **Типичная ошибка:** Создание функций вида `load_and_process_and_save_data()`, скрывающих внутри весь жизненный цикл пайплайна.
   **Источник:** [Clean Code (Robert C. Martin)](https://www.oreilly.com/library/view/clean-code-a/9780136083238/)

35. Что представляет собой small function principle (принцип небольших функций)?

   **Ответ:** Это рекомендация декомпозировать код на компактные функции, каждая из которых решает одну элементарную подзадачу и целиком помещается на одном экране, позволяя охватить логику одним взглядом.
   **Пример:** Вместо простыни на 150 строк код разбивается на 4–5 шагов с ясными декларативными именами.
   **Типичная ошибка:** Доведение идеи до абсурда: разбиение линейного читаемого алгоритма на десятки микрофункций по 1 строке, размазанных по всему классу.
   **Источник:** [C++ Core Guidelines: F.3](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#f3-keep-functions-short-and-simple)

36. Почему чрезмерно длинные функции сложно читать и тестировать?

   **Ответ:** Длинные функции накапливают огромное количество возможных комбинаций внутренних состояний и ветвлений, что порождает комбинаторный взрыв тестовых сценариев и перегружает кратковременную память программиста.
   **Пример:** Функция с 5 вложенными `if` требует десятки тестов для полного покрытия всех веток исполнения, в отличие от нескольких изолированных функций.
   **Типичная ошибка:** Добавление новой логики простым дописыванием еще 20 строк в конец существующей 300-строчной функции.
   **Источник:** [Refactoring: Large Class and Long Method (Martin Fowler)](https://refactoring.guru/smells/long-method)

37. Что означает single responsibility (принцип единственной ответственности) на уровне функции?

   **Ответ:** Функция должна отвечать за выполнение одного конкретного алгоритма или действия, и у нее должна быть только одна причина для изменения в случае смены требований.
   **Пример:**
   ```cpp
   // Функция только фильтрует, но не выводит в лог и не пишет в базу
   std::vector<User> filter_active_users(const std::vector<User>& users);

   ```


   **Типичная ошибка:** Совмещение вычислений с побочным сетевым вводом-выводом или логированием в бизнес-функциях.
   **Источник:** [Clean Architecture (Robert C. Martin)](https://blog.cleancoder.com/uncle-bob/2014/05/08/SingleReponsibilityPrinciple.html)

38. Почему глубокая вложенность условий `if` и циклов ухудшает читаемость?

   **Ответ:** С каждым новым уровнем вложенности читающему приходится держать в голове все предыдущие предикаты условий, что приводит к эффекту «лесенки кода» (Arrow Anti-Pattern) и быстрой утомляемости.
   **Пример:** Код с 4 уровнями отступов `if (...) { while(...) { if (...) { ... } } }` маскирует основной сценарий успешного выполнения.
   **Типичная ошибка:** Помещение всего основного тела функции внутрь одного гигантского блока `if (success) { ... }`.
   **Источник:** [Code Complete: Chapter 19 (Steve McConnell)](https://en.wikipedia.org/wiki/Code_Complete)

39. Что такое early return (ранний возврат) и как он улучшает структуру кода?

   **Ответ:** Это паттерн (guard clauses), при котором проверка граничных условий, невалидных аргументов или ошибок происходит в самом начале функции с немедленным выходом из нее через `return`.
   **Пример:**
   ```cpp
   // Использование Guard Clauses:
   void process(Widget* w) {
       if (!w) return;
       if (!w->is_ready()) return;

       // Основная работа без лишних отступов:
       w->execute();
   }

   ```


   **Типичная ошибка:** Устаревшее следование академическому правилу «у функции должна быть только одна точка выхода (Single Exit Point)», ведущее к спагетти из вложенных `if`.
   **Источник:** [Refactoring: Replace Nested Conditional with Guard Clauses](https://refactoring.guru/replace-nested-conditional-with-guard-clauses)

40. Каким образом уменьшение вложенности делает логику прозрачнее?

   **Ответ:** Оно выпрямляет поток выполнения в линейную последовательность: граничные случаи обрабатываются и отсекаются первыми, а целевой алгоритм идет единым блоком на основном уровне отступа.
   **Пример:** Замена вложенного условия на предикат раннего выхода снижает цикломатическую сложность функции и визуально обособляет успешный путь (happy path).
   **Типичная ошибка:** Стремление во что бы то ни стало объединить все условия в одно гигантское булево выражение с операторами `&&` и `||`.
   **Источник:** [C++ Core Guidelines: ES.3](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#es3-dont-nest-blocks-deeply)

41. Почему в профессиональной разработке принято избегать глобальных переменных?

   **Ответ:** Глобальные переменные разрушают инкапсуляцию, создают скрытую связь между несвязанными частями программы и превращают многопоточный код в источник недетерминированных гонок данных (data races).
   **Пример:** Изменение глобальной переменной конфигурации в потоке А ломает сетевой запрос в потоке Б.
   **Типичная ошибка:** Использование паттерна Singleton в качестве замаскированного хранилища глобального изменяемого состояния.
   **Источник:** [C++ Core Guidelines: I.2](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#i2-avoid-global-variables)

42. Какие системные проблемы порождает использование глобального изменяемого состояния?

   **Ответ:** Невозможность изоляции тестов (тесты начинают влиять друг на друга при запуске), проблемы с порядком инициализации между единицами трансляции (Static Initialization Order Fiasco) и сложность отладки.
   **Пример:**
   ```cpp
   // Порядок инициализации a и b в разных .cpp файлах не определен:
   extern int a;
   int b = a + 1;

   ```


   **Типичная ошибка:** Попытка защитить гигантское глобальное состояние десятком мьютексов вместо передачи зависимостей через параметры.
   **Источник:** [C++ Core Guidelines: CP.2](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#cp2-avoid-data-races)

43. Что такое скрытая зависимость (hidden dependency) компонента?

   **Ответ:** Это ситуация, когда класс или функция неявно обращаются к глобальным объектам, синглтонам, системному времени, файловой системе или сетевым ресурсам, не декларируя это в сигнатуре конструктора или метода.
   **Пример:**
   ```cpp
   // Скрытая зависимость от глобального контекста:
   void render() { Database::get_instance().fetch(); }

   ```


   **Типичная ошибка:** Вызов статических методов для получения внешних сервисов прямо посреди бизнес-расчетов.
   **Источник:** [Dependency Injection in .NET / General Concepts (Mark Seemann)](https://en.wikipedia.org/wiki/Dependency_injection)

44. Почему наличие hidden dependencies усложняет сопровождение и модульное тестирование?

   **Ответ:** Такой компонент невозможно протестировать в изоляции: нельзя подменить реальную базу данных или сокет на тестовый дублер (mock), а для запуска теста приходится инициализировать все внешнее окружение.
   **Пример:** Нельзя протестировать парсер, если он жестко зашит на вызов `std::chrono::system_clock::now()` и чтение реального файла `/etc/config.json`.
   **Типичная ошибка:** Отказ от передачи абстракций через интерфейсы в пользу прямого вызова статических методов сторонних библиотек.
   **Источник:** [Growing Object-Oriented Software, Guided by Tests (Steve Freeman, Nat Pryce)](http://www.growing-object-oriented-software.com/)

45. Что такое локальность рассуждения о коде (locality of reasoning)?

   **Ответ:** Это способность разработчика полностью понять поведение, корректность и инварианты конкретного фрагмента кода, глядя исключительно на него, без необходимости изучать глобальный контекст всего проекта.
   **Пример:** Чистая функция `int square(int x) { return x * x; }` обладает идеальной локальностью: для ее понимания не нужно знать, что происходит в других потоках и модулях.
   **Типичная ошибка:** Разнесение тесно связанной логики (например, создания и настройки объекта) по разным концам исходного файла.
   **Источник:** [A Philosophy of Software Design (John Ousterhout)](https://web.stanford.edu/~ouster/cgi-bin/book.php)

46. Почему локальное понимание кода критически важно в масштабных проектах?

   **Ответ:** Ни один разработчик не в состоянии удержать в голове архитектуру кодовой базы на сотни тысяч или миллионы строк; если для правки функции требуется знать весь проект целиком, разработка парализуется.
   **Пример:** Если класс зависит только от переданных ему аргументов, разработчик может безопасно отрефакторить его за 10 минут, не боясь уронить сервер на проде.
   **Типичная ошибка:** Повсеместное использование неявных глобальных контекстов (`AppContext`, `ServiceLocator`), убивающих локальность.
   **Источник:** [C++ Core Guidelines: P.10](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#p10-prefer-immutable-data-to-mutable-data)

47. Почему область видимости переменных всегда следует делать минимальной?

   **Ответ:** Это снижает вероятность случайного изменения переменной вне ее целевого контекста, освобождает ресурсы сразу по выходу из блока и разгружает внимание человека, читающего код.
   **Пример:**
   ```cpp
   // Область видимости 'it' ограничена только циклом:
   for (auto it = vec.begin(); it != vec.end(); ++it) { /* ... */ }

   ```


   **Типичная ошибка:** Объявление всех локальных переменных функции скопом в самом начале метода по старой привычке языка C89.
   **Источник:** [C++ Core Guidelines: ES.5](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#es5-keep-scopes-small)

48. Когда и почему переменную стоит объявлять как можно ближе к месту первого использования?

   **Ответ:** Переменную следует объявлять непосредственно в момент, когда готовы данные для ее корректной инициализации. Это устраняет неинициализированные состояния и избавляет от необходимости листать экран вверх для проверки ее типа.
   **Пример:**
   ```cpp
   // Инициализация сразу с полезными данными:
   const auto connection = open_connection(server_address);

   ```


   **Типичная ошибка:** Объявление переменной без инициализации за 50 строк до ее реального заполнения.
   **Источник:** [C++ Core Guidelines: ES.20](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#es20-always-initialize-an-object)

49. Почему не рекомендуется сохранять избыточное состояние «впрок» на будущее?

   **Ответ:** Любое сохраняемое состояние требует синхронизации и валидации. Хранение избыточных данных усложняет класс, провоцирует рассинхронизацию полей и нарушает принцип YAGNI (You Aren't Gonna Need It).
   **Пример:** Хранение в классе поля `is_adult` одновременно с `birth_date`: при изменении даты придется не забыть обновить и флаг, иначе возникнет расхождение данных.
   **Типичная ошибка:** Добавление десятка полей «на будущее расширение», которые годами остаются мертвым грузом.
   **Источник:** [Extreme Programming Explained (Kent Beck)](https://en.wikipedia.org/wiki/You_aren't_gonna_need_it)

50. В чём заключается хорошая практика инициализации объектов в современном C++?

   **Ответ:** Объект должен быть полностью сконструирован, валиден и готов к работе сразу в точке объявления (через список инициализации конструктора или унифицированную инициализацию `{}`), исключая двухфазную инициализацию через пустые методы `init()`.
   **Пример:**
   ```cpp
   class Socket {
   public:
       // Ресурс захватывается сразу при создании:
       explicit Socket(int port) : handle_{open_port(port)} {
           if (handle_ < 0) throw std::runtime_error("Port open failed");
       }
   private:
       int handle_;
   };

   ```


   **Типичная ошибка:** Создание пустого «полуживого» объекта с последующим обязательным ручным вызовом метода `.init()`, о котором пользователь легко может забыть.
   **Источник:** [C++ Core Guidelines: C.41](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#c41-a-constructor-should-create-a-fully-initialized-object)

## Ниже среднего уровня


51. Почему объекты лучше инициализировать сразу при создании?

   **Ответ:** Это гарантирует соблюдение инвариантов класса с первой строки его существования и исключает появление зомби-объектов с мусорными значениями в полях.
   **Пример:**
   ```cpp
   // Объект сразу готов к работе
   std::string buffer = read_payload();

   ```


   **Типичная ошибка:** Разделение объявления переменной и ее фактического наполнения данными через несколько экранов кода.
   **Источник:** [C++ Core Guidelines: ES.20](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#es20-always-initialize-an-object)

52. Чем инициализация предпочтительнее отложенного присваивания?

   **Ответ:** Инициализация конструирует объект ровно один раз на месте, тогда как цепочка «конструктор по умолчанию + присваивание» совершает двойную работу и не применима к типам без дефолтного конструктора, константам и ссылкам.
   **Пример:**
   ```cpp
   // Инициализация напрямую:
   const Widget w = fetch_widget();

   ```


   **Типичная ошибка:** Создание пустого объекта `Widget w;` с последующим вызовом оператора `w = fetch_widget();`.
   **Источник:** [C++ Core Guidelines: ES.22](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#es22-dont-declare-a-variable-until-you-have-a-value-to-initialize-it-with)

53. Почему неинициализированные переменные считаются грубой ошибкой в коде?

   **Ответ:** Чтение неинициализированной переменной тривиального типа приводит к неопределенному поведению (UB), утечкам данных из стека и плавающим багам, зависящим от уровня оптимизации компилятора.
   **Пример:**
   ```cpp
   int counter; // Мусор на стеке!
   if (flag) counter = 10;
   // UB при обращении к counter, если flag == false

   ```


   **Типичная ошибка:** Предположение, что компилятор или ОС автоматически обнуляют переменные на стеке.
   **Источник:** [SEI CERT C++: EXP53-CPP](https://wiki.sei.cmu.edu/confluence/display/cplusplus/EXP53-CPP.+Do+not+read+uninitialized+memory)

54. Почему в modern C++ отдают предпочтение списочной инициализации `{}`?

   **Ответ:** Унифицированная инициализация `{}` запрещает сужающие неявные преобразования типов (narrowing conversions) и защищает от синтаксической неоднозначности Most Vexing Parse.
   **Пример:**
   ```cpp
   int x{3.14}; // Ошибка компиляции! Потеря точности не пройдет незамеченной

   ```


   **Типичная ошибка:** Использование `{}` с `std::vector`, когда планировался вызов конструктора размера, а не списка элементов (например, `std::vector<int> v{10, 2}`).
   **Источник:** [C++ Core Guidelines: ES.23](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#es23-prefer-the-curly-brace-initializer-syntax)

55. Когда использование ключевого слова `auto` улучшает качество кода?

   **Ответ:** Когда точный тип либо избыточен и повторяет имя фабрики/приведения, либо громоздок (итераторы, замыкания лямбд), а также для защиты от непреднамеренных срезных приведений и копирований.
   **Пример:**
   ```cpp
   auto it = my_map.find(key);
   auto ptr = std::make_unique<SessionHandler>();

   ```


   **Типичная ошибка:** Ручной ввод сложных шаблонных типов, приводящий к случайным неявным конверсиям (например, `std::pair<int, int>` вместо правильного ключа `std::pair<const int, int>` в цикле по ассоциативному контейнеру).
   **Источник:** [C++ Core Guidelines: ES.11](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#es11-use-auto-to-avoid-redundant-repetition-of-type-names)

56. В каких сценариях `auto` ухудшает восприятие кода?

   **Ответ:** Когда по правому выражению читателю невозможно понять семантику и поведение возвращаемого типа без перехода к исходникам вызываемой функции.
   **Пример:**
   ```cpp
   // Читатель не знает, что это: указатель, число, ссылка или объект
   auto res = calculate(data);

   ```


   **Типичная ошибка:** Написание `auto flag = ...` для функций, возвращающих прокси-типы (например, `std::vector<bool>::reference`), что провоцирует висячие ссылки.
   **Источник:** [Google C++ Style Guide: Type Deduction](https://google.github.io/styleguide/cppguide.html#auto)

57. Почему `auto` особенно ценен для сложных и длинных шаблонных типов?

   **Ответ:** Он избавляет от визуального шума, уменьшает дублирование сигнатур и страхует разработчика от опечаток при ручном выводе параметров аллокаторов и предикатов.
   **Пример:**
   ```cpp
   // Вместо: std::unordered_map<std::string, std::vector<Transaction>>::const_iterator
   auto it = transactions.cbegin();

   ```


   **Типичная ошибка:** Написание пятиуровневых вложенных типов вручную при переборе контейнеров STL.
   **Источник:** [Modern Effective C++: Item 5 (Scott Meyers)](https://www.oreilly.com/library/view/effective-modern-c/9781491908419/)

58. Почему не следует применять `auto`, если тип неочевиден из контекста инициализации?

   **Ответ:** Это заставляет рецензента или сопровождающего разработчика тратить ресурсы на прыжки по кодовой базе и работу в роли статического анализатора ради базового понимания логики.
   **Пример:**
   ```cpp
   // Плохо: непонятно, что возвращает query
   auto result = db.query(raw_sql);

   ```


   **Типичная ошибка:** Использование Everywhere Auto («AAA style») без оглядки на читаемость в отрыве от тяжелых IDE.
   **Источник:** [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html)

59. В каких ситуациях явное указание типа приносит больше пользы, чем `auto`?

   **Ответ:** При необходимости принудительного преобразования к определенной разрядности (`uint64_t`), для фиксации интерфейсного контракта в сигнатурах и для избежания неожиданных неявных приведений к `int`.
   **Пример:**
   ```cpp
   // Явно задаем необходимый тип для исключения переполнения:
   uint64_t total_bytes = compute_size();

   ```


   **Типичная ошибка:** Написание `auto x = 0;`, из-за чего выводится знаковый `int` вместо нужного `size_t` или `double`.
   **Источник:** [C++ Core Guidelines: ES.20](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#es20-always-initialize-an-object)

60. Почему спецификатор `const` следует применять повсеместно, но осмысленно?

   **Ответ:** `const` документирует неизменяемость состояния для программиста и компилятора, предотвращает случайные сайд-эффекты и делает многопоточный доступ безопасным без использования блокировок.
   **Пример:**
   ```cpp
   const auto timeout = std::chrono::seconds(5);

   ```


   **Типичная ошибка:** Игнорирование const-correctness на ранних этапах, что приводит к лавинообразным ошибкам компиляции при попытке передать объект по константной ссылке.
   **Источник:** [C++ Core Guidelines: Con.1](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#con1-by-default-make-objects-immutable)

61. Что обеспечивает модификатор `const` с точки зрения читаемости и безопасности?

   **Ответ:** Он создает четкий контракт: читающий код уверен, что переменная или объект не изменит свое значение после инициализации, а компилятор блокирует любые несанкционированные мутации.
   **Пример:**
   ```cpp
   void render(const Scene& scene); // scene гарантированно не изменится

   ```


   **Типичная ошибка:** Использование `const_cast` для снятия константности ради вызова непродуманного стороннего метода.
   **Источник:** [C++ Core Guidelines: Con.2](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#con2-by-default-make-member-functions-const)

62. Почему парадигма «все сущности изменяемы (`mutable`) по умолчанию» считается антипаттерном?

   **Ответ:** Неконтролируемая изменяемость размывает жизненный цикл сущностей, многократно усложняет отладку и поиск места возникновения дефекта, а также лишает компилятор шансов на глубокую оптимизацию регистров.
   **Пример:** Переменная, переприсваиваемая 10 раз в течение 200 строк функции, делает невозможным локальное доказательство ее корректности.
   **Типичная ошибка:** Оставлять неконстантными переменные, значение которых рассчитывается единожды при старте функции.
   **Источник:** [A Philosophy of Software Design (John Ousterhout)](https://web.stanford.edu/~ouster/cgi-bin/book.php)

63. Какую роль играет спецификатор `constexpr` в формировании надежного стиля кода?

   **Ответ:** Он переносит валидацию и сложные вычисления на этап компиляции, превращая потенциальные падения во время исполнения (runtime crashes) в немедленные ошибки сборки программы.
   **Пример:**
   ```cpp
   constexpr size_t calculate_buffer(size_t n) { return n * 64; }

   ```


   **Типичная ошибка:** Замена `constexpr` макросами препроцессора, не имеющими типизации и игнорирующими пространства имен.
   **Источник:** [Cppreference: constexpr specifier](https://en.cppreference.com/w/cpp/language/constexpr)

64. Когда применение `constexpr` оправдано, а когда оно избыточно усложняет архитектуру?

   **Ответ:** Оно отлично подходит для конфигураций, математических констант, таблиц поиска и метапрограммирования, но избыточно усложняет код, если логика требует сложного ввода-вывода или заставляет разработчика писать вычурные конструкции без реальной выгоды по производительности.
   **Пример:** Таблица синусов на этапе компиляции — хорошо; попытка загнать всю логику обработки сетевых пакетов в `constexpr` — оверинжиниринг.
   **Типичная ошибка:** Превращение прямолинейного рантайм-кода в запутанные шаблоны только ради того, чтобы выполнить его во время компиляции без профилирования.
   **Источник:** [C++ Core Guidelines: F.4](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#f4-if-a-function-might-have-to-be-evaluated-at-compile-time-declare-it-constexpr)

65. Почему строго типизированный `enum class` предпочтительнее обычного `enum`?

   **Ответ:** Он изолирует имена значений в собственном скоупе (не засоряет внешнее пространство имен) и запрещает неявные опасные приведения к целочисленным типам (`int`).
   **Пример:**
   ```cpp
   enum class Status { Ok, Error };
   Status s = Status::Ok; // Status::Ok не спутается с глобальным Ok

   ```


   **Типичная ошибка:** Сравнение двух нетипизированных enum из разных доменов (`Color::Red == Alert::High`), которое успешно компилируется из-за неявного приведения к `int`.
   **Источник:** [C++ Core Guidelines: Enum.3](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#enum3-prefer-class-enums-over-plain-enums)

66. Почему литерал `nullptr` надежнее констант `NULL` и `0`?

   **Ответ:** `nullptr` имеет собственный тип `std::nullptr_t`, что предотвращает коллизии при перегрузке функций между указателями и целочисленными типами данных.
   **Пример:**
   ```cpp
   void handle(int);
   void handle(char*);

   handle(nullptr); // Однозначно вызовет handle(char*)
   // handle(NULL); // Может вызвать handle(int) или дать ошибку неоднозначности

   ```


   **Типичная ошибка:** Передача `0` в интерфейсы ожидающие сырой или умный указатель.
   **Источник:** [C++ Core Guidelines: ES.47](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#es47-use-nullptr-rather-than-0-or-null)

67. Почему синтаксис `using` удобнее устаревшего `typedef`?

   **Ответ:** `using` обладает логичным порядком записи «имя = значение», единообразен с инициализацией и напрямую поддерживает параметризацию шаблонами (alias templates).
   **Пример:**
   ```cpp
   template <typename T>
   using StringMap = std::unordered_map<std::string, T>;

   ```


   **Типичная ошибка:** Попытка эмулировать шаблонные алиасы через громоздкие обертки со структурами внутри `typedef`.
   **Источник:** [C++ Core Guidelines: T.43](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#t43-prefer-using-over-typedef-for-defining-aliases)

68. В каких случаях оправдано использование `using` для создания алиасов типов?

   **Ответ:** Для сокращения многоуровневых типов STL, абстрагирования платформозависимых структур и фиксации общепринятых интерфейсных соглашений в рамках библиотеки.
   **Пример:**
   ```cpp
   using PacketId = uint32_t;
   using Callbacks = std::vector<std::function<void(Status)>>;

   ```


   **Типичная ошибка:** Создание алиасов ради алиасов на базовые типы (`using Number = int;`), засоряющих пространство имен без внесения дополнительного контекста.
   **Источник:** [Google C++ Style Guide: Aliases](https://google.github.io/styleguide/cppguide.html#Type_Aliases)

69. Что представляет собой практика strong type aliasing и как она улучшает дизайн?

   **Ответ:** Это создание легковесных типов-оберток над базовыми сущностями для изоляции их на уровне компилятора, чтобы значения из разных доменов нельзя было случайно перепутать.
   **Пример:**
   ```cpp
   struct Meter { double val; };
   struct Second { double val; };
   void set_speed(Meter m, Second s);

   ```


   **Типичная ошибка:** Использование сырого `double` для всех физических величин, что часто ведет к передаче координат или единиц времени в обратном порядке.
   **Источник:** [Fluent C++: Strong Types for Strong Interfaces](https://www.fluentcpp.com/2016/12/08/strong-types-for-strong-interfaces/)

70. Почему объявление `typedef int UserId;` не гарантирует реальной типобезопасности?

   **Ответ:** `typedef` и `using` создают лишь синоним (псевдоним) типа, а не новый изолированный тип; для компилятора `UserId` и `int` остаются абсолютно эквивалентными и взаимозаменяемыми.
   **Пример:**
   ```cpp
   using UserId = int;
   using OrderId = int;
   UserId u = 10;
   OrderId o = u; // Спокойно компилируется, безопасность не обеспечена!

   ```


   **Типичная ошибка:** Предположение, что псевдоним защитит от случайной передачи идентификатора пользователя вместо идентификатора заказа в функцию.
   **Источник:** [C++ Core Guidelines: Type.1](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#type1-dont-use-type-aliases-for-types-that-should-be-distinct)

71. Когда необходимо заменять примитивный `int` отдельной структурой или классом?

   **Ответ:** Когда значение имеет строгие границы валидности, специфическую размерность, логические ограничения предметной области или может быть случайно перепутано с другими числовыми сущностями.
   **Пример:**
   ```cpp
   struct Port {
       explicit Port(int val) : value{val} {
           if (val < 1 || val > 65535) throw std::invalid_argument("Bad port");
       }
       int value;
   };

   ```


   **Типичная ошибка:** Передача кортежей из пяти целых чисел `process(1, 404, 100, 20, 0)` без типизации.
   **Источник:** [C++ Core Guidelines: I.4](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#i4-make-interfaces-strongly-typed)

72. Почему булевы аргументы ухудшают читаемость вызова функции?

   **Ответ:** В месте вызова литералы `true` и `false` полностью анонимны: без обращения к заголовочному файлу невозможно понять, на что именно они влияют.
   **Пример:**
   ```cpp
   // Что означает true, а что false?
   window.resize(800, 600, true, false);

   ```


   **Типичная ошибка:** Добавление очередного булева флага в конец существующего метода для переключения режима работы.
   **Источник:** [Clean Code (Robert C. Martin)](https://www.oreilly.com/library/view/clean-code-a/9780136083238/)

73. В чём заключается фундаментальный недостаток вызова `openFile(path, true, false)`?

   **Ответ:** Сигнатура страдает отсутствием выразительности (call-site opacity): читатель вынужден угадывать, значат ли флаги режим чтения, перезапись, создание файла или буферизацию.
   **Пример:**
   ```cpp
   // Непонятно:
   open_file("log.txt", true, false);
   // Понятно:
   open_file("log.txt", OpenMode::ReadOnly, CachePolicy::Disabled);

   ```


   **Типичная ошибка:** Исправление таких вызовов комментариями `/*is_append=*/true` вместо улучшения самого интерфейса.
   **Источник:** [C++ Core Guidelines: I.4](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#i4-make-interfaces-strongly-typed)

74. Чем специализированные enum-параметры превосходят булевы флаги?

   **Ответ:** Они явно самодокументируют код в месте вызова, исключают путаницу флагов местами и позволяют расширять набор состояний без поломки сигнатуры.
   **Пример:**
   ```cpp
   enum class Truncate { Yes, No };
   void save(std::string_view path, Truncate truncate);

   ```


   **Типичная ошибка:** Создание функции с тремя последовательными параметрами типа `bool`, которые легко перепутать при передаче.
   **Источник:** [C++ Core Guidelines: I.4](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#i4-make-interfaces-strongly-typed)

75. Почему длинный список аргументов функции является тревожным сигналом (code smell)?

   **Ответ:** Это признак размытой ответственности функции (нарушение SRP), сильной связности с окружающим кодом и повышенной вероятности передачи параметров в ошибочном порядке.
   **Пример:** Сигнатура с 7–8 параметрами свидетельствует о том, что функция выполняет слишком много сценариев одновременно.
   **Типичная ошибка:** Непрерывное расширение списка параметров метода новыми необязательными аргументами по мере роста требований.
   **Источник:** [Refactoring: Long Parameter List (Martin Fowler)](https://refactoring.guru/smells/long-parameter-list)

76. В каких ситуациях набор параметров целесообразно объединить в структуру настроек (Parameter Object)?

   **Ответ:** Когда группа параметров логически связана, часто передается вместе между несколькими подсистемами или когда количество аргументов функции превышает 3–4 штуки.
   **Пример:**
   ```cpp
   struct ConnectionOptions {
       std::string host;
       int port = 8080;
       std::chrono::seconds timeout{5};
   };
   void connect(const ConnectionOptions& options);

   ```


   **Типичная ошибка:** Передача отдельных разрозненных параметров `ip`, `port`, `retry_count`, `timeout` через 5 уровней абстракций подряд.
   **Источник:** [Refactoring: Introduce Parameter Object (Martin Fowler)](https://refactoring.guru/introduce-parameter-object)

77. Что понимают под input, output и in-out параметрами функции?

   **Ответ:** Input — параметры, только читаемые функцией (по значению или `const&`); Output — неинициализированные переменные, заполняемые функцией для возврата наружу (неконстантные ссылки или сырые указатели); In-Out — входящие данные, модифицируемые внутри и возвращаемые в измененном виде.
   **Пример:**
   ```cpp
   void process(const Input& in,    // input
                Output& out,        // output (устаревший стиль)
                State& state);      // in-out

   ```


   **Типичная ошибка:** Использование output-параметров для сущностей, которые тривиально возвращаются через оператор `return`.
   **Источник:** [C++ Core Guidelines: F.15](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#f15-prefer-simple-and-conventional-ways-of-passing-information)

78. Почему output-параметры ухудшают чистоту интерфейса?

   **Ответ:** Они ломают естественный поток данных (выражения нельзя вкладывать в пайплайны), запрещают декларативный стиль инициализации через `const` и заставляют объявлять неинициализированные пустышки до вызова.
   **Пример:**
   ```cpp
   // Неудобно:
   Data d;
   get_data(&d);
   // Намного чище:
   const auto d = get_data();

   ```


   **Типичная ошибка:** Применение выходных параметров по старой привычке из чистого C ради «экономии на копировании», игнорируя современные move-семантику и RVO.
   **Источник:** [C++ Core Guidelines: F.20](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#f20-for-out-output-values-prefer-return-values-to-output-parameters)

79. Когда предпочтительнее возвращать результат через `return`, а не через параметр?

   **Ответ:** Практически всегда. Благодаря Return Value Optimization (RVO) и гарантированному copy elision в C++17, возврат по значению бесплатен по накладным расходам и максимально выразителен.
   **Пример:**
   ```cpp
   std::vector<int> generate_data() {
       std::vector<int> res;
       // наполнение...
       return res; // RVO или Move: нет дорогого копирования
   }

   ```


   **Типичная ошибка:** Ручная передача неконстантной ссылки на вектор в метод ради мнимой производительности.
   **Источник:** [C++ Core Guidelines: F.20](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#f20-for-out-output-values-prefer-return-values-to-output-parameters)

80. В каких редких случаях использование выходного параметра остаётся оправданным?

   **Ответ:** При необходимости повторного использования уже выделенного тяжелого буфера в высоконагруженных циклах (zero-allocation hot loops) или при интеропе с C-библиотеками.
   **Пример:**
   ```cpp
   // Переиспользование аллоцированной памяти вектора между итерациями:
   void read_chunk(std::vector<char>& preallocated_buffer);

   ```


   **Типичная ошибка:** Использование таких микрооптимизаций вне критических путей выполнения и без предварительного профилирования.
   **Источник:** [C++ Core Guidelines: F.20](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#f20-for-out-output-values-prefer-return-values-to-output-parameters)

81. Почему возврат нескольких значений через `struct` лучше передачи нескольких ссылок?

   **Ответ:** Это четко объединяет результат в единую именованную сущность, позволяет вызывающему коду использовать structured binding (`auto [x, y] = ...`) и гарантирует атомарную инициализацию констант.
   **Пример:**
   ```cpp
   struct ParseResult { bool success; int value; };
   ParseResult parse(std::string_view s);

   ```


   **Типичная ошибка:** Возврат значений через `std::tuple` или `std::pair`, где поля `.first` и `.second` анонимны и легко путаются местами.
   **Источник:** [C++ Core Guidelines: F.21](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#f21-to-return-multiple-out-values-prefer-returning-a-struct-or-tuple)

82. Почему `std::optional` предпочтительнее искусственных сигнальных значений (sentinel values)?

   **Ответ:** Значения-маркеры (вроде `-1`, `nullptr` или пустой строки `""`) легко пропустить или счесть валидными данными; `std::optional` делает факт возможного отсутствия значения частью системы типов.
   **Пример:**
   ```cpp
   // Понятно, что результат может отсутствовать:
   std::optional<User> find_user(int id);

   ```


   **Типичная ошибка:** Возврат `-1` при поиске индекса и отсутствие проверки в клиентском коде, ведущее к `out_of_range`.
   **Источник:** [Cppreference: std::optional](https://en.cppreference.com/w/cpp/utility/optional)

83. Когда применение `std::optional` делает API более надежным и прозрачным?

   **Ответ:** В операциях поиска, парсинга или извлечения значений из словарей/кэшей, когда отсутствие данных — это штатная ситуация, а не аварийная исключительная ошибка системы.
   **Пример:**
   ```cpp
   std::optional<int> parse_int(std::string_view str);

   ```


   **Типичная ошибка:** Использование `std::optional` для возврата детальной информации об ошибке вместо `std::expected` (C++23) или выброса исключений.
   **Источник:** [C++ Core Guidelines: I.30](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#i30-express-preconditions-without-checking-at-runtime)

84. Почему `std::variant` превосходит ручные union-схемы и флаги состояний?

   **Ответ:** `std::variant` является типобезопасным размеченным объединением (type-safe tagged union): он знает активный тип, корректно вызывает конструкторы/деструкторы нетривиальных объектов и защищает от ошибочного чтения неактивного поля.
   **Пример:**
   ```cpp
   using Response = std::variant<SuccessPayload, ErrorCode>;

   ```


   **Типичная ошибка:** Использование сырого C-style `union` с ручным сохранением текущего тега в соседнем поле структуры.
   **Источник:** [Cppreference: std::variant](https://en.cppreference.com/w/cpp/utility/variant)

85. Когда `std::string_view` улучшает проектирование интерфейса?

   **Ответ:** Когда функции нужен доступ к строке только на чтение: он позволяет принимать без аллокаций строковые литералы, `std::string` и подстроки.
   **Пример:**
   ```cpp
   void log_message(std::string_view msg); // 0 аллокаций памяти

   ```


   **Типичная ошибка:** Прием `const std::string&` там, где часто передаются строковые литералы `"text"`, что порождает лишние временные аллокации в куче.
   **Источник:** [C++ Core Guidelines: F.24](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#f24-use-a-stdstring_view-or-a-gslstring_span-to-refer-to-a-character-sequence)

86. Почему при работе со `std::string_view` критически важно контролировать lifetime?

   **Ответ:** `std::string_view` не владеет данными, а лишь ссылается на них. Если владеющий буфер или временный объект `std::string` уничтожается, `string_view` превращается в висячий указатель (dangling reference).
   **Пример:**
   ```cpp
   // Опасный антипаттерн:
   std::string_view get_sub() {
       return std::string("temporary"); // UB! Временный объект погибнет на выходе
   }

   ```


   **Типичная ошибка:** Сохранение `std::string_view` в долгоживущие поля классов или асинхронные очереди задач.
   **Источник:** [C++ Core Guidelines: ES.84](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#es84-dont-try-to-declare-a-local-variable-with-the-same-name-as-an-already-declared-variable)

87. В каких случаях `std::span` является лучшим выбором для параметров функций?

   **Ответ:** Для передачи непрерывных последовательностей данных на чтение или запись (массивы, `std::vector`, `std::array`) без привязки к конкретному контейнеру и без копирования.
   **Пример:**
   ```cpp
   void process_samples(std::span<const float> samples);

   ```


   **Типичная ошибка:** Жесткая фиксация интерфейса на `const std::vector<float>&`, блокирующая возможность передать сырой C-массив или `std::array`.
   **Источник:** [Cppreference: std::span](https://en.cppreference.com/w/cpp/container/span)

88. Почему работа с невладеющими типами (`span`, `string_view`, сырые указатели) требует повышенной дисциплины?

   **Ответ:** Любая асинхронная задача или переаллокация базового контейнера инвалидирует ссылки, приводя к трудноуловимым падениям памяти (use-after-free).
   **Пример:** Добавление элементов в `std::vector` может вызвать его реаллокацию в памяти, мгновенно превратив ранее созданный `std::span` в невалидный указатель.
   **Типичная ошибка:** Возврат невладеющих типов из функций, генерирующих данные динамически.
   **Источник:** [C++ Core Guidelines: Lifetimes](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#lifetime-safety)

89. Почему стандартная библиотека предпочтительнее самописных решений?

   **Ответ:** Алгоритмы и контейнеры STL протестированы миллионами разработчиков, оптимизированы под целевые архитектуры, гарантируют соблюдение требований к сложности и знакомы каждому инженеру из коробки.
   **Пример:** `std::sort` использует гибридный Introsort с защитой от худшего времени $O(N^2)$, превосходя средний самописный quicksort.
   **Типичная ошибка:** Реализация собственных кольцевых очередей и односвязных списков без замеров реальной пользы.
   **Источник:** [C++ Core Guidelines: P.8](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#p8-prefer-the-standard-library-to-other-libraries-and-to-handcrafted-code)

90. Когда разработка собственной реализации контейнера или утилиты становится оправданной?

   **Ответ:** В специфических нишах: жесткий real-time с нулевыми аллокациями, экстремально низкая задержка (HFT), узкоспециализированные структуры данных (B-tree, lock-free очереди) или встраиваемые системы без поддержки исключений и runtime.
   **Пример:** Разработка flat-map на базе отсортированного массива для кэш-локального поиска среди 10 элементов.
   **Типичная ошибка:** Написание кастомного контейнера без тщательного профилирования и тестов на утечки памяти.
   **Источник:** [Electronic Arts Standard Template Library (EASTL)](https://github.com/electronicarts/EASTL)

91. Почему стандартные алгоритмы STL лучше ручных циклов?

   **Ответ:** Они явно сообщают о намерении алгоритма (`std::all_of`, `std::transform`), избавляют от ручной работы с индексами и граничными условиями и потенциально поддерживают параллельное исполнение.
   **Пример:**
   ```cpp
   // Сразу видна суть операции:
   bool all_positive = std::all_of(v.begin(), v.end(), [](int x) { return x > 0; });

   ```


   **Типичная ошибка:** Написание пятистрочного вложенного цикла со счетчиками и прерываниями `break` вместо лаконичного вызова `std::find`.
   **Источник:** [C++ Core Guidelines: Alg.1](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#alg1-prefer-standard-algorithms-over-handcrafted-loops)

92. Что делает код более понятным: `std::find_if` или рукописный цикл поиска?

   **Ответ:** `std::find_if` декларирует намерение поиска сразу в названии функции, исключая чтение тела цикла и анализ условий остановки и мутации итератора.
   **Пример:**
   ```cpp
   auto it = std::find_if(users.begin(), users.end(), is_admin);

   ```


   **Типичная ошибка:** Ручной перебор с временными булевыми флагами (`bool found = false; for(...) if(...) { found = true; break; }`).
   **Источник:** [Cppreference: std::find_if](https://en.cppreference.com/w/cpp/algorithm/find)

93. Почему range-based `for` предпочтительнее классической итерации по индексам?

   **Ответ:** Он предотвращает ошибки смещения на единицу (off-by-one errors), выход за пределы массива и избавляет от необходимости вычислять длину контейнера.
   **Пример:**
   ```cpp
   for (const auto& item : items) {
       item.process();
   }

   ```


   **Типичная ошибка:** Ошибка в знаке `<` или `<=` при классическом цикле `for (size_t i = 0; i <= v.size(); ++i)`.
   **Источник:** [C++ Core Guidelines: ES.71](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#es71-prefer-a-range-for-statement-to-a-for-statement-when-there-is-a-choice)

94. В каких ситуациях явный доступ по индексу всё же необходим?

   **Ответ:** Когда значение индекса непосредственно участвует в бизнес-логике (шаг алгоритма, параллельный доступ к двум синхронным массивам) или требуется сложная навигация по шагам (пропуск элементов, движение назад).
   **Пример:**
   ```cpp
   for (size_t i = 0; i < size; ++i) {
       result[i] = input_a[i] + input_b[i];
   }

   ```


   **Типичная ошибка:** Использование индексов там, где достаточно обычного чтения элементов подряд.
   **Источник:** [C++ Core Guidelines: ES.72](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#es72-prefer-a-range-for-statement-to-a-for-statement-when-there-is-a-choice)

95. Чем `std::array` превосходит сырой C-style массив?

   **Ответ:** `std::array` хранит свой размер, не деградирует (decay) самопроизвольно в указатель при передаче в функцию, поддерживает интерфейс STL (итераторы) и копируется как value-тип.
   **Пример:**
   ```cpp
   std::array<int, 4> arr = {1, 2, 3, 4};
   // arr.size() всегда доступен, нет затирания в int*

   ```


   **Типичная ошибка:** Использование `sizeof(c_arr) / sizeof(c_arr[0])` внутри функций, куда массив уже передался как указатель.
   **Источник:** [C++ Core Guidelines: SL.con.2](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#slcon2-prefer-using-stdarray-or-stdvector-instead-of-a-c-array)

96. Почему `std::vector` считается универсальным контейнером по умолчанию?

   **Ответ:** Данные вектора размещены в непрерывном блоке памяти (contiguity), что дает идеальную локальность данных в процессорном кэше (L1/L2/L3) и делает обход вектора быстрее любых списков даже при вставке в середину для умеренных размеров.
   **Пример:**
   ```cpp
   std::vector<int> numbers; // Компактное кэш-дружелюбное хранение

   ```


   **Типичная ошибка:** Выбор списков или деревьев без замеров производительности на реальных размерах данных.
   **Источник:** [C++ Core Guidelines: SL.con.1](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#slcon1-prefer-using-stl-vector-by-default)

97. Почему `std::list` на практике используется значительно реже, чем предполагают новички?

   **Ответ:** Каждый элемент двусвязного списка требует отдельной аллокации в куче и накладных расходов на указатели, а хаотичное размещение нод в памяти вызывает постоянные промахи кэша процессора (cache misses).
   **Пример:** Линейный поиск в векторе на 10 000 элементов часто в разы быстрее поиска в `std::list` из-за аппаратного prefetching процессора.
   **Типичная ошибка:** Использование `std::list` «ради быстрой вставки в середину за $O(1)$», забывая, что поиск места этой вставки стоит $O(N)$ медленных переходов по указателям.
   **Источник:** [Bjarne Stroustrup: Why you should avoid Linked Lists](https://www.youtube.com/watch?v=YQs6IC-vgmo)

98. Почему выбор структуры данных «по привычке» является антипаттерном?

   **Ответ:** Неправильно подобранный контейнер может изменить алгоритмическую сложность критического пути с $O(1)$ до $O(N)$ или спровоцировать фрагментацию памяти и деградацию производительности всей системы.
   **Пример:** Использование `std::map` там, где нет необходимости в упорядоченности и достаточно `std::unordered_map` с доступом в среднем за $O(1)$.
   **Типичная ошибка:** Повсеместное применение `std::set` вместо сортированного `std::vector` для неизменяемых наборов данных.
   **Источник:** [Effective STL (Scott Meyers)](https://www.oreilly.com/library/view/effective-stl-50/0201749629/)

99. Что означает принцип «выбора контейнера на основе паттерна доступа»?

   **Ответ:** Это подбор структуры данных под преобладающие сценарии использования: частоту вставок/удалений, необходимость произвольного доступа по индексу, стабильность итераторов и требования к потреблению памяти.
   **Пример:** Если данные пишутся один раз при старте, а затем только читаются — идеален отсортированный `std::vector` с бинарным поиском, а не дерево или хеш-таблица.
   **Типичная ошибка:** Ориентация только на теоретическую асимптотику Big-O без учета аппаратных особенностей современного "железа" (memory hierarchy).
   **Источник:** [C++ Core Guidelines: SL.con.3](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#slcon3-choose-containers-based-on-performance-needs)

100. Почему best practices в разработке всегда привязаны к конкретному контексту задачи?

   **Ответ:** Универсальных решений не существует: требования к экстремальной задержке (HFT), критической безопасности (авионика), минимальному энергопотреблению (встраиваемые чипы) или простоте серверного API прямо противоречат друг другу.
   **Пример:** RAII и исключения являются базовым стандартом в десктопном и серверном коде, но жестко ограничиваются в ядрах операционных систем или микроконтроллерах без кучи.
   **Типичная ошибка:** Догматическое внедрение практик без понимания ограничений целевой архитектуры и бизнес-требований.
   **Источник:** [C++ Core Guidelines: Philosophy](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#p-philosophy)

## Средний уровень


101. Почему RAII считается одной из главных best practices в C++?

   **Ответ:** RAII (*Resource Acquisition Is Initialization*) связывает жизненный цикл системного ресурса со временем жизни объекта в автоматической памяти (на стеке): ресурс захватывается в конструкторе и гарантированно освобождается в деструкторе, предотвращая утечки даже при возникновении исключений.

   **Пример:**

   ```cpp
   void process_file() {
       std::ifstream file("data.txt"); // Ресурс открыт
       // При выходе из блока или выбросе исключения деструктор file сам закроет дескриптор
   }
   ```

   **Типичная ошибка:** Ручное освобождение ресурсов в конце функции (`file.close()`), которое пропускается при раннем `return` или выбросе исключения.

   **Источник:** [Cppreference: RAII](https://en.cppreference.com/w/cpp/language/raii)

102. Что такое владение ресурсом и почему его нужно выражать явно?

   **Ответ:** Владение ресурсом — это обязанность конкретной сущности (объекта или скоупа) управлять его жизненным циклом и своевременно освободить. Явное выражение владения через систему типов исключает утечки ресурсов и ошибки повторного освобождения (*double free*).

   **Пример:**

   ```cpp
   // Явное монопольное владение:
   std::unique_ptr<Widget> create_widget();
   ```

   **Типичная ошибка:** Возврат сырого указателя `Widget*` из фабричной функции, из-за чего вызывающему коду неизвестно, нужно ли вызывать `delete`.

   **Источник:** [C++ Core Guidelines: R.1](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#r1-manage-resources-automatically-using-resource-handles-and-raii-resource-acquisition-is-initialization)

103. Почему сырых вызовов `new` и `delete` обычно избегают в прикладном коде?

   **Ответ:** Ручное управление памятью нарушает гарантии безопасности исключений (*exception safety*) и легко приводит к утечкам или висячим указателям при ветвлении логики программы.

   **Пример:**

   ```cpp
   // Предпочтительный современный подход:
   auto item = std::make_unique<Item>();
   ```

   **Типичная ошибка:** Написание пары `Item* p = new Item(); ... delete p;`, где между ними вызывается функция, способная выбросить исключение.

   **Источник:** [C++ Core Guidelines: R.11](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#r11-avoid-calling-new-and-delete-explicitly)

104. В каких случаях прямой вызов `new` всё же может быть оправдан?

   **Ответ:** При реализации низкоуровневых структур данных, нестандартных аллокаторов памяти или при использовании *placement new* для создания объекта в предварительно выделенном буфере.

   **Пример:**

   ```cpp
   alignas(Widget) std::byte buffer[sizeof(Widget)];
   Widget* w = new (buffer) Widget(); // Placement new
   w->~Widget();                      // Явный вызов деструктора
   ```

   **Типичная ошибка:** Использование сырого `new` в обычном прикладном коде для создания объектов, передаваемых между функциями.

   **Источник:** [Cppreference: new expression](https://en.cppreference.com/w/cpp/language/new)

105. Почему `std::unique_ptr` часто является лучшим умным указателем по умолчанию?

   **Ответ:** Он обеспечивает строгое монопольное владение с нулевыми накладными расходами по памяти и скорости (*zero-cost abstraction*), полностью совпадая по характеристикам с сырым указателем.

   **Пример:**

   ```cpp
   std::unique_ptr<Session> session = std::make_unique<Session>();
   ```

   **Типичная ошибка:** Использование `std::shared_ptr` там, где время жизни объекта укладывается в границы одного владельца.

   **Источник:** [C++ Core Guidelines: R.20](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#r20-use-unique_ptr-or-shared_ptr-to-represent-ownership)

106. Почему `std::shared_ptr` не стоит использовать «на всякий случай»?

   **Ответ:** Он требует создания контрольного блока (*control block*) и выполнения атомарных операций инкремента/декремента при каждом копировании, что снижает производительность и скрывает границы владения.

   **Пример:** Передача `std::shared_ptr<T>` по значению во внутренние вспомогательные функции вместо передачи `const T&`.

   **Типичная ошибка:** Попытка скрыть запутанную архитектуру жизненного цикла программы с помощью бесконтрольного разделения владения.

   **Источник:** [C++ Core Guidelines: R.21](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#r21-prefer-unique_ptr-over-shared_ptr-unless-you-need-to-share-ownership)

107. Какие проблемы создаёт неразборчивое использование `shared_ptr`?

   **Ответ:** Оно делает время жизни объектов недетерминированным, усложняет многопоточную отладку, может приводить к скрытому удержанию тяжелых ресурсов и рискам циклических ссылок.

   **Пример:** Забытая лямбда в очереди задач, захватившая `std::shared_ptr`, удерживает весь сервис в памяти после его закрытия.

   **Типичная ошибка:** Принятие решения о разделении владения вместо выбора одного четкого хозяина ресурса.

   **Источник:** [Modern Effective C++: Item 19 (Scott Meyers)](https://www.oreilly.com/library/view/effective-modern-c/9781491908419/)

108. Почему циклическое владение через `shared_ptr` опасно?

   **Ответ:** Взаимные ссылки двух объектов друг на друга удерживают счетчик ссылок выше нуля, из-за чего деструкторы никогда не вызываются, приводя к утечке памяти всей замкнутой структуры.

   **Пример:**

   ```cpp
   struct Node {
       std::shared_ptr<Node> next;
       std::shared_ptr<Node> prev; // Цикл: счетчик никогда не станет 0
   };
   ```

   **Типичная ошибка:** Попытка связать родительские и дочерние узлы дерева исключительно через `std::shared_ptr`.

   **Источник:** [Cppreference: std::shared_ptr](https://en.cppreference.com/w/cpp/memory/shared_ptr)

109. В каких ситуациях необходим `std::weak_ptr`?

   **Ответ:** Когда нужно ссылаться на объект, управляемый `std::shared_ptr`, без продления его времени жизни: для разрыва циклических связей, в кэшах и при реализации паттерна *Observer*.

   **Пример:**

   ```cpp
   struct Node {
       std::shared_ptr<Node> child;
       std::weak_ptr<Node> parent; // Не продлевает жизнь родителю
   };
   ```

   **Типичная ошибка:** Разыменование `std::weak_ptr` напрямую без предварительного получения `std::shared_ptr` через метод `.lock()`.

   **Источник:** [Cppreference: std::weak_ptr](https://en.cppreference.com/w/cpp/memory/weak_ptr)

110. Что такое Rule of Zero и почему оно считается хорошей практикой?

   **Ответ:** Это подход, согласно которому класс, не управляющий ресурсами напрямую, не должен явно объявлять деструктор, конструкторы копирования/перемещения и операторы присваивания, делегируя это стандартным полям (`std::string`, `std::vector`).

   **Пример:**

   ```cpp
   struct User {
       std::string name;
       std::vector<int> scores;
       // Никаких явных деструкторов и конструкторов копирования
   };
   ```

   **Типичная ошибка:** Объявление пустого виртуального деструктора в обычном значении-классе (*value type*), что блокирует автоматическую генерацию move-операций.

   **Источник:** [Cppreference: Rule of three/five/zero](https://en.cppreference.com/w/cpp/language/rule_of_three)

111. Почему для классов без прямого владения ресурсами не стоит писать special member functions вручную?

   **Ответ:** Ручное объявление любой из этих функций отключает или изменяет правила неявной генерации остальных (например, ручной деструктор подавляет неявный move-конструктор), делая класс менее эффективным.

   **Пример:** Добавление `~Class() = default;` отключает компиляторный move-конструктор, возвращая класс к неявному копированию.

   **Типичная ошибка:** Дублирование кода стандартных конструкторов и операторов присваивания вручную вместо `= default;` или их отсутствия.

   **Источник:** [C++ Core Guidelines: C.20](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#c20-if-you-can-avoid-defining-default-operations-do)

112. Когда Правило трёх / пяти действительно необходимо применять?

   **Ответ:** Когда класс непосредственно управляет системным хэндлом, сырой памятью или нестандартным ресурсом и нуждается в явной реализации логики освобождения и дублирования.

   **Пример:**

   ```cpp
   class RawBuffer {
       int* data_;
   public:
       ~RawBuffer();
       RawBuffer(const RawBuffer&);
       RawBuffer& operator=(const RawBuffer&);
       RawBuffer(RawBuffer&&) noexcept;
       RawBuffer& operator=(RawBuffer&&) noexcept;
   };
   ```

   **Типичная ошибка:** Реализация деструктора и конструктора копирования с пропуском оператора присваивания копированием.

   **Источник:** [C++ Core Guidelines: C.21](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#c21-if-you-define-or-delete-any-copy-move-or-destructor-function-define-or-delete-them-all)

113. Почему класс должен либо владеть ресурсом, либо не заниматься владением вовсе?

   **Ответ:** Смешивание управления ресурсами с бизнес-логикой нарушает принцип единственной ответственности (*Single Responsibility Principle*) и кратно усложняет обеспечение гарантий безопасности исключений.

   **Пример:** Класс `OrderProcessor` должен агрегировать готовые `std::ofstream` или `std::unique_ptr<Database>`, а не выделять память через `malloc` и вручную закрывать сокеты в деструкторе.

   **Типичная ошибка:** Помещение логики парсинга данных и сырых вызовов Win32/POSIX API внутрь одного класса.

   **Источник:** [C++ Core Guidelines: C.31](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#c31-all-resources-acquired-by-a-class-must-be-released-by-the-classs-destructor)

114. Что представляет собой single responsibility для класса-владельца ресурса?

   **Ответ:** Единственной задачей такого класса является изоляция жизненного цикла ресурса: правильное получение при конструировании, корректный перенос/копирование и своевременное освобождение при разрушении.

   **Пример:** `std::unique_ptr` отвечает только за память одного объекта и не берет на себя логику работы с самими данными объекта.

   **Типичная ошибка:** Добавление бизнес-методов обработки полезной нагрузки прямо в низкоуровневую обертку дескриптора сокета.

   **Источник:** [Clean Code (Robert C. Martin)](https://www.oreilly.com/library/view/clean-code-a/9780136083238/)

115. Почему композиция обычно предпочтительнее наследования?

   **Ответ:** Композиция сохраняет слабую связность (*loose coupling*), защищает внутреннее состояние от вмешательства извне и позволяет легко менять реализацию во время выполнения без ломки интерфейса.

   **Пример:**

   ```cpp
   class Car {
       Engine engine_; // Композиция вместо class Car : public Engine
   };
   ```

   **Типичная ошибка:** Использование наследования только для получения доступа к методам другого класса.

   **Источник:** [Design Patterns (GoF): Favor object composition over class inheritance](https://en.wikipedia.org/wiki/Design_Patterns)

116. В каких случаях наследование в C++ действительно уместно?

   **Ответ:** Для создания полиморфных иерархий, работающих через динамическую диспетчеризацию чистых интерфейсов (*runtime polymorphism*), либо для статического полиморфизма (CRTP).

   **Пример:**

   ```cpp
   class IRenderer {
   public:
       virtual ~IRenderer() = default;
       virtual void draw() = 0;
   };
   ```

   **Типичная ошибка:** Создание многоуровневых ветвистых деревьев классов с глубоким наследованием конкретной реализации.

   **Источник:** [C++ Core Guidelines: C.120](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#c120-use-class-hierarchies-to-represent-concepts-with-inherent-hierarchical-structure-only)

117. Почему отношение «is-a» важнее механического повторного использования кода через наследование?

   **Ответ:** Публичное наследование устанавливает семантический контракт: объект производного класса должен корректно работать везде, где ожидается базовый (*Liskov Substitution Principle*). Механическое переиспользование часто нарушает этот контракт.

   **Пример:** Наследование `Square` от `Rectangle` ломает логику независимой установки сторон через `set_width()`.

   **Типичная ошибка:** Наследование `Stack` от `std::vector` ради повторного использования методов вставки.

   **Источник:** [C++ Core Guidelines: C.121](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#c121-if-a-concrete-class-is-both-an-implementation-detail-and-a-base-use-concrete-classes-for-both)

118. Почему публичное наследование ради повторного использования реализации часто считается плохой практикой?

   **Ответ:** Оно делает внутренние детали базового класса частью открытого интерфейса производного класса, нарушая инкапсуляцию и связывая клиента с реализацией, которую нельзя изменить без поломки API.

   **Пример:** Если класс `Queue` публично наследует `std::deque`, пользователь получает доступ к случайному удалению элементов из середины очереди через методы базового класса.

   **Типичная ошибка:** Раскрытие внутренних вспомогательных методов наружу через открытое наследование.

   **Источник:** [Effective C++: Item 32 (Scott Meyers)](https://www.oreilly.com/library/view/effective-c-55/0321334876/)

119. Когда приватное наследование оправдано и почему композиция чаще лучше?

   **Ответ:** Приватное наследование оправдано, когда требуется переопределить виртуальные методы базового класса или воспользоваться оптимизацией пустого базового класса (*EBO*); в остальных ситуациях композиция предпочтительнее, так как не связывает жизненный цикл и зависимости классов столь жестко.

   **Пример:**

   ```cpp
   class Task : private TimerCallback {
       void on_timer_tick() override; // Переопределение приватного интерфейса
   };
   ```

   **Типичная ошибка:** Использование приватного наследования там, где достаточно обычного поля-члена класса.

   **Источник:** [C++ Core Guidelines: C.129](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#c129-when-designing-a-class-hierarchy-distinguish-between-implementation-inheritance-and-interface-inheritance)

120. Что такое интерфейс класса с точки зрения best practices?

   **Ответ:** Это минимальный, непротиворечивый и самодокументируемый набор публичных типов, методов и контрактов, позволяющий использовать объект по назначению, не раскрывая деталей его внутренней работы.

   **Пример:** Интерфейс сетевого клиента `connect()` и `send()`, скрывающий работу с сырыми дескрипторами ОС.

   **Типичная ошибка:** Включение в открытый интерфейс вспомогательных методов, предназначенных исключительно для внутреннего состояния класса.

   **Источник:** [C++ Core Guidelines: I.1](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#i1-make-interfaces-explicit)

121. Почему интерфейс класса должен быть «минимальным, но достаточным»?

   **Ответ:** Чем меньше методов в интерфейсе, тем легче поддерживать класс, тестировать его инварианты и менять внутреннюю реализацию без риска сломать клиентский код.

   **Пример:** Реализация операций в виде свободных внешних функций (`std::erase_if`) вместо бесконечного расширения методов внутри класса.

   **Типичная ошибка:** Добавление десятков методов-хелперов под частные случаи прямо в основной класс.

   **Источник:** [Effective C++: Item 23 (Scott Meyers)](https://www.oreilly.com/library/view/effective-c-55/0321334876/)

122. Почему не стоит делать все поля класса общедоступными (`public`)?

   **Ответ:** Это полностью лишает класс инкапсуляции: внешний код может напрямую перевести переменные в несогласованное состояние, минуя проверки и валидацию.

   **Пример:**

   ```cpp
   class Percentage {
   public:
       int value; // Внешний код может записать 999 или -50
   };
   ```

   **Типичная ошибка:** Открытие прямого доступа к полям структуры ради сокращения пары строк кода для геттеров/сеттеров при наличии инварианта.

   **Источник:** [C++ Core Guidelines: C.9](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#c9-minimize-exposure-of-members)

123. Когда структура с публичными полями абсолютно оправдана?

   **Ответ:** Когда структура является простым объединением независимых данных (*Plain Old Data / Aggregate*), где значения полей могут меняться произвольно и между ними нет зависимости или инвариантов.

   **Пример:**

   ```cpp
   struct Point {
       double x{0.0};
       double y{0.0};
   };
   ```

   **Типичная ошибка:** Создание приватных полей и тривиальных геттеров/сеттеров для математических структур, где любое значение каждого поля валидно.

   **Источник:** [C++ Core Guidelines: C.2](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#c2-use-class-if-the-class-has-an-invariant-use-struct-if-the-data-members-can-vary-independently)

124. Чем Value Object отличается от обычного «мешка данных»?

   **Ответ:** Value Object идентифицируется значениями своих полей, а не идентификатором/указателем, и строго контролирует корректность своего состояния (часто являясь неизменяемым — *immutable*).

   **Пример:**

   ```cpp
   class CurrencyAmount {
       int64_t cents_;
       std::string currency_;
   public:
       CurrencyAmount(int64_t cents, std::string_view cur); // Проверяет инвариант
   };
   ```

   **Типичная ошибка:** Хранение денег в виде примитивного `double`, допускающего отрицательные значения там, где они недопустимы.

   **Источник:** [Domain-Driven Design (Eric Evans)](https://en.wikipedia.org/wiki/Value_object)

125. Почему хороший класс обязан непрерывно поддерживать свои инварианты?

   **Ответ:** Это защищает программу от повреждения данных: вызывающему коду не нужно выполнять внешние защитные проверки перед каждым действием, так как объект всегда находится в корректном рабочем состоянии.

   **Пример:** `std::vector` всегда гарантирует, что `size() <= capacity()`, и клиентскому коду не нужно проверять корректность внутренних указателей буфера.

   **Типичная ошибка:** Допущение состояний, при которых объект валиден только после вызова определенных методов в строго определенном порядке.

   **Источник:** [C++ Core Guidelines: C.1](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#c1-organize-related-data-into-structures-structs-or-classes)

126. Что такое инвариант класса?

   **Ответ:** Это фундаментальное логическое условие относительно внутреннего состояния класса, которое истинно сразу после завершения конструктора и сохраняется неизменным до и после выполнения любого открытого метода.

   **Пример:** Для структуры рационального числа `Rational(numerator, denominator)` инвариантом является условие `denominator != 0`.

   **Типичная ошибка:** Временное нарушение инварианта в публичном методе с последующим выходом по неожиданному исключению.

   **Источник:** [Cppreference: Constraints and concepts](https://en.cppreference.com/w/cpp/language/constraints)

127. Почему методы класса должны сохранять инварианты даже при возникновении ошибок?

   **Ответ:** Это требование базовой гарантии безопасности исключений (*basic exception safety*): при сбое операции объект может перейти в другое допустимое состояние, но не должен оставлять после себя поврежденные структуры данных или утечки памяти.

   **Пример:** При неудачной вставке в середину вектора из-за нехватки памяти сам вектор должен остаться валидным контейнером исходного размера.

   **Типичная ошибка:** Частичная модификация полей объекта до операции, которая может выбросить исключение.

   **Источник:** [C++ Core Guidelines: E.19](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#e19-use-a-final_action-object-to-express-cleanup-if-no-suitable-resource-handle-is-available)

128. Что значит «объект должен всегда оставаться валидным»?

   **Ответ:** Это означает, что у объекта не существует промежуточного «мертвого» состояния, в котором вызов его публичных константных методов или деструктора приводит к неопределенному поведению (*UB*).

   **Пример:** Даже после перемещения (*moved-from state*) объект обязан оставаться в валидном состоянии, позволяющем его корректное уничтожение или присваивание нового значения.

   **Типичная ошибка:** Обнуление внутренних указателей при перемещении таким образом, что деструктор падает при проверке.

   **Источник:** [C++ Core Guidelines: C.40](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#c40-define-a-constructor-if-a-class-has-an-invariant)

129. Почему конструктор должен либо создать валидный объект, либо завершиться ошибкой?

   **Ответ:** Это исключает появление в программе неинициализированных экземпляров; если конструктор не может захватить ресурс или проверить инварианты, он обязан выбросить исключение, прерывая конструирование.

   **Пример:**

   ```cpp
   FileSession::FileSession(const std::string& path) {
       handle_ = open_file(path);
       if (!handle_) throw std::runtime_error("Cannot open file");
   }
   ```

   **Типичная ошибка:** Конструкторы, сохраняющие код ошибки во внутреннее поле и требующие последующего ручного вызова `if (!obj.is_valid())`.

   **Источник:** [C++ Core Guidelines: C.42](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#c42-if-a-constructor-cannot-construct-a-valid-object-throw-an-exception)

130. Почему «двухфазная инициализация» часто считается антипаттерном?

   **Ответ:** Разделение конструирования и инициализации через метод `init()` порождает временное невалидное состояние объекта, требует постоянных проверок флагов во всех методах и провоцирует ошибки забытого вызова `init()`.

   **Пример:**

   ```cpp
   // Плохой подход:
   Widget w;
   w.init(); // Если вызвать w.render() до init(), программа упадет
   ```

   **Типичная ошибка:** Перенос устаревших практик сред без исключений в современный C++ код.

   **Источник:** [C++ Core Guidelines: C.41](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#c41-a-constructor-should-create-a-fully-initialized-object)

131. Когда фабричная функция предпочтительнее публичного конструктора?

   **Ответ:** Когда создание объекта может завершиться штатным отсутствием результата (через `std::optional`), требует полиморфного возврата базового типа, сложной асинхронной подготовки данных или когда требуются понятные имена для конструкторов с одинаковыми типами параметров.

   **Пример:**

   ```cpp
   class Point {
   public:
       static Point from_cartesian(double x, double y);
       static Point from_polar(double r, double angle);
   };
   ```

   **Типичная ошибка:** Создание перегрузок конструктора с одинаковым набором параметров, различающихся фиктивными флагами.

   **Источник:** [C++ Core Guidelines: C.43](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#c43-ensure-that-a-class-has-an-invariant)

132. Почему модификатор `explicit` важен для конструкторов с одним аргументом?

   **Ответ:** Он предотвращает неявные преобразования типов при передаче аргументов в функции, защищая от незаметного создания временных объектов и скрытых ошибок вызова.

   **Пример:**

   ```cpp
   class StringHolder {
   public:
       explicit StringHolder(int capacity);
   };

   void print(const StringHolder&);
   // print(10); // Ошибка компиляции благодаря explicit, что спасает от багов!
   ```

   **Типичная ошибка:** Конструктор с одним аргументом без `explicit`, позволяющий неявно приводить примитивные типы к сложным бизнес-сущностям.

   **Источник:** [C++ Core Guidelines: C.46](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#c46-by-default-declare-single-argument-constructors-explicit)

133. В каких ситуациях неявные преобразования наносят реальный ущерб API?

   **Ответ:** Они приводят к выбору не той перегрузки функции, порождают скрытые аллокации памяти при создании временных объектов и маскируют смысловые ошибки передачи данных.

   **Пример:** Неявное преобразование `const char*` в `std::string` при передаче аргумента по ссылке может порождать скрытую аллокацию памяти внутри горячего цикла.

   **Типичная ошибка:** Предоставление оператора неявного приведения `operator bool()` без спецификатора `explicit`.

   **Источник:** [Google C++ Style Guide: Implicit Conversions](https://google.github.io/styleguide/cppguide.html#Implicit_Conversions)

134. Почему `const`-методы важны для интерфейса класса?

   **Ответ:** Они документируют намерение не изменять состояние объекта, обеспечивают константную корректность (*const-correctness*) и позволяют безопасно вызывать методы для константных ссылок и при параллельном чтении из нескольких потоков.

   **Пример:**

   ```cpp
   class Matrix {
   public:
       double at(size_t r, size_t c) const; // Метод только для чтения
   };
   ```

   **Типичная ошибка:** Отсутствие `const` у методов-инспекторов, из-за чего их невозможно вызвать, если объект передан как `const T&`.

   **Источник:** [C++ Core Guidelines: Con.2](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#con2-by-default-make-member-functions-const)

135. Почему сеттеры на все поля подряд — признак слабого дизайна?

   **Ответ:** Беспорядочные сеттеры выставляют наружу внутреннее устройство класса, разрушают целостность инвариантов и провоцируют процедурный стиль управления объектом извне вместо инкапсуляции поведения.

   **Пример:** Вместо раздельных `set_x()` и `set_y()` лучше реализовать целевой доменный метод `move_to(Point p)`.

   **Типичная ошибка:** Создание класса с приватными полями, для каждого из которых написан механический тривиальный сеттер.

   **Источник:** [Clean Code (Robert C. Martin)](https://www.oreilly.com/library/view/clean-code-a/9780136083238/)

136. Когда геттеры и сеттеры полезны, а когда они маскируют плохой дизайн?

   **Ответ:** Они полезны для доступа к независимым свойствам компонентов UI или конфигураций; они маскируют плохой дизайн, когда объект превращается в пассивную модель данных (*Anemic Domain Model*), а вся логика манипуляции этими данными пишется во внешних сервисах.

   **Пример:** Получение баланса счета через геттер, прибавление суммы и сохранение через сеттер вместо прямого вызова `account.deposit(amount)`.

   **Типичная ошибка:** Предоставление неконстантного геттера, возвращающего прямую ссылку на внутренний приватный контейнер.

   **Источник:** [Martin Fowler: TellDontAsk](https://martinfowler.com/bliki/TellDontAsk.html)

137. Почему методы с побочными эффектами должны быть очевидны по своему интерфейсу?

   **Ответ:** Неявные побочные эффекты (сетевые запросы, запись на диск, сброс состояний) нарушают принцип наименьшего удивления (*Principle of Least Surprise*) и делают код сложным для отладки и тестирования.

   **Пример:** Метод `is_connected()` не должен инициировать процедуру переподключения сокета, если соединение разорвано.

   **Типичная ошибка:** Изменение глобального состояния программы или полей класса внутри геттера.

   **Источник:** [C++ Core Guidelines: F.1](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#f1-package-meaningful-operations-as-carefully-named-functions)

138. Каким образом правила именования методов должны отражать изменение состояния?

   **Ответ:** Общепринятая практика разделяет методы-запросы (существительные и прилагательные, возвращающие значения без мутаций: `size()`, `empty()`) и методы-команды (глаголы в повелительном наклонении, изменяющие состояние: `clear()`, `sort()`).

   **Пример:**

   ```cpp
   auto copy = v.sorted(); // Возвращает отсортированную копию
   v.sort();               // Сортирует вектор на месте
   ```

   **Типичная ошибка:** Использование имени `compute_hash()` для функции, которая очищает внутренний кэш объекта.

   **Источник:** [Google C++ Style Guide: Function Names](https://google.github.io/styleguide/cppguide.html#Function_Names)

139. Почему функции без внутреннего состояния (stateless) легче тестировать?

   **Ответ:** Их результат детерминирован и полностью определяется входными аргументами; они не требуют предварительной настройки глобального контекста, моков или сложного сброса окружения между тестами.

   **Пример:** Функция парсинга `parse_header(std::string_view)` тестируется передачей тестовых строк без инициализации базы данных.

   **Типичная ошибка:** Неявная зависимость функции расчета от системного времени или глобальных флагов настроек.

   **Источник:** [Working Effectively with Legacy Code (Michael Feathers)](https://www.oreilly.com/library/view/working-effectively-with/0131177052/)

140. Что такое чистая функция (pure function) и почему это полезная концепция?

   **Ответ:** Это функция, которая всегда возвращает один и тот же результат для одинаковых входных аргументов и не вызывает наблюдаемых побочных эффектов (*side effects*). Такие функции легко оптимизировать компилятором, кэшировать и распараллеливать.

   **Пример:**

   ```cpp
   [[nodiscard]] int add(int a, int b) noexcept {
       return a + b;
   }
   ```

   **Типичная ошибка:** Использование статических локальных переменных для накопления промежуточных данных внутри функции.

   **Источник:** [C++ Core Guidelines: F.8](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#f8-prefer-pure-functions)

141. Почему лучше минимизировать побочные эффекты в функциях?

   **Ответ:** Побочные эффекты порождают скрытые зависимости по времени вызова (*temporal coupling*), когда функции должны вызываться в строгой последовательности, что делает кодовую базу хрупкой при рефакторинге.

   **Пример:** Функция преобразования координат не должна попутно писать сообщения в системный лог.

   **Типичная ошибка:** Модификация переданных по неконстантной ссылке параметров при вычислении вспомогательного значения.

   **Источник:** [Code Complete (Steve McConnell)](https://en.wikipedia.org/wiki/Code_Complete)

142. Когда побочные эффекты неизбежны и как с ними аккуратно работать?

   **Ответ:** Они неизбежны при взаимодействии с аппаратной частью, операционной системой и сетью. Их изолируют на границах системы в специальных адаптерах и контроллерах, отделяя чистую бизнес-логику от операций ввода-вывода.

   **Пример:** Отделение бизнес-логики формирования банковского чека от слоя отправки данных на физический термопринтер.

   **Типичная ошибка:** Размазывание прямых вызовов файлового ввода-вывода по всем доменным классам.

   **Источник:** [Clean Architecture (Robert C. Martin)](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html)

143. Почему Dependency Injection часто улучшает архитектурный дизайн?

   **Ответ:** Внедрение зависимостей отделяет конструирование объектов от их использования, ослабляет связность компонентов и позволяет подменять тяжелые сервисы тестовыми заглушками (*mocks/stubs*).

   **Пример:**

   ```cpp
   class AccountManager {
   public:
       explicit AccountManager(std::shared_ptr<IDatabase> db) : db_{std::move(db)} {}
   private:
       std::shared_ptr<IDatabase> db_;
   };
   ```

   **Типичная ошибка:** Создание конкретных реализаций сетевых или базовых сервисов через `new` прямо внутри конструктора бизнес-класса.

   **Источник:** [Dependency Injection in .NET / Architectural Principles](https://en.wikipedia.org/wiki/Dependency_injection)

144. Чем явная зависимость лучше скрытой?

   **Ответ:** Явная зависимость декларируется прямо в интерфейсе (сигнатуре конструктора или метода), делая требования компонента очевидными для читателя и компилятора, в отличие от неявного обращения к глобальным переменным или синглтонам.

   **Пример:** Сигнатура `generate_report(const Config&, Database&)` сразу показывает, что требуется функции, в отличие от скрытого обращения к `Database::instance()`.

   **Типичная ошибка:** Использование паттерна *Service Locator*, скрывающего истинные зависимости модуля.

   **Источник:** [C++ Core Guidelines: I.2](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#i2-avoid-global-variables)

145. Когда зависимость стоит передавать по ссылке, а когда — через передачу владения?

   **Ответ:** По ссылке (`T&` или `const T&`) зависимость передают, если вызываемый объект лишь временно использует ее на время выполнения операции; с передачей владения (`std::unique_ptr` или по значению) — если вызываемый компонент сохраняет объект для длительного или асинхронного использования.

   **Пример:**

   ```cpp
   void render_frame(const Camera& cam);       // Временное чтение по ссылке
   void save_task(std::unique_ptr<Task> task); // Передача полного владения
   ```

   **Типичная ошибка:** Передача умных указателей `std::shared_ptr` в алгоритмы, которым достаточно временного доступа к объекту по константной ссылке.

   **Источник:** [C++ Core Guidelines: F.15](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#f15-prefer-simple-and-conventional-ways-of-passing-information)

146. Почему ссылка `T&` часто лучше указателя `T*`, если отсутствие значения недопустимо?

   **Ответ:** Ссылка в C++ гарантирует существование валидного объекта на уровне языка, избавляя вызываемый код от избыточных защитных проверок на равенство `nullptr`.

   **Пример:**

   ```cpp
   void process(Widget& w) {
       w.execute(); // Проверка на nullptr не требуется
   }
   ```

   **Типичная ошибка:** Прием сырого указателя `Widget*` с последующим разыменованием без предварительной проверки `if (ptr)`.

   **Источник:** [C++ Core Guidelines: F.60](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#f60-for-arguments-that-must-not-be-null-prefer-t-over-t)

147. В каких случаях сырой указатель в сигнатуре предпочтительнее ссылки?

   **Ответ:** Когда параметр является опциональным и вызывающий код может передать `nullptr` для обозначения отсутствия значения, либо когда внутри функции требуется перепривязывать адрес на другой объект.

   **Пример:**

   ```cpp
   void run_job(Context& ctx, ILogger* optional_logger = nullptr);
   ```

   **Типичная ошибка:** Использование фиктивных «пустых ссылок» или разыменования нулевых указателей (`*p`) при попытке передать опциональный аргумент в функцию, принимающую ссылку.

   **Источник:** [C++ Core Guidelines: I.12](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#i12-declare-a-pointer-that-must-not-be-null-as-not_null)

148. Почему nullable и non-nullable зависимости лучше различать на уровне типов?

   **Ответ:** Это устраняет двусмысленность интерфейсного контракта: разработчику не нужно проверять документацию или исходники метода, чтобы понять, готов ли он принять нулевой указатель.

   **Пример:** Использование `T&` или `gsl::not_null<T*>` для обязательных сущностей и `T*` или `std::optional` для опциональных.

   **Типичная ошибка:** Одинаковое использование сырых указателей `T*` для обязательных и необязательных параметров без явных пометок в коде.

   **Источник:** [C++ Core Guidelines: I.12](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#i12-declare-a-pointer-that-must-not-be-null-as-not_null)

149. Что такое non-owning pointer и почему его семантику важно явно фиксировать?

   **Ответ:** Это указатель, используемый исключительно для доступа или наблюдения за объектом, жизненным циклом которого управляет кто-то другой; фиксация этой семантики защищает от случайного вызова `delete` принимающей стороной.

   **Пример:**

   ```cpp
   void register_observer(Observer* obs); // obs не будет удален внутри
   ```

   **Типичная ошибка:** Передача владения через сырой указатель, из-за чего клиенту непонятно, лежит ли на нем обязанность освобождения памяти.

   **Источник:** [C++ Core Guidelines: F.22](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#f22-use-t-or-owner-to-designate-a-single-object)

150. Почему выражение владения через типы данных надежнее комментариев в коде?

   **Ответ:** Комментарии не проверяются компилятором и устаревают при первом же рефакторинге, в то время как типы данных (`std::unique_ptr`, `std::shared_ptr`, `T&`) принудительно контролируются системой типов языка при каждой сборке программы.

   **Пример:**

   ```cpp
   // Надежный самодокументируемый контракт:
   std::unique_ptr<Connection> make_connection();
   ```

   **Типичная ошибка:** Возврат сырого указателя `Connection*` с комментарием `// Не забудьте вызвать delete!`.

   **Источник:** [C++ Core Guidelines: P.1](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#p1-express-ideas-directly-in-code)

## Выше среднего уровня


151. Почему стратегия обработки ошибок является неотъемлемой частью best practices, а не изолированной темой?

   **Ответ:** Выбор стратегии обработки ошибок определяет дизайн интерфейсов функций, семантику типов возвращаемых значений, структуру владения ресурсами и гарантии корректности программы при возникновении сбоев.

   **Пример:**

   ```cpp
   // Дизайн функции прямо продиктован моделью обработки ошибок:
   std::expected<Data, ErrorCode> fetch_data(Endpoint endpoint);
   ```

   **Типичная ошибка:** Попытка дописать обработку ошибок «поверх» уже готовой архитектуры, что приводит к размыванию контрактов и утечкам ресурсов.

   **Источник:** [C++ Core Guidelines: E.principles](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#e-error-handling)

152. Когда оправдано использование исключений, а когда предпочтительнее коды ошибок или подход с `std::optional` / `std::expected`?

   **Ответ:** Исключения подходят для редких аварийных ситуаций, нарушающих выполнение базового контракта функции или конструктора; `std::optional` и `std::expected` предпочтительны для ожидаемых локальных исходов (например, промах кэша, ошибки парсинга ввода) и в средах с жесткими ограничениями по задержкам или запретом на RTTI.

   **Пример:**

   ```cpp
   // Ожидаемый исход парсинга пользовательского ввода:
   std::expected<int, ParseError> parse_number(std::string_view text);
   ```

   **Типичная ошибка:** Выброс исключений для управления нормальным ходом выполнения программы (*control flow*).

   **Источник:** [C++ Core Guidelines: E.12](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#e12-use-exceptions-only-for-error-handling)

153. Почему стиль обработки ошибок должен быть единообразным в рамках проекта?

   **Ответ:** Разрозненные подходы вынуждают писать адаптеры и промежуточные преобразования на границах каждого модуля, создают риск случайного пропуска ошибок и усложняют понимание контрактов функций.

   **Пример:** Согласованное соглашение команды: все инфраструктурные сбои бросают `AppException`, а бизнес-валидация возвращает `std::expected`.

   **Типичная ошибка:** Смешивание в одном слое возврата C-кодов ошибок (-1), глобальной переменной `errno`, сигнальных значений `nullptr` и выброса исключений.

   **Источник:** [C++ Core Guidelines: E.1](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#e1-develop-an-error-handling-strategy-early-in-a-design)

154. Что означает концепция exception-safe дизайна?

   **Ответ:** Это подход к архитектуре, при котором выброс исключения на любом этапе выполнения оставляет программу в предсказуемом, согласованном состоянии, не допуская повреждения инвариантов, утечек памяти, зависания мьютексов или дублирования ресурсов.

   **Пример:** Использование RAII-оберток для всех системных дескрипторов гарантирует безопасную очистку при размотке стека.

   **Типичная ошибка:** Расчет на то, что безопасность исключений сводится лишь к оборачиванию опасных мест в блоки `try-catch`.

   **Источник:** [Cppreference: Exception safety](https://en.cppreference.com/w/cpp/language/exceptions)

155. Каким образом RAII напрямую обеспечивает гарантии exception safety?

   **Ответ:** Механизм размотки стека (*stack unwinding*) гарантированно вызывает деструкторы всех локальных объектов автоматической памяти в порядке, обратном их созданию, что делает RAII единственным надежным средством очистки ресурсов при прерывании функции.

   **Пример:**

   ```cpp
   void do_work() {
       std::unique_lock<std::mutex> lock(mtx); // Гарантированно отпустит мьютекс при размотке
       risky_operation();
   }
   ```

   **Типичная ошибка:** Ручные попытки очистки памяти внутри многоуровневых блоков `catch`, дублирующие деструкторы.

   **Источник:** [C++ Core Guidelines: E.6](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#e6-use-raii-to-prevent-leaks)

156. Почему деструкторы никогда не должны выбрасывать исключения?

   **Ответ:** Если деструктор выбрасывает исключение во время размотки стека, вызванной другим активным исключением, среда выполнения немедленно вызывает `std::terminate`, аварийно завершая весь процесс без возможности восстановления.

   **Пример:**

   ```cpp
   struct FileGuard {
       ~FileGuard() noexcept {
           // Ошибки при закрытии логируются или подавляются, но не выбрасываются наружу
       }
   };
   ```

   **Типичная ошибка:** Вызов из деструктора сетевых операций сброса буферов, способных выбросить исключение при разрыве соединения.

   **Источник:** [Cppreference: Destructors](https://en.cppreference.com/w/cpp/language/destructor)

157. Что такое strong exception guarantee (строгая гарантия) и когда она необходима?

   **Ответ:** Это семантика «всё или ничего» (*commit-or-rollback*): операция либо завершается успешно, либо, при возникновении сбоя, оставляет объект в исходном состоянии до начала вызова. Она критична для транзакционных операций и контейнеров.

   **Пример:** Метод `std::vector::push_back` обеспечивает строгую гарантию: при сбое аллокации или копирования элементы вектора остаются неизменными.

   **Типичная ошибка:** Изменение полей текущего объекта до завершения сторонних потенциально падающих операций вместо использования идиомы *copy-and-swap*.

   **Источник:** [C++ Core Guidelines: E.19](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#e19-use-a-final_action-object-to-express-cleanup-if-no-suitable-resource-handle-is-available)

158. Что представляет собой basic exception guarantee (базовая гарантия) и когда её достаточно?

   **Ответ:** Базовая гарантия обещает, что при возникновении ошибки не произойдет утечек ресурсов, а программа и объекты останутся в валидном (хотя, возможно, измененном) состоянии, поддерживающем разрушение и переприсваивание. Это необходимый минимум для любого кода.

   **Пример:** Состояние буфера после неудачной пакетной вставки может содержать часть прочитанных байтов, но не содержит мусорных указателей.

   **Типичная ошибка:** Оставление невалидных указателей внутри объекта при прерывании операций очистки.

   **Источник:** [C++ Core Guidelines: E.16](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#e16-destructors-deallocation-and-swap-must-never-fail)

159. Почему перехват с последующим молчаливым подавлением исключения признан опасным антипаттерном?

   **Ответ:** Подавление исключения маскирует факт критического нарушения инварианта, оставляет программу работать в непредусмотренном и потенциально поврежденном состоянии, затрудняя поиск истинной причины сбоя.

   **Пример:**

   ```cpp
   // Опасный антипаттерн:
   try { init_subsystem(); } catch (...) {}
   ```

   **Типичная ошибка:** Использование пустого `catch(...)` для «быстрого устранения падений» перед релизом.

   **Источник:** [C++ Core Guidelines: E.14](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#e14-use-purpose-designed-user-defined-types-as-exceptions-not-built-in-types)

160. Что означает принцип «перехватывать исключение только на том уровне, где возможна его осмысленная обработка»?

   **Ответ:** Промежуточный код не должен ловить исключения, если он не способен исправить ситуацию (например, повторить операцию с альтернативным путем или перейти на резервный сценарий); исключение должно свободно пройти вверх до уровня, обладающего достаточным контекстом.

   **Пример:** Низкоуровневая функция чтения сокета дает исключению всплыть до диспетчера задач, который перезапустит сессию.

   **Типичная ошибка:** Добавление блоков `try-catch` в каждую функцию проекта для локальной печати сообщения об ошибке.

   **Источник:** [Clean Code (Robert C. Martin)](https://www.oreilly.com/library/view/clean-code-a/9780136083238/)

161. Почему логирование ошибки не является эквивалентом её обработки?

   **Ответ:** Запись строки в лог не восстанавливает нарушенные инварианты программы, не освобождает зависшие логические состояния и не сообщает вызывающему коду о невозможности продолжить операцию.

   **Пример:** Логирование исключения в середине цепочки вычислений без повторного выброса оставляет вызывающий код в неведении о сбое.

   **Типичная ошибка:** Запись в лог и продолжение работы с неинициализированным результатом операции (*log and ignore*).

   **Источник:** [C++ Core Guidelines: E.15](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#e15-catch-exceptions-from-a-hierarchy-as-part-of-a-subset-of-its-subsystem-and-dont-swallow-exceptions)

162. Почему блок `catch(...)` требует повышенной осторожности при использовании?

   **Ответ:** Он перехватывает абсолютно любые исключения, включая системные прерывания или сигналы отмены потоков, не предоставляя доступа к типу и сообщению ошибки (без вызова `std::current_exception`).

   **Пример:**

   ```cpp
   catch (...) {
       // Допустимо только на самом верхнем уровне потока или для безопасного логирования:
       log_critical_error();
       throw; // Проброс дальше
   }
   ```

   **Типичная ошибка:** Использование `catch(...)` в библиотечном коде с полным сокрытием типа возникшей аварии.

   **Источник:** [C++ Core Guidelines: E.15](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#e15-catch-exceptions-from-a-hierarchy-as-part-of-a-subset-of-its-subsystem-and-dont-swallow-exceptions)

163. В каких ситуациях повторный выброс исключения (`throw;`) считается хорошей практикой?

   **Ответ:** Когда на промежуточном уровне необходимо выполнить локальные действия (зафиксировать контекст ошибки в метриках, освободить внешние не-RAII ресурсы или обогатить трассировку) и затем передать исключение вышестоящему обработчику.

   **Пример:**

   ```cpp
   try {
       connect();
   } catch (const NetworkError& err) {
       metrics.increment("connection_failures");
       throw; // Корректный повторный выброс исходного объекта
   }
   ```

   **Типичная ошибка:** Написание `throw err;` вместо `throw;`, приводящее к срезке типа (*object slicing*).

   **Источник:** [Cppreference: throw expression](https://en.cppreference.com/w/cpp/language/throw)

164. Почему спецификатор `noexcept` важен как часть контракта функции, а не только инструмент оптимизации?

   **Ответ:** Он декларирует безусловную гарантию отсутствия исключений, на которую опираются стандартные алгоритмы и контейнеры при выборе между эффективным перемещением (*move*) и защитным глубоким копированием.

   **Пример:** Контейнер `std::vector` использует `std::move_if_noexcept` при переаллокации буфера только если move-конструктор типа помечен как `noexcept`.

   **Типичная ошибка:** Восприятие `noexcept` исключительно как подсказки компилятору для микрооптимизации машинного кода.

   **Источник:** [Cppreference: noexcept specifier](https://en.cppreference.com/w/cpp/language/noexcept_spec)

165. В каких случаях уместно явно помечать функцию спецификатором `noexcept`?

   **Ответ:** Для деструкторов (неявно по умолчанию), операций перемещения (move-конструкторы и move-присваивания), функций обмена состоянием (`swap`), тривиальных геттеров и низкоуровневых интерфейсов освобождения системных хэндлов.

   **Пример:**

   ```cpp
   Widget(Widget&& other) noexcept : data_{std::exchange(other.data_, nullptr)} {}
   ```

   **Типичная ошибка:** Расстановка `noexcept` на сложные методы, вызывающие сторонний код с динамическим выделением памяти в куче.

   **Источник:** [C++ Core Guidelines: F.6](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#f6-if-your-function-may-not-throw-declare-it-noexcept)

166. Чем опасно необоснованное добавление спецификатора `noexcept` (ложный `noexcept`)?

   **Ответ:** Если из функции, помеченной `noexcept`, все же попытается вылететь исключение, рантайм вызывает `std::terminate`, приводя к мгновенному падению процесса без возможности перехвата и нормальной размотки стека.

   **Пример:** Пометка метода `noexcept`, внутри которого вызывается код, способный бросить `std::bad_alloc`.

   **Типичная ошибка:** Слепое подавление предупреждений компилятора через добавление `noexcept` ко всем методам подряд.

   **Источник:** [Modern Effective C++: Item 14 (Scott Meyers)](https://www.oreilly.com/library/view/effective-modern-c/9781491908419/)

167. Почему инженерные best practices всегда включают требования к тестируемости кодовой базы?

   **Ответ:** Код, который невозможно протестировать изолированными тестами, почти всегда страдает от скрытых зависимостей, высокой связности (*high coupling*) и нарушений модульности, что делает его хрупким при сопровождении.

   **Пример:** Разделение логики валидации и непосредственной записи в файл позволяет покрыть алгоритм тестами за микросекунды без обращения к диску.

   **Типичная ошибка:** Написание монолитного кода с убеждением, что функциональность можно проверить только ручным тестированием интерфейса.

   **Источник:** [Working Effectively with Legacy Code (Michael Feathers)](https://www.oreilly.com/library/view/working-effectively-with/0131177052/)

168. Какие архитектурные свойства делают код легко тестируемым?

   **Ответ:** Детерминированность поведения, явная передача зависимостей через интерфейсы или параметры, минимальная область видимости состояний и следование принципу единственной ответственности (SRP).

   **Пример:** Функция принимает интерфейс `ITimeProvider` вместо прямого вызова системного времени через `std::chrono::system_clock::now()`.

   **Типичная ошибка:** Жесткая прошивка путей к локальным файлам или IP-адресов внутри классов бизнес-логики.

   **Источник:** [Clean Code (Robert C. Martin)](https://www.oreilly.com/library/view/clean-code-a/9780136083238/)

169. Почему изменяемое глобальное состояние и синглтоны разрушают модульное тестирование?

   **Ответ:** Они создают неявные связи между изолированными тестовыми сценариями: состояние, измененное одним тестом, влияет на результат следующего, нарушая воспроизводимость и блокируя параллельный запуск тестов.

   **Пример:** Тест А изменил глобальный синглтон конфигурации, из-за чего независимый тест Б в соседнем потоке завершился падением.

   **Типичная ошибка:** Попытка написать специальные методы очистки `Singleton::reset_for_testing()` вместо устранения самого синглтона.

   **Источник:** [C++ Core Guidelines: I.2](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#i2-avoid-global-variables)

170. Когда паттерн Singleton допустим, а когда он является запахом кода (code smell)?

   **Ответ:** Он допустим, когда объект действительно уникален в рамках физического процесса (например, корневой диспетчер прерываний или драйвер уникального аппаратного чипа); он превращается в code smell, когда используется просто как удобный способ получить глобальный доступ к данным.

   **Пример:** Запах кода: `ConfigurationManager::instance()`, доступный из любого класса вместо передачи локальных настроек.

   **Типичная ошибка:** Превращение доменных сущностей (база данных, кэш, корзина пользователя) в синглтоны.

   **Источник:** [Design Patterns (GoF)](https://en.wikipedia.org/wiki/Singleton_pattern)

171. Почему избыточное и тотальное создание мок-объектов (mock-everything) считается плохой практикой?

   **Ответ:** Чрезмерное мокирование привязывает тесты к деталям внутренней реализации классов, а не к их наблюдаемому поведению, делая тесты хрупкими: малейший рефакторинг ломает тесты даже при сохранении корректной работы системы.

   **Пример:** Мокирование внутренних служебных структур данных вместо тестирования конечного результата работы публичного API.

   **Типичная ошибка:** Написание тестов, проверяющих исключительно последовательность внутренних вызовов приватных интерфейсов.

   **Источник:** [Growing Object-Oriented Software, Guided by Tests (Steve Freeman, Nat Pryce)](http://www.growing-object-oriented-software.com/)

172. Что такое seam (стык/шов) в контексте проектирования для тестирования?

   **Ответ:** Это точка в кодовой базе, где можно изменить поведение программы или подменить зависимость (на этапе компиляции через шаблоны или в рантайме через полиморфные интерфейсы) без модификации исходного кода самого тестируемого модуля.

   **Пример:** Передача фабрики или шаблона стратегии в класс в качестве точки стыка с окружением.

   **Типичная ошибка:** Отсутствие явных стыков, вынуждающее разработчиков использовать препроцессорные хаки вроде `#define private public` в модульных тестах.

   **Источник:** [Working Effectively with Legacy Code (Michael Feathers)](https://www.oreilly.com/library/view/working-effectively-with/0131177052/)

173. В чём практический смысл принципа «Make interfaces easy to use correctly and hard to use use incorrectly»?

   **Ответ:** Интерфейс должен направлять разработчика к корректному использованию с помощью сильной системы типов, явных контрактов и идиом RAII, делая ошибки применения невозможными на этапе компиляции программы.

   **Пример:**

   ```cpp
   // Легко ошибиться: set_interval(100); (секунды или миллисекунды?)
   // Трудно ошибиться:
   void set_interval(std::chrono::milliseconds ms);
   ```

   **Типичная ошибка:** Создание интерфейсов, требующих обязательного вызова методов в строго определенном порядке без проверки на уровне типов.

   **Источник:** [The Key Design Principles (Scott Meyers)](https://www.aristeia.com/effective-c++-3rd-ed_framers.html)

174. Что представляет собой misuse-resistant API (устойчивый к ошибкам API)?

   **Ответ:** Это API, спроектированный так, что некорректная передача параметров, пропуск шагов инициализации или использование в невалидном состоянии пресекаются компилятором (через запрет копирования, strong types, concept constraints) либо приводят к контролируемому немедленному сбою.

   **Пример:** Применение атрибута `[[nodiscard]]` для функций, чей код ошибки или возвращаемый RAII-объект нельзя игнорировать.

   **Типичная ошибка:** Использование универсальных строковых параметров `std::string` для передачи дат, URL, путей и токенов без строгой типизации.

   **Источник:** [C++ Core Guidelines: I.4](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#i4-make-interfaces-strongly-typed)

175. Почему осмысленные значения параметров по умолчанию улучшают восприятие API?

   **Ответ:** Они снижают порог входа, избавляя вызывающий код от необходимости явно настраивать тонкие технические параметры в 90% стандартных сценариев, сохраняя возможность гибкой кастомизации при необходимости.

   **Пример:**

   ```cpp
   void render(Quality quality = Quality::Balanced);
   ```

   **Типичная ошибка:** Выбор в качестве значения по умолчанию магических чисел, требующих изучения документации.

   **Источник:** [C++ Core Guidelines: F.51](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#f51-where-there-is-a-choice-prefer-default-arguments-over-overloading)

176. В каких ситуациях параметры по умолчанию порождают опасную неоднозначность?

   **Ответ:** Когда функции перегружены и наличие параметров по умолчанию порождает конфликты вызова при неполной передаче аргументов, либо при наследовании, когда значения по умолчанию не переопределяются статически.

   **Пример:**

   ```cpp
   void execute(int timeout = 10);
   void execute(int timeout, bool async);
   // При вызове execute() с одним параметром легко запутаться в перегрузках
   ```

   **Типичная ошибка:** Переопределение значения параметра по умолчанию в виртуальном методе класса-наследника.

   **Источник:** [Effective C++: Item 37 (Scott Meyers)](https://www.oreilly.com/library/view/effective-c-55/0321334876/)

177. Почему семейство перегрузок функций должно быть компактным и семантически согласованным?

   **Ответ:** Все функции с одним именем обязаны иметь эквивалентное поведение и решать одну задачу; разнородные действия с одним именем сбивают читателя и приводят к вызову непредусмотренной перегрузки из-за неявных приведений типов.

   **Пример:** Набор перегрузок `print(int)`, `print(double)`, `print(std::string_view)` решает одну задачу форматирования для разных типов.

   **Типичная ошибка:** Перегрузка одного имени функции для выполнения принципиально разных бизнес-сценариев.

   **Источник:** [Google C++ Style Guide: Function Overloading](https://google.github.io/styleguide/cppguide.html#Function_Overloading)

178. Когда набор перегрузок (overload set) становится чрезмерно сложным и опасным?

   **Ответ:** Когда в перегрузках смешиваются шаблонные функции с универсальными ссылками (*forwarding references*), неявные приведения базовых числовых типов и аргументы со значениями по умолчанию.

   **Пример:** Перегрузка `template<typename T> void process(T&&)` вместе с обычной `void process(int)`.

   **Типичная ошибка:** Добавление жадного универсального шаблона конструктора в класс без ограничения через `std::enable_if` или `requires`.

   **Источник:** [Modern Effective C++: Item 26 (Scott Meyers)](https://www.oreilly.com/library/view/effective-modern-c/9781491908419/)

179. Почему шаблоны не следует использовать там, где достаточно обычной функции?

   **Ответ:** Шаблоны раздувают время компиляции, усложняют заголовочные файлы, ухудшают читаемость ошибок сборщика и приводят к дублированию бинарного кода (*code bloat*) при инстанцировании для схожих типов.

   **Пример:** Использование `std::string_view` вместо написания шаблонной функции `template<typename S> void print(const S& s)`.

   **Типичная ошибка:** Параметризация всей бизнес-логики шаблонами без реальной необходимости обобщения поведения.

   **Источник:** [C++ Core Guidelines: T.10](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#t10-specify-concepts-for-all-template-arguments)

180. В каких ситуациях обобщённый код (шаблоны/generics) полностью оправдан?

   **Ответ:** Для разработки контейнеров, независимых математических и инфраструктурных алгоритмов, общих типов-оберток (`std::optional`, `std::expected`) и библиотек сериализации/метапрограммирования.

   **Пример:** Функция сортировки массива `std::sort` одинаково корректна для любого типа, поддерживающего отношение строгого слабого порядка.

   **Типичная ошибка:** Применение шаблонов только ради того, чтобы не указывать конкретный базовый класс в прикладной архитектуре.

   **Источник:** [C++ Core Guidelines: T.1](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#t1-use-templates-to-raise-the-level-of-abstraction-of-code)

181. Каким образом ограничения и концепты (constraints & concepts) улучшают шаблонный API?

   **Ответ:** Они переносят проверку требований к типам на этап декларации сигнатуры, заменяют многостраничные простыни ошибок компилятора на ясные диагностические сообщения и служат машиночитаемой документацией интерфейса.

   **Пример:**

   ```cpp
   template <std::integral T>
   T compute_hash(T value);
   ```

   **Типичная ошибка:** Создание не ограниченных шаблонов с падением глубоко внутри тела функции на этапе обращения к приватным операторам.

   **Источник:** [Cppreference: Constraints and concepts](https://en.cppreference.com/w/cpp/language/constraints)

182. Почему неоправданное использование низкоуровневой магии SFINAE считается плохой практикой в modern C++?

   **Ответ:** Шаблоны на базе SFINAE (`std::enable_if_t`) крайне сложны для чтения, сопровождаются трудноуловимыми ошибками перегрузки и существенно замедляют фазу семантического анализа компилятора по сравнению с языковыми концептами C++20.

   **Пример:** Замена громоздких условий `typename std::enable_if<...>::type` лаконичным выражением `requires`.

   **Типичная ошибка:** Написание самописных метафункций на SFINAE для задач, которые стандартная библиотека решает через `concepts`.

   **Источник:** [C++ Core Guidelines: T.11](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#t11-whenever-possible-use-standard-concepts)

183. В каких сценариях `if constexpr` предпочтительнее специализации шаблонов?

   **Ответ:** При выборе логики внутри тела функции на основе свойств типов: это сохраняет алгоритм локальным в одном месте, исключает дублирование сигнатур и бойлерплейта специализаций.

   **Пример:**

   ```cpp
   template <typename T>
   void process(T val) {
       if constexpr (std::is_pointer_v<T>) {
           *val = 0;
       } else {
           val = 0;
       }
   }
   ```

   **Типичная ошибка:** Написание нескольких перегрузок с тегами диспетчеризации (*tag dispatching*) там, где достаточно одной ветки `if constexpr`.

   **Источник:** [Cppreference: if statement (constexpr)](https://en.cppreference.com/w/cpp/language/if)

184. Почему качество сообщений об ошибках компиляции считается частью UX шаблонной библиотеки?

   **Ответ:** Непонятный текст ошибок компиляции отпугивает пользователей библиотеки и кратно увеличивает время отладки клиентского кода; качественный API превентивно падает с ясным указанием на отсутствующий метод или оператор.

   **Пример:** Сообщение «Type must satisfy Sortable concept» вместо 50 строк стека инстанцирования стандартного алгоритма.

   **Типичная ошибка:** Отсутствие явных проверок входных шаблонных параметров в публичном API библиотеки.

   **Источник:** [C++ Core Guidelines: T.12](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#t12-prefer-concept-definitions-over-requires-clauses-when-meaningful)

185. Почему применение `static_assert` с понятным текстом считается хорошей инженерной практикой?

   **Ответ:** Он фиксирует архитектурные допущения и предпосылки (размерности, требования к выравниванию, свойства типов) непосредственно в исходном коде, останавливая сборку с точным объяснением причины.

   **Пример:**

   ```cpp
   static_assert(sizeof(PacketHeader) == 16, "PacketHeader must be exactly 16 bytes for network wire format");
   ```

   **Типичная ошибка:** Замена проверок `static_assert` рантайм-утверждениями `assert()`, срабатывающими только при выполнении тестов.

   **Источник:** [C++ Core Guidelines: P.4](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#p4-ideally-a-program-should-be-statically-type-safe)

186. Что такое semantic constraint (семантическое ограничение) и почему оно важнее чисто синтаксического?

   **Ответ:** Синтаксическое ограничение требует лишь наличия операции (например, оператора `<`), а семантическое требует математических гарантий ее поведения (строгий слабый порядок, транзитивность, ассоциативность); без семантики код компилируется, но дает логический сбой.

   **Пример:** Передача предиката сравнения с нестрогим отношением (`<=`) в `std::sort` синтаксически верна, но ведет к UB из-за нарушения семантики строгой упорядоченности.

   **Типичная ошибка:** Ограничение типов проверкой наличия метода с нужным именем без верификации контракта его поведения.

   **Источник:** [Cppreference: Constraints and concepts](https://en.cppreference.com/w/cpp/language/constraints)

187. Почему шаблонное метапрограммирование не должно ухудшать читаемость кода без критической необходимости?

   **Ответ:** Код читается значительно чаще, чем пишется; необоснованное увлечение сложным шаблонным метапрограммированием превращает библиотеку в закрытый «черный ящик», который невозможно сопровождать рядовым инженерам команды.

   **Пример:** Вынесение сложных вычислений в обычный `constexpr`-код вместо рекурсивного инстанцирования шаблонных структур.

   **Типичная ошибка:** Самоцельное конструирование сложных метафункций ради демонстрации возможностей языка.

   **Источник:** [C++ Core Guidelines: T.1](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#t1-use-templates-to-raise-the-level-of-abstraction-of-code)

188. В каких случаях использование концептов делает код объективно проще?

   **Ответ:** Когда концепты заменяют многоуровневые проверки SFINAE, упрощают сигнатуры шаблонных перегрузок и избавляют от необходимости писать вспомогательные структуры-трейты (*type traits*).

   **Пример:**

   ```cpp
   // Лаконично и очевидно:
   void print(std::formattable auto value);
   ```

   **Типичная ошибка:** Создание уникального концепта с одним тривиальным условием для каждой отдельной прикладной функции.

   **Источник:** [C++ Core Guidelines: T.10](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#t10-specify-concepts-for-all-template-arguments)

189. Почему библиотека Ranges и алгоритмы предпочтительнее классической ручной работы с парами итераторов?

   **Ответ:** Диапазоны (*Ranges*) объединяют начало и конец последовательности в единый объект, предотвращают ошибки несогласованных итераторов разных контейнеров и позволяют составлять декларативные пайплайны обработки данных без промежуточных аллокаций.

   **Пример:**

   ```cpp
   auto results = data | std::views::filter(is_even)
                       | std::views::transform(square);
   ```

   **Типичная ошибка:** Передача в алгоритм итератора `begin()` от одного вектора и `end()` от другого.

   **Источник:** [Cppreference: Ranges library](https://en.cppreference.com/w/cpp/ranges)

190. В каких ситуациях классический ручной цикл остаётся более читаемым, чем цепочка алгоритмов?

   **Ответ:** Когда логика шага цикла содержит нетривиальное управление потоком (сложные условия одновременного пропуска нескольких элементов, движение вперед-назад по индексам или множественные точки досрочного выхода).

   **Пример:** Итерация по потоковому протоколу переменной длины с разбором заголовка и последующим смещением смешанного типа.

   **Типичная ошибка:** Попытка упаковать сложный стейт-машинный алгоритм с побочными эффектами в одно нечитаемое выражение `std::transform` с многострочной лямбдой.

   **Источник:** [C++ Core Guidelines: ES.71](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#es71-prefer-a-range-for-statement-to-a-for-statement-when-there-is-a-choice)

191. Почему публичный API не должен раскрывать внутренние детали технической реализации?

   **Ответ:** Раскрытие внутренних типов и полей связывает клиентов с архитектурными нюансами версии библиотеки, лишая разработчиков возможности оптимизировать реализацию без нарушения бинарной и исходной совместимости (*ABI/API break*).

   **Пример:** Экспорт полей сторонней библиотеки через заголовочные файлы собственного интерфейса.

   **Типичная ошибка:** Включение деталей реализации сокетов конкретной ОС в публичные заголовочные файлы клиентского сетевого менеджера.

   **Источник:** [C++ Core Guidelines: I.1](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#i1-make-interfaces-explicit)

192. В каких случаях идиома PIMPL (Pointer to Implementation) считается оправданной практикой?

   **Ответ:** Для стабилизации ABI в распространяемых динамических библиотеках и для радикального ускорения сборки крупных проектов за счет изоляции тяжелых приватных зависимостей от внешних заголовочных файлов.

   **Пример:**

   ```cpp
   class Engine {
   public:
       Engine();
       ~Engine();
   private:
       struct Impl;
       std::unique_ptr<Impl> pimpl_;
   };
   ```

   **Типичная ошибка:** Использование PIMPL для мелких, критичных к производительности математических структур, где дополнительная косвенность (*indirection*) убивает инлайнинг.

   **Источник:** [Cppreference: PImpl](https://en.cppreference.com/w/cpp/language/pimpl)

193. Почему контроль за зависимостями в заголовочных файлах (header dependencies) относится к best practices?

   **Ответ:** Каждый лишний `#include` рекурсивно парсится компилятором в каждой единице трансляции, куда он включен, что многократно увеличивает время полной сборки проекта и повышает вероятность непреднамеренных коллизий макросов и имен.

   **Пример:** Замена включения тяжелого заголовочного файла `<vector>` опережающим объявлением там, где используются только указатели или ссылки.

   **Типичная ошибка:** Включение огромных монолитных заголовочных файлов (вроде `<windows.h>`) в общедоступные базовые заголовки проекта.

   **Источник:** [Google C++ Style Guide: Header Files](https://google.github.io/styleguide/cppguide.html#Header_Files)

194. Почему правило Include-What-You-Use (IWYU) считается важным стандартом гигиены кодовой базы?

   **Ответ:** Файл исходного кода должен явно включать те заголовки, типы из которых он непосредственно использует, не полагаясь на то, что нужный заголовок случайно «приедет» транзитивно через чужой `#include`.

   **Пример:** Явное добавление `#include <string>` в файл, использующий `std::string`, даже если он включен через другой сервис.

   **Типичная ошибка:** Падение сборки файла после рефакторинга соседнего модуля из-за удаления скрытого транзитивного включения.

   **Источник:** [Include What You Use Project](https://include-what-you-use.org/)

195. В каких случаях forward declaration (опережающее объявление) помогает, а когда вредит?

   **Ответ:** Помогает разорвать циклические зависимости и ускорить компиляцию, если тип используется только по указателю или ссылке; вредит, если скрывает размер типа (неполный тип — *incomplete type*), блокируя работу умных указателей `std::unique_ptr` при отсутствии явного деструктора в `.cpp`.

   **Пример:**

   ```cpp
   class Transaction; // Достаточно для void register(const Transaction&);
   ```

   **Типичная ошибка:** Попытка использовать `std::unique_ptr<IncompleteType>` в заголовочном файле с инлайновым деструктором по умолчанию.

   **Источник:** [Google C++ Style Guide: Forward Declarations](https://google.github.io/styleguide/cppguide.html#Forward_Declarations)

196. Каким образом физическая структура файлов и каталогов проекта влияет на скорость сборки и сопровождение?

   **Ответ:** Четкое разделение на публичные интерфейсы (`include/`) и детали реализации (`src/`), изоляция модулей и минимизация перекрестных зависимостей между библиотеками локализуют инкрементальную пересборку при внесении правок.

   **Пример:** Изменение файла реализации `.cpp` пересобирает только одну единицу трансляции, тогда как изменение корневого заголовочного файла приводит к полной пересборке всего проекта.

   **Типичная ошибка:** Сваливание всех заголовочных файлов и реализаций в одну общую директорию без разграничения зон видимости.

   **Источник:** [Large-Scale C++ Software Design (John Lakos)](https://en.wikipedia.org/wiki/Large-Scale_C%2B%2B_Software_Design)

197. Почему инженерные best practices предполагают постепенное внедрение (gradual adoption), а не немедленное «переписывание всего с нуля»?

   **Ответ:** Полное переписывание крупных систем сопряжено с колоссальными рисками срыва сроков и повторного внесения ранее исправленных граничных багов; постепенная эволюция через введение стандартов на новый код снижает риски.

   **Пример:** Внедрение правил `clang-tidy` только для вновь создаваемых или модифицируемых файлов через механизм проверки git-diff.

   **Типичная ошибка:** Остановка продуктовой разработки на год ради тотального переписывания легаси-системы на новый стандарт.

   **Источник:** [C++ Core Guidelines: In.force](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#inforce-enforcement)

198. Что значит «улучшать кодовую базу профилями и слоями правил», а не точечными случайными запретами?

   **Ответ:** Это системный подход к качеству: проект поэтапно подключает целостные согласованные наборы статических проверок (например, Type Safety Profile, Bounds Profile, Lifetime Profile) вместо разрозненных субъективных замечаний на код-ревью.

   **Пример:** Активация на уровне CI-пайплайна профиля проверки безопасности времени жизни указателей (*Lifetime Safety Profile*).

   **Типичная ошибка:** Хаотичные субъективные запреты отдельных языковых конструкций на код-ревью без автоматизированного инструмента контроля.

   **Источник:** [C++ Core Guidelines: Profile](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#profile-profiles)

199. Почему любое правило стиля или гайдлайна должно быть обоснованным, а не основываться на формулировке «так принято»?

   **Ответ:** Понимание инженерной мотивации правила (предотвращение UB, улучшение оптимизации, устранение race condition) позволяет разработчикам осознанно применять его в контексте, а также делать аргументированные исключения там, где ограничение вредит задаче.

   **Пример:** Правило «маркировать конструкторы с одним аргументом `explicit`» обосновывается защитой от неявных аллокаций и скрытых ошибок типизации.

   **Типичная ошибка:** Слепое соблюдение устаревших ограничений тридцатилетней давности без понимания причин их появления в старых версиях языка.

   **Источник:** [C++ Core Guidelines: Introduction](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#in-introduction)

200. Какие ключевые базовые best practices современного C++ можно сформулировать для старта нового проекта?

   **Ответ:**

      1. Использование RAII для управления всеми ресурсами без исключения;

      2. Отказ от прямого ручного управления памятью через `new`/`delete` в пользу стандартных контейнеров и `std::unique_ptr`;

      3. Соблюдение строгой константной корректности (*const-correctness*);

      4. Предпочтение стандартной библиотеки (`algorithms`, `ranges`, `string_view`, `span`) созданию велосипедов;

      5. Автоматизация контроля качества через строгие флаги компилятора (`-Wall -Wextra -Werror`), статические анализаторы (`clang-tidy`) и форматирование (`clang-format`).

   **Пример:**

   ```cpp
   // Иллюстрация современного стиля:
   // RAII, строгая типизация, отсутствие сырых указателей, constexpr и алгоритмы:
   constexpr size_t max_items = 100;

   [[nodiscard]] std::vector<std::string> filter_data(std::span<const std::string> items) {
       std::vector<std::string> result;
       std::ranges::copy_if(items, std::back_inserter(result), [](const auto& s) {
           return !s.empty();
       });
       return result;
   }
   ```
