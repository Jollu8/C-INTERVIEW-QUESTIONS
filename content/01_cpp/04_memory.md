# Память_и_lifetime

## Лёгкий уровень

1. Что в C++ обычно понимают под памятью программы?

   **Ответ:** Под памятью программы понимают непрерывное виртуальное адресное пространство, выделяемое операционной системой для хранения исполняемого кода, глобальных данных, стека вызовов и динамически выделяемых данных (кучи).

   **Пример:**

   ```cpp
   int global_var = 10; // Сегмент данных

   int main() {
       int stack_var = 20;          // Стек
       int* heap_var = new int(30); // Куча
       delete heap_var;
       return 0;
   }
   ```

   **Типичная ошибка:** Считать, что программа работает напрямую с физическими микросхемами RAM. На современных ОС программа всегда видит абстракцию — виртуальную память.

   **Источник:** [Cppreference: Memory model](https://en.cppreference.com/w/cpp/language/memory_model)

2. Что такое объект в C++?

   **Ответ:** Объект в C++ — это область памяти (region of storage), обладающая типом, размером, временем жизни и, опционально, именем или значением.

   **Пример:**

   ```cpp
   int x = 42; // x — именованный объект типа int
   ```

   **Типичная ошибка:** Думать, что «объект» бывает только у классов и структур. Примитивные типы (`int`, `double`, `char`) в стандарте C++ также образуют объекты.

   **Источник:** [Cppreference: Object](https://en.cppreference.com/w/cpp/language/object)

3. Что такое переменная с точки зрения памяти?

   **Ответ:** Переменная — это именованная сущность, которая вводит объект или ссылку и связывает читаемый идентификатор (имя) с конкретным участком памяти.

   **Пример:**

   ```cpp
   double speed = 9.8; // Имя 'speed' привязано к 8 байтам памяти, где лежит 9.8
   ```

   **Типичная ошибка:** Отождествлять имя переменной и сам объект. Объект может существовать в памяти и без имени (например, в динамической памяти или как временный объект).

   **Источник:** [Cppreference: Declarations](https://en.cppreference.com/w/cpp/language/declarations)

4. Что такое адрес в памяти?

   **Ответ:** Адрес — это числовой идентификатор (номер байта) в виртуальном адресном пространстве процесса, указывающий на начало расположения объекта в памяти.

   **Пример:**

   ```cpp
   #include <iostream>

   int main() {
       int a = 5;
       std::cout << &a << '\n'; // Выводит адрес первого байта объекта 'a'
   }
   ```

   **Типичная ошибка:** Предполагать, что адреса одинаковы при каждом запуске программы. Из-за механизма ASLR (рандомизация адресного пространства) адреса меняются от запуска к запуску.

   **Источник:** [Cppreference: Pointer declaration](https://en.cppreference.com/w/cpp/language/pointer)

5. Что значит “объект занимает память”?

   **Ответ:** Это означает, что под хранение состояния объекта зарезервировано фиксированное количество последовательных байт, начиная с определенного адреса, которые не могут быть заняты другим независимым объектом в этот же момент времени.

   **Пример:**

   ```cpp
   int a = 1;
   int b = 2;
   // &a и &b не совпадают: каждый объект резервирует свой диапазон байт
   ```

   **Типичная ошибка:** Полагать, что пустая структура `struct Empty {};` занимает 0 байт. В C++ любой отдельный объект занимает минимум 1 байт, чтобы иметь уникальный адрес.

   **Источник:** [Cppreference: Object (Size)](https://en.cppreference.com/w/cpp/language/object)

6. Что такое байт?

   **Ответ:** В C++ байт — это минимально адресуемая единица памяти, состоящая из непрерывной последовательности бит (определяется константой `CHAR_BIT`, практически всегда 8 бит), достаточная для хранения базового символа кодировки.

   **Пример:**

   ```cpp
   #include <climits>
   static_assert(sizeof(char) == 1, "Размер char всегда ровно 1 байт");
   ```

   **Типичная ошибка:** Полагать, что байт обязан быть аппаратно 8 бит во всех архитектурах, хотя `sizeof(char)` всегда строго равен 1 независимо от платформы.

   **Источник:** [Cppreference: Fundamental types](https://en.cppreference.com/w/cpp/language/types)

7. Что показывает `sizeof`?

   **Ответ:** Оператор `sizeof` вычисляет размер типа или объекта в байтах на этапе компиляции.

   **Пример:**

   ```cpp
   #include <iostream>

   int main() {
       std::cout << sizeof(int) << " bytes\n";
   }
   ```

   **Типичная ошибка:** Попытка узнать через `sizeof` размер данных, на которые указывает указатель (`sizeof(ptr)` вернет размер самого указателя, обычно 4 или 8 байт, а не размер буфера).

   **Источник:** [Cppreference: sizeof operator](https://en.cppreference.com/w/cpp/language/sizeof)

8. Почему разные типы занимают разный объём памяти?

   **Ответ:** Типы данных представляют разные диапазоны значений и требуют разной точности: для символа достаточно 1 байта, а для числа с плавающей точкой двойной точности требуется 8 байт для мантиссы и порядка.

   **Пример:**

   ```cpp
   bool b = true;     // 1 байт
   double d = 3.1415; // 8 байт
   ```

   **Типичная ошибка:** Ожидать, что размеры `int` или `long` абсолютно одинаковы на всех ОС и компиляторах. Они зависят от используемой модели данных (LLP64 vs LP64).

   **Источник:** [Cppreference: Fundamental types](https://en.cppreference.com/w/cpp/language/types)

9. Что такое время жизни объекта?

   **Ответ:** Время жизни (lifetime) — это интервал выполнения программы, в течение которого объект гарантированно существует в памяти, сохраняет валидное состояние и к нему разрешено обращаться.

   **Пример:**

   ```cpp
   {
       int x = 10; // Начало lifetime x
       // x доступен
   } // Конец lifetime x
   ```

   **Типичная ошибка:** Обращаться к объекту после завершения его времени жизни, что приводит к неопределённому поведению (UB).

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

10. Чем время жизни объекта отличается от области видимости переменной?

   **Ответ:** Область видимости (scope) — это статическое свойство текста программы (где имя доступно компилятору), а время жизни (lifetime) — динамическое свойство выполнения (когда память реально занята валидным объектом).

   **Пример:**

   ```cpp
   void foo() {
       static int counter = 0; // Scope — внутри foo(), lifetime — вся программа
   }
   ```

   **Типичная ошибка:** Считать, что если имя вышло из области видимости, объект обязательно уничтожен.

   **Источник:** [Cppreference: Scope](https://en.cppreference.com/w/cpp/language/scope)

11. Что такое область видимости?

   **Ответ:** Область видимости (scope) — фрагмент текста программы, внутри которого объявленный идентификатор однозначно ассоциируется компилятором с конкретным объявлением.

   **Пример:**

   ```cpp
   void bar() {
       int x = 5;
   }
   // Здесь 'x' не виден
   ```

   **Типичная ошибка:** Путать выход из области видимости со скрытием имён (shadowing), когда внутренняя переменная маскирует одноименную внешнюю.

   **Источник:** [Cppreference: Scope](https://en.cppreference.com/w/cpp/language/scope)

12. Когда начинается lifetime локальной переменной?

   **Ответ:** Время жизни начинается в момент завершения её инициализации при прохождении потока выполнения через строку объявления.

   **Пример:**

   ```cpp
   void f() {
       int x = 10; // Lifetime начинается здесь
   }
   ```

   **Типичная ошибка:** Предполагать, что lifetime начинается в момент входа в функцию.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

13. Когда заканчивается lifetime локальной переменной?

   **Ответ:** Заканчивается в момент выхода потока выполнения из блока кода, в котором переменная объявлена, непосредственно перед возвратом памяти стека.

   **Пример:**

   ```cpp
   {
       std::string s = "test";
   } // Вызывается деструктор s, lifetime завершён
   ```

   **Типичная ошибка:** Возвращать ссылку или указатель на локальную переменную наружу из функции (dangling pointer/reference).

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

14. Где обычно размещаются локальные переменные?

   **Ответ:** На аппаратном стеке вызовов (в текущем стековом фрейме) либо в регистрах процессора благодаря оптимизациям компилятора.

   **Пример:**

   ```cpp
   void calc() {
       int a = 1; // В стековом фрейме calc()
   }
   ```

   **Типичная ошибка:** Думать, что для каждой переменной обязательно резервируется ячейка в ОЗУ — оптимизатор компилятора может хранить её исключительно в регистрах CPU.

   **Источник:** [Cppreference: Storage duration](https://en.cppreference.com/w/cpp/language/storage_duration)

15. Что такое стековая память?

   **Ответ:** Стек (call stack) — быстрая LIFO-структура памяти, где выделение и освобождение происходят смещением указателя стека при вызовах и возвратах из функций.

   **Пример:**

   ```cpp
   void b() { int y = 20; }
   void a() { int x = 10; b(); }
   ```

   **Типичная ошибка:** Создание слишком больших массивов на стеке (`int arr[10'000'000]`), что приводит к аварии stack overflow.

   **Источник:** [Cppreference: Storage duration](https://en.cppreference.com/w/cpp/language/storage_duration)

16. Что такое автоматическая длительность хранения?

   **Ответ:** Режим времени жизни, при котором память под объект выделяется на стеке при входе в контекст объявления и гарантированно автоматически освобождается при выходе из блока.

   **Пример:**

   ```cpp
   void test() {
       auto val = 42; // Автоматическое освобождение
   }
   ```

   **Типичная ошибка:** Попытка вызвать `delete &val` для автоматической переменной.

   **Источник:** [Cppreference: Storage duration](https://en.cppreference.com/w/cpp/language/storage_duration)

17. Что такое глобальная переменная?

   **Ответ:** Переменная, объявленная вне функций и классов в глобальном пространстве имён или namespace, доступная на протяжении всей работы программы.

   **Пример:**

   ```cpp
   int app_state = 1;
   ```

   **Типичная ошибка:** Злоупотребление глобальными переменными, приводящее к скрытой связности компонентов и состояниям гонки в многопоточности.

   **Источник:** [Cppreference: Storage duration](https://en.cppreference.com/w/cpp/language/storage_duration)

18. Где обычно размещаются глобальные объекты?

   **Ответ:** В статических секциях исполняемого файла (`.data` для инициализированных ненулевыми значениями данных и `.bss` для нулевых/неинициализированных).

   **Пример:**

   ```cpp
   int val1 = 10; // .data
   int val2;      // .bss
   ```

   **Типичная ошибка:** Полагать, что глобальные переменные выделяются в куче или на стеке.

   **Источник:** [Cppreference: Storage duration](https://en.cppreference.com/w/cpp/language/storage_duration)

19. Когда начинается lifetime глобального объекта?

   **Ответ:** До входа в функцию `main()` во время инициализации программы исполняющей средой.

   **Пример:**

   ```cpp
   struct App { App() {} } app; // Конструктор отрабатывает до main()
   int main() {}
   ```

   **Типичная ошибка:** Рассчитывать на детерминированный порядок инициализации глобальных объектов из разных файлов (.cpp).

   **Источник:** [Cppreference: Initialization](https://en.cppreference.com/w/cpp/language/initialization#Non-local_variables)

20. Когда заканчивается lifetime глобального объекта?

   **Ответ:** После завершения `main()` или при вызове `std::exit()`, в порядке, строго обратном их инициализации.

   **Пример:**

   ```cpp
   struct Clean { ~Clean() {} } c; // ~Clean() вызовется после main()
   int main() { return 0; }
   ```

   **Типичная ошибка:** Обращаться к уже разрушенному глобальному объекту из деструктора другого глобального объекта.

   **Источник:** [Cppreference: exit](https://en.cppreference.com/w/cpp/utility/program/exit)

21. Что такое статическая длительность хранения?

   **Ответ:** Свойство объектов существовать в памяти на протяжении всего времени выполнения программы — от старта до завершения процесса.

   **Пример:**

   ```cpp
   static int cache_size = 1024;
   ```

   **Типичная ошибка:** Путать статическую длительность хранения с областью видимости и внутренним связыванием (internal linkage).

   **Источник:** [Cppreference: Storage duration](https://en.cppreference.com/w/cpp/language/storage_duration)

22. Что такое переменная `static` внутри функции?

   **Ответ:** Локальная переменная, память под которую выделяется статически: она сохраняет свое значение между последовательными вызовами функции.

   **Пример:**

   ```cpp
   int counter() {
       static int c = 0;
       return ++c;
   }
   ```

   **Типичная ошибка:** Думать, что `static` переменная инициализируется заново при каждом входе в функцию.

   **Источник:** [Cppreference: Storage duration](https://en.cppreference.com/w/cpp/language/storage_duration#Static_local_variables)

23. Когда создаётся локальная `static`-переменная?

   **Ответ:** При первом прохождении потока выполнения через строку её объявления.

   **Пример:**

   ```cpp
   void foo(bool flag) {
       if (flag) {
           static int x = 42; // Создастся только если flag == true
       }
   }
   ```

   **Типичная ошибка:** Предполагать создание локального статического объекта до фактического вызова функции.

   **Источник:** [Cppreference: Storage duration](https://en.cppreference.com/w/cpp/language/storage_duration#Static_local_variables)

24. Сколько раз создаётся локальная `static`-переменная?

   **Ответ:** Ровно один раз. Начиная с C++11 её инициализация гарантированно потокобезопасна (magic statics).

   **Пример:**

   ```cpp
   struct Instance {};
   Instance& get() {
       static Instance inst; // Потокобезопасно инициализируется 1 раз
       return inst;
   }
   ```

   **Типичная ошибка:** Навешивать ручные мьютексы вокруг статической инициализации в C++11+, вызывая лишние накладные расходы.

   **Источник:** [Cppreference: Storage duration](https://en.cppreference.com/w/cpp/language/storage_duration#Static_local_variables)

25. Когда уничтожается локальная `static`-переменная?

   **Ответ:** При нормальном завершении работы всей программы (после выхода из `main`), в порядке, обратном завершению конструирования.

   **Пример:**

   ```cpp
   void run() {
       static struct Logger { ~Logger() {} } log;
   }
   ```

   **Типичная ошибка:** Ожидать вызова деструкторов статических объектов при завершении через `std::abort()` или `std::quick_exit()`.

   **Источник:** [Cppreference: exit](https://en.cppreference.com/w/cpp/utility/program/exit)

26. Что такое динамическая память?

   **Ответ:** Область памяти (куча), выделением и освобождением которой программа управляет вручную во время исполнения по мере необходимости.

   **Пример:**

   ```cpp
   int* p = new int(100);
   delete p;
   ```

   **Типичная ошибка:** Забыть освободить память (утечка памяти) или обратиться к ней после освобождения.

   **Источник:** [Cppreference: Dynamic memory management](https://en.cppreference.com/w/cpp/memory)

27. Чем стековая память отличается от динамической?

   **Ответ:** Стек имеет фиксированный небольшой размер, работает мгновенно и управляется компилятором; куча намного больше по размеру, медленнее при выделении и требует явного освобождения.

   **Пример:**

   ```cpp
   int stack_val = 1;
   int* heap_val = new int(2);
   delete heap_val;
   ```

   **Типичная ошибка:** Выделять в куче мелкие временные переменные, где стек был бы в разы эффективнее и безопаснее.

   **Источник:** [Cppreference: Storage duration](https://en.cppreference.com/w/cpp/language/storage_duration)

28. Для чего используют оператор `new`?

   **Ответ:** Для запроса блока памяти нужного размера в куче и последующего конструирования объекта по этому адресу.

   **Пример:**

   ```cpp
   std::string* s = new std::string("test");
   delete s;
   ```

   **Типичная ошибка:** Заменять `new` на C-функцию `malloc`, которая не вызывает конструкторы классов.

   **Источник:** [Cppreference: new expression](https://en.cppreference.com/w/cpp/language/new)

29. Для чего используют оператор `delete`?

   **Ответ:** Для вызова деструктора объекта и последующего возврата занимаемой им динамической памяти обратно распределителю.

   **Пример:**

   ```cpp
   int* p = new int(10);
   delete p;
   ```

   **Типичная ошибка:** Использование `delete` вместо `delete[]` для памяти, выделенной через `new[]`.

   **Источник:** [Cppreference: delete expression](https://en.cppreference.com/w/cpp/language/delete)

30. Что делает `new`?

   **Ответ:** Выделяет сырую память через `operator new(size_t)` и сразу вызывает конструктор целевого типа на этой памяти.

   **Пример:**

   ```cpp
   struct Item { Item() {} };
   Item* it = new Item(); // operator new + вызов конструктора
   delete it;
   ```

   **Типичная ошибка:** Путать new-expression (оператор конструирования) и функцию распределения `operator new`.

   **Источник:** [Cppreference: new expression](https://en.cppreference.com/w/cpp/language/new)

31. Что делает `delete`?

   **Ответ:** Вызывает деструктор разрушаемого объекта, после чего передает его адрес функции деаллокации `operator delete(void*)`.

   **Пример:**

   ```cpp
   struct S { ~S() {} };
   S* s = new S();
   delete s; // s->~S() + operator delete(s)
   ```

   **Типичная ошибка:** Очищать объект сложного типа через `free()`, оставляя неуничтоженными внутренние поля класса.

   **Источник:** [Cppreference: delete expression](https://en.cppreference.com/w/cpp/language/delete)

32. Что означает, что объект “живёт до конца блока”?

   **Ответ:** Объект автоматически уничтожается в момент достижения закрывающей скобки `}` блока, где он объявлен.

   **Пример:**

   ```cpp
   {
       int x = 5;
   } // конец жизни x
   ```

   **Типичная ошибка:** Возвращать указатель на такой объект из функции.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

33. Что такое блок кода `{ ... }` в контексте lifetime?

   **Ответ:** Граница видимости и время жизни локальных автоматических объектов, определяющая область немедленного вызова их деструкторов при выходе.

   **Пример:**

   ```cpp
   #include <mutex>
   std::mutex m;
   void f() {
       {
           std::lock_guard<std::mutex> lock(m); // Мьютекс захвачен
       } // Мьютекс отпущен
   }
   ```

   **Типичная ошибка:** Удерживать блокировки и RAII-ресурсы дольше необходимого из-за отсутствия локальных вложенных блоков.

   **Источник:** [Cppreference: Statements](https://en.cppreference.com/w/cpp/language/statements#Compound_statements)

34. Что происходит с локальными переменными при выходе из блока?

   **Ответ:** Для них вызываются деструкторы в порядке, строго обратном порядку их конструирования, а память стека освобождается.

   **Пример:**

   ```cpp
   {
       std::string a = "1";
       std::string b = "2";
   } // Сначала ~b(), затем ~a()
   ```

   **Типичная ошибка:** Создавать взаимные зависимости между объектами, игнорируя их порядок разрушения.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

35. Что такое конструктор?

   **Ответ:** Специальный метод класса, инициализирующий выделенную под объект память и переводящий его состояние в согласованное.

   **Пример:**

   ```cpp
   struct Point {
       int x, y;
       Point(int x_, int y_) : x(x_), y(y_) {}
   };
   ```

   **Типичная ошибка:** Попытка вызвать конструктор повторно на существующем объекте как обычный метод.

   **Источник:** [Cppreference: Constructors](https://en.cppreference.com/w/cpp/language/initializer_list)

36. Когда вызывается конструктор объекта?

   **Ответ:** Сразу после выделения памяти под объект (на стеке, в куче или в статической области) перед началом его использования.

   **Пример:**

   ```cpp
   Point p(10, 20); // Память получена -> конструктор отработал
   ```

   **Типичная ошибка:** Думать, что конструктор сам распределяет память из ОС.

   **Источник:** [Cppreference: Constructors](https://en.cppreference.com/w/cpp/language/initializer_list)

37. Что такое деструктор?

   **Ответ:** Метод класса (с префиксом `~`), освобождающий ресурсы (память, файлы, сокеты), которыми владел объект перед прекращением его существования.

   **Пример:**

   ```cpp
   #include <cstdio>
   struct File {
       FILE* f;
       ~File() { if (f) fclose(f); }
   };
   ```

   **Типичная ошибка:** Выбрасывать исключения из деструктора, что приводит к краху программы через `std::terminate`.

   **Источник:** [Cppreference: Destructors](https://en.cppreference.com/w/cpp/language/destructor)

38. Когда вызывается деструктор объекта?

   **Ответ:** В момент завершения времени жизни: при выходе автоматической переменной из блока, при удалении динамического объекта через `delete` или при завершении программы для статических данных.

   **Пример:**

   ```cpp
   {
       std::string str = "abc";
   } // str.~basic_string()
   ```

   **Типичная ошибка:** Вызывать деструктор вручную для переменных на стеке.

   **Источник:** [Cppreference: Destructors](https://en.cppreference.com/w/cpp/language/destructor)

39. Зачем нужен деструктор?

   **Ответ:** Чтобы автоматизировать освобождение ресурсов (идиома RAII) и предотвратить утечки независимо от ветвления кода и исключений.

   **Пример:**

   ```cpp
   #include <memory>
   void test() {
       auto p = std::make_unique<int>(42); // Деструктор сам вызовет delete
   }
   ```

   **Типичная ошибка:** Надеяться на ручную очистку ресурсов, забывая про ветвления логики и ранние возвраты.

   **Источник:** [Cppreference: RAII](https://en.cppreference.com/w/cpp/language/raii)

40. Что происходит с памятью объекта после вызова деструктора?

   **Ответ:** Память возвращается обратно: регистр стека сдвигается, либо аллокатор кучи возвращает чанк в список свободной памяти; объект перестает существовать.

   **Пример:**

   ```cpp
   int* p = new int(5);
   delete p; // Память освобождена, обращение по p недопустимо
   ```

   **Типичная ошибка:** Попытка чтения или записи по адресу только что уничтоженного объекта (Use-After-Free).

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

41. Что такое инициализация объекта?

   **Ответ:** Присвоение начального валидного значения объекту в момент выделения под него памяти.

   **Пример:**

   ```cpp
   int a = 10;
   int b{20};
   ```

   **Типичная ошибка:** Использование объекта до того, как он был должным образом инициализирован.

   **Источник:** [Cppreference: Initialization](https://en.cppreference.com/w/cpp/language/initialization)

42. Чем инициализация отличается от присваивания?

   **Ответ:** Инициализация создает объект в сырой памяти, вызывая конструктор; присваивание перезаписывает значение уже существующего и инициализированного объекта через `operator=`.

   **Пример:**

   ```cpp
   std::string s = "one"; // Инициализация
   s = "two";             // Присваивание
   ```

   **Типичная ошибка:** Присваивать поля в теле конструктора вместо использования списков инициализации членов.

   **Источник:** [Cppreference: Initialization](https://en.cppreference.com/w/cpp/language/initialization)

43. Можно ли пользоваться объектом до его инициализации?

   **Ответ:** Нет, чтение неинициализированного объекта тривиального типа приводит к неопределенному поведению (UB).

   **Пример:**

   ```cpp
   int x;
   int y = x; // UB: чтение мусора
   ```

   **Типичная ошибка:** Полагать, что компилятор гарантированно заполняет локальные переменные нулями в релизной сборке.

   **Источник:** [Cppreference: Default initialization](https://en.cppreference.com/w/cpp/language/default_initialization)

44. Почему неинициализированные данные опасны?

   **Ответ:** Они вызывают непредсказуемое поведение алгоритмов, компрометируют безопасность данных и провоцируют компилятор на непредвиденные оптимизации из-за предположения об отсутствии UB.

   **Пример:**

   ```cpp
   bool flag;
   if (flag) { /* Может сработать произвольно */ }
   ```

   **Типичная ошибка:** Полагаться на поведение неинициализированных флагов в отладочных сборках.

   **Источник:** [Cppreference: Undefined behavior](https://en.cppreference.com/w/cpp/language/ub)

45. Что такое мусорное значение?

   **Ответ:** Случайная битовая последовательность, оставшаяся в адресованной памяти от предыдущих вызовов и интерпретируемая как значение переменной.

   **Пример:**

   ```cpp
   void foo() {
       int garbage; // Содержит остатки предыдущих фреймов стека
   }
   ```

   **Типичная ошибка:** Ожидать отладочных паттернов (`0xCDCDCDCD`) на реальном production-сервере.

   **Источник:** [Cppreference: Default initialization](https://en.cppreference.com/w/cpp/language/default_initialization)

46. Что такое указатель на объект в памяти?

   **Ответ:** Переменная, которая хранит числовой адрес первого байта области памяти, где размещен другой объект.

   **Пример:**

   ```cpp
   int val = 50;
   int* p = &val;
   ```

   **Типичная ошибка:** Путать адрес памяти объекта со значением, хранящимся в этом объекте.

   **Источник:** [Cppreference: Pointer declaration](https://en.cppreference.com/w/cpp/language/pointer)

47. Влияет ли сам указатель на lifetime объекта?

   **Ответ:** Нет, сырой указатель — это пассивный наблюдатель; уничтожение объекта делает указатель недействительным, а уничтожение указателя не трогает объект.

   **Пример:**

   ```cpp
   int* ptr = nullptr;
   {
       int a = 10;
       ptr = &a;
   } // 'a' уничтожен, ptr стал висячим
   ```

   **Типичная ошибка:** Считать, что пока указатель жив, объект в памяти также защищен от уничтожения.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

48. Что такое `nullptr` в контексте безопасности памяти?

   **Ответ:** Строго типизированный литерал нулевого указателя (`std::nullptr_t`), позволяющий однозначно проверять указатель на отсутствие ассоциированного объекта.

   **Пример:**

   ```cpp
   int* ptr = nullptr;
   if (ptr != nullptr) {
       *ptr = 10;
   }
   ```

   **Типичная ошибка:** Использование `0` или `NULL`, способное приводить к нежелательному вызову целочисленных перегрузок функций.

   **Источник:** [Cppreference: nullptr](https://en.cppreference.com/w/cpp/language/nullptr)

49. Что произойдёт, если обратиться к памяти через неверный указатель?

   **Ответ:** Произойдет неопределенное поведение: аварийное завершение процесса (Segfault / Access Violation) или тихое повреждение памяти приложения.

   **Пример:**

   ```cpp
   int* ptr = (int*)0xDEAD;
   *ptr = 100; // Крах программы
   ```

   **Типичная ошибка:** Рассчитывать, что программа всегда упадет с ошибкой — иногда порча памяти остается незамеченной длительное время.

   **Источник:** [Cppreference: Undefined behavior](https://en.cppreference.com/w/cpp/language/ub)

50. Что такое неопределённое поведение при работе с памятью?

   **Ответ:** Ситуация нарушения правил языка (разыменование висячего или нулевого указателя, выход за границы массива), при которой поведение программы стандартом не гарантируется.

   **Пример:**

   ```cpp
   int* p = new int(10);
   delete p;
   int val = *p; // Use-After-Free: компилятор не гарантирует ничего
   ```

   **Типичная ошибка:** Думать, что если программа не упала прямо сейчас, то код корректен.

   **Источник:** [Cppreference: Undefined behavior](https://en.cppreference.com/w/cpp/language/ub)

## Ниже среднего уровня

51. Что такое длительность хранения объекта в C++?

   **Ответ:** Длительность хранения (storage duration) — свойство объекта, определяющее минимальный срок существования памяти, зарезервированной под него (automatic, static, dynamic или thread).

   **Пример:**

   ```cpp
   void f() {
       int a;        // automatic
       static int b; // static
   }
   ```

   **Типичная ошибка:** Путать длительность хранения самой памяти с логическим временем жизни объекта (lifetime).

   **Источник:** [Cppreference: Storage duration](https://en.cppreference.com/w/cpp/language/storage_duration)

52. Какие основные виды длительности хранения существуют?

   **Ответ:** Существует четыре вида: автоматическая (automatic), статическая (static), динамическая (dynamic) и локальная для потока (thread-local).

   **Пример:**

   ```cpp
   int g;                     // static
   thread_local int t;        // thread
   void f() {
       int a;                 // automatic
       int* d = new int;      // dynamic
       delete d;
   }
   ```

   **Типичная ошибка:** Забывать про существование категории `thread_local`.

   **Источник:** [Cppreference: Storage duration](https://en.cppreference.com/w/cpp/language/storage_duration)

53. Чем automatic storage duration отличается от static storage duration?

   **Ответ:** Память с automatic storage выделяется при входе в блок и освобождается при выходе; с static storage — существует в единственном экземпляре всё время работы программы.

   **Пример:**

   ```cpp
   void count() {
       int a = 0;        // пересоздаётся каждый раз
       static int s = 0; // живёт всё время программы
   }
   ```

   **Типичная ошибка:** Предполагать, что `static` переменная сбрасывается к начальному значению при повторных вызовах функции.

   **Источник:** [Cppreference: Storage duration](https://en.cppreference.com/w/cpp/language/storage_duration)

54. Чем dynamic storage duration отличается от automatic storage duration?

   **Ответ:** Автоматическая память привязана к границам стекового блока и освобождается компилятором сама; динамическая память живет между явными запросами аллокации (`new`) и деаллокации (`delete`).

   **Пример:**

   ```cpp
   int* create() {
       int* p = new int(10); // dynamic: переживёт возврат из функции
       return p;
   }
   ```

   **Типичная ошибка:** Возвращать адрес переменной с automatic storage вместо динамически выделенного объекта.

   **Источник:** [Cppreference: Storage duration](https://en.cppreference.com/w/cpp/language/storage_duration)

55. Что такое thread storage duration?

   **Ответ:** Это длительность хранения объекта, при которой под каждую нить исполнения выделяется отдельная копия объекта, существующая до завершения данного потока.

   **Пример:**

   ```cpp
   thread_local int thread_counter = 0;
   ```

   **Типичная ошибка:** Считать, что переменная `thread_local` разделяется между потоками без синхронизации — у каждого потока свой независимый экземпляр.

   **Источник:** [Cppreference: Storage duration](https://en.cppreference.com/w/cpp/language/storage_duration#Storage_duration)

56. Когда создаётся объект с `thread_local`?

   **Ответ:** Для глобальных thread-local переменных — при создании потока; для локальных в функции — при первом прохождении потока через объявление.

   **Пример:**

   ```cpp
   void worker() {
       thread_local int local_tid = 1; // Создается при первом вызове в данном потоке
   }
   ```

   **Типичная ошибка:** Ожидать инициализации локальной thread_local переменной в потоке, который ни разу не вызывал содержащую её функцию.

   **Источник:** [Cppreference: Storage duration](https://en.cppreference.com/w/cpp/language/storage_duration#Storage_duration)

57. Когда уничтожается объект с `thread_local`?

   **Ответ:** Уничтожается непосредственно перед завершением того потока исполнения, для которого он был создан.

   **Пример:**

   ```cpp
   #include <thread>
   thread_local struct Tracker { ~Tracker() {} } t;
   void run() {}
   int main() {
       std::thread(run).join(); // Tracker потока разрушится здесь
   }
   ```

   **Типичная ошибка:** Обращаться к thread_local переменным завершенного потока через сохраненный сырой указатель.

   **Источник:** [Cppreference: Storage duration](https://en.cppreference.com/w/cpp/language/storage_duration#Storage_duration)

58. Что такое временный объект?

   **Ответ:** Неименованный объект (rvalue/prvalue), создаваемый компилятором для промежуточных вычислений, возврата значений или преобразования типов.

   **Пример:**

   ```cpp
   std::string a = "hello ";
   std::string b = "world";
   std::string c = a + b; // (a + b) создаёт временный объект std::string
   ```

   **Типичная ошибка:** Думать, что временные объекты живут столько же, сколько обычные именованные переменные в блоке.

   **Источник:** [Cppreference: Lifetime (Temporary objects)](https://en.cppreference.com/w/cpp/language/lifetime#Temporary_object_lifetime)

59. Когда создаются временные объекты?

   **Ответ:** При передаче аргументов по значению, приведении типов, вычислении выражений с операторами, возврате из функций по значению.

   **Пример:**

   ```cpp
   void take(const std::string&);
   take("literal"); // Создаётся временный std::string
   ```

   **Типичная ошибка:** Не учитывать накладные расходы на конструирование временных объектов при неявных преобразованиях типов в циклах.

   **Источник:** [Cppreference: Implicit conversions](https://en.cppreference.com/w/cpp/language/implicit_conversion)

60. Как долго обычно живёт временный объект?

   **Ответ:** По общему правилу временный объект уничтожается в самом конце полного выражения (full-expression), в котором он был создан.

   **Пример:**

   ```cpp
   std::string("hello").size(); // Строка уничтожится сразу после завершения вычисления точки с запятой
   ```

   **Типичная ошибка:** Сохранение указателя на внутренний буфер временного объекта за пределы строки выражения (`const char* p = std::string("hi").c_str();`).

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime#Temporary_object_lifetime)

61. Что такое full-expression в контексте времени жизни временных объектов?

   **Ответ:** Полное выражение — выражение, которое не является подвыражением какого-либо другого выражения (обычно завершается `;` либо условием в `if`/`while`).

   **Пример:**

   ```cpp
   int x = (2 + 3) * 4; // Всё выражение целиком до ';' — full-expression
   ```

   **Типичная ошибка:** Ожидать, что временный объект доживет до конца объемлющей функции или блока.

   **Источник:** [Cppreference: Expressions](https://en.cppreference.com/w/cpp/language/expressions#Full-expressions)

62. Когда уничтожается временный объект в простом выражении?

   **Ответ:** Как только управление доходит до точки с запятой `;`, завершающей данную инструкцию.

   **Пример:**

   ```cpp
   int len = std::string("test").length();
   // временный std::string уничтожен прямо здесь
   ```

   **Типичная ошибка:** Попытка использовать `std::string_view` на временный объект в следующей строке.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime#Temporary_object_lifetime)

63. Что такое продление времени жизни временного объекта?

   **Ответ:** Механизм языка (lifetime extension), продлевающий жизнь временного объекта до конца времени жизни ссылки, к которой он был напрямую привязан.

   **Пример:**

   ```cpp
   const std::string& s = std::string("prolonged"); // Живёт до конца области видимости s
   ```

   **Типичная ошибка:** Полагать, что продление времени жизни работает транзитивно через возвращаемые значения функций.

   **Источник:** [Cppreference: Reference initialization](https://en.cppreference.com/w/cpp/language/reference_initialization#Lifetime_of_a_temporary)

64. Когда `const T&` продлевает lifetime временного объекта?

   **Ответ:** Когда константная lvalue-ссылка инициализируется напрямую выражением, порождающим временный объект, в локальной области видимости.

   **Пример:**

   ```cpp
   const int& ref = 10 + 20; // Временный int живет столько же, сколько ref
   ```

   **Типичная ошибка:** Ожидать продления жизни при передаче временного объекта в функцию, возвращающую константную ссылку.

   **Источник:** [Cppreference: Reference initialization](https://en.cppreference.com/w/cpp/language/reference_initialization#Lifetime_of_a_temporary)

65. Продлевает ли `T&&` время жизни временного объекта?

   **Ответ:** Да, rvalue-ссылка `T&&` продлевает время жизни привязанного временного объекта по тем же правилам, что и `const T&`.

   **Пример:**

   ```cpp
   std::string&& rref = std::string("text"); // Объект живёт, пока жива rref
   ```

   **Типичная ошибка:** Считать, что rvalue-ссылка переносит владение автоматически без вызова конструктора перемещения.

   **Источник:** [Cppreference: Reference initialization](https://en.cppreference.com/w/cpp/language/reference_initialization#Lifetime_of_a_temporary)

66. Почему нельзя возвращать ссылку на локальную переменную?

   **Ответ:** Локальная переменная уничтожается при выходе из функции, в результате чего возвращенная ссылка становится висячей (dangling), а обращение к ней ведет к UB.

   **Пример:**

   ```cpp
   const int& bad() {
       int x = 42;
       return x; // Ошибка: x уничтожится при выходе
   }
   ```

   **Типичная ошибка:** Думать, что привязка возвращенной ссылки к `const T&` в вызывающем коде продлит жизнь уничтоженной локальной переменной.

   **Источник:** [Cppreference: Reference initialization](https://en.cppreference.com/w/cpp/language/reference_initialization)

67. Почему нельзя возвращать указатель на локальную переменную?

   **Ответ:** Память стекового фрейма функции освобождается/переиспользуется сразу после возврата; возвращенный указатель указывает на недействительную память.

   **Пример:**

   ```cpp
   int* bad_ptr() {
       int local = 5;
       return &local; // Ошибка!
   }
   ```

   **Типичная ошибка:** Игнорировать предупреждения компилятора "function returns address of local variable".

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

68. Что такое висячий указатель?

   **Ответ:** Указатель (dangling pointer), который содержит адрес объекта, чье время жизни уже завершилось, либо память которого была освобождена.

   **Пример:**

   ```cpp
   int* p = new int(10);
   delete p;
   // p стал висячим указателем
   ```

   **Типичная ошибка:** Забывать занулять (`p = nullptr;`) освобожденные указатели при отсутствии использования умных указателей.

   **Источник:** [Cppreference: Pointer declaration](https://en.cppreference.com/w/cpp/language/pointer)

69. Что такое висячая ссылка?

   **Ответ:** Ссылка (dangling reference), которая ссылается на уже разрушенный объект, чьё время жизни истекло.

   **Пример:**

   ```cpp
   auto& ref = *(new int(10));
   delete &ref;
   // ref теперь висячая
   ```

   **Типичная ошибка:** Использовать висячую ссылку, полагая, что раз ссылка синтаксически не может быть нулевой, она всегда валидна.

   **Источник:** [Cppreference: Reference initialization](https://en.cppreference.com/w/cpp/language/reference_initialization)

70. Как возникает висячий указатель после выхода из области видимости?

   **Ответ:** Когда указатель сохраняет адрес стекового объекта за пределами блока `{ ... }`, в котором этот объект был объявлен и уничтожен.

   **Пример:**

   ```cpp
   int* ptr;
   {
       int a = 100;
       ptr = &a;
   }
   // *ptr — висячий указатель
   ```

   **Типичная ошибка:** Передача указателей на локальные буферы в асинхронные задачи или callback-функции.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

71. Как возникает висячая ссылка после уничтожения объекта?

   **Ответ:** Когда объект уничтожается (по `delete`, выходу из блока или завершению полного выражения), а ссылка на него продолжает существовать в коде.

   **Пример:**

   ```cpp
   const std::string& ref = std::string("a") + std::string("b");
   // ref висячая: lifetime extension здесь не сработал через вызов operator+
   ```

   **Типичная ошибка:** Инициализация ссылок результатами сложных выражений с временными объектами.

   **Источник:** [Cppreference: Reference initialization](https://en.cppreference.com/w/cpp/language/reference_initialization)

72. Что такое use-after-free?

   **Ответ:** Ошибка безопасности и неопределенное поведение, заключающееся в чтении или записи памяти после её явного освобождения (деаллокации).

   **Пример:**

   ```cpp
   int* p = new int(42);
   delete p;
   *p = 10; // Use-After-Free!
   ```

   **Типичная ошибка:** Полагать, что память остается доступной и валидной ещё «некоторое время» после `delete`.

   **Источник:** [Cppreference: Undefined behavior](https://en.cppreference.com/w/cpp/language/ub)

73. Почему use-after-free опасен?

   **Ответ:** Он позволяет злоумышленникам перезаписывать критические структуры программы (vptr, указатели кучи), приводя к выполнению произвольного кода (RCE) или утечке конфиденциальных данных.

   **Пример:**

   ```cpp
   // Освобожденный блок перераспределяется под другой объект,
   // и старый указатель портит данные нового объекта
   ```

   **Типичная ошибка:** Недооценивать UAF как «просто случайный сбой программы».

   **Источник:** [Cppreference: Undefined behavior](https://en.cppreference.com/w/cpp/language/ub)

74. Что такое двойное удаление памяти?

   **Ответ:** Попытка вызвать `delete` или `free()` над одним и тем же адресом памяти более одного раза без промежуточного выделения.

   **Пример:**

   ```cpp
   int* p = new int(5);
   delete p;
   delete p; // Double delete!
   ```

   **Типичная ошибка:** Поверхностное копирование классов без реализованного конструктора копирования, владеющих сырыми указателями.

   **Источник:** [Cppreference: delete expression](https://en.cppreference.com/w/cpp/language/delete)

75. Почему double delete приводит к ошибкам?

   **Ответ:** Он разрушает метаданные внутреннего менеджера памяти аллокатора ОС/рантайма, вызывая немедленный аварийный сбой или уязвимости кучи.

   **Пример:**

   ```cpp
   // Приводит к вызову abort() со стороны glibc: free(): double free detected
   ```

   **Типичная ошибка:** Игнорировать «Правило трёх/пяти/нуля» при проектировании классов.

   **Источник:** [Cppreference: delete expression](https://en.cppreference.com/w/cpp/language/delete)

76. Что такое утечка памяти?

   **Ответ:** Ситуация, когда динамически выделенная память больше не используется программой, но так и не была освобождена обратно в систему.

   **Пример:**

   ```cpp
   void leak() {
       int* p = new int(10);
       // delete отсутствует: 4 байта утекли
   }
   ```

   **Типичная ошибка:** Полагать, что утечки не страшны, если программа работает на сервере с большим объемом оперативной памяти.

   **Источник:** [Cppreference: Dynamic memory management](https://en.cppreference.com/w/cpp/memory)

77. Как возникает утечка памяти при использовании `new`?

   **Ответ:** Когда для указателя, полученного из `new`, ни по одной из веток выполнения (включая ветки генерации исключений) не вызывается парный оператор `delete`.

   **Пример:**

   ```cpp
   void run() {
       int* p = new int(10);
       if (some_error()) return; // Утечка!
       delete p;
   }
   ```

   **Типичная ошибка:** Писать явные вызовы `delete` только в самом конце функции перед штатным выходом.

   **Источник:** [Cppreference: Dynamic memory management](https://en.cppreference.com/w/cpp/memory)

78. Почему забытый `delete` — это утечка?

   **Ответ:** Потому что рантайм C++ не имеет автоматического сборщика мусора и хранит информацию о занятом блоке, пока программист явно не отдаст команду на его возврат.

   **Пример:**

   ```cpp
   while (true) {
       new int[1000]; // Постепенное исчерпание ОЗУ
   }
   ```

   **Типичная ошибка:** Думать, что компилятор сам «догадается» вставить `delete` в деструктор объемлющей структуры без умных указателей.

   **Источник:** [Cppreference: delete expression](https://en.cppreference.com/w/cpp/language/delete)

79. Почему потеря последнего указателя на динамический объект ведёт к утечке?

   **Ответ:** Потому что адрес объекта в куче утрачивается безвозвратно: программа лишается технической возможности передать этот адрес в оператор `delete`.

   **Пример:**

   ```cpp
   int* p = new int(1);
   p = new int(2); // Адрес первого объекта потерян навсегда
   delete p;
   ```

   **Типичная ошибка:** Перезапись переменной-указателя новым адресом без предварительного удаления старого ресурса.

   **Источник:** [Cppreference: Dynamic memory management](https://en.cppreference.com/w/cpp/memory)

80. Что такое сырой указатель (`raw pointer`)?

   **Ответ:** Встроенный в язык тип указателя (`T*`), представляющий собой простой числовой адрес без логики автоматического управления временем жизни или семантики владения.

   **Пример:**

   ```cpp
   int* raw = new int(42);
   delete raw;
   ```

   **Типичная ошибка:** Перекладывать ответственность за время жизни динамических объектов на сырые указатели в современном C++.

   **Источник:** [Cppreference: Pointer declaration](https://en.cppreference.com/w/cpp/language/pointer)

81. Обозначает ли raw pointer владение объектом?

   **Ответ:** Нет, в современном C++ сырой указатель по соглашению обозначает лишь не-владеющий доступ (borrow/observe) и никогда не должен выражать исключительное владение.

   **Пример:**

   ```cpp
   void inspect(const Widget* w); // inspect не владеет w и не удаляет его
   ```

   **Типичная ошибка:** Передавать сырой указатель в функцию и удалять его внутри неё без явного документирования контракта.

   **Источник:** [Cppreference: Pointer declaration](https://en.cppreference.com/w/cpp/language/pointer)

82. Что такое владелец ресурса?

   **Ответ:** Объект или контекст, несущий исключительную или разделяемую ответственность за управление жизненным циклом ресурса и его своевременное освобождение.

   **Пример:**

   ```cpp
   std::unique_ptr<int> owner = std::make_unique<int>(10); // owner владеет памятью
   ```

   **Типичная ошибка:** Размывание ответственности владения между несколькими независимыми модулями программы.

   **Источник:** [Cppreference: unique_ptr](https://en.cppreference.com/w/cpp/memory/unique_ptr)

83. Что значит “объект владеет памятью”?

   **Ответ:** Это значит, что деструктор данного объекта содержит код деаллокации этой памяти, а сам объект контролирует монопольный доступ к ней.

   **Пример:**

   ```cpp
   std::vector<int> v(100); // Вектор владеет динамическим массивом из 100 элементов
   ```

   **Типичная ошибка:** Ручное удаление буфера, которым уже владеет контейнер стандартной библиотеки.

   **Источник:** [Cppreference: RAII](https://en.cppreference.com/w/cpp/language/raii)

84. Почему важно понимать, кто отвечает за освобождение памяти?

   **Ответ:** Четкое владение предотвращает две главные ошибки управления памятью: двойное удаление (double free) и утечки памяти (memory leaks).

   **Пример:**

   ```cpp
   // Если обе стороны считают себя владельцами — получим двойное удаление:
   void take(Widget* w) { delete w; } // Опасный API
   ```

   **Типичная ошибка:** Создание неоднозначных интерфейсов функций, где не ясно, нужно ли вызывающему коду вызывать `delete`.

   **Источник:** [Cppreference: RAII](https://en.cppreference.com/w/cpp/language/raii)

85. Что такое RAII?

   **Ответ:** RAII (Resource Acquisition Is Initialization) — базовая идиома C++, связывающая захват ресурса с инициализацией объекта, а освобождение — с вызовом его деструктора.

   **Пример:**

   ```cpp
   #include <fstream>
   void write() {
       std::ofstream file("log.txt"); // Ресурс захвачен в конструкторе
       file << "hello";
   } // Файл закрыт в деструкторе автоматически
   ```

   **Типичная ошибка:** Ручное закрытие файлов или освобождение памяти вместо использования специализированных RAII-обёрток.

   **Источник:** [Cppreference: RAII](https://en.cppreference.com/w/cpp/language/raii)

86. Как RAII связан с lifetime объекта?

   **Ответ:** Жизненный цикл внешнего ресурса (дескриптора, памяти) строго синхронизируется с границами времени жизни (lifetime) объемлющего C++ объекта.

   **Пример:**

   ```cpp
   {
       std::unique_ptr<int> p = std::make_unique<int>(5);
   } // Конец lifetime p -> ресурс освобожден
   ```

   **Типичная ошибка:** Использование сырых указателей на ресурсы в обход локального автоматического времени жизни.

   **Источник:** [Cppreference: RAII](https://en.cppreference.com/w/cpp/language/raii)

87. Почему RAII считается базовым подходом к управлению ресурсами в C++?

   **Ответ:** Потому что деструкторы автоматических переменных гарантированно вызываются компилятором при любых сценариях выхода из области видимости, включая исключения.

   **Пример:**

   ```cpp
   void work() {
       auto mem = std::make_unique<int[]>(1000);
       throw std::runtime_error("err"); // mem будет корректно освобожден
   }
   ```

   **Типичная ошибка:** Попытка написать сложную систему блоков `try/catch` для ручного очищения памяти вместо применения RAII.

   **Источник:** [Cppreference: RAII](https://en.cppreference.com/w/cpp/language/raii)

88. Что происходит с ресурсом, если он привязан к объекту RAII?

   **Ответ:** Ресурс освобождается детерминированно и безопасно ровно в тот момент, когда завершается время жизни этого RAII-объекта.

   **Пример:**

   ```cpp
   #include <mutex>
   std::mutex m;
   void task() {
       std::lock_guard<std::mutex> lk(m); // Захват
       // критическая секция
   } // Автоматическое освобождение мьютекса
   ```

   **Типичная ошибка:** Оставлять неблокируемые ручные вызовы `unlock()` перед каждым оператором `return`.

   **Источник:** [Cppreference: RAII](https://en.cppreference.com/w/cpp/language/raii)

89. Почему автоматические объекты безопаснее ручного `new/delete`?

   **Ответ:** Автоматические объекты управляются компилятором и исключают человеческий фактор: их невозможно забыть освободить, и они не могут подвергнуться двойному удалению.

   **Пример:**

   ```cpp
   std::string safe = "auto"; // Безопасно
   std::string* unsafe = new std::string("manual"); // Опасно
   delete unsafe;
   ```

   **Типичная ошибка:** Создание через `new` сущностей, которые могли бы просто быть объявлены локально на стеке.

   **Источник:** [Cppreference: Storage duration](https://en.cppreference.com/w/cpp/language/storage_duration)

90. Что такое стековая раскрутка при исключении?

   **Ответ:** Стековая раскрутка (stack unwinding) — процесс автоматического уничтожения локальных объектов при выходе из вложенных блоков в поисках подходящего обработчика `catch`.

   **Пример:**

   ```cpp
   void a() {
       std::string s = "unwind";
       throw std::runtime_error("boom"); // s.~basic_string() вызовется при раскрутке
   }
   ```

   **Типичная ошибка:** Думать, что при генерации исключения программа «рушится» без очистки ранее созданных локальных объектов.

   **Источник:** [Cppreference: throw expression](https://en.cppreference.com/w/cpp/language/throw)

91. Как стековая раскрутка связана с деструкторами?

   **Ответ:** При раскрутке стека рантайм C++ последовательно вызывает деструкторы для всех сконструированных объектов в обратном порядке их создания.

   **Пример:**

   ```cpp
   struct Tracer {
       ~Tracer() { /* гарантированно вызовется при раскрутке */ }
   };
   ```

   **Типичная ошибка:** Выбрасывать исключение из деструктора во время активной раскрутки другого исключения — это немедленный `std::terminate`.

   **Источник:** [Cppreference: throw expression](https://en.cppreference.com/w/cpp/language/throw)

92. Почему RAII особенно важен при исключениях?

   **Ответ:** При возникновении исключения нормальный поток выполнения прерывается, делая любые последующие ручные вызовы `delete` недостижимыми; только RAII гарантирует очистку.

   **Пример:**

   ```cpp
   void unsafe() {
       int* raw = new int(10);
       step_that_throws(); // утечка: delete raw не вызовется!
       delete raw;
   }
   ```

   **Типичная ошибка:** Попытка закрывать сокеты и освобождать память вручную после потенциально бросающих вызовов функций.

   **Источник:** [Cppreference: RAII](https://en.cppreference.com/w/cpp/language/raii)

93. Что такое объект, частично сконструированный при исключении из конструктора?

   **Ответ:** Объект, конструктор которого был прерван исключением: такой объект считается несозданным, и его собственный деструктор вызван не будет.

   **Пример:**

   ```cpp
   struct Complex {
       Complex() {
           // память выделена, но конструктор упал:
           throw std::runtime_error("failed");
       }
       ~Complex() { /* НЕ вызовется */ }
   };
   ```

   **Типичная ошибка:** Выделять в конструкторе сырые ресурсы до потенциально бросающей строки, полагая, что собственный деструктор их освободит.

   **Источник:** [Cppreference: Constructors](https://en.cppreference.com/w/cpp/language/initializer_list)

94. Какие деструкторы вызываются, если конструктор составного объекта выбросил исключение?

   **Ответ:** Вызываются деструкторы только тех базовых классов и полей-членов, конструирование которых было полностью завершено до выброса исключения.

   **Пример:**

   ```cpp
   struct Composed {
       std::string s; // 1. сконструирован успешно -> деструктор вызовется
       std::vector<int> v;
       Composed() : s("ok") {
           throw std::runtime_error("err"); // s разрушится, ~Composed() нет
       }
   };
   ```

   **Типичная ошибка:** Использовать в классе два сырых указателя, инициализируя их через `new`: если второй `new` бросит исключение, первый ресурс утечет навсегда.

   **Источник:** [Cppreference: Constructors](https://en.cppreference.com/w/cpp/language/initializer_list)

95. Что такое массив в памяти?

   **Ответ:** Непрерывная последовательность фиксированного количества объектов одного типа, расположенных непосредственно друг за другом без промежутков (кроме внутритипового выравнивания).

   **Пример:**

   ```cpp
   int arr[5] = {1, 2, 3, 4, 5}; // 20 непрерывных байт при sizeof(int) == 4
   ```

   **Типичная ошибка:** Предполагать, что элементы массива могут быть разбросаны компилятором по разным адресам.

   **Источник:** [Cppreference: Array declaration](https://en.cppreference.com/w/cpp/language/array)

96. Где могут размещаться массивы в зависимости от способа создания?

   **Ответ:** На стеке (локальные массивы), в сегментах статических данных (глобальные и static) или в куче (при создании через `new[]` или внутри `std::vector`).

   **Пример:**

   ```cpp
   int g_arr[10]; // static (.bss)
   void f() {
       int s_arr[10];           // stack
       int* d_arr = new int[10]; // heap
       delete[] d_arr;
   }
   ```

   **Типичная ошибка:** Создание динамических массивов переменной длины на стеке через non-standard расширение компилятора VLA.

   **Источник:** [Cppreference: Array declaration](https://en.cppreference.com/w/cpp/language/array)

97. Чем `new[]` отличается от `new`?

   **Ответ:** `new` конструирует одиночный объект; `new[]` выделяет память под $N$ элементов, сохраняет метаинформацию о размере массива и вызывает конструктор для каждого элемента.

   **Пример:**

   ```cpp
   Widget* single = new Widget;
   Widget* array = new Widget[10]; // 10 вызовов Widget()
   delete single;
   delete[] array;
   ```

   **Типичная ошибка:** Освобождение массива через одиночный `delete`.

   **Источник:** [Cppreference: new expression](https://en.cppreference.com/w/cpp/language/new)

98. Чем `delete[]` отличается от `delete`?

   **Ответ:** `delete[]` извлекает количество элементов массива из метаданных аллокатора, вызывает деструктор для каждого элемента массива в обратном порядке и освобождает весь блок.

   **Пример:**

   ```cpp
   delete[] array; // Вызывает деструктор для всех N элементов
   ```

   **Типичная ошибка:** Попытка вызвать `delete[]` для указателя на одиночный объект.

   **Источник:** [Cppreference: delete expression](https://en.cppreference.com/w/cpp/language/delete)

99. Что будет, если освободить массив через обычный `delete`?

   **Ответ:** Произойдет неопределенное поведение (UB): деструктор вызовется только для первого элемента, а смещение указателя аллокатора приведет к краху кучи.

   **Пример:**

   ```cpp
   std::string* arr = new std::string[5];
   delete arr; // UB: не вызовутся деструкторы остальных 4 строк, порча кучи!
   ```

   **Типичная ошибка:** Путать синтаксис удаления массивов при отказе от умных указателей `std::vector` / `std::unique_ptr<T[]>`.

   **Источник:** [Cppreference: delete expression](https://en.cppreference.com/w/cpp/language/delete)

100. Почему для массивов важно правильно сочетать `new[]` и `delete[]`?

   **Ответ:** Реализация оператора `new[]` обычно сохраняет служебный заголовок («cookie») со счетчиком элементов массива; `delete[]` знает о смещении этого заголовка, а `delete` — нет.

   **Пример:**

   ```cpp
   int* data = new int[50];
   delete[] data; // корректно считывает cookie и освобождает память
   ```

   **Типичная ошибка:** Считать, что для фундаментальных типов (`int`, `char`) вызов `delete` вместо `delete[]` безопасен — это все равно UB.

   **Источник:** [Cppreference: delete expression](https://en.cppreference.com/w/cpp/language/delete)

## Средний уровень

101. Что такое объектная модель C++ в контексте lifetime?

   **Ответ:** Формальная модель стандарта C++, описывающая, как сущности программы представляются в памяти, какими границами выравнивания, типами и жизненными циклами они обладают.

   **Пример:**

   ```cpp
   // Стандарт строго регламентирует, когда байты превращаются в объект типа T
   alignas(T) std::byte storage[sizeof(T)];
   ```

   **Типичная ошибка:** Думать о памяти абстрактно без привязки к модели типизации стандарта (Trivially Copyable, Object Representation).

   **Источник:** [Cppreference: Object](https://en.cppreference.com/w/cpp/language/object)

102. Когда начинается lifetime объекта, созданного в уже выделенной памяти?

   **Ответ:** Время жизни начинается строго в момент, когда завершается выполнение конструктора объекта (либо когда объект тривиального типа начинает существовать).

   **Пример:**

   ```cpp
   #include <new>
   alignas(int) char buf[sizeof(int)];
   int* p = new (buf) int(42); // Lifetime начинается по завершении placement new
   ```

   **Типичная ошибка:** Обращаться к буферу как к объекту типа `T` до фактического вызова конструктора.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

103. Достаточно ли просто выделить сырую память, чтобы объект начал существовать?

   **Ответ:** Для нетривиальных типов — абсолютно недостаточно; необходимо явное конструирование объекта для начала его времени жизни.

   **Пример:**

   ```cpp
   void* mem = std::malloc(sizeof(std::string));
   // std::string здесь НЕ существует! Чтение приведет к UB.
   std::free(mem);
   ```

   **Типичная ошибка:** Кастовать `malloc()` к указателям на нетривиальные классы без вызова конструктора.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

104. Чем выделение памяти отличается от создания объекта?

   **Ответ:** Выделение памяти лишь резервирует сырой диапазон адресов требуемого размера; создание объекта инициализирует это хранилище и запускает его время жизни.

   **Пример:**

   ```cpp
   void* raw = ::operator new(sizeof(std::string)); // 1. Выделение памяти
   std::string* s = new (raw) std::string("test");  // 2. Создание объекта
   s->~basic_string();                              // 3. Уничтожение объекта
   ::operator delete(raw);                          // 4. Освобождение памяти
   ```

   **Типичная ошибка:** Смешивать эти фазы при создании кастомных контейнеров или структур данных.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

105. Что такое placement new?

   **Ответ:** Форма оператора `new`, которая принимает указатель на уже выделенную память и конструирует объект непосредственно по этому адресу без повторного запроса памяти.

   **Пример:**

   ```cpp
   #include <new>
   char buffer[64];
   int* val = new (buffer) int(123);
   ```

   **Типичная ошибка:** Вызывать обычный `delete val` для объекта, сконструированного через placement new в стековом буфере.

   **Источник:** [Cppreference: new expression](https://en.cppreference.com/w/cpp/language/new#Placement_new)

106. Для чего нужен placement new?

   **Ответ:** Для конструирования объектов в специализированных буферах: внутри пулов памяти, арен, `std::vector`, `std::optional` или разделяемой памяти.

   **Пример:**

   ```cpp
   template<typename T>
   class OptionalStorage {
       alignas(T) char data[sizeof(T)];
   public:
       void construct(T val) { new (data) T(val); }
   };
   ```

   **Типичная ошибка:** Игнорирование требований выравнивания буфера памяти под целевой тип.

   **Источник:** [Cppreference: new expression](https://en.cppreference.com/w/cpp/language/new#Placement_new)

107. Когда используют ручное разделение “выделить память” и “сконструировать объект”?

   **Ответ:** При разработке высокоэффективных структур данных (векторы, циклические буферы), чтобы избежать дорогостоящей конструктивизации элементов до момента реальной вставки.

   **Пример:**

   ```cpp
   // Резервирование емкости в векторе выделяет сырую память,
   // а push_back конструирует элементы по одному
   ```

   **Типичная ошибка:** Конструирование дефолтных элементов массива заранее с последующей их перезаписью новыми значениями.

   **Источник:** [Cppreference: Allocator](https://en.cppreference.com/w/cpp/named_req/Allocator)

108. Нужно ли явно вызывать деструктор для объекта, созданного placement new?

   **Ответ:** Да, если тип нетривиальный, деструктор обязан быть вызван вручную (`obj->~Type()`), поскольку обычный `delete` для такого буфера вызывать нельзя.

   **Пример:**

   ```cpp
   alignas(std::string) char buf[sizeof(std::string)];
   auto* s = new (buf) std::string("demo");
   s->~basic_string(); // Явный вызов обязателен!
   ```

   **Типичная ошибка:** Применение `delete s` к объекту, размещенному во внешнем буфере.

   **Источник:** [Cppreference: Destructors](https://en.cppreference.com/w/cpp/language/destructor)

109. Что произойдёт, если вызвать деструктор, но не освободить сырой буфер?

   **Ответ:** Объект перестанет существовать, память останется выделенной; в этот же буфер можно сконструировать новый объект либо освободить буфер позже.

   **Пример:**

   ```cpp
   auto* s = new (buf) std::string("test");
   s->~basic_string(); // Память buf цела, но объект разрушен
   new (buf) std::string("next"); // Повторное использование
   ```

   **Типичная ошибка:** Обращение к полям старого объекта после вызова деструктора, пока буфер еще существует.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

110. Что произойдёт, если освободить память без вызова деструктора, когда он нужен?

   **Ответ:** Произойдет утечка всех ресурсов, которыми владел этот объект (динамическая память, файловые дескрипторы, сокеты).

   **Пример:**

   ```cpp
   void* mem = malloc(sizeof(std::vector<int>));
   auto* v = new (mem) std::vector<int>{1, 2, 3};
   free(mem); // Внутренний буфер вектора утечет навсегда!
   ```

   **Типичная ошибка:** Очистка `malloc`-буферов со сложными объектами через `free()` без ручного обхода деструкторов.

   **Источник:** [Cppreference: Destructors](https://en.cppreference.com/w/cpp/language/destructor)

111. Что такое trivially destructible тип?

   **Ответ:** Тип, чей деструктор не выполняет никаких действий (не является пользовательским, а все поля и базы также имеют тривиальные деструкторы).

   **Пример:**

   ```cpp
   struct Point { int x, y; };
   static_assert(std::is_trivially_destructible_v<Point>);
   ```

   **Типичная ошибка:** Попытка вызывать явный деструктор для примитивных типов (`p->~int()`), хотя для них разрушение не требует операций в рантайме.

   **Источник:** [Cppreference: is_trivially_destructible](https://en.cppreference.com/w/cpp/types/is_destructible)

112. Почему для trivially destructible типов управление lifetime проще?

   **Ответ:** Их время жизни завершается без необходимости вызова деструктора; память под них можно просто мгновенно освобождать или перезаписывать.

   **Пример:**

   ```cpp
   // В векторе тривиальных типов pop_back() не требует выполнения кода
   ```

   **Типичная ошибка:** Написание циклов вызова деструкторов над миллионами тривиальных структур.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

113. Что такое trivially copyable тип?

   **Ответ:** Тип, чье состояние может быть корректно скопировано простым копированием сырых байтов памяти (через `std::memcpy`).

   **Пример:**

   ```cpp
   #include <cstring>
   Point a{1, 2}, b;
   std::memcpy(&b, &a, sizeof(Point)); // Абсолютно законно
   ```

   **Типичная ошибка:** Копирование через `memcpy` типов со сложным владением (например, `std::string`, `std::unique_ptr`), что приводит к double free.

   **Источник:** [Cppreference: is_trivially_copyable](https://en.cppreference.com/w/cpp/types/is_trivially_copyable)

114. Всегда ли можно безопасно копировать объект побайтно?

   **Ответ:** Нет, побайтно можно копировать только trivially copyable типы; классы с указателями на себя или управляемыми ресурсами сломаются.

   **Пример:**

   ```cpp
   std::string s1 = "long string payload";
   std::string s2;
   std::memcpy(&s2, &s1, sizeof(std::string)); // Неопределенное поведение!
   ```

   **Типичная ошибка:** Побайтовая сериализация структур со ссылками или умными указателями.

   **Источник:** [Cppreference: is_trivially_copyable](https://en.cppreference.com/w/cpp/types/is_trivially_copyable)

115. Что такое выравнивание памяти?

   **Ответ:** Требование архитектуры процессора, чтобы адреса объектов определенного типа были кратны фиксированному числу байт ($1, 2, 4, 8, 16$).

   **Пример:**

   ```cpp
   alignas(16) int aligned_val;
   ```

   **Типичная ошибка:** Попытка прочитать 64-битное число с плавающей точкой по нечётному адресу на строгих архитектурах (вызывает Hardware Fault).

   **Источник:** [Cppreference: alignof operator](https://en.cppreference.com/w/cpp/language/alignof)

116. Что показывает `alignof`?

   **Ответ:** Оператор `alignof` возвращает строгое требование выравнивания (в байтах) для указанного типа данных.

   **Пример:**

   ```cpp
   #include <iostream>
   int main() {
       std::cout << alignof(double) << '\n'; // Обычно 8
   }
   ```

   **Типичная ошибка:** Путать размер объекта `sizeof` и его выравнивание `alignof`.

   **Источник:** [Cppreference: alignof operator](https://en.cppreference.com/w/cpp/language/alignof)

117. Почему неправильное выравнивание может быть проблемой?

   **Ответ:** Невыровненный доступ приводит либо к падению программы на уровне процессора (Bus Error / Alignment Fault), либо к серьезному падению производительности доступа к шине данных.

   **Пример:**

   ```cpp
   char raw[10];
   int* p = (int*)(raw + 1); // Не выровнен! Разыменование — UB
   ```

   **Типичная ошибка:** Кастовать сырые буферы `char*` напрямую к указателям на типы с большим выравниванием.

   **Источник:** [Cppreference: alignof operator](https://en.cppreference.com/w/cpp/language/alignof)

118. Что такое padding внутри объекта?

   **Ответ:** Неиспользуемые байты («прокладки»), автоматически вставляемые компилятором между полями или в конце структуры для соблюдения правил выравнивания каждого поля.

   **Пример:**

   ```cpp
   struct Sample {
       char c;    // 1 байт
       // 3 байта padding
       int i;     // 4 байта (выровнен по адресу, кратному 4)
   }; // sizeof == 8
   ```

   **Типичная ошибка:** Ожидать, что байты padding имеют определенные значения; их содержимое по умолчанию недетерминировано.

   **Источник:** [Cppreference: Object (Padding)](https://en.cppreference.com/w/cpp/language/object)

119. Почему размер структуры может быть больше суммы размеров полей?

   **Ответ:** Из-за необходимости внутреннего и концевого padding для обеспечения корректного выравнивания всех полей структуры и элементов в массивах таких структур.

   **Пример:**

   ```cpp
   struct Data {
       char a;   // 1 байт
       double b; // 8 байт
       char c;   // 1 байт
   }; // sizeof(Data) равен 24, а сумма полей — всего 10 байт!
   ```

   **Типичная ошибка:** Использовать размер структуры для вычисления объема чистых полезных данных при сохранении в файл.

   **Источник:** [Cppreference: sizeof operator](https://en.cppreference.com/w/cpp/language/sizeof)

120. Как порядок полей влияет на размер объекта и использование памяти?

   **Ответ:** Размещение полей в порядке убывания их выравнивания минимизирует количество байтов заполнителя (padding) и сокращает суммарный размер структуры.

   **Пример:**

   ```cpp
   struct Optimized {
       double b; // 8 байт
       char a;   // 1 байт
       char c;   // 1 байт
       // 6 байт концевого padding
   }; // sizeof(Optimized) равен 16 (вместо 24)
   ```

   **Типичная ошибка:** Случайный порядок объявления разнородных полей в структурах, раздувающий размер сотен тысяч объектов в памяти.

   **Источник:** [Cppreference: Data members](https://en.cppreference.com/w/cpp/language/data_members)

121. Что такое объектное представление (object representation)?

   **Ответ:** Последовательность из `sizeof(T)` байт, которую объект занимает в памяти, включая значащие биты и биты выравнивания (padding).

   **Пример:**

   ```cpp
   // Чтение через unsigned char* обращается к object representation
   ```

   **Типичная ошибка:** Сравнивать объекты через `memcmp(&a, &b, sizeof(T))` — байты padding могут отличаться даже у логически равных объектов.

   **Источник:** [Cppreference: Object](https://en.cppreference.com/w/cpp/language/object#Object_representation_and_value_representation)

122. Что такое storage reuse?

   **Ответ:** Повторное использование уже выделенного участка памяти для конструирования нового объекта (того же или другого типа) после завершения времени жизни предыдущего.

   **Пример:**

   ```cpp
   alignas(int) char buf[sizeof(int)];
   int* p1 = new (buf) int(1);
   p1->~int();
   int* p2 = new (buf) int(2); // Память переиспользована
   ```

   **Типичная ошибка:** Использование памяти без предварительного корректного завершения времени жизни старого объекта.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime#Storage_reuse)

123. Можно ли в одной и той же области памяти последовательно создавать разные объекты?

   **Ответ:** Да, при условии, что размер и выравнивание буфера достаточны для обоих типов, а время жизни первого объекта было корректно завершено до конструирования второго.

   **Пример:**

   ```cpp
   alignas(std::max(alignof(int), alignof(float))) char buf[16];
   new (buf) int(10);
   // ...
   new (buf) float(3.14f);
   ```

   **Типичная ошибка:** Создание объекта большего размера или с более строгим выравниванием в неподходящем буфере.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime#Storage_reuse)

124. Какие риски есть при повторном использовании памяти под другой тип?

   **Ответ:** Нарушение правил строгой синонимии типов (strict aliasing), обращение по старым указателям и порча невыровненной памяти.

   **Пример:**

   ```cpp
   // Использование старого указателя на тип A, когда в памяти уже лежит B — опасный UB
   ```

   **Типичная ошибка:** Попытка разыменования старых ссылок после реинициализации памяти под другой тип.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

125. Что такое lifetime у членов класса?

   **Ответ:** Время жизни каждого поля-члена строго заключено внутри времени жизни всего экземпляра класса: они создаются при конструировании объекта и уничтожаются при его разрушении.

   **Пример:**

   ```cpp
   struct Container {
       std::string member;
   };
   ```

   **Типичная ошибка:** Считать, что поле-член может пережить сам объект класса.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

126. В каком порядке создаются поля класса?

   **Ответ:** Исключительно в порядке их объявления внутри определения класса, независимо от того, в каком порядке они записаны в списке инициализации конструктора.

   **Пример:**

   ```cpp
   struct Order {
       int a;
       int b;
       Order() : b(10), a(b) {} // ОШИБКА: 'a' создается раньше, чем 'b'! 'a' инициализируется мусором
   };
   ```

   **Типичная ошибка:** Думать, что порядок в списке инициализации конструктора (`: b(0), a(1)`) управляет последовательностью создания полей.

   **Источник:** [Cppreference: Constructors](https://en.cppreference.com/w/cpp/language/initializer_list)

127. В каком порядке уничтожаются поля класса?

   **Ответ:** Строго в порядке, обратном порядку их объявления в определении класса.

   **Пример:**

   ```cpp
   struct Data {
       A a;
       B b;
   }; // При разрушении Data: сначала ~B(), затем ~A()
   ```

   **Типичная ошибка:** Полагаться в деструкторе поля `b` на доступ к ресурсам поля `a`, если `a` было объявлено позже `b`.

   **Источник:** [Cppreference: Destructors](https://en.cppreference.com/w/cpp/language/destructor)

128. Как lifetime базового класса связан с lifetime производного?

   **Ответ:** Базовый класс создается до начала выполнения конструктора производного класса и уничтожается после завершения деструктора производного класса.

   **Пример:**

   ```cpp
   struct Base {};
   struct Derived : Base {};
   ```

   **Типичная ошибка:** Обращаться к членам производного класса из конструктора базового класса.

   **Источник:** [Cppreference: Derived classes](https://en.cppreference.com/w/cpp/language/derived_class)

129. В каком порядке вызываются конструкторы при наследовании?

   **Ответ:** Сначала виртуальные базовые классы, затем прямые невиртуальные базовые классы (в порядке объявления в списке наследования), затем поля-члены, и лишь затем тело конструктора наследника.

   **Пример:**

   ```cpp
   struct D : B1, B2 {
       D() {} // 1. B1(), 2. B2(), 3. члены D, 4. тело D()
   };
   ```

   **Типичная ошибка:** Попытка передать неинициализированные поля производного класса в аргументы конструктора базового.

   **Источник:** [Cppreference: Derived classes](https://en.cppreference.com/w/cpp/language/derived_class)

130. В каком порядке вызываются деструкторы при наследовании?

   **Ответ:** В строго обратном порядке: тело деструктора наследника, деструкторы его полей, деструкторы прямых базовых классов и в конце деструкторы виртуальных баз.

   **Пример:**

   ```cpp
   // 1. тело ~D(), 2. поля D, 3. ~B2(), 4. ~B1()
   ```

   **Типичная ошибка:** Использование полиморфных вызовов в деструкторе: в момент деструктора базы производная часть уже мертва.

   **Источник:** [Cppreference: Destructors](https://en.cppreference.com/w/cpp/language/destructor)

131. Что такое временный материализованный объект?

   **Ответ:** Временный объект, фактически создаваемый в памяти при преобразовании численного значения (prvalue) в реальный объект (xvalue/glvalue), например, при привязке к ссылке.

   **Пример:**

   ```cpp
   struct Point { int x, y; };
   const Point& p = Point{1, 2}; // Temporary materialization conversion
   ```

   **Типичная ошибка:** Не понимать концепцию Guaranteed Copy Elision (C++17), где prvalue не материализуется до точки конечной инициализации.

   **Источник:** [Cppreference: Temporary materialization](https://en.cppreference.com/w/cpp/language/implicit_conversion#Temporary_materialization)

132. Как lifetime связан с копированием объекта?

   **Ответ:** Копирование создает абсолютно новый независимый объект с собственной памятью и собственным отдельным жизненным циклом.

   **Пример:**

   ```cpp
   std::string original = "text";
   std::string copy = original; // copy живет автономно от original
   ```

   **Типичная ошибка:** Считать, что изменение скопированного объекта может повлиять на оригинал при глубоком копировании.

   **Источник:** [Cppreference: Copy constructors](https://en.cppreference.com/w/cpp/language/copy_constructor)

133. Как lifetime связан с перемещением объекта?

   **Ответ:** Перемещение передает владение внутренними ресурсами от одного существующего объекта к другому; при этом оба объекта продолжают существовать до своих собственных деструкторов.

   **Пример:**

   ```cpp
   std::vector<int> src{1, 2, 3};
   std::vector<int> dst = std::move(src); // Ресурсы переданы, но src всё ещё жив
   ```

   **Типичная ошибка:** Думать, что перемещение «уничтожает» исходный объект.

   **Источник:** [Cppreference: Move constructors](https://en.cppreference.com/w/cpp/language/move_constructor)

134. Что означает “объект после перемещения остаётся валидным, но в неопределённом логическом состоянии”?

   **Ответ:** Инварианты класса соблюдены, его можно безопасно уничтожить или присвоить ему новое значение, но конкретное содержимое не гарантируется (valid but unspecified).

   **Пример:**

   ```cpp
   std::string s1 = "hello";
   std::string s2 = std::move(s1);
   s1.clear(); // Безопасно
   ```

   **Типичная ошибка:** Читать данные из перемещенного объекта в предположении, что он пустой (это не гарантируется стандартом для всех классов).

   **Источник:** [Cppreference: Move constructors](https://en.cppreference.com/w/cpp/language/move_constructor)

135. Почему lifetime перемещённого объекта не заканчивается после `std::move`?

   **Ответ:** Потому что `std::move` — это всего лишь приведение типа к rvalue-ссылке (`static_cast<T&&>`), а сам объект остается локальной переменной в своей области видимости.

   **Пример:**

   ```cpp
   void f() {
       std::string s = "test";
       std::string other = std::move(s);
   } // s.~basic_string() всё равно будет вызван здесь
   ```

   **Типичная ошибка:** Попытка повторно объявить переменную с тем же именем после `std::move`.

   **Источник:** [Cppreference: std::move](https://en.cppreference.com/w/cpp/utility/move)

136. Что реально делает `std::move` в контексте lifetime?

   **Ответ:** Ничего в рантайме. На этапе компиляции он лишь преобразует выражение в rvalue-ссылку, позволяя компилятору выбрать перемещающий конструктор или оператор присваивания.

   **Пример:**

   ```cpp
   int a = 5;
   std::move(a); // Никакого эффекта в ассемблере не производит вообще
   ```

   **Типичная ошибка:** Считать, что вызов `std::move(x)` физически освобождает память объекта `x`.

   **Источник:** [Cppreference: std::move](https://en.cppreference.com/w/cpp/utility/move)

137. Когда завершается lifetime параметров функции?

   **Ответ:** Параметры, переданные по значению, уничтожаются в момент завершения функции (стандартом допускается уничтожение в конце тела функции либо в выражении вызова).

   **Пример:**

   ```cpp
   void process(std::string val) {
       // ...
   } // val.~basic_string() вызывается при возврате
   ```

   **Типичная ошибка:** Возвращать ссылку на переданный по значению аргумент функции.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

138. Когда завершается lifetime возвращаемого значения?

   **Ответ:** Возвращаемый по значению временный объект живет до конца полного выражения, в котором была вызвана функция (если его жизнь не продлена привязкой к ссылке).

   **Пример:**

   ```cpp
   std::string make() { return "abc"; }
   int main() {
       make().size(); // Уничтожается после выполнения этой строки
   }
   ```

   **Типичная ошибка:** Сохранять `std::string_view` на возвращенный временный объект.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime#Temporary_object_lifetime)

139. Что такое copy elision?

   **Ответ:** Оптимизация компилятора, позволяющая пропустить вызовы копирующих и перемещающих конструкторов, конструируя объект сразу в целевой памяти.

   **Пример:**

   ```cpp
   struct Widget {};
   Widget w = Widget(); // В C++17 конструкторы копирования вообще не вызываются
   ```

   **Типичная ошибка:** Полагаться на побочные эффекты (например, логирование) в конструкторах копирования, которые могут быть выброшены оптимизатором.

   **Источник:** [Cppreference: Copy elision](https://en.cppreference.com/w/cpp/language/copy_elision)

140. Как copy elision влияет на количество реально существующих объектов?

   **Ответ:** Уменьшает количество создаваемых и уничтожаемых временных объектов: промежуточный объект попросту не создается.

   **Пример:**

   ```cpp
   // Без copy elision: создается временный объект, затем копируется, затем уничтожается.
   // С copy elision: конструируется сразу один итоговый объект.
   ```

   **Типичная ошибка:** Удивляться несовпадению числа вызовов конструкторов и деструкторов в отладочном выводе.

   **Источник:** [Cppreference: Copy elision](https://en.cppreference.com/w/cpp/language/copy_elision)

141. Что такое guaranteed copy elision в современном C++?

   **Ответ:** Начиная с C++17, правило языка, обязывающее не создавать временный объект при инициализации из prvalue (копирование исключается на уровне семантики языка).

   **Пример:**

   ```cpp
   struct NonMovable {
       NonMovable() = default;
       NonMovable(const NonMovable&) = delete;
       NonMovable(NonMovable&&) = delete;
   };
   NonMovable make() { return NonMovable(); } // Законно в C++17!
   NonMovable obj = make();
   ```

   **Типичная ошибка:** Считать, что функции не могут возвращать неперемещаемые типы по значению в C++17+.

   **Источник:** [Cppreference: Copy elision](https://en.cppreference.com/w/cpp/language/copy_elision)

142. Как NRVO связано с lifetime временных объектов?

   **Ответ:** NRVO (Named Return Value Optimization) позволяет компилятору конструировать именованную локальную переменную функции прямо на месте возвращаемого значения вызывающего контекста.

   **Пример:**

   ```cpp
   std::string create() {
       std::string result = "payload";
       return result; // NRVO: исключает перемещение
   }
   ```

   **Типичная ошибка:** Написание `return std::move(result);`, что ломает оптимизацию NRVO и заставляет компилятор всегда применять операцию перемещения.

   **Источник:** [Cppreference: Copy elision](https://en.cppreference.com/w/cpp/language/copy_elision)

143. Почему оптимизации копирования меняют наблюдаемое количество конструкторов и деструкторов?

   **Ответ:** Стандарт C++ явно разрешает компилятору исключать вызовы конструкторов и деструкторов при copy elision, даже если они содержат побочные эффекты.

   **Пример:**

   ```cpp
   struct Probe {
       Probe() { puts("Construct"); }
       ~Probe() { puts("Destruct"); }
   };
   Probe f() { return Probe(); }
   // Выведет по 1 разу "Construct" и "Destruct"
   ```

   **Типичная ошибка:** Завязывать бизнес-логику приложения на количество вызовов конструкторов копирования.

   **Источник:** [Cppreference: Copy elision](https://en.cppreference.com/w/cpp/language/copy_elision)

144. Что такое lifetime контейнера?

   **Ответ:** Интервал времени от завершения конструирования контейнера (`std::vector`, `std::list`) до завершения его деструктора.

   **Пример:**

   ```cpp
   {
       std::vector<int> v;
       // lifetime контейнера v
   }
   ```

   **Типичная ошибка:** Использовать ссылки на внутренние данные контейнера после завершения его времени жизни.

   **Источник:** [Cppreference: Containers library](https://en.cppreference.com/w/cpp/container)

145. Как lifetime контейнера влияет на lifetime его элементов?

   **Ответ:** Время жизни элементов контейнера строго ограничено временем жизни самого контейнера: элементы уничтожаются до освобождения памяти самого контейнера.

   **Пример:**

   ```cpp
   const int* ptr = nullptr;
   {
       std::vector<int> v = {10, 20};
       ptr = &v[0];
   }
   // ptr указывает на уничтоженный int!
   ```

   **Типичная ошибка:** Возврат ссылки на элемент локального контейнера из функции.

   **Источник:** [Cppreference: Containers library](https://en.cppreference.com/w/cpp/container)

146. Когда уничтожаются элементы `std::vector`?

   **Ответ:** При вызове методов очистки (`clear()`, `pop_back()`, `resize()`), при замене новыми элементами, при реаллокации буфера и в деструкторе вектора.

   **Пример:**

   ```cpp
   std::vector<std::string> v = {"a", "b"};
   v.pop_back(); // "b" уничтожена немедленно
   ```

   **Типичная ошибка:** Считать, что `pop_back()` лишь сдвигает указатель, оставляя объект живым.

   **Источник:** [Cppreference: vector::pop_back](https://en.cppreference.com/w/cpp/container/vector/pop_back)

147. Что происходит с элементами контейнера при его разрушении?

   **Ответ:** Контейнер последовательно вызывает деструкторы всех хранящихся в нем элементов, после чего возвращает динамический буфер своему аллокатору.

   **Пример:**

   ```cpp
   // Для каждого элемента вызывается T::~T()
   ```

   **Типичная ошибка:** Хранить в контейнере сырые указатели на динамические данные в надежде, что вектор сам сделает `delete` по адресам указателей.

   **Источник:** [Cppreference: vector::~vector](https://en.cppreference.com/w/cpp/container/vector/%7Evector)

148. Что такое инвалидирование указателей, ссылок и итераторов?

   **Ответ:** Состояние, при котором сохраненный указатель, ссылка или итератор больше не указывают на валидный элемент контейнера из-за перемещения, реаллокации или удаления данных.

   **Пример:**

   ```cpp
   std::vector<int> v = {1, 2, 3};
   int& ref = v[0];
   v.push_back(4); // Реаллокация! ref инвалидирована
   ```

   **Типичная ошибка:** Разыменование итератора после модифицирующей операции над контейнером.

   **Источник:** [Cppreference: Container iterator invalidation](https://en.cppreference.com/w/cpp/container#Iterator_invalidation)

149. Почему `std::vector::push_back` может инвалидировать указатели и ссылки на элементы?

   **Ответ:** Если текущий `size()` равен `capacity()`, вектор выделяет новый больший блок памяти, переносит туда существующие элементы и уничтожает их в старом буфере.

   **Пример:**

   ```cpp
   std::vector<int> v;
   v.reserve(1);
   v.push_back(1);
   int* p = &v[0];
   v.push_back(2); // Выделение нового буфера -> p инвалидирован
   ```

   **Типичная ошибка:** Кэширование указателей на элементы вектора в цикле, где происходит вставка.

   **Источник:** [Cppreference: vector::push_back](https://en.cppreference.com/w/cpp/container/vector/push_back)

150. Как реаллокация контейнера связана с памятью и lifetime объектов?

   **Ответ:** При реаллокации создаются новые объекты в новом блоке памяти (через перемещение/копирование), а старые объекты уничтожаются (завершают lifetime), освобождая старый буфер.

   **Пример:**

   ```cpp
   // 1. allocate(new_cap)
   // 2. placement new -> перенос элементов
   // 3. destroy элементов старого буфера
   // 4. deallocate(old_buf)
   ```

   **Типичная ошибка:** Не учитывать, что отсутствие `noexcept` у перемещающего конструктора заставляет `vector` выполнять дорогое глубокое копирование вместо перемещения.

   **Источник:** [Cppreference: vector::reserve](https://en.cppreference.com/w/cpp/container/vector/reserve)

## Сложный уровень

151. Что такое allocator в C++?

   **Ответ:** Абстракция, инкапсулирующая низкоуровневые стратегии управления памятью (выделение, освобождение) и управление жизненным циклом объектов для стандартных контейнеров.

   **Пример:**

   ```cpp
   #include <memory>
   std::allocator<int> alloc;
   ```

   **Типичная ошибка:** Думать, что `std::allocator` напрямую вызывает `malloc` и `free` без возможности кастомизации под арены или GPU-память.

   **Источник:** [Cppreference: Allocators](https://en.cppreference.com/w/cpp/named_req/Allocator)

152. Чем allocator управляет: памятью, объектами или обоими аспектами?

   **Ответ:** Аллокатор изначально отвечает за распределение сырой памяти (`allocate`/`deallocate`), а через `std::allocator_traits` также координирует конструирование и уничтожение объектов (`construct`/`destroy`).

   **Пример:**

   ```cpp
   auto p = alloc.allocate(1); // Выделил память
   std::allocator_traits<decltype(alloc)>::construct(alloc, p, 42); // Создал объект
   ```

   **Типичная ошибка:** Смешивать этапы выделения байт и создания объекта в единый шаг при реализации пользовательского аллокатора.

   **Источник:** [Cppreference: allocator_traits](https://en.cppreference.com/w/cpp/memory/allocator_traits)

153. Почему аллокатор и конструирование объектов — не одно и то же?

   **Ответ:** Память — это лишь последовательность байт с адресом, тогда как конструирование активирует инварианты типа, заполняет vptr (для полиморфных типов) и начинает lifetime.

   **Пример:**

   ```cpp
   // Аллокатор может заранее зарезервировать буфер под 1000 элементов,
   // но сконструировано в нем будет только 5 элементов.
   ```

   **Типичная ошибка:** Попытка вызвать `deallocate` над памятью, в которой ещё не вызваны деструкторы живых объектов.

   **Источник:** [Cppreference: allocator_traits](https://en.cppreference.com/w/cpp/memory/allocator_traits)

154. Что такое `std::allocator_traits`?

   **Ответ:** Стандартный фасадный интерфейс, предоставляющий стандартизованные методы доступа к функционалу аллокатора и определяющий значения по умолчанию для опциональных операций.

   **Пример:**

   ```cpp
   using Traits = std::allocator_traits<MyAlloc>;
   Traits::destroy(alloc, ptr);
   ```

   **Типичная ошибка:** Прямой вызов нестандартизованных методов пользовательских аллокаторов вместо использования интерфейса `std::allocator_traits`.

   **Источник:** [Cppreference: allocator_traits](https://en.cppreference.com/w/cpp/memory/allocator_traits)

155. Почему в контейнерах стандартной библиотеки важно разделение allocate/deallocate и construct/destroy?

   **Ответ:** Это гарантирует строгую безопасность исключений (exception safety) и предотвращает создание пустых/фиктивных объектов при резервировании емкости (`reserve()`).

   **Пример:**

   ```cpp
   // std::vector::reserve выделяет сырую память без вызова конструкторов по умолчанию
   ```

   **Типичная ошибка:** Требование наличия конструктора по умолчанию у типов элементов при вызове `reserve()`.

   **Источник:** [Cppreference: vector::reserve](https://en.cppreference.com/w/cpp/container/vector/reserve)

156. Что такое неинициализированная память?

   **Ответ:** Выделенная область адресного пространства, в которой еще не начался lifetime ни одного объекта данного типа, а её биты имеют произвольное (недетерминированное) состояние.

   **Пример:**

   ```cpp
   #include <memory>
   int* mem = std::allocator<int>{}.allocate(5); // 5 неинициализированных int
   ```

   **Типичная ошибка:** Чтение неинициализированной памяти через lvalue-выражения целевого типа.

   **Источник:** [Cppreference: uninitialized_copy](https://en.cppreference.com/w/cpp/memory/uninitialized_copy)

157. Чем `operator new` как функция выделения памяти отличается от выражения `new`?

   **Ответ:** Функция `operator new` просто аллоцирует сырой непрерывный кусок памяти заданного объема (аналог `malloc`), а выражение `new` вызывает эту функцию и затем запускает конструктор объекта.

   **Пример:**

   ```cpp
   void* raw = ::operator new(sizeof(Widget)); // Функция аллокации
   Widget* w = new Widget();                  // Выражение new
   ```

   **Типичная ошибка:** Попытка передать аргументы конструктора в системный вызов `::operator new(size_t)`.

   **Источник:** [Cppreference: operator new](https://en.cppreference.com/w/cpp/memory/new/operator_new)

158. Что делает глобальный `::operator new`?

   **Ответ:** Запрашивает у рантайма ОС блок сырой памяти требуемого размера; при неудаче вызывает зарегистрированный `std::new_handler` или выбрасывает исключение `std::bad_alloc`.

   **Пример:**

   ```cpp
   void* p = ::operator new(1024);
   ::operator delete(p);
   ```

   **Типичная ошибка:** Полагать, что `::operator new` возвращает `nullptr` при нехватке памяти (он бросает исключение, если не использован `std::nothrow`).

   **Источник:** [Cppreference: operator new](https://en.cppreference.com/w/cpp/memory/new/operator_new)

159. Что делает глобальный `::operator delete`?

   **Ответ:** Возвращает блок сырой памяти по указанному адресу обратно в пул менеджера кучи рантайма.

   **Пример:**

   ```cpp
   ::operator delete(raw);
   ```

   **Типичная ошибка:** Ожидать от `::operator delete` вызова деструкторов объектов, лежащих по этому адресу.

   **Источник:** [Cppreference: operator delete](https://en.cppreference.com/w/cpp/memory/new/operator_delete)

160. Почему `operator new` может выделить память без создания объекта?

   **Ответ:** Потому что его единственная зонная ответственность по стандарту — управление системным адресным пространством и предоставление сырых байт с нужным выравниванием.

   **Пример:**

   ```cpp
   // operator new ничего не знает о типе, конструируемом впоследствии
   ```

   **Типичная ошибка:** Попытка перегрузить `operator new` под конкретные бизнес-классы с логикой инициализации полей.

   **Источник:** [Cppreference: operator new](https://en.cppreference.com/w/cpp/memory/new/operator_new)

161. Что такое memory pool?

   **Ответ:** Шаблон проектирования и структура управления памятью, которая заранее выделяет большой монолитный блок памяти и раздает из него куски фиксированного размера за $O(1)$.

   **Пример:**

   ```cpp
   // Пул для мелких нод связного списка или графа
   ```

   **Типичная ошибка:** Пренебрежение фрагментацией памяти и требованиями выравнивания при нарезке буфера пула.

   **Источник:** [Cppreference: polymorphic_allocator](https://en.cppreference.com/w/cpp/memory/polymorphic_allocator)

162. Для чего используют арены памяти и пулы?

   **Ответ:** Для исключения системных накладных расходов на частые вызовы `malloc/free`, устранения фрагментации памяти и мгновенного освобождения всех объектов группы одной операцией.

   **Пример:**

   ```cpp
   // Игровая арена кадра (Frame Arena): в конце кадра очищается весь пул целиком
   ```

   **Типичная ошибка:** Забывать вызывать деструкторы нетривиальных объектов перед общей очисткой всей арены.

   **Источник:** [Cppreference: monotonic_buffer_resource](https://en.cppreference.com/w/cpp/memory/monotonic_buffer_resource)

163. Какие риски возникают у пулов в контексте lifetime?

   **Ответ:** Очистка арены уничтожает память без вызова деструкторов лежащих там объектов, что чревато утечками внешних ресурсов и использованием «мертвых» ссылок (Use-After-Free).

   **Пример:**

   ```cpp
   // Если объект держал файл или сокет, сброс арены приведет к утечке дескриптора
   ```

   **Типичная ошибка:** Размещение объектов с нетривиальными деструкторами в аренах, сбрасываемых без обхода деструкторов.

   **Источник:** [Cppreference: monotonic_buffer_resource](https://en.cppreference.com/w/cpp/memory/monotonic_buffer_resource)

164. Что такое lifetime объекта внутри union?

   **Ответ:** В каждый момент времени в `union` может быть активен только один член; время жизни этого члена начинается с его инициализации/placement new и прекращается перед сменой активного члена.

   **Пример:**

   ```cpp
   union U {
       int i;
       std::string s;
       U() {}
       ~U() {}
   };
   ```

   **Типичная ошибка:** Чтение неактивного члена union (в C++ это UB, в отличие от языка C).

   **Источник:** [Cppreference: Union declaration](https://en.cppreference.com/w/cpp/language/union)

165. Почему в union активен только один член?

   **Ответ:** Все члены union перекрываются в памяти и делят единое начальное адресное пространство; запись одного члена разрушает объектное представление других.

   **Пример:**

   ```cpp
   union Data { int a; float b; }; // &a == &b
   ```

   **Типичная ошибка:** Использование union для битового каста (Type Punning), что по стандарту C++ является строгим UB.

   **Источник:** [Cppreference: Union declaration](https://en.cppreference.com/w/cpp/language/union)

166. Что происходит с lifetime прежнего активного члена union при создании нового?

   **Ответ:** Если прежний член имел нетривиальный деструктор, программист обязан вручную вызвать его деструктор до конструирования нового члена, иначе старый lifetime завершится некорректно.

   **Пример:**

   ```cpp
   U u;
   new (&u.s) std::string("test");
   u.s.~basic_string(); // Явное завершение lifetime старого члена
   u.i = 10;            // Начало lifetime int
   ```

   **Типичная ошибка:** Прямая перезапись нетривиального поля простым присваиванием другого члена union.

   **Источник:** [Cppreference: Union declaration](https://en.cppreference.com/w/cpp/language/union)

167. Почему union требует аккуратного ручного управления lifetime нетривиальных типов?

   **Ответ:** Компилятор отключает неявные конструкторы и деструкторы union, если хотя бы один из его членов имеет нетривиальные специальные функции-члены.

   **Пример:**

   ```cpp
   // Использование std::variant безопаснее, чем низкоуровневый union
   ```

   **Типичная ошибка:** Попытка использовать `union` с `std::string` без реализации конструкторов и деструктора объемлющего объединения.

   **Источник:** [Cppreference: Union declaration](https://en.cppreference.com/w/cpp/language/union)

168. Что такое implicit-lifetime types?

   **Ответ:** Категория типов (начиная с C++20), чьи объекты могут автоматически начинать время жизни при выполнении определенных операций с сырой памятью (например, `memcpy`, `malloc`).

   **Пример:**

   ```cpp
   // Скалярные типы, агрегаты тривиальных типов, массивы таких типов
   ```

   **Типичная ошибка:** Предполагать, что типы с пользовательскими конструкторами могут неявно начинать lifetime при вызове `memcpy`.

   **Источник:** [Cppreference: Lifetime (Implicit-lifetime types)](https://en.cppreference.com/w/cpp/language/lifetime#Implicit-lifetime_types)

169. Какие типы могут начинать lifetime не только через обычный конструктор?

   **Ответ:** Типы с тривиальными конструкторами по умолчанию или деструкторами, а также встроенные примитивные типы (`char`, `int`, POD-структуры) при заполнении памяти через `std::start_lifetime_as` (C++23) или `memmove`.

   **Пример:**

   ```cpp
   // C++23: std::start_lifetime_as<T>(buffer)
   ```

   **Типичная ошибка:** Чтение нетривиальных объектов сразу после вызова `fread()` без конструирования.

   **Источник:** [Cppreference: start_lifetime_as](https://en.cppreference.com/w/cpp/memory/start_lifetime_as)

170. Что такое strict aliasing и как он связан с памятью?

   **Ответ:** Правило компилятора, запрещающее разыменовывать указатели разных типов, указывающие на одну и ту же область памяти (за редкими исключениями вроде `char*` или `std::byte*`).

   **Пример:**

   ```cpp
   float f = 5.0f;
   int* p = (int*)&f; // Нарушение Strict Aliasing Rule!
   ```

   **Типичная ошибка:** Игнорирование strict aliasing при оптимизациях `-O2/-O3`, приводящее к тому, что компилятор выбрасывает нужные чтения из памяти.

   **Источник:** [Cppreference: reinterpret_cast](https://en.cppreference.com/w/cpp/language/reinterpret_cast#Type_aliasing)

171. Почему чтение памяти как объекта другого несвязанного типа может быть ошибкой?

   **Ответ:** Компилятор полагает, что указатели несовместимых типов не могут перекрываться в памяти, и оптимизирует инструкции, переставляя или удаляя чтения и записи.

   **Пример:**

   ```cpp
   void evil(int* i, float* f) {
       *i = 1;
       *f = 2.0f;
       // Компилятор вправе считать, что *i остался равен 1
   }
   ```

   **Типичная ошибка:** Применение C-style кастов для конвертации между несвязанными указателями структур.

   **Источник:** [Cppreference: reinterpret_cast](https://en.cppreference.com/w/cpp/language/reinterpret_cast#Type_aliasing)

172. Что такое type punning?

   **Ответ:** Техника обхода системы типов языка для интерпретации битовой последовательности объекта одного типа в качестве значения другого типа.

   **Пример:**

   ```cpp
   #include <bit>
   float f = 1.0f;
   uint32_t u = std::bit_cast<uint32_t>(f); // Легальный C++20 Type Punning
   ```

   **Типичная ошибка:** Использование `*(uint32_t*)&f` вместо стандарта `std::bit_cast` или `std::memcpy`.

   **Источник:** [Cppreference: std::bit_cast](https://en.cppreference.com/w/cpp/numeric/bit_cast)

173. Почему `reinterpret_cast` не решает автоматически проблемы lifetime?

   **Ответ:** Он лишь указывает компилятору трактовать битовый шаблон адреса как указатель на другой тип, но не вызывает конструкторы и не начинает время жизни объекта целевого типа.

   **Пример:**

   ```cpp
   char buf[sizeof(std::string)];
   auto* s = reinterpret_cast<std::string*>(buf);
   s->size(); // UB: std::string в памяти не существует!
   ```

   **Типичная ошибка:** Считать, что `reinterpret_cast` создает новый объект по указанному адресу.

   **Источник:** [Cppreference: reinterpret_cast](https://en.cppreference.com/w/cpp/language/reinterpret_cast)

174. Что такое `std::launder`?

   **Ответ:** Функция стандартной библиотеки C++17, сообщающая компилятору, что по данному адресу был создан новый объект, помогая обойти чрезмерные оптимизации старых константных/ссылочных полей.

   **Пример:**

   ```cpp
   #include <new>
   struct X { const int n; };
   X* p = new X{1};
   new (p) X{2}; // Пересоздание объекта с константным полем
   int val = std::launder(p)->n; // Без launder компилятор вправе вернуть 1
   ```

   **Типичная ошибка:** Попытка «починить» с помощью `std::launder` обычные висячие указатели или невыровненную память.

   **Источник:** [Cppreference: std::launder](https://en.cppreference.com/w/cpp/utility/launder)

175. В каких случаях нужен `std::launder` после повторного создания объекта в той же памяти?

   **Ответ:** Когда новый объект создается на месте старого, и этот тип содержит поля, объявленные со спецификатором `const` или являющиеся ссылками.

   **Пример:**

   ```cpp
   struct Node { const int id; };
   // При пересоздании Node в том же буфере старый указатель требует обертки в std::launder
   ```

   **Типичная ошибка:** Игнорирование `std::launder` при реализации пулов объектов с `const`-членами.

   **Источник:** [Cppreference: std::launder](https://en.cppreference.com/w/cpp/utility/launder)

176. Что такое provenance указателя на концептуальном уровне?

   **Ответ:** Происхождение указателя — скрытая семантическая связь между указателем и исходным блоком памяти/объектом, из которого этот адрес был изначально вычислен.

   **Пример:**

   ```cpp
   int a = 1;
   int b = 2;
   int* p = &a + 1; // Даже если случайно равен &b, обращаться к 'b' через p — UB!
   ```

   **Типичная ошибка:** Выход за границы одного массива для перехода к адресам соседнего объекта.

   **Источник:** [Cppreference: Pointer declaration](https://en.cppreference.com/w/cpp/language/pointer)

177. Почему не любой адрес в памяти можно безопасно интерпретировать как любой объект?

   **Ответ:** Потому что доступ ограничивается требованиями к выравниванию (alignment), допустимостью синонимов (strict aliasing), а также реальным наличием начатого lifetime объекта этого типа по данному адресу.

   **Пример:**

   ```cpp
   // Невыровненный адрес или память чужого объекта ведут к hardware traps или UB
   ```

   **Типичная ошибка:** Каст произвольного адреса сетевого пакета к сложной C++ структуре.

   **Источник:** [Cppreference: reinterpret_cast](https://en.cppreference.com/w/cpp/language/reinterpret_cast)

178. Что такое subobject lifetime?

   **Ответ:** Время жизни подобъекта (поля класса или базового класса), которое строго вложено в границы времени жизни полного объемлющего объекта.

   **Пример:**

   ```cpp
   struct Full {
       struct Sub {} sub;
   };
   ```

   **Типичная ошибка:** Попытка продлить жизнь ссылки на подобъект после разрушения полного объекта.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

179. Как lifetime подобъекта связан с lifetime полного объекта?

   **Ответ:** Время жизни подобъекта начинается после начала конструирования полного объекта и завершается до завершения деструктора полного объекта.

   **Пример:**

   ```cpp
   // Конструктор Full: конструирует sub -> Full готов
   // Деструктор Full: завершает Full -> разрушает sub
   ```

   **Типичная ошибка:** Обращение к полям из деструктора полного объекта после того, как они уже были уничтожены в обратном порядке.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

180. Что происходит с lifetime члена класса, если разрушен весь объект?

   **Ответ:** Время жизни каждого члена класса немедленно и бесповоротно завершается; любые внешние ссылки на эти члены становятся висячими.

   **Пример:**

   ```cpp
   std::string* s_ptr = nullptr;
   {
       struct Box { std::string s = "nested"; } b;
       s_ptr = &b.s;
   }
   // s_ptr теперь висячий
   ```

   **Типичная ошибка:** Сохранение ссылок на внутренние поля временных структур.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

181. Что такое base subobject?

   **Ответ:** Часть объекта производного класса, представляющая экземпляр унаследованного базового класса.

   **Пример:**

   ```cpp
   struct Base { int x; };
   struct Derived : Base { int y; }; // Base внутри Derived — это base subobject
   ```

   **Типичная ошибка:** Думать, что базовый объект размещается в изолированном отдельном участке динамической памяти.

   **Источник:** [Cppreference: Derived classes](https://en.cppreference.com/w/cpp/language/derived_class)

182. Как lifetime базового подобъекта соотносится с lifetime производного объекта?

   **Ответ:** Базовый подобъект начинает жизнь раньше и завершает жизнь позже, чем код конструктора и деструктора самого производного класса.

   **Пример:**

   ```cpp
   // 1. Base::Base()
   // 2. Derived::Derived()
   // 3. Derived::~Derived()
   // 4. Base::~Base()
   ```

   **Типичная ошибка:** Попытка обращения к еще не созданным полям наследника из виртуальных функций, вызываемых в конструкторе базы.

   **Источник:** [Cppreference: Derived classes](https://en.cppreference.com/w/cpp/language/derived_class)

183. Почему виртуальный деструктор важен для корректного lifetime при полиморфизме?

   **Ответ:** Без виртуального деструктора оператор `delete base_ptr` вызовет деструктор только базового класса; поля производного класса не будут уничтожены, а вызов `operator delete` может получить неверный адрес (UB).

   **Пример:**

   ```cpp
   struct Base { virtual ~Base() = default; }; // Виртуальный деструктор обязателен!
   struct Derived : Base { std::string data; };
   ```

   **Типичная ошибка:** Наследование от классов стандартной библиотеки (`std::vector`), у которых нет виртуального деструктора.

   **Источник:** [Cppreference: Destructors (Virtual destructors)](https://en.cppreference.com/w/cpp/language/destructor#Virtual_destructors)

184. Что будет, если удалить производный объект через указатель на базовый класс без виртуального деструктора?

   **Ответ:** Это чистое неопределенное поведение (UB) по стандарту: деструктор наследника не выполнится, внутренние ресурсы утекут, память может разрушиться.

   **Пример:**

   ```cpp
   struct Base { ~Base() {} };
   struct Derived : Base { std::vector<int> v{1, 2}; };
   Base* b = new Derived();
   delete b; // UB! Утечка памяти вектора v
   ```

   **Типичная ошибка:** Забывать ключевое слово `virtual` у деструктора базового класса полиморфной иерархии.

   **Источник:** [Cppreference: delete expression](https://en.cppreference.com/w/cpp/language/delete)

185. Как lifetime связан с полиморфным удалением?

   **Ответ:** Виртуальный деструктор обеспечивает динамический поиск реального типа конечного объекта во время выполнения, позволяя полностью свернуть весь стек деструкторов от самого нижнего наследника до корня.

   **Пример:**

   ```cpp
   Base* p = new MostDerived();
   delete p; // Через vtable запускает цепочку: ~MostDerived -> ~Derived -> ~Base
   ```

   **Типичная ошибка:** Использование множественного наследования без полиморфных деструкторов при удалении через указатели на вторичные базы.

   **Источник:** [Cppreference: Destructors](https://en.cppreference.com/w/cpp/language/destructor)

186. Что такое destruction sequence?

   **Ответ:** Строго стандартизованная последовательность шагов, выполняемая средой выполнения при разрушении объекта класса.

   **Пример:**

   ```cpp
   // 1. Тело деструктора
   // 2. Деструкторы полей в обратном порядке
   // 3. Деструкторы прямых не-виртуальных баз
   // 4. Деструкторы виртуальных баз
   ```

   **Типичная ошибка:** Попытка вручную вызывать методы членов класса в деструкторе базового класса.

   **Источник:** [Cppreference: Destructors](https://en.cppreference.com/w/cpp/language/destructor)

187. Какие действия происходят при разрушении объекта класса шаг за шагом?

   **Ответ:** Сначала исполняется тело функции `~Class()`, затем в порядке, обратном объявлению, разрушаются нестатические члены класса, затем в обратном порядке разрушаются базовые классы.

   **Пример:**

   ```cpp
   struct S : B {
       M1 m1;
       M2 m2;
       ~S() { /* 1. тело ~S */ }
       // 2. ~M2(), 3. ~M1(), 4. ~B()
   };
   ```

   **Типичная ошибка:** Использование ресурса поля `m2` внутри деструктора поля `m1`.

   **Источник:** [Cppreference: Destructors](https://en.cppreference.com/w/cpp/language/destructor)

188. Почему порядок уничтожения обратен порядку создания?

   **Ответ:** Порядок создания гарантирует, что более поздние сущности могут безопасно полагаться на уже сконструированные ранние; уничтожение в обратном порядке сохраняет эту гарантию симметрично.

   **Пример:**

   ```cpp
   // Если B зависит от A:
   // A создается первым -> B использует A.
   // B уничтожается первым -> A всё еще валиден во время закрытия B.
   ```

   **Типичная ошибка:** Проектирование классов с циклическими зависимостями между полями.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

189. Что такое статическая инициализация?

   **Ответ:** Фаза инициализации статических объектов, выполняемая до запуска любого динамического кода: включает нулевую инициализацию (zero-initialization) и инициализацию константных выражений (constant initialization).

   **Пример:**

   ```cpp
   int zero;               // zero-initialization (гарантированно 0)
   constexpr int val = 42; // constant initialization
   ```

   **Типичная ошибка:** Путать статическую инициализацию с динамической инициализацией глобальных объектов во время исполнения.

   **Источник:** [Cppreference: Static initialization](https://en.cppreference.com/w/cpp/language/initialization#Non-local_variables)

190. Что такое динамическая инициализация объектов со static storage duration?

   **Ответ:** Инициализация глобальных или `static` переменных, требующая вычисления выражений во время выполнения программы или вызова пользовательских конструкторов.

   **Пример:**

   ```cpp
   int init_val() { return 100; }
   int g_val = init_val(); // Динамическая инициализация
   ```

   **Типичная ошибка:** Предполагать, что все глобальные переменные инициализируются до компиляции.

   **Источник:** [Cppreference: Dynamic initialization](https://en.cppreference.com/w/cpp/language/initialization#Non-local_variables)

191. Что такое static initialization order fiasco?

   **Ответ:** Ошибка времени выполнения, возникающая, когда глобальный объект в одной единице трансляции зависит от другого глобального объекта в другой единице трансляции, а порядок их динамической инициализации стандартом не определен.

   **Пример:**

   ```cpp
   // file1.cpp: int x = get_y() + 1;
   // file2.cpp: int y = 42; int get_y() { return y; }
   // Если file1 инициализируется раньше — x получит мусор!
   ```

   **Типичная ошибка:** Обращение к внешним глобальным объектам из конструкторов других глобальных сущностей.

   **Источник:** [Cppreference: Non-local variables](https://en.cppreference.com/w/cpp/language/initialization#Non-local_variables)

192. Почему порядок инициализации глобальных объектов между единицами трансляции опасен?

   **Ответ:** Стандарт не фиксирует последовательность компиляции и компоновки файлов; программа может успешно работать на одной платформе и падать на другой.

   **Пример:**

   ```cpp
   // В одном компиляторе порядок файлов в линковщике спасает код, в другом приводит к краху
   ```

   **Типичная ошибка:** Полагаться на порядок передачи исходных файлов в командной строке компилятора.

   **Источник:** [Cppreference: Non-local variables](https://en.cppreference.com/w/cpp/language/initialization#Non-local_variables)

193. Как локальные static-переменные помогают избежать части проблем порядка инициализации?

   **Ответ:** Идиома «Meyers' Singleton»: помещение глобального объекта внутрь функции как локального `static` гарантирует его создание строго при первом вызове этой функции (on-demand).

   **Пример:**

   ```cpp
   Database& get_db() {
       static Database db; // Инициализируется гарантированно в момент первого обращения
       return db;
   }
   ```

   **Типичная ошибка:** Возврат по значению вместо возврата по ссылке из синглтона Мейерса.

   **Источник:** [Cppreference: Static local variables](https://en.cppreference.com/w/cpp/language/storage_duration#Static_local_variables)

194. Что такое constant initialization?

   **Ответ:** Форма статической инициализации, при которой переменная инициализируется константным выражением на этапе компиляции, исключая любые риски порядка инициализации.

   **Пример:**

   ```cpp
   struct ConstData { int val; };
   constinit ConstData cd{10}; // Вычисляется строго на этапе компиляции
   ```

   **Типичная ошибка:** Вызов не-constexpr функций внутри инициализатора `constinit`.

   **Источник:** [Cppreference: constant initialization](https://en.cppreference.com/w/cpp/language/constant_initialization)

195. Почему `constexpr` и `constinit` важны для контроля инициализации и lifetime?

   **Ответ:** Они гарантируют, что объект будет полностью готов к работе еще до запуска любого динамического кода и входа в `main()`, устраняя race conditions и order fiasco.

   **Пример:**

   ```cpp
   constinit static int state = 1; // Защищен от порядка динамической инициализации
   ```

   **Типичная ошибка:** Считать, что `constinit` делает переменную неизменяемой (`const`).

   **Источник:** [Cppreference: constinit](https://en.cppreference.com/w/cpp/language/constinit)

196. Что такое `constinit`?

   **Ответ:** Ключевое слово (C++20), требующее, чтобы переменная со статической или thread-local длительностью хранения была инициализирована исключительно на этапе компиляции.

   **Пример:**

   ```cpp
   constinit int global_flag = 100;
   ```

   **Типичная ошибка:** Попытка применить `constinit` к локальной автоматической переменной внутри функции.

   **Источник:** [Cppreference: constinit](https://en.cppreference.com/w/cpp/language/constinit)

197. Чем `constinit` отличается от `constexpr`?

   **Ответ:** `constexpr` объявляет переменную константой (read-only), а `constinit` лишь форсирует инициализацию на этапе компиляции, оставляя саму переменную изменяемой в рантайме.

   **Пример:**

   ```cpp
   constinit int counter = 0; // Инициализирован на этапе сборки
   void inc() { counter++; }  // Изменение разрешено!
   ```

   **Типичная ошибка:** Думать, что `constinit` запрещает перезапись значения переменной в процессе работы программы.

   **Источник:** [Cppreference: constinit](https://en.cppreference.com/w/cpp/language/constinit)

198. Что такое destruction order fiasco для глобальных объектов?

   **Ответ:** Ситуация при завершении программы, когда один глобальный объект в своем деструкторе пытается обратиться к другому глобальному объекту, который уже был разрушен.

   **Пример:**

   ```cpp
   // Деструктор Cache обращается к Logger, но Logger уже уничтожен рантаймом
   ```

   **Типичная ошибка:** Логирование завершения программы из деструкторов статических подсистем без контроля времени жизни логгера.

   **Источник:** [Cppreference: exit](https://en.cppreference.com/w/cpp/utility/program/exit)

199. Почему использование одного глобального объекта в деструкторе другого может быть опасно?

   **Ответ:** Поскольку порядок их разрушения строго обратен порядку инициализации, малейшее изменение логики старта программы может неявно изменить порядок деструкторов и привести к краху на выходе из процесса.

   **Пример:**

   ```cpp
   struct A { ~A() { get_b().flush(); } }; // Если b уже уничтожен — крах
   ```

   **Типичная ошибка:** Создание неявных циклических связей между деструкторами глобальных сервисов.

   **Источник:** [Cppreference: exit](https://en.cppreference.com/w/cpp/utility/program/exit)

200. Что такое lifetime extension и какие у него ограничения?

   **Ответ:** Механизм стандарта, позволяющий продлить жизнь временного объекта привязкой к ссылке; он НЕ работает для возвращаемых значений функций, полей классов и ссылок в аргументах вызовов.

   **Пример:**

   ```cpp
   const std::string& ok = std::string("test"); // Работает
   struct Bad { const std::string& ref; };      // НЕ работает для поля!
   ```

   **Типичная ошибка:** Попытка продлить жизнь временного объекта через передачу ссылки внутрь конструктора структуры.

   **Источник:** [Cppreference: Reference initialization](https://en.cppreference.com/w/cpp/language/reference_initialization#Lifetime_of_a_temporary)

201. Продлевает ли lifetime привязка временного объекта к полю класса-ссылке?

   **Ответ:** Нет, стандарт C++ прямо указывает, что привязка временного объекта к полю-ссылке в конструкторе продлевает его жизнь лишь до окончания работы самого конструктора.

   **Пример:**

   ```cpp
   struct Holder {
       const int& val;
       Holder(int v) : val(v) {} // ОШИБКА: 'v' уничтожится при выходе из конструктора!
   };
   ```

   **Типичная ошибка:** Хранение константных ссылок на параметры конструктора внутри полей структуры.

   **Источник:** [Cppreference: Reference initialization](https://en.cppreference.com/w/cpp/language/reference_initialization#Lifetime_of_a_temporary)

202. Продлевает ли lifetime возврат `const T&` на временный объект из функции?

   **Ответ:** Нет, временный объект, созданный внутри функции, уничтожается при выходе из нее, и возвращаемая ссылка сразу становится недействительной.

   **Пример:**

   ```cpp
   const std::string& get() {
       return std::string("oops"); // Warning: returning reference to temporary
   }
   ```

   **Типичная ошибка:** Присвоение результата такой функции локальной константной ссылке в надежде на lifetime extension.

   **Источник:** [Cppreference: Reference initialization](https://en.cppreference.com/w/cpp/language/reference_initialization#Lifetime_of_a_temporary)

203. Почему некоторые ситуации с временными объектами выглядят безопасно, но не являются такими?

   **Ответ:** Из-за синтаксической скрытности: функции могут принимать параметры по ссылке и возвращать их наружу, скрывая факт привязки к временному объекту первой строки.

   **Пример:**

   ```cpp
   const int& val = std::max(10, 20); // std::max принимает по ссылке и возвращает ссылку!
   // Литералы 10 и 20 материализуются во временные объекты, умирающие в конце строки: val висячая!
   ```

   **Типичная ошибка:** Использование `std::min` / `std::max` с временными объектами при сохранении ссылки.

   **Источник:** [Cppreference: min](https://en.cppreference.com/w/cpp/algorithm/min)

204. Что такое lifetime у строки, возвращаемой `c_str()`?

   **Ответ:** Указатель `c_str()` указывает напрямую на внутренний непрерывный массив символов объекта `std::string` и живет ровно столько, сколько существует сама строка без модификаций.

   **Пример:**

   ```cpp
   std::string s = "text";
   const char* c = s.c_str(); // Валиден, пока s не изменена и не уничтожена
   ```

   **Типичная ошибка:** Вызов `c_str()` у временной строки (`const char* p = (a + b).c_str();`).

   **Источник:** [Cppreference: basic_string::c_str](https://en.cppreference.com/w/cpp/string/basic_string/c_str)

205. Когда указатель, полученный через `c_str()`, становится недействительным?

   **Ответ:** При вызове любого неконстантного метода строки (вставка, удаление, резервирование) или в момент вызова деструктора объекта `std::string`.

   **Пример:**

   ```cpp
   std::string s = "old";
   const char* p = s.c_str();
   s += "_very_long_string_that_reallocates"; // p инвалидирован!
   ```

   **Типичная ошибка:** Сохранение указателя `c_str()` для долговременного использования между вызовами API.

   **Источник:** [Cppreference: basic_string::c_str](https://en.cppreference.com/w/cpp/string/basic_string/c_str)

206. Как изменение `std::string` влияет на валидность ранее полученных указателей?

   **Ответ:** Любая модификация строки может вызвать реаллокацию внутреннего буфера кучи, делая все ранее полученные указатели висячими.

   **Пример:**

   ```cpp
   s.append("more data"); // Старый указатель c_str() указывает на освобожденную память
   ```

   **Типичная ошибка:** Чтение из `c_str()` после передачи той же строки по неконстантной ссылке в метод модификации.

   **Источник:** [Cppreference: basic_string](https://en.cppreference.com/w/cpp/string/basic_string)

207. Как реаллокация `std::vector` влияет на lifetime элементов?

   **Ответ:** Старые элементы уничтожаются (их lifetime завершается), а в новом выделенном блоке памяти конструируются новые элементы.

   **Пример:**

   ```cpp
   // Все старые указатели на элементы становятся висячими
   ```

   **Типичная ошибка:** Доступ к элементам через ранее сохраненные ссылки после вызова `insert()` или `push_back()`.

   **Источник:** [Cppreference: vector](https://en.cppreference.com/w/cpp/container/vector)

208. Уничтожаются ли старые элементы при реаллокации контейнера?

   **Ответ:** Да, старые элементы перемещаются или копируются во вновь выделенный буфер, после чего в старом буфере для них вызываются деструкторы.

   **Пример:**

   ```cpp
   // Для старых элементов отрабатывает деструктор T::~T()
   ```

   **Типичная ошибка:** Ожидать, что реаллокация перемещает память «на месте» без перезапуска времени жизни элементов.

   **Источник:** [Cppreference: vector::reserve](https://en.cppreference.com/w/cpp/container/vector/reserve)

209. Почему после realocation старые указатели становятся висячими?

   **Ответ:** Потому что исходный блок памяти полностью деаллоцируется и возвращается аллокатору, а адреса элементов изменяются на новый диапазон.

   **Пример:**

   ```cpp
   std::vector<int> v = {1};
   int* p = &v[0];
   v.resize(1000); // Адрес буфера изменился!
   *p = 5; // Use-After-Free
   ```

   **Типичная ошибка:** Сохранение индексов элементов в виде прямых указателей в динамически растущем векторе.

   **Источник:** [Cppreference: vector](https://en.cppreference.com/w/cpp/container/vector)

210. Что такое move-only владелец ресурса с точки зрения lifetime?

   **Ответ:** Тип, запрещающий копирование и поддерживающий исключительно перемещение; он гарантирует строго уникальное владение ресурсом ровно в одном месте программы.

   **Пример:**

   ```cpp
   std::unique_ptr<int> u = std::make_unique<int>(10);
   // std::unique_ptr нельзя скопировать, только передать (move)
   ```

   **Типичная ошибка:** Попытка передать `std::unique_ptr` по значению без вызова `std::move`.

   **Источник:** [Cppreference: unique_ptr](https://en.cppreference.com/w/cpp/memory/unique_ptr)

211. Почему `std::unique_ptr` хорошо выражает владение и время жизни?

   **Ответ:** Он исключает накладные расходы рантайма (zero overhead), однозначно определяет единственного хозяина объекта и автоматически удаляет его при выходе из области видимости.

   **Пример:**

   ```cpp
   std::unique_ptr<FILE, decltype(&fclose)> f(fopen("a.txt", "r"), &fclose);
   ```

   **Типичная ошибка:** Использование `std::shared_ptr` там, где логически достаточно монопольного владения через `std::unique_ptr`.

   **Источник:** [Cppreference: unique_ptr](https://en.cppreference.com/w/cpp/memory/unique_ptr)

212. Как `std::shared_ptr` моделирует совместное владение lifetime?

   **Ответ:** Через счетчик ссылок (reference count) в контрольном блоке: объект продолжает жить в памяти до тех пор, пока существует хотя бы один экземпляр `std::shared_ptr`, указывающий на него.

   **Пример:**

   ```cpp
   auto sp1 = std::make_shared<int>(42);
   auto sp2 = sp1; // use_count == 2
   ```

   **Типичная ошибка:** Передача сырого адреса `get()` в другой независимый `shared_ptr`, что создаст два несвязанных контрольных блока и double free.

   **Источник:** [Cppreference: shared_ptr](https://en.cppreference.com/w/cpp/memory/shared_ptr)

213. Что такое control block у `shared_ptr`?

   **Ответ:** Специальный служебный динамический объект, хранящий счетчик сильных ссылок (`shared_count`), счетчик слабых ссылок (`weak_count`), кастомный делитер и аллокатор.

   **Пример:**

   ```cpp
   // make_shared размещает объект и контрольный блок в едином монолитном куске памяти
   ```

   **Типичная ошибка:** Создание нескольких control blocks на один и тот же сырой указатель (`shared_ptr<T>(ptr)` дважды).

   **Источник:** [Cppreference: shared_ptr](https://en.cppreference.com/w/cpp/memory/shared_ptr)

214. Когда реально уничтожается объект, на который указывает `shared_ptr`?

   **Ответ:** В момент, когда счетчик сильных ссылок (`use_count()`) уменьшается до нуля при разрушении или сбросе последнего владеющего им `std::shared_ptr`.

   **Пример:**

   ```cpp
   sp1.reset(); // use_count = 1
   sp2.reset(); // use_count = 0 -> вызов деструктора объекта
   ```

   **Типичная ошибка:** Путать уничтожение управляемого объекта и освобождение самого контрольного блока (блок живет, пока есть `std::weak_ptr`).

   **Источник:** [Cppreference: shared_ptr](https://en.cppreference.com/w/cpp/memory/shared_ptr)

215. Почему `shared_ptr` не решает все проблемы lifetime?

   **Ответ:** Он не защищает от циклических ссылок, создает накладные расходы на атомарные счетчики и маскирует архитектурные ошибки проектирования владения в системе.

   **Пример:**

   ```cpp
   // Не спасает от гонок данных над самим управляемым объектом
   ```

   **Типичная ошибка:** Использование `shared_ptr` повсеместно «на всякий случай» вместо ясной архитектуры владения.

   **Источник:** [Cppreference: shared_ptr](https://en.cppreference.com/w/cpp/memory/shared_ptr)

216. Что такое циклическое владение через `shared_ptr`?

   **Ответ:** Ситуация, когда два или более объектов содержат внутри себя `std::shared_ptr` друг на друга, образуя замкнутый цикл владения.

   **Пример:**

   ```cpp
   struct Node {
       std::shared_ptr<Node> next;
   };
   auto a = std::make_shared<Node>();
   auto b = std::make_shared<Node>();
   a->next = b;
   b->next = a; // Цикл! Память никогда не освободится
   ```

   **Типичная ошибка:** Проектирование графов или двусвязных списков на одних лишь `std::shared_ptr`.

   **Источник:** [Cppreference: shared_ptr](https://en.cppreference.com/w/cpp/memory/shared_ptr)

217. Почему цикл из `shared_ptr` приводит к утечке?

   **Ответ:** Счетчик ссылок ни одного из объектов в цикле никогда не сможет опуститься до нуля, так как каждый объект удерживается сильной ссылкой из соседнего узла.

   **Пример:**

   ```cpp
   // Исходные внешние shared_ptr уничтожены, но счетчики узлов равны 1: деструкторы не вызываются
   ```

   **Типичная ошибка:** Попытка разрушить цикл без явного разрыва одного из ребер (`a->next.reset()`).

   **Источник:** [Cppreference: shared_ptr](https://en.cppreference.com/w/cpp/memory/shared_ptr)

218. Как `std::weak_ptr` помогает управлять lifetime без владения?

   **Ответ:** `weak_ptr` наблюдает за объектом, не увеличивая сильный счетчик ссылок; перед доступом он позволяет безопасно проверить жив ли объект через метод `lock()`.

   **Пример:**

   ```cpp
   std::shared_ptr<int> sp = std::make_shared<int>(5);
   std::weak_ptr<int> wp = sp;
   if (auto locked = wp.lock()) {
       // Объект гарантированно жив внутри блока
   }
   ```

   **Типичная ошибка:** Попытка прямого разыменования `weak_ptr` без предварительного преобразования в `shared_ptr` через `lock()`.

   **Источник:** [Cppreference: weak_ptr](https://en.cppreference.com/w/cpp/memory/weak_ptr)

219. Что такое observer pointer в контексте времени жизни?

   **Ответ:** Указатель или ссылка, предназначенная исключительно для кратковременного наблюдения за объектом без каких-либо прав на продление его жизни или его уничтожение.

   **Пример:**

   ```cpp
   void draw(const Mesh* mesh); // mesh — observer pointer
   ```

   **Типичная ошибка:** Сохранение observer pointer в долговременных структурах данных без подписки на событие уничтожения цели.

   **Источник:** [Cppreference: Pointer declaration](https://en.cppreference.com/w/cpp/language/pointer)

220. Почему non-owning ссылки и указатели требуют внешних гарантий lifetime?

   **Ответ:** Поскольку они пассивны, вызывающий код обязан внешними средствами гарантировать, что владелец не уничтожит целевой объект раньше, чем завершатся операции наблюдателя.

   **Пример:**

   ```cpp
   // Асинхронный поток использует ссылку на объект главного потока:
   // если главный поток выйдет из блока раньше фонового потока — произойдет UB
   ```

   **Типичная ошибка:** Передача локальных ссылок в фоновые задачи без ожидания завершения через `.join()`.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

221. Что такое borrow-семантика на практическом уровне в C++?

   **Ответ:** Паттерн проектирования, при котором владелец передает временный доступ к объекту через ссылку (`T&`, `const T&`) или `std::string_view` на строго ограниченное время вызова функции.

   **Пример:**

   ```cpp
   void process(const BigData& data); // Заимствование (borrow) на время работы process
   ```

   **Типичная ошибка:** Сохранение заимствованной ссылки во внутреннем поле глобального объекта или долгоживущего сервиса.

   **Источник:** [Cppreference: Reference initialization](https://en.cppreference.com/w/cpp/language/reference_initialization)

222. Почему ссылка не гарантирует более долгий lifetime объекта?

   **Ответ:** Ссылка в C++ — это просто псевдоним (alias) существующего объекта; она не имеет собственного механизма удержания объекта и становится недействительной сразу после его гибели.

   **Пример:**

   ```cpp
   const int& r = *new int(10);
   delete &r;
   // r жива как ссылка, но указывает на разрушенный объект
   ```

   **Типичная ошибка:** Считать ссылки «безопасной альтернативой указателям», якобы защищающей от ошибок времени жизни.

   **Источник:** [Cppreference: Reference initialization](https://en.cppreference.com/w/cpp/language/reference_initialization)

223. В чём разница между “объект существует” и “на него всё ещё есть ссылка”?

   **Ответ:** Существование объекта определяется рамками его lifetime; ссылка же является просто синтаксической сущностью и может продолжать указывать на адрес мертвого объекта.

   **Пример:**

   ```cpp
   // Ссылка синтаксически легальна, но объект уже уничтожен деструктором
   ```

   **Типичная ошибка:** Предполагать, что компилятор выдаст ошибку при любом разыменовании ссылки на мертвый объект.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

224. Что такое data race и как она может косвенно ломать предположения о lifetime?

   **Ответ:** Состояние гонки данных (data race) — одновременный несинхронизированный доступ двух потоков к одной памяти, где хотя бы один выполняет запись; это ведет к UB и чтению разрушенных указателей.

   **Пример:**

   ```cpp
   // Поток 1 делает delete ptr;
   // Поток 2 в это же время читает *ptr;
   ```

   **Типичная ошибка:** Попытка защитить lifetime объекта неатомарным булевым флагом `bool is_alive`.

   **Источник:** [Cppreference: Memory model](https://en.cppreference.com/w/cpp/language/memory_model)

225. Почему многопоточность усложняет управление lifetime?

   **Ответ:** Время жизни объекта перестает быть привязанным к детерминированному стеку одной нити; уничтожение объекта в одном потоке может произойти во время его использования в другом.

   **Пример:**

   ```cpp
   // Необходимы атомарные счетчики ссылок или явные барьеры синхронизации
   ```

   **Типичная ошибка:** Использование `std::unique_ptr` разделяемо между потоками без синхронизации передачи владения.

   **Источник:** [Cppreference: Memory model](https://en.cppreference.com/w/cpp/language/memory_model)

226. Что такое безопасная публикация объекта между потоками?

   **Ответ:** Шаблон передачи указателя/ссылки на сконструированный объект через механизмы синхронизации (мьютексы, атомики с `release/acquire`), гарантирующий, что читающий поток видит полностью инициализированные данные.

   **Пример:**

   ```cpp
   std::atomic<Widget*> global_w{nullptr};
   void publish() {
       Widget* w = new Widget();
       global_w.store(w, std::memory_order_release); // Гарантирует инициализацию w до публикации
   }
   ```

   **Типичная ошибка:** Публикация адреса объекта через обычный неатомарный указатель, когда другой поток видит сырую память до окончания работы конструктора.

   **Источник:** [Cppreference: memory_order](https://en.cppreference.com/w/cpp/atomic/memory_order)

227. Почему разрушение объекта в одном потоке при использовании в другом опасно?

   **Ответ:** Это классический use-after-free в многопоточной среде, приводящий к разыменованию освобожденной памяти, повреждению кучи и фатальным сбоям.

   **Пример:**

   ```cpp
   // Поток А разрушает структуру, Поток Б вызывает метод через this
   ```

   **Типичная ошибка:** Завершение главного потока и уничтожение локальных объектов, пока фоновые `std::thread` продолжают работу с ними.

   **Источник:** [Cppreference: thread](https://en.cppreference.com/w/cpp/thread/thread)

228. Как `thread_local` влияет на lifetime объектов в многопоточной программе?

   **Ответ:** Обеспечивает изоляцию: каждый поток имеет независимый экземпляр со своим собственным временем жизни, исключая конфликты при уничтожении потоков.

   **Пример:**

   ```cpp
   thread_local std::string per_thread_buffer;
   ```

   **Типичная ошибка:** Попытка синхронизировать доступ к `thread_local` между разными потоками через сырые указатели.

   **Источник:** [Cppreference: Storage duration](https://en.cppreference.com/w/cpp/language/storage_duration#Storage_duration)

229. Что такое ABA-подобные проблемы на уровне адресов и повторного использования памяти?

   **Ответ:** Ситуация в lock-free алгоритмах, когда блок памяти освобождается и повторно аллоцируется по тому же самому адресу; алгоритм видит прежний адрес и ошибочно считает, что объект не изменялся.

   **Пример:**

   ```cpp
   // Указатель P указывает на адрес 0x1000. Объект удален, создан новый по 0x1000.
   // CAS(compare_and_swap) успешно срабатывает, хотя объект совершенно другой!
   ```

   **Типичная ошибка:** Реализация lock-free стека без версионирования указателей или использования hazard pointers.

   **Источник:** [Cppreference: atomic_compare_exchange](https://en.cppreference.com/w/cpp/atomic/atomic_compare_exchange)

230. Почему один и тот же адрес памяти не означает тот же самый объект с точки зрения lifetime?

   **Ответ:** Адрес — это лишь геометрическая позиция в памяти; объект определяется своим жизненным циклом. Если старый объект уничтожен, а новый создан по тому же адресу, это совершенно другой объект.

   **Пример:**

   ```cpp
   alignas(int) char buf[4];
   int* p1 = new (buf) int(1);
   p1->~int();
   int* p2 = new (buf) int(2); // Тот же адрес buf, но это другой объект!
   ```

   **Типичная ошибка:** Использование кэшированных указателей на основании проверки `ptr == old_address`.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

## Очень сложный уровень

231. Что такое storage duration без начатого object lifetime?

   **Ответ:** Ситуация, когда под объект выделена память (зарезервирован диапазон адресов требуемого размера и выравнивания), но конструктор типа еще не завершился или не вызывался.

   **Пример:**

   ```cpp
   alignas(Widget) char raw[sizeof(Widget)]; // Storage есть, но lifetime Widget не начат
   ```

   **Типичная ошибка:** Разыменование указателя на тип `Widget` по адресу `raw` до вызова placement new.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

232. Может ли область памяти существовать без объекта в ней в смысле модели языка?

   **Ответ:** Да, сырая динамическая память, возвращенная `malloc` или `::operator new`, представляет собой просто последовательность байтов хранения без ассоциированных с ней C++ объектов.

   **Пример:**

   ```cpp
   void* p = ::operator new(100); // 100 байт неинициализированной памяти
   ::operator delete(p);
   ```

   **Типичная ошибка:** Предполагать, что выделение $N$ байт в C++ автоматически конструирует там массив `char` или `std::byte` без специальных операций.

   **Источник:** [Cppreference: Memory model](https://en.cppreference.com/w/cpp/language/memory_model)

233. Чем lifetime отличается от простого факта доступности адреса памяти?

   **Ответ:** Доступность адреса — низкоуровневое аппаратное свойство страниц виртуальной памяти ОС; lifetime — абстрактное семантическое правило C++, определяющее, законно ли обращение к объекту с точки зрения компилятора.

   **Пример:**

   ```cpp
   int* p = new int(10);
   delete p;
   // Адрес все еще доступен в ОС (страница не сброшена), но lifetime окончен: обращение — строгий UB!
   ```

   **Типичная ошибка:** Делать выводы о корректности кода на том основании, что чтение по мертвому адресу не привело к Segfault.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

234. Когда байты памяти становятся представлением нового объекта?

   **Ответ:** В момент успешного завершения конструктора объекта либо (для implicit-lifetime типов) в момент выполнения операций, неявно создающих объекты (`std::start_lifetime_as`, `memcpy`).

   **Пример:**

   ```cpp
   #include <new>
   alignas(int) char buf[sizeof(int)];
   int* p = new (buf) int(10); // Байты стали представлением 'p'
   ```

   **Типичная ошибка:** Попытка манипулировать байтами представления как живым объектом до его конструирования.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

235. Можно ли считать, что объект “тот же самый”, если он создан заново по тому же адресу?

   **Ответ:** Нет, по правилам модели памяти C++ это абсолютно новый логический объект с собственным временем жизни, даже если он идентичен по типу и содержимому.

   **Пример:**

   ```cpp
   struct X { int a; };
   alignas(X) char buf[sizeof(X)];
   X* x1 = new (buf) X{1};
   x1->~X();
   X* x2 = new (buf) X{1}; // Новый объект!
   ```

   **Типичная ошибка:** Разыменование указателя `x1` после создания `x2` (без соблюдения строгих условий прозрачной замены).

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

236. Почему идентичный адрес не гарантирует идентичность объекта?

   **Ответ:** Компилятор C++ строит граф оптимизаций исходя из предположения об уникальности жизненных циклов объектов; идентичность адреса не восстанавливает аннулированные связи старых указателей.

   **Пример:**

   ```cpp
   // Компилятор может закешировать значения старого объекта в регистрах
   ```

   **Типичная ошибка:** Сравнение адресов указателей (`ptr1 == ptr2`) для проверки равенства жизненных циклов объектов.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime)

237. Что такое transparently replaceable object в контексте повторного создания объекта?

   **Ответ:** Правило стандарта, позволяющее старому указателю/ссылке автоматически стать валидным для нового объекта, созданного на том же месте, если соблюден строгий набор критериев.

   **Пример:**

   ```cpp
   // Новый объект занимает точно то же место, имеет в точности тот же тип,
   // не содержит const/ссылочных полей и не является base subobject.
   ```

   **Типичная ошибка:** Предполагать прозрачную замену для структур, содержащих константные поля (`const int id;`).

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime#Storage_reuse)

238. В каких случаях повторное создание объекта в той же памяти прозрачно для существующих ссылок и указателей, а в каких нет?

   **Ответ:** Прозрачно, если типы строго совпадают, размер и выравнивание идентичны, и тип не содержит `const` членов или ссылок; НЕ прозрачно, если тип изменился или содержит константные поля (требуется `std::launder`).

   **Пример:**

   ```cpp
   struct Mut { int val; };
   Mut* m = new (buf) Mut{1};
   new (buf) Mut{2};
   // m->val легален и вернет 2 (прозрачная замена)
   ```

   **Типичная ошибка:** Попытка прозрачной замены полиморфных объектов или объектов производных типов.

   **Источник:** [Cppreference: Lifetime](https://en.cppreference.com/w/cpp/language/lifetime#Storage_reuse)

239. Почему self-assignment и self-placement-new требуют особой осторожности?

   **Ответ:** Они могут случайно уничтожить объект до того, как его состояние будет скопировано само в себя, приведя к чтению из уже разрушенной памяти.

   **Пример:**

   ```cpp
   Type& operator=(const Type& rhs) {
       if (this == &rhs) return *this; // Защита от self-assignment
       delete ptr;
       ptr = new Resource(*rhs.ptr);
       return *this;
   }
   ```

   **Типичная ошибка:** Вызов `new (this) Type(*this)` — уничтожение старого объекта разрушает данные аргумента копирования.

   **Источник:** [Cppreference: Copy assignment operator](https://en.cppreference.com/w/cpp/language/copy_assignment)

240. Что такое lifetime-правила для стандартной библиотеки и почему они критичны при работе с view-типами?

   **Ответ:** Правила, определяющие, какие вызовы методов контейнеров инвалидируют итераторы, указатели и не-владеющие представления (views); их нарушение ведет к чтению висячих данных.

   **Пример:**

   ```cpp
   std::string_view sv = std::string("temporary"); // Временная строка уничтожена
   // sv стал висячим немедленно!
   ```

   **Типичная ошибка:** Недооценка опасности view-типов как источников висячих ссылок.

   **Источник:** [Cppreference: string_view](https://en.cppreference.com/w/cpp/string/basic_string_view)

241. Что такое `std::string_view` в контексте не-владения памятью?

   **Ответ:** Легковесный объект (указатель `const char*` и длина `size_t`), предоставляющий интерфейс доступа к непрерывной последовательности символов без управления её памятью.

   **Пример:**

   ```cpp
   void print(std::string_view sv); // Zero-allocation доступ к строкам
   ```

   **Типичная ошибка:** Возврат `std::string_view` из функции, где аргумент конструировался неявно через временный `std::string`.

   **Источник:** [Cppreference: string_view](https://en.cppreference.com/w/cpp/string/basic_string_view)

242. Почему `std::string_view` часто становится источником dangling reference?

   **Ответ:** Потому что он прозрачно и неявно конструируется из временных `std::string`, которые уничтожаются сразу после завершения выражения.

   **Пример:**

   ```cpp
   std::string get_name() { return "Alice"; }
   std::string_view sv = get_name(); // get_name() умер -> sv висит
   ```

   **Типичная ошибка:** Сохранение `std::string_view` в полях долгоживущих классов.

   **Источник:** [Cppreference: string_view](https://en.cppreference.com/w/cpp/string/basic_string_view)

243. Чем lifetime `std::span` определяется вне самого `span`?

   **Ответ:** `std::span` хранит только сырой указатель и размер; время жизни данных контролируется исключительно внешним контейнером (`std::vector`, `std::array`).

   **Пример:**

   ```cpp
   #include <span>
   std::span<int> get_span() {
       std::vector<int> v = {1, 2, 3};
       return v; // ОШИБКА: v уничтожится на выходе, span станет висячим!
   }
   ```

   **Типичная ошибка:** Рассматривать `std::span` как полноценную замену `std::vector` с хранением данных.

   **Источник:** [Cppreference: span](https://en.cppreference.com/w/cpp/container/span)

244. Почему view-типы удобны, но опасны без чётких гарантий времени жизни данных?

   **Ответ:** Они обеспечивают колоссальный выигрыш в производительности (избегая лишних аллокаций), но компилятор не имеет borrow-чекера и не может предотвратить разыменование после смерти владельца.

   **Пример:**

   ```cpp
   // View идеален как параметр функции, но крайне опасен как возвращаемое значение
   ```

   **Типичная ошибка:** Использование view-типов в цепочках асинхронных вызовов (future/coroutines).

   **Источник:** [Cppreference: span](https://en.cppreference.com/w/cpp/container/span)

245. Как lifetime влияет на дизайн API в C++?

   **Ответ:** Качественный API обязан явно выражать передачу прав на владение через типы (by value, `std::unique_ptr`, `std::shared_ptr`) или временное заимствование (`T&`, `string_view`).

   **Пример:**

   ```cpp
   void consume(std::unique_ptr<Data> d); // API явно заявляет: я забираю владение навсегда
   ```

   **Типичная ошибка:** Прием сырых `T*` указателей с неявным соглашением о том, что вызываемая функция вызовет `delete`.

   **Источник:** [Cppreference: unique_ptr](https://en.cppreference.com/w/cpp/memory/unique_ptr)

246. Почему хороший API должен явно выражать владение, заимствование и передачу ресурса?

   **Ответ:** Это переносит проверку безопасности работы с памятью на этап компиляции, устраняя утечки и use-after-free на уровне сигнатур методов.

   **Пример:**

   ```cpp
   void borrow(const Resource& r);      // Заимствование (read-only)
   void take(std::unique_ptr<Resource> r); // Передача исключительного владения
   ```

   **Типичная ошибка:** Использование неоднозначных аргументов `Resource*`, требующих чтения документации для понимания ответственности за очистку.

   **Источник:** [Cppreference: RAII](https://en.cppreference.com/w/cpp/language/raii)

247. Когда лучше возвращать объект по значению, чем ссылку или указатель?

   **Ответ:** Практически всегда, когда функция порождает новые данные: возврат по значению гарантирует безопасность времени жизни и благодаря NRVO/Move семантике работает предельно быстро.

   **Пример:**

   ```cpp
   std::vector<int> generate() {
       std::vector<int> res;
       // заполнение
       return res; // Быстро, безопасно, исключает висячие ссылки
   }
   ```

   **Типичная ошибка:** Возврат ссылки на внутренний статический буфер для «оптимизации» (нарушает реентерабельность и безопасность).

   **Источник:** [Cppreference: Copy elision](https://en.cppreference.com/w/cpp/language/copy_elision)

248. Почему “возвращать по значению” в современном C++ часто безопаснее и дешевле, чем кажется?

   **Ответ:** Благодаря Mandatory Copy Elision (C++17) и Move Semantics накладные расходы на копирование полностью устраняются: объект конструируется сразу в вызывающем фрейме.

   **Пример:**

   ```cpp
   BigMatrix create_matrix() {
       return BigMatrix(1000, 1000); // 0 байт копирования
   }
   ```

   **Типичная ошибка:** Принудительное оборачивание возвращаемых объектов в `std::unique_ptr` исключительно из страха перед копированием.

   **Источник:** [Cppreference: Copy elision](https://en.cppreference.com/w/cpp/language/copy_elision)

249. Какие практические приёмы уменьшают число lifetime-ошибок в кодовой базе?

   **Ответ:** Соблюдение Core Guidelines (Rule of Zero), отказ от сырых владеющих указателей, включение статических анализаторов (Clang-Tidy), компиляция с адресным санитайзером (`-fsanitize=address`) и минимизация областей видимости переменных.

   **Пример:**

   ```bash
   clang++ -fsanitize=address,undefined main.cpp -g
   ```

   **Типичная ошибка:** Игнорирование предупреждений компилятора и отказ от использования ASan при прогоне тестов.

   **Источник:** [Cppreference: RAII](https://en.cppreference.com/w/cpp/language/raii)

250. Какие основные правила вы бы сформулировали для безопасной работы с памятью и lifetime в современном C++?

   **Ответ:** 1. Применяйте RAII повсеместно. 2. Предпочитайте автоматические стековые объекты динамическим. 3. Передавайте владение через `std::unique_ptr`. 4. Используйте view-типы только в качестве параметров функций, не сохраняя их. 5. Регулярно тестируйте код под AddressSanitizer.

   **Пример:**

   ```cpp
   // Идеальный C++ код не содержит явных операторов new и delete
   auto resource = std::make_unique<Device>();
   ```

   **Типичная ошибка:** Ручное управление памятью в стиле C без использования преимуществ современных стандартов языка.

   **Источник:** [Cppreference: Memory management](https://en.cppreference.com/w/cpp/memory)
