# Инструменты, сборка и совместимость CUDA

Цель — научиться собирать минимальную CUDA-программу, проверять выбранное устройство, различать причины ошибок и воспроизводить окружение. Предварительно разберите [архитектуру GPU](01_gpu_architecture.md), [основы C++](../01_cpp/01_base.md) и [сборку C++](../01_cpp/14_macro_and_build.md).

## Лёгкий уровень

1. Какие роли выполняют драйвер NVIDIA, CUDA Toolkit и CUDA Runtime? Определите, какие компоненты нужны для сборки исходников, а какие — для запуска уже собранной программы; объясните, почему наличие одного компонента не доказывает наличие остальных.

   **Ответ:** Драйвер обеспечивает взаимодействие с GPU и исполнение device-кода, toolkit содержит компилятор, заголовки и инструменты, runtime предоставляет высокоуровневый API. Для сборки нужны toolkit и поддерживаемый host-компилятор; для запуска — совместимый драйвер, GPU и требуемые runtime/библиотеки либо их статически включённые части.

   **Типичная ошибка:** Считать установленный драйвер установленным toolkit.

   **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

2. Как перед началом работы проверить, что выбранные операционная система, GPU, драйвер и host-компилятор поддерживаются конкретной версией CUDA Toolkit? Составьте порядок проверки по официальной документации и предложите доступный вариант практики, если локальная машина не поддерживает CUDA.

   **Ответ:** Проверяют release notes и installation guide выбранного toolkit: ОС, архитектуру GPU, минимальный драйвер и host-компилятор. Затем собирают и запускают минимальную программу. При отсутствии CUDA GPU используют удалённый сервер с совместимым NVIDIA GPU; локальная компиляция не заменяет аппаратную проверку.

   **Типичная ошибка:** Обещать CUDA-выполнение на любой видеокарте.

   **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

3. Что показывает `nvcc --version`, а что — сведения о драйвере и поле CUDA Version в `nvidia-smi`? Объясните, почему различающиеся версии в этих выводах ещё не доказывают неисправность установки и почему поле `nvidia-smi` не подтверждает наличие установленного toolkit той же версии.

   **Ответ:** `nvcc --version` относится к найденному в PATH toolkit. `nvidia-smi` сообщает драйвер, а CUDA Version — поддерживаемый им уровень CUDA, а не версию установленного компилятора. Версии могут законно различаться при соблюдении правил совместимости.

   **Типичная ошибка:** Делать вывод о toolkit по полю CUDA Version.

   **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

4. Зачем для CUDA-программы нужен обычный компилятор C++, если уже используется `nvcc`? Для файла `.cu`, содержащего функцию `main` и kernel, разделите host-код и device-код и обозначьте, на каких этапах появляются объектные файлы и итоговый исполняемый файл.

   **Ответ:** `nvcc` разделяет `.cu` на host- и device-части; host-код компилирует поддерживаемый C++ компилятор, device-код проходит CUDA-компиляцию. Образы GPU встраиваются в host object; линкер соединяет объекты, runtime и библиотеки в executable.

   **Типичная ошибка:** Считать `nvcc` заменой всем инструментам host C++.

   **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

5. Чем обозначения `__host__`, `__device__` и `__global__` различаются по назначению функции и допустимым вызовам? Разберите обычную вспомогательную функцию, device-функцию и kernel; объясните, почему произвольная host-библиотека не становится доступной внутри kernel после подключения её заголовка.

   **Ответ:** `__host__` исполняется на CPU, `__device__` — на GPU, `__global__` обозначает kernel с конфигурацией запуска. Для `__host__ __device__` формируются подходящие версии с ограничениями соответствующей стороны. Заголовок CPU-библиотеки не создаёт device-реализацию и не делает её API допустимым в kernel.

   **Типичная ошибка:** Вызывать произвольную CPU-функцию из device-кода.

   **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

6. Что такое compute capability GPU NVIDIA и чем она отличается от версии драйвера или toolkit? Найдите способ узнать её программно и объясните, какие решения о поддержке возможностей нельзя принимать только по маркетинговому названию видеокарты.

   **Ответ:** Compute capability — версия аппаратных возможностей GPU, обычно пара major/minor. Её читают из `cudaDeviceProp.major/minor` или атрибутов устройства. Версии драйвера и toolkit описывают ПО; поддержку конкретной инструкции проверяют также по документации и цели сборки.

   **Типичная ошибка:** Принимать номер CUDA Toolkit за compute capability.

   **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

7. Как получить число CUDA-устройств и выбрать устройство для следующих операций Runtime API? Опишите поведение программы при отсутствии GPU и при наличии двух GPU, указав, какие свойства нужно прочитать перед выделением памяти и запуском kernel.

   **Ответ:** Проверяют результат `cudaGetDeviceCount`, затем выбирают допустимый ordinal через `cudaSetDevice`. При отсутствии устройств дают явную диагностику или CPU fallback; при двух читают свойства обоих и выбирают по требованиям. Проверяют память, compute capability, лимиты grid/block и нужные возможности.

   **Типичная ошибка:** Всегда выбирать устройство 1 или игнорировать ошибку перечисления.

   **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

8. Зачем проверять возвращаемый `cudaError_t` после вызовов API и сохранять текст ошибки вместе с контекстом операции? Предложите формат сообщения, по которому можно различить ошибку выделения памяти, выбора устройства и копирования данных, не имея доступа к машине автора.

   **Ответ:** Каждый результат API проверяют сразу и связывают с операцией, устройством и размерами. Полезны `cudaGetErrorName` и `cudaGetErrorString`; при ошибке прекращают зависимые операции и освобождают уже созданные ресурсы.

   **Пример:** `device=0 op=cudaMalloc bytes=1048576 error=cudaErrorMemoryAllocation`.

   **Типичная ошибка:** Продолжать запуск после неудачного выделения.

   **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

## Средний уровень

9. Чем PTX отличается от машинного кода GPU, который обычно называют SASS? Проследите путь от CUDA C++ до выполнения на конкретном устройстве и объясните, на каком этапе может потребоваться JIT-компиляция драйвером.

   **Ответ:** PTX — виртуальный ISA и промежуточный код, SASS — инструкции конкретного GPU. Компиляция может заранее получить cubin/SASS либо сохранить PTX в артефакте; драйвер при отсутствии подходящего готового образа JIT-компилирует совместимый PTX.

   **Типичная ошибка:** Считать PTX непосредственно исполняемыми инструкциями GPU.

   **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

10. Зачем fat binary может содержать несколько образов машинного кода и PTX? Для программы, которую нужно запускать на нескольких поколениях GPU NVIDIA, предложите состав артефакта и объясните компромисс между размером файла, временем сборки и необходимостью компиляции при запуске.

    **Ответ:** Fat binary хранит образы для выбранных реальных архитектур и при необходимости PTX для поддерживаемой виртуальной цели. Готовые cubin уменьшают JIT на известных GPU; PTX расширяет допустимые варианты в рамках совместимости. Цена — размер, сборка и возможная задержка JIT.

    **Типичная ошибка:** Включать единственный cubin и ожидать запуска на любом поколении.

    **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

11. Что задают виртуальная архитектура `compute_XX` и реальная архитектура `sm_XX` в параметрах генерации кода `nvcc`? На условном наборе двух поддерживаемых GPU объясните, какие цели следует проверить в установленном toolkit и почему нельзя бездумно копировать список `-gencode` из старого проекта.

    **Ответ:** `compute_XX` задаёт возможности виртуальной архитектуры при генерации PTX, `sm_XX` — реальную цель машинного кода. Для двух GPU выбирают поддерживаемые toolkit цели, включают нужные cubin и осмысленный PTX fallback; список сверяют через возможности `nvcc` и документацию.

    **Типичная ошибка:** Копировать снятые с поддержки цели из старого проекта.

    **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

12. Как различать ошибку конфигурации запуска и ошибку, возникшую во время асинхронного выполнения kernel? Опишите диагностическую последовательность с проверкой запуска и ожиданием завершения, отдельно указав, почему успешный возврат host после запуска ещё не подтверждает корректность вычисления.

    **Ответ:** После launch сразу проверяют `cudaGetLastError`, затем при диагностике — `cudaStreamSynchronize` соответствующего stream. Первая проверка ловит ошибки постановки, ожидание выявляет сбой исполнения; каждый результат проверяется отдельно. Успешный launch не доказывает правильность результата.

    **Пример:**

    ```cpp
    kernel<<<grid, block, 0, stream>>>(/* аргументы */);
    check(cudaGetLastError());             // проверка постановки
    check(cudaStreamSynchronize(stream)); // проверка исполнения
    ```

    Здесь `check` — host-функция, которая проверяет `cudaSuccess` и сообщает ошибку вместе с контекстом; `kernel` и его аргументы задаются задачей.

    **Типичная ошибка:** Проверять только возврат после асинхронной постановки.

    **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

13. Чем `cudaGetLastError()` отличается от `cudaPeekAtLastError()` в работе с состоянием последней ошибки Runtime API? Разберите диагностический код, который проверяет несколько запусков подряд, и объясните, как очистка состояния или несвоевременная проверка могут затруднить поиск источника ошибки.

    **Ответ:** `cudaPeekAtLastError` читает состояние без сброса; `cudaGetLastError` возвращает и сбрасывает его. Проверять нужно сразу с контекстом запуска, учитывая ранее возникшие ошибки; очистка состояния не исправляет сбой устройства.

    **Типичная ошибка:** Приписывать старую ошибку последнему kernel или терять её преждевременным сбросом.

    **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

14. Почему ошибка device-операции может впервые обнаружиться при последующем вызове API? Предложите способ локализовать проблемный kernel в цепочке из трёх запусков и объясните, как временные проверки завершения меняют поведение и производительность отладочной версии.

    **Ответ:** Host продолжает работу до завершения device-команд, поэтому сбой может проявиться в более позднем API. Временно ставят проверяемое ожидание после каждого из трёх kernels и находят первую ошибочную границу. Это сериализует работу и меняет тайминг, поэтому такие замеры не характеризуют release-производительность.

    **Типичная ошибка:** Считать место обнаружения ошибки местом её возникновения.

    **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

15. Как организовать минимальный воспроизводимый пример сложения векторов с проверкой всего жизненного цикла ресурсов? Перечислите этапы выделения памяти, подготовки входов, копирования, запуска, ожидания, сравнения с CPU и освобождения, определив, что должно произойти при ошибке посередине.

    **Ответ:** Проверяют размеры и выделения, заполняют host-входы, копируют H2D, запускают сумму с границами, проверяют launch и завершение, копируют D2H и сравнивают с CPU. RAII освобождает частично созданные буферы при любой ошибке; до окончания работы память не уничтожают.

    **Типичная ошибка:** Освобождать буфер, пока его использует stream.

    **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

16. Какие сведения об окружении должны сопровождать результат CUDA-эксперимента? Составьте небольшой паспорт запуска с моделью GPU, compute capability, версиями ПО, точной командой сборки, параметрами запуска и исходными данными; объясните, какие различия могут повлиять на корректность, а какие — на измеренное время.

    **Ответ:** Сохраняют модель/UUID GPU, compute capability, driver, toolkit/runtime, host-компилятор, ОС, точную команду, исходники, данные/seed и launch. Архитектура и версии меняют допустимые возможности; частоты, питание, конкуренция и прогрев существенно меняют время.

    **Типичная ошибка:** Публиковать одно время без входного размера и окружения.

    **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

## Сложный уровень

17. Почему PTX в исполняемом файле не является безусловной гарантией запуска на любом будущем или более старом GPU? Разберите отдельно поддержку версии PTX драйвером, минимальные требования виртуальной архитектуры и специальные архитектурные возможности; сформулируйте, какие обещания совместимости нужно подтвердить документацией.

    **Ответ:** Драйвер должен понимать версию PTX, а GPU — минимальные возможности виртуальной цели. PTX для новых возможностей не делает старый GPU совместимым; специализированные архитектурные варианты могут иметь дополнительные ограничения. Совместимость подтверждают матрицами NVIDIA и тестом JIT на целевых системах.

    **Типичная ошибка:** Принимать PTX за гарантию любой прямой и обратной совместимости.

    **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

18. Как различаются совместимость старого приложения с новым драйвером, minor version compatibility и механизм forward compatibility через пакет `cuda-compat`? Для управляемого сервера, где драйвер обновляется реже приложения, предложите дерево проверки допустимости запуска с учётом ограничений платформы и используемых возможностей.

    **Ответ:** Сначала проверяют обычную обратную совместимость приложения с новым драйвером. Для нового runtime на более старом драйвере проверяют minor compatibility и её ограничения; `cuda-compat` — отдельный механизм forward compatibility только для допустимых платформ и сочетаний. Если требования не выполнены, обновляют драйвер или меняют сборку.

    **Типичная ошибка:** Считать `cuda-compat` универсальной заменой драйвера.

    **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

19. Что меняется в сборке, если device-функция вызывается из другого `.cu`-файла? Объясните назначение relocatable device code и device linking, затем предложите минимальный проект из двух единиц трансляции, позволяющий отличить проблему компиляции от проблемы линковки.

    **Ответ:** Межфайловые device-вызовы требуют relocatable device code и device link, например `nvcc -dc a.cu b.cu`, затем `nvcc a.o b.o -o app`. В одном файле объявляют device-функцию, в другом определяют; ошибки объявления видны при компиляции, отсутствующего определения — при device linking.

    **Типичная ошибка:** Линковать device-зависимости только обычным host-линкером.

    **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

20. Как проверить, что исполняемый файл содержит ожидаемые архитектурные образы и реально исполняет нужную специализацию kernel? Предложите проверку с подходящими инструментами CUDA для просмотра бинарного кода и отдельными тестами JIT-пути; объясните, почему строка команды сборки сама по себе не заменяет проверку готового артефакта.

    **Ответ:** `cuobjdump` показывает встроенные образы/PTX/SASS, `nvdisasm` разбирает cubin. Сопоставляют фактические архитектуры и kernel с ожидаемыми, отдельно тестируют PTX JIT через `CUDA_FORCE_PTX_JIT=1` и обычный путь, фиксируя окружение.

    **Типичная ошибка:** Проверять только конфигурацию сборки, а не полученный executable.

    **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

21. Почему первая итерация CUDA-программы может занимать больше времени последующих даже при одинаковых входных данных? Спланируйте эксперимент, разделяющий создание контекста, загрузку модулей, JIT-компиляцию, выделение памяти и выполнение kernel; отдельно сохраните показатель первого запуска, если он важен пользователю программы.

    **Ответ:** Холодный запуск включает инициализацию, загрузку модулей, возможный JIT и выделения. Измеряют отдельные границы host-таймером с ожиданиями, затем повторяют kernel с уже созданными ресурсами и CUDA events. Холодное и установившееся время сохраняют отдельно, учитывая JIT cache и lazy loading.

    **Типичная ошибка:** Скрывать пользовательскую задержку первого запуска прогревом.

    **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

22. Как воспроизвести ошибку «на моей машине работает», если устройство разработчика и сервер имеют разные compute capability, драйверы и toolkit? Составьте матрицу проверок артефакта, аппаратных возможностей и входных размеров, затем предложите минимальные изменения сборки или требований к окружению, которые можно проверить отдельно.

    **Ответ:** Сопоставляют GPU/CC, драйвер/runtime, образы fatbin, PTX и входные размеры; проверяют launch и completion на обеих машинах. По одному меняют архитектурные цели, используемый API или минимальный драйвер и повторяют минимальный пример.

    **Типичная ошибка:** Менять одновременно код, драйвер и размеры, теряя причину исправления.

    **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

23. Что обеспечивает контейнер с CUDA-пользовательскими библиотеками и какие зависимости от host-системы у него остаются? Разберите доступ к GPU, драйвер, совместимость библиотек и выбор устройства; объясните, какие данные нужно фиксировать помимо тега образа, чтобы эксперимент был воспроизводимым.

    **Ответ:** Контейнер фиксирует user-space библиотеки и среду приложения, но использует GPU и драйвер host через runtime интеграции. Нужны доступ к устройствам и совместимый host-драйвер. Фиксируют digest образа, host driver, GPU/UUID, runtime контейнеров, лимиты и команду запуска.

    **Типичная ошибка:** Принимать тег образа за полную воспроизводимость GPU-среды.

    **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).

24. Как спроектировать процесс сборки и проверки CUDA-проекта для команды с несколькими GPU и машинами без GPU? Разделите проверки компиляции, содержимого артефакта, выполнения и производительности, задайте поддерживаемую матрицу окружений и определите, как явно отмечать пропущенные аппаратные проверки.

    **Ответ:** Задают матрицу toolkit/компиляторов и целевых GPU. На машинах без GPU проверяют компиляцию и образы артефакта, на GPU — корректность, sanitizer и совместимость; производительность сравнивают в контролируемой среде. Отсутствие аппаратной проверки помечают как пропуск с причиной.

    **Типичная ошибка:** Выдавать успешную компиляцию за успешное CUDA-исполнение.

    **Источник:** [NVCC](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html); [CUDA Compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/index.html).
