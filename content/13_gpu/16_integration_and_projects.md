# Интеграция GPU, переносимость и сквозные проекты

Цель — встроить вычисление в приложение с понятными контрактами, временем жизни данных и обработкой ошибок, а затем оценить переносимость решения. Предварительно разберите [toolchain](02_cuda_toolchain.md), [streams](07_streams_events_and_graphs.md), [передачи](08_transfers_and_unified_memory.md), [профилирование](13_profiling_and_optimization.md) и [корректность](14_debugging_and_correctness.md). Для связи с Python полезна [интеграция C++](../10_python/08_cpp_integration.md).

## Лёгкий уровень

1. По каким признакам выбирать часть существующего приложения для переноса на GPU? Сопоставьте долю времени, параллелизм, объём данных, передачи и частоту повторного использования; почему сначала нужен профиль и корректная CPU-версия?

   **Ответ:** Ищут горячую часть CPU-профиля с достаточным параллелизмом и reuse данных, оценивают передачи и зависимости. Корректная CPU-версия задаёт эталон и baseline. Небольшая доля общего времени либо дорогой ввод/вывод могут сделать перенос невыгодным даже при быстром kernel.

   **Типичная ошибка:** Выбирать часть для переноса только по числу циклов в исходнике.

   **Источник:** [CUDA Best Practices](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html).

2. Как сформулировать контракт GPU-функции, принимающей массив? Определите тип, размер, stride, допустимое перекрытие, устройство размещения и ожидаемый результат, затем отдельно укажите, когда функция возвращает управление и когда данные готовы к чтению.

   **Ответ:** Контракт задаёт dtype, N/shape, strides, memory/device, допустимые aliasing и диапазоны, результат и ошибки. Отдельно указывают sync/async возврат, stream и completion token, после которого выход готов. Владелец обязан сохранить память до последнего использования.

   **Типичная ошибка:** Возвращать указатель без правила готовности и lifetime.

   **Источник:** [CUDA Asynchronous Execution](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html).

3. Какие ресурсы GPU-приложения имеют собственное время жизни? Для device buffer, pinned buffer, stream, event и библиотечного handle укажите владельца и момент освобождения; какие незавершённые операции могут продолжать обращаться к каждому ресурсу?

   **Ответ:** Allocation владеет памятью, stream — очередью, event — точкой completion, handle — состоянием библиотеки; pinned-вход тоже продолжает использоваться DMA. Каждый ресурс освобождают по его API после необходимых завершений, а владелец учитывает зависимости операций.

   **Типичная ошибка:** Уничтожать C++ wrapper сразу после async enqueue без удержания ресурсов.

   **Источник:** [CUDA Asynchronous Execution](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html).

4. Как RAII помогает управлять ресурсами CUDA в C++? Опишите свойства обёртки с единственным владельцем, перемещением и освобождением, учитывая частичную инициализацию и ограничения обработки ошибки в деструкторе.

   **Ответ:** Move-only RAII wrapper хранит handle/pointer и device, запрещает копирование владельца, передаёт владение при move и безопасно освобождает частично созданные ресурсы. Деструктор не бросает исключений; ошибки завершения удобнее отдавать явным wait/close. RAII не заменяет async lifetime protocol.

   **Типичная ошибка:** Считать scope-exit безопасным free при незавершённой работе.

   **Источник:** [CUDA Asynchronous Execution](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html).

5. Чем передача GPU-данных между библиотеками отличается от копирования результата через CPU? На примере массива в Python определите, какие сведения об адресе, форме, типе, strides, устройстве и готовности нужны потребителю.

   **Ответ:** GPU interop передаёт адрес и метаданные без обязательного D2H/H2D: shape, dtype, strides, device и готовность. Producer/consumer согласуют streams и владельца, чтобы память не исчезла. Это уменьшает копии, но не устраняет синхронизацию.

   **Типичная ошибка:** Передавать голый GPU pointer в библиотеку с другим устройством или layout.

   **Источник:** [DLPack Python Specification](https://dmlc.github.io/dlpack/latest/python_spec.html).

6. Зачем GPU-сервису CPU fallback и какие условия должны запускать этот путь? Сравните отсутствие поддерживаемого устройства, слишком маленький вход и ошибку уже начатого вычисления; как сохранить контракт результата и не скрыть проблему исполнения?

   **Ответ:** Fallback полезен при отсутствии совместимого GPU, неподдержанном режиме или слишком малом входе. После device failure сначала оценивают состояние/владение и диагностируют ошибку: нельзя молча использовать частично записанный результат. CPU-путь сохраняет тот же численный и функциональный контракт.

   **Типичная ошибка:** Скрывать серьёзную CUDA-ошибку бесконтрольным повтором на CPU.

   **Источник:** [CUDA Best Practices](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html).

7. Почему ускорение одной функции не гарантирует ускорения приложения? Для исходной доли 60% времени и её ускорения в десять раз вычислите идеальный общий выигрыш без новых расходов, затем перечислите расходы, которые нужно включить в практическую оценку.

   **Ответ:** По Амдалу `S=1/(0,4+0,6/10)=1/0,46≈2,17`. Практический итог включает передачи, allocation, launch, sync и преобразования. Даже бесконечное ускорение этой части ограничено 1/0,4=2,5 без изменения остального приложения.

   **Типичная ошибка:** Называть десятикратное ускорение функции ускорением всего приложения.

   **Источник:** [CUDA Best Practices](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html).

8. Какие сведения нужны для воспроизводимого запуска на другой машине? Составьте описание GPU, драйвера, toolkit, библиотек, входов, параметров сборки, требований к памяти и процедуры проверки результата.

   **Ответ:** Нужны исходники/commit, exact build/run commands, GPU/CC, driver/toolkit/libs, ОС и вход/seed. Указывают memory budget, launch, выбранные algorithms/math mode, expected/dopusk и процедуру CPU/GPU проверки. Cold/steady измерения и аппаратные ограничения фиксируют отдельно.

   **Типичная ошибка:** Считать контейнерный тег единственным требованием запуска.

   **Источник:** [CUDA Best Practices](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html).

## Средний уровень

9. Как спроектировать интерфейс асинхронной C++-операции, чтобы вызывающий код мог узнать завершение и ошибку? Определите роль stream или события, владение входом и выходом и запрет действий, нарушающих lifetime; как будет выглядеть явное завершение работы приложения?

   **Ответ:** Async API принимает stream и возвращает event/future, удерживающий владельцев входа, выхода и workspace. Ошибку постановки сообщают сразу, execution — при query/wait. Shutdown прекращает новые задачи, завершает/обрабатывает in-flight и только затем освобождает ресурсы.

   **Типичная ошибка:** Возвращать future, который не удерживает используемые буферы.

   **Источник:** [CUDA Asynchronous Execution](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html).

10. Как stream-ordered allocation меняет повторное использование буфера? Для выделения, работы в двух streams и освобождения через `cudaMallocAsync`/`cudaFreeAsync` нарисуйте необходимые зависимости и объясните, почему одна только передача указателя другой очереди не задаёт порядок.

    **Ответ:** Allocation→producer→consumer→free должны иметь stream-order рёбра. Для перехода во второй stream используют event/wait и ещё одно ожидание перед free, если он в третьей очереди. Передача pointer не создаёт зависимости; pool не делает одновременное использование одного блока памяти безопасным.

    **Типичная ошибка:** Считать `cudaFreeAsync` безопасным в произвольном stream.

    **Источник:** [Stream-Ordered Allocator](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/stream-ordered-memory-allocation.html).

11. Как выбрать размер пула буферов для pipeline с несколькими запросами в полёте? Для четырёх одновременных запросов с входом 20 MiB, выходом 10 MiB и временной областью 30 MiB на запрос оцените базовый device-memory бюджет, затем учтите общие данные, allocator и запас.

    **Ответ:** На запрос нужно 20+10+30=60 MiB, четыре одновременно — 240 MiB device memory. Дополнительно учитывают общие веса/таблицы, библиотечный workspace, context, allocator reserve/fragmentation и запас. Pinned host pools считают отдельным бюджетом.

    **Типичная ошибка:** Выдавать 240 MiB за полный расход процесса.

    **Источник:** [Stream-Ordered Allocator](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/stream-ordered-memory-allocation.html).

12. Какие действия нужны при обмене GPU-массивом через DLPack? Разберите устройство, dtype, layout, время жизни и согласование stream между producer и consumer; почему zero-copy не означает отсутствие зависимости и обязательной передачи метаданных?

    **Ответ:** Проверяют device/dtype/shape/strides и поддерживаемость layout, передают владение managed tensor/capsule по DLPack-контракту и согласуют stream через protocol. Producer обеспечивает нужный порядок, consumer удерживает ресурс и корректно вызывает deleter. Поддержку копии/zero-copy и версии проверяют явно.

    **Типичная ошибка:** Повторно потреблять одноразовую capsule или терять владельца памяти.

    **Источник:** [DLPack Python Specification](https://dmlc.github.io/dlpack/latest/python_spec.html).

13. Как библиотека, вызываемая из нескольких CPU-потоков, должна управлять текущим устройством и состоянием handles? Опишите контракт потокобезопасности и владения streams, затем предложите тест, выявляющий случайное использование ресурса другого GPU.

    **Ответ:** На каждом host-потоке явно выбирают device, связывают stream и handle с ним, запрещают конкурентное изменение общего состояния без гарантий API. Удобны per-thread/per-device handles. Тест одновременно запускает различимые задачи на двух GPU и проверяет принадлежность ресурсов и результат.

    **Типичная ошибка:** Полагаться на `cudaSetDevice` другого host-потока.

    **Источник:** [CUDA Asynchronous Execution](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html).

14. Как ограниченная очередь между CPU-подготовкой и GPU-обработкой помогает управлять нагрузкой? Задайте предел числа запросов в полёте, backpressure и правила отмены; когда буфер отменённого запроса действительно можно вернуть в пул?

    **Ответ:** Ограниченная очередь ограничивает in-flight и память; при заполнении применяют backpressure, отказ или deadline policy. Отмена после enqueue не останавливает уже исполняемое обращение к буферу. Слот возвращают после фактического завершения всех использований, даже если ответ больше не нужен.

    **Типичная ошибка:** Немедленно возвращать отменённый device buffer в пул.

    **Источник:** [CUDA Asynchronous Execution](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html).

15. Чем контейнер с CUDA-приложением отличается от полностью независимой виртуальной GPU-машины? Разделите библиотеки приложения, доступ к устройствам и драйвер хоста; какие проверки совместимости нужны, даже если один и тот же образ успешно запускается на двух серверах?

    **Ответ:** Контейнер фиксирует userspace приложения, но GPU и kernel-mode driver принадлежат host. Проверяют доступ к устройствам, driver/runtime compatibility, целевые архитектурные образы и библиотеки. Успешный запуск на двух серверах не гарантирует одинаковых функций, памяти или скорости.

    **Типичная ошибка:** Принимать контейнер за виртуальную машину с независимым GPU-драйвером.

    **Источник:** [CUDA Best Practices](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html).

16. Какие задачи решают MPS и MIG на поддерживаемом NVIDIA GPU? Сравните совместное использование исполнения и разделение аппаратных ресурсов по документации выбранной версии; какие требования к изоляции, памяти, наблюдаемости и влиянию соседней нагрузки нужно проверить отдельно?

    **Ответ:** MPS помогает нескольким процессам совместно использовать исполнение GPU; MIG на поддержанных моделях разделяет аппаратные ресурсы на экземпляры с определённой изоляцией. Возможности, профили и ограничения зависят от GPU/версии. Ни один механизм сам по себе не доказывает p99 SLA приложения.

    **Типичная ошибка:** Считать MPS и MIG одинаковыми механизмами изоляции.

    **Источник:** [NVIDIA MPS](https://docs.nvidia.com/deploy/mps/index.html); [MIG User Guide](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/index.html).

## Сложный уровень

17. Как разделить общую часть алгоритма и платформенный backend перед переносом с CUDA на HIP? Разберите выделение памяти, запуск, streams, warp collectives, библиотеки и встроенные инструкции; почему механическая замена API не подтверждает корректность и сохранение скорости?

    **Ответ:** Общими оставляют математический контракт, данные/эталон и тесты, backend включает allocations, launches, queues/events и библиотеки. При HIP-переносе отдельно проверяют warp/wave size, masks, intrinsics, atomics и доступные library API. После компиляции нужны correctness и performance измерения.

    **Типичная ошибка:** Считать механическую замену `cuda` на `hip` завершённым переносом.

    **Источник:** [HIP Porting Guide](https://rocm.docs.amd.com/projects/HIP/en/latest/how-to/hip_porting_guide.html).

18. Как выразить знакомый CUDA-алгоритм в модели SYCL 2020? Сопоставьте work-items, work-groups, sub-groups, очереди, события и управление памятью, затем укажите места, где нельзя предполагать прежний размер группы или порядок выполнения.

    **Ответ:** CUDA threads/blocks сопоставляют work-items/work-groups, warp collectives — подходящим sub-group operations. Queue/events задают зависимости; buffer/accessor либо USM — память. Queue может быть out-of-order, subgroup size не обязан равняться 32; барьеры и atomics выражают по модели SYCL.

    **Типичная ошибка:** Переносить CUDA full-warp маски и порядок stream в SYCL без изменений.

    **Источник:** [SYCL 2020](https://registry.khronos.org/SYCL/specs/sycl-2020/html/sycl-2020.html).

19. Как обеспечить взаимодействие вычисления с графическим или внешним API без лишнего копирования? Определите контракт импорта памяти, владения, semaphores и завершения для выбранной пары API; какие ограничения формата и устройства нужно проверить до обмена ресурсом?

    **Ответ:** Для выбранной пары API проверяют совместимое устройство, экспортируемый/importable memory handle, format/layout/size и ownership. External semaphores задают producer completion→consumer access и обратную передачу владения. Ресурсы живут до завершения обеих сторон и освобождаются по правилам импорта.

    **Типичная ошибка:** Делиться памятью без соответствующей синхронизации внешнего API.

    **Источник:** [CUDA External Interoperability](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/graphics-interop.html).

20. Когда persistent kernel с очередью работ может быть полезен? Сравните его с повторными launches и CUDA Graphs, учитывая стоимость подачи задач, memory ordering, занятые ресурсы, backpressure и возможность завершить обработку без недокументированных гарантий прогресса.

    **Ответ:** Persistent kernel может уменьшить overhead множества мелких динамических задач, читая очередь без новых host launches. Цена — постоянно занятые SM, сложные atomics/order, backpressure, shutdown и progress. Сравнивают с batching/Graphs; очередь не должна ждать производителя, которому недоступны ресурсы.

    **Типичная ошибка:** Делать бесконечный kernel без доказанного протокола остановки.

    **Источник:** [CUDA Asynchronous Execution](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html).

21. Как организовать сервис на общей GPU-машине с ограничениями p99 и памяти? Спроектируйте admission control, batching, измерение очереди, изоляцию ресурсов и диагностику деградации, затем задайте критерии, по которым конфигурацию можно считать пригодной для нагрузки.

    **Ответ:** Задают admission control по in-flight/memory, ограниченное batching по deadline, измеряют очередь от поступления и p99 под ожидаемым и пиковым rate. Изоляцию MPS/MIG выбирают после проверки модели GPU и соседней нагрузки. Критерии включают p99, throughput, errors и memory high-water mark.

    **Типичная ошибка:** Оценивать SLA по среднему времени одиночного запроса без очереди.

    **Источник:** [NVIDIA MPS](https://docs.nvidia.com/deploy/mps/index.html); [MIG User Guide](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/index.html).

22. Как построить поток обработки сигналов «CPU-приём → GPU FFT → преобразование спектра → обратное преобразование → CPU-результат»? Определите размеры блоков, масштабирование, обработку границ, зависимости и буферы, затем раздельно проверьте численный результат и end-to-end latency.

    **Ответ:** Задают FFT length/batch и правила overlap/add либо иные границы блоков сигнала. Каждый слот проходит H2D→FFT→spectral transform→inverse→scale→D2H с plan/workspace и событиями. Проверяют impulse/sine/CPU reference, padding и нормировку; latency включает CPU приём, очередь и возврат.

    **Типичная ошибка:** Фильтровать независимые блоки, игнорируя межблоковые границы сигнала.

    **Источник:** [cuFFT](https://docs.nvidia.com/cuda/cufft/index.html).

23. Когда запуск дочерних kernels с GPU, или dynamic parallelism, оправдан по сравнению с host launches и заранее построенным графом? Для нерегулярно возникающих подзадач сравните требования к runtime и compute capability, управление результатами, расходы запуска и альтернативу через очередь работ.

    **Ответ:** Dynamic parallelism полезен для достаточно крупных динамически обнаруживаемых задач, если поддержаны GPU/runtime/device link и выбранный API. Parent/child зависимости и доступную память описывают по текущему контракту; device launch имеет расходы. Сравнивают host scheduling, заранее заданный graph и persistent queue на том же workload.

    **Типичная ошибка:** Считать дочерний launch бесплатным или переносить устаревший device-sync протокол.

    **Источник:** [CUDA Dynamic Parallelism](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/dynamic-parallelism.html).

24. Подготовьте законченный проект ускорения: обработку изображений, sparse-расчёт или pipeline сообщений. Какие исходники, тесты, CPU-эталон, профиль, графики скорости и памяти, сценарии ошибок и инструкции запуска нужны, чтобы другой инженер мог воспроизвести результат и продолжить развитие?

    **Ответ:** Проект содержит CPU-эталон, baseline GPU, оптимизированный вариант, входы/seed, границы/точность и команды запуска. Добавляют проверки пустых/некратных размеров, ошибок и lifetime, профиль и графики latency/throughput/memory на семействе входов. Отчёт объясняет выигрыш полного pipeline и границы применимости.

    **Типичная ошибка:** Предъявлять только быстрый kernel без воспроизводимого приложения и проверки результата.

    **Источник:** [CUDA Best Practices](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html).

## Критерий освоения

У вас есть законченное вычисление с контрактом данных, явными зависимостями, владельцами ресурсов и обработкой ошибок. Измерение охватывает весь pipeline, перенос на другую платформу опирается на её модель памяти и исполнения, а следующий шаг проекта следует из результатов проверки.
