# Global memory, coalescing и размещение данных

Цель — связывать адреса, которые запрашивают потоки CUDA, с полезным объёмом данных, обслуживанием памяти и наблюдаемой производительностью. Предварительно разберите [индексацию kernels](03_kernels_and_indexing.md), [кэш CPU](../12_computer_architecture/05_cache_hierarchy.md) и [расположение данных для SIMD](../12_computer_architecture/10_simd_and_data_layout.md).

## Лёгкий уровень

1. Что называют global memory в CUDA и каковы её область доступности и время жизни по сравнению с локальной переменной потока? Проследите использование device-буфера двумя последовательными kernels и объясните, какие операции управляют выделением и освобождением его памяти.

   **Ответ:** Global memory доступна потокам через допустимые device-адреса и сохраняет содержимое между kernels до освобождения allocation. Её выделяют, например, `cudaMalloc`, освобождают после последнего использования через `cudaFree`. Локальная переменная принадлежит потоку, её логическое время жизни определяется кодом.

   **Типичная ошибка:** Считать global-буфер автоматически уничтоженным после kernel.

   **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

2. Чем адрес элемента массива отличается от его порядкового номера? Для массива `float`, начинающегося по адресу `A`, запишите адреса элементов с индексами 0, 1 и 8 и объясните, почему шаг в элементах необходимо переводить в байты при анализе обращений.

   **Ответ:** Индекс — номер элемента, адрес — базовый адрес плюс индекс, умноженный на размер типа. При 4-байтном float адреса равны A, A+4 и A+32 байта. Арифметика `float*` уже масштабирует шаг на sizeof(float).

   **Типичная ошибка:** Умножать индекс на sizeof дважды при арифметике типизированного указателя.

   **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

3. Что означает coalescing обращений потоков одного warp к global memory? Сравните чтение соседних элементов и чтение далеко расположенных элементов; объясните, почему анализировать нужно адреса одной выполняемой инструкции группы потоков, а не только последовательность обращений одного потока.

   **Ответ:** Coalescing объединяет обращения активных lanes одной инструкции в обслуживание затронутых сегментов. Соседние элементы обычно затрагивают мало сегментов; далёкие — много при том же числе полезных байт. Анализировать нужно набор адресов каждой warp-инструкции.

   **Типичная ошибка:** Судить по последовательным адресам одного потока.

   **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

4. Как построчное размещение матрицы влияет на выбор координаты, которую обрабатывают соседние потоки? Для матрицы `64 × 64` сравните чтение одной строки и одного столбца группой из 32 потоков NVIDIA CUDA, выписав шаг между адресами в байтах.

   **Ответ:** При row-major соседние столбцы имеют шаг 4 байта, соседние строки столбца — `64*4=256` байт. Координату x соседних lanes обычно связывают со столбцом, чтобы получить плотный набор адресов.

   **Типичная ошибка:** Направлять соседние lanes вдоль строкового индекса без анализа stride.

   **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

5. Что такое выравнивание адреса и почему начало выделенного буфера и начало подмассива могут иметь разное выравнивание? Для базового адреса, кратного 256 байтам, проверьте выравнивание указателей на элементы `float` с индексами 0, 1 и 8 относительно границы 32 байта.

   **Ответ:** Адрес выровнен на K, если делится на K. Для базы, кратной 256, смещения 0 и 32 байта сохраняют выравнивание на 32, а 4 байта — нет; это индексы 0,8 и 1 соответственно.

   **Типичная ошибка:** Переносить выравнивание allocation на любой подмассив.

   **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

6. Чем array of structures, или AoS, отличается от structure of arrays, или SoA? Для частиц с координатами `x`, `y`, `z` опишите расположение данных в обоих вариантах и сравните адреса соседних значений `x`, если kernel читает только эту координату.

   **Ответ:** AoS хранит `x0,y0,z0,x1,y1,z1`; SoA — отдельные массивы x,y,z. Без padding шаг x в AoS равен 12 байтам, в SoA — 4. Если нужны только x, SoA обычно уменьшает лишнее обслуживание памяти.

   **Типичная ошибка:** Забывать фактический padding структуры.

   **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

7. Чем задержка чтения global memory отличается от пропускной способности памяти? Сравните одно зависимое чтение по цепочке указателей и большой поток независимых чтений; объясните, почему одинаковый суммарный объём данных не означает одинаковое время.

   **Ответ:** Задержка — время отдельного обращения, bandwidth — устойчивый объём в единицу времени. Зависимая цепочка не может запросить следующий адрес заранее; независимые чтения создают много обращений в полёте и лучше используют канал. Одинаковые байты не означают одинаковый параллелизм.

   **Типичная ошибка:** Делить объём pointer chasing на пиковую bandwidth как точный прогноз.

   **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

8. Как посчитать полезный объём чтения и записи для сложения двух массивов `float` в третий? Для `N = 1 000 000` определите число байтов в модели однократного чтения каждого входа и однократной записи выхода, не включая обмен между host и device.

   **Ответ:** На элемент приходится два чтения и запись: `3*4=12` байт. Для миллиона элементов полезный трафик равен 12 000 000 байт, или 12 MB; фактический DRAM-трафик зависит от кэша и обслуживания.

   **Типичная ошибка:** Считать только входные массивы и забывать запись.

   **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

## Средний уровень

9. Как оценить число затронутых сегментов памяти для одного обращения warp в явно заданной модели? Предположите 32 активных потока, загрузку одного `float` каждым потоком и обслуживание по выровненным 32-байтным сегментам; сравните последовательные индексы при начальном адресе, кратном 32, и при сдвиге на один `float`, не приравнивая результат к числу физических DRAM-команд.

   **Ответ:** В модели 32-байтных сегментов выровненные 128 байт занимают 4 сегмента. Сдвиг на float даёт диапазон байтов 4…131 и 5 сегментов. Это число затронутых сегментов запроса, не число физических команд DRAM.

   **Типичная ошибка:** Приравнивать сегменты к транзакциям всех уровней памяти.

   **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

10. Почему перестановка адресов между lanes внутри того же набора сегментов не обязана ухудшать coalescing? В модели предыдущего вопроса сравните чтение элементов `0…31` в прямом и обратном порядке, затем отдельно разберите случай, когда каждый поток читает элемент с индексом `8 * lane`.

    **Ответ:** Прямой и обратный порядок 0…31 затрагивают те же четыре сегмента. Для `8*lane` каждый float начинает отдельный 32-байтный сегмент: 32 сегмента. Важен набор адресов инструкции, а не возрастание адреса с lane.

    **Типичная ошибка:** Считать обратный порядок автоматически некоалесцированным.

    **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

11. Как stride между соседними потоками влияет на долю полезных данных? Для одной инструкции, 32 потоков, 4-байтных элементов и 32-байтных сегментов посчитайте покрываемые сегменты при stride 1, 2 и 8, предполагая подходящее выравнивание и отсутствие попаданий в кэш.

    **Ответ:** Stride 1,2,8 дают соответственно 4,8,32 сегмента при заданном выравнивании. Полезны 128 байт; обслуживаются 128,256,1024 байта, доля полезного — 100%,50%,12,5%. Кэш и реальные инструкции могут изменить наблюдаемый трафик.

    **Типичная ошибка:** Сравнивать bandwidth без указания полезных и обслуженных байт.

    **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

12. Почему два чтения каждого потока с соседними адресами не гарантируют эффективного доступа всей группы? Сравните схемы, в которых поток `t` читает `a[2*t]` и `a[2*t+1]` двумя инструкциями либо `a[t]` и `a[t+32]`; анализируйте адреса отдельно для каждой инструкции и явно отметьте, что компилятор может изменить форму загрузок.

    **Ответ:** В `a[2*t]` и `a[2*t+1]` каждая скалярная инструкция имеет stride 2 и затрагивает 8 сегментов. В `a[t]` и `a[t+32]` каждая затрагивает 4. Кэш может повторно обслужить общие сегменты, а компилятор объединить загрузки; проверяют SASS и счётчики.

    **Типичная ошибка:** Складывать два адреса потока в одну несуществующую инструкцию.

    **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

13. Как шаг строки, или pitch, влияет на адреса двумерного буфера и выравнивание строк? Для ширины 100 элементов `float` и шага строки 512 байт запишите адрес элемента `(row, col)` и объясните, почему умножение `row * width` здесь не описывает физическое размещение.

    **Ответ:** При pitch=512 байт адрес равен `base+row*512+col*4`. Полезная строка занимает 400 байт, остаток — padding. В типизированных элементах ld равен 128, а не 100.

    **Типичная ошибка:** Передавать pitch в байтах как число float.

    **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

14. Какие компромиссы возникают при выборе AoS, SoA и AoSoA? Сравните kernels, которые читают одно поле, все поля одной частицы или группы полей нескольких частиц, учитывая padding структур, объём преобразования формата и фактическое повторное использование данных.

    **Ответ:** SoA удобен для отдельных полей; AoS может быть удобен при обработке всех полей объекта; AoSoA группирует поля по небольшим пакетам. Выбор зависит от инструкций, padding, reuse и стоимости преобразования, которую включают в полный замер.

    **Типичная ошибка:** Объявлять SoA лучшим для любого доступа.

    **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

15. Как вычислить эффективную пропускную способность kernel и не смешать GB/s с GiB/s? Для копирования массива из 64 миллионов `float` за 1 мс посчитайте полезные байты чтения и записи, затем объясните, почему полученное значение нельзя автоматически считать трафиком DRAM.

    **Ответ:** Читают и записывают `64 000 000*4*2=512 000 000` байт. За 0,001 с это 512 GB/s или примерно 476,84 GiB/s. Это эффективная полезная bandwidth, а не обязательно физический DRAM-трафик.

    **Типичная ошибка:** Смешивать десятичные GB и двоичные GiB.

    **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

16. Какие задачи выполняют L1 и L2 при обращениях к global memory на конкретном GPU NVIDIA? Сравните однократный проход по большому массиву и повторное чтение небольшого набора; объясните, почему политика кэширования и размеры кэшей требуют проверки для целевой архитектуры.

    **Ответ:** L1 обслуживает локальность на SM, L2 — общий уровень между SM и DRAM; конкретные пути и политики зависят от архитектуры. Поток большого массива почти не повторяет данные, малый набор может многократно попадать в кэш. Проверяют размеры, инструкции и hit rates.

    **Типичная ошибка:** Считать каждый global load обязательным чтением DRAM.

    **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

## Сложный уровень

17. Когда uniform-доступ к небольшому набору коэффициентов может быть подходящим случаем для constant memory в CUDA? Сравните чтение одного и того же адреса всеми активными потоками warp и чтение разных адресов, затем сформулируйте эксперимент, который проверит пригодность без предположения «read-only всегда быстрее».

    **Ответ:** Constant memory подходит небольшим коэффициентам с одинаковым адресом у lanes: возможен broadcast. Разные адреса внутри warp могут обслуживаться последовательно по различным значениям адресов. Сравнивают uniform и разнородные индексы с обычным чтением на одном GPU.

    **Типичная ошибка:** Считать любую read-only таблицу хорошим кандидатом для constant memory.

    **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

18. Для чего в CUDA используются texture objects и какие свойства доступа они могут предоставлять помимо обычного чтения указателя? Сравните целочисленное чтение массива с пространственно локальными выборками, адресацией на границах и фильтрацией, учитывая поддерживаемый формат данных и конкретные настройки объекта.

    **Ответ:** Texture objects задают представление данных, режимы координат, границ и при поддержке формата — фильтрацию. Для простого целочисленного fetch преимущества не гарантированы; spatial locality и аппаратная интерполяция могут быть полезны. Проверяют тип ресурса, normalized coordinates и доступные режимы.

    **Типичная ошибка:** Ожидать линейную фильтрацию для любого формата и ресурса.

    **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

19. Почему полезные байты алгоритма, запросы к кэшам и трафик DRAM могут существенно различаться? Разберите повторное чтение общего входного массива соседними блоками и чтение подмассива со сдвигом, затем определите, какие показатели профиля нужны для проверки гипотез о повторном использовании и лишних передачах.

    **Ответ:** Полезные байты считают логическую работу, cache requests — запросы инструкций, DRAM — промахи/записи нижнего уровня. Общие данные блоков могут попадать в L2, сдвиги — увеличивать число секторов. Смотрят sectors/request, L1/L2 hits и DRAM bytes на одинаковом входе.

    **Типичная ошибка:** Выводить DRAM-трафик только из количества выражений чтения в C++.

    **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

20. При каких условиях векторизованная загрузка нескольких элементов одним потоком может оказаться полезной? Сравните скалярные загрузки и доступ к типу наподобие `float4`, отдельно проверив выравнивание, хвост массива, действительный тип объектов, количество инструкций и влияние на регистры; не выводите coalescing только из имени векторного типа.

    **Ответ:** Векторная загрузка может уменьшить число инструкций при нескольких элементах на поток. Нужны допустимый тип/aliasing, 16-байтное выравнивание float4, корректный хвост и достаточно регистров. Coalescing определяют адреса всей warp-инструкции; проверяют машинный код и время.

    **Типичная ошибка:** Делать `reinterpret_cast<float4*>` на смещённый невыравненный адрес.

    **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

21. Как разработать микробенчмарк, который отделяет влияние stride, выравнивания и кэша? Задайте размеры рабочих наборов, объём полезных данных, прогрев, проверку результата и способ исключить удаление загрузок компилятором, затем объясните, какие параметры нужно сохранять одинаковыми при сравнении.

    **Ответ:** Меняют по одному stride, сдвиг и размер рабочего набора относительно кэшей; сохраняют объём полезных обращений, данные и launch. Делают warm/cold варианты, повторения и проверку checksum, записанного в выход, чтобы загрузки не удалились. Измеряют events и счётчики памяти.

    **Типичная ошибка:** Одновременно менять размер, stride и число потоков.

    **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

22. Почему изменение cache policy или использование read-only пути не является универсальной оптимизацией CUDA? Сформулируйте гипотезы для однократного потока данных и многократного чтения небольшого набора, затем предложите проверку поддержки механизма, сгенерированных инструкций и изменения трафика на выбранном GPU.

    **Ответ:** Однократный поток может выиграть от уменьшения загрязнения кэша; повторное чтение малого набора — от сохранения данных. Проверяют доступность политики, сгенерированные инструкции, hit rates, DRAM bytes и время. Эффект зависит от конкурирующих обращений и архитектуры.

    **Типичная ошибка:** Включать cache hint без подтверждения его эффекта.

    **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

23. Как определить, окупается ли предварительное преобразование AoS в SoA? В учебной модели преобразование занимает 2 мс, одна обработка AoS — 1,2 мс, а SoA — 0,7 мс; найдите число повторных обработок, после которого преобразование выгодно, и отдельно разберите необходимость обратного преобразования за 1 мс.

    **Ответ:** Без обратного преобразования выгодно `2+0,7k<1,2k`, то есть k>4: с 5 обработок. С обратным за 1 мс требуется `3<0,5k`, то есть с 7; при 4 и 6 соответственно — равенство.

    **Типичная ошибка:** Называть точку равенства строгим выигрышем.

    **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).

24. Как последовательно улучшать kernel, который читает частицы со случайными индексами и записывает результат в исходном порядке? Сравните изменение расположения полей, группировку или сортировку запросов, дополнительное отображение индексов и использование кэша, сохраняя семантику повторяющихся индексов; определите, какие замеры подтвердят выигрыш всей операции с учётом подготовки данных.

    **Ответ:** Сначала измеряют чтения нужных полей и переходят к подходящему layout. Затем пробуют группировать индексы по локальности с обратным отображением результата; повторяющиеся запросы сохраняют отдельные выходы либо явно согласованную семантику. Время сортировки, перестановки и восстановления порядка включают в end-to-end.

    **Типичная ошибка:** Ускорить kernel сортировкой, потеряв порядок или стоимость подготовки.

    **Источник:** [CUDA Best Practices: Memory Optimizations](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#memory-optimizations).
