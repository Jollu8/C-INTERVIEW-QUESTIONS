# 6. CI/CD и автоматизация

## 6.1 CI Pipelines

### Сборка + тесты + линтинг

## L1

1. (L1, T) Что такое CI?

   **Ответ:** Continuous Integration — частая интеграция изменений с автоматической сборкой и проверками общего состояния проекта.

   **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

2. (L1, T) Что такое CD?

   **Ответ:** Continuous Delivery поддерживает готовность к выпуску; Continuous Deployment автоматически выпускает прошедшие проверки изменения.

   **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

3. (L1, T) Зачем C/C++ проекту CI pipeline?

   **Ответ:** Проверять совместимость toolchain, dependencies, конфигураций и поведение кода до интеграции, а не на машине автора.

   **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

4. (L1, T) Какие базовые стадии обычно есть в pipeline?

   **Ответ:** Checkout/setup → configure/build → tests/analysis → package; deploy добавляют по требованиям продукта.

   **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

5. (L1, T) Почему недостаточно просто “чтобы код компилировался локально”?

   **Ответ:** Локально могут быть лишние dependencies, stale artifacts, иные flags и окружение; общий gate должен быть воспроизводимым.

   **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

6. (L1, T) Что обычно проверяется на этапе build?

   **Ответ:** Доступность dependencies, корректность configure, compilation и linking в выбранной конфигурации.

   **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

7. (L1, T) Что обычно проверяется на этапе test?

   **Ответ:** Ожидаемое поведение и regression scenarios; build success не проверяет runtime correctness.

   **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

8. (L1, T) Что обычно проверяется на этапе lint?

   **Ответ:** Согласованные formatting/static rules и выбранные code quality checks; состав зависит от политики проекта.

   **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

9. (L1, P) Какие минимальные шаги ты бы добавил в CI для небольшого C++ проекта?

   **Ответ:** Clean checkout, pinned toolchain, CMake configure/build, CTest и проверка форматирования; сохранить failure logs.

   **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

10. (L1, D) Почему pipeline может падать, если локально все “работает”?

    **Ответ:** Различаются compiler, dependency versions, filesystem, locale, permissions, ресурсы или скрытое локальное состояние.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)


## L2

11. (L2, T) Чем unit tests отличаются от integration tests в контексте CI?

    **Ответ:** Unit проверяет узкий компонент, integration — связи компонентов/систем; вторые обычно требуют дополнительных ресурсов и окружения.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

12. (L2, T) Почему build, tests и linting лучше разделять на отдельные jobs?

    **Ответ:** Независимые jobs дают parallelism и понятный failure owner; зависимые тесты должны получать exact build artifacts.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

13. (L2, T) Что такое fail-fast pipeline?

    **Ответ:** Рано прекращает явно бесполезную работу после ошибки; в matrix может отменять оставшиеся jobs.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

14. (L2, T) Когда fail-fast полезен, а когда мешает?

    **Ответ:** Экономит время после fatal ошибки, но может скрыть независимые failures, нужные для анализа platform matrix.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

15. (L2, P) Как организовать pipeline: configure → build → test?

    **Ответ:** `cmake -S . -B build`, `cmake --build build --parallel 2`, `ctest --test-dir build --output-on-failure`; ошибки не подавлять.

    **Пример:** Linux shell steps, с отдельным build tree на конфигурацию:

    ```bash
    cmake -S . -B build-ci -DCMAKE_BUILD_TYPE=RelWithDebInfo -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
    cmake --build build-ci --parallel 2
    ctest --test-dir build-ci --output-on-failure --no-tests=error
    ```

    BUILD_TYPE относится к single-config generators; для multi-config задают `--config`. `--no-tests=error` поддерживается CTest 3.26+ и предотвращает ложный успех пустого test suite.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

16. (L2, P) Как добавить линтер в pipeline?

    **Ответ:** Зафиксировать version/config и отдельным step запустить clang-tidy либо formatter check; определить exit-code policy.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

17. (L2, D) Почему тесты проходят локально, но нестабильны в CI?

    **Ответ:** Меньше CPU, иные timing/order, ресурсы и изоляция проявляют races и shared-state assumptions.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

18. (L2, D) Какие причины flaky tests наиболее типичны для C/C++?

    **Ответ:** Data races, time-based sleeps, зависимость от test order, shared ports/files, UB и внешняя сеть.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

19. (L2, T) Почему environment parity важен для CI?

    **Ответ:** Близкое окружение уменьшает различия, которые мешают воспроизводить failures; дополнительные platforms всё равно проверяют отдельно.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

20. (L2, T) Что такое reproducible pipeline?

    **Ответ:** Pipeline с фиксированными inputs и описанным окружением, который можно повторить; это ещё не гарантирует bit-identical binaries.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)


## L3

21. (L3, T) Как проектировать stages для большого C/C++ проекта?

    **Ответ:** Строить dependency DAG, отделять cheap gates от full matrix и передавать exact artifacts вместо случайных rebuilds.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

22. (L3, T) Когда делать matrix builds?

    **Ответ:** Когда продукт поддерживает несколько OS, architectures, compilers или options; выбирать комбинации по риску и стоимости.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

23. (L3, T) Зачем проверять несколько компиляторов и несколько build types?

    **Ответ:** Разные компиляторы обнаруживают разные проблемы, optimization проявляет UB, debug облегчает диагностику.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

24. (L3, P) Как встроить sanitizer builds в pipeline?

    **Ответ:** Отдельные build directories и compile/link sanitizer flags; запускать ASan/UBSan и TSan в совместимых отдельных jobs.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

25. (L3, P) Как встроить static analysis в pipeline без чрезмерного slowdown?

    **Ответ:** Быстрые trusted checks на PR, cache конфигурации и full analysis по расписанию; generated/third-party paths исключать явно.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

26. (L3, D) Почему pipeline медленный и как найти узкие места?

    **Ответ:** Измерить queue, setup, configure, compile, linking и tests отдельно; оптимизировать крупнейший critical path.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

27. (L3, D) Почему CI обнаруживает missing dependencies, которые не видны локально?

    **Ответ:** Clean runner не содержит случайных packages и старых generated headers; это выявляет незаявленные inputs.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

28. (L3, T) Когда нужны nightly jobs, а не только per-commit jobs?

    **Ответ:** Для долгих stress/fuzz, полной matrix и глубокого анализа; критичные быстрые проверки должны оставаться на PR.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

29. (L3, S) Как разделить “быстрые обязательные проверки” и “дорогие глубокие проверки”?

    **Ответ:** Разделить по времени, defect impact и supported configurations; nightly failures тоже должны иметь owner и срок реакции.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

30. (L3, D) Как расследовать intermittent failures в C++ pipeline?

    **Ответ:** Сохранять exact inputs, logs, seed и environment; различать infrastructure, flaky test и product defect.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)


## L4

31. (L4, S) Как спроектировать CI strategy для большого монорепозитория на C/C++?

    **Ответ:** Dependency-aware affected checks, общие templates, full periodic validation и владельцы каждого gate; не полагаться на path filters без graph.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

32. (L4, S) Как выбрать quality gates, чтобы не убить velocity команды?

    **Ответ:** Блокировать reproducible high-signal defects; шумные проверки сначала стабилизировать или делать advisory с owner.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

33. (L4, S) Как построить pipeline, который одновременно быстрый, надежный и воспроизводимый?

    **Ответ:** Pinned images/dependencies, isolated workspaces, correct caching, parallel DAG и сохранение diagnostic artifacts.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

34. (L4, D) Как triage'ить постоянный поток CI failures в большой организации?

    **Ответ:** Классифицировать причины и frequency, назначать owners, устранять повторяющиеся flakes и infrastructure failures.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)

35. (L4, S) Как превратить CI из “формальной галочки” в реальный инженерный контроль качества?

    **Ответ:** Проверки должны соответствовать реальным defect classes, иметь прозрачный failure report и измеримую полезность.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html)


### Caching Build Artifacts

## L1

36. (L1, T) Что такое build cache?

    **Ответ:** Повторное использование результатов, вычисленных для эквивалентных inputs; корректность зависит от полноты ключа.

    **Источник:** [ccache manual](https://ccache.dev/manual/latest.html); [GitHub: Caching dependencies](https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows)

37. (L1, T) Зачем кэшировать артефакты сборки?

    **Ответ:** Чтобы не повторять дорогую compilation/download работу при неизменных inputs.

    **Источник:** [ccache manual](https://ccache.dev/manual/latest.html); [GitHub: Caching dependencies](https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows)

38. (L1, T) Что обычно кэшируют в C/C++ pipeline?

    **Ответ:** Package downloads, compiler cache вроде ccache/sccache и outputs поддерживающей cache build system.

    **Источник:** [ccache manual](https://ccache.dev/manual/latest.html); [GitHub: Caching dependencies](https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows)

39. (L1, T) Чем dependency cache отличается от artifact cache?

    **Ответ:** Dependency cache ускоряет получение inputs; artifact cache переиспользует outputs. Release artifacts требуют отдельной идентичности и хранения.

    **Источник:** [ccache manual](https://ccache.dev/manual/latest.html); [GitHub: Caching dependencies](https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows)

40. (L1, D) Почему без cache pipeline может быть слишком медленным?

    **Ответ:** Каждый job заново скачивает и компилирует одинаковые зависимости, даже если изменений почти нет.

    **Источник:** [ccache manual](https://ccache.dev/manual/latest.html); [GitHub: Caching dependencies](https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows)


## L2

41. (L2, T) Какие риски у build caching?

    **Ответ:** Неполные keys, stale outputs, несовместимые configs и cache poisoning; cache не должен быть необходим для correctness.

    **Источник:** [ccache manual](https://ccache.dev/manual/latest.html); [GitHub: Caching dependencies](https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows)

42. (L2, D) Почему cache может приводить к “ложно зеленым” pipeline?

    **Ответ:** Ошибочно переиспользует output, игнорируя изменённый header, generator, flag или dependency.

    **Источник:** [ccache manual](https://ccache.dev/manual/latest.html); [GitHub: Caching dependencies](https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows)

43. (L2, T) Что влияет на cache key?

    **Ответ:** Source/generated inputs, compiler/toolchain, platform, flags и dependency lockfiles; конкретный compiler cache учитывает часть автоматически.

    **Пример:** Внешний cache scope: OS + target + compiler identity + dependency-lock hash + sanitizer/config. Это схема inputs, а не готовая строка key для любого cache backend.

    **Типичная ошибка:** Один writable cache для release и untrusted PR, содержащий одновременно package downloads и готовые executables.

    **Источник:** [ccache manual](https://ccache.dev/manual/latest.html); [GitHub: Caching dependencies](https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows)

44. (L2, P) Какие директории обычно стоит кэшировать в CMake/Ninja проекте?

    **Ответ:** Compiler cache и package cache; перенос всего build tree рискован из-за absolute paths, generator state и toolchain mismatch.

    **Источник:** [ccache manual](https://ccache.dev/manual/latest.html); [GitHub: Caching dependencies](https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows)

45. (L2, P) Как кэшировать зависимости package manager'а?

    **Ответ:** Использовать documented package-manager cache path и key от lockfile/platform/toolchain; не кэшировать credentials.

    **Источник:** [ccache manual](https://ccache.dev/manual/latest.html); [GitHub: Caching dependencies](https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows)

46. (L2, D) Почему stale cache ломает сборку?

    **Ответ:** Старые outputs не соответствуют текущим inputs либо содержат state, который build graph не умеет инвалидировать.

    **Источник:** [ccache manual](https://ccache.dev/manual/latest.html); [GitHub: Caching dependencies](https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows)

47. (L2, T) Когда лучше сохранять артефакты, а не кэш?

    **Ответ:** Когда нужен конкретный output данного run: binaries, symbols, packages и reports для downstream jobs или выпуска.

    **Источник:** [ccache manual](https://ccache.dev/manual/latest.html); [GitHub: Caching dependencies](https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows)

48. (L2, D) Почему cache hit не гарантирует корректность результата?

    **Ответ:** Key может быть неполным, а cache entry повреждённым; periodic clean builds проверяют независимость от cache.

    **Источник:** [ccache manual](https://ccache.dev/manual/latest.html); [GitHub: Caching dependencies](https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows)

49. (L2, P) Как разделять cache между branch'ами и main?

    **Ответ:** Общий доверенный read baseline и отдельные write scopes для branches; untrusted jobs не должны менять release cache.

    **Источник:** [ccache manual](https://ccache.dev/manual/latest.html); [GitHub: Caching dependencies](https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows)

50. (L2, T) Почему compiler version должна участвовать в cache key?

    **Ответ:** Версия влияет на codegen, object format, diagnostics и ABI; одинаковый source не означает эквивалентный output.

    **Источник:** [ccache manual](https://ccache.dev/manual/latest.html); [GitHub: Caching dependencies](https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows)


## L3

51. (L3, T) Что такое remote build cache?

    **Ответ:** Общее хранилище результатов сборки для нескольких workers, обычно адресуемое по digest inputs.

    **Источник:** [ccache manual](https://ccache.dev/manual/latest.html); [GitHub: Caching dependencies](https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows)

52. (L3, T) Как cache взаимодействует с reproducibility?

    **Ответ:** Корректный cache сохраняет результат; reproducibility позволяет независимо проверить его пересборкой с теми же inputs.

    **Источник:** [ccache manual](https://ccache.dev/manual/latest.html); [GitHub: Caching dependencies](https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows)

53. (L3, D) Почему инкрементальная локальная логика не всегда переносится на CI cache?

    **Ответ:** CI меняет paths, workspace lifetime и toolchain; сохранённый локальный build tree может содержать скрытые machine-specific inputs.

    **Источник:** [ccache manual](https://ccache.dev/manual/latest.html); [GitHub: Caching dependencies](https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows)

54. (L3, P) Как проектировать ключи кэша для toolchain + dependencies + build config?

    **Ответ:** Включить image/toolchain identity, target, dependency lock hash и config; source keys делегировать compiler/build cache где возможно.

    **Источник:** [ccache manual](https://ccache.dev/manual/latest.html); [GitHub: Caching dependencies](https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows)

55. (L3, D) Почему LTO/sanitizer/debug/release сборки нельзя бездумно смешивать в одном cache?

    **Ответ:** Отличаются instrumentation, bitcode compatibility и runtime dependencies; cache должен различать все влияющие flags.

    **Источник:** [ccache manual](https://ccache.dev/manual/latest.html); [GitHub: Caching dependencies](https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows)

73. (L2, P) Как настроить matrix build для GCC и Clang?

    **Ответ:** Добавить `strategy.matrix` с compiler entries и выбрать согласованные CC/CXX при configure в отдельный build directory.

    **Пример:** Фрагмент job GitHub Actions для Linux runner с установленными GCC/Clang; checkout и setup выполняются предыдущими steps.

    ```yaml
    strategy:
      fail-fast: false
      matrix:
        include:
          - { cc: gcc, cxx: g++ }
          - { cc: clang, cxx: clang++ }
    steps:
      - name: Configure
        env:
          CC: ${{ matrix.cc }}
          CXX: ${{ matrix.cxx }}
        run: cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo
      - name: Build
        run: cmake --build build --parallel 2
      - name: Test
        run: ctest --test-dir build --output-on-failure
    ```

    Каждая matrix entry — отдельный job; versions compilers задаёт setup/image, а имена gcc/clang сами их не фиксируют.

    **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions)

126. (L1, T) Что такое Jenkins?

     **Ответ:** CI automation server с extensible plugins и выполнением jobs на agents.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

127. (L1, T) В чем базовая идея Jenkins pipeline?

     **Ответ:** Описывать checkout/build/test/package как versioned pipeline с явными stages, inputs и failure semantics.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

128. (L1, T) Что такое Jenkins agent?

     **Ответ:** Execution node для jobs; controller управляет orchestration, а heavy build лучше выполнять на agents.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

129. (L1, T) Что такое Jenkinsfile?

     **Ответ:** Файл pipeline-as-code в репозитории, обычно Declarative или Scripted Pipeline.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

130. (L1, P) Как на базовом уровне описать C++ build job в Jenkins?

     **Ответ:** В Jenkinsfile определить agent и stages с `sh` для cmake configure/build и ctest; сохранять test reports в post.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)


## L2

131. (L2, T) Разница freestyle jobs vs pipeline as code?

     **Ответ:** Freestyle настраивается преимущественно через UI; pipeline-as-code версионирует логику и позволяет review вместе с исходниками.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

132. (L2, P) Как разбить Jenkins pipeline на stages?

     **Ответ:** Declarative `stages { stage('Build') { steps { ... } } }`; boundaries выбирать по зависимости и диагностике.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

133. (L2, P) Как сохранять artifacts в Jenkins?

     **Ответ:** Использовать archiveArtifacts для outputs; stash/unstash предназначены для передачи в рамках pipeline и не заменяют release repository.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

134. (L2, D) Почему Jenkins job может зависеть от состояния машины-агента?

     **Ответ:** Workspace, installed packages, environment и external files могут сохраняться между runs и образовывать скрытые dependencies.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

135. (L2, T) Почему Jenkins historically часто ассоциируется с “snowflake CI”?

     **Ответ:** Ручные UI configs и индивидуально настроенные agents исторически создавали уникальные environments; Jenkins не требует такого подхода.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

136. (L2, P) Как параметризовать pipeline по compiler/build type?

     **Ответ:** Declarative parameters/environment либо matrix axes; compiler и config фиксировать в manifest и отдельном build tree.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

137. (L2, D) Почему один и тот же job нестабилен на разных agents?

     **Ответ:** Разные images/toolchains, resources, workspaces и permissions; label сам по себе не доказывает environment equivalence.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

138. (L2, T) Как plugins влияют на надежность Jenkins?

     **Ответ:** Добавляют capabilities, но также dependencies, compatibility и update/security burden.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

139. (L2, D) Почему Jenkins instance со временем “обрастает” скрытой сложностью?

     **Ответ:** Накапливаются plugins, scripts, shared state, UI settings и credentials без единого ownership/versioning.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

140. (L2, P) Как запускать тесты и собирать отчеты в Jenkins?

     **Ответ:** Запустить CTest с JUnit output при поддержке версии и опубликовать `junit` report в post/always.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)


## L3

141. (L3, S) Как проектировать Jenkins pipeline для legacy C++ проекта?

     **Ответ:** Сначала воспроизводимая CLI сборка и artifact identity, затем перенос existing gates в Jenkinsfile без смены смысла тестов.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

142. (L3, D) Как расследовать проблемы из-за дрейфа окружения на agents?

     **Ответ:** Снять agent/image/package manifest и compare successful/failed run; использовать disposable agents и pinned toolchain.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

143. (L3, T) Когда Jenkins still makes sense по сравнению с GitHub/GitLab CI?

     **Ответ:** Когда нужны существующие integrations, special hardware и controlled on-prem operation при приемлемой стоимости сопровождения.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

144. (L3, P) Как изолировать сборки через containerized agents?

     **Ответ:** Использовать supported container agents с pinned image; workspace, mounts и privileges тоже входят в isolation contract.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

145. (L3, D) Почему Jenkins plugins — частый источник operational риска?

     **Ответ:** Обновления затрагивают dependency graph и совместимость server; plugin выполняет код с существенным доступом.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

146. (L3, S) Как организовать shared libraries и reusable stages в Jenkins?

     **Ответ:** Shared Libraries с versioned API и tests; consumer должен контролировать version, а rollout иметь rollback.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

147. (L3, D) Как уменьшить build queue и contention на limited agents?

     **Ответ:** Измерять resource/queue utilization, разграничивать heavy jobs, масштабировать agent pools и избегать конкурирующих builds за один workspace.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

148. (L3, S) Как мигрировать Jenkins pipelines без потери контроля над quality gates?

     **Ответ:** Перенести gates с contract tests и shadow runs; сравнить results/artifacts до включения новой платформы как required.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

149. (L3, D) Как диагностировать деградацию производительности Jenkins master/agents?

     **Ответ:** Проверить controller CPU/heap/GC, plugin load, I/O и agent network/resources; не смешивать controller bottleneck с compile time.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

150. (L3, S) Как управлять секретами и доступом в Jenkins для C++ delivery pipeline?

     **Ответ:** Credentials bindings и least privilege с scoped access; untrusted builds не должны получать release credentials или privileged agents.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)


## L4

151. (L4, S) Как принимать решение: оставаться на Jenkins или мигрировать?

     **Ответ:** Сравнить migration cost, integrations, reliability, security и ownership; наличие legacy pipelines само по себе не решает выбор.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

152. (L4, S) Как строить governance для Jenkins platform в крупной организации?

     **Ответ:** Configuration-as-code, approved plugins, managed agent images, owners и staged upgrade policy.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

153. (L4, D) Как расследовать supply-chain риски и плагин-зависимости Jenkins?

     **Ответ:** Инвентаризировать plugins/versions, источники updates и privileges; сопоставить advisories и pipeline credentials exposure.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

154. (L4, S) Как стандартизировать pipeline-as-code в исторически “ручной” Jenkins среде?

     **Ответ:** Инвентаризация jobs, reproducible CLI, Jenkinsfile/shared libraries и удаление недокументированных UI dependencies поэтапно.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

155. (L4, S) Как организовать поэтапную миграцию legacy Jenkins estate в современную CI/CD платформу?

     **Ответ:** Классифицировать jobs, перенести типовые, сравнить shadow results, переключать по группам с rollback и retirement plan.

     **Источник:** [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/)

## 6.3 Code Quality

### clang-tidy

## L1

156. (L1, T) Что такое clang-tidy?

     **Ответ:** Clang-based инструмент статического анализа и lint checks для C/C++ с доступом к AST.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

157. (L1, T) Зачем нужен clang-tidy, если код уже компилируется?

     **Ответ:** Compilation не проверяет все подозрительные паттерны и API misuse; tidy добавляет configurable проверки и некоторые fixes.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

158. (L1, T) Какие типы проблем ищет clang-tidy?

     **Ответ:** Bug-prone patterns, portability, performance, modernization, readability и analyzer diagnostics; checks зависят от версии.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

159. (L1, P) Как запустить clang-tidy локально?

     **Ответ:** `clang-tidy src/main.cpp -p build`; build должен содержать актуальную compilation database и generated headers.

     **Пример:** Для CMake с Makefiles/Ninja:

     ```bash
     cmake -S . -B build-analysis -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
     cmake --build build-analysis --parallel 2
     clang-tidy src/main.cpp -p build-analysis
     ```

     Build нужен, если анализируемый TU включает generated headers. Выбранный файл должен присутствовать в database.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

160. (L1, T) Почему clang-tidy опирается на compile_commands.json?

     **Ответ:** Точные flags, includes и macros нужны для правильного разбора translation unit в контексте проекта.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)


## L2

161. (L2, T) Чем clang-tidy отличается от compiler warnings?

     **Ответ:** Warnings встроены в compiler pipeline; tidy предоставляет отдельные extensible checks и transformation tooling. Области пересекаются.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

162. (L2, P) Как запускать clang-tidy только на измененных файлах?

     **Ответ:** Запустить на changed translation units; header changes требуют затронутых consumers. Diff-only reporting не заменяет dependency analysis.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

163. (L2, D) Почему clang-tidy в CI может ругаться на код, который локально “чистый”?

     **Ответ:** Иные version/checks, compilation database, include paths и macros; сравнивать exact command lines.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

164. (L2, T) Какие категории проверок бывают у clang-tidy?

     **Ответ:** Например bugprone, performance, modernize, readability, portability и clang-analyzer; конкретные checks выбирать явно.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

165. (L2, P) Как настраивать checks через `.clang-tidy`?

     **Ответ:** Задать `Checks`, `WarningsAsErrors` и CheckOptions; проверить effective configuration через `--dump-config`.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

166. (L2, D) Почему слишком много правил делает tool бесполезным для команды?

     **Ответ:** Шум и низкая полезность снижают доверие; правила должны соответствовать реальным рискам и стилю проекта.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

167. (L2, T) Что такое auto-fix в clang-tidy и где он уместен?

     **Ответ:** Автоматическое применение предложенных edits; подходит механическим изменениям после review, diff и проверки сборки/тестов.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

168. (L2, D) Как бороться с false positives?

     **Ответ:** Сначала проверить configuration и reproducer; затем точечный NOLINT с причиной или исправление upstream, без blanket disable.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

169. (L2, P) Как встроить clang-tidy в pipeline без чрезмерного времени выполнения?

     **Ответ:** Анализировать relevant TUs параллельно с bounded memory, reuse build metadata и полный scheduled pass.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

170. (L2, T) Когда clang-tidy должен быть advisory, а когда blocking?

     **Ответ:** High-confidence correctness checks могут блокировать; новые/шумные правила сначала advisory с измерением false positives.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)


## L3

171. (L3, S) Как выбрать обязательный набор clang-tidy checks для команды?

     **Ответ:** Выбирать по defect history, поддержке toolchain и signal/noise; документировать rationale и owner.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

172. (L3, D) Как внедрять clang-tidy в legacy-кодовую базу без “красного моря” ошибок?

     **Ответ:** Зафиксировать existing baseline, блокировать новые важные findings, исправлять legacy по приоритету.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

173. (L3, P) Как организовать baseline/suppressions для постепенного улучшения качества?

     **Ответ:** Стабильная baseline identity, узкие suppressions с owner/reason и регулярным пересмотром; не скрывать новые findings в старом шуме.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

174. (L3, D) Почему clang-tidy может давать разные результаты при смене toolchain/flags?

     **Ответ:** Меняются AST, models, macros и implementation checks; version/config входят в анализируемое окружение.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

175. (L3, S) Как разделять style rules и correctness rules?

     **Ответ:** Formatting оставить formatter, correctness checks отделить по gate/severity; субъективный стиль не должен маскировать bug reports.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

176. (L3, P) Как связать clang-tidy output с review process?

     **Ответ:** Публиковать file/line/check/message и воспроизводимую команду; reviewer оценивает root cause и diff, а не только число warnings.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

177. (L3, D) Как triage'ить тысячи старых замечаний clang-tidy?

     **Ответ:** Дедупликация, группировка по rule/root cause, severity и ownership; массовые mechanical fixes отдельно от logic changes.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

178. (L3, S) Как измерять эффективность clang-tidy, а не просто “количество warning'ов”?

     **Ответ:** Измерять подтверждённые defects, false positives, fix time и feedback latency, а не raw warning count.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

179. (L3, P) Как запускать разные наборы проверок для PR и nightly?

     **Ответ:** Отдельные configs/check sets с общей version baseline; PR — быстрые checks, nightly — полный анализ с owners.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

180. (L3, S) Как интегрировать clang-tidy с developer workflow, а не только с CI?

     **Ответ:** Одинаковый config/version в editor, локальном script и CI; быстрый reproduction path снижает friction.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)


## L4

181. (L4, S) Как строить organizational policy по static checks для C/C++?

     **Ответ:** Базовый обязательный набор и product-specific extensions, versioned rollout и exception process с owner.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

182. (L4, S) Как выбирать между строгим quality gate и постепенной миграцией?

     **Ответ:** Строгий gate подходит новым high-signal checks; legacy debt снижать постепенно без требования исправить всё сразу.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

183. (L4, D) Как расследовать случаи, когда clang-tidy мешает velocity больше, чем помогает?

     **Ответ:** Измерить run time, false positives и rework, опросить concrete failure cases; убрать ineffective rules или настроить окружение.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

184. (L4, S) Как формализовать ownership за quality rule set?

     **Ответ:** Назначить maintainers, review rule changes и срок пересмотра suppressions; конфигурация — versioned часть проекта.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

185. (L4, S) Как использовать clang-tidy как часть архитектурной дисциплины, а не только lint?

     **Ответ:** Проверять agreed ownership/API patterns подходящими checks, но архитектурные свойства дополнять review и runtime tests.

     **Источник:** [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)


### clang-format

## L1

186. (L1, T) Что такое clang-format?

     **Ответ:** Инструмент автоматического форматирования source code по конфигурации style.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

187. (L1, T) Зачем нужен единый code style?

     **Ответ:** Уменьшает различия оформления и освобождает review для поведения и дизайна.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

188. (L1, P) Как форматировать файл через clang-format?

     **Ответ:** `clang-format -i src/main.cpp`; сначала убедиться в версии и выбранной `.clang-format`.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

189. (L1, T) Почему автоформатирование уменьшает шум в review?

     **Ответ:** Механические решения единообразны, а отдельные format commits не смешивают стиль с логикой.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

190. (L1, D) Почему “споры о стиле” лучше решать инструментом?

     **Ответ:** Согласованная конфигурация автоматически исполняет принятые правила, не требуя обсуждения каждого отступа.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)


## L2

191. (L2, T) Как настраивается `.clang-format`?

     **Ответ:** YAML с BasedOnStyle и overrides; доступные options зависят от версии formatter.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

192. (L2, P) Как проверять форматирование в CI?

     **Ответ:** `clang-format --dry-run --Werror src/main.cpp` на выбранных файлах при поддержке версии; никакой записи в рабочее дерево не требуется.

     **Типичная ошибка:** Запускать `clang-format -i` в CI и не проверять diff/exit status: job может остаться зелёным после изменения исходников.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

193. (L2, P) Как форматировать только измененные строки/файлы?

     **Ответ:** Передавать changed files либо применять git-clang-format/clang-format-diff; форматирование строк может затронуть соседний syntactic context.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

194. (L2, D) Почему несогласованная версия clang-format ломает workflow команды?

     **Ответ:** Версии по-разному интерпретируют options и layout; закрепить единую версию в editor и CI.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

195. (L2, T) Почему массовое reformatting-изменение опасно для blame/history?

     **Ответ:** Создаёт широкий diff и меняет line attribution; отдельный commit можно добавить в blame ignore revisions.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

196. (L2, S) Когда делать big-bang reformat, а когда gradual adoption?

     **Ответ:** Big-bang удобен при координированном коротком freeze; gradual adoption уменьшает разовый конфликт, но временно смешивает стиль.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

197. (L2, D) Почему форматирование не должно смешиваться с логическими изменениями?

     **Ответ:** Иначе reviewer труднее видит semantic change и переносит patch между branches.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

198. (L2, P) Как встроить clang-format в pre-commit или editor integration?

     **Ответ:** Общий versioned script/hook и format-on-save; CI проверяет тем же инструментом, не полагаясь только на локальный hook.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

199. (L2, T) Какие ограничения у clang-format как style tool?

     **Ответ:** Не проверяет correctness, naming semantics и архитектуру; не все preferences выразимы настройками.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

200. (L2, D) Что делать, если tool форматирует “не так, как нравится”?

     **Ответ:** Проверить доступную option и договорённость команды; локальное исключение должно иметь конкретную причину, а не персональный вкус.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)


## L3

201. (L3, S) Как внедрять clang-format в legacy-репозитории?

     **Ответ:** Определить scope/version, exclude vendored/generated code, выполнить отдельный mechanical rollout с документированной локальной командой.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

202. (L3, D) Как избежать конфликтов между formatter, generated code и third-party code?

     **Ответ:** Явный allowlist/exclude paths и форматирование источника generator template вместо его outputs где уместно.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

203. (L3, P) Как отделить policy для internal code и external/vendored code?

     **Ответ:** Собственный config для internal paths; vendor snapshots сохранять по upstream policy, проверяя только свои изменения при необходимости.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

204. (L3, S) Как сделать style checks быстрыми и нераздражающими?

     **Ответ:** Проверять changed files, выдавать точную fix command и согласовать editor version с CI.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

205. (L3, D) Почему строгий format gate может неожиданно тормозить delivery?

     **Ответ:** Version drift, неправильный scope или format churn создают повторные failures без полезного качества.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

206. (L3, S) Как минимизировать merge conflicts после массового форматирования?

     **Ответ:** Короткое окно rollout, отдельный commit и координация активных branches; заранее сообщить rebase strategy.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

207. (L3, P) Как организовать auto-format suggestions в CI/PR comments?

     **Ответ:** Генерировать downloadable patch или review suggestions с точным scope; запись/комментарии требуют соответствующих permissions.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

208. (L3, D) Как выбирать стабильную версию formatter для команды?

     **Ответ:** Выбрать доступную всем supported version, проверить на representative code и обновлять отдельно от feature changes.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

209. (L3, S) Как встроить style automation в редакторы и IDE команды?

     **Ответ:** Настроить путь к pinned executable и общий config; дать простой bootstrap, не оставлять каждому IDE default.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

210. (L3, S) Как отделять объективные formatting rules от спорных style preferences?

     **Ответ:** Фиксировать только поддерживаемые однозначные rules; disputed preferences решать как изменение конфигурации, не в каждом PR.

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)

214. (L4, S) Как связать formatter policy с code review culture?

215. (L4, S) Как избежать превращения formatting automation в бюрократический ритуал?

     **Источник:** [ClangFormat](https://clang.llvm.org/docs/ClangFormat.html)


### Static Analysis

## L1

216. (L1, T) Что такое static analysis?

     **Ответ:** Анализ кода без исполнения целевой программы с использованием syntax, types, control/data-flow models.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

217. (L1, T) Чем static analysis отличается от компиляции и тестов?

     **Ответ:** Compilation обеспечивает построение программы и diagnostics, tests проверяют executions, static analysis исследует возможные пути моделями.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

218. (L1, T) Какие типы ошибок может находить static analyzer?

     **Ответ:** Null dereference, use-after-free, leaks, uninitialized values и API misuse в пределах моделей инструмента.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

219. (L1, T) Почему тесты не заменяют static analysis?

     **Ответ:** Tests покрывают лишь выбранные inputs/interleavings; analyzer может обнаружить paths, которые не были исполнены.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

220. (L1, P) Какие static analysis tools применимы к C/C++?

     **Ответ:** Clang Static Analyzer, clang-tidy, GCC analyzer и Cppcheck; выбирать по нужным defect classes и поддерживаемой среде.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)


## L2

221. (L2, T) Чем static analysis отличается от linting?

     **Ответ:** Lint часто проверяет локальные patterns/style, static analysis может моделировать control/data flow; граница терминов размыта.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

222. (L2, D) Почему static analysis может находить баги в редко исполняемом коде?

     **Ответ:** Исследует модели путей, не требуя фактического запуска каждого branch.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

223. (L2, D) Почему false positives — центральная проблема анализа?

     **Ответ:** Неисполняемые paths и неполные models дают ложные findings; шум снижает доверие и отнимает время review.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

224. (L2, T) Какие классы дефектов особенно важны для C/C++?

     **Ответ:** Memory lifetime, bounds, initialization, integer errors, concurrency и unsafe API use; инструменты покрывают их неодинаково.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

225. (L2, P) Как встроить static analysis в CI pipeline?

     **Ответ:** Собрать актуальные compile commands/generated inputs, запустить versioned analyzer и сохранить отчёт с выбранной gate policy.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

226. (L2, D) Почему полный анализ на каждом commit может быть слишком дорогим?

     **Ответ:** Межпроцедурный анализ и полный набор configurations требуют значительных CPU/RAM; полезность и coverage надо измерять.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

227. (L2, S) Как разделять quick checks и deep analysis?

     **Ответ:** PR — high-signal/diff-focused checks, nightly — broad deep analysis; не терять owner и сроки для scheduled findings.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

228. (L2, D) Почему static analysis tool без доверия команды быстро перестает использоваться?

     **Ответ:** Когда finding часто неверен или нерепродуцируем, его перестают проверять; нужны настройка и быстрая обратная связь.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

229. (L2, T) Как quality findings должны попадать в инженерный workflow?

     **Ответ:** Каждый actionable finding получает owner, severity, reproducer и решение fix/suppress с причиной.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

230. (L2, D) Когда warning должен блокировать merge, а когда нет?

     **Ответ:** Новый подтверждаемый high-impact defect блокирует; noise/legacy требуют triage, а исключения — владельца и срока.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

233. (L3, P) Как использовать baseline, diff-only analysis и suppression policy?

     **Ответ:** Baseline фиксирует долг, diff scope ограничивает review, suppressions документируют конкретные исключения; не скрывать root-cause spread.

234. (L3, D) Как triage'ить важность findings: correctness, security, maintainability?

     **Ответ:** Оценивать достижимость, impact и вероятность, а не только category; security labels не заменяют техническую проверку.

235. (L3, S) Как увязать static analysis, sanitizer builds и tests в единую quality модель?

     **Ответ:** Static analysis исследует модели, sanitizers — реальные executions с instrumentation, tests задают inputs и expected behavior.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

236. (L3, D) Почему результаты анализа меняются при изменении compile flags/config?

     **Ответ:** Меняются включённые branches, types, macros и target ABI; вывод относится к конкретной конфигурации.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

237. (L3, S) Как измерять signal-to-noise ratio у анализатора?

     **Ответ:** Доля actionable/confirmed findings, false-positive rate и время triage; отдельно учитывать missed defects из incident history.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

238. (L3, D) Как расследовать “мы исправили warning, а баг остался”?

     **Ответ:** Проверить root cause и coverage: устранение syntax pattern могло убрать warning, сохранив нарушенный invariant.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

239. (L3, S) Как построить процесс ownership для suppressions и accepted risks?

     **Ответ:** Каждое исключение имеет scope, owner, rationale и review date; изменение surrounding code может потребовать повторной оценки.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

240. (L3, S) Когда static analysis должен быть частью release criteria?

     **Ответ:** Когда анализ покрывает существенные risks supported configurations, стабилен и имеет заранее определённые criteria/exception policy.

     **Источник:** [Clang Static Analyzer](https://clang.llvm.org/docs/ClangStaticAnalyzer.html); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

## 10. Practical / Real-world Scenarios

## L2

246. (L2, D) Локально проект собирается, а в CI падает на этапе configure/build. Какие типовые причины проверишь?

     **Ответ:** Toolchain/dependency versions, CMake cache, generated files, flags, paths/case sensitivity и доступ к package registry.

     **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

247. (L2, D) Тесты нестабильны только в CI. Какие первые гипотезы?

     **Ответ:** CPU pressure, races, sleeps/timeouts, test order, shared resources и network; сохранить seed и runtime environment.

     **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

248. (L2, D) Pipeline стал вдвое медленнее после добавления quality checks. Как разбирать?

     **Ответ:** Разбить duration по checks, setup и очереди; устранить повторные parses/builds, parallelize и перенести действительно дорогие checks в schedule.

     **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

249. (L2, D) После включения cache сборка ускорилась, но иногда появляются “странные” ошибки. Какие причины?

     **Ответ:** Неполные keys, смешанные configs, stale build tree и untrusted cache writes; сравнить clean run и hashes.

     **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

250. (L2, D) clang-format/clang-tidy падают только на runner'е, а локально нет. Что проверять?

     **Ответ:** Executable version, config discovery, working directory, compile commands и generated includes; воспроизвести точную CI command.

     **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)


## L3

251. (L3, D) После обновления compiler image часть pipeline'ов стала красной. Как строить расследование?

     **Ответ:** Зафиксировать old/new digests и diagnostics, проверить минимальный reproducer; разделить реальные defects и toolchain/config regression.

     **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

252. (L3, D) GitHub Actions/GitLab CI/Jenkins дают разные результаты на одном и том же проекте. Какие категории причин рассмотрешь?

     **Ответ:** Различия source checkout/submodules, image, shell/env, permissions, dependency resolution, parallelism и artifacts.

     **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

253. (L3, D) Из-за большого числа legacy warning'ов команда игнорирует новые quality findings. Как исправлять процесс?

     **Ответ:** Зафиксировать baseline, показывать отдельно новые findings, назначить legacy owners и включить проверенные high-signal gates.

     **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

254. (L3, D) Build artifacts из одного stage переиспользуются дальше, но иногда тесты проходят на “не тех” бинарях. Что проверять?

     **Ответ:** Artifact run/commit identity, names, download scope, stale paths и implicit rebuild; сравнить hashes реально запущенных binaries.

     **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

255. (L3, D) CI green, но production defect rate не снижается. Какие изъяны в quality automation возможны?

     **Ответ:** Слабый workload coverage, отсутствующие integration/failure tests, ignored reports и gates, не соответствующие реальным defect classes.

     **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)


## L4

256. (L4, S) Как спроектировать CI/CD и automation strategy для C/C++ организации с несколькими командами и разными репозиториями?

     **Ответ:** Общая platform contract, managed toolchains/templates и artifact identity, а продуктовые gates определяются рисками и поддерживаемыми targets.

     **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

257. (L4, S) Какие проверки должны быть обязательными на PR, какие — nightly, а какие — release-only?

     **Ответ:** PR — быстрые correctness/build gates; nightly — stress/full matrix/deep analysis; release — exact artifact и compatibility validation.

     **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

258. (L4, S) Как уменьшить стоимость и время pipeline без потери инженерной строгости?

     **Ответ:** Оптимизировать critical path, caching и redundant work, сохраняя проверяемые inputs и coverage; измерять эффект и clean-build reliability.

     **Источник:** [GitHub Actions documentation](https://docs.github.com/en/actions); [Clang-Tidy](https://clang.llvm.org/extra/clang-tidy/)

259. (L4, S) Как формализовать ownership за CI templates, runners, quality rules и suppressions?

     **Ответ:** Назначить platform owners для runners/templates и product owners для rules/findings; исключения документировать и пересматривать.

260. (L4, S) Как выстроить культуру, где CI/CD — это инструмент доказательного качества, а не просто “красно-зеленая лампочка”?

     **Ответ:** Сохранять reproducible evidence, исправлять recurring failure causes и связывать checks с defect history/SLO, а не только pass rate.
