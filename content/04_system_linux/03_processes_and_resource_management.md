## Processes & Resource Management — Questions (C/C++ oriented)

## Process Lifecycle

1. Что такое процесс в Linux?

   **Ответ:** Процесс — это выполняющийся экземпляр программы, которому операционная система выделила изолированное адресное пространство в оперативной памяти, процессорное время, дескрипторы ресурсов и метаданные управления.

   **Пример:**

   ```bash
   ps -ef | grep my_app

   ```

   **Типичная ошибка:** Путать процесс и исполняемый файл (бинарник на диске). Один и тот же файл на диске может быть запущен одновременно в виде десятков независимых процессов.

   **Источник:** [man7: pid_namespaces(7)](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html)

2. Чем процесс отличается от программы?

   **Ответ:** Программа — это пассивный набор машинных инструкций и статических данных, хранящийся на постоянном носителе (диске). Процесс — это динамическая сущность: выполняющаяся программа со счетчиком команд (`PC`), регистрами процессора, стеком, кучей и открытыми дескрипторами.
   **Пример:**
   ```bash
   # Программа на диске:
   ls -l /bin/ls

   # Процесс в момент работы:
   /bin/ls &

   ```

   **Типичная ошибка:** Считать, что состояние процесса сохраняется в исполняемом ELF-файле при завершении.
   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

3. Какие основные состояния процесса существуют?

   **Ответ:** В ядре Linux выделяют: выполняемый/готовый к выполнению (`TASK_RUNNING`), прерываемый сон (`TASK_INTERRUPTIBLE`), непрерываемый сон (`TASK_UNINTERRUPTIBLE`), остановленный (`TASK_STOPPED`), трассируемый (`TASK_TRACED`) и завершившийся/зомби (`EXIT_ZOMBIE`, `EXIT_DEAD`).
   **Пример:**
   ```bash
   # Колонка STAT: R, S, D, T, Z
   ps aux

   ```

   **Типичная ошибка:** Полагать, что состояние "Running" означает только то, что процесс прямо сейчас физически исполняется на ядре CPU. В `TASK_RUNNING` входят и те процессы, которые просто стоят в очереди планировщика (`runqueue`).
   **Источник:** [man7: ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)

4. Что означает состояние running?

   **Ответ:** Процесс либо физически выполняет инструкции на ядре процессора в данный момент, либо находится в очереди планировщика (`runqueue`) и ждет выделения кванта процессорного времени. В `ps` обозначается символом `R`.
   **Пример:**
   ```cpp
   // Нагружает ядро CPU, переводя поток в TASK_RUNNING
   int main() {
       while (true) {}
       return 0;
   }

   ```

   **Типичная ошибка:** Думать, что если процесс в состоянии `R`, он не может быть прерван планировщиком ОС.
   **Источник:** [man7: sched(7)](https://man7.org/linux/man-pages/man7/sched.7.html)

5. Что означает состояние sleeping?

   **Ответ:** Процесс приостановил выполнение, освободил ядро CPU и ожидает наступления некоторого события: таймера, ввода/вывода (диск, сеть) или освобождения примитива синхронизации (mutex). Бывает прерываемым (`S`) и непрерываемым (`D`).
   **Пример:**
   ```cpp
   #include <unistd.h>

   int main() {
       sleep(10); // Процесс переходит в состояние ожидания таймера
       return 0;
   }

   ```

   **Типичная ошибка:** Использовать активный пустой цикл (`busy-waiting`) вместо перевода процесса в спящий режим через системные вызовы ожидания.
   **Источник:** [man7: nanosleep(2)](https://man7.org/linux/man-pages/man2/nanosleep.2.html)

6. Что означает состояние interruptible sleep?

   **Ответ:** Процесс заблокирован в ожидании ресурса или события (`TASK_INTERRUPTIBLE`, в выводе `ps` флаг `S`), но может быть немедленно разбужен поступлением асинхронного сигнала (например, `SIGINT` или `SIGTERM`).
   **Пример:**
   ```bash
   # Процесс ждет ввода из терминала, его можно прервать по Ctrl+C
   cat

   ```

   **Типичная ошибка:** Забывать проверять системные вызовы на возврат ошибки `EINTR`, которая возникает, когда вызов прерван сигналом во время прерываемого сна.
   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

7. Что означает состояние uninterruptible sleep?

   **Ответ:** Процесс заблокирован в ядре (`TASK_UNINTERRUPTIBLE`, флаг `D`), обычно в ожидании быстрого прямого ответа от аппаратного устройства (жесткий диск, NFS). Процесс в этом состоянии не обрабатывает сигналы и не может быть убит даже сигналом `SIGKILL` (`kill -9`).
   **Пример:**
   ```bash
   # Просмотр процессов в D-state
   ps aux | awk '$8 ~ /D/'

   ```

   **Типичная ошибка:** Пытаться завершить зависший в `D`-состоянии процесс (например, при отвале NFS-диска) командой `kill -9`. Поможет только перезагрузка или восстановление работы дискового драйвера.
   **Источник:** [man7: ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)

8. Что означает состояние stopped?

   **Ответ:** Выполнение процесса приостановлено сигналом остановки (`SIGSTOP`, `SIGTSTP`, `SIGTTIN` или `SIGTTOU`) либо отладчиком. Процесс не потребляет CPU и возобновляет работу только по сигналу `SIGCONT`. В `ps` обозначается буквой `T`.
   **Пример:**
   ```bash
   kill -STOP <PID> # перевести в stopped
   kill -CONT <PID> # продолжить исполнение

   ```

   **Типичная ошибка:** Полагать, что процесс в состоянии `T` освободил занятую оперативную память. Память остается выделенной.
   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

9. Что означает состояние zombie?

   **Ответ:** Процесс завершил выполнение своего кода (через `exit()`), освободил память, дескрипторы и почти все структуры, но его запись в таблице процессов ядра сохраняется, пока родительский процесс не прочитает его код возврата через `wait()`/`waitpid()`. В `ps` обозначается `Z` или `<defunct>`.
   **Пример:**
   ```bash
   ps aux | grep 'Z'

   ```

   **Типичная ошибка:** Пытаться убить зомби с помощью `kill -9 <PID>`. Зомби уже мертв; чтобы убрать его из таблицы, нужно заставить родителя вызвать `wait()` или убить родителя.
   **Источник:** [man7: wait(2)](https://man7.org/linux/man-pages/man2/wait.2.html)

10. Что означает состояние dead/terminated?

   **Ответ:** Финальная фаза уничтожения процесса (`EXIT_DEAD`). После того как родитель прочитал статус завершения, ядро полностью удаляет запись `task_struct` из памяти. Это состояние транзитное и практически никогда не фиксируется утилитами вроде `ps`.
   **Пример:**
   ```text
   TASK_RUNNING -> do_exit() -> EXIT_ZOMBIE -> release_task() -> EXIT_DEAD

   ```

   **Типичная ошибка:** Искать процессы в состоянии `DEAD` через системный монитор.
   **Источник:** [man7: exit(2)](https://man7.org/linux/man-pages/man2/exit.2.html)

11. Как процесс создается в Linux?

   **Ответ:** Новый процесс создается системным вызовом `fork()` (или `clone()`), который дублирует текущий процесс. После этого дочерний процесс обычно вызывает одно из семейств системных вызовов `execve()`, чтобы загрузить и запустить новый исполняемый файл.
   **Пример:**
   ```cpp
   #include <unistd.h>

   pid_t pid = fork();
   if (pid == 0) {
       char* args[] = {(char*)"/bin/ls", nullptr};
       execv(args[0], args);
   }

   ```

   **Типичная ошибка:** Полагать, что запуск программы в Linux выполняется одной неделимой атомарной операцией без создания промежуточной ветки.
   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

12. Какой первый пользовательский процесс запускается системой?

   **Ответ:** Процесс инициализации `init` (в современных дистрибутивах — `systemd`), который всегда имеет идентификатор `PID = 1`. Он запускается ядром при старте ОС и является прямым или косвенным предком всех пользовательских процессов.
   **Пример:**
   ```bash
   ps -p 1 -o comm=
   # Выведет: systemd или init

   ```

   **Типичная ошибка:** Считать, что `PID 1` можно принудительно завершить сигналом `kill -9 1` изнутри обычной системы (ядро игнорирует сигналы к `PID 1`, которые привели бы к его падению).
   **Источник:** [man7: systemd(1)](https://man7.org/linux/man-pages/man1/systemd.1.html)

13. Что такое PID?

   **Ответ:** Process ID — уникальный положительный целочисленный идентификатор процесса в пределах текущего пространства имен процессов (`PID namespace`), используемый ядром и пользователем для адресации сигналов и мониторинга.
   **Пример:**
   ```cpp
   #include <unistd.h>
   #include <iostream>

   int main() {
       std::cout << "My PID: " << getpid() << '\n';
       return 0;
   }

   ```

   **Типичная ошибка:** Предполагать, что PID уникален навсегда. Ядро повторно использует PID освободившихся процессов по кругу по достижении лимита `/proc/sys/kernel/pid_max`.
   **Источник:** [man7: getpid(2)](https://man7.org/linux/man-pages/man2/getpid.2.html)

14. Что такое PPID?

   **Ответ:** Parent Process ID — идентификатор родительского процесса, который инициировал создание текущего процесса вызовом `fork()`.
   **Пример:**
   ```cpp
   #include <unistd.h>
   #include <iostream>

   int main() {
       std::cout << "Parent PID: " << getppid() << '\n';
       return 0;
   }

   ```

   **Типичная ошибка:** Рассчитывать, что PPID остается неизменным на протяжении всей жизни процесса. Если родитель умирает раньше дочернего процесса, PPID меняется на PID процесса-усыновителя (например, `1` или subreaper).
   **Источник:** [man7: getppid(2)](https://man7.org/linux/man-pages/man2/getppid.2.html)

15. Как процесс связан с родительским процессом?

   **Ответ:** Процессы формируют иерархическое дерево (`process tree`). Родитель отслеживает завершение дочернего процесса и забирает его код выхода через `waitpid()`. Если родитель завершается раньше, дочерний процесс "сиротеет" и перепривязывается к ближайшему процессу-субреаперу или `init`.
   **Пример:**
   ```bash
   pstree -p

   ```

   **Типичная ошибка:** Считать, что завершение родительского процесса автоматически безусловно убивает всех его потомков. По умолчанию они продолжают выполняться в фоне.
   **Источник:** [man7: pstree(1)](https://man7.org/linux/man-pages/man1/pstree.1.html)

16. Что хранится в PCB / task_struct?

   **Ответ:** В структуре ядра `task_struct` (Process Control Block) хранятся: PID/TGID, статус процесса, приоритет планировщика, указатели на страницы виртуальной памяти (`mm_struct`), таблица открытых файлов (`files_struct`), таблица обработчиков сигналов (`sighand_struct`), учетные данные пользователя (`cred`: UID, GID) и статистика CPU.
   **Пример:**
   ```bash
   # Частичное отображение информации из task_struct в пользовательском пространстве:
   cat /proc/self/status

   ```

   **Типичная ошибка:** Полагать, что `task_struct` находится в адресном пространстве самого пользовательского процесса. Она хранится исключительно в защищенной памяти ядра.
   **Источник:** [kernel.org: struct task_struct](https://www.google.com/search?q=https://elixir.bootlin.com/linux/latest/source/include/linux/sched.h&utm_source=gemini)

17. Что получает новый процесс при создании?

   **Ответ:** Новый процесс получает собственный уникальный PID, собственную копию таблицы дескрипторов (ссылающихся на те же открытые файловые описания), изолированное виртуальное адресное пространство (через Copy-on-Write) и независимый контекст выполнения регистров процессора.
   **Пример:**
   ```cpp
   #include <unistd.h>
   #include <iostream>

   int main() {
       int x = 42;
       if (fork() == 0) {
           x = 100; // Изменяет x только в изолированной памяти дочернего процесса
           _exit(0);
       }
       return 0;
   }

   ```

   **Типичная ошибка:** Думать, что дочерний процесс получает полностью общую оперативную память с родителем как в случае потоков (`threads`).
   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

18. Какие ресурсы наследуются дочерним процессом?

   **Ответ:** Дочерний процесс наследует открытые файловые дескрипторы, переменные окружения, текущую рабочую директорию, umask, лимиты ресурсов (`rlimit`), маску сигналов и привязку к CPU (`CPU affinity`). Не наследуются: блокировки файлов (`fcntl record locks`), ожидающие сигналы (`pending signals`) и таймеры (`timer_create`).
   **Пример:**
   ```cpp
   #include <unistd.h>
   #include <fcntl.h>

   int fd = open("log.txt", O_WRONLY | O_CREAT, 0644);
   if (fork() == 0) {
       // fd открыт и валиден здесь
       write(fd, "child\n", 6);
       _exit(0);
   }

   ```

   **Типичная ошибка:** Думать, что блокировки файлов `fcntl` автоматически распространяются на потомка.
   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

19. Что происходит с адресным пространством процесса при завершении?

   **Ответ:** Все страницы виртуальной памяти (стек, куча, отображенные файлы через `mmap`, сегменты данных и BSS) немедленно освобождаются ядром ОС, а соответствующие физические фреймы памяти возвращаются в общий пул доступной памяти системы.
   **Пример:**
   ```cpp
   int main() {
       int* ptr = new int[1000000];
       // При завершении main память освободится ядром даже без delete[]
       return 0;
   }

   ```

   **Типичная ошибка:** Считать, что утечка памяти процесса на куче (`malloc`/`new`) продолжает висеть в ОЗУ после полного завершения процесса ОС.
   **Источник:** [man7: exit(2)](https://man7.org/linux/man-pages/man2/exit.2.html)

20. Что происходит с файловыми дескрипторами при завершении процесса?

   **Ответ:** Ядро автоматически закрывает все открытые файловые дескрипторы процесса (эквивалентно вызову `close()` для каждого FD). Для файлов счетчик ссылок уменьшается; если он стал равен 0, ресурсы освобождаются. Сетевые TCP-сокеты инициируют процедуру закрытия соединения (отправка `FIN`).
   **Пример:**
   ```cpp
   #include <fcntl.h>
   #include <unistd.h>

   int main() {
       int fd = open("test.txt", O_RDONLY);
       // fd будет автоматически закрыт ядром при выходе
       return 0;
   }

   ```

   **Типичная ошибка:** Полагаться на автоматическое закрытие дескрипторов ядром в долгоживущих демонах и серверах, приводя к исчерпанию лимита дескрипторов (`EMFILE`).
   **Источник:** [man7: close(2)](https://man7.org/linux/man-pages/man2/close.2.html)

21. Как процесс завершает работу?

   **Ответ:** Процесс завершается добровольно через системные вызовы `exit()` или `_exit()` (явный вызов или возврат из функции `main`), либо принудительно при получении неперехваченного терминирующего сигнала (например, `SIGSEGV`, `SIGKILL`, `SIGTERM`).
   **Пример:**
   ```cpp
   #include <cstdlib>

   int main() {
       std::exit(0); // Нормальное завершение процесса
   }

   ```

   **Типичная ошибка:** Использовать вызов `abort()` для штатного завершения (он приводит к аварийной генерации `SIGABRT` и core dump).
   **Источник:** [man7: exit(3)](https://man7.org/linux/man-pages/man3/exit.3.html)

22. В чем разница между exit() и _exit()?

   **Ответ:** `exit()` — функция библиотеки C (`libc`), которая сбрасывает и закрывает буферы ввода/вывода потоков C (`fflush(stdout)`), вызывает зарегистрированные через `atexit()` функции и деструкторы статических объектов. `_exit()` (или `_Exit()`) — прямой системный вызов ядра, завершающий процесс немедленно без вызова пользовательских коллбэков и сброса буферов `stdio`.
   **Пример:**
   ```cpp
   #include <unistd.h>

   void child() {
       // В дочернем процессе после fork() безопаснее вызывать _exit,
       // чтобы случайно не сбросить повторно буферы родителя
       _exit(0);
   }

   ```

   **Типичная ошибка:** Использовать `exit()` внутри дочернего процесса после неудавшегося `execve()`, что может дважды закрыть или сбросить общие буферы `FILE*` родителя.
   **Источник:** [man7: _exit(2)](https://man7.org/linux/man-pages/man2/_exit.2.html)

23. Что такое код завершения процесса?

   **Ответ:** Это целочисленное значение (младшие 8 бит, диапазон 0–255), передаваемое процессу-родителю через вызовы семейства `wait()`. Код `0` традиционно означает успешное выполнение, ненулевые значения — ошибки.
   **Пример:**
   ```cpp
   int main() {
       return 42; // Код завершения 42
   }

   ```

   **Типичная ошибка:** Возвращать отрицательные значения (например, `-1`). В shell код превратится в беззнаковый байт: `-1 & 0xFF = 255`.
   **Источник:** [man7: exit(3)](https://man7.org/linux/man-pages/man3/exit.3.html)

24. Как родитель получает статус завершения дочернего процесса?

   **Ответ:** Через системные вызовы `wait()` или `waitpid()`. Статус возвращается в целочисленную переменную, которую затем разбирают макросами `WIFEXITED`, `WEXITSTATUS`, `WIFSIGNALED`, `WTERMSIG`.
   **Пример:**
   ```cpp
   #include <sys/wait.h>
   #include <unistd.h>
   #include <iostream>

   int main() {
       if (fork() == 0) _exit(7);
       int status = 0;
       wait(&status);
       if (WIFEXITED(status)) {
           std::cout << "Exit code: " << WEXITSTATUS(status) << '\n'; // 7
       }
       return 0;
   }

   ```

   **Типичная ошибка:** Напрямую читать переменную `status` без использования макросов `WEXITSTATUS()` (переменная содержит битовую маску сигналов и флагов).
   **Источник:** [man7: wait(2)](https://man7.org/linux/man-pages/man2/wait.2.html)

25. Что такое wait()?

   **Ответ:** Системный вызов `pid_t wait(int *status)`, блокирующий выполнение вызывающего потока до тех пор, пока любой из его дочерних процессов не завершит выполнение или не получит терминирующий сигнал.
   **Пример:**
   ```cpp
   #include <sys/wait.h>
   #include <unistd.h>

   int main() {
       if (fork() == 0) _exit(0);
       int status;
       pid_t child_pid = wait(&status); // ждет любого ребенка
       return 0;
   }

   ```

   **Типичная ошибка:** Вызывать `wait()` в цикле без проверки возврата `-1` с `errno == ECHILD` (когда дочерних процессов больше не осталось).
   **Источник:** [man7: wait(2)](https://man7.org/linux/man-pages/man2/wait.2.html)

26. Что такое waitpid()?

   **Ответ:** Расширенная версия вызова `wait()`, позволяющая ожидать конкретный процесс по PID (или группу процессов) и поддерживающая флаг `WNOHANG` для неблокирующей проверки состояния.
   **Пример:**
   ```cpp
   #include <sys/wait.h>
   #include <unistd.h>

   int status;
   pid_t pid = fork();
   if (pid > 0) {
       // Неблокирующий опрос
       pid_t result = waitpid(pid, &status, WNOHANG);
   }

   ```

   **Типичная ошибка:** Использовать блокирующий `waitpid(pid, &status, 0)` в цикле обработки событий (event loop), замораживая весь поток.
   **Источник:** [man7: waitpid(2)](https://man7.org/linux/man-pages/man2/waitpid.2.html)

27. Что такое zombie process?

   **Ответ:** Процесс, который завершил работу, освободил свои вычислительные ресурсы, но запись о котором сохраняется в таблице процессов ядра до тех пор, пока родитель не заберет его статус завершения через `wait()`.
   **Пример:**
   ```cpp
   #include <unistd.h>

   int main() {
       if (fork() == 0) {
           _exit(0); // Стал зомби, так как родитель спит и не вызывает wait
       }
       sleep(60);
       return 0;
   }

   ```

   **Типичная ошибка:** Полагать, что процесс-зомби расходует процессорное время или оперативную память. Он занимает только запись в таблице PID.
   **Источник:** [man7: wait(2)](https://man7.org/linux/man-pages/man2/wait.2.html)

28. Почему zombie не освобождается полностью сразу?

   **Ответ:** Ядро сохраняет запись, чтобы родительский процесс мог гарантированно узнать, завершился ли его дочерний процесс, с каким кодом выхода или по какому сигналу он погиб.
   **Пример:**
   ```bash
   # Поле exitcode хранится в структуре ядра до вызова wait
   cat /proc/<zombie_pid>/status | grep State

   ```

   **Типичная ошибка:** Рассматривать состояние зомби как системную ошибку или сбой ядра — это штатный механизм синхронизации завершения процессов.
   **Источник:** [man7: wait(2)](https://man7.org/linux/man-pages/man2/wait.2.html)

29. Как появляются zombie-процессы?

   **Ответ:** Зомби возникают, когда дочерний процесс завершается, а родительский процесс продолжает длительно работать и не вызывает функции семейства `wait()`/`waitpid()` и не обрабатывает сигнал `SIGCHLD`.
   **Пример:**
   ```cpp
   #include <unistd.h>

   int main() {
       for (int i = 0; i < 5; ++i) {
           if (fork() == 0) _exit(0); // плодит 5 зомби
       }
       while (true) sleep(1); // родитель никогда не делает wait
   }

   ```

   **Типичная ошибка:** Забывать вызывать `waitpid()` в цикле внутри обработчика сигнала `SIGCHLD`.
   **Источник:** [man7: sigaction(2)](https://man7.org/linux/man-pages/man2/sigaction.2.html)

30. Как избежать накопления zombie-процессов?

   **Ответ:** 1) Обрабатывать сигнал `SIGCHLD` и вызывать внутри обработчика `waitpid(-1, &st, WNOHANG)` в цикле. 2) Установить обработчик `SIGCHLD` в `SIG_IGN` (или выставить флаг `SA_NOCLDWAIT`), что заставляет ядро автоматически утилизировать процессы без образования зомби. 3) Делать двойной fork (`double fork`).
   **Пример:**
   ```cpp
   #include <csignal>

   int main() {
       // Указывает ядру автоматически собирать дочерние процессы
       struct sigaction sa;
       sa.sa_handler = SIG_IGN;
       sa.sa_flags = SA_NOCLDWAIT;
       sigemptyset(&sa.sa_mask);
       sigaction(SIGCHLD, &sa, nullptr);
       return 0;
   }

   ```

   **Типичная ошибка:** Вызывать `waitpid()` в обработчике `SIGCHLD` ровно один раз без цикла `while`. Так как сигналы Linux объединяются (`coalescing`), несколько одновременно завершившихся детей приведут к генерации только одного сигнала.
   **Источник:** [man7: sigaction(2)](https://man7.org/linux/man-pages/man2/sigaction.2.html)

31. Что такое orphan process?

   **Ответ:** Процесс-сирота — это процесс, чей родительский процесс завершил свое выполнение раньше, чем сам этот процесс.
   **Пример:**
   ```cpp
   #include <unistd.h>

   int main() {
       if (fork() > 0) {
           _exit(0); // Родитель немедленно умирает
       }
       sleep(30); // Потомок стал orphan
       return 0;
   }

   ```

   **Типичная ошибка:** Путать orphan-процессы и zombie-процессы. Сирота активно исполняется в системе, а зомби уже завершил выполнение.
   **Источник:** [man7: prctl(2)](https://man7.org/linux/man-pages/man2/prctl.2.html)

32. Что происходит с orphan-процессом?

   **Ответ:** Процесс не прекращает свою работу. Ядро операционной системы автоматически переназначает его родителем другой процесс (процедура "усыновления" / `reparenting`), который берет на себя вызов `wait()` после его завершения.
   **Пример:**
   ```bash
   # После смерти родителя PPID станет 1 или PID менеджера сессий
   ps -o pid,ppid,comm -p <child_pid>

   ```

   **Типичная ошибка:** Считать, что осиротевший процесс автоматически превратится в зомби навсегда. Новый родитель вызовет `wait()`.
   **Источник:** [man7: prctl(2)](https://man7.org/linux/man-pages/man2/prctl.2.html)

33. Кто “усыновляет” orphan-процесс?

   **Ответ:** Традиционно orphan-процесс усыновляет корневой процесс инициализации (`init` / `systemd`, `PID 1`). В современном Linux процесс также может быть усыновлен ближайшим предком, который зарегистрировал себя как `subreaper` с помощью `prctl(PR_SET_CHILD_SUBREAPER, 1)`.
   **Пример:**
   ```cpp
   #include <sys/prctl.h>

   // Назначить текущий процесс "субреапером" для всех своих потомков
   prctl(PR_SET_CHILD_SUBREAPER, 1, 0, 0, 0);

   ```

   **Типичная ошибка:** Полагать, что усыновителем всегда безусловно является только `PID 1`. В контейнерах и под управлением менеджеров процессов усыновителем часто выступает локальный supervisor.
   **Источник:** [man7: prctl(2)](https://man7.org/linux/man-pages/man2/prctl.2.html)

34. Что такое session leader?

   **Ответ:** Процесс, создавший новую сессию вызовом `setsid()`, чей PID совпадает с Session ID (SID). Лидер сессии управляет привязкой к управляющему терминалу (`controlling terminal`).
   **Пример:**
   ```cpp
   #include <unistd.h>

   pid_t sid = setsid(); // Процесс становится лидером новой сессии

   ```

   **Типичная ошибка:** Вызывать `setsid()` из процесса, который уже является лидером группы процессов (вызов вернет ошибку `EPERM`). Перед `setsid()` необходим вызов `fork()`.
   **Источник:** [man7: setsid(2)](https://man7.org/linux/man-pages/man2/setsid.2.html)

35. Что такое process group?

   **Ответ:** Коллекция из одного или нескольких процессов (обычно объединенных конвейером пайпов), имеющая общий PGID (Process Group ID). Группы позволяют направлять сигналы (например, по нажатию `Ctrl+C`) одновременно всем процессам в конвейере.
   **Пример:**
   ```bash
   # cat и grep попадают в одну группу процессов
   cat large.log | grep "ERROR"

   ```

   **Типичная ошибка:** Полагать, что сигнал из терминала посылается только первому процессу конвейера. Он транслируется ядром всей foreground process group.
   **Источник:** [man7: setpgid(2)](https://man7.org/linux/man-pages/man2/setpgid.2.html)

36. Что такое foreground process?

   **Ответ:** Процесс (или группа процессов), имеющий прямой доступ к управляющему терминалу для чтения ввода (`stdin`) и вывода. Терминал направляет клавиатурные сигналы прерывания (`SIGINT`, `SIGTSTP`) только активной foreground-группе.
   **Пример:**
   ```bash
   # Запуск в foreground режиме — блокирует ввод в shell
   sleep 10

   ```

   **Типичная ошибка:** Попытка запустить фоновый процесс, требующий интерактивного ввода от пользователя, без перевода в foreground (процесс получит сигнал `SIGTTIN` и остановится).
   **Источник:** [man7: tcsetpgrp(3)](https://man7.org/linux/man-pages/man3/tcsetpgrp.3.html)

37. Что такое background process?

   **Ответ:** Процесс, выполняющийся в фоне без прямого контроля над терминалом. При попытке чтения из `stdin` терминала фоновый процесс останавливается ядром сигналом `SIGTTIN`.
   **Пример:**
   ```bash
   # Запуск команды в background режиме
   ./worker &

   ```

   **Типичная ошибка:** Забывать перенаправлять `stdout`/`stderr` фонового процесса, из-за чего он может засорять вывод интерактивного терминала.
   **Источник:** [man7: tcsetpgrp(3)](https://man7.org/linux/man-pages/man3/tcsetpgrp.3.html)

38. Что происходит с процессом после Ctrl+Z?

   **Ответ:** Драйвер терминала перехватывает комбинацию клавиш и посылает сигнал `SIGTSTP` текущей группе процессов переднего плана. Процесс приостанавливает выполнение и переходит в состояние `TASK_STOPPED` (`T`).
   **Пример:**
   ```bash
   # В терминале:
   # [1]+  Stopped                 nano

   ```

   **Типичная ошибка:** Думать, что по `Ctrl+Z` процесс завершился. Он просто заморожен в памяти и возобновляется командой `fg` или `bg`.
   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

39. Что такое job control в shell?

   **Ответ:** Механизм командного интерпретатора, позволяющий пользователю переключать выполнение программ между передним планом (`fg`) и фоновым режимом (`bg`), просматривать список заданий (`jobs`) и приостанавливать/возобновлять их работу.
   **Пример:**
   ```bash
   jobs -l
   bg %1
   fg %1

   ```

   **Типичная ошибка:** Путать концепцию Shell Job (сущность оболочки) и Process Group ОС (структура ядра). Shell управляет группами процессов под видом своих Jobs.
   **Источник:** [man7: bash(1)](https://man7.org/linux/man-pages/man1/bash.1.html)

40. Чем жизненный цикл процесса важен для C/C++ backend/system developer?

   **Ответ:** Понимание жизненного цикла необходимо для корректного освобождения сетевых сокетов и дескрипторов, предотвращения зомби-процессов, реализации демонизации, graceful shutdown (корректная обработка сигналов `SIGTERM`/`SIGINT`), а также архитектуры мультипроцессных серверов (Master-Worker, как в NGINX или PostgreSQL).
   **Пример:**
   ```cpp
   // Изящная остановка сервера (graceful shutdown)
   volatile std::sig_atomic_t g_stop = 0;
   void handle_sigterm(int) { g_stop = 1; }

   ```

   **Типичная ошибка:** Использовать не реентерабельные функции (такие как `malloc`, `printf`, `std::cout`) внутри обработчиков сигналов ОС.
   **Источник:** [man7: signal-safety(7)](https://man7.org/linux/man-pages/man7/signal-safety.7.html)

## fork()

41. Что делает fork()?

   **Ответ:** Системный вызов `fork()` создает новый процесс (child), который является почти точной копией вызывающего процесса (parent), включая виртуальную память, регистры, открытые дескрипторы и состояние исполнения на момент вызова.
   **Пример:**
   ```cpp
   #include <unistd.h>
   #include <iostream>

   int main() {
       pid_t pid = fork();
       std::cout << "Done\n"; // Вызовется дважды: родителем и потомком
       return 0;
   }

   ```

   **Типичная ошибка:** Полагать, что дочерний процесс начинает выполнение с начала функции `main()`. Он продолжает исполнение строго со следующей инструкции после вызова `fork()`.
   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

42. Что возвращает fork() в родительском процессе?

   **Ответ:** В случае успеха родительскому процессу возвращается положительное число — PID созданного дочернего процесса.
   **Пример:**
   ```cpp
   #include <unistd.h>

   pid_t pid = fork();
   if (pid > 0) {
       // Родительский процесс, pid == ID ребенка
   }

   ```

   **Типичная ошибка:** Забывать сохранять возвращенный PID ребенка в родителе, из-за чего в дальнейшем невозможно выборочно адресовать сигналы и вызывать `waitpid()`.
   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

43. Что возвращает fork() в дочернем процессе?

   **Ответ:** Дочернему процессу вызов `fork()` возвращает целочисленный ноль (`0`).
   **Пример:**
   ```cpp
   #include <unistd.h>

   pid_t pid = fork();
   if (pid == 0) {
       // Дочерний процесс
   }

   ```

   **Типичная ошибка:** Думать, что если `fork()` вернул 0, то PID самого дочернего процесса равен 0. Реальный PID дочернего процесса получается через `getpid()`.
   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

44. Что возвращает fork() при ошибке?

   **Ответ:** Возвращает `-1`, дочерний процесс не создается, а глобальная переменная `errno` устанавливается в код ошибки (обычно `EAGAIN` при исчерпании лимита процессов или `ENOMEM` при нехватке памяти ядра).
   **Пример:**
   ```cpp
   #include <unistd.h>
   #include <cerrno>
   #include <iostream>

   pid_t pid = fork();
   if (pid < 0) {
       std::cerr << "Fork failed, errno: " << errno << '\n';
   }

   ```

   **Типичная ошибка:** Не обрабатывать отрицательный результат `fork()`, продолжая исполнение кода в предположении, что ветвление прошло успешно.
   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

45. Что копируется при fork()?

   **Ответ:** Логически копируется все адресное пространство (память стека, кучи, сегментов данных), таблица дескрипторов файлов, контекст регистров CPU, маска сигналов. На физическом уровне ядро дублирует только структуры управления процессом и таблицы страниц (Page Tables).
   **Пример:**
   ```cpp
   int val = 10;
   if (fork() == 0) {
       val = 20; // Изменение затрагивает только виртуальную память ребенка
   }

   ```

   **Типичная ошибка:** Полагать, что при вызове `fork()` гигабайты кучи мгновенно физически переписываются в новые фреймы ОЗУ.
   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

46. Что не копируется буквально при fork()?

   **Ответ:** Физические страницы памяти не копируются благодаря механизму Copy-on-Write. Также не копируются PID процесса, PPID, отложенные сигналы (`pending signals`), блокировки файлов (`record locks`) и счетчики потребления ресурсов.
   **Пример:**
   ```cpp
   #include <unistd.h>
   #include <cassert>

   pid_t p1 = getpid();
   if (fork() == 0) {
       assert(getpid() != p1); // PID уникален и не скопирован буквально
       _exit(0);
   }

   ```

   **Типичная ошибка:** Ожидать, что таймеры `POSIX timer_create` продолжат тикать в дочернем процессе после `fork()`.
   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

47. Что такое copy-on-write?

   **Ответ:** Copy-on-Write (CoW) — механизм оптимизации виртуальной памяти. При `fork()` ядро не дублирует страницы ОЗУ, а лишь копирует таблицы страниц, помечая все физические фреймы как `read-only` для обоих процессов. Реальное выделение нового фрейма и побайтовое копирование происходят аппаратным прерыванием (`page fault`) только в момент, когда один из процессов пытается записать данные в эту страницу.
   **Пример:**
   ```cpp
   // До записи в память оба процесса читают одни и те же физические фреймы
   std::vector<int> huge_data(10'000'000, 1);
   if (fork() == 0) {
       // До этой строки физического копирования нет:
       huge_data[0] = 42; // Вызывает Page Fault -> ядро создает копию страницы 4КБ
       _exit(0);
   }

   ```

   **Типичная ошибка:** Не учитывать влияние аллокаторов памяти: вызов функций, изменяющих скрытые служебные заголовки блоков на куче (например, даже чтение с модификацией счетчиков), вызывает лавинообразное срабатывание CoW.
   **Источник:** [kernel.org: Memory Management COW](https://docs.kernel.org/admin-guide/mm/index.html)

48. Почему fork() считается относительно дешевым?

   **Ответ:** Благодаря Copy-on-Write: ядру требуется скопировать только записи в таблицах страниц (`page tables`) и инициализировать структуру `task_struct`, избегая дорогостоящего физического дублирования всей выделенной процессу оперативной памяти.
   **Пример:**
   ```bash
   # Время создания процесса измеряется микросекундами даже для программ с гигабайтами памяти
   time ./fork_large_app

   ```

   **Типичная ошибка:** Считать вызов абсолютно бесплатным для процессов с сотнями гигабайт памяти: копирование самих таблиц страниц в таком случае может занять десятки миллисекунд и вызвать просадку latency.
   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

49. Какие file descriptors наследуются после fork()?

   **Ответ:** Дочерний процесс наследует копии абсолютно всех открытых файловых дескрипторов родителя на момент вызова `fork()`. Флаг `FD_CLOEXEC` на наследование дескрипторов при самом `fork()` не влияет (он срабатывает только при последующем вызове `execve`).
   **Пример:**
   ```cpp
   #include <unistd.h>

   int fd = 3;
   if (fork() == 0) {
       // fd 3 здесь открыт и указывает на то же открытое описание файла
   }

   ```

   **Типичная ошибка:** Путать флаг `O_CLOEXEC` / `FD_CLOEXEC` с запретом наследования при `fork()`. Этот флаг закрывает дескрипторы при вызове `exec()`, а не при `fork()`.
   **Источник:** [man7: fcntl(2)](https://man7.org/linux/man-pages/man2/fcntl.2.html)

50. Разделяют ли parent и child смещение файла после fork()?

   **Ответ:** Да. Дескрипторы в родительском и дочернем процессах являются независимыми ссылками на одну и ту же общую запись в системной таблице открытых файлов ядра (`struct file`). По этой причине текущий файловый оффсет (`file offset`) и статус-флаги являются общими.
   **Пример:**
   ```cpp
   #include <unistd.h>
   #include <fcntl.h>

   int fd = open("test.txt", O_RDWR);
   if (fork() == 0) {
       lseek(fd, 10, SEEK_SET); // Сдвигает оффсет и для родителя тоже!
       _exit(0);
   }

   ```

   **Типичная ошибка:** Ожидать, что чтение из одного FD в ребенке не сдвинет позицию чтения для родителя.
   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

51. Наследуются ли переменные окружения после fork()?

   **Ответ:** Да, дочерний процесс получает полную копию окружения (`environ`) родителя через механизм виртуальной памяти CoW.
   **Пример:**
   ```cpp
   #include <unistd.h>
   #include <cstdlib>
   #include <iostream>

   int main() {
       setenv("MY_VAR", "123", 1);
       if (fork() == 0) {
           std::cout << getenv("MY_VAR") << '\n'; // Выведет "123"
           _exit(0);
       }
       return 0;
   }

   ```

   **Типичная ошибка:** Полагать, что модификация переменной через `setenv()` в дочернем процессе изменит значение переменной в родительском процессе.
   **Источник:** [man7: environ(7)](https://man7.org/linux/man-pages/man7/environ.7.html)

52. Наследуется ли текущая рабочая директория после fork()?

   **Ответ:** Да, дочерний процесс наследует текущую рабочую директорию (`CWD`) родительского процесса.
   **Пример:**
   ```cpp
   #include <unistd.h>

   chdir("/tmp");
   if (fork() == 0) {
       // CWD здесь также "/tmp"
       _exit(0);
   }

   ```

   **Типичная ошибка:** Рассчитывать на то, что последующий вызов `chdir()` внутри ребенка повлияет на текущую директорию родительского процесса.
   **Источник:** [man7: chdir(2)](https://man7.org/linux/man-pages/man2/chdir.2.html)

53. Наследуются ли обработчики сигналов после fork()?

   **Ответ:** Да, дочерний процесс полностью наследует таблицу действий по сигналам (`dispositions`: `SIG_DFL`, `SIG_IGN` или пользовательские обработчики), так как адресное пространство дублируется. Не наследуются только таймеры сигналов и очередь отложенных сигналов (`pending signals`).
   **Пример:**
   ```cpp
   #include <csignal>
   #include <unistd.h>

   void my_handler(int) {}

   int main() {
       signal(SIGUSR1, my_handler);
       if (fork() == 0) {
           // my_handler останется назначенным на SIGUSR1
       }
   }

   ```

   **Типичная ошибка:** Путать поведение `fork()` и `execve()`. При вызове `execve()` пользовательские обработчики сбрасываются в `SIG_DFL`, а при `fork()` — сохраняются.
   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

54. Чем fork() полезен при создании worker-процессов?

   **Ответ:** Модель мультипроцессинга обеспечивает максимальную изоляцию сбоев: падение (например, Segfault) или зависание одного воркера не ломает мастер-процесс и соседние воркеры. Мастер может легко перезапустить упавший дочерний процесс.
   **Пример:**
   ```cpp
   // Архитектурная схема серверов NGINX/PostgreSQL
   while (running) {
       pid_t p = fork();
       if (p == 0) { run_worker(); _exit(0); }
       waitpid(p, nullptr, 0); // Перезапуск при падении
   }

   ```

   **Типичная ошибка:** Использовать только многопоточность для ненадежных плагинов: падение потока по ошибке памяти крашит весь процесс целиком.
   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

55. Почему fork() может быть проблемным в multithreaded-программе?

   **Ответ:** В дочернем процессе дублируется только тот поток, который непосредственно вызвал `fork()`. Все остальные потоки внезапно исчезают. Если исчезнувший поток в этот момент удерживал блокировку мьютекса (`pthread_mutex_lock`), этот мьютекс навсегда останется заблокированным в дочернем процессе, что ведет к взаимным блокировкам (Deadlock).
   **Пример:**
   ```cpp
   // Поток 1 захватил std::mutex mtx;
   // Поток 2 делает fork();
   // В дочернем процессе mtx захвачен навсегда несуществующим потоком!

   ```

   **Типичная ошибка:** Использовать многопоточность совместно с `fork()` без немедленного вызова `execve()` в дочернем процессе.
   **Источник:** [man7: pthread_atfork(3)](https://man7.org/linux/man-pages/man3/pthread_atfork.3.html)

56. Что происходит с другими потоками после fork() в многопоточном процессе?

   **Ответ:** Другие потоки родительского процесса просто не переносятся в дочерний процесс. Для дочернего процесса они бесследно исчезают: их деструкторы не вызываются, очистка стека не производится, ресурсы не освобождаются.
   **Пример:**
   ```cpp
   #include <thread>
   #include <unistd.h>

   void worker() { while(true); }

   int main() {
       std::thread t(worker);
       t.detach();
       if (fork() == 0) {
           // В дочернем процессе существует только один главный поток!
           _exit(0);
       }
       return 0;
   }

   ```

   **Типичная ошибка:** Ожидать корректной работы фоновых пулов потоков внутри дочернего процесса без их явной повторной инициализации.
   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

57. Почему после fork() в multithreaded-коде часто рекомендуют сразу вызывать exec()?

   **Ответ:** Вызов семейства `exec()` полностью заменяет разрушенное и потенциально заблокированное состояние адресного пространства программы новым чистым образом бинарника, безопасно сбрасывая все повисшие мьютексы и внутреннее состояние стандартных библиотек. До `exec()` разрешено вызывать только async-signal-safe функции.
   **Пример:**
   ```cpp
   if (fork() == 0) {
       // Минимальные действия без аллокаций:
       execl("/bin/ls", "ls", nullptr);
       _exit(127); // Если exec провалился
   }

   ```

   **Типичная ошибка:** Вызывать сложные методы с захватом локов или аллокацией памяти (например, `malloc`, `new`, `syslog`) между `fork()` и `exec()` в многопоточном приложении.
   **Источник:** [man7: signal-safety(7)](https://man7.org/linux/man-pages/man7/signal-safety.7.html)

58. Какие ошибки может вернуть fork()?

   **Ответ:** 1) `EAGAIN` — достигнут системный лимит на максимальное количество процессов (`RLIMIT_NPROC` или общесистемный `pid_max`). 2) `ENOMEM` — ядру не хватило памяти под структуры `task_struct` или таблицы страниц. 3) `ENOSYS` — `fork()` не поддерживается архитектурой платформы (например, MMU-less системами).
   **Пример:**
   ```cpp
   #include <cerrno>
   #include <unistd.h>

   pid_t p = fork();
   if (p < 0 && errno == EAGAIN) {
       // Превышен лимит потоков/процессов
   }

   ```

   **Типичная ошибка:** Предполагать, что `fork()` может завершиться неудачей только при физическом переполнении оперативной памяти.
   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

59. Что может ограничивать количество fork()?

   **Ответ:** Системный глобальный лимит PID в `/proc/sys/kernel/pid_max`, лимит процессов на пользователя через `ulimit -u` (`RLIMIT_NPROC`), лимиты подсистемы `cgroups pids.max`, а также общий объем физической оперативной памяти и файла подкачки (механизм `vm.overcommit_memory`).
   **Пример:**
   ```bash
   # Проверка лимитов:
   cat /proc/sys/kernel/pid_max
   ulimit -u

   ```

   **Типичная ошибка:** Не настраивать лимит `pids.max` в systemd/cgroups для контейнеров, что делает узел уязвимым к исчерпанию PID всей хост-машины.
   **Источник:** [man7: getrlimit(2)](https://man7.org/linux/man-pages/man2/getrlimit.2.html)

60. Что такое fork bomb?

   **Ответ:** Форма DoS-атаки, при которой процесс бесконечно создает свои копии в геометрической прогрессии через вызов `fork()`, быстро заполняя таблицу процессов ОС и монополизируя время планировщика процессора.
   **Пример:**
   ```bash
   # Классическая bash fork-bomb:
   :(){ :|:& };:

   ```

   **Типичная ошибка:** Запуск непроверенного рекурсивного скрипта без выставленных предварительно защитных ограничений `ulimit -u`.
   **Источник:** [man7: getrlimit(2)](https://man7.org/linux/man-pages/man2/getrlimit.2.html)

61. Почему fork bomb опасен для системы?

   **Ответ:** Лавинообразное создание процессов быстро исчерпывает таблицу PID и память ядра. В результате операционная система перестает создавать новые процессы: администратор не может зайти на сервер по SSH или запустить команду `kill` для ликвидации источника проблемы.
   **Пример:**
   ```text
   -bash: fork: retry: Resource temporarily unavailable

   ```

   **Типичная ошибка:** Пытаться остановить активную fork-бомбу запуском стандартных внешних команд вроде `killall bad_app`, так как сам запуск `killall` требует нового `fork()`, который падает с ошибкой.
   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

62. Как ОС ограничивает создание процессов?

   **Ответ:** Через лимиты `RLIMIT_NPROC` (управляемые утилитой `ulimit` или `/etc/security/limits.conf`), контроллер `pids` в Linux Control Groups (cgroups v2: параметр `pids.max`), а также глобальные ограничения ядра `/proc/sys/kernel/threads-max` и `/proc/sys/kernel/pid_max`.
   **Пример:**
   ```bash
   # Установить жесткий лимит максимум 100 процессов на шелл
   ulimit -u 100

   ```

   **Типичная ошибка:** Полагаться только на `ulimit` в многопользовательской среде: `RLIMIT_NPROC` считается суммарно по реальному UID пользователя, а не по конкретному процессу или терминалу.
   **Источник:** [man7: setrlimit(2)](https://man7.org/linux/man-pages/man2/setrlimit.2.html)

63. Как проверить PID дочернего процесса после fork()?

   **Ответ:** В родительском процессе PID ребенка — это возвращаемое значение функции `fork()`. Внутри самого дочернего процесса свой собственный PID узнают системным вызовом `getpid()`.
   **Пример:**
   ```cpp
   #include <unistd.h>
   #include <iostream>

   pid_t pid = fork();
   if (pid > 0) {
       std::cout << "Parent: child PID is " << pid << '\n';
   } else if (pid == 0) {
       std::cout << "Child: my PID is " << getpid() << '\n';
       _exit(0);
   }

   ```

   **Типичная ошибка:** Вызывать `getpid()` в родителе с мыслью, что это идентификатор созданного ребенка (это вернет собственный PID родителя).
   **Источник:** [man7: getpid(2)](https://man7.org/linux/man-pages/man2/getpid.2.html)

64. Можно ли после fork() выполнять разный код в parent и child?

   **Ответ:** Да. Это стандартная идиома использования `fork()`: условный оператор ветвит исполнение на основе возвращенного значения (`> 0` для родителя, `== 0` для дочернего процесса).
   **Пример:**
   ```cpp
   #include <unistd.h>

   pid_t pid = fork();
   if (pid == 0) {
       // Код только для дочернего процесса
       _exit(0);
   } else if (pid > 0) {
       // Код только для родителя
   }

   ```

   **Типичная ошибка:** Не использовать блок обработки ошибки (`pid < 0`), из-за чего при отказе создания процесса код может ошибочно пойти по ветке родителя или привести к аварии.
   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

65. Как организовать parent-child pipeline через fork()?

   **Ответ:** Перед вызовом `fork()` создается однонаправленный канал `pipe(fds)`. После `fork()` родитель закрывает неиспользуемый конец канала (например, для чтения) и пишет в `fds[1]`, а дочерний процесс закрывает конец для записи и читает из `fds[0]` (часто перенаправляя его в `stdin` через `dup2`).
   **Пример:**
   ```cpp
   #include <unistd.h>

   int fds[2];
   pipe(fds);
   if (fork() == 0) {
       close(fds[1]); // Закрываем запись в потомке
       dup2(fds[0], STDIN_FILENO);
       close(fds[0]);
       execlp("grep", "grep", "pattern", nullptr);
   }
   close(fds[0]); // Закрываем чтение в родителе
   write(fds[1], "hello\n", 6);
   close(fds[1]); // Отправляет EOF читателю

   ```

   **Типичная ошибка:** Забывать закрывать неиспользуемые концы пайпа в обоих процессах: читатель никогда не получит символ конца файла (`EOF`), если конец для записи остался открытым хотя бы в одном процессе.
   **Источник:** [man7: pipe(2)](https://man7.org/linux/man-pages/man2/pipe.2.html)

66. Что происходит с памятью heap после fork()?

   **Ответ:** Дочерний процесс получает точную виртуальную копию кучи с теми же виртуальными адресами. За счет CoW физическая память разделяется до первой операции модификации. Изменения, производимые дочерним процессом на куче, никак не влияют на кучу родителя.
   **Пример:**
   ```cpp
   #include <unistd.h>

   int* p = new int(100);
   if (fork() == 0) {
       *p = 500; // Память кучи модифицирована только в ребенке
       _exit(0);
   }
   // Здесь *p по-прежнему равен 100

   ```

   **Типичная ошибка:** Пытаться передавать результаты вычислений из ребенка обратно родителю через запись в общие указатели в куче (для межпроцессного обмена требуются каналы, сокеты или `shmget`/`mmap`).
   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

67. Что происходит со стеком после fork()?

   **Ответ:** Стек родительского потока точно так же дублируется для дочернего процесса с сохранением тех же виртуальных адресов и кадров стека на момент вызова, подчиняясь правилам Copy-on-Write при изменении локальных переменных.
   **Пример:**
   ```cpp
   #include <unistd.h>

   void test() {
       int local_var = 1;
       if (fork() == 0) {
           local_var = 2; // Разделение фрейма стека через CoW
           _exit(0);
       }
   }

   ```

   **Типичная ошибка:** Считать, что адреса локальных переменных в родителе и ребенке будут физически разными. Числовое значение виртуального адреса `&local_var` совпадает, но указывает на разные физические страницы.
   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

68. Меняются ли глобальные переменные независимо в parent и child после fork()?

   **Ответ:** Да, абсолютно независимо. Сегменты `.data` и `.bss` изолированы для каждого процесса благодаря механизму виртуальной памяти и Copy-on-Write.
   **Пример:**
   ```cpp
   #include <unistd.h>

   int g_counter = 0;

   int main() {
       if (fork() == 0) {
           g_counter = 42;
           _exit(0);
       }
       // В родителе g_counter остается равным 0
       return 0;
   }

   ```

   **Типичная ошибка:** Пытаться синхронизировать процессы выставлением флагов в глобальных переменных без использования общей памяти `mmap(MAP_SHARED)`.
   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

69. Что будет, если оба процесса пишут в один и тот же stdout?

   **Ответ:** Если они пишут напрямую через небуферизованный системный вызов `write(1, ...)`, данные будут выводиться корректно, перемешиваясь на уровне отдельных вызовов. Если используется буферизованный ввод/вывод (`printf`, `std::cout`), их вывод может перемешаться в непредсказуемом порядке или дублироваться из-за сброса внутренних буферов библиотек.
   **Пример:**
   ```cpp
   #include <unistd.h>

   if (fork() == 0) {
       write(STDOUT_FILENO, "Child\n", 6);
       _exit(0);
   }
   write(STDOUT_FILENO, "Parent\n", 7);

   ```

   **Типичная ошибка:** Не синхронизировать доступ к терминалу, что приводит к разрыву и смешиванию строк в логах.
   **Источник:** [man7: write(2)](https://man7.org/linux/man-pages/man2/write.2.html)

70. Как избежать дублей буферизованного вывода после fork()?

   **Ответ:** Перед вызовом `fork()` необходимо всегда принудительно сбрасывать пользовательские буферы ввода/вывода с помощью вызова `fflush(nullptr)` (для потоков C) или `std::cout.flush()` (для C++). Если этого не сделать, данные из буфера скопируются в ребенка и будут напечатаны дважды при завершении процессов.
   **Пример:**
   ```cpp
   #include <iostream>
   #include <unistd.h>

   int main() {
       std::cout << "Preparing work..."; // Без \n остается в буфере!
       std::cout.flush(); // Защита от дублирования перед ветвлением

       pid_t p = fork();
       if (p == 0) {
           _exit(0);
       }
       return 0;
   }

   ```

   **Типичная ошибка:** Использовать вывод без сброса буфера (`printf("Log")`) прямо перед `fork()`, в результате чего строка дублируется в консоли или файле логов родителем и потомком.
   **Источник:** [man7: fflush(3)](https://man7.org/linux/man-pages/man3/fflush.3.html)

### exec()

71. Что делает exec()?

   **Ответ:** Семейство системных вызовов `exec` заменяет текущий образ процесса (код, стек, кучу, данные) новым исполняемым файлом, считываемым с диска, и начинает его выполнение с точки входа.

   **Пример:**

   ```cpp
   #include <unistd.h>

   int main() {
       char* args[] = {(char*)"ls", (char*)"-l", nullptr};
       execvp("ls", args);
       return 0;
   }

   ```

   **Типичная ошибка:** Ожидать, что вызов `exec` создает дочерний процесс параллельно текущему. Он уничтожает старый образ текущего процесса.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

72. Заменяет ли exec() текущий процесс новым?

   **Ответ:** Да. Он полностью перезаписывает виртуальное адресное пространство текущего процесса новым кодом и данными, сбрасывая регистры процессора, стек и кучу.

   **Пример:**

   ```cpp
   #include <unistd.h>
   #include <iostream>

   int main() {
       execl("/bin/echo", "echo", "Hello", nullptr);
       std::cout << "This line will NEVER be printed\n";
       return 0;
   }

   ```

   **Типичная ошибка:** Писать код очистки ресурсов сразу после `exec()`, рассчитывая, что он выполнится после завершения новой программы.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

73. Создает ли exec() новый PID?

   **Ответ:** Нет, `PID` (а также `PPID` и `PGID`) процесса остается прежним. С точки зрения ядра это тот же самый процесс, но с другим исполняемым кодом.

   **Пример:**

   ```cpp
   #include <unistd.h>
   #include <iostream>

   int main() {
       std::cout << "PID before: " << getpid() << '\n';
       execl("/bin/sh", "sh", "-c", "echo PID after: $$", nullptr);
       return 0;
   }

   ```

   **Типичная ошибка:** Полагать, что мониторинг процессов по PID зафиксирует появление новой сущности после `exec()`.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

74. Какие есть варианты семейства exec*?

   **Ответ:** Существует системный вызов `execve()` и библиотечные обертки: `execl()`, `execlp()`, `execle()`, `execv()`, `execvp()`, `execvpe()`. Суффиксы кодируют интерфейс: `l` — аргументы списком, `v` — вектором (`char*[]`), `p` — поиск по `$PATH`, `e` — явная передача окружения (`char* envp[]`).

   **Пример:**

   ```text
   l: execl, execlp, execle  (va_list аргументов)
   v: execv, execvp, execvpe (массив аргументов)
   p: execlp, execvp, execvpe (ищет файл в PATH)
   e: execle, execve, execvpe (принимает массив envp)

   ```

   **Типичная ошибка:** Путаться в суффиксах и передавать массив аргументов в функцию с суффиксом `l` (`execl`).

   **Источник:** [man7: exec(3)](https://man7.org/linux/man-pages/man3/exec.3.html)

75. Чем execve() отличается от execl()?

   **Ответ:** `execve()` — это настоящий системный вызов ядра, принимающий путь, массив аргументов (`char* argv[]`) и массив окружения (`char* envp[]`). `execl()` — функция-обертка libc, принимающая аргументы через запятую в виде списка переменной длины и использующая текущее окружение `environ`.

   **Пример:**

   ```cpp
   #include <unistd.h>

   // execl (список):
   execl("/bin/ls", "ls", "-a", nullptr);

   // execve (системный вызов):
   char* args[] = {(char*)"/bin/ls", (char*)"-a", nullptr};
   char* env[] = {nullptr};
   execve("/bin/ls", args, env);

   ```

   **Типичная ошибка:** Забывать передавать завершающий `nullptr` (или `(char*)NULL`) в конце списка аргументов `execl()`, что приводит к UB при чтении `va_list`.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

76. Чем execvp() отличается от execv()?

   **Ответ:** `execvp()` производит автоматический поиск исполняемого файла в каталогах, перечисленных в переменной окружения `$PATH`, если имя файла не содержит слеша (`/`). `execv()` требует точного относительного или абсолютного пути.

   **Пример:**

   ```cpp
   #include <unistd.h>

   char* args[] = {(char*)"ls", nullptr};
   execvp("ls", args); // Найдет /bin/ls через PATH
   execv("ls", args);  // Ошибка ENOENT, если файла "ls" нет в текущей папке

   ```

   **Типичная ошибка:** Использовать `execv` с коротким именем команды без указания пути (например, `"grep"` вместо `"/usr/bin/grep"`).

   **Источник:** [man7: exec(3)](https://man7.org/linux/man-pages/man3/exec.3.html)

77. Когда удобно использовать execvp()?

   **Ответ:** Когда нужно запустить стандартную утилиту ОС или команду по имени, не зная ее точного расположения в файловой системе (например, при реализации собственной командной оболочки Shell).

   **Пример:**

   ```cpp
   #include <unistd.h>

   void run_user_cmd(char** argv) {
       execvp(argv[0], argv); // Shell-подобный запуск
   }

   ```

   **Типичная ошибка:** Использовать `execvp` в сервисах с повышенными привилегиями (SUID), так как подмена `$PATH` злоумышленником позволяет выполнить произвольный бинарник.

   **Источник:** [man7: exec(3)](https://man7.org/linux/man-pages/man3/exec.3.html)

78. Что происходит с адресным пространством при exec()?

   **Ответ:** Старое виртуальное адресное пространство полностью уничтожается: все маппинги памяти (`mmap`), секции кода, статических данных, кучи и стека сбрасываются. Ядро выделяет новое пространство согласно сегментам запускаемого ELF-файла.

   **Пример:**

   ```bash
   # До и после exec карта памяти /proc/<pid>/maps полностью пересоздается
   cat /proc/self/maps

   ```

   **Типичная ошибка:** Пытаться передать указатель на структуру данных в куче из старой программы в новую через аргументы `exec`. В новом образе этот адрес будет невалиден.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

79. Что происходит со стеком и heap при exec()?

   **Ответ:** Старые стек и куча полностью освобождаются. Ядро инициализирует новый стек (куда помещает аргументы `argv`, переменные окружения `envp` и вспомогательный вектор `auxv`) и пустую кучу с нулевым `brk`.

   **Пример:**

   ```cpp
   // Любые выделения памяти (malloc/new) исчезают без утечки памяти ОС
   int* leaked = new int[1000];
   execl("/bin/true", "true", nullptr);

   ```

   **Типичная ошибка:** Считать, что утечки памяти перед вызовом `exec()` могут пережить замену образа процесса.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

80. Сохраняются ли file descriptors после exec()?

   **Ответ:** По умолчанию — да, все файловые дескрипторы остаются открытыми и наследуются новой программой, если на них не был установлен флаг `FD_CLOEXEC`.

   **Пример:**

   ```cpp
   #include <unistd.h>
   #include <fcntl.h>

   int fd = open("log.txt", O_WRONLY);
   // Без FD_CLOEXEC дескриптор fd будет доступен и в новой программе!
   execl("/bin/sh", "sh", nullptr);

   ```

   **Типичная ошибка:** Оставлять открытыми сетевые сокеты и файлы баз данных, которые утекают в запущенные дочерние утилиты.

   **Источник:** [man7: fcntl(2)](https://man7.org/linux/man-pages/man2/fcntl.2.html)

81. Что такое close-on-exec?

   **Ответ:** Битовый флаг дескриптора (`FD_CLOEXEC`), сообщающий ядру, что данный файловый дескриптор должен быть автоматически закрыт при успешном выполнении системного вызова семейства `exec`.

   **Пример:**

   ```cpp
   #include <fcntl.h>

   int fd = open("secret.key", O_RDONLY | O_CLOEXEC);
   // fd автоматически закроется при любом вызове exec

   ```

   **Типичная ошибка:** Открывать файл обычным `open()` и устанавливать `FD_CLOEXEC` отдельным вызовом `fcntl()` в многопоточной среде — между этими вызовами возникает race condition.

   **Источник:** [man7: open(2)](https://man7.org/linux/man-pages/man2/open.2.html)

82. Как установить FD_CLOEXEC?

   **Ответ:** Либо атомарно при создании дескриптора передачей флага `O_CLOEXEC` (в `open()`, `pipe2()`, `socket()`, `accept4()`), либо постфактум через `fcntl(fd, F_SETFD, FD_CLOEXEC)`.

   **Пример:**

   ```cpp
   #include <fcntl.h>

   int flags = fcntl(fd, F_GETFD);
   if (flags != -1) {
       fcntl(fd, F_SETFD, flags | FD_CLOEXEC);
   }

   ```

   **Типичная ошибка:** Перезаписывать флаги через `F_SETFD` значением `FD_CLOEXEC` без предварительного чтения `F_GETFD`.

   **Источник:** [man7: fcntl(2)](https://man7.org/linux/man-pages/man2/fcntl.2.html)

83. Какие атрибуты процесса сохраняются после exec()?

   **Ответ:** Сохраняются: PID, PPID, PGID, SID, реальные UID и GID, текущая рабочая директория (CWD), umask, лимиты ресурсов (`rlimit`), таймеры ожидания, маска блокировки сигналов (`signal mask`) и неперехваченные сигналы (`pending signals`).

   **Пример:**

   ```cpp
   #include <unistd.h>

   // CWD сохранится в запущенной программе
   chdir("/var/log");
   execl("/bin/pwd", "pwd", nullptr);

   ```

   **Типичная ошибка:** Предполагать, что `exec` сбрасывает маску заблокированных сигналов (`sigprocmask`).

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

84. Какие атрибуты сбрасываются после exec()?

   **Ответ:** Сбрасываются: память и стек, таблицы зарегистрированных пользовательских обработчиков сигналов (сбрасываются в `SIG_DFL`), дескрипторы с `FD_CLOEXEC`, контексты потоков (остается один главный поток), альтернативный стек сигналов (`sigaltstack`), имя процесса/потока (`PR_SET_NAME`), привязки к памяти POSIX (`shmat`).

   **Пример:**

   ```text
   Обработчик сигнала -> сброс в SIG_DFL
   Пользовательские потоки -> полностью уничтожаются

   ```

   **Типичная ошибка:** Рассчитывать на срабатывание установленного до `exec()` кастомного `signal(SIGINT, handler)` в новой программе.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

85. Что происходит с обработчиками сигналов после exec()?

   **Ответ:** Сигналы, для которых были зарегистрированы пользовательские функции-обработчики, сбрасываются в действие по умолчанию (`SIG_DFL`), так как адрес памяти старой функции больше не существует. Сигналы с действием `SIG_IGN` (игнорирование) сохраняют состояние игнорирования.

   **Пример:**

   ```cpp
   #include <csignal>
   #include <unistd.h>

   int main() {
       signal(SIGINT, SIG_IGN); // SIGINT останется проигнорированным после exec!
       execl("/bin/sleep", "sleep", "10", nullptr);
   }

   ```

   **Типичная ошибка:** Игнорировать сигналы перед `exec()`: новая программа унаследует `SIG_IGN` и не сможет перехватить их штатно, пока явно не сбросит обработчик.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

86. Что происходит с argv при exec()?

   **Ответ:** Переданный массив строк копируется ядром на верхушку нового стека создаваемой программы. Указатель на этот массив передается в качестве первого аргумента функции `main(int argc, char *argv[])` новой программы.

   **Пример:**

   ```cpp
   char* args[] = {(char*)"prog_name", (char*)"arg1", nullptr};
   execv("/path/to/binary", args);

   ```

   **Типичная ошибка:** Пропускать `argv[0]`. По соглашению `argv[0]` — это имя вызываемой программы. Если забыть его передать, реальный первый аргумент превратится в имя программы.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

87. Что происходит с envp при exec()?

   **Ответ:** В вызовах без суффикса `e` новое адресное пространство получает текущий массив `environ`. При явной передаче аргумента `envp` (в `execve`, `execle`, `execvpe`) новое окружение заменяется переданным массивом.

   **Пример:**

   ```cpp
   char* custom_env[] = {(char*)"PORT=8080", (char*)"ENV=PROD", nullptr};
   execle("/bin/app", "app", nullptr, custom_env);

   ```

   **Типичная ошибка:** Забывать завершать массив `envp` нулевым указателем `nullptr`.

   **Источник:** [man7: environ(7)](https://man7.org/linux/man-pages/man7/environ.7.html)

88. Как передать переменные окружения в execve()?

   **Ответ:** Сформировать массив указателей `char* envp[]`, где каждая строка имеет вид `"KEY=VALUE"`, и последним элементом поставить `nullptr`. Этот массив передается третьим параметром в `execve()`.

   **Пример:**

   ```cpp
   #include <unistd.h>

   int main() {
       char* args[] = {(char*)"printenv", nullptr};
       char* env[] = {(char*)"FOO=BAR", (char*)"USER=admin", nullptr};
       execve("/usr/bin/printenv", args, env);
       return 0;
   }

   ```

   **Типичная ошибка:** Пытаться передавать переменные раздельно без знака `=`, из-за чего libc не сможет распарсить значение.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

89. Что вернет exec(), если он успешен?

   **Ответ:** Успешный `exec()` не возвращает никакого значения, так как вызывающий контекст программы полностью перестает существовать в памяти.

   **Пример:**

   ```cpp
   #include <unistd.h>

   int main() {
       execl("/bin/true", "true", nullptr);
       // Сюда выполнение НИКОГДА не дойдет при успехе
   }

   ```

   **Типичная ошибка:** Писать проверку вида `if (execl(...) == 0)` — успешный возврат физически невозможен.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

90. Почему успешный exec() не возвращает управление?

   **Ответ:** Потому что адрес возврата (instruction pointer) и стек вызывающей функции больше не существуют. Процессор начинает выполнять код с адреса точки входа (`_start`), указанного в заголовке нового ELF-бинарника.

   **Пример:**

   ```text
   [Старый ELF] -- execve() -> Ядро перезаписывает память -> [Новый ELF (_start)]

   ```

   **Типичная ошибка:** Полагать, что процесс работает как подпрограмма (subroutine) и вернется в вызывающую функцию после выхода из новой программы.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

91. Как обработать ошибку exec()?

   **Ответ:** Если `exec()` вернул управление, значит произошла ошибка. Возвращаемое значение всегда равно `-1`. Ошибку логируют с помощью `perror()` или `errno` и немедленно завершают процесс вызовом `_exit()`.

   **Пример:**

   ```cpp
   #include <unistd.h>
   #include <cstdio>

   execl("/bin/non_existing", "non_existing", nullptr);
   perror("exec failed");
   _exit(127);

   ```

   **Типичная ошибка:** Забывать прерывать выполнение после ошибки `exec()` в дочернем процессе, из-за чего дочерний процесс начинает выполнять дальнейший код родителя.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

92. Какие типичные причины ошибки exec()?

   **Ответ:** `ENOENT` (файл или интерпретатор не найден), `EACCES` (нет прав на исполнение файла или чтение пути), `ENOEXEC` (неверный формат исполняемого файла / битый ELF), `E2BIG` (список аргументов или окружения превышает лимит `ARG_MAX`), `ENOMEM` (недостаточно памяти ядра).

   **Пример:**

   ```cpp
   #include <cerrno>
   // Если размер argv превышает лимит ядра:
   // errno == E2BIG

   ```

   **Типичная ошибка:** Не учитывать лимит ядра на размер аргументов командной строки при передаче миллионов параметров через `exec`.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

93. Что означает ENOENT при exec()?

   **Ответ:** Файл по указанному пути не существует, либо для скрипта с shebang (`#!/path/to/interp`) не существует указанный интерпретатор, либо отсутствует необходимый ELF dynamic linker (например, `/lib64/ld-linux-x86-64.so.2`).

   **Пример:**

   ```bash
   # Ошибка ENOENT при запуске скрипта с несуществующим интерпретатором:
   #!/bin/bash_custom_not_found

   ```

   **Типичная ошибка:** Искать причину `ENOENT` только в самом бинарнике, не проверяя наличие путей в строке shebang скрипта или динамического компоновщика.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

94. Что означает EACCES при exec()?

   **Ответ:** Отсутствуют права на выполнение файла (нет бита `x` для текущего пользователя), либо нет прав на поиск/проход (`x`) через один из родительских каталогов пути, либо файловая система смонтирована с опцией `noexec`.

   **Пример:**

   ```bash
   chmod -x ./my_app
   ./my_app # вернет EACCES (Permission denied)

   ```

   **Типичная ошибка:** Пытаться запустить бинарник из каталога `/tmp`, смонтированного с флагом `noexec`, получая `EACCES` даже с правами `chmod 777`.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

95. Как shell использует fork()+exec() для запуска команд?

   **Ответ:** Shell парсит введенную строку, вызывает `fork()`, внутри дочернего процесса при необходимости настраивает ввод/вывод (`dup2` для редиректов и пайпов) и вызывает `execvp()`, а родительский shell ждет завершения команды с помощью `waitpid()`.

   **Пример:**

   ```cpp
   pid_t p = fork();
   if (p == 0) {
       execlp("ls", "ls", nullptr);
       _exit(1);
   }
   waitpid(p, nullptr, 0);

   ```

   **Типичная ошибка:** Вызывать `exec()` напрямую в родительском shell: это приведет к немедленному закрытию самого терминала shell после отработки команды.

   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

96. Почему fork()+exec() — классическая модель Unix?

   **Ответ:** Модель разделяет создание процесса (`fork`) и загрузку программы (`exec`). В промежутке между ними дочерний процесс может легко и гибко настроить окружение без усложнения API: перенаправить дескрипторы, сменить пользователя (`setuid`), сменить рабочую директорию или группу процессов.

   **Пример:**

   ```cpp
   if (fork() == 0) {
       // Гибкая настройка до загрузки бинарника:
       dup2(fd, STDOUT_FILENO);
       setuid(1001);
       execl("/bin/app", "app", nullptr);
   }

   ```

   **Типичная ошибка:** Считать такое разделение устаревшим и ненужным: оно лежит в основе всех пайплайнов Unix (`cmd1 | cmd2`).

   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

97. Когда используют posix_spawn() вместо fork()+exec()?

   **Ответ:** В системах с ограниченными ресурсами, на платформах без MMU (где нет виртуальной памяти), либо в огромных многопоточных процессах для минимизации накладных расходов на дублирование таблиц страниц памяти при `fork()`.

   **Пример:**

   ```cpp
   #include <spawn.h>

   pid_t pid;
   char* argv[] = {(char*)"ls", nullptr};
   posix_spawn(&pid, "/bin/ls", nullptr, nullptr, argv, environ);

   ```

   **Типичная ошибка:** Полагать, что `posix_spawn()` в Linux — это совершенно отдельный системный вызов ядра: внутри libc он оптимизирован через `clone(CLONE_VM | CLONE_VFORK)`.

   **Источник:** [man7: posix_spawn(3)](https://man7.org/linux/man-pages/man3/posix_spawn.3.html)

98. Как через exec() запустить другую C++ программу?

   **Ответ:** Скомпилировать целевую программу в отдельный исполняемый файл и вызвать один из вызовов семейства `exec` (например, `execl`), передав путь к скомпилированному бинарнику.

   **Пример:**

   ```cpp
   #include <unistd.h>

   int main() {
       execl("./my_other_cpp_binary", "my_other_cpp_binary", "arg1", nullptr);
       return 1;
   }

   ```

   **Типичная ошибка:** Передавать путь к исходному файлу `.cpp` вместо скомпилированного бинарника.

   **Источник:** [man7: exec(3)](https://man7.org/linux/man-pages/man3/exec.3.html)

99. Что будет с открытыми сокетами после exec(), если не выставлен CLOEXEC?

   **Ответ:** Сокеты останутся открытыми в новом процессе. Соединение не закроется, а новая программа сможет отправлять и получать данные через унаследованные файловые дескрипторы, что создает утечку дескрипторов и риски безопасности.

   **Пример:**

   ```cpp
   int sfd = socket(AF_INET, SOCK_STREAM, 0); // Без SOCK_CLOEXEC
   execl("/bin/bash", "bash", nullptr);       // Баш унаследует открытый сокет

   ```

   **Типичная ошибка:** Забывать флаг `SOCK_CLOEXEC` при создании серверных слушающих сокетов, из-за чего дочерняя утилита держит порт занятым даже после падения основного сервера.

   **Источник:** [man7: socket(2)](https://man7.org/linux/man-pages/man2/socket.2.html)

100. Почему важно контролировать наследование FD при exec()?

   **Ответ:** Незакрытые FD приводят к утечкам ресурсов (невозможность освободить порт, удалить файл или получить EOF в пайпе) и уязвимостям безопасности (запущенная сторонняя утилита может прочитать конфиденциальные данные из файлов родителя).

   **Пример:**

   ```cpp
   // Защита дескриптора от утечки в дочерние приложения
   int fd = open("auth.db", O_RDWR | O_CLOEXEC);
   ```

   **Типичная ошибка:** Запуск утилит вроде `tar` или `curl` через `fork+exec` без флага `CLOEXEC` на внутренних соединениях базы данных.

   **Источник:** [man7: open(2)](https://man7.org/linux/man-pages/man2/open.2.html)

### Signals

101. Что такое signal в Linux?

   **Ответ:** Сигнал — это асинхронное уведомление ядра, посылаемое процессу или потоку для информирования о наступлении системного события, аппаратного сбоя или запроса от другого процесса.

   **Пример:**

   ```bash
   kill -s SIGUSR1 <PID>
   ```

   **Типичная ошибка:** Путать сигналы Linux с синхронными сообщениями IPC (такими как очереди сообщений или сокеты): сигналы не передают произвольных массивов данных.

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

102. Для чего нужны сигналы?

   **Ответ:** Сигналы используются для обработки исключительных ситуаций (деление на ноль, доступ к запрещенной памяти), управления процессами (остановка, возобновление, завершение), оповещения об изменении состояния дочерних процессов (`SIGCHLD`) и таймеров.

   **Пример:**

   ```cpp
   #include <csignal>
   #include <unistd.h>

   // Мягкая перезагрузка конфигурации демона
   void reload_config(int) { /* re-read config */ }
   ```

   **Типичная ошибка:** Использовать сигналы для регулярного обмена бизнес-данными между процессами с высокой интенсивностью.

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

103. Чем signal отличается от exception?

   **Ответ:** Сигнал генерируется и доставляется ядром ОС на уровне процессов/потоков асинхронно в любой момент времени (прерывая выполнение машинных инструкций). C++ exception — это языковая синхронная конструкция, инициируемая явно выражением `throw` и раскручивающая стек вызовов в строгом соответствии с моделью типов.

   **Пример:**

   ```cpp
   // Сигнал ОС (прилетает извне):
   kill(getpid(), SIGTERM);

   // Исключение языка C++:
   throw std::runtime_error("Logical error");
   ```

   **Типичная ошибка:** Пытаться поймать аппаратный `SIGSEGV` с помощью блока `try { ... } catch (...)`. Сигналы ОС не перехватываются блоками `catch`.

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

104. Какие сигналы нельзя перехватить?

   **Ответ:** Нельзя перехватить, заблокировать или проигнорировать два сигнала: `SIGKILL` (принудительное уничтожение) и `SIGSTOP` (принудительная остановка). Ядро обрабатывает их безусловно.

   **Пример:**

   ```cpp
   #include <csignal>

   // Попытка установить обработчик вернет ошибку EINVAL:
   signal(SIGKILL, [](int){});
   ```

   **Типичная ошибка:** Попытка зарегистрировать обработчик для `SIGKILL`, чтобы сбросить несохраненные данные перед аварийным завершением.

   **Источник:** [man7: sigaction(2)](https://man7.org/linux/man-pages/man2/sigaction.2.html)

105. Чем SIGTERM отличается от SIGKILL?

   **Ответ:** `SIGTERM` — сигнал мягкого завершения по умолчанию: процесс может перехватить его, закрыть файлы, сбросить буферы и корректно выйти. `SIGKILL` обрабатывается исключительно ядром: процесс уничтожается мгновенно, не имея шанса выполнить какой-либо код.

   **Пример:**

   ```bash
   kill -15 <pid> # Посылает SIGTERM (штатная остановка)
   kill -9  <pid> # Посылает SIGKILL (мгновенное убийство)
   ```

   **Типичная ошибка:** Сразу убивать зависшие сервисы командой `kill -9` вместо попытки дать сервису завершиться через `kill -15`.

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

106. Что делает SIGTERM?

   **Ответ:** Посылает процессу запрос на штатное завершение. Действие по умолчанию — завершение работы процесса. Однако процесс может перехватить или проигнорировать этот сигнал.

   **Пример:**

   ```cpp
   #include <csignal>

   void handle_term(int) {
       // Очистить ресурсы и корректно выйти
   }
   ```

   **Типичная ошибка:** Считать, что `SIGTERM` гарантированно остановит процесс (если процесс завис в дедлоке или игнорирует сигнал, он продолжит работу).

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

107. Что делает SIGKILL?

   **Ответ:** Немедленно и принудительно останавливает и уничтожает процесс на уровне ядра ОС. Процесс освобождает память и дескрипторы, переходя в состояние zombie до вызова `wait` родителем.

   **Пример:**

   ```bash
   kill -KILL <PID>
   ```

   **Типичная ошибка:** Надеяться, что при `SIGKILL` сработают деструкторы локальных и глобальных объектов C++.

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

108. Почему SIGKILL нельзя обработать?

   **Ответ:** Это фундаментальное архитектурное решение Unix, гарантирующее системному администратору и ядру возможность принудительно остановить любой некорректно работающий или вредоносный процесс, потерявший управление.

   **Пример:**

   ```text
   Ядро проверяет (sig == SIGKILL || sig == SIGSTOP) -> прямой вызов do_exit()
   ```

   **Типичная ошибка:** Проектировать систему с расчетом на то, что процесс всегда успеет отправить сетевой пакет перед завершением по `SIGKILL`.

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

109. Почему SIGTERM считается “мягким” завершением?

   **Ответ:** Потому что он дает приложению возможность выполнить graceful shutdown: остановить прием новых запросов, дождаться завершения текущих транзакций, сбросить буферы на диск, закрыть соединения с базами данных и удалить временные PID-файлы.

   **Пример:**

   ```cpp
   std::atomic<bool> g_stop{false};
   void on_sigterm(int) { g_stop = true; }
   ```

   **Типичная ошибка:** Делать внутри обработчика `SIGTERM` немедленный `exit(0)`, превращая мягкое завершение в жесткое без корректной очистки.

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

110. Что делает SIGINT?

   **Ответ:** Сигнал прерывания с клавиатуры, генерируемый терминалом при нажатии пользователем комбинации клавиш `Ctrl+C`. Действие по умолчанию — завершение процесса.

   **Пример:**

   ```bash
   # Прерывает выполнение запущенной команды в foreground
   ^C
   ```

   **Типичная ошибка:** Полагать, что `Ctrl+C` посылает `SIGTERM`. Он посылает `SIGINT`.

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

111. Что делает SIGSTOP?

   **Ответ:** Безусловно приостанавливает выполнение процесса ядром (переводит в состояние `TASK_STOPPED`). Процесс не потребляет процессорное время, не может обработать или перехватить этот сигнал и ожидает сигнала `SIGCONT`.

   **Пример:**

   ```bash
   kill -STOP <PID>
   ```

   **Типичная ошибка:** Путать `SIGSTOP` (неперехватываемый сигнал от любого процесса) и `SIGTSTP` (сигнал остановки с клавиатуры по `Ctrl+Z`, который можно перехватить).

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

112. Что делает SIGCONT?

   **Ответ:** Возобновляет выполнение ранее остановленного процесса (находившегося в состояниях `TASK_STOPPED` после сигналов `SIGSTOP`, `SIGTSTP`, `SIGTTIN`, `SIGTTOU`).

   **Пример:**

   ```bash
   kill -CONT <PID>
   ```

   **Типичная ошибка:** Отправлять `SIGCONT` процессу, который не был остановлен: сигнал будет проигнорирован (если на него не назначен кастомный обработчик).

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

113. Что делает SIGCHLD?

   **Ответ:** Сигнал, отправляемый ядром родительскому процессу всякий раз, когда любой из его дочерних процессов завершился, был остановлен или возобновлен. Действие по умолчанию — игнорирование (`SIG_IGN`).

   **Пример:**

   ```cpp
   #include <csignal>
   #include <sys/wait.h>

   void on_sigchld(int) {
       while (waitpid(-1, nullptr, WNOHANG) > 0);
   }
   ```

   **Типичная ошибка:** Считать, что `SIGCHLD` генерируется только при полной смерти ребенка; он генерируется также при событиях стоп/продолжение (`stop`/`continue`).

   **Источник:** [man7: sigaction(2)](https://man7.org/linux/man-pages/man2/sigaction.2.html)

114. Что делает SIGSEGV?

   **Ответ:** Сигнал нарушения сегментации памяти (Segmentation Fault). Генерируется процессором (через MMU) и ядром при попытке обращения к невыделенному адресу памяти или нарушения прав доступа (например, запись в страницу `read-only`). По умолчанию завершает процесс и создает core dump.

   **Пример:**

   ```cpp
   int* p = nullptr;
   *p = 42; // Вызывает аппаратное прерывание -> ядро шлет SIGSEGV
   ```

   **Типичная ошибка:** Пытаться продолжить нормальное исполнение кода из обработчика `SIGSEGV` без исправления контекста памяти: процессор снова выполнит сбойную инструкцию, вызвав бесконечный цикл сигнала.

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

115. Что делает SIGABRT?

   **Ответ:** Сигнал аварийного завершения, отправляемый процессу функцией `abort()` (например, при несработанном макросе `assert`, повторном выбрасывании исключения из деструктора или нарушении целостности кучи). По умолчанию завершает процесс с генерацией core dump.

   **Пример:**

   ```cpp
   #include <cstdlib>
   #include <cassert>

   int main() {
       assert(2 + 2 == 5); // Вызовет abort(), который отправит SIGABRT
       return 0;
   }
   ```

   **Типичная ошибка:** Блокировать `SIGABRT` с целью предотвратить падение программы. Функция `abort()` сбросит обработчик в `SIG_DFL` и принудительно завершит процесс.

   **Источник:** [man7: abort(3)](https://man7.org/linux/man-pages/man3/abort.3.html)

116. Как отправить сигнал процессу из shell?

   **Ответ:** С помощью встроенной команды shell `kill` или утилиты `/bin/kill`, передавая имя или номер сигнала и целевой PID.

   **Пример:**

   ```bash
   kill -SIGTERM 1234
   kill -15 1234
   ```

   **Типичная ошибка:** Думать, что команда `kill` предназначена исключительно для «убийства» процесса. Это утилита для отправки любых сигналов, включая информационные (`SIGUSR1`, `SIGWINCH`).

   **Источник:** [man7: kill(1)](https://man7.org/linux/man-pages/man1/kill.1.html)

117. Что делает kill -15?

   **Ответ:** Отправляет процессу сигнал `SIGTERM` (номер 15), запрашивая его корректное штатное завершение.

   **Пример:**

   ```bash
   kill -15 $(pgrep my_daemon)
   ```

   **Типичная ошибка:** Считать, что `kill -15` применится мгновенно: если процесс блокирует ввод/вывод или выполняет долгий цикл, завершение произойдет с задержкой.

   **Источник:** [man7: kill(1)](https://man7.org/linux/man-pages/man1/kill.1.html)

118. Что делает kill -9?

   **Ответ:** Отправляет сигнал `SIGKILL` (номер 9), заставляя ядро немедленно уничтожить процесс в обход любых пользовательских обработчиков.

   **Пример:**

   ```bash
   kill -9 9876
   ```

   **Типичная ошибка:** Отправлять `kill -9` процессу в состоянии `D` (Uninterruptible Sleep): ядро не сможет доставить сигнал, пока процесс не завершит системную операцию I/O.

   **Источник:** [man7: kill(1)](https://man7.org/linux/man-pages/man1/kill.1.html)

119. Почему kill -9 стоит использовать осторожно?

   **Ответ:** Процесс уничтожается мгновенно без вызова деструкторов и функций очистки: на диске могут остаться поврежденные файлы баз данных, блокировочные lock-файлы (`.pid`), незакрытые транзакции и неосвобожденные разделяемые ресурсы IPC.

   **Пример:**

   ```bash
   # Оставшийся lock-файл помешает новому запуску сервиса:
   /var/run/my_service.pid
   ```

   **Типичная ошибка:** Настраивать скрипты развертывания (CI/CD) на постоянное использование `kill -9` для остановки серверов вместо корректного таймаута: `SIGTERM -> wait -> SIGKILL`.

   **Источник:** [man7: kill(1)](https://man7.org/linux/man-pages/man1/kill.1.html)

120. Что происходит с ресурсами процесса при SIGKILL?

   **Ответ:** Все ресурсы, управляемые ядром (виртуальная память, файловые дескрипторы, сокеты, семафоры POSIX), принудительно и полностью освобождаются операционной системой. Ресурсы уровня приложения (логические структуры данных, незавершенные транзакции) остаются в несогласованном состоянии.

   **Пример:**

   ```text
   Ядро: close(all_fds) + free(all_pages)
   Приложение: данные в памяти, не сброшенные на диск через write(), теряются
   ```

   **Типичная ошибка:** Полагать, что `SIGKILL` оставляет неосвобожденную оперативную память в системе. Ядро всегда очищает память процесса.

   **Источник:** [man7: exit(2)](https://man7.org/linux/man-pages/man2/exit.2.html)

121. Может ли процесс проигнорировать SIGTERM?

   **Ответ:** Да. Процесс может явно установить реакцию на `SIGTERM` в `SIG_IGN` или зарегистрировать собственный обработчик, который ничего не делает.

   **Пример:**

   ```cpp
   #include <csignal>

   int main() {
       signal(SIGTERM, SIG_IGN); // Игнорировать SIGTERM
       while (true) {}
       return 0;
   }
   ```

   **Типичная ошибка:** Забывать предусмотреть аварийный механизм завершения сервиса, полностью игнорирующего `SIGTERM`.

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

122. Может ли процесс проигнорировать SIGKILL?

   **Ответ:** Нет, ни при каких обстоятельствах. Ядро перехватывает `SIGKILL` до планирования процесса и не позволяет изменить обработчик или добавить его в маску блокировки.

   **Пример:**

   ```cpp
   sigset_t set;
   sigemptyset(&set);
   sigaddset(&set, SIGKILL);
   sigprocmask(SIG_BLOCK, &set, nullptr); // Ядро просто проигнорирует блокировку SIGKILL
   ```

   **Типичная ошибка:** Рассчитывать на защиту критических секций от завершения с помощью блокировки `SIGKILL`.

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

123. Что такое signal handler?

   **Ответ:** Пользовательская функция обратного вызова (коллбэк), которая автоматически вызывается ядром в контексте потока при поступлении соответствующего сигнала, прерывая обычный поток выполнения инструкций.

   **Пример:**

   ```cpp
   void my_handler(int signum) {
       // Код обработки сигнала
   }
   ```

   **Типичная ошибка:** Писать обработчик сигнала как тяжелую функцию бизнес-логики с выполнением сетевых и дисковых запросов.

   **Источник:** [man7: sigaction(2)](https://man7.org/linux/man-pages/man2/sigaction.2.html)

124. Как установить обработчик сигнала в C?

   **Ответ:** Исторически — через устаревший вызов `signal(signum, handler)`, современный стандартный способ — системный вызов `sigaction()`.

   **Пример:**

   ```cpp
   #include <csignal>

   struct sigaction sa{};
   sa.sa_handler = my_handler;
   sigaction(SIGINT, &sa, nullptr);
   ```

   **Типичная ошибка:** Использовать функцию `signal()` в переносимом коде: ее семантика различается между версиями Unix (может сбрасывать обработчик на `SIG_DFL` после первого вызова).

   **Источник:** [man7: sigaction(2)](https://man7.org/linux/man-pages/man2/sigaction.2.html)

125. Почему sigaction() предпочтительнее signal()?

   **Ответ:** `sigaction()` имеет строго определенное стандартом POSIX поведение: он надежно блокирует повторное поступление обрабатываемого сигнала во время работы обработчика, не сбрасывает диспозицию обратно в `SIG_DFL` и позволяет тонко настраивать поведение (флаги `SA_RESTART`, `SA_SIGINFO`).

   **Пример:**

   ```cpp
   struct sigaction sa{};
   sa.sa_handler = handler;
   sa.sa_flags = SA_RESTART; // Автоперезапуск прерванных syscalls
   sigaction(SIGTERM, &sa, nullptr);
   ```

   **Типичная ошибка:** Использование `signal()` вместо `sigaction()`, что чревато состоянием гонки при повторном поступлении сигнала.

   **Источник:** [man7: sigaction(2)](https://man7.org/linux/man-pages/man2/sigaction.2.html)

126. Что можно делать внутри signal handler?

   **Ответ:** Внутри обработчика разрешено вызывать строго ограниченный набор функций — `async-signal-safe` функции (например, системные вызовы `write`, `_exit`), либо производить запись в атомарную переменную типа `volatile sig_atomic_t` или `std::atomic`.

   **Пример:**

   ```cpp
   #include <unistd.h>

   void safe_handler(int) {
       const char msg[] = "Signal caught\n";
       write(STDOUT_FILENO, msg, sizeof(msg) - 1);
   }
   ```

   **Типичная ошибка:** Выделять динамическую память (`malloc`, `new`) или выбрасывать исключения C++ из обработчика асинхронного сигнала.

   **Источник:** [man7: signal-safety(7)](https://man7.org/linux/man-pages/man7/signal-safety.7.html)

127. Что такое async-signal-safe функции?

   **Ответ:** Функции, гарантирующие корректность и безопасность при вызове из любого места, включая обработчик сигнала, прервавший выполнение той же самой или другой библиотечной функции. Они не используют глобальных неблокированных структур и внутренних мьютексов.

   **Пример:**

   ```text
   Безопасные: write(), read(), _exit(), clock_gettime()
   Небезопасные: printf(), malloc(), free(), exit()
   ```

   **Типичная ошибка:** Вызов небезопасной функции (например, `gethostbyname`) из обработчика сигнала, что вызывает сбой внутренней статической памяти libc.

   **Источник:** [man7: signal-safety(7)](https://man7.org/linux/man-pages/man7/signal-safety.7.html)

128. Почему printf() опасен внутри signal handler?

   **Ответ:** `printf()` захватывает внутренний мьютекс потока ввода/вывода (`stdout lock`) и выделяет динамическую память буфера. Если сигнал пришел в момент, когда основной поток УЖЕ захватил этот мьютекс внутри другого `printf()`, повторный вызов приведет к классическому Deadlock (взаимной блокировке процесса самим собой).

   **Пример:**

   ```cpp
   void bad_handler(int) {
       printf("Got signal\n"); // Риск вечного Deadlock!
   }
   ```

   **Типичная ошибка:** Использовать `printf` или `std::cout` для отладки поведения обработчиков сигналов.

   **Источник:** [man7: signal-safety(7)](https://man7.org/linux/man-pages/man7/signal-safety.7.html)

129. Что такое reentrancy в контексте сигналов?

   **Ответ:** Реентерабельность — свойство функции безопасно выполняться параллельно в нескольких контекстах (например, когда функция была прервана сигналом, и этот же обработчик вызвал ее повторно), не повреждая свое состояние и корректно возвращая результат.

   **Пример:**

   ```cpp
   // Реентерабельная функция не использует static-переменные:
   int add(int a, int b) { return a + b; }
   ```

   **Типичная ошибка:** Использование нереентерабельных функций стандартной библиотеки (таких как `strtok` вместо `strtok_r`) в контексте сигналов.

   **Источник:** [man7: signal-safety(7)](https://man7.org/linux/man-pages/man7/signal-safety.7.html)

130. Как безопасно уведомить основной поток из signal handler?

   **Ответ:** 1) Изменить флаг типа `volatile std::sig_atomic_t` или `std::atomic<bool>`. 2) Использовать трюк с Self-Pipe (`write(pipe_fd[1], ...)`), пробуждающий `epoll`/`select` в основном цикле событий (event loop). 3) Использовать `signalfd()`.

   **Пример:**

   ```cpp
   #include <unistd.h>

   int notify_pipe[2];
   void on_sig(int) {
       char ch = 's';
       write(notify_pipe[1], &ch, 1); // Безопасное пробуждение epoll
   }
   ```

   **Типичная ошибка:** Использовать `std::condition_variable::notify_one()` внутри обработчика сигнала (условные переменные не входят в список async-signal-safe).

   **Источник:** [man7: signalfd(2)](https://man7.org/linux/man-pages/man2/signalfd.2.html)

131. Что такое volatile sig_atomic_t?

   **Ответ:** Целочисленный тип данных, чтение и запись которого гарантированно атомарны относительно сигналов процессора (выполняются за одну неделимую инструкцию памяти), а спецификатор `volatile` запрещает компилятору кешировать его значение в регистрах.

   **Пример:**

   ```cpp
   #include <csignal>

   volatile std::sig_atomic_t g_stop_requested = 0;

   void sig_handler(int) {
       g_stop_requested = 1;
   }
   ```

   **Типичная ошибка:** Использовать обычный составной тип или сложную структуру данных без синхронизации вместо `sig_atomic_t`.

   **Источник:** [man7: signal-safety(7)](https://man7.org/linux/man-pages/man7/signal-safety.7.html)

132. Как корректно завершать сервер по SIGTERM?

   **Ответ:** По получении сигнала взвести атомарный флаг завершения, прервать блокирующие операции ожидания соединений (`epoll_wait`), прекратить прием входящих запросов (`close listen socket`), завершить текущие сессии клиентов, сбросить кэши на диск и освободить ресурсы перед финальным выходом из `main()`.

   **Пример:**

   ```cpp
   while (!g_stop_requested) {
       // обработка сетевых событий с таймаутом
   }
   cleanup_resources();
   ```

   **Типичная ошибка:** Принудительно рубить соединения прямо внутри тела обработчика сигнала.

   **Источник:** [man7: sigaction(2)](https://man7.org/linux/man-pages/man2/sigaction.2.html)

133. Почему демоны обычно обрабатывают SIGTERM?

   **Ответ:** Демоны работают в фоновом режиме под управлением систем инициализации (systemd, Docker, Kubernetes). При остановке или обновлении сервиса система посылает именно `SIGTERM`. Демон должен перехватить его, чтобы сохранить состояние и не оставить несогласованных данных.

   **Пример:**

   ```ini
   # systemd останавливает сервис через SIGTERM:
   KillSignal=SIGTERM
   TimeoutStopSec=30
   ```

   **Типичная ошибка:** Не обрабатывать `SIGTERM`, что заставляет оркестратор ждать таймаут (обычно 30-90 сек) и жестко убивать сервис через `SIGKILL`.

   **Источник:** [man7: systemd.service(5)](https://man7.org/linux/man-pages/man5/systemd.service.5.html)

134. Как родитель узнает о завершении child через SIGCHLD?

   **Ответ:** Ядро автоматически посылает родителю сигнал `SIGCHLD`. Обработчик этого сигнала вызывает `waitpid(-1, &status, WNOHANG)` в цикле, получая PID завершившегося ребенка и код выхода без блокировки основного потока.

   **Пример:**

   ```cpp
   #include <sys/wait.h>
   #include <csignal>

   void handle_sigchld(int) {
       int saved_errno = errno;
       while (waitpid(-1, nullptr, WNOHANG) > 0);
       errno = saved_errno; // Обязательно восстановить errno!
   }
   ```

   **Типичная ошибка:** Забывать восстанавливать значение `errno` в конце обработчика сигнала: `waitpid` может перезаписать ошибку прерванного системного вызова в основном потоке.

   **Источник:** [man7: waitpid(2)](https://man7.org/linux/man-pages/man2/waitpid.2.html)

135. Что такое pending signal?

   **Ответ:** Отложенный сигнал, который уже был сгенерирован ядром или отправлен процессом, но еще не доставлен целевому потоку, так как данный сигнал в настоящий момент заблокирован в его сигнальной маске (`signal mask`).

   **Пример:**

   ```cpp
   #include <csignal>

   sigset_t pending;
   sigpending(&pending); // Получить список ожидающих сигналов
   ```

   **Типичная ошибка:** Полагать, что отложенные стандартные сигналы накапливаются в очередь. Если сигнал сгенерирован несколько раз, пока он заблокирован, ядро пометит его флаг только один раз.

   **Источник:** [man7: sigpending(2)](https://man7.org/linux/man-pages/man2/sigpending.2.html)

136. Что такое blocked signal?

   **Ответ:** Сигнал, доставка которого потоку временно отложена системным вызовом `pthread_sigmask()` или `sigprocmask()`. Сигнал не отбрасывается, а переводится в состояние ожидания (`pending`) до момента его разблокировки.

   **Пример:**

   ```cpp
   #include <csignal>

   sigset_t set;
   sigemptyset(&set);
   sigaddset(&set, SIGINT);
   sigprocmask(SIG_BLOCK, &set, nullptr); // SIGINT теперь заблокирован
   ```

   **Типичная ошибка:** Путать блокировку сигнала (`blocking`) и игнорирование (`ignoring`). Проигнорированный сигнал уничтожается, а заблокированный — доставляется сразу после разблокировки.

   **Источник:** [man7: sigprocmask(2)](https://man7.org/linux/man-pages/man2/sigprocmask.2.html)

137. Как временно заблокировать сигнал?

   **Ответ:** Добавить сигнал в сигнальную маску вызовом `sigprocmask(SIG_BLOCK, ...)` (или `pthread_sigmask` для потоков), выполнить критическую секцию кода и восстановить старую маску вызовом с `SIG_SETMASK`.

   **Пример:**

   ```cpp
   sigset_t mask, oldmask;
   sigemptyset(&mask);
   sigaddset(&mask, SIGTERM);
   sigprocmask(SIG_BLOCK, &mask, &oldmask);

   // Критическая секция: SIGTERM отложен
   do_critical_work();

   sigprocmask(SIG_SETMASK, &oldmask, nullptr); // Разблокировка
   ```

   **Типичная ошибка:** Использовать `SIG_UNBLOCK` вместо восстановления предыдущей сохраненной маски через `SIG_SETMASK`, случайно снимая внешние блокировки.

   **Источник:** [man7: sigprocmask(2)](https://man7.org/linux/man-pages/man2/sigprocmask.2.html)

138. Что такое default action сигнала?

   **Ответ:** Предусмотренное стандартом ядра Linux стандартное действие (`SIG_DFL`), которое выполняется при отсутствии зарегистрированного пользовательского обработчика: Term (завершение), Core (завершение с дампом памяти), Ignore (игнорирование), Stop (остановка), Cont (возобновление).

   **Пример:**

   ```text
   SIGTERM -> Term (завершение)
   SIGSEGV -> Core (дамп памяти + завершение)
   SIGCHLD -> Ignore (игнорирование)
   ```

   **Типичная ошибка:** Считать, что все необработанные сигналы приводят к завершению процесса (например, `SIGCHLD` и `SIGURG` по умолчанию игнорируются).

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

139. Чем terminate/core/ignore/stop отличаются как default action?

   **Ответ:** `Terminate` — процесс завершается без сохранения отладочной информации. `Core` — процесс завершается и ядро сбрасывает образ его памяти в файл `core dump`. `Ignore` — ядро отбрасывает сигнал без последствий. `Stop` — выполнение процесса приостанавливается до сигнала продолжения.

   **Пример:**

   ```bash
   # Игнорируемый сигнал не прерывает работу:
   kill -SIGWINCH <pid>
   ```

   **Типичная ошибка:** Ожидать генерации файла отладки core dump при падении процесса от обычного `SIGTERM` (он завершает без дампа).

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

140. Что такое core dump и какие сигналы его вызывают?

   **Ответ:** Core dump — это снимок виртуальной памяти процесса, регистров CPU и стека вызовов на момент падения, сохраняемый на диск для посмертной отладки в GDB. Его вызывают сигналы: `SIGSEGV`, `SIGABRT`, `SIGFPE`, `SIGILL`, `SIGBUS`, `SIGQUIT` и `SIGSYS`.

   **Пример:**

   ```bash
   gdb ./my_app core.dump
   (gdb) bt # распечатать стек падения
   ```

   **Типичная ошибка:** Искать сгенерированный core dump, когда лимит на размер дампа отключен в системе (`ulimit -c 0`).

   **Источник:** [man7: core(5)](https://man7.org/linux/man-pages/man5/core.5.html)

141. Как посмотреть список сигналов в системе?

   **Ответ:** В командной оболочке через утилиту `kill -l`, либо программно, открыв заголовочный файл `<signal.h>` или документацию `man 7 signal`.

   **Пример:**

   ```bash
   kill -l
   # Выведет: 1) SIGHUP 2) SIGINT 3) SIGQUIT ... 64) SIGRTMAX
   ```

   **Типичная ошибка:** Полагаться на жестко захардкоженные числовые номера сигналов (кроме 1-15): номера сигналов реального времени могут варьироваться между платформами.

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

142. Что делает raise()?

   **Ответ:** Посылает указанный сигнал вызывающему потоку/процессу (в однопоточной программе эквивалентно `kill(getpid(), sig)`, в многопоточной — `pthread_kill(pthread_self(), sig)`).

   **Пример:**

   ```cpp
   #include <csignal>

   int main() {
       raise(SIGTRAP); // Программная точка останова для отладчика
       return 0;
   }
   ```

   **Типичная ошибка:** Путать `raise()` и `abort()`: `raise(SIGABRT)` вызовет пользовательский обработчик, но если он вернется, процесс не будет принудительно убит ядром, в отличие от функции `abort()`.

   **Источник:** [man7: raise(3)](https://man7.org/linux/man-pages/man3/raise.3.html)

143. Чем raise() отличается от kill()?

   **Ответ:** `raise()` адресует сигнал исключительно текущему потоку выполнения, не требуя знания PID. Системный вызов `kill()` может адресовать сигнал произвольному процессу, группе процессов или всем процессам в системе по их идентификаторам.

   **Пример:**

   ```cpp
   raise(SIGINT);            // Сигнал самому себе
   kill(target_pid, SIGINT); // Сигнал стороннему процессу
   ```

   **Типичная ошибка:** Использовать `kill(getpid(), sig)` в многопоточной программе вместо `raise()`, так как сигнал может быть перехвачен случайным другим потоком процесса.

   **Источник:** [man7: raise(3)](https://man7.org/linux/man-pages/man3/raise.3.html)

144. Как отправить сигнал конкретной process group?

   **Ответ:** Вызовом `kill(-pgid, sig)` с отрицательным значением идентификатора группы процессов. Сигнал будет доставлен всем процессам, входящим в эту группу.

   **Пример:**

   ```cpp
   #include <csignal>

   // Отправить SIGTERM всей группе процессов с PGID = 4321:
   kill(-4321, SIGTERM);
   ```

   **Типичная ошибка:** Передать случайно `kill(-1, sig)`, что приведет к отправке сигнала вообще всем процессам в системе, на которые у пользователя хватает прав, кроме `init`.

   **Источник:** [man7: kill(2)](https://man7.org/linux/man-pages/man2/kill.2.html)

145. Что происходит с системным вызовом, если пришел сигнал?

   **Ответ:** Если поток был заблокирован в медленном системном вызове (например, `read()`, `write()`, `wait()`), ядро прерывает этот системный вызов, запускает обработчик сигнала, а после его возврата системный вызов либо завершается ошибкой с кодом `-1` и `errno = EINTR`, либо автоматически перезапускается (при флаге `SA_RESTART`).

   **Пример:**

   ```text
   Поток спит в read() -> Сигнал -> Handler() -> read() возвращает -1 (EINTR)
   ```

   **Типичная ошибка:** Считать аварийным сбоем возврат вызовами `epoll_wait` или `read` значения `-1` с `errno == EINTR`.

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

146. Что такое EINTR?

   **Ответ:** Константа ошибки ядра Linux (`Interrupted function call`), означающая, что выполнявшийся системный вызов был принудительно прерван доставкой сигнала до того, как успел завершить операцию.

   **Пример:**

   ```cpp
   #include <cerrno>
   #include <unistd.h>

   ssize_t ret;
   do {
       ret = read(fd, buf, size);
   } while (ret == -1 && errno == EINTR); // Повторить при прерывании
   ```

   **Типичная ошибка:** Не обрабатывать `EINTR` в цикле вокруг системных вызовов ввода/вывода, что приводит к ложным сбоям сетевых и дисковых операций.

   **Источник:** [man7: errno(3)](https://man7.org/linux/man-pages/man3/errno.3.html)

147. Почему read()/wait() могут прерваться сигналом?

   **Ответ:** Это фундаментальный механизм проектирования Unix, позволяющий асинхронно будить потоки, уснувшие в блокирующих операциях ожидания событий или I/O, без необходимости насильно уничтожать весь процесс.

   **Пример:**

   ```cpp
   // read() из сокета прерывается, чтобы процесс отреагировал на SIGTERM
   read(sock_fd, buf, 1024);
   ```

   **Типичная ошибка:** Полагать, что вызов `read()` из обычного файла на локальном диске вернет `EINTR`. Дисковые операции с локальной FS обычно выполняются в `TASK_UNINTERRUPTIBLE` и не прерываются.

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

148. Что такое SA_RESTART?

   **Ответ:** Флаг в структуре `sigaction`, указывающий ядру автоматически перезапускать определенные прерванные системные вызовы (например, `read()`, `write()`, `wait()`) после завершения пользовательского обработчика сигнала вместо возврата ошибки `EINTR`.

   **Пример:**

   ```cpp
   struct sigaction sa{};
   sa.sa_handler = handler;
   sa.sa_flags = SA_RESTART;
   sigaction(SIGUSR1, &sa, nullptr);
   ```

   **Типичная ошибка:** Полагать, что `SA_RESTART` перезапускает любые вызовы: таймауты (`select`, `poll`, `epoll_wait`) и вызовы вроде `nanosleep()` никогда не перезапускаются автоматически и всегда возвращают `EINTR`.

   **Источник:** [man7: sigaction(2)](https://man7.org/linux/man-pages/man2/sigaction.2.html)

149. Как SIGTERM и SIGKILL влияют на graceful shutdown?

   **Ответ:** Оркестратор сначала посылает `SIGTERM`, запуская таймер ожидания (grace period). Приложение перехватывает сигнал, прекращает прием соединений и штатно сбрасывает состояние. Если процесс не завершился до истечения таймаута, система посылает жесткий `SIGKILL`, принудительно снимая зависший сервис.

   **Пример:**

   ```text
   Система -> SIGTERM -> Приложение освобождает сокеты и БД -> exit(0)
   [Если таймаут 30 сек превышен] -> Система посылает SIGKILL
   ```

   **Типичная ошибка:** Делать таймаут graceful shutdown в приложении больше, чем `TimeoutStopSec` в systemd или `terminationGracePeriodSeconds` в Kubernetes.

   **Источник:** [man7: systemd.service(5)](https://man7.org/linux/man-pages/man5/systemd.service.5.html)

150. Почему знание сигналов важно для C/C++ сервисов?

   **Ответ:** Без понимания сигналов невозможно реализовать корректный production-сервер: игнорирование `SIGPIPE` предотвращает краш при разрыве сокетов клиентами, обработка `SIGTERM`/`SIGINT` обеспечивает целостность данных при перезапусках, сбор `SIGCHLD` предотвращает утечку ресурсов зомби-процессами, а понимание `async-signal-safety` защищает от скрытых deadlocks.

   **Пример:**

   ```cpp
   #include <csignal>

   // Обязательная строчка для любого сетевого демона на C/C++:
   signal(SIGPIPE, SIG_IGN);
   ```

   **Типичная ошибка:** Игнорирование сигнала `SIGPIPE`: сервер мгновенно аварийно завершается при попытке записи в сокет, который был закрыт удаленной стороной.

   **Источник:** [man7: signal-safety(7)](https://man7.org/linux/man-pages/man7/signal-safety.7.html)

### Monitoring: ps, top, htop

151. Что показывает команда ps?

   **Ответ:** Выводит снимок (snapshot) текущих активных процессов в системе, их идентификаторы (PID), терминалы, статус выполнения, потребление ресурсов и исполняемые команды.

   **Пример:**

   ```bash
   ps

   ```

   **Типичная ошибка:** Полагать, что `ps` обновляет данные в реальном времени (он фиксирует состояние строго на момент вызова).

   **Источник:** [man7: ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)

152. Чем ps aux отличается от ps -ef?

   **Ответ:** Различием в синтаксисе и наборе полей. `ps aux` использует BSD-стиль (без дефиса) и отображает `%CPU`, `%MEM`, `VSZ`, `RSS` и `STAT`. `ps -ef` использует стандартный POSIX/UNIX-стиль (с дефисом) и показывает `UID`, `PID`, `PPID`, `C`, `STIME`, `TTY`, `TIME`, `CMD`.

   **Пример:**

   ```bash
   ps aux | head -n 5
   ps -ef | head -n 5

   ```

   **Типичная ошибка:** Смешивать стили (например, вызывать `ps -aux`), что выводит предупреждение о смене парсинга параметров.

   **Источник:** [man7: ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)

153. Как найти процесс по имени через ps?

   **Ответ:** Скомбинировать `ps` с `grep` или использовать специализированную утилиту `pgrep` / `pidof`.

   **Пример:**

   ```bash
   ps aux | grep '[m]y_service'
   # или
   pgrep -a my_service

   ```

   **Типичная ошибка:** Вызывать `ps aux | grep my_service` без трюка с квадратными скобками `[m]`, из-за чего в вывод попадает сам процесс команды `grep`.

   **Источник:** [man7: pgrep(1)](https://man7.org/linux/man-pages/man1/pgrep.1.html)

154. Что показывает столбец PID?

   **Ответ:** Уникальный числовой идентификатор процесса (Process ID) в текущем пространстве имен (`PID namespace`).

   **Пример:**

   ```bash
   ps -o pid,comm

   ```

   **Типичная ошибка:** Полагаться на постоянство PID между перезапусками процесса или всей ОС.

   **Источник:** [man7: ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)

155. Что показывает столбец PPID?

   **Ответ:** Идентификатор родительского процесса (Parent Process ID), который создал данный процесс с помощью системного вызова `fork()`.

   **Пример:**

   ```bash
   ps -o pid,ppid,cmd

   ```

   **Типичная ошибка:** Считать, что `PPID` никогда не меняется (при завершении родителя он заменяется на `PID` субреапера или `init`).

   **Источник:** [man7: ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)

156. Что показывает столбец STAT?

   **Ответ:** Текущее состояние процесса в виде одно- или многобуквенного кода: базовое состояние ядра (`R`, `S`, `D`, `T`, `Z`) плюс модификаторы (`<` — высокий приоритет, `N` — низкий приоритет, `s` — лидер сессии, `+` — foreground process group).

   **Пример:**

   ```bash
   ps -o pid,stat,comm
   # Пример вывода: Ss, R+, Sl

   ```

   **Типичная ошибка:** Игнорировать суффиксы (например, букву `l`, которая означает, что процесс является многопоточным).

   **Источник:** [man7: ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)

157. Что означает Z в STAT?

   **Ответ:** Состояние зомби (`EXIT_ZOMBIE`): процесс завершился, освободил память и ресурсы, но запись в таблице ядра удерживается до вызова `wait()` родителем.

   **Пример:**

   ```text
   PID  STAT COMMAND
   1234 Z    [app] <defunct>

   ```

   **Типичная ошибка:** Пытаться освободить зомби отправкой `kill -9` на его PID.

   **Источник:** [man7: ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)

158. Что означает S в STAT?

   **Ответ:** Прерываемый сон (`TASK_INTERRUPTIBLE`): процесс ожидает события, таймера или завершения I/O, но может быть немедленно разбужен поступлением сигнала.

   **Пример:**

   ```bash
   # Большинство фоновых демонов находятся в состоянии S
   ps -C sshd -o pid,stat,cmd

   ```

   **Типичная ошибка:** Считать состояние `S` зависанием или аварией программы.

   **Источник:** [man7: ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)

159. Что означает R в STAT?

   **Ответ:** Процесс находится в состоянии выполнения (`TASK_RUNNING`): он либо в данный момент исполняется ядром CPU, либо находится в очереди планировщика (`runqueue`), готовый к исполнению.

   **Пример:**

   ```bash
   ps aux | awk '$8 ~ /R/'

   ```

   **Типичная ошибка:** Предполагать, что процесс `R` на 100% владеет CPU и никогда не вытесняется планировщиком.

   **Источник:** [man7: sched(7)](https://man7.org/linux/man-pages/man7/sched.7.html)

160. Что означает D в STAT?

   **Ответ:** Непрерываемый сон (`TASK_UNINTERRUPTIBLE`): процесс ожидает завершения дисковой или сетевой операции ядра (например, NFS, flush на диск) и не может быть прерван никакими сигналами, включая `SIGKILL`.

   **Пример:**

   ```bash
   ps -eo pid,stat,wchan:20,cmd | grep ' D'

   ```

   **Типичная ошибка:** Использовать автоматические скрипты перезапуска, которые зацикливаются при попытке убить `D`-процесс по `kill -9`.

   **Источник:** [man7: ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)

161. Что означает T в STAT?

   **Ответ:** Процесс остановлен (`TASK_STOPPED` или `TASK_TRACED`) либо сигналом управления заданиями (`SIGSTOP`, `SIGTSTP` по `Ctrl+Z`), либо отладчиком через `ptrace`.

   **Пример:**

   ```bash
   # Перевод в stopped и обратно:
   kill -STOP <PID>
   kill -CONT <PID>

   ```

   **Типичная ошибка:** Считать, что остановленный процесс выгружен из оперативной памяти.

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

162. Что показывает столбец %CPU?

   **Ответ:** Долю времени центрального процессора, использованную процессом с момента последнего обновления или за все время жизни процесса, выраженную в процентах от мощности одного логического ядра CPU.

   **Пример:**

   ```bash
   ps -eo pid,%cpu,comm --sort=-%cpu | head -n 5

   ```

   **Типичная ошибка:** Не учитывать, что в многопоточных процессах на многоядерных машинах значение `%CPU` может превышать 100% (например, 400% на 4 ядрах).

   **Источник:** [man7: ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)

163. Что показывает столбец %MEM?

   **Ответ:** Процент физической оперативной памяти (RAM) машины, занятый резидентным набором страниц (`RSS`) данного процесса.

   **Пример:**

   ```bash
   ps -eo pid,%mem,rss,comm --sort=-%mem | head -n 5

   ```

   **Типичная ошибка:** Суммировать `%MEM` всех процессов для вычисления общей занятой памяти (разделяемые библиотеки `shared memory` посчитаются многократно).

   **Источник:** [man7: ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)

164. Что показывает столбец VSZ?

   **Ответ:** Virtual Memory Size — общий объем виртуального адресного пространства (в КиБ), выделенный процессу, включая код, данные, кучу, стек, загруженные `.so`-библиотеки и неаллоцированные физически страницы `mmap`.

   **Пример:**

   ```bash
   ps -o pid,vsz,rss,comm -p <PID>

   ```

   **Типичная ошибка:** Считать `VSZ` реальным потреблением оперативной памяти (процесс может замаппить пустой файл на 1 ТБ и иметь `VSZ` 1 ТБ при `RSS` в пару мегабайт).

   **Источник:** [man7: ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)

165. Что показывает столбец RSS?

   **Ответ:** Resident Set Size — объем физической оперативной памяти (RAM) в КиБ, который процесс фактически удерживает в данный момент времени.

   **Пример:**

   ```bash
   ps -o pid,rss,comm -p <PID>

   ```

   **Типичная ошибка:** Полагать, что освобождение процесса вернет системе ровно объем `RSS` (часть `RSS` может приходиться на разделяемые библиотеки, используемые другими процессами).

   **Источник:** [man7: ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)

166. Чем VSZ отличается от RSS?

   **Ответ:** `VSZ` — это объем адресованного виртуального пространства (обещанная память), а `RSS` — объем реально выделенных и отображенных в физические чипы памяти страниц (реально потребляемая память).

   **Пример:**

   ```text
   mmap(NULL, 1GB, ...); // VSZ вырастет на 1 ГБ сразу
   // До записи в память RSS не изменится!

   ```

   **Типичная ошибка:** Оценивать утечку памяти исключительно по росту `VSZ`, игнорируя динамику `RSS`.

   **Источник:** [man7: ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)

167. Как через ps посмотреть дерево процессов?

   **Ответ:** Передать опции `--forest` (для стиля GNU/Linux) или `-H` / `f` (для вывода иерархических отступов).

   **Пример:**

   ```bash
   ps -ejH
   ps axjf
   ps aux --forest

   ```

   **Типичная ошибка:** Использовать базовый `ps aux` и вручную сопоставлять пары `PID`-`PPID`.

   **Источник:** [man7: ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)

168. Что делает pstree?

   **Ответ:** Отображает дерево запущенных процессов в виде наглядной ASCII-графики, группируя одноименные процессы и показывая их отношения предок-потомок.

   **Пример:**

   ```bash
   pstree -p -s <PID>

   ```

   **Типичная ошибка:** Забывать ключ `-p`, скрывающий числовые PID процессов в дереве.

   **Источник:** [man7: pstree(1)](https://man7.org/linux/man-pages/man1/pstree.1.html)

169. Что показывает top?

   **Ответ:** Интерактивный системный монитор, динамически обновляющий список процессов, общую загрузку CPU (по ядрам и режимам), статистику RAM/Swap и значения Load Average в реальном времени.

   **Пример:**

   ```bash
   top -d 1

   ```

   **Типичная ошибка:** Оценивать мгновенные кратковременные пики как устойчивую проблему производительности.

   **Источник:** [man7: top(1)](https://man7.org/linux/man-pages/man1/top.1.html)

170. Чем top полезен при диагностике CPU-bound процессов?

   **Ответ:** Позволяет отсортировать процессы по потреблению CPU (клавиша `P`), выявить процессы, утилизирующие 100% ядра, и различить вычисления в пользовательском пространстве (`us`) от системных оверхедов ядра (`sy`).

   **Пример:**

   ```bash
   # Запуск с сортировкой по CPU:
   top -o %CPU

   ```

   **Типичная ошибка:** Не переключать режим отображения отдельных ядер CPU (клавиша `1`), маскируя 100% нагрузку одного ядра низкой средней загрузкой по всей системе.

   **Источник:** [man7: top(1)](https://man7.org/linux/man-pages/man1/top.1.html)

171. Чем top полезен при диагностике memory leaks?

   **Ответ:** Позволяет отсортировать процессы по использованию памяти (клавиша `M`) и наблюдать за монотонным ростом столбцов `RES` (RSS) и `VIRT` (VSZ) в течение времени под постоянной нагрузкой.

   **Пример:**

   ```bash
   top -o %MEM

   ```

   **Типичная ошибка:** Принимать первоначальный рост пула аллокатора C++ за утечку памяти (необходимо отслеживать стабилизацию потребления).

   **Источник:** [man7: top(1)](https://man7.org/linux/man-pages/man1/top.1.html)

172. Что означает load average в top?

   **Ответ:** Среднее количество процессов, находившихся в состояниях готовности к вычислению (`TASK_RUNNING`) и непрерываемого ожидания I/O (`TASK_UNINTERRUPTIBLE`), усредненное за последние 1, 5 и 15 минут.

   **Пример:**

   ```text
   load average: 2.50, 1.75, 1.10

   ```

   **Типичная ошибка:** Считать Load Average прямым процентом загрузки CPU (значение может быть намного выше числа ядер при блокировках на диске).

   **Источник:** [man7: uptime(1)](https://man7.org/linux/man-pages/man1/uptime.1.html)

173. Как интерпретировать load average?

   **Ответ:** Значение сопоставляют с количеством логических ядер CPU (`nproc`). Если Load Average равен числу ядер — система утилизирована полностью без очередей. Если он стабильно выше числа ядер — процессы простаивают в очереди за CPU или заблокированы быстрым I/O.

   **Пример:**

   ```bash
   # Если nproc == 4, а LA == 8.0:
   # В среднем 4 процесса активно ждут очереди на исполнение/диск
   nproc

   ```

   **Типичная ошибка:** Паниковать при кратковременном всплеске 1-минутного значения при стабильно низких 5- и 15-минутных показателях.

   **Источник:** [man7: uptime(1)](https://man7.org/linux/man-pages/man1/uptime.1.html)

174. Что означает us/sy/id/wa в top?

   **Ответ:** Процентные метрики времени процессора: `us` (user) — выполнение пользовательского кода, `sy` (system) — системные вызовы ядра, `id` (idle) — простой процессора, `wa` (iowait) — простой в ожидании ответа от дисковой подсистемы.

   **Пример:**

   ```text
   %Cpu(s): 12.5 us,  3.2 sy,  0.0 ni, 82.0 id,  1.8 wa

   ```

   **Типичная ошибка:** Искать ошибки в коде C++ при высоком показателе `sy` (высокий `sy` указывает на частые системные вызовы, переключения контекста или неэффективную работу драйверов).

   **Источник:** [man7: top(1)](https://man7.org/linux/man-pages/man1/top.1.html)

175. Что такое wa (iowait)?

   **Ответ:** Время, в течение которого ядра CPU бездействовали (`idle`), но при этом в системе имелся хотя бы один незавершенный запрос к устройствам ввода/вывода (диск, медленный сетевой диск NFS).

   **Пример:**

   ```text
   %Cpu(s):  1.0 us,  0.5 sy,  0.0 ni, 30.0 id, 68.5 wa
   # Ядра простаивают, уперевшись в скорость диска

   ```

   **Типичная ошибка:** Считать `wa` признаком нехватки мощности CPU (причина в низкой производительности или перегрузке дисков).

   **Источник:** [man7: top(1)](https://man7.org/linux/man-pages/man1/top.1.html)

176. Как понять, что процесс упирается в CPU?

   **Ответ:** Значение `%CPU` процесса приближается к `100% * N` (где N — число активных потоков), в шапке монитора параметр `us` высокий при околонулевом `wa`, а профилировщик показывает высокую плотность вычислительных инструкций.

   **Пример:**

   ```bash
   pidstat -u 1 -p <PID>

   ```

   **Типичная ошибка:** Не проверять частоту переключения контекстов (`voluntary vs non-voluntary context switches`) через `pidstat -w`.

   **Источник:** [man7: pidstat(1)](https://man7.org/linux/man-pages/man1/pidstat.1.html)

177. Как понять, что процесс упирается в I/O?

   **Ответ:** Процесс проводит много времени в состоянии `D`, в строке CPU высокий процент `wa`, потребление `%CPU` процессом низкое, а утилита `iotop` или `iostat` фиксирует высокую дисковую утилизацию (`%util` около 100%).

   **Пример:**

   ```bash
   iotop -p <PID>
   iostat -xz 1

   ```

   **Типичная ошибка:** Пытаться оптимизировать вычислительные алгоритмы C++, когда программа деградирует из-за синхронного логирования на медленный HDD.

   **Источник:** [man7: iotop(8)](https://man7.org/linux/man-pages/man8/iotop.8.html)

178. Что показывает htop?

   **Ответ:** Интерактивный консольный монитор процессов с цветным псевдографическим интерфейсом, горизонтальными шкалами нагрузки ядер CPU, памяти, swap, поддержкой мыши, удобным поиском, фильтрацией и возможностью посылать сигналы процессам без ввода PID вручную.

   **Пример:**

   ```bash
   htop

   ```

   **Типичная ошибка:** Считать `htop` частью стандартной минимальной установки сервера (в отличие от `top`, его часто требуется ставить отдельно).

   **Источник:** [man7: htop(1)](https://man7.org/linux/man-pages/man1/htop.1.html)

179. Чем htop удобнее top?

   **Ответ:** Позволяет выполнять вертикальную и горизонтальную прокрутку командных строк, отображает древовидную структуру нажатием одной клавиши (`F5`), дает возможность фильтровать процессы по подстроке (`F4`) и интерактивно менять `nice` или слать сигналы через меню (`F7/F8/F9`).

   **Пример:**

   ```bash
   # Интерактивное управление через функциональные клавиши:
   # F3: Поиск, F4: Фильтр, F5: Дерево, F9: Kill

   ```

   **Типичная ошибка:** Забывать переключать отображение потоков в настройках (чтобы не путать потоки процесса с отдельными процессами).

   **Источник:** [man7: htop(1)](https://man7.org/linux/man-pages/man1/htop.1.html)

180. Можно ли из htop послать сигнал процессу?

   **Ответ:** Да. Достаточно выбрать строку процесса курсором, нажать клавишу `F9` (Kill) и выбрать нужный сигнал из открывшегося списка (например, `SIGTERM`, `SIGKILL`, `SIGHUP`).

   **Пример:**

   ```text
   Выделяем процесс -> F9 -> 15 (SIGTERM) -> Enter

   ```

   **Типичная ошибка:** Случайно отправить `SIGKILL` вместо `SIGTERM` по умолчанию при быстром нажатии клавиш.

   **Источник:** [man7: htop(1)](https://man7.org/linux/man-pages/man1/htop.1.html)

181. Как в htop увидеть дерево процессов?

   **Ответ:** Нажатием функциональной клавиши `F5` (Tree View). Повторное нажатие возвращает обычный плоский список процессов.

   **Пример:**

   ```text
   Запустить htop -> нажать F5

   ```

   **Типичная ошибка:** Искать родительские зависимости в плоском списке вместо включения режима дерева.

   **Источник:** [man7: htop(1)](https://man7.org/linux/man-pages/man1/htop.1.html)

182. Как посмотреть потоки процесса в top/htop?

   **Ответ:** В `top` нажать комбинацию клавиш `Shift + H` (переключатель режимов Process/Thread), либо запустить `top -H -p <PID>`. В `htop` нажать `Shift + H` для скрытия/отображения пользовательских потоков.

   **Пример:**

   ```bash
   top -H -p $(pgrep my_cpp_app)

   ```

   **Типичная ошибка:** Путать число процессов в системе с числом потоков при включенном режиме отображения потоков.

   **Источник:** [man7: top(1)](https://man7.org/linux/man-pages/man1/top.1.html)

183. Что делает ps -L?

   **Ответ:** Выводит список потоков (LWP — Light Weight Process) внутри процессов с отображением их идентификаторов `LWP` (TID) и общего количества потоков `NLWP`.

   **Пример:**

   ```bash
   ps -L -p <PID>

   ```

   **Типичная ошибка:** Считать, что `PID` и `LWP` всегда различаются: для главного потока процесса значение `LWP` равно значению `PID`.

   **Источник:** [man7: ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)

184. Как узнать, сколько потоков у процесса?

   **Ответ:** Прочитать поле `Threads:` в файле `/proc/<PID>/status`, посчитать количество записей в директории `/proc/<PID>/task/` или вызвать `ps -o nlwp -p <PID>`.

   **Пример:**

   ```bash
   grep Threads /proc/<PID>/status
   # или
   ls /proc/<PID>/task | wc -l

   ```

   **Типичная ошибка:** Оценивать число потоков по выводу обычного `ps aux`, где процесс отображается одной строкой.

   **Источник:** [man7: proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html)

185. Как посмотреть open file descriptors процесса?

   **Ответ:** Просмотреть список символических ссылок в псевдофайловой системе `/proc/<PID>/fd/` или воспользоваться утилитой `lsof -p <PID>`.

   **Пример:**

   ```bash
   ls -la /proc/<PID>/fd
   lsof -p <PID>

   ```

   **Типичная ошибка:** Забывать проверять права доступа (для просмотра дескрипторов чужого процесса требуются права суперпользователя или `CAP_SYS_PTRACE`).

   **Источник:** [man7: lsof(8)](https://man7.org/linux/man-pages/man8/lsof.8.html)

186. Как посмотреть usage памяти процесса через /proc?

   **Ответ:** Проверить сводку в `/proc/<PID>/status` (поля `VmSize`, `VmRSS`, `VmData`), детальную карту аллокаций в `/proc/<PID>/maps` или подробную разбивку по страницам памяти в `/proc/<PID>/smaps`.

   **Пример:**

   ```bash
   grep -E 'VmSize|VmRSS|VmSwap' /proc/<PID>/status

   ```

   **Типичная ошибка:** Читать огромный файл `smaps` высоконагруженного сервиса с миллионами страниц памяти в частом цикле мониторинга, вызывая задержки на уровне ядра.

   **Источник:** [man7: proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html)

187. Что можно увидеть в /proc/<pid>/status?

   **Ответ:** Читаемый текстовый статус: имя исполняемого файла (`Name`), состояние (`State`), PID/PPID/TGID, реальные и эффективные UID/GID, лимиты масок сигналов (`SigBlk`, `SigIgn`), детальное использование памяти (`VmPeak`, `VmRSS`, `VmHWM`) и количество потоков (`Threads`).

   **Пример:**

   ```bash
   cat /proc/self/status | head -n 10

   ```

   **Типичная ошибка:** Писать сложные регулярные выражения для парсинга, когда большинство метрик можно получить напрямую по префиксу строки.

   **Источник:** [man7: proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html)

188. Что можно увидеть в /proc/<pid>/stat?

   **Ответ:** Однострочный массив числовых метрик (более 50 полей), оптимизированный для быстрого чтения утилитами мониторинга: тики CPU в user- и kernel-пространстве (`utime`, `stime`), приоритет, nice, время старта процесса с момента загрузки ОС.

   **Пример:**

   ```bash
   cat /proc/self/stat

   ```

   **Типичная ошибка:** Парсить `/proc/<PID>/stat` простым разбиением по пробелам (имя программы во втором поле `comm` заключено в скобки и само может содержать пробелы).

   **Источник:** [man7: proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html)

189. Как мониторить процесс в реальном времени?

   **Ответ:** Использовать утилиту `pidstat` из пакета `sysstat`, запускать `top` с фильтрацией по конкретному PID (`top -p <PID>`), либо отслеживать системные вызовы через `strace -p <PID>`.

   **Пример:**

   ```bash
   pidstat -r -u 1 -p <PID>

   ```

   **Типичная ошибка:** Запускать `strace` на production-сервере с высокой сетевой нагрузкой (накладные расходы `strace` могут замедлить процесс на порядок).

   **Источник:** [man7: pidstat(1)](https://man7.org/linux/man-pages/man1/pidstat.1.html)

190. Какие инструменты полезны вместе с ps/top/htop для системного программиста?

   **Ответ:** `perf` (профилирование CPU и кэш-промахов), `strace` (трассировка системных вызовов), `lsof` (открытые дескрипторы и сокеты), `iotop` (нагрузка на диск), `vmstat` (память и swap), `bpftrace`/`eBPF` (динамическая низкоуровневая трассировка ядра).

   **Пример:**

   ```bash
   perf top -p <PID>

   ```

   **Типичная ошибка:** Ограничиваться только `top`, не используя профилировщики ядра при расследовании узких мест производительности.

   **Источник:** [man7: perf(1)](https://man7.org/linux/man-pages/man1/perf.1.html)

### nice / renice

191. Что такое nice value?

   **Ответ:** Целочисленный пользовательский атрибут процесса, определяющий его «вежливость» по отношению к другим процессам при распределении процессорного времени стандартным планировщиком ОС (CFS).

   **Пример:**

   ```bash
   nice -n 10 ./my_background_task

   ```

   **Типичная ошибка:** Путать показатель `nice` с аппаратным приоритетом прерываний или планированием реального времени.

   **Источник:** [man7: nice(1)](https://man7.org/linux/man-pages/man1/nice.1.html)

192. Как nice влияет на планирование процесса?

   **Ответ:** Планировщик Linux (Completely Fair Scheduler, CFS) рассчитывает динамический вес процесса на основе его `nice`. Процесс с меньшим значением `nice` получает больший вес, быстрее накапливает виртуальное время исполнения (`vruntime`) и получает больше квантов CPU.

   **Пример:**

   ```text
   Разница в 5 единиц nice меняет долю CPU примерно в 3 раза при конкуренции

   ```

   **Типичная ошибка:** Полагать, что процесс с высоким `nice` вообще не будет выполняться, если есть другие процессы (CFS гарантирует отсутствие полного голодания).

   **Источник:** [man7: sched(7)](https://man7.org/linux/man-pages/man7/sched.7.html)

193. Какой диапазон nice в Linux?

   **Ответ:** От `-20` (наивысший приоритет, наименьшая «вежливость») до `+19` (наинизший приоритет, максимальная «вежливость»). Значение по умолчанию для новых процессов равно `0`.

   **Пример:**

   ```bash
   # Значения от -20 до 19
   nice -n -20 ./critical_task # максимальный приоритет
   nice -n 19 ./idle_task      # минимальный приоритет

   ```

   **Типичная ошибка:** Считать, что максимальный приоритет задается числом `+20`.

   **Источник:** [man7: getpriority(2)](https://man7.org/linux/man-pages/man2/getpriority.2.html)

194. Что означает меньший nice?

   **Ответ:** Меньшее (или отрицательное) значение означает повышенный приоритет процесса: планировщик выделяет ему больше процессорного времени по сравнению с другими процессами при наличии конкуренции за CPU.

   **Пример:**

   ```bash
   nice -n -5 ./heavy_worker

   ```

   **Типичная ошибка:** Путать полярность шкалы: меньшее число = больше приоритет.

   **Источник:** [man7: nice(1)](https://man7.org/linux/man-pages/man1/nice.1.html)

195. Что означает больший nice?

   **Ответ:** Большее положительное значение означает пониженный приоритет: процесс уступает процессорное время другим задачам и потребляет CPU преимущественно тогда, когда система свободна.

   **Пример:**

   ```bash
   nice -n 19 tar -czf backup.tar.gz /data

   ```

   **Типичная ошибка:** Считать, что процесс с `nice = 19` будет работать медленно на абсолютно свободной машине (при отсутствии конкурентов он заберет 100% CPU).

   **Источник:** [man7: nice(1)](https://man7.org/linux/man-pages/man1/nice.1.html)

196. Что такое приоритет процесса с точки зрения scheduler?

   **Ответ:** Внутреннее числовое значение в планировщике ядра (столбец `PR` в `top`), определяющее позицию процесса в очереди планирования в данный момент. Для стандартных задач диапазон составляет от 0 до 39 (отображается как 20 + nice).

   **Пример:**

   ```text
   nice = 0  => PR = 20
   nice = -5 => PR = 15
   nice = 10 => PR = 30

   ```

   **Типичная ошибка:** Пытаться напрямую записать системный `PR` через пользовательские API без использования `nice` или политик `sched_setscheduler`.

   **Источник:** [man7: sched(7)](https://man7.org/linux/man-pages/man7/sched.7.html)

197. Чем priority отличается от nice conceptually?

   **Ответ:** `nice` — это статическая пользовательская настройка веса процесса, передаваемая в ядро. Приоритет (`priority`) — это динамическая величина, вычисляемая планировщиком ядра на основе `nice`, истории ввода/вывода и типа планирования.

   **Пример:**

   ```text
   Пользователь настраивает: nice (-20..19)
   Ядро оперирует: priority

   ```

   **Типичная ошибка:** Считать их синонимами в контексте системных вызовов Linux.

   **Источник:** [man7: sched(7)](https://man7.org/linux/man-pages/man7/sched.7.html)

198. Кто может понижать nice value в сторону более высокого приоритета?

   **Ответ:** Только суперпользователь `root` или процессы, обладающие специальной привилегией ядра `CAP_SYS_NICE`. Обычный пользователь может только повышать `nice` (делать процесс более вежливым).

   **Пример:**

   ```bash
   sudo renice -n -5 -p <PID>

   ```

   **Типичная ошибка:** Попытка обычного пользователя выставить отрицательный `nice`, что приведет к ошибке `Permission denied`.

   **Источник:** [man7: capabilities(7)](https://man7.org/linux/man-pages/man7/capabilities.7.html)

199. Что делает команда nice?

   **Ответ:** Запускает новую указанную программу с модифицированным значением «вежливости» (`nice value`).

   **Пример:**

   ```bash
   nice -n 10 ./my_script.sh

   ```

   **Типичная ошибка:** Пытаться применить утилиту `nice` к уже выполняющемуся процессу (для существующих процессов используется `renice`).

   **Источник:** [man7: nice(1)](https://man7.org/linux/man-pages/man1/nice.1.html)

200. Как запустить программу с другим nice?

   **Ответ:** Использовать префикс `nice -n <значение>` перед командой запуска.

   **Пример:**

   ```bash
   nice -n 15 ./batch_processor
   sudo nice -n -10 ./latency_sensitive_service

   ```

   **Типичная ошибка:** Синтаксис `nice -10 cmd`, который в старых утилитах означал значение `-10`, а в современных парсится как `-n 10`. Рекомендуется всегда явно писать `-n`.

   **Источник:** [man7: nice(1)](https://man7.org/linux/man-pages/man1/nice.1.html)

201. Что делает renice?

   **Ответ:** Изменяет значение `nice` одного или нескольких уже выполняющихся процессов, групп процессов или процессов определенного пользователя на лету.

   **Пример:**

   ```bash
   renice -n 5 -p 1234

   ```

   **Типичная ошибка:** Менять приоритет без проверки прав, получая отказ при попытке улучшить приоритет процесса.

   **Источник:** [man7: renice(1)](https://man7.org/linux/man-pages/man1/renice.1.html)

202. Как изменить nice уже работающего процесса?

   **Ответ:** Вызвать утилиту `renice` с указанием нового значения и целевого PID, либо программно вызвать функцию `setpriority(PRIO_PROCESS, pid, new_nice)`.

   **Пример:**

   ```cpp
   #include <sys/resource.h>

   setpriority(PRIO_PROCESS, 0, 5); // Понизить приоритет текущего процесса

   ```

   **Типичная ошибка:** Забывать, что системный вызов `setpriority` возвращает `-1` и при успехе, если новый `nice` равен `-1` (требуется предварительно сбрасывать `errno = 0`).

   **Источник:** [man7: setpriority(2)](https://man7.org/linux/man-pages/man2/setpriority.2.html)

203. Может ли обычный пользователь увеличить приоритет процесса?

   **Ответ:** По умолчанию — нет. Обычный пользователь может только уменьшать приоритет (увеличивать значение `nice`), если в `/etc/security/limits.conf` не выставлен специальный лимит `nice` (`RLIMIT_NICE`).

   **Пример:**

   ```bash
   renice -n -1 -p 1234
   # renice: failed to set priority: Permission denied

   ```

   **Типичная ошибка:** Считать, что пользователь может вернуть приоритет обратно на `0` после того, как сам добровольно увеличил `nice` до `10`.

   **Источник:** [man7: setpriority(2)](https://man7.org/linux/man-pages/man2/setpriority.2.html)

204. Почему отрицательные nice требуют привилегий?

   **Ответ:** Отрицательный `nice` позволяет монополизировать ядра CPU в ущерб другим задачам. Непривилегированный пользователь мог бы создать DoS-состояние для всей системы, заблокировав выполнение критических системных демонов.

   **Пример:**

   ```text
   Процесс с nice -20 забирает почти все кванты CPU у процессов с nice 0

   ```

   **Типичная ошибка:** Выдача полного `sudo` разработчикам исключительно ради запуска сервисов с высоким приоритетом вместо настройки `CAP_SYS_NICE`.

   **Источник:** [man7: capabilities(7)](https://man7.org/linux/man-pages/man7/capabilities.7.html)

205. Когда имеет смысл повышать priority процесса?

   **Ответ:** Для сервисов, критичных к задержкам отклика (latency-sensitive): аудиотракты в реальном времени, высокочастотные сетевые шлюзы, брокеры сообщений или UI-композиторы, где пропуск такта приводит к визуальным рывкам или потере сетевых пакетов.

   **Пример:**

   ```bash
   sudo renice -n -10 -p $(pgrep audio_engine)

   ```

   **Типичная ошибка:** Повышать приоритет плохо оптимизированного процесса с утечками ресурсов, усугубляя деградацию всей системы.

   **Источник:** [man7: sched(7)](https://man7.org/linux/man-pages/man7/sched.7.html)

206. Когда имеет смысл понижать priority процесса?

   **Ответ:** Для фоновых длительных вычислений (batch jobs): сбор логов, индексация поиска, сжатие бэкапов, кодирование видео, сборка пакетов компилятором в фоновом режиме.

   **Пример:**

   ```bash
   nice -n 19 find / -name "*.tmp" -delete

   ```

   **Типичная ошибка:** Запуск фоновых утилит бэкапа без повышенного `nice`, вызывающий проседание RPS боевого веб-сервера на том же сервере.

   **Источник:** [man7: nice(1)](https://man7.org/linux/man-pages/man1/nice.1.html)

207. Почему CPU-intensive batch job часто запускают с повышенным nice?

   **Ответ:** Чтобы такие пакетные задачи потребляли только свободные ресурсы процессора, не вытесняя интерактивные сетевые демоны и сессии администраторов.

   **Пример:**

   ```bash
   nice -n 15 ffmpeg -i input.mov output.mp4

   ```

   **Типичная ошибка:** Полагать, что повышенный `nice` ограничивает скорость дискового ввода-вывода (для I/O требуется настраивать `ionice`).

   **Источник:** [man7: nice(1)](https://man7.org/linux/man-pages/man1/nice.1.html)

208. Как nice влияет на interactive responsiveness системы?

   **Ответ:** Запуск ресурсоемких задач с высоким `nice` высвобождает кванты времени CPU для UI и SSH-терминалов, предотвращая подвисания пользовательского интерфейса при пиковых фоновых вычислениях.

   **Пример:**

   ```bash
   nice -n 19 make -j$(nproc)

   ```

   **Типичная ошибка:** Компиляция крупного C++ проекта в 64 потока без `nice`, приводящая к полной потере отзывчивости оболочки.

   **Источник:** [man7: sched(7)](https://man7.org/linux/man-pages/man7/sched.7.html)

209. Влияет ли nice на I/O priority напрямую?

   **Ответ:** В классическом планировщике I/O `BFQ` (или устаревшем `CFQ`) значение `nice` автоматически транслируется в соответствующий класс ввода-вывода. Однако в современных блочных планировщиках (таких как `none`, `mq-deadline`, `kyber`) прямого влияния нет.

   **Пример:**

   ```bash
   # Для строгого контроля дискового I/O используют ionice:
   ionice -c 3 ./disk_heavy_task

   ```

   **Типичная ошибка:** Рассчитывать, что `nice 19` предотвратит исчерпание IOPS на быстрых NVMe накопителях.

   **Источник:** [man7: ionice(1)](https://man7.org/linux/man-pages/man1/ionice.1.html)

210. Что такое ionice?

   **Ответ:** Утилита и системный вызов для установки класса и приоритета планирования ввода-вывода (I/O scheduling class) для обращений процесса к дисковой подсистеме.

   **Пример:**

   ```bash
   ionice -c 2 -n 7 -p <PID> # Best-effort, низкий приоритет

   ```

   **Типичная ошибка:** Использовать `ionice` на дисковых контроллерах с планировщиками, не поддерживающими классы приоритетов (например, `none` на NVMe).

   **Источник:** [man7: ionice(1)](https://man7.org/linux/man-pages/man1/ionice.1.html)

211. Чем ionice отличается от nice?

   **Ответ:** `nice` управляет распределением циклов центрального процессора (`CPU scheduling`), а `ionice` управляет очередью запросов к контроллеру диска (`Block I/O scheduling`).

   **Пример:**

   ```text
   nice:   конкуренция за арифметику ядер CPU
   ionice: конкуренция за полосу пропускания диска/SSD

   ```

   **Типичная ошибка:** Пытаться ускорить застрявший на чтении диска процесс повышением его CPU `nice`.

   **Источник:** [man7: ionice(1)](https://man7.org/linux/man-pages/man1/ionice.1.html)

212. Влияет ли nice на real-time процессы?

   **Ответ:** Нет, абсолютно не влияет. Процессы с политиками реального времени (`SCHED_FIFO`, `SCHED_RR`) имеют абсолютный приоритет над любыми стандартными задачами (`SCHED_OTHER`), и планировщик игнорирует значение `nice` для RT-потоков.

   **Пример:**

   ```bash
   chrt -f -p 50 <PID> # Перевод в SCHED_FIFO с приоритетом 50 (nice не учитывается)

   ```

   **Типичная ошибка:** Попытка оптимизировать поведение RT-аудиопотоков через `renice`.

   **Источник:** [man7: sched(7)](https://man7.org/linux/man-pages/man7/sched.7.html)

213. Почему real-time scheduling — отдельная тема от nice?

   **Ответ:** RT-планирование гарантирует детерминированное время реакции и не вытесняется обычными процессами. RT-потоки используют статическую шкалу приоритетов 1–99. `nice` применяется только в рамках справедливого пропорционального распределения времени (CFS) для обычных задач.

   **Пример:**

   ```text
   RT (SCHED_FIFO/RR): 1..99  -> Абсолютное вытеснение
   CFS (SCHED_OTHER):  nice   -> Пропорциональное разделение CPU

   ```

   **Типичная ошибка:** Путать приоритеты RT (где большее число означает высший приоритет) со шкалой `nice` (где меньшее число означает высший приоритет).

   **Источник:** [man7: sched(7)](https://man7.org/linux/man-pages/man7/sched.7.html)

214. Как посмотреть nice у процесса?

   **Ответ:** С помощью команд `ps -o pid,ni,comm -p <PID>`, `top` (столбец `NI`), либо прочитав поле 19 в файле `/proc/<PID>/stat`.

   **Пример:**

   ```bash
   ps -o pid,ni,pri,comm -p $$

   ```

   **Типичная ошибка:** Смотреть только на столбец `PRI` в `ps`, путая внутренний приоритет со значением `nice`.

   **Источник:** [man7: ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)

215. Что показывает столбец NI в top?

   **Ответ:** Точное числовое значение `nice` процесса в диапазоне от -20 до 19.

   **Пример:**

   ```text
   PID USER  PR  NI  VIRT  RES  SHR S  %CPU %MEM  COMMAND
   101 root  10 -10  120M  10M   5M S   0.0  0.1  critical_app

   ```

   **Типичная ошибка:** Не замечать отрицательный знак перед числом в столбце `NI`.

   **Источник:** [man7: top(1)](https://man7.org/linux/man-pages/man1/top.1.html)

216. Что показывает столбец PR в top?

   **Ответ:** Текущий динамический приоритет планирования с точки зрения ядра Linux. Для процессов реального времени в этом столбце отображается строка `rt`.

   **Пример:**

   ```text
   PR = 20 (для nice = 0)
   PR = rt (для задач реального времени)

   ```

   **Типичная ошибка:** Считать процесс со значением `PR = 20` процессом реального времени.

   **Источник:** [man7: top(1)](https://man7.org/linux/man-pages/man1/top.1.html)

217. Как связаны NI и PR?

   **Ответ:** Для стандартных задач планировщика `SCHED_OTHER` приоритет вычисляется по формуле: `PR = 20 + NI`. Таким образом, при `NI = 0` приоритет `PR = 20`, а при `NI = -20` приоритет `PR = 0`.

   **Пример:**

   ```text
   NI = -20  -->  PR = 0
   NI = 0    -->  PR = 20
   NI = 19   -->  PR = 39

   ```

   **Типичная ошибка:** Пытаться сопоставить эту формулу с процессами, работающими под управлением `chrt` (RT-задачи).

   **Источник:** [man7: top(1)](https://man7.org/linux/man-pages/man1/top.1.html)

218. Может ли renice помочь “шумному” процессу меньше мешать системе?

   **Ответ:** Да. Повышение `nice` (например, до `+15` или `+19`) резко снижает долю времени CPU, выделяемую процессу в периоды, когда ядра загружены другими задачами.

   **Пример:**

   ```bash
   renice -n 19 -p $(pgrep bad_miner)

   ```

   **Типичная ошибка:** Думать, что `renice` решит проблему нехватки оперативной памяти, вызванную процессом (он ограничивает только процессорные кванты).

   **Источник:** [man7: renice(1)](https://man7.org/linux/man-pages/man1/renice.1.html)

219. Почему nice не гарантирует точное процентное распределение CPU?

   **Ответ:** Планировщик CFS оперирует виртуальным временем (`vruntime`), взвешенным относительно всех конкурирующих активных задач на конкретном ядре. Если процесс часто блокируется на I/O или если другие ядра простаивают, соотношение фактического времени выполнения будет отклоняться от статических коэффициентов весов.

   **Пример:**

   ```text
   Процесс с nice 19 может получить 100% ядра, если все остальные задачи уснули в I/O

   ```

   **Типичная ошибка:** Ожидать от `nice` поведения жесткого лимита потребления CPU (жесткие лимиты настраиваются через cgroups `cpu.max`).

   **Источник:** [man7: sched(7)](https://man7.org/linux/man-pages/man7/sched.7.html)

220. Какие риски у неправильной настройки priority для продакшен-сервиса?

   **Ответ:** Установка неоправданно высокого приоритета может привести к голоданию (`starvation`) системных демонов, драйверов и сборщиков метрик. Установка чрезмерно низкого приоритета может вызвать скачки `p99 latency` и таймауты сетевых клиентов при кратковременных пиках сторонней нагрузки.

   **Пример:**

   ```text
   Приложение забирает весь CPU -> мониторинг node_exporter не успевает отправить метрики

   ```

   **Типичная ошибка:** Назначение отрицательного `nice` тяжелым расчетным процессам на одном узле с базами данных.

   **Источник:** [man7: sched(7)](https://man7.org/linux/man-pages/man7/sched.7.html)

### Practical C/C++ / Linux Process Questions

221. Как в C создать дочерний процесс и дождаться его завершения?

   **Ответ:** Вызвать системный вызов `fork()`, проверить возвращаемое значение и в родительской ветке выполнить блокирующий вызов `waitpid()`.

   **Пример:**

   ```c
   #include <unistd.h>
   #include <sys/wait.h>
   #include <stdio.h>

   int main(void) {
       pid_t pid = fork();
       if (pid == 0) {
           _exit(42);
       }
       int status;
       waitpid(pid, &status, 0);
       return 0;
   }

   ```

   **Типичная ошибка:** Использовать `wait(NULL)` вместо явного указания `waitpid(pid, ...)`, случайно перехватывая завершение другого фонового потомка.

   **Источник:** [man7: waitpid(2)](https://man7.org/linux/man-pages/man2/waitpid.2.html)

222. Как в C++ корректно обработать fork() error?

   **Ответ:** Проверить возвращенный `pid_t` на значение `< 0`, сохранить значение `errno` и выбросить системное исключение `std::system_error` либо обработать ошибку в соответствии со стратегией отказа.

   **Пример:**

   ```cpp
   #include <unistd.h>
   #include <system_error>

   pid_t safe_fork() {
       pid_t pid = fork();
       if (pid < 0) {
           throw std::system_error(errno, std::generic_category(), "fork failed");
       }
       return pid;
   }

   ```

   **Типичная ошибка:** Пытаться обрабатывать ошибку внутри блока `pid == 0`. При ошибке дочерний процесс вообще не создается.

   **Источник:** [man7: fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)

223. Как после fork() запустить другую программу через execvp()?

   **Ответ:** Сформировать массив указателей `char* argv[]`, завершающийся нулевым указателем `nullptr`, и передать имя исполняемого файла в `execvp()` внутри ветки ребенка.

   **Пример:**

   ```cpp
   #include <unistd.h>

   int main() {
       if (fork() == 0) {
           char* args[] = {(char*)"date", (char*)"+%Y-%m-%d", nullptr};
           execvp("date", args);
           _exit(127); // Вызовется только при ошибке запуска
       }
       return 0;
   }

   ```

   **Типичная ошибка:** Использовать обычный `exit()` вместо `_exit()` в случае провала `execvp()`.

   **Источник:** [man7: exec(3)](https://man7.org/linux/man-pages/man3/exec.3.html)

224. Как передать аргументы в execvp()?

   **Ответ:** Через нуль-терминированный массив указателей на строки `char*[]`. Первый элемент по соглашению содержит имя самой программы, а последний строго равен `nullptr`.

   **Пример:**

   ```cpp
   char* args[] = {
       (char*)"grep",
       (char*)"-i",
       (char*)"error",
       (char*)"app.log",
       nullptr
   };
   execvp("grep", args);

   ```

   **Типичная ошибка:** Передавать аргументы в виде единой строки `"grep -i error"`. Функция `execvp` не выполняет shell-парсинг пробелов.

   **Источник:** [man7: exec(3)](https://man7.org/linux/man-pages/man3/exec.3.html)

225. Как передать новое окружение в execve()?

   **Ответ:** Сформировать нуль-терминированный массив строк в формате `"KEY=VALUE"` и передать его третьим параметром в системный вызов `execve()`.

   **Пример:**

   ```cpp
   #include <unistd.h>

   int main() {
       char* args[] = {(char*)"env", nullptr};
       char* custom_env[] = {
           (char*)"ENV=PRODUCTION",
           (char*)"PORT=8080",
           nullptr
       };
       execve("/usr/bin/env", args, custom_env);
       return 1;
   }

   ```

   **Типичная ошибка:** Передавать в массив адреса временных `std::string`, которые уничтожаются до момента выполнения вызова.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

226. Как реализовать простейший shell на fork()+exec()+waitpid()?

   **Ответ:** В бесконечном цикле считывать команду пользователя, вызывать `fork()`, в дочернем процессе запускать команду через `execvp()`, а в родительском — ожидать завершения через `waitpid()`.

   **Пример:**

   ```cpp
   #include <iostream>
   #include <unistd.h>
   #include <sys/wait.h>

   int main() {
       std::string cmd;
       while (std::cout << "> " && std::cin >> cmd) {
           pid_t p = fork();
           if (p == 0) {
               char* args[] = {cmd.data(), nullptr};
               execvp(args[0], args);
               _exit(127);
           }
           waitpid(p, nullptr, 0);
       }
   }

   ```

   **Типичная ошибка:** Забывать обрабатывать встроенные команды оболочки (`cd`, `exit`) отдельно без вызова `fork()`.

   **Источник:** [man7: exec(3)](https://man7.org/linux/man-pages/man3/exec.3.html)

227. Как по коду определить, завершился ли child нормально или по сигналу?

   **Ответ:** С помощью макросов инспекции статуса: `WIFEXITED(status)` возвращает истину при штатном выходе (код забирается через `WEXITSTATUS`), а `WIFSIGNALED(status)` — если процесс был прерван неперехваченным сигналом (номер забирается через `WTERMSIG`).

   **Пример:**

   ```cpp
   #include <sys/wait.h>

   void check_status(int status) {
       if (WIFEXITED(status)) {
           // Нормальное завершение
       } else if (WIFSIGNALED(status)) {
           // Аварийное завершение сигналом
       }
   }

   ```

   **Типичная ошибка:** Прямой анализ битов переменной `status` вручную без использования стандартных макросов POSIX.

   **Источник:** [man7: wait(2)](https://man7.org/linux/man-pages/man2/wait.2.html)

228. Что делают WIFEXITED и WEXITSTATUS?

   **Ответ:** `WIFEXITED(status)` возвращает ненулевое значение, если дочерний процесс завершился нормально (вызовом `exit`, `_exit` или возвратом из `main`). `WEXITSTATUS(status)` извлекает младшие 8 бит кода завершения, переданного процессу.

   **Пример:**

   ```cpp
   int status;
   waitpid(child, &status, 0);
   if (WIFEXITED(status)) {
       int code = WEXITSTATUS(status);
   }

   ```

   **Типичная ошибка:** Вызывать `WEXITSTATUS()`, если макрос `WIFEXITED()` вернул `false` (значение будет содержать мусорные биты сигналов).

   **Источник:** [man7: wait(2)](https://man7.org/linux/man-pages/man2/wait.2.html)

229. Что делают WIFSIGNALED и WTERMSIG?

   **Ответ:** `WIFSIGNALED(status)` возвращает истину, если процесс был завершен из-за получения необработанного сигнала. `WTERMSIG(status)` возвращает номер этого сигнала (например, `SIGSEGV` или `SIGKILL`).

   **Пример:**

   ```cpp
   int status;
   waitpid(child, &status, 0);
   if (WIFSIGNALED(status)) {
       int sig = WTERMSIG(status); // Номер сигнала-убийцы
   }

   ```

   **Типичная ошибка:** Путать макрос завершения по сигналу `WTERMSIG` с макросом остановки `WSTOPSIG` (используется при отладке).

   **Источник:** [man7: wait(2)](https://man7.org/linux/man-pages/man2/wait.2.html)

230. Как корректно завершать child по SIGTERM с таймаутом и fallback на SIGKILL?

   **Ответ:** Послать `kill(pid, SIGTERM)`, запустить неблокирующий цикл ожидания с `waitpid(pid, &status, WNOHANG)` и проверкой прошедшего времени. Если таймаут истек, а процесс не вышел — послать безусловный `kill(pid, SIGKILL)` и выполнить финальный `waitpid()`.

   **Пример:**

   ```cpp
   #include <csignal>
   #include <sys/wait.h>
   #include <unistd.h>

   void kill_with_timeout(pid_t pid) {
       kill(pid, SIGTERM);
       for (int i = 0; i < 50; ++i) { // 5 секунд ожидания
           if (waitpid(pid, nullptr, WNOHANG) > 0) return;
           usleep(100'000);
       }
       kill(pid, SIGKILL);
       waitpid(pid, nullptr, 0);
   }

   ```

   **Типичная ошибка:** Забывать делать вызов `waitpid` после `SIGKILL`, оставляя процесс-зомби.

   **Источник:** [man7: kill(2)](https://man7.org/linux/man-pages/man2/kill.2.html)

231. Почему серверу лучше сначала послать SIGTERM, а не SIGKILL?

   **Ответ:** Сервер должен успеть выполнить процедуру gracefully: прекратить прием входящих соединений, сбросить буферизованные транзакции на диск, закрыть соединения с базой данных и освободить разделяемую память (shm) и lock-файлы.

   **Пример:**

   ```text
   SIGTERM -> Flush buffers -> Close DB pool -> Remove pidfile -> Exit

   ```

   **Типичная ошибка:** Немедленная отправка `SIGKILL`, приводящая к повреждению индексов баз данных на диске.

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

232. Как родителю убирать zombie-процессы без блокировки?

   **Ответ:** Использовать вызов `waitpid(-1, &status, WNOHANG)` в цикле внутри обработчика сигнала `SIGCHLD` или в рамках периодического тика основного event loop.

   **Пример:**

   ```cpp
   #include <sys/wait.h>

   void clean_zombies() {
       while (waitpid(-1, nullptr, WNOHANG) > 0) {
           // Очищает всех готовых зомби
       }
   }

   ```

   **Типичная ошибка:** Вызывать `waitpid` без цикла `while`. Если одновременно завершатся 3 процесса, сигнал `SIGCHLD` склеится в один, и без цикла 2 процесса останутся зомби.

   **Источник:** [man7: waitpid(2)](https://man7.org/linux/man-pages/man2/waitpid.2.html)

233. Как использовать waitpid(..., WNOHANG)?

   **Ответ:** Флаг `WNOHANG` указывает функции вернуть управление немедленно, не блокируя поток, если ни один из отслеживаемых дочерних процессов еще не изменил состояние (в этом случае возвращается `0`).

   **Пример:**

   ```cpp
   int status;
   pid_t result = waitpid(child_pid, &status, WNOHANG);
   if (result == 0) {
       // Ребенок все еще работает
   } else if (result > 0) {
       // Ребенок завершился
   }

   ```

   **Типичная ошибка:** Использовать `WNOHANG` в плотном пустом цикле `while(waitpid(...) == 0);`, приводя к 100% нагрузке на процессорное ядро (busy-wait).

   **Источник:** [man7: waitpid(2)](https://man7.org/linux/man-pages/man2/waitpid.2.html)

234. Как обрабатывать SIGCHLD в event-driven приложении?

   **Ответ:** Лучшая практика для Linux — создать специальный дескриптор сигналов вызовом `signalfd()`, заблокировать `SIGCHLD` в маске процесса через `sigprocmask()` и добавить полученный файловый дескриптор в `epoll`.

   **Пример:**

   ```cpp
   #include <sys/signalfd.h>
   #include <csignal>

   sigset_t mask;
   sigemptyset(&mask);
   sigaddset(&mask, SIGCHLD);
   sigprocmask(SIG_BLOCK, &mask, nullptr);

   int sfd = signalfd(-1, &mask, SFD_NONBLOCK | SFD_CLOEXEC);
   // Добавляем sfd в epoll

   ```

   **Типичная ошибка:** Попытка вызывать тяжелые методы C++ классов напрямую из классического прерывающего обработчика `sigaction`.

   **Источник:** [man7: signalfd(2)](https://man7.org/linux/man-pages/man2/signalfd.2.html)

235. Почему после fork() опасно пользоваться mutex-состоянием из многопоточной программы?

   **Ответ:** Если какой-либо мьютекс был заблокирован другим потоком в момент вызова `fork()`, то в дочернем процессе этот поток исчезает, а мьютекс остается захваченным навсегда. Любая попытка его захвата (`lock()`) вызовет вечный дедлок.

   **Пример:**

   ```cpp
   // Поток А захватил std::mutex m;
   // Поток Б вызвал fork();
   // В дочернем процессе потока А нет, m.lock() зависнет навсегда!

   ```

   **Типичная ошибка:** Вызов функций логирования или аллокации памяти (`malloc`), использующих глобальные скрытые мьютексы, в дочернем процессе многопоточного приложения.

   **Источник:** [man7: pthread_atfork(3)](https://man7.org/linux/man-pages/man3/pthread_atfork.3.html)

236. Какие функции безопасно вызывать между fork() и exec()?

   **Ответ:** Исключительно функции из официального списка POSIX `async-signal-safe` функций: системные вызовы ядра без блокировок (`_exit`, `dup2`, `close`, `execve`), манипуляции дескрипторами и сигнальными масками. Любые вызовы `malloc`, `free`, `printf`, `new` запрещены.

   **Пример:**

   ```cpp
   if (fork() == 0) {
       close(pipefd[0]);
       dup2(pipefd[1], STDOUT_FILENO);
       close(pipefd[1]);
       _exit(127);
   }

   ```

   **Типичная ошибка:** Бросать C++ исключения или создавать объекты `std::string` между `fork()` и `exec()`.

   **Источник:** [man7: signal-safety(7)](https://man7.org/linux/man-pages/man7/signal-safety.7.html)

237. Как перенаправить stdout child-процесса в pipe?

   **Ответ:** Создать `pipe(fds)`, вызвать `fork()`, в дочернем процессе закрыть вход для чтения `fds[0]`, продублировать дескриптор записи в стандартный вывод через `dup2(fds[1], STDOUT_FILENO)` и закрыть исходный `fds[1]`.

   **Пример:**

   ```cpp
   #include <unistd.h>

   int fds[2];
   pipe(fds);
   if (fork() == 0) {
       close(fds[0]);
       dup2(fds[1], STDOUT_FILENO);
       close(fds[1]);
       execlp("ls", "ls", nullptr);
       _exit(1);
   }

   ```

   **Типичная ошибка:** Забывать закрыть исходный `fds[1]` после `dup2()`, удерживая дескриптор открытым дважды.

   **Источник:** [man7: dup2(2)](https://man7.org/linux/man-pages/man2/dup2.2.html)

238. Как организовать parent-child communication для чтения output дочерней программы?

   **Ответ:** Создать канал через `pipe()`, перенаправить вывод в ребенке через `dup2`, закрыть неиспользуемый конец записи в родителе и читать данные через системный вызов `read(fds[0], ...)` до получения конца потока (`EOF`).

   **Пример:**

   ```cpp
   #include <unistd.h>
   #include <iostream>

   int fds[2];
   pipe(fds);
   if (fork() == 0) {
       close(fds[0]);
       dup2(fds[1], STDOUT_FILENO);
       close(fds[1]);
       execlp("echo", "echo", "hello world", nullptr);
       _exit(1);
   }
   close(fds[1]); // Важно закрыть в родителе для получения EOF!
   char buf[128];
   ssize_t n = read(fds[0], buf, sizeof(buf) - 1);
   buf[n] = '\0';
   std::cout << "Received: " << buf;
   close(fds[0]);

   ```

   **Типичная ошибка:** Не закрывать дескриптор записи `fds[1]` в родительском процессе, из-за чего вызов `read` блокируется навечно в ожидании данных, так как ядро видит открытый писатель.

   **Источник:** [man7: pipe(2)](https://man7.org/linux/man-pages/man2/pipe.2.html)

239. Как ограничить влияние фонового процесса на систему с помощью nice?

   **Ответ:** Вызвать системный вызов `setpriority(PRIO_PROCESS, 0, 19)` в начале выполнения дочернего фонового воркера (или запустить его через утилиту `nice -n 19`).

   **Пример:**

   ```cpp
   #include <sys/resource.h>
   #include <unistd.h>

   if (fork() == 0) {
       setpriority(PRIO_PROCESS, 0, 19); // Минимальный приоритет CPU
       run_heavy_background_job();
       _exit(0);
   }

   ```

   **Типичная ошибка:** Пытаться выставлять приоритет родителем над ребенком без проверки состояния гонки (ребенок может завершить работу до того, как родитель применит `setpriority`).

   **Источник:** [man7: setpriority(2)](https://man7.org/linux/man-pages/man2/setpriority.2.html)

240. Какие ошибки управления процессами чаще всего встречаются в C/C++ backend/system code?

   **Ответ:** 1) Потеря дочерних процессов с образованием зомби из-за отсутствия `waitpid`. 2) Использование небезопасных функций (аллокаций, мьютексов) между `fork()` и `exec()` в многопоточных сервисах. 3) Незакрытые дескрипторы сокетов/файлов при запуске чужих бинарников без `O_CLOEXEC`. 4) Игнорирование ошибок системных вызовов (`EINTR`, `EAGAIN`). 5) Некорректная обработка `SIGTERM` без сброса буферов I/O.

   **Пример:**

   ```cpp
   // Ошибка: отсутствие O_CLOEXEC приводит к утечке сокета БД в потомка
   int fd = open("db.lock", O_RDWR); // Без O_CLOEXEC!
   if (fork() == 0) {
       execlp("external_tool", "external_tool", nullptr);
   }

   ```

   **Типичная ошибка:** Полагаться на поведение "все работает на локальной машине без нагрузки", игнорируя краевые условия гонок и сбоев выделения ресурсов в production.

   **Источник:** [man7: signal-safety(7)](https://man7.org/linux/man-pages/man7/signal-safety.7.html)
