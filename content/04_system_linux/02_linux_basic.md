## Linux Basics — Questions (C/C++ oriented)


## Linux Architecture


---

1. Что такое Linux kernel?

   **Ответ:** Ядро Linux — монолитное свободное ядро операционной системы, работающее в привилегированном режиме процессора (Ring 0). Оно выступает базовым уровнем абстракции между аппаратным обеспечением и прикладным программным обеспечением, управляя процессами, потоками, физической памятью, файловыми системами, сетью и периферийными устройствами.

   **Пример:**

   ```bash
   uname -r
   # Вывод версии работающего ядра: 6.8.0-31-generic

   ```

   **Типичная ошибка:** Называть «Linux» полноценной операционной системой. Linux — это исключительно ядро; полноценная ОС включает стек GNU (компиляторы, утилиты coreutils, glibc), systemd и прикладные сервисы.

   **Источник:** [The Linux Kernel documentation](https://docs.kernel.org/)

   ---

2. Что относится к user space в Linux?

   **Ответ:** User space (пользовательское пространство) — непривилегированная область виртуальной памяти и режим исполнения процессора (Ring 3), в котором работают все пользовательские программы, системные сервисы (демоны), оболочки (shell), графические серверы и стандартные библиотеки (например, glibc).

   **Пример:**

   ```cpp
   #include <unistd.h>

   int main() {
       // Этот код, стек, куча и вызовы libc исполняются в Ring 3
       return 0;
   }

   ```

   **Типичная ошибка:** Считать системного демона (например, `sshd` или `systemd`), запущенного от пользователя `root`, частью kernel space. Любой процесс, работающий под учетной записью `root`, по-прежнему ограничен рамками Ring 3 и user space.

   **Источник:** [Robert Love: Linux System Programming](https://www.oreilly.com/library/view/linux-system-programming/9781449341527/)

   ---

3. В чем разница между kernel space и user space?

   **Ответ:** Разница заключается в уровне аппаратных привилегий CPU (Ring 0 против Ring 3) и доступности памяти. В kernel space код имеет прямой неограниченный доступ к инструкциям управления железом, портам I/O и всей физической памяти. В user space программы изолированы виртуальной памятью (MMU) и могут взаимодействовать с внешним миром только через системные вызовы.

   **Пример:**

   | Характеристика | Kernel Space (Ring 0) | User Space (Ring 3) |
   | --- | --- | --- |
   | Доступ к железу | Прямой (инструкции `in`, `out`, `cli`, `sti`) | Только через системные вызовы ядра |
   | Изоляция памяти | Доступ ко всей физической/виртуальной памяти | Доступ только к своему виртуальному адресному пространству |
   | Последствия сбоя | Kernel Panic / зависание всей ОС | Завершение упавшего процесса (`SIGSEGV`), ОС стабильна |

   **Типичная ошибка:** Полагать, что изоляция user space и kernel space обеспечивается программным кодом Linux. Изоляция опирается на кремниевые кольца защиты CPU и аппаратные таблицы MMU.

   **Источник:** [Intel® 64 and IA-32 Architectures Software Developer Manuals (Volume 3A: System Architecture Overview)](https://www.intel.com/)

   ---

4. Почему пользовательские приложения не работают напрямую с железом?

   **Ответ:** Прямой доступ привел бы к отсутствию безопасности и отказоустойчивости: любая ошибка в коде могла бы разрушить состояние всей ОС или повредить оборудование. Кроме того, прямое управление лишает систему мультизадачности (невозможно безопасно делить один диск или сетевую карту между сотнями приложений без централизованного арбитра — ядра).

   **Пример:**

   ```cpp
   // Прямая попытка выполнить инструкцию Ring 0 из User Space:
   asm volatile("hlt"); // Hardware Exception -> Ядро перехватывает и шлет SIGSEGV

   ```

   **Типичная ошибка:** Считать, что отсутствие прямого доступа фатально замедляет работу. Ядро предоставляет буферизацию, планирование и DMA, что чаще всего работает быстрее наивного ручного управления железом.

   **Источник:** [Andrew S. Tanenbaum: Modern Operating Systems](https://www.pearson.com/)

   ---

5. Как приложение взаимодействует с ядром?

   **Ответ:** Приложение взаимодействует с ядром через четко регламентированный интерфейс системных вызовов (system calls). Обычно это происходит прозрачно через функции-обертки стандартной библиотеки Си (glibc), которая загружает аргументы в регистры процессора и выполняет аппаратную инструкцию перехода в ядро (`syscall`).

   **Пример:**

   ```
   Код C++ (std::cout) -> glibc (write) -> Инструкция CPU 'syscall' -> Ядро Linux (sys_write)

   ```

   **Типичная ошибка:** Думать, что взаимодействие возможно через запись в произвольные структуры ядра по указателям. Виртуальная память ядра защищена от записи со стороны Ring 3 на уровне страниц MMU.

   **Источник:** [Michael Kerrisk: The Linux Programming Interface (Chapter 3: System Programming Concepts)](https://man7.org/tlpi/)

   ---

6. Что такое system call?

   **Ответ:** Системный вызов — программно-аппаратный механизм запроса сервиса ядра из непривилегированного пользовательского пространства, при котором процессор аппаратно переключает уровень привилегий с сохранением регистров и переходом на стек ядра.

   **Пример:**

   ```cpp
   #include <unistd.h>
   #include <sys/syscall.h>

   // Прямой системный вызов получения идентификатора текущего процесса:
   pid_t pid = syscall(SYS_getpid);

   ```

   **Типичная ошибка:** Путать библиотечный вызов `malloc()` с системным вызовом. `malloc` — это алгоритм пользовательского пространства в libc, запрашивающий у ядра память через `brk()` или `mmap()` только по мере необходимости.

   **Источник:** [Linux man pages: syscalls(2)](https://man7.org/linux/man-pages/man2/syscalls.2.html)

   ---

7. Какие основные подсистемы есть у ядра Linux?

   **Ответ:** Ядро разделено на ключевые функциональные подсистемы:

   1. **Process Management (Scheduler):** создание, планирование и завершение процессов/потоков.

   2. **Memory Management (MM):** виртуальная память, paging, swap, трансляция адресов.

   3. **VFS (Virtual File System):** унифицированный абстрактный интерфейс к файловым системам и устройствам.

   4. **Network Stack:** протоколы TCP/IP, сокеты, сетевые драйверы.

   5. **IPC (Interprocess Communication):** каналы, очереди, семафоры, shm.

   6. **Device Drivers:** модули взаимодействия с конкретными физическими устройствами.

   **Пример:**

   ```
                     ┌──────────────────────────────────────────────┐
                     │                 System Calls                 │
                     └──────┬──────────┬──────────┬──────────┬──────┘
                            │          │          │          │
   ┌────────────────────────▼─┐ ┌──────▼─────┐ ┌──▼──────┐ ┌─▼────────────────────┐
   │ Process Mgmt & Scheduler │ │ Memory Mgmt│ │   VFS   │ │ Network Stack & IPC  │
   └──────────────────────────┘ └────────────┘ └──┬──────┘ └──────────────────────┘
                                                  │
                                       ┌──────────▼──────────┐
                                       │    Device Drivers   │
                                       └─────────────────────┘

   ```

   **Типичная ошибка:** Считать, что эти подсистемы изолированы в разные независимые процессы (как в микроядре). В монолитном ядре Linux все подсистемы компилируются в единое адресное пространство ядра и вызывают функции друг друга напрямую.

   **Источник:** [Bovet, Cesati: Understanding the Linux Kernel](https://www.oreilly.com/library/view/understanding-the-linux/0596005652/)

   ---

8. Что такое scheduler в Linux?

   **Ответ:** Scheduler (планировщик) — подсистема ядра, решающая, какой из готовых к выполнению потоков (`TASK_RUNNING`) должен занять доступное ядро CPU в следующий квант времени, гарантируя справедливость распределения ресурсов и низкую задержку отклика.

   **Пример:**

   ```bash
   # Просмотр класса планирования процесса:
   chrt -p <PID>
   # Вывод по умолчанию: pid <PID>'s current scheduling policy: SCHED_OTHER

   ```

   **Типичная ошибка:** Считать, что современный Linux использует простой Round-Robin для обычных задач. По умолчанию используется планировщик EEVDF (Earliest Eligible Virtual Deadline First), пришедший на смену CFS (Completely Fair Scheduler).

   **Источник:** [Linux Kernel Documentation: CFS/EEVDF Scheduler](https://docs.kernel.org/scheduler/sched-design-CFS.html)

   ---

9. Что такое VFS (Virtual File System)?

   **Ответ:** VFS — уровень абстракции ядра, предоставляющий унифицированный программный интерфейс (POSIX API: `open`, `read`, `write`) для работы с любыми файловыми системами (ext4, XFS, Btrfs, NFS) и псевдофайловыми системами (`procfs`, `sysfs`).

   **Пример:**

   ```cpp
   // Один и тот же системный вызов работает прозрачно для ext4, сетевого диска или сокета:
   int fd = open("/path/to/file", O_RDONLY);
   read(fd, buffer, 1024);

   ```

   **Типичная ошибка:** Полагать, что драйвер конкретной файловой системы напрямую взаимодействует с кодом пользователя. Пользовательский код всегда общается только с VFS, которая маршрутизирует вызовы через таблицу указателей на функции `file_operations`.

   **Источник:** [Linux Kernel Documentation: Overview of the Virtual Filesystem](https://docs.kernel.org/filesystems/vfs.html)

   ---

10. Что такое process manager в Linux?

   **Ответ:** Process Manager (диспетчер процессов) — подсистема ядра, управляющая жизненным циклом потоков и процессов: их порождением (`clone`, `fork`), заменой исполняемого кода (`execve`), синхронизацией состояний, отслеживанием связей предок-потомок и очисткой структур `task_struct` при завершении (`exit`, `waitpid`).

   **Пример:**

   ```bash
   ps -eo pid,ppid,stat,comm
   # Отображение дерева процессов и их текущих состояний (R, S, D, Z)

   ```

   **Типичная ошибка:** Считать процессы и потоки принципиально разными сущностями на уровне ядра Linux. Для ядра существует только `task_struct` (scheduling entity); поток — это просто процесс, разделяющий память и файловые дескрипторы с родителем (`CLONE_VM | CLONE_FILES`).

   **Источник:** [Robert Love: Linux Kernel Development (Chapter 3: Process Management)](https://www.pearson.com/)

   ---

11. Что такое memory manager в Linux?

   **Ответ:** Memory Manager — подсистема ядра, отвечающая за распределение физической и виртуальной памяти: управление таблицами страниц, обработку Page Faults, реализацию Demand Paging, кэширование страниц с диска (Page Cache), выгрузку неактивной памяти (swap) и защиту областей памяти (VMA).

   **Пример:**

   ```bash
   cat /proc/meminfo
   # Детальный отчет менеджера памяти ядра о занятых страницах, кэшах и буферах

   ```

   **Типичная ошибка:** Полагать, что выделение памяти через `malloc()` моментально забирает физические планки RAM. Менеджер памяти выделяет только виртуальные диапазоны, а физическую память выделяет лениво при первом касании страницы.

   **Источник:** [Mel Gorman: Understanding the Linux Virtual Memory Manager](https://www.kernel.org/doc/gorman/)

   ---

12. Что такое device driver?

   **Ответ:** Device driver (драйвер устройства) — модуль программного кода ядра, знающий аппаратные спецификации конкретного физического или виртуального контроллера и транслирующий высокоуровневые запросы ядра (например, «прочитать блок 50») в низкоуровневые команды шины/устройства (PCIe, USB, I2C).

   **Пример:**

   ```bash
   lspci -k
   # Показывает устройства на шине PCI и привязанные к ним драйверы ядра (Kernel driver in use)

   ```

   **Типичная ошибка:** Полагать, что драйвер устройства работает в пользовательском пространстве как отдельное приложение. В классической архитектуре Linux подавляющее большинство драйверов исполняется внутри единого адресного пространства Ring 0.

   **Источник:** [Corbet, Rubini, Kroah-Hartman: Linux Device Drivers](https://lwn.net/Kernel/LDD3/)

   ---

13. Зачем ядру нужны драйверы?

   **Ответ:** Драйверы изолируют универсальный код операционной системы от бесконечного разнообразия специфичного железа. Благодаря драйверам ядро оперирует стандартными абстракциями (блочное устройство, сетевой интерфейс, tty), а нюансы регистров конкретного вендора скрыты внутри конкретного драйвера.

   **Пример:**

   ```
   Пользователь -> VFS -> Блочный уровень -> Драйвер NVMe / SATA -> Контроллер диска

   ```

   **Типичная ошибка:** Думать, что ядро должно заново перекомпилироваться под каждую новую модель мыши или сетевой карты: архитектура абстракций позволяет подключать и отключать драйверы на лету.

   **Источник:** [Linux Kernel Documentation: Driver Model](https://docs.kernel.org/driver-api/driver-model/index.html)

   ---

14. Чем kernel module отличается от встроенного драйвера?

   **Ответ:** Встроенный драйвер (built-in) компилируется непосредственно в образ бинарного файла ядра (`vmlinuz`) и постоянно находится в памяти с момента старта. Модуль ядра (Loadable Kernel Module, `.ko`) — это отдельный объектный файл, который может динамически загружаться в память ядра и выгружаться из нее прямо во время работы системы без перезагрузки.

   **Пример:**

   ```bash
   lsmod              # Список динамически загруженных модулей
   sudo modprobe dummy # Загрузка модуля dummy.ko на лету
   sudo rmmod dummy    # Выгрузка модуля из памяти ядра

   ```

   **Типичная ошибка:** Считать, что модуль ядра исполняется в user space с меньшими привилегиями. Будучи загруженным, модуль исполняется с полными правами Ring 0 внутри адресного пространства ядра.

   **Источник:** [The Linux Kernel Module Programming Guide](https://sysprog21.github.io/lkmpg/)

   ---

15. Что происходит при запуске программы в Linux?

   **Ответ:**

      1. Оболочка вызывает системный вызов `fork()`, клонируя текущий процесс.

      2. Дочерний процесс вызывает `execve(path, argv, envp)`.

      3. Ядро валидирует права, сбрасывает старое адресное пространство и парсит заголовок бинарника.

      4. ELF loader ядра мапит секции файла в виртуальную память и передает управление либо dynamic linker (`ld.so`), либо точке входа (`_start`).

      5. Рантайм libc выполняет инициализацию и вызывает функцию `main()`.

   **Пример:**

   ```
   fork() -> execve() -> Kernel ELF Loader -> ld-linux.so -> libc _start -> main()

   ```

   **Типичная ошибка:** Полагать, что системный вызов `execve()` создает новый PID. `execve` полностью переиспользует существующий PID, лишь заменяя тело и контекст исполняемой программы.

   **Источник:** [How programs get run: ELF binaries (LWN.net)](https://lwn.net/Articles/631631/)

   ---

16. Что делает ELF loader?

   **Ответ:** ELF loader (внутри ядра или в лице dynamic linker) анализирует структуру файла формата Executable and Linkable Format: читает Program Headers, сопоставляет сегменты (`PT_LOAD`) с виртуальной памятью процесса с нужными правами доступа (R, W, X), выделяет память под BSS-сегмент и настраивает регистр счетчика команд (RIP) на точку входа.

   **Пример:**

   ```bash
   readelf -l /bin/ls
   # Отображение Program Headers, указывающих ядру, как отображать сегменты в память

   ```

   **Типичная ошибка:** Считать, что ELF loader целиком считывает весь бинарник с диска в оперативную память при старте. Он лишь настраивает отображения `mmap`, а фактическая загрузка кода происходит страницами по требованию (demand paging).

   **Источник:** [Tool Interface Standard (TIS) Executable and Linking Format (ELF) Specification](https://refspecs.linuxfoundation.org/elf/elf.pdf)

   ---

17. Что такое init process?

   **Ответ:** Init process — самый первый процесс пользовательского пространства, порождаемый ядром на финальной стадии загрузки операционной системы. Он является предком всех остальных процессов в системе и отвечает за монтирование файловых систем, запуск фоновых служб и управление остановкой машины.

   **Пример:**

   ```bash
   ps -p 1 -o comm=
   # На современных системах выведет: systemd (или init)

   ```

   **Типичная ошибка:** Попытка принудительно завершить процесс с PID 1 командой `kill -9 1`. Ядро игнорирует сигнал `SIGKILL` для init процесса, защищая систему от немедленной паники.

   **Источник:** [Linux man pages: init(1)](https://man7.org/linux/man-pages/man1/init.1.html)

   ---

18. Что такое PID 1 и почему он важен?

   **Ответ:** PID 1 — уникальный идентификатор процесса `init`. Он играет две ключевые роли: во-первых, инициализирует пользовательское окружение; во-вторых, служит «усыновителем» (subreaper) для процессов-сирот (orphaned processes), собирая их коды возврата через вызовы семейства `waitpid()`, тем самым предотвращая утечку зомби-процессов в системе.

   **Пример:**

   ```cpp
   // Если процесс-родитель умирает раньше ребенка:
   // ядро автоматически переназначает PPID дочернего процесса на PID 1.

   ```

   **Типичная ошибка:** Запуск процессов внутри контейнеров Docker без легковесного init (например, `tini`): фоновые отпочковавшиеся зомби-процессы накапливаются бесконечно, поскольку контейнеризованное приложение обычно не имеет логики сбора чужих сирот.

   **Источник:** [Linux man pages: prctl(2) / PR_SET_CHILD_SUBREAPER](https://man7.org/linux/man-pages/man2/prctl.2.html)

   ---

19. Что делает systemd?

   **Ответ:** Systemd — современная подсистема инициализации (init) и управления сервисами в Linux. Она обеспечивает параллельный запуск служб, отслеживание демонов через cgroups (гарантируя уничтожение всех потомков при остановке), сокет-активацию, журналирование (journald), монтирование дисков и управление сессиями пользователей.

   **Пример:**

   ```bash
   systemctl status sshd.service
   # Запрос состояния демона SSH через интерфейс systemd

   ```

   **Типичная ошибка:** Считать systemd простым аналогом старых bash-скриптов SysVinit. Systemd — это обширный фреймворк системного управления, контролирующий таймеры, сеть, логирование и контейнеризацию сервисов.

   **Источник:** [systemd System and Service Manager](https://systemd.io/)

   ---

20. Что такое shell?

   **Ответ:** Shell (командная оболочка) — интерфейсная программа пользовательского пространства, принимающая команды от пользователя (через клавиатуру или скрипты), интерпретирующая их и запускающая соответствующие системные программы или встроенные директивы, управляя их вводом-выводом.

   **Пример:**

   ```bash
   echo $SHELL
   # Вывод пути текущей командной оболочки, например: /bin/bash

   ```

   **Типичная ошибка:** Путать окно эмулятора терминала (GNOME Terminal, Alacritty) с оболочкой (bash, zsh). Терминал лишь отрисовывает символы и обрабатывает нажатия клавиш, передавая байты шеллу.

   **Источник:** [POSIX.1-2017: Shell & Utilities](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html)

   ---

21. Чем shell отличается от kernel?

   **Ответ:** Ядро (kernel) — это привилегированная низкоуровневая программа (Ring 0), управляющая ресурсами машины и не имеющая прямого пользовательского текстового интерфейса. Shell — это обычная непривилегированная утилита (Ring 3), парсящая текстовые команды человека и транслирующая их в вызовы к ядру.

   **Пример:**

   | Характеристика | Kernel | Shell |
   | --- | --- | --- |
   | Пространство памяти | Kernel Space | User Space |
   | Интерфейс | Syscalls (двоичный ABI) | CLI (текстовый ввод/вывод) |
   | Роль | Управление ресурсами и изоляция | Интерпретация команд пользователя |

   **Типичная ошибка:** Думать, что команда `cd` — это системный вызов или отдельный бинарный файл. `cd` — это встроенная внутренняя команда shell (built-in), так как дочерний процесс не может изменить текущую директорию родительского шелла.

   **Источник:** [The Open Group Base Specifications: Shell Command Language](https://pubs.opengroup.org/)

   ---

22. Что такое bash?

   **Ответ:** Bash (Bourne Again SHell) — де-факто стандартная командная оболочка проекта GNU, являющаяся обратно совместимым расширением стандарта POSIX sh (`/bin/sh`) с добавлением автодополнения, массивов, работы с историей команд и расширенным скриптовым синтаксисом.

   **Пример:**

   ```bash
   # Bash-специфичный синтаксис (process substitution):
   diff <(ls dir1) <(ls dir2)

   ```

   **Типичная ошибка:** Писать bash-скрипты с шебангом `#!/bin/sh`. На многих системах (например, Ubuntu/Debian) `/bin/sh` указывает на легковесную оболочку `dash`, в которой многие конструкции bash ("bashisms") вызывают синтаксическую ошибку.

   **Источник:** [GNU Bash Manual](https://www.gnu.org/software/bash/manual/)

   ---

23. Что делает dynamic linker?

   **Ответ:** Dynamic Linker (динамический компоновщик, `ld.so` или `ld-linux.so`) — программа в user space, запускаемая ядром до начала исполнения основного кода программы. Она находит на диске зависимые разделяемые библиотеки (`.so`), мапит их в память, разрешает неразрешенные символы (перемещения / relocations) и связывает адреса функций (через PLT и GOT).

   **Пример:**

   ```bash
   ldd /bin/ls
   # Показывает зависимости бинарника, которые dynamic linker обязан подгрузить в память

   ```

   **Типичная ошибка:** Считать, что dynamic linker работает в момент компиляции программы. В момент сборки работает статический линкер `ld`, а `ld.so` работает во время реального запуска приложения на целевой машине.

   **Источник:** [Linux man pages: ld.so(8)](https://man7.org/linux/man-pages/man8/ld.so.8.html)

   ---

24. Что такое shared library?

   **Ответ:** Разделяемая библиотека (Shared Library, `.so`) — скомпилированный ELF-файл, содержащий позиционно-независимый код (PIC), который может одновременно использоваться несколькими независимыми процессами. Физические страницы секции кода (`.text`) такой библиотеки хранятся в памяти в единственном экземпляре и разделяются всеми процессами.

   **Пример:**

   ```bash
   gcc -fPIC -shared mylib.c -o libmylib.so

   ```

   **Типичная ошибка:** Считать, что переменные и глобальные данные shared-библиотеки тоже разделяются между процессами. Секция изменяемых данных (`.data`) дублируется для каждого процесса индивидуально по механизму Copy-on-Write.

   **Источник:** [David A. Wheeler: Program Library HOWTO (Shared Libraries)](https://dwheeler.com/program-library/)

   ---

25. Чем static linking отличается от dynamic linking?

   **Ответ:** При статической линковке машинный код используемых библиотек (`.a`) целиком копируется линкером в итоговый исполняемый файл на этапе сборки (создается самодостаточный бинарник). При динамической линковке бинарник содержит лишь список необходимых имен библиотек и внешних символов, связывание которых происходит в RAM при запуске программы.

   **Пример:**

   ```bash
   # Статическая сборка (тяжелый автономный бинарник):
   g++ main.cpp -static -o app_static

   # Динамическая сборка (легкий бинарник с внешними зависимостями):
   g++ main.cpp -o app_dynamic

   ```

   **Типичная ошибка:** Полагать, что статическая сборка всегда быстрее. Статические бинарники занимают в разы больше места на диске и лишают систему оптимизации разделения физических страниц общего кода в оперативной памяти.

   **Источник:** [John R. Levine: Linkers and Loaders](https://www.iecc.com/linker/)

   ---

26. Что такое /proc?

   **Ответ:** `/proc` (procfs) — виртуальная (псевдо) файловая система, генерируемая ядром на лету в оперативной памяти. Она служит интерфейсом для наблюдения за состоянием работающих процессов (директории с числовыми именами `/proc/<PID>`) и параметрами самого ядра (память, прерывания, статистика).

   **Пример:**

   ```bash
   cat /proc/$$/status # Статус и потребление ресурсов текущего процесса оболочки
   cat /proc/cpuinfo   # Характеристики установленных процессоров

   ```

   **Типичная ошибка:** Попытка измерить размер файлов в `/proc` через `ls -l`. Большинство файлов в `/proc` имеют размер 0 байт, так как их содержимое генерируется ядром динамически только в момент чтения (`read()`).

   **Источник:** [Linux man pages: proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html)

   ---

27. Что такое /sys?

   **Ответ:** `/sys` (sysfs) — псевдофайловая система, экспортирующая структурированную иерархию объектов ядра (kobjects): шины, устройства, драйверы, параметры энергосбережения и топологию оборудования. Она предназначена для структурированного чтения и конфигурирования устройств из user space.

   **Пример:**

   ```bash
   # Чтение текущего состояния сетевого интерфейса:
   cat /sys/class/net/eth0/operstate

   ```

   **Типичная ошибка:** Модифицировать настройки железа прямыми вызовами в обход sysfs. Sysfs является каноническим механизмом ядра для настройки параметров драйверов (вместо устаревших ioctl).

   **Источник:** [Linux Kernel Documentation: sysfs - *The* filesystem for exporting kernel objects](https://docs.kernel.org/filesystems/sysfs.html)

   ---

28. Чем procfs отличается от sysfs?

   **Ответ:** `/proc` исторически создавался для экспорта информации о процессах, но со временем превратился в неструктурированную свалку разнообразных отчетов ядра. `/sys` был спроектирован позже с жесткой иерархией модели устройств ядра (kobject tree), где действует строгое правило: «одно значение на один текстовый файл».

   **Пример:**

   ```bash
   # procfs: выдает полотно неструктурированного текста:
   cat /proc/loadavg

   # sysfs: строго атомарное значение:
   cat /sys/devices/system/cpu/cpu0/topology/core_id

   ```

   **Типичная ошибка:** Использовать `/proc/sys` и `/sys` как синонимы. Каталог `/proc/sys` — это механизм настройки внутренних параметров ядра через `sysctl`, а `/sys` — дерево оборудования и объектов драйверов.

   **Источник:** [Greg Kroah-Hartman: The sysfs Filesystem](https://www.kernel.org/)

   ---

29. Что такое pseudo-filesystem?

   **Ответ:** Псевдофайловая система — виртуальная файловая система, не имеющая физического хранилища на блочном носителе (жестком диске или SSD). Её каталоги и файлы формируются функциями ядра прямо в RAM при обращении к VFS (примеры: `procfs`, `sysfs`, `devtmpfs`, `cgroup`).

   **Пример:**

   ```bash
   mount | grep -E "(proc|sysfs|tmpfs)"

   ```

   **Типичная ошибка:** Пытаться восстановить удаленный файл из `/proc` или считать, что запись в псевдофайловую систему изнашивает ресурс ячеек диска.

   **Источник:** [Linux Kernel Documentation: Filesystems](https://docs.kernel.org/filesystems/index.html)

   ---

30. Что значит “everything is a file” в Linux?

   **Ответ:** Философия Unix/Linux, согласно которой доступ к подавляющему большинству разнородных ресурсов системы (файлы на диске, устройства ввода, последовательные порты, сокеты, каналы IPC, системная статистика) унифицирован через абстракцию потока байт и файлового дескриптора с единым набором системных вызовов (`open`, `read`, `write`, `close`).

   **Пример:**

   ```bash
   # Чтение случайных байтов из аппаратного генератора как из обычного файла:
   head -c 16 /dev/urandom

   ```

   **Типичная ошибка:** Абсолютизировать принцип. Сетевые интерфейсы (например, `eth0`) не представлены как файлы в директории `/dev` и настраиваются через сетевой стек/netlink-сокеты, а не операцией `open()`.

   **Источник:** [Eric S. Raymond: The Art of Unix Programming](http://www.catb.org/~esr/writings/taoup/html/)

   ---

31. Что такое file descriptor?

   **Ответ:** Файловый дескриптор — неотрицательное целое число (`int`), являющееся индексом во внутренней таблице открытых процессом файлов ядра. По этому индексу ядро связывает пользовательские системные вызовы со структурой `struct file`, указывающей на конкретный inode и операции VFS.

   **Пример:**

   ```cpp
   #include <unistd.h>
   #include <fcntl.h>

   int fd = open("/dev/null", O_WRONLY); // Возвращает дескриптор (например, 3)
   write(fd, "a", 1);
   close(fd);

   ```

   **Типичная ошибка:** Полагать, что числовые значения дескрипторов глобальны для всей системы. В разных процессах один и тот же номер дескриптора (например, 4) указывает на совершенно разные открытые файлы или сокеты.

   **Источник:** [Linux man pages: open(2)](https://man7.org/linux/man-pages/man2/open.2.html)

   ---

32. Как stdin/stdout/stderr связаны с архитектурой Linux?

   **Ответ:** Это фундаментальное соглашение POSIX: при создании процесса первые три дескриптора таблицы открытых файлов (0, 1, 2) резервируются под стандартные потоки:

   * `0` — `stdin` (ввод, клавиатура/pipe)
   * `1` — `stdout` (вывод, экран/pipe)
   * `2` — `stderr` (вывод ошибок, экран)
   Благодаря этой фиксации номеров оболочка shell может конструировать конвейеры (`|`) и перенаправления (`>`), просто подменяя дескрипторы через вызовы `dup2()`.

   **Пример:**

   ```bash
   # Оболочка закрывает дескриптор 1 и открывает вместо него файл out.txt:
   ./app > out.txt 2>&1

   ```

   **Типичная ошибка:** Закрывать дескриптор 2 при подавлении ошибок и затем открывать новый файл. Новый файл займет освободившийся индекс `2`, и если какая-то библиотека запишет в `stderr`, она перезапишет данные вашего файла.

   **Источник:** [The Open Group Base Specifications: File Descriptors](https://pubs.opengroup.org/onlinepubs/9699919799/basedefs/V1_chap02.html)

   ---

33. Что такое daemon?

   **Ответ:** Демон — долгоживущий фоновый процесс, запускаемый для обслуживания определенных системных запросов (веб-сервер, база данных, планировщик задач). Демон не имеет управляющего терминала (controlling TTY), отвязан от родительской сессии пользователя и обычно имеет PID предка равный 1.

   **Пример:**

   ```cpp
   #include <unistd.h>

   int main() {
       // Традиционный способ демонизации (форк, отвязка от терминала, сброс umask):
       daemon(0, 0);
       while (true) { pause(); }
   }

   ```

   **Типичная ошибка:** Полагать, что добавление символа `&` в конце команды в bash делает программу полноценным демоном. Фоновый процесс `&` по-прежнему привязан к терминальной сессии и будет убит сигналом `SIGHUP` при закрытии терминала (если не запущен через `nohup` или `disown`).

   **Источник:** [Linux man pages: daemon(3)](https://man7.org/linux/man-pages/man3/daemon.3.html)

   ---

34. Что такое TTY?

   **Ответ:** TTY (teletypewriter) — изначально аппаратный телетайп, а в современной архитектуре Linux — драйвер ядра, реализующий интерфейс терминала. Он обрабатывает ввод символов, реализует линейную дисциплину (line discipline: эхо, обработку горячих клавиш Ctrl+C, стирание символов Backspace) и связывает экран с сессией процесса.

   **Пример:**

   ```bash
   tty
   # Выводит текущий подключенный терминал, например: /dev/tty1 или /dev/pts/0

   ```

   **Типичная ошибка:** Считать виртуальные консоли `/dev/tty1-6` эмуляторами терминала. Виртуальные консоли обрабатываются непосредственно драйвером терминала внутри ядра Linux.

   **Источник:** [The TTY demystified: Linus Åkesson](https://www.linusakesson.net/programming/tty/)

   ---

35. Что такое PTY?

   **Ответ:** PTY (pseudo-terminal) — пара программных виртуальных устройств (master и slave), эмулирующих физический терминал для программ в пользовательском пространстве. Сторона slave ведет себя в точности как обычный TTY, а сторона master управляется эмулятором терминала (GNOME Terminal, xterm) или демоном SSH для передачи байтов по сети.

   **Пример:**

   ```
   SSH Client -> Network -> sshd -> [PTY Master] === Linux Kernel === [PTY Slave /dev/pts/X] -> bash

   ```

   **Типичная ошибка:** Запуск утилит, требующих интерактивный ввод пароля (например, `sudo`), внутри скриптов без выделения PTY. Программа завершится ошибкой «no tty present and no askpass program specified».

   **Источник:** [Linux man pages: pty(7)](https://man7.org/linux/man-pages/man7/pty.7.html)

   ---

36. Что такое login shell?

   **Ответ:** Login shell — оболочка, запускаемая первой при успешной аутентификации пользователя в системе (первый символ в `argv[0]` выставляется в `-`, например, `-bash`). Она считывает глобальные конфигурационные файлы начальной инициализации профиля (`/etc/profile`, `~/.bash_profile` или `~/.bash_login`), настраивая окружение на всю сессию.

   **Пример:**

   ```bash
   # Проверка типа оболочки:
   shopt login_shell
   # вернет login_shell on (если это login shell)

   ```

   **Типичная ошибка:** Прописывать переменные окружения только в `~/.bash_profile` и удивляться, почему они не подхватываются при открытии новых окон терминала в графической оболочке (графические эмуляторы по умолчанию запускают non-login shell, читающий `~/.bashrc`).

   **Источник:** [GNU Bash Manual: Bash Startup Files](https://www.gnu.org/software/bash/manual/html_node/Bash-Startup-Files.html)

   ---

37. Что такое environment variables?

   **Ответ:** Переменные окружения — набор пар «ключ=значение» в формате строк `KEY=VALUE`, хранящийся в сегменте пользовательской памяти процесса (на стеке над аргументами `argv`). Они неявно наследуются дочерними процессами при вызове `fork()`/`execve()` и служат для глобальной конфигурации путей, локали и поведения программ.

   **Пример:**

   ```cpp
   #include <cstdlib>
   #include <iostream>

   int main() {
       const char* path = std::getenv("PATH");
       std::cout << "Path: " << (path ? path : "empty") << '\n';
   }

   ```

   **Типичная ошибка:** Считать, что модификация переменной окружения в дочернем процессе (через `export` или `setenv()`) повлияет на родительский процесс. Окружение передается только сверху вниз при порождении процесса.

   **Источник:** [Linux man pages: environ(7)](https://man7.org/linux/man-pages/man7/environ.7.html)

   ---

38. Как процесс получает argv и envp?

   **Ответ:** Ядро при обработке системного вызова `execve()` копирует строки аргументов и переменные окружения на самую верхушку нового пользовательского стека создаваемой программы. В момент старта функции `_start` указатель стека (RSP) ссылается на структуру: `argc`, массив указателей `argv[]`, терминатор `NULL`, массив указателей `envp[]`, терминатор `NULL` и вектор метаданных `auxv`.

   **Пример:**

   ```
   Высокие адреса памяти (Стек)
   ├── Строки аргументов и окружения ("PATH=/usr/bin", "app", etc.)
   ├── Вектор Auxiliary Vector (auxv)
   ├── Указатели envp[] (завершается NULL)
   ├── Указатели argv[] (завершается NULL)
   ├── argc (целое число аргументов) <- Начальный указатель RSP процессора
   Низкие адреса памяти

   ```

   **Типичная ошибка:** Полагать, что `main()` вызывается первым. Первой вызывается ассемблерная функция libc `_start`, которая извлекает эти параметры из стека и передает их в сигнатуру `int main(int argc, char** argv, char** envp)`.

   **Источник:** [System V Application Binary Interface: AMD64 Architecture (Initial Stack and Register State)](https://gitlab.com/x86-psABIs/x86-64-ABI)

   ---

39. Что такое glibc?

   **Ответ:** GNU C Library (glibc) — основная реализация стандартной библиотеки языка Си для систем GNU/Linux. Она предоставляет реализацию стандарта ANSI C/POSIX, математические функции, алгоритмы кучи (`malloc`), потоки (`pthreads`) и тонкие системные обертки над системными вызовами ядра с сохранением кодов ошибок в `errno`.

   **Пример:**

   ```bash
   ldd --version
   # Вывод версии установленной библиотеки: ldd (Ubuntu GLIBC 2.39)

   ```

   **Типичная ошибка:** Считать, что glibc — единственная библиотека Си под Linux. Для встраиваемых систем и легковесных контейнеров (например, Alpine Linux) часто используют альтернативные реализации (musl, uClibc).

   **Источник:** [The GNU C Library Reference Manual](https://www.gnu.org/software/libc/manual/)

   ---

40. Чем libc отличается от kernel API?

   **Ответ:** Kernel API — это низкоуровневый двоичный системный интерфейс ядра (номера syscall, передача аргументов через регистры CPU, флаги ядра). Libc API — переносимая высокоуровневая C-библиотека, которая стандартизирует интерфейсы под POSIX, обеспечивает буферизацию ввода-вывода (структура `FILE*` против сырого `int fd`) и скрывает аппаратно-зависимые детали инструкций перехода в ядро.

   **Пример:**

   | Характеристика | Kernel API (Syscalls) | Libc API |
   | --- | --- | --- |
   | Идентификация ошибок | Возврат отрицательного кода в регистре (`-EINVAL`) | Запись положительного кода ошибки в `errno`, возврат `-1` |
   | Буферизация | Отсутствует (прямая передача в page cache/драйвер) | Буфер в user space (`std::string`, буферы `FILE`) |
   | Аллокация памяти | Грубая, страницами (`brk`, `mmap`) | Гранулярная, по байтам (`malloc`, `free`) |

   **Типичная ошибка:** Считать функцию `pthread_create()` системным вызовом. В ядре нет системного вызова `pthread_create`, libc реализует его с помощью комплексного вызова `clone()` с набором специфичных битовых флагов.

   **Источник:** [Linux man pages: syscalls(2)](https://man7.org/linux/man-pages/man2/syscalls.2.html)

   ---

41. Что происходит при переходе user mode → kernel mode?

   **Ответ:**

      1. CPU переключает привилегии с Ring 3 на Ring 0 (изменяется поле CPL).

      2. Аппаратно сохраняются текущие регистры счетчика команд (RIP) и флагов (RFLAGS).

      3. Процессор переключается с пользовательского стека на изолированный стек ядра для текущего процесса (загружается из структуры TSS/MSR).

      4. Управление передается по жестко зафиксированному адресу шлюза системных вызовов в ядре (MSR `LSTAR`).

   **Пример:**

   ```
   Пользовательский стек (RSP_user) -> [SYSCALL] -> Стек ядра (RSP_kernel)

   ```

   **Типичная ошибка:** Считать, что переключение режима очищает кэши CPU. L1/L2 кэши данных сохраняются, однако при возврате ядро может инвалидировать часть предсказателей переходов для предотвращения Spectre-атак.

   **Источник:** [AMD64 Architecture Programmer’s Manual Volume 2: System Programming (SYSCALL/SYSRET)](https://www.amd.com/)

   ---

42. Что такое trap?

   **Ответ:** Trap (ловушка, программное исключение) — синхронное прерывание, намеренно или непреднамеренно порожденное исполнением текущей процессорной инструкции самого потока (деление на ноль `#DE`, невалидная инструкция `#UD`, системный вызов `syscall`, обращение к незамапленной памяти `#PF` или точка останова отладчика `int 3`).

   **Пример:**

   ```cpp
   int x = 5 / 0; // Генерирует синхронный процессорный trap (Divide by Zero) -> SIGFPE

   ```

   **Типичная ошибка:** Путать trap и аппаратное прерывание. Trap всегда вызывается кодом программы синхронно и воспроизводим на том же месте; прерывание возникает асинхронно от внешних устройств.

   **Источник:** [Intel® 64 Architectures Software Developer’s Manual: Interrupt and Exception Handling](https://www.intel.com/)

   ---

43. Что такое interrupt?

   **Ответ:** Interrupt (аппаратное прерывание, IRQ) — асинхронный электрический сигнал, посылаемый контроллеру прерываний (APIC) физическим внешним устройством (сетевая карта приняла пакет, таймер отсчитал квант, диск завершил DMA-чтение). Процессор немедленно приостанавливает текущий поток и выполняет функцию драйвера — обработчик прерывания (ISR).

   **Пример:**

   ```bash
   cat /proc/interrupts
   # Статистика распределения аппаратных прерываний по ядрам процессора

   ```

   **Типичная ошибка:** Выполнять тяжелые длительные расчеты прямо в основном обработчике прерывания. В Linux обработчики прерываний делятся на top-half (быстрая критическая фаза) и bottom-half/softirq (отложенная тяжелая обработка данных в фоне).

   **Источник:** [Robert Love: Linux Kernel Development (Chapter 7: Interrupts and Interrupt Handlers)](https://www.pearson.com/)

   ---

44. Чем interrupt отличается от signal?

   **Ответ:** Прерывание (Interrupt) генерируется аппаратным обеспечением, обрабатывается процессором на уровне микрокода и перехватывается функциями ядра в Ring 0. Сигнал (Signal) — это чисто программная эмуляция прерывания на уровне ядра Linux, доставляемая процессу в пользовательском пространстве (Ring 3).

   **Пример:**

   | Характеристика | Hardware Interrupt | POSIX Signal |
   | --- | --- | --- |
   | Источник | Физическое оборудование (NIC, Keyboard, Timer) | Ядро ОС или другой процесс (`kill`) |
   | Уровень обработки | Ядро Linux (Ring 0) | Обработчик в пользовательском коде (Ring 3) |
   | Синхронность | Полностью асинхронно для CPU | Доставляется процессу при возврате из ядра |

   **Типичная ошибка:** Считать аппаратное прерывание таймера прямым вызовом сигнала `SIGALRM`. Ядро получает прерывание таймера в Ring 0 и уже самостоятельно формирует структуру сигнала для процесса.

   **Источник:** [Linux man pages: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

   ---

45. Что такое context switch?

   **Ответ:** Переключение контекста (Context Switch) — процедура ядра, при которой выполнение одного потока на процессоре приостанавливается, все регистры CPU (RIP, RSP, регистры общего назначения, FPU/AVX) сохраняются в его дескриптор `task_struct`, а сохраненные регистры другого готового потока загружаются в CPU, передавая ему управление.

   **Пример:**

   ```bash
   pidstat -w 1
   # Мониторинг добровольных (cswch/s) и принудительных (nvcswch/s) переключений контекста

   ```

   **Типичная ошибка:** Полагать, что context switch бесплатен. Переключение между разными процессами требует смены указателя таблиц страниц в регистре `CR3`, что приводит к инвалидации TLB и вымыванию горячих данных из кэшей CPU.

   **Источник:** [Silberschatz, Galvin: Operating System Concepts (Context Switch)](https://www.os-book.com/)

   ---

46. Когда происходит context switch?

   **Ответ:** Переключение контекста происходит в двух случаях:

      1. **Добровольно (Cooperative / Voluntary):** поток засыпает сам в ожидании ресурса (I/O, мьютекс, `sleep`, `poll`).

      2. **Принудительно (Preemptive / Involuntary):** планировщик ядра отбирает у потока процессор, когда истек его квант времени (timeslice), либо в системе появился поток с более высоким приоритетом (Real-Time).

   **Пример:**

   ```
   Поток А делает read() -> Данных нет -> Перевод в TASK_INTERRUPTIBLE -> Context Switch на Поток Б

   ```

   **Типичная ошибка:** Создавать тысячи активно конкурирующих потоков CPU. Чрезмерное количество принудительных переключений контекста приводит к падению полезной производительности системы (thrashing).

   **Источник:** [Brendan Gregg: Systems Performance (CPU Scheduling)](http://www.brendangregg.com/systems-performance-2nd-edition-book.html)

   ---

47. Что такое preemption в Linux?

   **Ответ:** Preemption (вытеснение) — способность операционной системы принудительно прерывать выполняющийся поток без его согласия для немедленной передачи процессора более приоритетной задаче. Linux поддерживает как вытеснение пользовательских процессов (User Preemption), так и вытеснение самого кода ядра внутри Ring 0 (Kernel Preemption: `CONFIG_PREEMPT`).

   **Пример:**

   ```bash
   uname -v | grep PREEMPT
   # Проверка поддержки вытеснения ядром задач реального времени

   ```

   **Типичная ошибка:** Считать, что код ядра Linux не может быть вытеснен. В современных ядрах с флагом `CONFIG_PREEMPT` (или RT-патчем) процесс может быть вытеснен прямо в середине выполнения большинства системных вызовов в Ring 0.

   **Источник:** [Linux Kernel Documentation: Kernel Preemption](https://docs.kernel.org/)

   ---

48. Что такое cgroups на базовом уровне?

   **Ответ:** Контрольные группы (Control Groups, cgroups) — механизм ядра Linux, позволяющий изолировать, ограничивать и измерять использование физических ресурсов системы (процессорного времени, оперативной памяти, операций дискового I/O, сетевых пакетов) для иерархических групп процессов.

   **Пример:**

   ```bash
   # Ограничение памяти процесса до 500 МБ в cgroups v2:
   echo "500M" > /sys/fs/cgroup/my_group/memory.max
   echo $$ > /sys/fs/cgroup/my_group/cgroup.procs

   ```

   **Типичная ошибка:** Путать cgroups и namespaces. Cgroups ограничивают **количество** ресурсов («не более 2 ядер CPU и 1 ГБ ОЗУ»), а namespaces ограничивают **видимость** ресурсов («видит только свои процессы и свой сетевой интерфейс»).

   **Источник:** [Linux man pages: cgroups(7)](https://man7.org/linux/man-pages/man7/cgroups.7.html)

   ---

49. Что такое namespaces на базовом уровне?

   **Ответ:** Пространства имен (Namespaces) — механизм ядра Linux, обеспечивающий изоляцию системных ресурсов для группы процессов. Процессы внутри пространства имен имеют иллюзию владения собственной изолированной средой: таблицей PID, сетевыми интерфейсами (NET), точками монтирования (MNT), пользователями (USER), сетевыми портами и IPC-очередями. Это базовый фундамент контейнеризации (Docker, LXC).

   **Пример:**

   ```bash
   # Запуск изолированного bash с собственной таблицей процессов:
   sudo unshare --pid --fork --mount-proc /bin/bash
   ps aux # Отобразит только что созданный bash как PID 1

   ```

   **Типичная ошибка:** Считать контейнеры аналогом виртуальных машин. Процессы внутри namespace исполняются на том же самом ядре хоста без эмуляции виртуального железа и гипервизоров.

   **Источник:** [Linux man pages: namespaces(7)](https://man7.org/linux/man-pages/man7/namespaces.7.html)

   ---

50. Чем Linux отличается от Unix на концептуальном уровне?

   **Ответ:** Исторический Unix (AT&T, BSD, Solaris) — проприетарное семейство ОС со строгой монолитной интеграцией ядра и базового набора утилит. Linux концептуально создавался «с нуля» как свободный, POSIX-совместимый клон ядра без проприетарного кода Unix, развиваемый на основе открытого сообщества. Архитектурно Linux сделал ставку на полностью монолитное ядро с динамическими модулями (LKM), модель потоков NPTL «поток как процесс с общими ресурсами», интеграцию псевдофайловых систем sysfs/procfs и ориентацию на масштабирование от мелких роутеров до топ-суперкомпьютеров.

   **Пример:**

   ```bash
   # Проверка соответствия стандартам POSIX через макросы:
   getconf _POSIX_VERSION

   ```

   **Типичная ошибка:** Считать Linux прямой веткой исходного кода Unix. Linux был написан Линусом Торвальдсом полностью с чистого листа и является «Unix-like» (Unix-подобной) системой, не содержащей юридического или кодового наследия исходного Bell Labs Unix.

   **Источник:** [The Single UNIX Specification: History and Concepts](https://www.unix.org/what_is_unix/history_timeline.html)

## Filesystem Hierarchy (FHS)


---

51. Что такое FHS?

   **Ответ:** FHS (Filesystem Hierarchy Standard) — стандарт, определяющий структуру каталогов, размещение файлов и их назначение в Unix-подобных операционных системах. Он регламентирует, где должны лежать исполняемые файлы, конфигурации, библиотеки, логи и временные данные, чтобы программное обеспечение могло предсказуемо работать на любых дистрибутивах.

   **Пример:**

   ```bash
   man hier
   # Системное описание иерархии файловой системы в соответствии с FHS

   ```

   **Типичная ошибка:** Считать FHS жестким требованием ядра Linux. FHS — это соглашение уровня пользовательского пространства (user space), соблюдаемое дистрибутивами (Debian, RHEL, Arch) и утилитами, но не контролируемое ядром.

   **Источник:** [Filesystem Hierarchy Standard (Linux Foundation Specifications)](https://refspecs.linuxfoundation.org/fhs.shtml)

   ---

52. Зачем нужен стандарт иерархии файловой системы?

   **Ответ:** Стандарт необходим для интероперабельности: пакетные менеджеры (`apt`, `dnf`), сборочные системы (`cmake`, `autotools`), скрипты и демоны должны знать заранее согласованные пути установки бинарников, заголовочных файлов и поиска конфигураций без ручной адаптации под каждый отдельный дистрибутив. Также стандарт позволяет монтировать каталоги (`/usr`, `/var`, `/home`) на независимые физические диски или сетевые хранилища (NFS).

   **Пример:**

   ```cmake
   # CMake использует стандартные пути GNUInstallDirs, опирающиеся на FHS:
   include(GNUInstallDirs)
   install(TARGETS my_app DESTINATION ${CMAKE_INSTALL_BINDIR}) # /usr/local/bin или /usr/bin

   ```

   **Типичная ошибка:** Жестко прописывать (hardcode) нестандартные пути вроде `/my_configs/app.conf` вместо канонического пути `/etc/app.conf` или `$XDG_CONFIG_HOME`.

   **Источник:** [Linux Standard Base Core Specification](https://refspecs.linuxfoundation.org/lsb.shtml)

   ---

53. Что находится в / ?

   **Ответ:** Каталог `/` (root directory, корень) — вершина единой иерархической файловой системы в Linux. В нем монтируется корневая файловая система (rootfs), содержащая минимально необходимый набор каталогов (`/bin`, `/sbin`, `/etc`, `/lib`, `/dev`), требуемый для запуска ядра, монтирования других разделов и аварийного восстановления системы.

   **Пример:**

   ```bash
   ls -ld /
   # Вывод: drwxr-xr-x ... /

   ```

   **Типичная ошибка:** Путать корневой каталог `/` (root directory) и домашний каталог суперпользователя `/root` (root user's home).

   **Источник:** [FHS 3.0: The Root Filesystem](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03.html)

   ---

54. Для чего используется /bin?

   **Ответ:** Исторически каталог `/bin` предназначен для хранения базовых системных утилит и команд общего назначения (для всех пользователей), которые критически необходимы как при нормальной работе, так и в однопользовательском режиме (single-user mode), когда каталог `/usr` еще не смонтирован (`sh`, `bash`, `cp`, `ls`, `cat`).

   **Пример:**

   ```bash
   ls -l /bin/cat /bin/sh

   ```

   **Типичная ошибка:** Помещать в `/bin` бинарники пользовательских сервисов или скриптов автоматизации проекта. Для стороннего ПО предназначены `/usr/local/bin` или `/opt`.

   **Источник:** [FHS 3.0: /bin : Essential user command binaries](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s04.html)

   ---

55. Для чего используется /sbin?

   **Ответ:** Каталог `/sbin` (System Binaries) содержит утилиты системного администрирования, необходимые для начальной загрузки, восстановления, монтирования файловых систем и настройки сети (`fsck`, `init`, `reboot`, `iptables`, `fdisk`). Эти команды требуют привилегий суперпользователя (`root`) для выполнения.

   **Пример:**

   ```bash
   which fdisk ip
   # /sbin/fdisk (или /usr/sbin/fdisk)
   # /sbin/ip (или /usr/sbin/ip)

   ```

   **Типичная ошибка:** Полагать, что обычный пользователь технически не может запустить бинарник из `/sbin`. Запустить файл с правами на чтение и исполнение (`rx`) можно, однако системный вызов ядра внутри утилиты завершится с ошибкой `EPERM` (Operation not permitted) из-за отсутствия capabilities/root.

   **Источник:** [FHS 3.0: /sbin : Essential system binaries](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s16.html)

   ---

56. Чем /bin отличается от /sbin?

   **Ответ:** Различие заключается в целевой аудитории и правах: `/bin` содержит утилиты общего назначения, доступные и регулярно используемые любыми рядовыми пользователями системы, в то время как `/sbin` содержит низкоуровневые административные утилиты, предназначенные для системного администратора (`root`) и работы загрузочных сценариев ОС.

   **Пример:**

   | Каталог | Назначение | Примеры утилит |
   | --- | --- | --- |
   | `/bin` | Общепользовательские базовые команды | `ls`, `cat`, `grep`, `mkdir`, `cp` |
   | `/sbin` | Утилиты администрирования и железа | `mkfs`, `iptables`, `sysctl`, `shutdown` |

   **Типичная ошибка:** Добавлять `/sbin` в переменную окружения `$PATH` непривилегированных пользователей, ожидая, что системные утилиты смогут менять состояние ОС без `sudo`.

   **Источник:** [FHS 3.0: Dual binary hierarchy](https://refspecs.linuxfoundation.org/FHS_3.0/)

   ---

57. Для чего нужен /etc?

   **Ответ:** Каталог `/etc` (Extended Text Config / Editable Text Configuration) зарезервирован исключительно для хранения общесистемных статических конфигурационных текстовых файлов системы и установленных демонов. В нем настраиваются параметры загрузки, пользователи, сетевые интерфейсы и демоны сервисов.

   **Пример:**

   ```bash
   ls /etc/fstab /etc/resolv.conf /etc/passwd

   ```

   **Типичная ошибка:** Размещать исполняемые скомпилированные бинарные файлы внутри `/etc`. Стандарт FHS категорически запрещает размещение исполняемых бинарников в `/etc` (допустимы только shell-скрипты инициализации).

   **Источник:** [FHS 3.0: /etc : Host-specific configuration](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s07.html)

   ---

58. Что обычно хранится в /etc?

   **Ответ:** В каталоге хранятся текстовые конфигурации:

   * `/etc/passwd`, `/etc/shadow` — база учетных записей и хэшей паролей;
   * `/etc/fstab` — таблица автомонтирования файловых систем;
   * `/etc/hosts`, `/etc/resolv.conf` — параметры сетевого разрешения DNS;
   * `/etc/systemd/` — конфигурационные юниты служб systemd;
   * Подкаталоги конфигураций серверов: `/etc/nginx/`, `/etc/ssh/`.

   **Пример:**

   ```bash
   cat /etc/os-release
   # Спецификация дистрибутива и версии ОС

   ```

   **Типичная ошибка:** Ручная правка `/etc/resolv.conf` на современных системах с `systemd-resolved` или `NetworkManager`: файл часто является symlink на файл в `/run` и перезаписывается демоном на лету.

   **Источник:** [Linux man pages: hier(7)](https://man7.org/linux/man-pages/man7/hier.7.html)

   ---

59. Почему конфиги лежат именно в /etc?

   **Ответ:** Исторически в первых версиях Unix (Bell Labs) в `/etc` сбрасывалось все вспомогательное («etcetera» — «и так далее»), что не являлось чистым бинарником пользователя. По мере стандартизации FHS каталог закрепили строго за машинно-специфичными (host-specific) текстовыми конфигурационными файлами, не зависящими от архитектуры процессора (architecture-independent).

   **Пример:**

   ```bash
   # Файлы в /etc машинно-зависимы: если смонтировать общий сетевой /usr по NFS на 10 серверов,
   # то /etc у каждой машины должен оставаться свой собственный.

   ```

   **Типичная ошибка:** Распространять общий сетевой `/etc` между разными серверами кластера без шаблонизации: каждый сервер имеет уникальные параметры (`machine-id`, `hostname`, `fstab`).

   **Источник:** [Dennis M. Ritchie: The Evolution of the Unix Time-sharing System](https://www.bell-labs.com/usr/dmr/www/hist.html)

   ---

60. Что находится в /home?

   **Ответ:** Каталог `/home` служит местом размещения домашних директорий пользователей (`/home/<username>`). Внутри каждой домашней папки пользователь хранит личные данные, документы, локальные репозитории кода и пользовательские конфигурации программ (dotfiles).

   **Пример:**

   ```bash
   echo $HOME
   # /home/developer

   ```

   **Типичная ошибка:** Жестко рассчитывать, что домашняя папка всегда лежит в `/home`. Путь определяется полем в файле `/etc/passwd` и для конкретных пользователей может находиться в `/var/lib/daemon` или на сетевом диске LDAP.

   **Источник:** [FHS 3.0: /home : User home directories](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s08.html)

   ---

61. Что хранится в /root?

   **Ответ:** Каталог `/root` — домашняя директория суперпользователя `root`. В отличие от обычных пользователей, чьи каталоги располагаются в `/home`, профиль `root` расположен непосредственно на корневом разделе `/`, что гарантирует доступ к учетной записи администратора при сбоях монтирования вспомогательных файловых систем.

   **Пример:**

   ```bash
   sudo ls -la /root
   # Личные dotfiles суперпользователя: .bashrc, .ssh, .profile

   ```

   **Типичная ошибка:** Попытка зайти в `/root` под обычным непривилегированным пользователем: по умолчанию каталог имеет строгие права доступа `0700` (`drwx------`).

   **Источник:** [FHS 3.0: /root : Home directory for the root user](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s14.html)

   ---

62. Чем /root отличается от /home/root?

   **Ответ:** `/root` лежит непосредственно на корневом разделе файловой системы, а `/home` исторически часто выносится на отдельный физический диск, LVM-том или сетевой ресурс (NFS). Если бы профиль root находился в `/home/root`, при сбое или повреждении монтирования раздела `/home` администратор не смог бы войти в систему для восстановления в аварийном режиме. Путь `/home/root` в стандартных дистрибутивах Linux отсутствует.

   **Пример:**

   ```
   [Диск 1: Rootfs] ───► /root (всегда доступен на корне)
   [Диск 2: Раздел Home] ───► /home/user1, /home/user2 (монтируется позже)

   ```

   **Типичная ошибка:** Вручную переносить домашнюю директорию root в `/home/root` в файле `/etc/passwd`, нарушая отказоустойчивость загрузки в emergency mode.

   **Источник:** [Linux Standard Base: System Administrator Home Directory](https://refspecs.linuxfoundation.org/)

   ---

63. Для чего нужен /tmp?

   **Ответ:** Каталог `/tmp` (Temporary) предназначен для временных файлов, создаваемых программами во время выполнения. Доступ на создание файлов в `/tmp` открыт для любых пользователей и процессов, а его содержимое очищается системой при перезагрузке (или автоматически демонами очистки раз в заданный период).

   **Пример:**

   ```bash
   ls -ld /tmp
   # drwxrwxrwt ... /tmp (права 1777 — полный доступ с Sticky bit)

   ```

   **Типичная ошибка:** Использовать `/tmp` для хранения файлов, которые должны гарантированно пережить перезагрузку системы (для этого используется `/var/tmp`).

   **Источник:** [FHS 3.0: /tmp : Temporary files](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s18.html)

   ---

64. Какие особенности у /tmp?

   **Ответ:**

      1. **Sticky Bit (`chmod +t` / права `1777`):** Любой пользователь может создавать файлы, но удалять или переименовывать файл имеет право только его владелец или `root`.

      2. **Монтирование в RAM (tmpfs):** В современных дистрибутивах `/tmp` часто монтируется как файловая система в оперативной памяти, что дает высокую скорость I/O, но расходует ОЗУ при записи больших объемов.

   **Пример:**

   ```bash
   df -h /tmp
   # Filesystem  Size  Used  Avail  Use%  Mounted on
   # tmpfs       16G   1.2M  16G    1%    /tmp

   ```

   **Типичная ошибка:** Небезопасное создание файлов в `/tmp` с фиксированным именем (insecure temp file vulnerability), ведущее к атакам через symlink race condition (вместо этого нужно использовать `mkstemp()` или `std::filesystem::temp_directory_path()`).

   **Источник:** [CWE-377: Insecure Temporary File](https://cwe.mitre.org/data/definitions/377.html)

   ---

65. Что обычно хранится в /var?

   **Ответ:** Каталог `/var` (Variable data) предназначен для хранения изменяемых данных, размер которых динамически растет в процессе штатной работы операционной системы: системные логи, spool-очереди печати и почты, кэши пакетных менеджеров, временные runtime-блокировки и базы данных.

   **Пример:**

   ```bash
   du -sh /var/*
   # /var/log, /var/cache, /var/lib, /var/spool

   ```

   **Типичная ошибка:** Размещать статические бинарники программ в `/var`. Данный каталог должен содержать исключительно динамически меняющиеся данные приложений.

   **Источник:** [FHS 3.0: /var : Variable data](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch05.html)

   ---

66. Что лежит в /var/log?

   **Ответ:** В каталоге `/var/log` централизованно хранятся текстовые и бинарные файлы журналов (логов) ядра, операционной системы, служб аутентификации и сторонних сервисов (`syslog`, `journald`, `auth.log`, логи веб-серверов nginx, СУБД).

   **Пример:**

   ```bash
   ls /var/log/nginx/ /var/log/dmesg /var/log/auth.log

   ```

   **Типичная ошибка:** Не настраивать ротацию логов (`logrotate`): неконтролируемый рост файлов в `/var/log` может полностью переполнить дисковое пространство раздела, заблокировав запись для баз данных и системных сервисов.

   **Источник:** [Linux man pages: logrotate(8)](https://man7.org/linux/man-pages/man8/logrotate.8.html)

   ---

67. Для чего нужен /var/tmp?

   **Ответ:** Каталог `/var/tmp` предназначен для хранения временных файлов большого размера или файлов, которые должны гарантированно сохраняться между перезагрузками операционной системы (например, кэши компиляции ccache, дампы отчетов, образы временных дампов баз данных).

   **Пример:**

   ```cpp
   #include <filesystem>
   // Использование /var/tmp для файлов, требующих выживания после перезагрузки узла:
   namespace fs = std::filesystem;
   fs::path p = "/var/tmp/large_calculation_checkpoint.dat";

   ```

   **Типичная ошибка:** Полагать, что файлы в `/var/tmp` хранятся вечно. По стандарту systemd-tmpfiles файлы в `/var/tmp` удаляются, если к ним не обращались в течение 30 дней (для `/tmp` — обычно 10 дней или каждая перезагрузка).

   **Источник:** [FHS 3.0: /var/tmp : Temporary files preserved between reboots](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch05s15.html)

   ---

68. Чем /tmp отличается от /var/tmp?

   **Ответ:** Различие состоит в энергонезависимости и времени жизни: `/tmp` обычно расположен в ОЗУ (`tmpfs`) и полностью очищается при каждом ребуте, а `/var/tmp` всегда размещается на постоянном дисковом носителе и сохраняет данные при перезагрузке машины.

   **Пример:**

   | Характеристика | `/tmp` | `/var/tmp` |
   | --- | --- | --- |
   | Носитель | Часто RAM (`tmpfs`) | Физический диск |
   | Очистка при reboot | Да (гарантированно очищается) | Нет (сохраняется) |
   | Срок хранения | Кратковременный (часы / дни) | Долговременный (по умолчанию 30 дней) |

   **Типичная ошибка:** Записывать временный файл объемом 100 ГБ в `/tmp`, смонтированный в `tmpfs` на машине с 32 ГБ RAM. Система исчерпает память и аварийно завершит процессы через OOM Killer; такие файлы необходимо направлять в `/var/tmp`.

   **Источник:** [systemd-tmpfiles configuration: tmp.conf](https://www.freedesktop.org/software/systemd/man/tmpfiles.d.html)

   ---

69. Что находится в /usr?

   **Ответ:** Каталог `/usr` (Unix System Resources / Universal System Resources) содержит вторую, основную иерархию системы: всё прикладное ПО, библиотеки, документацию, заголовочные файлы и графические среды, доступные только для чтения обычным пользователям. Исторически `/usr` проектировался как раздел, доступный для монтирования в режиме Read-Only сразу нескольким машинам по сети.

   **Пример:**

   ```bash
   ls /usr
   # bin  include  lib  lib64  local  sbin  share  src

   ```

   **Типичная ошибка:** Считать, что каталог `/usr` изменяется при обычной пользовательской работе. Данные в `/usr` модифицируются исключительно системным пакетным менеджером при установке/обновлении ПО.

   **Источник:** [FHS 3.0: /usr : Secondary hierarchy](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch04.html)

   ---

70. Почему /usr — не домашняя папка пользователя?

   **Ответ:** В 1970-х годах в Unix на PDP-11 первый жесткий диск переполнился, и разработчики смонтировали второй диск в точку `/usr` («user»), перенеся туда пользовательские папки. Однако очень быстро `/usr` заполнился общими утилитами операционной системы, компиляторами и библиотеками. Для домашних директорий пользователей создали отдельный каталог `/home`, а аббревиатуру `/usr` ретроспективно переосмыслили как **Unix System Resources**.

   **Пример:**

   ```
   Историческая трансформация:
   1971: /usr/dmr, /usr/ken (домашки)
   1980-е: /home/dmr (домашки вынесены), /usr становится хранилищем системного софта

   ```

   **Типичная ошибка:** Создавать учетные записи пользователей с путями домашних директорий в `/usr/<username>`.

   **Источник:** [Ken Thompson, Dennis Ritchie: Bell Labs Unix History Notes](https://www.bell-labs.com/)

   ---

71. Что хранится в /usr/bin?

   **Ответ:** Каталог `/usr/bin` содержит подавляющее большинство скомпилированных исполняемых пользовательских программ и утилит, установленных пакетным менеджером дистрибутива (`python3`, `gcc`, `git`, `curl`, `gdb`).

   **Пример:**

   ```bash
   which git g++
   # /usr/bin/git
   # /usr/bin/g++

   ```

   **Типичная ошибка:** Вручную копировать собственные бинарники самописных проектов в `/usr/bin`. Каталог полностью управляется пакетным менеджером (`apt`/`dnf`), который может стереть или затереть сторонний файл при обновлении пакетов.

   **Источник:** [FHS 3.0: /usr/bin : Most user commands](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch04s04.html)

   ---

72. Что хранится в /usr/lib?

   **Ответ:** Каталог `/usr/lib` (или `/usr/lib64`) содержит динамические и статические разделяемые библиотеки (`.so`, `.a`), необходимые для работы бинарников из `/usr/bin` и `/usr/sbin`, а также внутренние бинарные модули пакетов, не предназначенные для прямого вызова пользователем.

   **Пример:**

   ```bash
   ls /usr/lib/x86_64-linux-gnu/libstdc++.so.*

   ```

   **Типичная ошибка:** Путать `/usr/lib` и `/usr/libexec`. Вспомогательные исполняемые бинарные программы демонов по стандарту FHS 3.0 должны размещаться в `/usr/libexec`, а не в библиотечных каталогах.

   **Источник:** [FHS 3.0: /usr/lib : Libraries for programming and packages](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch04s06.html)

   ---

73. Что хранится в /usr/local?

   **Ответ:** Каталог `/usr/local` предназначен для программ, утилит и библиотек, устанавливаемых системным администратором вручную (например, сборка из исходников через `make install`, минуя официальный пакетный менеджер ОС). Он имеет ту же внутреннюю структуру, что и `/usr` (`bin`, `lib`, `include`, `share`).

   **Пример:**

   ```bash
   # Ручная сборка библиотеки из исходников по умолчанию ставится сюда:
   cmake -B build -DCMAKE_INSTALL_PREFIX=/usr/local
   cmake --install build
   # Заголовочные файлы попадут в /usr/local/include, а библиотека — в /usr/local/lib

   ```

   **Типичная ошибка:** Очищать `/usr/local` пакетным менеджером дистрибутива. Пакетный менеджер Linux никогда не трогает содержимое `/usr/local` при штатных операциях обновления ОС.

   **Источник:** [FHS 3.0: /usr/local : Local hierarchy](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch04s09.html)

   ---

74. Чем /usr/local/bin отличается от /usr/bin?

   **Ответ:** `/usr/bin` управляется исключительно системным пакетным менеджером ОС (`apt`, `dnf`, `pacman`). `/usr/local/bin` управляется администратором вручную для кастомных сборок. В переменной `$PATH` каталог `/usr/local/bin` по умолчанию стоит **раньше**, чем `/usr/bin`, что позволяет переопределять системные версии утилит собственными сборками.

   **Пример:**

   ```bash
   echo $PATH
   # Вывод: /usr/local/bin:/usr/bin:/bin:...
   # Если положить свой cmake в /usr/local/bin, вызов 'cmake' выполнит именно его, а не системный из /usr/bin

   ```

   **Типичная ошибка:** Устанавливать утилиты из исходников прямо в `/usr/bin`, перезаписывая системные зависимости дистрибутива.

   **Источник:** [FHS 3.0: /usr/local/bin](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch04s09.html)

   ---

75. Когда программы ставятся в /opt?

   **Ответ:** Каталог `/opt` (Optional software) зарезервирован для установки крупного стороннего, проприетарного или монолитного программного обеспечения, которое поставляется в виде самодостаточного изолированного пакета и не разбивается по стандартным каталогам системы (`/opt/<vendor>/<package>` — например, Google Chrome, CLion, Docker Desktop).

   **Пример:**

   ```bash
   ls -d /opt/*
   # /opt/google/chrome
   # /opt/jetbrains

   ```

   **Типичная ошибка:** Ожидать, что бинарники из `/opt/myapp/bin` будут доступны сразу в консоли. Каталоги из `/opt` не входят в `$PATH` по умолчанию; для запуска создают symlink в `/usr/local/bin` или настраивают переменную окружения.

   **Источник:** [FHS 3.0: /opt : Add-on application software packages](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s13.html)

   ---

76. Для чего нужен /dev?

   **Ответ:** Каталог `/dev` (Devices) содержит специальные файлы устройств, предоставляющие интерфейс ввода-вывода к драйверам оборудования ядра (диски, видеокарты, последовательные порты, псевдотерминалы) и виртуальным генераторам ядра (`/dev/null`, `/dev/urandom`). Файловая система управляется ядром динамически через `devtmpfs` и демон `udev`.

   **Пример:**

   ```bash
   ls -l /dev/sda /dev/urandom

   ```

   **Типичная ошибка:** Пытаться создать файл устройства обычной командой `touch`. Файлы устройств создаются системным вызовом `mknod()` с указанием типа (block/character) и номеров major/minor, либо автоматически ядром через udev.

   **Источник:** [Linux man pages: udev(7)](https://man7.org/linux/man-pages/man7/udev.7.html)

   ---

77. Что такое device files в /dev?

   **Ответ:** Device files (файлы устройств / специальные файлы узлов) — это точки входа в драйверы ядра, представленные в VFS. Они не занимают места на диске и идентифицируются двумя числами: **Major number** (определяет драйвер ядра) и **Minor number** (определяет конкретное устройство или раздел этого драйвера). Разделяются на символьные (`c`, побайтовый поток: мыши, терминалы) и блочные (`b`, произвольный блочный доступ через page cache: SSD, HDD).

   **Пример:**

   ```bash
   ls -l /dev/null /dev/nvme0n1
   # crw-rw-rw- 1 root root  1, 3 ... /dev/null     (Character: Major 1, Minor 3)
   # brw-rw---- 1 root disk 259, 0 ... /dev/nvme0n1 (Block: Major 259, Minor 0)

   ```

   **Типичная ошибка:** Считать, что чтение из блочного устройства (`/dev/sda`) идет в обход оперативной памяти. Доступ к блочным файлам устройств кэшируется в системном Page Cache так же, как и обычные файлы.

   **Источник:** [Linux man pages: mknod(2)](https://man7.org/linux/man-pages/man2/mknod.2.html)

   ---

78. Что такое /proc и почему он выглядит как обычная ФС?

   **Ответ:** `/proc` — псевдофайловая система (procfs), генерируемая ядром Linux непосредственно в RAM. Она реализована через интерфейс VFS (Virtual File System) ядра: функции чтения/записи VFS перенаправляются на внутренние структуры ядра, поэтому системная информация выглядит как стандартные текстовые файлы и папки для удобства навигации стандартными утилитами Unix (`cat`, `grep`).

   **Пример:**

   ```cpp
   #include <fstream>
   #include <string>

   // Чтение параметров ядра через стандартный интерфейс файлового ввода-вывода:
   std::ifstream file("/proc/sys/kernel/osrelease");
   std::string release;
   file >> release;

   ```

   **Типичная ошибка:** Пытаться открыть файл из `/proc` в режиме одновременного чтения и записи (`O_RDWR`), если файл ядра поддерживает только односторонний вывод или одностороннюю конфигурацию.

   **Источник:** [Linux Kernel Documentation: The /proc Filesystem](https://docs.kernel.org/filesystems/proc.html)

   ---

79. Что можно посмотреть в /proc/cpuinfo?

   **Ответ:** Файл содержит детальные аппаратные характеристики каждого логического ядра CPU, зарегистрированного ядром: архитектуру, модель процессора, тактовую частоту, размер кэшей (L1/L2/L3), физический ID сокета, а также флаги аппаратных инструкций (SSE, AVX-512, VMX, AES).

   **Пример:**

   ```bash
   grep -m 1 "model name" /proc/cpuinfo
   grep "flags" /proc/cpuinfo | head -n 1

   ```

   **Типичная ошибка:** Парсить `/proc/cpuinfo` в latency-critical C++ коде для проверки инструкций при каждом вызове функции. Информацию парсят один раз при старте или используют вызов `getauxval(AT_HWCAP)` / инструкцию `cpuid`.

   **Источник:** [Linux man pages: proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html)

   ---

80. Что можно посмотреть в /proc/meminfo?

   **Ответ:** Файл предоставляет полную оперативную сводку подсистемы виртуальной памяти ядра: общий объем ОЗУ (`MemTotal`), свободную память (`MemFree`), доступную для новых приложений без ухода в swap память (`MemAvailable`), объем Page Cache (`Cached`), размер буферов ядра (`Buffers`), использование Swap, а также объем структур SLAB-аллокатора ядра.

   **Пример:**

   ```bash
   grep -E "MemTotal|MemAvailable|SwapFree" /proc/meminfo

   ```

   **Типичная ошибка:** Считать показатель `MemFree` индикатором нехватки памяти в Linux. Ядро намеренно утилизирует «свободную» память под кэширование файлов (Page Cache). Реальным индикатором доступных ресурсов является поле `MemAvailable`.

   **Источник:** [Linux man pages: proc(5) - /proc/meminfo](https://man7.org/linux/man-pages/man5/proc.5.html)

   ---

81. Что такое /proc/?

   **Ответ:** Директория в `procfs`, представляющая состояние конкретного процесса с идентификатором `PID`. Содержит метаданные процесса:

   * `/proc/<pid>/cmdline` — аргументы запуска;
   * `/proc/<pid>/status` — детальный статус, потребление памяти (VmRSS, VmSize) и потоки;
   * `/proc/<pid>/fd/` — симлинки на все открытые файловые дескрипторы;
   * `/proc/<pid>/maps` — карта виртуального адресного пространства (VMA);
   * `/proc/<pid>/exe` — симлинк на исполняемый ELF-файл на диске.

   **Пример:**

   ```bash
   # Просмотр открытых сокетов и файлов текущего процесса оболочки:
   ls -l /proc/$$/fd

   ```

   **Типичная ошибка:** Читать `/proc/<pid>/cmdline` как одну строку с пробелами: ядро разделяет аргументы символом `\0` (null byte), а не пробелом.

   **Источник:** [Linux man pages: proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html)

82. Для чего нужен /sys?

   **Ответ:** Каталог `/sys` (sysfs) — псевдофайловая система, отражающая внутреннее объектное дерево ядра (`kobjects`). Она предназначена для структурированного экспорта информации об устройствах, драйверах, системных шинах (PCI, USB), топологии ядер CPU, энергопотреблении и блочных очередях в строгом машиночитаемом формате «один параметр — один файл».

   **Пример:**

   ```bash
   # Чтение максимальной частоты процессора CPU 0:
   cat /sys/devices/system/cpu/cpu0/cpufreq/cpuinfo_max_freq

   ```

   **Типичная ошибка:** Парсить конфигурацию устройств через сырой вывод `dmesg` вместо использования структурированных узлов в `/sys`.

   **Источник:** [Linux Kernel Documentation: sysfs](https://docs.kernel.org/filesystems/sysfs.html)

83. Что находится в /run?

   **Ответ:** Каталог `/run` — энергонезависимая псевдофайловая система в оперативной памяти (`tmpfs`), хранящая runtime-состояние системы с момента загрузки: pid-файлы запущенных демонов, UNIX Domain Sockets (`.sock`), lock-файлы и сокеты управления systemd. Очищается при выключении питания.

   **Пример:**

   ```bash
   ls /run/systemd/system /run/user/1000

   ```

   **Типичная ошибка:** Использовать устаревший путь `/var/run`. В современных системах `/var/run` является простой символической ссылкой на `/run` для обеспечения обратной совместимости.

   **Источник:** [FHS 3.0: /run : Run-time variable data](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s15.html)

   ---

84. Что находится в /mnt?

   **Ответ:** Каталог `/mnt` (Mount) предназначен для временного ручного монтирования файловых систем системным администратором (например, аварийное подключение диска для восстановления `mount /dev/sdb1 /mnt`).

   **Пример:**

   ```bash
   sudo mount /dev/sdb1 /mnt
   cd /mnt

   ```

   **Типичная ошибка:** Использовать `/mnt` для постоянного автомонтирования дисков серверов в продакшене. Долговременные точки монтирования принято размещать в подкаталогах вроде `/data`, `/srv` или специализированных путях.

   **Источник:** [FHS 3.0: /mnt : Mount point for a temporarily mounted filesystem](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s12.html)

   ---

85. Что находится в /media?

   **Ответ:** Каталог `/media` используется как точка автомонтирования сменных носителей информации (USB-флешки, внешние жесткие диски, CD/DVD-диски), подключаемых пользователем. Монтирование выполняется автоматически системными демонами (например, `udisks2`) в поддиректории вида `/media/<user>/<label>`.

   **Пример:**

   ```bash
   ls /media/$USER/
   # Отобразит вставленный внешний накопитель "USB_FLASH"

   ```

   **Типичная ошибка:** Ожидать автоматического монтирования флешек в `/mnt`. Графические оболочки и сервисы рабочего стола монтируют сменные диски строго в `/media`.

   **Источник:** [FHS 3.0: /media : Mount point for removable media](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s11.html)

   ---

86. Чем /mnt отличается от /media?

   **Ответ:** `/mnt` предназначен для статического ручного монтирования системным администратором для служебных разовых нужд. `/media` используется операционной системой для автоматического динамического монтирования сменных пользовательских носителей с генерацией подкаталогов по имени носителя.

   **Пример:**

   | Каталог | Тип монтирования | Кем управляется | Применение |
   | --- | --- | --- | --- |
   | `/mnt` | Ручное | Системный администратор (`root`) | Временный диск для бэкапа, chroot |
   | `/media` | Автоматическое | Системные службы (`udisks2`) | Вставленная USB-флешка, диск |

   **Типичная ошибка:** Монтировать сетевой NFS-ресурс прямо в корень `/media`, ломая структуру автодетекта съемных устройств.

   **Источник:** [FHS 3.0: Comparison of /mnt and /media](https://refspecs.linuxfoundation.org/FHS_3.0/)

87. Что хранится в /boot?

   **Ответ:** Каталог `/boot` содержит всё необходимое для начального этапа загрузки ОС до момента инициализации VFS ядра: сжатый бинарный образ ядра Linux (`vmlinuz`), образ начальной файловой системы RAM (`initramfs` / `initrd`), карту системных символов ядра (`System.map`) и конфигурацию загрузчика GRUB (`/boot/grub/grub.cfg`).

   **Пример:**

   ```bash
   ls /boot
   # config-6.8.0-31-generic  initrd.img-6.8.0-31-generic  vmlinuz-6.8.0-31-generic  grub

   ```

   **Типичная ошибка:** Переполнение раздела `/boot` старыми ядрами. Если `/boot` вынесен на отдельный небольшой раздел (например, 500 МБ), накопление старых версий ядер блокирует обновление системы из-за невозможности сгенерировать новый initramfs.

   **Источник:** [FHS 3.0: /boot : Static files of the boot loader](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s05.html)

   ---

88. Что такое initramfs?

   **Ответ:** Initramfs (initial RAM filesystem) — сжатый cpio-архив корневой файловой системы, который ядро распаковывает в rootfs при загрузке; внешний архив передаётся ядру загрузчиком. Он содержит минимальный набор драйверов (для контроллеров дисков NVMe/SATA, RAID, шифрования LUKS, LVM) и скриптов, необходимых для обнаружения и монтирования реального корневого раздела (`/`), после чего управление передается постоянному `/sbin/init`.

   **Пример:**

   ```bash
   lsinitramfs /boot/initrd.img-$(uname -r) | grep nvme

   ```

   **Типичная ошибка:** Полагать, что ядро Linux содержит драйверы для всех существующих дисковых контроллеров внутри файла `vmlinuz`. Ядро делают компактным, а драйверы контроллеров дисков выносят в модули внутри `initramfs`.

   **Источник:** [Linux Kernel Documentation: ramfs-rootfs-initramfs](https://docs.kernel.org/filesystems/ramfs-rootfs-initramfs.html)

   ---

89. Что лежит в /lib?

   **Ответ:** Исторически каталог `/lib` содержит критически важные разделяемые библиотеки (`libc.so`, динамический компоновщик `ld-linux.so`), необходимые для запуска бинарников из `/bin` и `/sbin`, а также каталог с модулями текущего ядра Linux (`/lib/modules/$(uname -r)/`).

   **Пример:**

   ```bash
   ls /lib/modules/$(uname -r)
   # Драйверы ядра (.ko), скомпилированные под текущую запущенную версию

   ```

   **Типичная ошибка:** Попытка вручную скопировать стороннюю библиотеку в `/lib` вместо использования стандартного `/usr/local/lib` или настройки `rpath`/`LD_LIBRARY_PATH`.

   **Источник:** [FHS 3.0: /lib : Essential shared libraries and kernel modules](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s10.html)

   ---

90. Чем /lib отличается от /usr/lib?

   **Ответ:** В классическом FHS разделение строгое: в `/lib` располагаются библиотеки, жизненно необходимые для старта системы в аварийном режиме до монтирования раздела `/usr` (базовая `libc`, math library). В `/usr/lib` находятся библиотеки для остального прикладного ПО (`libcurl`, `libssl`, библиотеки GUI и фреймворков). В современных дистрибутивах (UsrMerge) `/lib` является символической ссылкой на `/usr/lib`.

   **Пример:**

   ```bash
   ls -ld /lib
   # lrwxrwxrwx 1 root root 7 ... /lib -> usr/lib

   ```

   **Типичная ошибка:** Полагаться в скриптах на физическую раздельность каталогов `/lib` и `/usr/lib` на современных дистрибутивах Linux.

   **Источник:** [The Case for the /usr Merge: Lennart Poettering](https://www.freedesktop.org/wiki/Software/systemd/TheCaseForTheUsrMerge/)

   ---

91. Что такое symbolic links внутри FHS?

   **Ответ:** Символическая ссылка (symlink) — специальный тип файла в VFS, содержащий в виде текста путь к целевому файлу или директории. Внутри FHS symlink активно используются для обеспечения обратной совместимости при переходе на новые схемы стандартов (например, ссылки на объединенный `/usr`, ссылки на версионированные библиотеки `libfoo.so -> libfoo.so.1.0`).

   **Пример:**

   ```bash
   ls -l /usr/lib/x86_64-linux-gnu/libz.so
   # lrwxrwxrwx ... libz.so -> libz.so.1.2.13

   ```

   **Типичная ошибка:** Создание циклических символических ссылок (`a -> b -> a`), вызывающее ошибку ядра `ELOOP` (Too many levels of symbolic links).

   **Источник:** [Linux man pages: symlink(7)](https://man7.org/linux/man-pages/man7/symlink.7.html)

   ---

92. Почему /bin иногда является symlink на /usr/bin?

   **Ответ:** Это результат реформы **UsrMerge**. Историческое разделение на `/bin` и `/usr/bin` было обусловлено маленьким размером жестких дисков в 1970-х годах. В современных системах все бинарники объединили в единый каталог `/usr/bin`, а `/bin` оставили в виде символической ссылки (`/bin -> usr/bin`), чтобы сохранить совместимость со старыми скриптами с жестко прописанным шебангом `#!/bin/sh` или `#!/bin/bash`.

   **Пример:**

   ```bash
   ls -ld /bin /sbin /lib /lib64
   # lrwxrwxrwx ... /bin -> usr/bin
   # lrwxrwxrwx ... /sbin -> usr/sbin
   # lrwxrwxrwx ... /lib -> usr/lib
   # lrwxrwxrwx ... /lib64 -> usr/lib64

   ```

   **Типичная ошибка:** Попытка удалить «дублирующийся» каталог `/bin`, что моментально уничтожает всю систему исполнения команд ОС.

   **Источник:** [Debian Wiki: UsrMerge](https://wiki.debian.org/UsrMerge)

   ---

93. Что произойдет, если удалить важный файл из /etc?

   **Ответ:** Зависит от файла:

   * Удаление `/etc/fstab`: система не сможет смонтировать файловые системы при следующем ребуте и свалится в Emergency Shell.
   * Удаление `/etc/passwd`: перестанет работать авторизация, команды `sudo`, `login` и определение владельцев процессов.
   * Удаление `/etc/resolv.conf`: перестанет резолвиться сетевые доменные имена (DNS).
   Однако работающие процессы не упадут немедленно, так как они уже загрузили настройки в память при старте.

   **Пример:**

   ```bash
   # Восстановление типовых конфигов из шаблонов пакетов (Debian/Ubuntu):
   sudo apt-get install --reinstall -o Dpkg::Options::="--force-confmiss" <package_name>

   ```

   **Типичная ошибка:** Редактировать важные файлы в `/etc` без создания резервной копии (`cp /etc/fstab /etc/fstab.bak`).

   **Источник:** [Linux Administration Handbook: Configuration files failure](https://www.pearson.com/)

   ---

94. Где обычно лежат system-wide config файлы?

   **Ответ:** Общесистемные конфигурации располагаются строго в каталоге `/etc/` или его поддиректориях (`/etc/ssh/sshd_config`, `/etc/nginx/nginx.conf`). Конфигурации по умолчанию, поставляемые разработчиками пакетов и не предназначенные для прямой правки администратором, часто хранятся в `/usr/lib/<package>/` (например, `/usr/lib/systemd/system/`).

   **Пример:**

   ```bash
   # Иерархия переопределения конфигурации systemd:
   # 1. /etc/systemd/system/ (высший приоритет — переопределение администратором)
   # 2. /usr/lib/systemd/system/ (низший приоритет — дефолт пакета)

   ```

   **Типичная ошибка:** Редактировать дефолтные файлы конфигураций пакетов в `/usr/lib/`, которые будут перезаписаны при первом же обновлении системы через `apt upgrade`.

   **Источник:** [systemd.unit(5) — Unit Load Path](https://www.freedesktop.org/software/systemd/man/systemd.unit.html)

   ---

95. Где обычно лежат user-specific config файлы?

   **Ответ:** Пользовательские конфигурационные файлы располагаются в домашней директории пользователя `$HOME`. Согласно современному стандарту **XDG Base Directory Specification**, они должны лежать в каталоге `~/.config/` (`$XDG_CONFIG_HOME`), а исторически располагаются в виде скрытых dot-файлов прямо в корне домашнего каталога (`~/.bashrc`, `~/.vimrc`).

   **Пример:**

   ```bash
   echo ${XDG_CONFIG_HOME:-$HOME/.config}
   # Каноническое место пользовательских конфигов: ~/.config/<app_name>/config

   ```

   **Типичная ошибка:** Жестко записывать конфиги в корень `$HOME/.myapp` в новых программах вместо поддержки спецификации XDG (`~/.config/myapp`).

   **Источник:** [XDG Base Directory Specification](https://specifications.freedesktop.org/basedir-spec/basedir-spec-latest.html)

   ---

96. Что такое hidden files в home directory?

   **Ответ:** Hidden files («скрытые файлы» или dotfiles) — файлы или директории, имя которых начинается с символа точки (`.`). Утилита `ls` и графические менеджеры по умолчанию скрывают их отображение при обычном листинге. Традиционно используются для хранения индивидуальных пользовательских настроек окружения, профилей и кэшей.

   **Пример:**

   ```bash
   ls -a ~
   # .bashrc  .profile  .ssh  .config  .local  .cache

   ```

   **Типичная ошибка:** Считать, что точка в начале имени файла обеспечивает безопасность или защиту данных. Это исключительно соглашение отображения в утилитах пользовательского пространства (`ls` пропускает файлы, начинающиеся с точки, если не передан флаг `-a`).

   **Источник:** [Rob Pike: A brief history of the hidden dotfiles bug](https://plus.google.com/)

   ---

97. Что такое ~/.bashrc?

   **Ответ:** `~/.bashrc` — командный скрипт, исполняемый оболочкой Bash при запуске каждого нового интерактивного non-login шелла (например, открытие нового окна терминала в графической среде или запуск подоболочки `bash`). В нем настраиваются алиасы (`alias`), персональный вид приглашения ввода (`PS1`), функции и специфичные переменные окружения.

   **Пример:**

   ```bash
   # Фрагмент ~/.bashrc:
   alias ll='ls -alF'
   export EDITOR=vim

   ```

   **Типичная ошибка:** Добавлять в `~/.bashrc` команды, генерирующие текстовый вывод в `stdout` (например, `echo "Hello"`). Это может нарушить работу утилит удаленного копирования `scp` и `sftp`, которые ожидают чистый поток данных при открытии сессии.

   **Источник:** [GNU Bash Manual: Bash Startup Files](https://www.gnu.org/software/bash/manual/html_node/Bash-Startup-Files.html)

   ---

98. Что такое ~/.profile?

   **Ответ:** `~/.profile` — скрипт конфигурации, выполняемый один раз при успешном входе пользователя в систему (login shell). Он предназначен для общих настроек всей пользовательской сессии, не привязанных к конкретной оболочке (запуск ssh-agent, глобальный экспорт переменных `$PATH`, локали).

   **Пример:**

   ```bash
   # Добавление пользовательских бинарников в PATH на уровне всей сессии в ~/.profile:
   if [ -d "$HOME/.local/bin" ] ; then
       PATH="$HOME/.local/bin:$PATH"
   fi

   ```

   **Типичная ошибка:** Настраивать shell-специфичные псевдонимы (`alias`) внутри `~/.profile`: при запуске последующих подоболочек этот файл повторно не считывается.

   **Источник:** [POSIX.1-2017: sh startup](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html)

   ---

99. Чем отличаются system config и user config?

   **Ответ:** Различие заключается в области действия и правах:

      1. **System Config (`/etc/`):** Задает глобальные параметры системы по умолчанию, применяется ко всем пользователям ОС и может редактироваться только пользователем `root`.

      2. **User Config (`~/.config/`, dotfiles):** Находится в домашней папке пользователя, управляется самим пользователем без прав `sudo` и переопределяет общесистемные параметры конкретно для его сессии.

   **Пример:**

   ```
   Глобальный конфиг Git: /etc/gitconfig (для всех учетных записей машины)
   Пользовательский Git:  ~/.gitconfig   (переопределяет user.name и user.email для текущего юзера)

   ```

   **Типичная ошибка:** Менять общесистемный конфиг в `/etc/` для решения локальной задачи одного пользователя, подвергая риску остальных пользователей машины.

   **Источник:** [Linux man pages: hier(7)](https://man7.org/linux/man-pages/man7/hier.7.html)

100. Почему важно понимать FHS разработчику C/C++?

   **Ответ:** Разработчик C/C++ взаимодействует со стандартом FHS на всех стадиях жизненного цикла ПО:

      1. **Сборка и линковка:** Понимание стандартных путей поиска заголовочных файлов (`/usr/include`, `/usr/local/include`) компилятором и библиотек компоновщиком (`/usr/lib`, `/usr/local/lib`).

      2. **Инсталляция:** Корректная настройка сборочных систем (CMake `GNUInstallDirs`, autotools) с разнесением бинарников (`bin`), библиотек (`lib`), заголовков (`include`) и документации (`share/man`).

      3. **Runtime архитектура:** Корректный выбор путей для сокетов IPC (`/run` или `/tmp`), lock-файлов, файлов конфигурации (`/etc`) и изменяемых данных (`/var/lib`).

      4. **Упаковка:** Создание deb/rpm пакетов, полностью совместимых с дистрибутивами Linux.

   **Пример:**

   ```cpp
   #include <cstdlib>
   #include <filesystem>

   // Пример корректного FHS-aware выбора пути конфигурации в C++:
   std::filesystem::path get_config_path() {
       const char* xdg = std::getenv("XDG_CONFIG_HOME");
       if (xdg && *xdg && std::filesystem::path(xdg).is_absolute()) return std::filesystem::path(xdg) / "my_app/app.conf";

       const char* home = std::getenv("HOME");
       if (home && *home) return std::filesystem::path(home) / ".config/my_app/app.conf";

       return "/etc/my_app/app.conf"; // Общесистемный fallback по FHS
   }

   ```

   **Типичная ошибка:** Размещение сгенерированных логов, баз данных SQLite или временных сокетов рядом с исполняемым бинарным файлом в `/usr/bin/` — в Unix-подобных ОС этот каталог доступен приложению исключительно на чтение (`Read-Only`).

   **Источник:** [CMake Documentation: GNUInstallDirs](https://cmake.org/cmake/help/latest/module/GNUInstallDirs.html)
