## Linux Basics — Questions (C/C++ oriented)

## Linux Architecture

1. Что такое Linux kernel?

   **Ответ:** Ядро Linux — монолитное свободное ядро операционной системы, работающее в привилегированном режиме процессора (Ring 0). Оно выступает базовым уровнем абстракции между аппаратным обеспечением и прикладным программным обеспечением, управляя процессами, потоками, физической памятью, файловыми системами, сетью и периферийными устройствами.

   **Пример:**

   ```bash
   uname -r
   # Вывод версии работающего ядра: 6.8.0-31-generic

   ```

   **Типичная ошибка:** Называть «Linux» полноценной операционной системой. Linux — это исключительно ядро; полноценная ОС включает стек GNU (компиляторы, утилиты coreutils, glibc), systemd и прикладные сервисы.

   **Источник:** [The Linux Kernel documentation](https://docs.kernel.org/)

2. Что относится к user space в Linux?

   **Ответ:** User space (пользовательское пространство) — непривилегированная область виртуальной памяти и режим исполнения процессора (Ring 3), в котором работают все пользовательские программы, системные сервисы (демоны), оболочки (shell), графические серверы и стандартные библиотеки (например, glibc).

   **Пример:**

   ```cpp
   #include <unistd.h>

   int main() {
       // Этот код, стек, куча и вызовы libc исполняются в Ring 3
       return 0;
   }

   ```

   **Типичная ошибка:** Считать системного демона (например, `sshd` или `systemd`), запущенного от пользователя `root`, частью kernel space. Любой процесс, работающий под учетной записью `root`, по-прежнему ограничен рамками Ring 3 и user space.

   **Источник:** [Robert Love: Linux System Programming](https://www.oreilly.com/library/view/linux-system-programming/9781449341527/)

3. В чем разница между kernel space и user space?

   **Ответ:** Разница заключается в уровне аппаратных привилегий CPU (Ring 0 против Ring 3) и доступности памяти. В kernel space код имеет прямой неограниченный доступ к инструкциям управления железом, портам I/O и всей физической памяти. В user space программы изолированы виртуальной памятью (MMU) и могут взаимодействовать с внешним миром только через системные вызовы.

   **Пример:**

   | Характеристика | Kernel Space (Ring 0) | User Space (Ring 3) |
   | --- | --- | --- |
   | Доступ к железу | Прямой (инструкции `in`, `out`, `cli`, `sti`) | Только через системные вызовы ядра |
   | Изоляция памяти | Доступ ко всей физической/виртуальной памяти | Доступ только к своему виртуальному адресному пространству |
   | Последствия сбоя | Kernel Panic / зависание всей ОС | Завершение упавшего процесса (`SIGSEGV`), ОС стабильна |

   **Типичная ошибка:** Полагать, что изоляция user space и kernel space обеспечивается программным кодом Linux. Изоляция опирается на кремниевые кольца защиты CPU и аппаратные таблицы MMU.

   **Источник:** [Intel® 64 and IA-32 Architectures Software Developer Manuals (Volume 3A: System Architecture Overview)](https://www.intel.com/)

4. Почему пользовательские приложения не работают напрямую с железом?

   **Ответ:** Прямой доступ привел бы к отсутствию безопасности и отказоустойчивости: любая ошибка в коде могла бы разрушить состояние всей ОС или повредить оборудование. Кроме того, прямое управление лишает систему мультизадачности (невозможно безопасно делить один диск или сетевую карту между сотнями приложений без централизованного арбитра — ядра).

   **Пример:**

   ```cpp
   // Прямая попытка выполнить инструкцию Ring 0 из User Space:
   asm volatile("hlt"); // Hardware Exception -> Ядро перехватывает и шлет SIGSEGV

   ```

   **Типичная ошибка:** Считать, что отсутствие прямого доступа фатально замедляет работу. Ядро предоставляет буферизацию, планирование и DMA, что чаще всего работает быстрее наивного ручного управления железом.

   **Источник:** [Andrew S. Tanenbaum: Modern Operating Systems](https://www.pearson.com/)

5. Как приложение взаимодействует с ядром?

   **Ответ:** Приложение взаимодействует с ядром через четко регламентированный интерфейс системных вызовов (system calls). Обычно это происходит прозрачно через функции-обертки стандартной библиотеки Си (glibc), которая загружает аргументы в регистры процессора и выполняет аппаратную инструкцию перехода в ядро (`syscall`).

   **Пример:**

   Код C++ (std::cout) -> glibc (write) -> Инструкция CPU 'syscall' -> Ядро Linux (sys_write)

   **Типичная ошибка:** Думать, что взаимодействие возможно через запись в произвольные структуры ядра по указателям. Виртуальная память ядра защищена от записи со стороны Ring 3 на уровне страниц MMU.

   **Источник:** [Michael Kerrisk: The Linux Programming Interface (Chapter 3: System Programming Concepts)](https://man7.org/tlpi/)

6. Что такое system call?

   **Ответ:** Системный вызов — программно-аппаратный механизм запроса сервиса ядра из непривилегированного пользовательского пространства, при котором процессор аппаратно переключает уровень привилегий с сохранением регистров и переходом на стек ядра.

   **Пример:**

   ```cpp
   #include <unistd.h>
   #include <sys/syscall.h>

   // Прямой системный вызов получения идентификатора текущего процесса:
   pid_t pid = syscall(SYS_getpid);

   ```

   **Типичная ошибка:** Путать библиотечный вызов `malloc()` с системным вызовом. `malloc` — это алгоритм пользовательского пространства в libc, запрашивающий у ядра память через `brk()` или `mmap()` только по мере необходимости.

   **Источник:** [Linux man pages: syscalls(2)](https://man7.org/linux/man-pages/man2/syscalls.2.html)

7. Какие основные подсистемы есть у ядра Linux?

   **Ответ:** Ядро разделено на ключевые функциональные подсистемы:

   1. **Process Management (Scheduler):** создание, планирование и завершение процессов/потоков.

   2. **Memory Management (MM):** виртуальная память, paging, swap, трансляция адресов.

   3. **VFS (Virtual File System):** унифицированный абстрактный интерфейс к файловым системам и устройствам.

   4. **Network Stack:** протоколы TCP/IP, сокеты, сетевые драйверы.

   5. **IPC (Interprocess Communication):** каналы, очереди, семафоры, shm.

   6. **Device Drivers:** модули взаимодействия с конкретными физическими устройствами.

   **Пример:**

                     ┌──────────────────────────────────────────────┐
                     │                 System Calls                 │
                     └──────┬──────────┬──────────┬──────────┬──────┘
                            │          │          │          │
   ┌────────────────────────▼─┐ ┌──────▼─────┐ ┌──▼──────┐ ┌─▼────────────────────┐
   │ Process Mgmt & Scheduler │ │ Memory Mgmt│ │   VFS   │ │ Network Stack & IPC  │
   └──────────────────────────┘ └────────────┘ └──┬──────┘ └──────────────────────┘
                                                  │
                                       ┌──────────▼──────────┐
                                       │    Device Drivers   │
                                       └─────────────────────┘

   **Типичная ошибка:** Считать, что эти подсистемы изолированы в разные независимые процессы (как в микроядре). В монолитном ядре Linux все подсистемы компилируются в единое адресное пространство ядра и вызывают функции друг друга напрямую.

   **Источник:** [Bovet, Cesati: Understanding the Linux Kernel](https://www.oreilly.com/library/view/understanding-the-linux/0596005652/)

8. Что такое scheduler в Linux?

   **Ответ:** Scheduler (планировщик) — подсистема ядра, решающая, какой из готовых к выполнению потоков (`TASK_RUNNING`) должен занять доступное ядро CPU в следующий квант времени, гарантируя справедливость распределения ресурсов и низкую задержку отклика.

   **Пример:**

   ```bash
   # Просмотр класса планирования процесса:
   chrt -p <PID>
   # Вывод по умолчанию: pid <PID>'s current scheduling policy: SCHED_OTHER

   ```

   **Типичная ошибка:** Считать, что современный Linux использует простой Round-Robin для обычных задач. По умолчанию используется планировщик EEVDF (Earliest Eligible Virtual Deadline First), пришедший на смену CFS (Completely Fair Scheduler).

   **Источник:** [Linux Kernel Documentation: CFS/EEVDF Scheduler](https://docs.kernel.org/scheduler/sched-design-CFS.html)

9. Что такое VFS (Virtual File System)?

   **Ответ:** VFS — уровень абстракции ядра, предоставляющий унифицированный программный интерфейс (POSIX API: `open`, `read`, `write`) для работы с любыми файловыми системами (ext4, XFS, Btrfs, NFS) и псевдофайловыми системами (`procfs`, `sysfs`).

   **Пример:**

   ```cpp
   // Один и тот же системный вызов работает прозрачно для ext4, сетевого диска или сокета:
   int fd = open("/path/to/file", O_RDONLY);
   read(fd, buffer, 1024);

   ```

   **Типичная ошибка:** Полагать, что драйвер конкретной файловой системы напрямую взаимодействует с кодом пользователя. Пользовательский код всегда общается только с VFS, которая маршрутизирует вызовы через таблицу указателей на функции `file_operations`.

   **Источник:** [Linux Kernel Documentation: Overview of the Virtual Filesystem](https://docs.kernel.org/filesystems/vfs.html)

10. Что такое process manager в Linux?

   **Ответ:** Process Manager (диспетчер процессов) — подсистема ядра, управляющая жизненным циклом потоков и процессов: их порождением (`clone`, `fork`), заменой исполняемого кода (`execve`), синхронизацией состояний, отслеживанием связей предок-потомок и очисткой структур `task_struct` при завершении (`exit`, `waitpid`).

   **Пример:**

   ```bash
   ps -eo pid,ppid,stat,comm
   # Отображение дерева процессов и их текущих состояний (R, S, D, Z)

   ```

   **Типичная ошибка:** Считать процессы и потоки принципиально разными сущностями на уровне ядра Linux. Для ядра существует только `task_struct` (scheduling entity); поток — это просто процесс, разделяющий память и файловые дескрипторы с родителем (`CLONE_VM | CLONE_FILES`).

   **Источник:** [Robert Love: Linux Kernel Development (Chapter 3: Process Management)](https://www.pearson.com/)

11. Что такое memory manager в Linux?

   **Ответ:** Memory Manager — подсистема ядра, отвечающая за распределение физической и виртуальной памяти: управление таблицами страниц, обработку Page Faults, реализацию Demand Paging, кэширование страниц с диска (Page Cache), выгрузку неактивной памяти (swap) и защиту областей памяти (VMA).

   **Пример:**

   ```bash
   cat /proc/meminfo
   # Детальный отчет менеджера памяти ядра о занятых страницах, кэшах и буферах

   ```

   **Типичная ошибка:** Полагать, что выделение памяти через `malloc()` моментально забирает физические планки RAM. Менеджер памяти выделяет только виртуальные диапазоны, а физическую память выделяет лениво при первом касании страницы.

   **Источник:** [Mel Gorman: Understanding the Linux Virtual Memory Manager](https://www.kernel.org/doc/gorman/)

12. Что такое device driver?

   **Ответ:** Device driver (драйвер устройства) — модуль программного кода ядра, знающий аппаратные спецификации конкретного физического или виртуального контроллера и транслирующий высокоуровневые запросы ядра (например, «прочитать блок 50») в низкоуровневые команды шины/устройства (PCIe, USB, I2C).

   **Пример:**

   ```bash
   lspci -k
   # Показывает устройства на шине PCI и привязанные к ним драйверы ядра (Kernel driver in use)

   ```

   **Типичная ошибка:** Полагать, что драйвер устройства работает в пользовательском пространстве как отдельное приложение. В классической архитектуре Linux подавляющее большинство драйверов исполняется внутри единого адресного пространства Ring 0.

   **Источник:** [Corbet, Rubini, Kroah-Hartman: Linux Device Drivers](https://lwn.net/Kernel/LDD3/)

13. Зачем ядру нужны драйверы?

   **Ответ:** Драйверы изолируют универсальный код операционной системы от бесконечного разнообразия специфичного железа. Благодаря драйверам ядро оперирует стандартными абстракциями (блочное устройство, сетевой интерфейс, tty), а нюансы регистров конкретного вендора скрыты внутри конкретного драйвера.

   **Пример:**

   Пользователь -> VFS -> Блочный уровень -> Драйвер NVMe / SATA -> Контроллер диска

   **Типичная ошибка:** Думать, что ядро должно заново перекомпилироваться под каждую новую модель мыши или сетевой карты: архитектура абстракций позволяет подключать и отключать драйверы на лету.

   **Источник:** [Linux Kernel Documentation: Driver Model](https://docs.kernel.org/driver-api/driver-model/index.html)

14. Чем kernel module отличается от встроенного драйвера?

   **Ответ:** Встроенный драйвер (built-in) компилируется непосредственно в образ бинарного файла ядра (`vmlinuz`) и постоянно находится в памяти с момента старта. Модуль ядра (Loadable Kernel Module, `.ko`) — это отдельный объектный файл, который может динамически загружаться в память ядра и выгружаться из нее прямо во время работы системы без перезагрузки.

   **Пример:**

   ```bash
   lsmod              # Список динамически загруженных модулей
   sudo modprobe dummy # Загрузка модуля dummy.ko на лету
   sudo rmmod dummy    # Выгрузка модуля из памяти ядра

   ```

   **Типичная ошибка:** Считать, что модуль ядра исполняется в user space с меньшими привилегиями. Будучи загруженным, модуль исполняется с полными правами Ring 0 внутри адресного пространства ядра.

   **Источник:** [The Linux Kernel Module Programming Guide](https://sysprog21.github.io/lkmpg/)

15. Что происходит при запуске программы в Linux?

   **Ответ:**

      1. Оболочка вызывает системный вызов `fork()`, клонируя текущий процесс.

      2. Дочерний процесс вызывает `execve(path, argv, envp)`.

      3. Ядро валидирует права, сбрасывает старое адресное пространство и парсит заголовок бинарника.

      4. ELF loader ядра мапит секции файла в виртуальную память и передает управление либо dynamic linker (`ld.so`), либо точке входа (`_start`).

      5. Рантайм libc выполняет инициализацию и вызывает функцию `main()`.

   **Пример:**

   fork() -> execve() -> Kernel ELF Loader -> ld-linux.so -> libc _start -> main()

   **Типичная ошибка:** Полагать, что системный вызов `execve()` создает новый PID. `execve` полностью переиспользует существующий PID, лишь заменяя тело и контекст исполняемой программы.

   **Источник:** [How programs get run: ELF binaries (LWN.net)](https://lwn.net/Articles/631631/)

16. Что делает ELF loader?

   **Ответ:** ELF loader (внутри ядра или в лице dynamic linker) анализирует структуру файла формата Executable and Linkable Format: читает Program Headers, сопоставляет сегменты (`PT_LOAD`) с виртуальной памятью процесса с нужными правами доступа (R, W, X), выделяет память под BSS-сегмент и настраивает регистр счетчика команд (RIP) на точку входа.

   **Пример:**

   ```bash
   readelf -l /bin/ls
   # Отображение Program Headers, указывающих ядру, как отображать сегменты в память

   ```

   **Типичная ошибка:** Считать, что ELF loader целиком считывает весь бинарник с диска в оперативную память при старте. Он лишь настраивает отображения `mmap`, а фактическая загрузка кода происходит страницами по требованию (demand paging).

   **Источник:** [Tool Interface Standard (TIS) Executable and Linking Format (ELF) Specification](https://refspecs.linuxfoundation.org/elf/elf.pdf)

17. Что такое init process?

   **Ответ:** Init process — самый первый процесс пользовательского пространства, порождаемый ядром на финальной стадии загрузки операционной системы. Он является предком всех остальных процессов в системе и отвечает за монтирование файловых систем, запуск фоновых служб и управление остановкой машины.

   **Пример:**

   ```bash
   ps -p 1 -o comm=
   # На современных системах выведет: systemd (или init)

   ```

   **Типичная ошибка:** Попытка принудительно завершить процесс с PID 1 командой `kill -9 1`. Ядро игнорирует сигнал `SIGKILL` для init процесса, защищая систему от немедленной паники.

   **Источник:** [Linux man pages: init(1)](https://man7.org/linux/man-pages/man1/init.1.html)

18. Что такое PID 1 и почему он важен?

   **Ответ:** PID 1 — уникальный идентификатор процесса `init`. Он играет две ключевые роли: во-первых, инициализирует пользовательское окружение; во-вторых, служит «усыновителем» (subreaper) для процессов-сирот (orphaned processes), собирая их коды возврата через вызовы семейства `waitpid()`, тем самым предотвращая утечку зомби-процессов в системе.

   **Пример:**

   ```cpp
   // Если процесс-родитель умирает раньше ребенка:
   // ядро автоматически переназначает PPID дочернего процесса на PID 1.

   ```

   **Типичная ошибка:** Запуск процессов внутри контейнеров Docker без легковесного init (например, `tini`): фоновые отпочковавшиеся зомби-процессы накапливаются бесконечно, поскольку контейнеризованное приложение обычно не имеет логики сбора чужих сирот.

   **Источник:** [Linux man pages: prctl(2) / PR_SET_CHILD_SUBREAPER](https://man7.org/linux/man-pages/man2/prctl.2.html)

19. Что делает systemd?

   **Ответ:** Systemd — современная подсистема инициализации (init) и управления сервисами в Linux. Она обеспечивает параллельный запуск служб, отслеживание демонов через cgroups (гарантируя уничтожение всех потомков при остановке), сокет-активацию, журналирование (journald), монтирование дисков и управление сессиями пользователей.

   **Пример:**

   ```bash
   systemctl status sshd.service
   # Запрос состояния демона SSH через интерфейс systemd

   ```

   **Типичная ошибка:** Считать systemd простым аналогом старых bash-скриптов SysVinit. Systemd — это обширный фреймворк системного управления, контролирующий таймеры, сеть, логирование и контейнеризацию сервисов.

   **Источник:** [systemd System and Service Manager](https://systemd.io/)

20. Что такое shell?

   **Ответ:** Shell (командная оболочка) — интерфейсная программа пользовательского пространства, принимающая команды от пользователя (через клавиатуру или скрипты), интерпретирующая их и запускающая соответствующие системные программы или встроенные директивы, управляя их вводом-выводом.

   **Пример:**

   ```bash
   echo $SHELL
   # Вывод пути текущей командной оболочки, например: /bin/bash

   ```

   **Типичная ошибка:** Путать окно эмулятора терминала (GNOME Terminal, Alacritty) с оболочкой (bash, zsh). Терминал лишь отрисовывает символы и обрабатывает нажатия клавиш, передавая байты шеллу.

   **Источник:** [POSIX.1-2017: Shell & Utilities](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html)

21. Чем shell отличается от kernel?

   **Ответ:** Ядро (kernel) — это привилегированная низкоуровневая программа (Ring 0), управляющая ресурсами машины и не имеющая прямого пользовательского текстового интерфейса. Shell — это обычная непривилегированная утилита (Ring 3), парсящая текстовые команды человека и транслирующая их в вызовы к ядру.

   **Пример:**

   | Характеристика | Kernel | Shell |
   | --- | --- | --- |
   | Пространство памяти | Kernel Space | User Space |
   | Интерфейс | Syscalls (двоичный ABI) | CLI (текстовый ввод/вывод) |
   | Роль | Управление ресурсами и изоляция | Интерпретация команд пользователя |

   **Типичная ошибка:** Думать, что команда `cd` — это системный вызов или отдельный бинарный файл. `cd` — это встроенная внутренняя команда shell (built-in), так как дочерний процесс не может изменить текущую директорию родительского шелла.

   **Источник:** [The Open Group Base Specifications: Shell Command Language](https://pubs.opengroup.org/)

22. Что такое bash?

   **Ответ:** Bash (Bourne Again SHell) — де-факто стандартная командная оболочка проекта GNU, являющаяся обратно совместимым расширением стандарта POSIX sh (`/bin/sh`) с добавлением автодополнения, массивов, работы с историей команд и расширенным скриптовым синтаксисом.

   **Пример:**

   ```bash
   # Bash-специфичный синтаксис (process substitution):
   diff <(ls dir1) <(ls dir2)

   ```

   **Типичная ошибка:** Писать bash-скрипты с шебангом `#!/bin/sh`. На многих системах (например, Ubuntu/Debian) `/bin/sh` указывает на легковесную оболочку `dash`, в которой многие конструкции bash ("bashisms") вызывают синтаксическую ошибку.

   **Источник:** [GNU Bash Manual](https://www.gnu.org/software/bash/manual/)

23. Что делает dynamic linker?

   **Ответ:** Dynamic Linker (динамический компоновщик, `ld.so` или `ld-linux.so`) — программа в user space, запускаемая ядром до начала исполнения основного кода программы. Она находит на диске зависимые разделяемые библиотеки (`.so`), мапит их в память, разрешает неразрешенные символы (перемещения / relocations) и связывает адреса функций (через PLT и GOT).

   **Пример:**

   ```bash
   ldd /bin/ls
   # Показывает зависимости бинарника, которые dynamic linker обязан подгрузить в память

   ```

   **Типичная ошибка:** Считать, что dynamic linker работает в момент компиляции программы. В момент сборки работает статический линкер `ld`, а `ld.so` работает во время реального запуска приложения на целевой машине.

   **Источник:** [Linux man pages: ld.so(8)](https://man7.org/linux/man-pages/man8/ld.so.8.html)

24. Что такое shared library?

   **Ответ:** Разделяемая библиотека (Shared Library, `.so`) — скомпилированный ELF-файл, содержащий позиционно-независимый код (PIC), который может одновременно использоваться несколькими независимыми процессами. Физические страницы секции кода (`.text`) такой библиотеки хранятся в памяти в единственном экземпляре и разделяются всеми процессами.

   **Пример:**

   ```bash
   gcc -fPIC -shared mylib.c -o libmylib.so

   ```

   **Типичная ошибка:** Считать, что переменные и глобальные данные shared-библиотеки тоже разделяются между процессами. Секция изменяемых данных (`.data`) дублируется для каждого процесса индивидуально по механизму Copy-on-Write.

   **Источник:** [David A. Wheeler: Program Library HOWTO (Shared Libraries)](https://dwheeler.com/program-library/)

25. Чем static linking отличается от dynamic linking?

   **Ответ:** При статической линковке машинный код используемых библиотек (`.a`) целиком копируется линкером в итоговый исполняемый файл на этапе сборки (создается самодостаточный бинарник). При динамической линковке бинарник содержит лишь список необходимых имен библиотек и внешних символов, связывание которых происходит в RAM при запуске программы.

   **Пример:**

   ```bash
   # Статическая сборка (тяжелый автономный бинарник):
   g++ main.cpp -static -o app_static

   # Динамическая сборка (легкий бинарник с внешними зависимостями):
   g++ main.cpp -o app_dynamic

   ```

   **Типичная ошибка:** Полагать, что статическая сборка всегда быстрее. Статические бинарники занимают в разы больше места на диске и лишают систему оптимизации разделения физических страниц общего кода в оперативной памяти.

   **Источник:** [John R. Levine: Linkers and Loaders](https://www.iecc.com/linker/)

26. Что такое /proc?

   **Ответ:** `/proc` (procfs) — виртуальная (псевдо) файловая система, генерируемая ядром на лету в оперативной памяти. Она служит интерфейсом для наблюдения за состоянием работающих процессов (директории с числовыми именами `/proc/<PID>`) и параметрами самого ядра (память, прерывания, статистика).

   **Пример:**

   ```bash
   cat /proc/$$/status # Статус и потребление ресурсов текущего процесса оболочки
   cat /proc/cpuinfo   # Характеристики установленных процессоров

   ```

   **Типичная ошибка:** Попытка измерить размер файлов в `/proc` через `ls -l`. Большинство файлов в `/proc` имеют размер 0 байт, так как их содержимое генерируется ядром динамически только в момент чтения (`read()`).

   **Источник:** [Linux man pages: proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html)

27. Что такое /sys?

   **Ответ:** `/sys` (sysfs) — псевдофайловая система, экспортирующая структурированную иерархию объектов ядра (kobjects): шины, устройства, драйверы, параметры энергосбережения и топологию оборудования. Она предназначена для структурированного чтения и конфигурирования устройств из user space.

   **Пример:**

   ```bash
   # Чтение текущего состояния сетевого интерфейса:
   cat /sys/class/net/eth0/operstate

   ```

   **Типичная ошибка:** Модифицировать настройки железа прямыми вызовами в обход sysfs. Sysfs является каноническим механизмом ядра для настройки параметров драйверов (вместо устаревших ioctl).

   **Источник:** [Linux Kernel Documentation: sysfs - *The* filesystem for exporting kernel objects](https://docs.kernel.org/filesystems/sysfs.html)

28. Чем procfs отличается от sysfs?

   **Ответ:** `/proc` исторически создавался для экспорта информации о процессах, но со временем превратился в неструктурированную свалку разнообразных отчетов ядра. `/sys` был спроектирован позже с жесткой иерархией модели устройств ядра (kobject tree), где действует строгое правило: «одно значение на один текстовый файл».

   **Пример:**

   ```bash
   # procfs: выдает полотно неструктурированного текста:
   cat /proc/loadavg

   # sysfs: строго атомарное значение:
   cat /sys/devices/system/cpu/cpu0/topology/core_id

   ```

   **Типичная ошибка:** Использовать `/proc/sys` и `/sys` как синонимы. Каталог `/proc/sys` — это механизм настройки внутренних параметров ядра через `sysctl`, а `/sys` — дерево оборудования и объектов драйверов.

   **Источник:** [Greg Kroah-Hartman: The sysfs Filesystem](https://www.kernel.org/)

29. Что такое pseudo-filesystem?

   **Ответ:** Псевдофайловая система — виртуальная файловая система, не имеющая физического хранилища на блочном носителе (жестком диске или SSD). Её каталоги и файлы формируются функциями ядра прямо в RAM при обращении к VFS (примеры: `procfs`, `sysfs`, `devtmpfs`, `cgroup`).

   **Пример:**

   ```bash
   mount | grep -E "(proc|sysfs|tmpfs)"

   ```

   **Типичная ошибка:** Пытаться восстановить удаленный файл из `/proc` или считать, что запись в псевдофайловую систему изнашивает ресурс ячеек диска.

   **Источник:** [Linux Kernel Documentation: Filesystems](https://docs.kernel.org/filesystems/index.html)

30. Что значит “everything is a file” в Linux?

   **Ответ:** Философия Unix/Linux, согласно которой доступ к подавляющему большинству разнородных ресурсов системы (файлы на диске, устройства ввода, последовательные порты, сокеты, каналы IPC, системная статистика) унифицирован через абстракцию потока байт и файлового дескриптора с единым набором системных вызовов (`open`, `read`, `write`, `close`).

   **Пример:**

   ```bash
   # Чтение случайных байтов из аппаратного генератора как из обычного файла:
   head -c 16 /dev/urandom

   ```

   **Типичная ошибка:** Абсолютизировать принцип. Сетевые интерфейсы (например, `eth0`) не представлены как файлы в директории `/dev` и настраиваются через сетевой стек/netlink-сокеты, а не операцией `open()`.

   **Источник:** [Eric S. Raymond: The Art of Unix Programming](http://www.catb.org/~esr/writings/taoup/html/)

31. Что такое file descriptor?

   **Ответ:** Файловый дескриптор — неотрицательное целое число (`int`), являющееся индексом во внутренней таблице открытых процессом файлов ядра. По этому индексу ядро связывает пользовательские системные вызовы со структурой `struct file`, указывающей на конкретный inode и операции VFS.

   **Пример:**

   ```cpp
   #include <unistd.h>
   #include <fcntl.h>

   int fd = open("/dev/null", O_WRONLY); // Возвращает дескриптор (например, 3)
   write(fd, "a", 1);
   close(fd);

   ```

   **Типичная ошибка:** Полагать, что числовые значения дескрипторов глобальны для всей системы. В разных процессах один и тот же номер дескриптора (например, 4) указывает на совершенно разные открытые файлы или сокеты.

   **Источник:** [Linux man pages: open(2)](https://man7.org/linux/man-pages/man2/open.2.html)

32. Как stdin/stdout/stderr связаны с архитектурой Linux?

   **Ответ:** Это фундаментальное соглашение POSIX: при создании процесса первые три дескриптора таблицы открытых файлов (0, 1, 2) резервируются под стандартные потоки:

   * `0` — `stdin` (ввод, клавиатура/pipe)
   * `1` — `stdout` (вывод, экран/pipe)
   * `2` — `stderr` (вывод ошибок, экран)
   Благодаря этой фиксации номеров оболочка shell может конструировать конвейеры (`|`) и перенаправления (`>`), просто подменяя дескрипторы через вызовы `dup2()`.

   **Пример:**

   ```bash
   # Оболочка закрывает дескриптор 1 и открывает вместо него файл out.txt:
   ./app > out.txt 2>&1

   ```

   **Типичная ошибка:** Закрывать дескриптор 2 при подавлении ошибок и затем открывать новый файл. Новый файл займет освободившийся индекс `2`, и если какая-то библиотека запишет в `stderr`, она перезапишет данные вашего файла.

   **Источник:** [The Open Group Base Specifications: File Descriptors](https://pubs.opengroup.org/onlinepubs/9699919799/basedefs/V1_chap02.html)

33. Что такое daemon?

   **Ответ:** Демон — долгоживущий фоновый процесс, запускаемый для обслуживания определенных системных запросов (веб-сервер, база данных, планировщик задач). Демон не имеет управляющего терминала (controlling TTY), отвязан от родительской сессии пользователя и обычно имеет PID предка равный 1.

   **Пример:**

   ```cpp
   #include <unistd.h>

   int main() {
       // Традиционный способ демонизации (форк, отвязка от терминала, сброс umask):
       daemon(0, 0);
       while (true) { pause(); }
   }

   ```

   **Типичная ошибка:** Полагать, что добавление символа `&` в конце команды в bash делает программу полноценным демоном. Фоновый процесс `&` по-прежнему привязан к терминальной сессии и будет убит сигналом `SIGHUP` при закрытии терминала (если не запущен через `nohup` или `disown`).

   **Источник:** [Linux man pages: daemon(3)](https://man7.org/linux/man-pages/man3/daemon.3.html)

34. Что такое TTY?

   **Ответ:** TTY (teletypewriter) — изначально аппаратный телетайп, а в современной архитектуре Linux — драйвер ядра, реализующий интерфейс терминала. Он обрабатывает ввод символов, реализует линейную дисциплину (line discipline: эхо, обработку горячих клавиш Ctrl+C, стирание символов Backspace) и связывает экран с сессией процесса.

   **Пример:**

   ```bash
   tty
   # Выводит текущий подключенный терминал, например: /dev/tty1 или /dev/pts/0

   ```

   **Типичная ошибка:** Считать виртуальные консоли `/dev/tty1-6` эмуляторами терминала. Виртуальные консоли обрабатываются непосредственно драйвером терминала внутри ядра Linux.

   **Источник:** [The TTY demystified: Linus Åkesson](https://www.linusakesson.net/programming/tty/)

35. Что такое PTY?

   **Ответ:** PTY (pseudo-terminal) — пара программных виртуальных устройств (master и slave), эмулирующих физический терминал для программ в пользовательском пространстве. Сторона slave ведет себя в точности как обычный TTY, а сторона master управляется эмулятором терминала (GNOME Terminal, xterm) или демоном SSH для передачи байтов по сети.

   **Пример:**

   SSH Client -> Network -> sshd -> [PTY Master] === Linux Kernel === [PTY Slave /dev/pts/X] -> bash

   **Типичная ошибка:** Запуск утилит, требующих интерактивный ввод пароля (например, `sudo`), внутри скриптов без выделения PTY. Программа завершится ошибкой «no tty present and no askpass program specified».

   **Источник:** [Linux man pages: pty(7)](https://man7.org/linux/man-pages/man7/pty.7.html)

36. Что такое login shell?

   **Ответ:** Login shell — оболочка, запускаемая первой при успешной аутентификации пользователя в системе (первый символ в `argv[0]` выставляется в `-`, например, `-bash`). Она считывает глобальные конфигурационные файлы начальной инициализации профиля (`/etc/profile`, `~/.bash_profile` или `~/.bash_login`), настраивая окружение на всю сессию.

   **Пример:**

   ```bash
   # Проверка типа оболочки:
   shopt login_shell
   # вернет login_shell on (если это login shell)

   ```

   **Типичная ошибка:** Прописывать переменные окружения только в `~/.bash_profile` и удивляться, почему они не подхватываются при открытии новых окон терминала в графической оболочке (графические эмуляторы по умолчанию запускают non-login shell, читающий `~/.bashrc`).

   **Источник:** [GNU Bash Manual: Bash Startup Files](https://www.gnu.org/software/bash/manual/html_node/Bash-Startup-Files.html)

37. Что такое environment variables?

   **Ответ:** Переменные окружения — набор пар «ключ=значение» в формате строк `KEY=VALUE`, хранящийся в сегменте пользовательской памяти процесса (на стеке над аргументами `argv`). Они неявно наследуются дочерними процессами при вызове `fork()`/`execve()` и служат для глобальной конфигурации путей, локали и поведения программ.

   **Пример:**

   ```cpp
   #include <cstdlib>
   #include <iostream>

   int main() {
       const char* path = std::getenv("PATH");
       std::cout << "Path: " << (path ? path : "empty") << '\n';
   }

   ```

   **Типичная ошибка:** Считать, что модификация переменной окружения в дочернем процессе (через `export` или `setenv()`) повлияет на родительский процесс. Окружение передается только сверху вниз при порождении процесса.

   **Источник:** [Linux man pages: environ(7)](https://man7.org/linux/man-pages/man7/environ.7.html)

38. Как процесс получает argv и envp?

   **Ответ:** Ядро при обработке системного вызова `execve()` копирует строки аргументов и переменные окружения на самую верхушку нового пользовательского стека создаваемой программы. В момент старта функции `_start` указатель стека (RSP) ссылается на структуру: `argc`, массив указателей `argv[]`, терминатор `NULL`, массив указателей `envp[]`, терминатор `NULL` и вектор метаданных `auxv`.

   **Пример:**

   Высокие адреса памяти (Стек)
   ├── Строки аргументов и окружения ("PATH=/usr/bin", "app", etc.)
   ├── Вектор Auxiliary Vector (auxv)
   ├── Указатели envp[] (завершается NULL)
   ├── Указатели argv[] (завершается NULL)
   ├── argc (целое число аргументов) <- Начальный указатель RSP процессора
   Низкие адреса памяти

   **Типичная ошибка:** Полагать, что `main()` вызывается первым. Первой вызывается ассемблерная функция libc `_start`, которая извлекает эти параметры из стека и передает их в сигнатуру `int main(int argc, char** argv, char** envp)`.

   **Источник:** [System V Application Binary Interface: AMD64 Architecture (Initial Stack and Register State)](https://gitlab.com/x86-psABIs/x86-64-ABI)

39. Что такое glibc?

   **Ответ:** GNU C Library (glibc) — основная реализация стандартной библиотеки языка Си для систем GNU/Linux. Она предоставляет реализацию стандарта ANSI C/POSIX, математические функции, алгоритмы кучи (`malloc`), потоки (`pthreads`) и тонкие системные обертки над системными вызовами ядра с сохранением кодов ошибок в `errno`.

   **Пример:**

   ```bash
   ldd --version
   # Вывод версии установленной библиотеки: ldd (Ubuntu GLIBC 2.39)

   ```

   **Типичная ошибка:** Считать, что glibc — единственная библиотека Си под Linux. Для встраиваемых систем и легковесных контейнеров (например, Alpine Linux) часто используют альтернативные реализации (musl, uClibc).

   **Источник:** [The GNU C Library Reference Manual](https://www.gnu.org/software/libc/manual/)

40. Чем libc отличается от kernel API?

   **Ответ:** Kernel API — это низкоуровневый двоичный системный интерфейс ядра (номера syscall, передача аргументов через регистры CPU, флаги ядра). Libc API — переносимая высокоуровневая C-библиотека, которая стандартизирует интерфейсы под POSIX, обеспечивает буферизацию ввода-вывода (структура `FILE*` против сырого `int fd`) и скрывает аппаратно-зависимые детали инструкций перехода в ядро.

   **Пример:**

   | Характеристика | Kernel API (Syscalls) | Libc API |
   | --- | --- | --- |
   | Идентификация ошибок | Возврат отрицательного кода в регистре (`-EINVAL`) | Запись положительного кода ошибки в `errno`, возврат `-1` |
   | Буферизация | Отсутствует (прямая передача в page cache/драйвер) | Буфер в user space (`std::string`, буферы `FILE`) |
   | Аллокация памяти | Грубая, страницами (`brk`, `mmap`) | Гранулярная, по байтам (`malloc`, `free`) |

   **Типичная ошибка:** Считать функцию `pthread_create()` системным вызовом. В ядре нет системного вызова `pthread_create`, libc реализует его с помощью комплексного вызова `clone()` с набором специфичных битовых флагов.

   **Источник:** [Linux man pages: syscalls(2)](https://man7.org/linux/man-pages/man2/syscalls.2.html)

41. Что происходит при переходе user mode → kernel mode?

   **Ответ:**

      1. CPU переключает привилегии с Ring 3 на Ring 0 (изменяется поле CPL).

      2. Аппаратно сохраняются текущие регистры счетчика команд (RIP) и флагов (RFLAGS).

      3. Процессор переключается с пользовательского стека на изолированный стек ядра для текущего процесса (загружается из структуры TSS/MSR).

      4. Управление передается по жестко зафиксированному адресу шлюза системных вызовов в ядре (MSR `LSTAR`).

   **Пример:**

   Пользовательский стек (RSP_user) -> [SYSCALL] -> Стек ядра (RSP_kernel)

   **Типичная ошибка:** Считать, что переключение режима очищает кэши CPU. L1/L2 кэши данных сохраняются, однако при возврате ядро может инвалидировать часть предсказателей переходов для предотвращения Spectre-атак.

   **Источник:** [AMD64 Architecture Programmer’s Manual Volume 2: System Programming (SYSCALL/SYSRET)](https://www.amd.com/)

42. Что такое trap?

   **Ответ:** Trap (ловушка, программное исключение) — синхронное прерывание, намеренно или непреднамеренно порожденное исполнением текущей процессорной инструкции самого потока (деление на ноль `#DE`, невалидная инструкция `#UD`, системный вызов `syscall`, обращение к незамапленной памяти `#PF` или точка останова отладчика `int 3`).

   **Пример:**

   ```cpp
   int x = 5 / 0; // Генерирует синхронный процессорный trap (Divide by Zero) -> SIGFPE

   ```

   **Типичная ошибка:** Путать trap и аппаратное прерывание. Trap всегда вызывается кодом программы синхронно и воспроизводим на том же месте; прерывание возникает асинхронно от внешних устройств.

   **Источник:** [Intel® 64 Architectures Software Developer’s Manual: Interrupt and Exception Handling](https://www.intel.com/)

43. Что такое interrupt?

   **Ответ:** Interrupt (аппаратное прерывание, IRQ) — асинхронный электрический сигнал, посылаемый контроллеру прерываний (APIC) физическим внешним устройством (сетевая карта приняла пакет, таймер отсчитал квант, диск завершил DMA-чтение). Процессор немедленно приостанавливает текущий поток и выполняет функцию драйвера — обработчик прерывания (ISR).

   **Пример:**

   ```bash
   cat /proc/interrupts
   # Статистика распределения аппаратных прерываний по ядрам процессора

   ```

   **Типичная ошибка:** Выполнять тяжелые длительные расчеты прямо в основном обработчике прерывания. В Linux обработчики прерываний делятся на top-half (быстрая критическая фаза) и bottom-half/softirq (отложенная тяжелая обработка данных в фоне).

   **Источник:** [Robert Love: Linux Kernel Development (Chapter 7: Interrupts and Interrupt Handlers)](https://www.pearson.com/)

44. Чем interrupt отличается от signal?

   **Ответ:** Прерывание (Interrupt) генерируется аппаратным обеспечением, обрабатывается процессором на уровне микрокода и перехватывается функциями ядра в Ring 0. Сигнал (Signal) — это чисто программная эмуляция прерывания на уровне ядра Linux, доставляемая процессу в пользовательском пространстве (Ring 3).

   **Пример:**

   | Характеристика | Hardware Interrupt | POSIX Signal |
   | --- | --- | --- |
   | Источник | Физическое оборудование (NIC, Keyboard, Timer) | Ядро ОС или другой процесс (`kill`) |
   | Уровень обработки | Ядро Linux (Ring 0) | Обработчик в пользовательском коде (Ring 3) |
   | Синхронность | Полностью асинхронно для CPU | Доставляется процессу при возврате из ядра |

   **Типичная ошибка:** Считать аппаратное прерывание таймера прямым вызовом сигнала `SIGALRM`. Ядро получает прерывание таймера в Ring 0 и уже самостоятельно формирует структуру сигнала для процесса.

   **Источник:** [Linux man pages: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

45. Что такое context switch?

   **Ответ:** Переключение контекста (Context Switch) — процедура ядра, при которой выполнение одного потока на процессоре приостанавливается, все регистры CPU (RIP, RSP, регистры общего назначения, FPU/AVX) сохраняются в его дескриптор `task_struct`, а сохраненные регистры другого готового потока загружаются в CPU, передавая ему управление.

   **Пример:**

   ```bash
   pidstat -w 1
   # Мониторинг добровольных (cswch/s) и принудительных (nvcswch/s) переключений контекста

   ```

   **Типичная ошибка:** Полагать, что context switch бесплатен. Переключение между разными процессами требует смены указателя таблиц страниц в регистре `CR3`, что приводит к инвалидации TLB и вымыванию горячих данных из кэшей CPU.

   **Источник:** [Silberschatz, Galvin: Operating System Concepts (Context Switch)](https://www.os-book.com/)

46. Когда происходит context switch?

   **Ответ:** Переключение контекста происходит в двух случаях:

      1. **Добровольно (Cooperative / Voluntary):** поток засыпает сам в ожидании ресурса (I/O, мьютекс, `sleep`, `poll`).

      2. **Принудительно (Preemptive / Involuntary):** планировщик ядра отбирает у потока процессор, когда истек его квант времени (timeslice), либо в системе появился поток с более высоким приоритетом (Real-Time).

   **Пример:**

   Поток А делает read() -> Данных нет -> Перевод в TASK_INTERRUPTIBLE -> Context Switch на Поток Б

   **Типичная ошибка:** Создавать тысячи активно конкурирующих потоков CPU. Чрезмерное количество принудительных переключений контекста приводит к падению полезной производительности системы (thrashing).

   **Источник:** [Brendan Gregg: Systems Performance (CPU Scheduling)](http://www.brendangregg.com/systems-performance-2nd-edition-book.html)

47. Что такое preemption в Linux?

   **Ответ:** Preemption (вытеснение) — способность операционной системы принудительно прерывать выполняющийся поток без его согласия для немедленной передачи процессора более приоритетной задаче. Linux поддерживает как вытеснение пользовательских процессов (User Preemption), так и вытеснение самого кода ядра внутри Ring 0 (Kernel Preemption: `CONFIG_PREEMPT`).

   **Пример:**

   ```bash
   uname -v | grep PREEMPT
   # Проверка поддержки вытеснения ядром задач реального времени

   ```

   **Типичная ошибка:** Считать, что код ядра Linux не может быть вытеснен. В современных ядрах с флагом `CONFIG_PREEMPT` (или RT-патчем) процесс может быть вытеснен прямо в середине выполнения большинства системных вызовов в Ring 0.

   **Источник:** [Linux Kernel Documentation: Kernel Preemption](https://docs.kernel.org/)

48. Что такое cgroups на базовом уровне?

   **Ответ:** Контрольные группы (Control Groups, cgroups) — механизм ядра Linux, позволяющий изолировать, ограничивать и измерять использование физических ресурсов системы (процессорного времени, оперативной памяти, операций дискового I/O, сетевых пакетов) для иерархических групп процессов.

   **Пример:**

   ```bash
   # Ограничение памяти процесса до 500 МБ в cgroups v2:
   echo "500M" > /sys/fs/cgroup/my_group/memory.max
   echo $$ > /sys/fs/cgroup/my_group/cgroup.procs

   ```

   **Типичная ошибка:** Путать cgroups и namespaces. Cgroups ограничивают **количество** ресурсов («не более 2 ядер CPU и 1 ГБ ОЗУ»), а namespaces ограничивают **видимость** ресурсов («видит только свои процессы и свой сетевой интерфейс»).

   **Источник:** [Linux man pages: cgroups(7)](https://man7.org/linux/man-pages/man7/cgroups.7.html)

49. Что такое namespaces на базовом уровне?

   **Ответ:** Пространства имен (Namespaces) — механизм ядра Linux, обеспечивающий изоляцию системных ресурсов для группы процессов. Процессы внутри пространства имен имеют иллюзию владения собственной изолированной средой: таблицей PID, сетевыми интерфейсами (NET), точками монтирования (MNT), пользователями (USER), сетевыми портами и IPC-очередями. Это базовый фундамент контейнеризации (Docker, LXC).

   **Пример:**

   ```bash
   # Запуск изолированного bash с собственной таблицей процессов:
   sudo unshare --pid --fork --mount-proc /bin/bash
   ps aux # Отобразит только что созданный bash как PID 1

   ```

   **Типичная ошибка:** Считать контейнеры аналогом виртуальных машин. Процессы внутри namespace исполняются на том же самом ядре хоста без эмуляции виртуального железа и гипервизоров.

   **Источник:** [Linux man pages: namespaces(7)](https://man7.org/linux/man-pages/man7/namespaces.7.html)

50. Чем Linux отличается от Unix на концептуальном уровне?

   **Ответ:** Исторический Unix (AT&T, BSD, Solaris) — проприетарное семейство ОС со строгой монолитной интеграцией ядра и базового набора утилит. Linux концептуально создавался «с нуля» как свободный, POSIX-совместимый клон ядра без проприетарного кода Unix, развиваемый на основе открытого сообщества. Архитектурно Linux сделал ставку на полностью монолитное ядро с динамическими модулями (LKM), модель потоков NPTL «поток как процесс с общими ресурсами», интеграцию псевдофайловых систем sysfs/procfs и ориентацию на масштабирование от мелких роутеров до топ-суперкомпьютеров.

   **Пример:**

   ```bash
   # Проверка соответствия стандартам POSIX через макросы:
   getconf _POSIX_VERSION

   ```

   **Типичная ошибка:** Считать Linux прямой веткой исходного кода Unix. Linux был написан Линусом Торвальдсом полностью с чистого листа и является «Unix-like» (Unix-подобной) системой, не содержащей юридического или кодового наследия исходного Bell Labs Unix.

   **Источник:** [The Single UNIX Specification: History and Concepts](https://www.unix.org/what_is_unix/history_timeline.html)

## Filesystem Hierarchy (FHS)

51. Что такое FHS?

   **Ответ:** FHS (Filesystem Hierarchy Standard) — стандарт, определяющий структуру каталогов, размещение файлов и их назначение в Unix-подобных операционных системах. Он регламентирует, где должны лежать исполняемые файлы, конфигурации, библиотеки, логи и временные данные, чтобы программное обеспечение могло предсказуемо работать на любых дистрибутивах.

   **Пример:**

   ```bash
   man hier
   # Системное описание иерархии файловой системы в соответствии с FHS

   ```

   **Типичная ошибка:** Считать FHS жестким требованием ядра Linux. FHS — это соглашение уровня пользовательского пространства (user space), соблюдаемое дистрибутивами (Debian, RHEL, Arch) и утилитами, но не контролируемое ядром.

   **Источник:** [Filesystem Hierarchy Standard (Linux Foundation Specifications)](https://refspecs.linuxfoundation.org/fhs.shtml)

52. Зачем нужен стандарт иерархии файловой системы?

   **Ответ:** Стандарт необходим для интероперабельности: пакетные менеджеры (`apt`, `dnf`), сборочные системы (`cmake`, `autotools`), скрипты и демоны должны знать заранее согласованные пути установки бинарников, заголовочных файлов и поиска конфигураций без ручной адаптации под каждый отдельный дистрибутив. Также стандарт позволяет монтировать каталоги (`/usr`, `/var`, `/home`) на независимые физические диски или сетевые хранилища (NFS).

   **Пример:**

   ```cmake
   # CMake использует стандартные пути GNUInstallDirs, опирающиеся на FHS:
   include(GNUInstallDirs)
   install(TARGETS my_app DESTINATION ${CMAKE_INSTALL_BINDIR}) # /usr/local/bin или /usr/bin

   ```

   **Типичная ошибка:** Жестко прописывать (hardcode) нестандартные пути вроде `/my_configs/app.conf` вместо канонического пути `/etc/app.conf` или `$XDG_CONFIG_HOME`.

   **Источник:** [Linux Standard Base Core Specification](https://refspecs.linuxfoundation.org/lsb.shtml)

53. Что находится в / ?

   **Ответ:** Каталог `/` (root directory, корень) — вершина единой иерархической файловой системы в Linux. В нем монтируется корневая файловая система (rootfs), содержащая минимально необходимый набор каталогов (`/bin`, `/sbin`, `/etc`, `/lib`, `/dev`), требуемый для запуска ядра, монтирования других разделов и аварийного восстановления системы.

   **Пример:**

   ```bash
   ls -ld /
   # Вывод: drwxr-xr-x ... /

   ```

   **Типичная ошибка:** Путать корневой каталог `/` (root directory) и домашний каталог суперпользователя `/root` (root user's home).

   **Источник:** [FHS 3.0: The Root Filesystem](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03.html)

54. Для чего используется /bin?

   **Ответ:** Исторически каталог `/bin` предназначен для хранения базовых системных утилит и команд общего назначения (для всех пользователей), которые критически необходимы как при нормальной работе, так и в однопользовательском режиме (single-user mode), когда каталог `/usr` еще не смонтирован (`sh`, `bash`, `cp`, `ls`, `cat`).

   **Пример:**

   ```bash
   ls -l /bin/cat /bin/sh

   ```

   **Типичная ошибка:** Помещать в `/bin` бинарники пользовательских сервисов или скриптов автоматизации проекта. Для стороннего ПО предназначены `/usr/local/bin` или `/opt`.

   **Источник:** [FHS 3.0: /bin : Essential user command binaries](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s04.html)

55. Для чего используется /sbin?

   **Ответ:** Каталог `/sbin` (System Binaries) содержит утилиты системного администрирования, необходимые для начальной загрузки, восстановления, монтирования файловых систем и настройки сети (`fsck`, `init`, `reboot`, `iptables`, `fdisk`). Эти команды требуют привилегий суперпользователя (`root`) для выполнения.

   **Пример:**

   ```bash
   which fdisk ip
   # /sbin/fdisk (или /usr/sbin/fdisk)
   # /sbin/ip (или /usr/sbin/ip)

   ```

   **Типичная ошибка:** Полагать, что обычный пользователь технически не может запустить бинарник из `/sbin`. Запустить файл с правами на чтение и исполнение (`rx`) можно, однако системный вызов ядра внутри утилиты завершится с ошибкой `EPERM` (Operation not permitted) из-за отсутствия capabilities/root.

   **Источник:** [FHS 3.0: /sbin : Essential system binaries](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s16.html)

56. Чем /bin отличается от /sbin?

   **Ответ:** Различие заключается в целевой аудитории и правах: `/bin` содержит утилиты общего назначения, доступные и регулярно используемые любыми рядовыми пользователями системы, в то время как `/sbin` содержит низкоуровневые административные утилиты, предназначенные для системного администратора (`root`) и работы загрузочных сценариев ОС.

   **Пример:**

   | Каталог | Назначение | Примеры утилит |
   | --- | --- | --- |
   | `/bin` | Общепользовательские базовые команды | `ls`, `cat`, `grep`, `mkdir`, `cp` |
   | `/sbin` | Утилиты администрирования и железа | `mkfs`, `iptables`, `sysctl`, `shutdown` |

   **Типичная ошибка:** Добавлять `/sbin` в переменную окружения `$PATH` непривилегированных пользователей, ожидая, что системные утилиты смогут менять состояние ОС без `sudo`.

   **Источник:** [FHS 3.0: Dual binary hierarchy](https://refspecs.linuxfoundation.org/FHS_3.0/)

57. Для чего нужен /etc?

   **Ответ:** Каталог `/etc` (Extended Text Config / Editable Text Configuration) зарезервирован исключительно для хранения общесистемных статических конфигурационных текстовых файлов системы и установленных демонов. В нем настраиваются параметры загрузки, пользователи, сетевые интерфейсы и демоны сервисов.

   **Пример:**

   ```bash
   ls /etc/fstab /etc/resolv.conf /etc/passwd

   ```

   **Типичная ошибка:** Размещать исполняемые скомпилированные бинарные файлы внутри `/etc`. Стандарт FHS категорически запрещает размещение исполняемых бинарников в `/etc` (допустимы только shell-скрипты инициализации).

   **Источник:** [FHS 3.0: /etc : Host-specific configuration](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s07.html)

58. Что обычно хранится в /etc?

   **Ответ:** В каталоге хранятся текстовые конфигурации:

   * `/etc/passwd`, `/etc/shadow` — база учетных записей и хэшей паролей;
   * `/etc/fstab` — таблица автомонтирования файловых систем;
   * `/etc/hosts`, `/etc/resolv.conf` — параметры сетевого разрешения DNS;
   * `/etc/systemd/` — конфигурационные юниты служб systemd;
   * Подкаталоги конфигураций серверов: `/etc/nginx/`, `/etc/ssh/`.

   **Пример:**

   ```bash
   cat /etc/os-release
   # Спецификация дистрибутива и версии ОС

   ```

   **Типичная ошибка:** Ручная правка `/etc/resolv.conf` на современных системах с `systemd-resolved` или `NetworkManager`: файл часто является symlink на файл в `/run` и перезаписывается демоном на лету.

   **Источник:** [Linux man pages: hier(7)](https://man7.org/linux/man-pages/man7/hier.7.html)

59. Почему конфиги лежат именно в /etc?

   **Ответ:** Исторически в первых версиях Unix (Bell Labs) в `/etc` сбрасывалось все вспомогательное («etcetera» — «и так далее»), что не являлось чистым бинарником пользователя. По мере стандартизации FHS каталог закрепили строго за машинно-специфичными (host-specific) текстовыми конфигурационными файлами, не зависящими от архитектуры процессора (architecture-independent).

   **Пример:**

   ```bash
   # Файлы в /etc машинно-зависимы: если смонтировать общий сетевой /usr по NFS на 10 серверов,
   # то /etc у каждой машины должен оставаться свой собственный.

   ```

   **Типичная ошибка:** Распространять общий сетевой `/etc` между разными серверами кластера без шаблонизации: каждый сервер имеет уникальные параметры (`machine-id`, `hostname`, `fstab`).

   **Источник:** [Dennis M. Ritchie: The Evolution of the Unix Time-sharing System](https://www.bell-labs.com/usr/dmr/www/hist.html)

60. Что находится в /home?

   **Ответ:** Каталог `/home` служит местом размещения домашних директорий пользователей (`/home/<username>`). Внутри каждой домашней папки пользователь хранит личные данные, документы, локальные репозитории кода и пользовательские конфигурации программ (dotfiles).

   **Пример:**

   ```bash
   echo $HOME
   # /home/developer

   ```

   **Типичная ошибка:** Жестко рассчитывать, что домашняя папка всегда лежит в `/home`. Путь определяется полем в файле `/etc/passwd` и для конкретных пользователей может находиться в `/var/lib/daemon` или на сетевом диске LDAP.

   **Источник:** [FHS 3.0: /home : User home directories](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s08.html)

61. Что хранится в /root?

   **Ответ:** Каталог `/root` — домашняя директория суперпользователя `root`. В отличие от обычных пользователей, чьи каталоги располагаются в `/home`, профиль `root` расположен непосредственно на корневом разделе `/`, что гарантирует доступ к учетной записи администратора при сбоях монтирования вспомогательных файловых систем.

   **Пример:**

   ```bash
   sudo ls -la /root
   # Личные dotfiles суперпользователя: .bashrc, .ssh, .profile

   ```

   **Типичная ошибка:** Попытка зайти в `/root` под обычным непривилегированным пользователем: по умолчанию каталог имеет строгие права доступа `0700` (`drwx------`).

   **Источник:** [FHS 3.0: /root : Home directory for the root user](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s14.html)

62. Чем /root отличается от /home/root?

   **Ответ:** `/root` лежит непосредственно на корневом разделе файловой системы, а `/home` исторически часто выносится на отдельный физический диск, LVM-том или сетевой ресурс (NFS). Если бы профиль root находился в `/home/root`, при сбое или повреждении монтирования раздела `/home` администратор не смог бы войти в систему для восстановления в аварийном режиме. Путь `/home/root` в стандартных дистрибутивах Linux отсутствует.

   **Пример:**

   [Диск 1: Rootfs] ───► /root (всегда доступен на корне)
   [Диск 2: Раздел Home] ───► /home/user1, /home/user2 (монтируется позже)

   **Типичная ошибка:** Вручную переносить домашнюю директорию root в `/home/root` в файле `/etc/passwd`, нарушая отказоустойчивость загрузки в emergency mode.

   **Источник:** [Linux Standard Base: System Administrator Home Directory](https://refspecs.linuxfoundation.org/)

63. Для чего нужен /tmp?

   **Ответ:** Каталог `/tmp` (Temporary) предназначен для временных файлов, создаваемых программами во время выполнения. Доступ на создание файлов в `/tmp` открыт для любых пользователей и процессов, а его содержимое очищается системой при перезагрузке (или автоматически демонами очистки раз в заданный период).

   **Пример:**

   ```bash
   ls -ld /tmp
   # drwxrwxrwt ... /tmp (права 1777 — полный доступ с Sticky bit)

   ```

   **Типичная ошибка:** Использовать `/tmp` для хранения файлов, которые должны гарантированно пережить перезагрузку системы (для этого используется `/var/tmp`).

   **Источник:** [FHS 3.0: /tmp : Temporary files](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s18.html)

64. Какие особенности у /tmp?

   **Ответ:**

      1. **Sticky Bit (`chmod +t` / права `1777`):** Любой пользователь может создавать файлы, но удалять или переименовывать файл имеет право только его владелец или `root`.

      2. **Монтирование в RAM (tmpfs):** В современных дистрибутивах `/tmp` часто монтируется как файловая система в оперативной памяти, что дает высокую скорость I/O, но расходует ОЗУ при записи больших объемов.

   **Пример:**

   ```bash
   df -h /tmp
   # Filesystem  Size  Used  Avail  Use%  Mounted on
   # tmpfs       16G   1.2M  16G    1%    /tmp

   ```

   **Типичная ошибка:** Небезопасное создание файлов в `/tmp` с фиксированным именем (insecure temp file vulnerability), ведущее к атакам через symlink race condition (вместо этого нужно использовать `mkstemp()` или `std::filesystem::temp_directory_path()`).

   **Источник:** [CWE-377: Insecure Temporary File](https://cwe.mitre.org/data/definitions/377.html)

65. Что обычно хранится в /var?

   **Ответ:** Каталог `/var` (Variable data) предназначен для хранения изменяемых данных, размер которых динамически растет в процессе штатной работы операционной системы: системные логи, spool-очереди печати и почты, кэши пакетных менеджеров, временные runtime-блокировки и базы данных.

   **Пример:**

   ```bash
   du -sh /var/*
   # /var/log, /var/cache, /var/lib, /var/spool

   ```

   **Типичная ошибка:** Размещать статические бинарники программ в `/var`. Данный каталог должен содержать исключительно динамически меняющиеся данные приложений.

   **Источник:** [FHS 3.0: /var : Variable data](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch05.html)

66. Что лежит в /var/log?

   **Ответ:** В каталоге `/var/log` централизованно хранятся текстовые и бинарные файлы журналов (логов) ядра, операционной системы, служб аутентификации и сторонних сервисов (`syslog`, `journald`, `auth.log`, логи веб-серверов nginx, СУБД).

   **Пример:**

   ```bash
   ls /var/log/nginx/ /var/log/dmesg /var/log/auth.log

   ```

   **Типичная ошибка:** Не настраивать ротацию логов (`logrotate`): неконтролируемый рост файлов в `/var/log` может полностью переполнить дисковое пространство раздела, заблокировав запись для баз данных и системных сервисов.

   **Источник:** [Linux man pages: logrotate(8)](https://man7.org/linux/man-pages/man8/logrotate.8.html)

67. Для чего нужен /var/tmp?

   **Ответ:** Каталог `/var/tmp` предназначен для хранения временных файлов большого размера или файлов, которые должны гарантированно сохраняться между перезагрузками операционной системы (например, кэши компиляции ccache, дампы отчетов, образы временных дампов баз данных).

   **Пример:**

   ```cpp
   #include <filesystem>
   // Использование /var/tmp для файлов, требующих выживания после перезагрузки узла:
   namespace fs = std::filesystem;
   fs::path p = "/var/tmp/large_calculation_checkpoint.dat";

   ```

   **Типичная ошибка:** Полагать, что файлы в `/var/tmp` хранятся вечно. По стандарту systemd-tmpfiles файлы в `/var/tmp` удаляются, если к ним не обращались в течение 30 дней (для `/tmp` — обычно 10 дней или каждая перезагрузка).

   **Источник:** [FHS 3.0: /var/tmp : Temporary files preserved between reboots](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch05s15.html)

68. Чем /tmp отличается от /var/tmp?

   **Ответ:** Различие состоит в энергонезависимости и времени жизни: `/tmp` обычно расположен в ОЗУ (`tmpfs`) и полностью очищается при каждом ребуте, а `/var/tmp` всегда размещается на постоянном дисковом носителе и сохраняет данные при перезагрузке машины.

   **Пример:**

   | Характеристика | `/tmp` | `/var/tmp` |
   | --- | --- | --- |
   | Носитель | Часто RAM (`tmpfs`) | Физический диск |
   | Очистка при reboot | Да (гарантированно очищается) | Нет (сохраняется) |
   | Срок хранения | Кратковременный (часы / дни) | Долговременный (по умолчанию 30 дней) |

   **Типичная ошибка:** Записывать временный файл объемом 100 ГБ в `/tmp`, смонтированный в `tmpfs` на машине с 32 ГБ RAM. Система исчерпает память и аварийно завершит процессы через OOM Killer; такие файлы необходимо направлять в `/var/tmp`.

   **Источник:** [systemd-tmpfiles configuration: tmp.conf](https://www.freedesktop.org/software/systemd/man/tmpfiles.d.html)

69. Что находится в /usr?

   **Ответ:** Каталог `/usr` (Unix System Resources / Universal System Resources) содержит вторую, основную иерархию системы: всё прикладное ПО, библиотеки, документацию, заголовочные файлы и графические среды, доступные только для чтения обычным пользователям. Исторически `/usr` проектировался как раздел, доступный для монтирования в режиме Read-Only сразу нескольким машинам по сети.

   **Пример:**

   ```bash
   ls /usr
   # bin  include  lib  lib64  local  sbin  share  src

   ```

   **Типичная ошибка:** Считать, что каталог `/usr` изменяется при обычной пользовательской работе. Данные в `/usr` модифицируются исключительно системным пакетным менеджером при установке/обновлении ПО.

   **Источник:** [FHS 3.0: /usr : Secondary hierarchy](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch04.html)

70. Почему /usr — не домашняя папка пользователя?

   **Ответ:** В 1970-х годах в Unix на PDP-11 первый жесткий диск переполнился, и разработчики смонтировали второй диск в точку `/usr` («user»), перенеся туда пользовательские папки. Однако очень быстро `/usr` заполнился общими утилитами операционной системы, компиляторами и библиотеками. Для домашних директорий пользователей создали отдельный каталог `/home`, а аббревиатуру `/usr` ретроспективно переосмыслили как **Unix System Resources**.

   **Пример:**

   Историческая трансформация:
   1971: /usr/dmr, /usr/ken (домашки)
   1980-е: /home/dmr (домашки вынесены), /usr становится хранилищем системного софта

   **Типичная ошибка:** Создавать учетные записи пользователей с путями домашних директорий в `/usr/<username>`.

   **Источник:** [Ken Thompson, Dennis Ritchie: Bell Labs Unix History Notes](https://www.bell-labs.com/)

71. Что хранится в /usr/bin?

   **Ответ:** Каталог `/usr/bin` содержит подавляющее большинство скомпилированных исполняемых пользовательских программ и утилит, установленных пакетным менеджером дистрибутива (`python3`, `gcc`, `git`, `curl`, `gdb`).

   **Пример:**

   ```bash
   which git g++
   # /usr/bin/git
   # /usr/bin/g++

   ```

   **Типичная ошибка:** Вручную копировать собственные бинарники самописных проектов в `/usr/bin`. Каталог полностью управляется пакетным менеджером (`apt`/`dnf`), который может стереть или затереть сторонний файл при обновлении пакетов.

   **Источник:** [FHS 3.0: /usr/bin : Most user commands](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch04s04.html)

72. Что хранится в /usr/lib?

   **Ответ:** Каталог `/usr/lib` (или `/usr/lib64`) содержит динамические и статические разделяемые библиотеки (`.so`, `.a`), необходимые для работы бинарников из `/usr/bin` и `/usr/sbin`, а также внутренние бинарные модули пакетов, не предназначенные для прямого вызова пользователем.

   **Пример:**

   ```bash
   ls /usr/lib/x86_64-linux-gnu/libstdc++.so.*

   ```

   **Типичная ошибка:** Путать `/usr/lib` и `/usr/libexec`. Вспомогательные исполняемые бинарные программы демонов по стандарту FHS 3.0 должны размещаться в `/usr/libexec`, а не в библиотечных каталогах.

   **Источник:** [FHS 3.0: /usr/lib : Libraries for programming and packages](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch04s06.html)

73. Что хранится в /usr/local?

   **Ответ:** Каталог `/usr/local` предназначен для программ, утилит и библиотек, устанавливаемых системным администратором вручную (например, сборка из исходников через `make install`, минуя официальный пакетный менеджер ОС). Он имеет ту же внутреннюю структуру, что и `/usr` (`bin`, `lib`, `include`, `share`).

   **Пример:**

   ```bash
   # Ручная сборка библиотеки из исходников по умолчанию ставится сюда:
   cmake -B build -DCMAKE_INSTALL_PREFIX=/usr/local
   cmake --install build
   # Заголовочные файлы попадут в /usr/local/include, а библиотека — в /usr/local/lib

   ```

   **Типичная ошибка:** Очищать `/usr/local` пакетным менеджером дистрибутива. Пакетный менеджер Linux никогда не трогает содержимое `/usr/local` при штатных операциях обновления ОС.

   **Источник:** [FHS 3.0: /usr/local : Local hierarchy](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch04s09.html)

74. Чем /usr/local/bin отличается от /usr/bin?

   **Ответ:** `/usr/bin` управляется исключительно системным пакетным менеджером ОС (`apt`, `dnf`, `pacman`). `/usr/local/bin` управляется администратором вручную для кастомных сборок. В переменной `$PATH` каталог `/usr/local/bin` по умолчанию стоит **раньше**, чем `/usr/bin`, что позволяет переопределять системные версии утилит собственными сборками.

   **Пример:**

   ```bash
   echo $PATH
   # Вывод: /usr/local/bin:/usr/bin:/bin:...
   # Если положить свой cmake в /usr/local/bin, вызов 'cmake' выполнит именно его, а не системный из /usr/bin

   ```

   **Типичная ошибка:** Устанавливать утилиты из исходников прямо в `/usr/bin`, перезаписывая системные зависимости дистрибутива.

   **Источник:** [FHS 3.0: /usr/local/bin](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch04s09.html)

75. Когда программы ставятся в /opt?

   **Ответ:** Каталог `/opt` (Optional software) зарезервирован для установки крупного стороннего, проприетарного или монолитного программного обеспечения, которое поставляется в виде самодостаточного изолированного пакета и не разбивается по стандартным каталогам системы (`/opt/<vendor>/<package>` — например, Google Chrome, CLion, Docker Desktop).

   **Пример:**

   ```bash
   ls -d /opt/*
   # /opt/google/chrome
   # /opt/jetbrains

   ```

   **Типичная ошибка:** Ожидать, что бинарники из `/opt/myapp/bin` будут доступны сразу в консоли. Каталоги из `/opt` не входят в `$PATH` по умолчанию; для запуска создают symlink в `/usr/local/bin` или настраивают переменную окружения.

   **Источник:** [FHS 3.0: /opt : Add-on application software packages](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s13.html)

76. Для чего нужен /dev?

   **Ответ:** Каталог `/dev` (Devices) содержит специальные файлы устройств, предоставляющие интерфейс ввода-вывода к драйверам оборудования ядра (диски, видеокарты, последовательные порты, псевдотерминалы) и виртуальным генераторам ядра (`/dev/null`, `/dev/urandom`). Файловая система управляется ядром динамически через `devtmpfs` и демон `udev`.

   **Пример:**

   ```bash
   ls -l /dev/sda /dev/urandom

   ```

   **Типичная ошибка:** Пытаться создать файл устройства обычной командой `touch`. Файлы устройств создаются системным вызовом `mknod()` с указанием типа (block/character) и номеров major/minor, либо автоматически ядром через udev.

   **Источник:** [Linux man pages: udev(7)](https://man7.org/linux/man-pages/man7/udev.7.html)

77. Что такое device files в /dev?

   **Ответ:** Device files (файлы устройств / специальные файлы узлов) — это точки входа в драйверы ядра, представленные в VFS. Они не занимают места на диске и идентифицируются двумя числами: **Major number** (определяет драйвер ядра) и **Minor number** (определяет конкретное устройство или раздел этого драйвера). Разделяются на символьные (`c`, побайтовый поток: мыши, терминалы) и блочные (`b`, произвольный блочный доступ через page cache: SSD, HDD).

   **Пример:**

   ```bash
   ls -l /dev/null /dev/nvme0n1
   # crw-rw-rw- 1 root root  1, 3 ... /dev/null     (Character: Major 1, Minor 3)
   # brw-rw---- 1 root disk 259, 0 ... /dev/nvme0n1 (Block: Major 259, Minor 0)

   ```

   **Типичная ошибка:** Считать, что чтение из блочного устройства (`/dev/sda`) идет в обход оперативной памяти. Доступ к блочным файлам устройств кэшируется в системном Page Cache так же, как и обычные файлы.

   **Источник:** [Linux man pages: mknod(2)](https://man7.org/linux/man-pages/man2/mknod.2.html)

78. Что такое /proc и почему он выглядит как обычная ФС?

   **Ответ:** `/proc` — псевдофайловая система (procfs), генерируемая ядром Linux непосредственно в RAM. Она реализована через интерфейс VFS (Virtual File System) ядра: функции чтения/записи VFS перенаправляются на внутренние структуры ядра, поэтому системная информация выглядит как стандартные текстовые файлы и папки для удобства навигации стандартными утилитами Unix (`cat`, `grep`).

   **Пример:**

   ```cpp
   #include <fstream>
   #include <string>

   // Чтение параметров ядра через стандартный интерфейс файлового ввода-вывода:
   std::ifstream file("/proc/sys/kernel/osrelease");
   std::string release;
   file >> release;

   ```

   **Типичная ошибка:** Пытаться открыть файл из `/proc` в режиме одновременного чтения и записи (`O_RDWR`), если файл ядра поддерживает только односторонний вывод или одностороннюю конфигурацию.

   **Источник:** [Linux Kernel Documentation: The /proc Filesystem](https://docs.kernel.org/filesystems/proc.html)

79. Что можно посмотреть в /proc/cpuinfo?

   **Ответ:** Файл содержит детальные аппаратные характеристики каждого логического ядра CPU, зарегистрированного ядром: архитектуру, модель процессора, тактовую частоту, размер кэшей (L1/L2/L3), физический ID сокета, а также флаги аппаратных инструкций (SSE, AVX-512, VMX, AES).

   **Пример:**

   ```bash
   grep -m 1 "model name" /proc/cpuinfo
   grep "flags" /proc/cpuinfo | head -n 1

   ```

   **Типичная ошибка:** Парсить `/proc/cpuinfo` в latency-critical C++ коде для проверки инструкций при каждом вызове функции. Информацию парсят один раз при старте или используют вызов `getauxval(AT_HWCAP)` / инструкцию `cpuid`.

   **Источник:** [Linux man pages: proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html)

80. Что можно посмотреть в /proc/meminfo?

   **Ответ:** Файл предоставляет полную оперативную сводку подсистемы виртуальной памяти ядра: общий объем ОЗУ (`MemTotal`), свободную память (`MemFree`), доступную для новых приложений без ухода в swap память (`MemAvailable`), объем Page Cache (`Cached`), размер буферов ядра (`Buffers`), использование Swap, а также объем структур SLAB-аллокатора ядра.

   **Пример:**

   ```bash
   grep -E "MemTotal|MemAvailable|SwapFree" /proc/meminfo

   ```

   **Типичная ошибка:** Считать показатель `MemFree` индикатором нехватки памяти в Linux. Ядро намеренно утилизирует «свободную» память под кэширование файлов (Page Cache). Реальным индикатором доступных ресурсов является поле `MemAvailable`.

   **Источник:** [Linux man pages: proc(5) - /proc/meminfo](https://man7.org/linux/man-pages/man5/proc.5.html)

81. Что такое /proc/?

   **Ответ:** Директория в `procfs`, представляющая состояние конкретного процесса с идентификатором `PID`. Содержит метаданные процесса:

   * `/proc/<pid>/cmdline` — аргументы запуска;
   * `/proc/<pid>/status` — детальный статус, потребление памяти (VmRSS, VmSize) и потоки;
   * `/proc/<pid>/fd/` — симлинки на все открытые файловые дескрипторы;
   * `/proc/<pid>/maps` — карта виртуального адресного пространства (VMA);
   * `/proc/<pid>/exe` — симлинк на исполняемый ELF-файл на диске.

   **Пример:**

   ```bash
   # Просмотр открытых сокетов и файлов текущего процесса оболочки:
   ls -l /proc/$$/fd

   ```

   **Типичная ошибка:** Читать `/proc/<pid>/cmdline` как одну строку с пробелами: ядро разделяет аргументы символом `\0` (null byte), а не пробелом.

   **Источник:** [Linux man pages: proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html)

82. Для чего нужен /sys?

   **Ответ:** Каталог `/sys` (sysfs) — псевдофайловая система, отражающая внутреннее объектное дерево ядра (`kobjects`). Она предназначена для структурированного экспорта информации об устройствах, драйверах, системных шинах (PCI, USB), топологии ядер CPU, энергопотреблении и блочных очередях в строгом машиночитаемом формате «один параметр — один файл».

   **Пример:**

   ```bash
   # Чтение максимальной частоты процессора CPU 0:
   cat /sys/devices/system/cpu/cpu0/cpufreq/cpuinfo_max_freq

   ```

   **Типичная ошибка:** Парсить конфигурацию устройств через сырой вывод `dmesg` вместо использования структурированных узлов в `/sys`.

   **Источник:** [Linux Kernel Documentation: sysfs](https://docs.kernel.org/filesystems/sysfs.html)

83. Что находится в /run?

   **Ответ:** Каталог `/run` — энергонезависимая псевдофайловая система в оперативной памяти (`tmpfs`), хранящая runtime-состояние системы с момента загрузки: pid-файлы запущенных демонов, UNIX Domain Sockets (`.sock`), lock-файлы и сокеты управления systemd. Очищается при выключении питания.

   **Пример:**

   ```bash
   ls /run/systemd/system /run/user/1000

   ```

   **Типичная ошибка:** Использовать устаревший путь `/var/run`. В современных системах `/var/run` является простой символической ссылкой на `/run` для обеспечения обратной совместимости.

   **Источник:** [FHS 3.0: /run : Run-time variable data](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s15.html)

84. Что находится в /mnt?

   **Ответ:** Каталог `/mnt` (Mount) предназначен для временного ручного монтирования файловых систем системным администратором (например, аварийное подключение диска для восстановления `mount /dev/sdb1 /mnt`).

   **Пример:**

   ```bash
   sudo mount /dev/sdb1 /mnt
   cd /mnt

   ```

   **Типичная ошибка:** Использовать `/mnt` для постоянного автомонтирования дисков серверов в продакшене. Долговременные точки монтирования принято размещать в подкаталогах вроде `/data`, `/srv` или специализированных путях.

   **Источник:** [FHS 3.0: /mnt : Mount point for a temporarily mounted filesystem](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s12.html)

85. Что находится в /media?

   **Ответ:** Каталог `/media` используется как точка автомонтирования сменных носителей информации (USB-флешки, внешние жесткие диски, CD/DVD-диски), подключаемых пользователем. Монтирование выполняется автоматически системными демонами (например, `udisks2`) в поддиректории вида `/media/<user>/<label>`.

   **Пример:**

   ```bash
   ls /media/$USER/
   # Отобразит вставленный внешний накопитель "USB_FLASH"

   ```

   **Типичная ошибка:** Ожидать автоматического монтирования флешек в `/mnt`. Графические оболочки и сервисы рабочего стола монтируют сменные диски строго в `/media`.

   **Источник:** [FHS 3.0: /media : Mount point for removable media](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s11.html)

86. Чем /mnt отличается от /media?

   **Ответ:** `/mnt` предназначен для статического ручного монтирования системным администратором для служебных разовых нужд. `/media` используется операционной системой для автоматического динамического монтирования сменных пользовательских носителей с генерацией подкаталогов по имени носителя.

   **Пример:**

   | Каталог | Тип монтирования | Кем управляется | Применение |
   | --- | --- | --- | --- |
   | `/mnt` | Ручное | Системный администратор (`root`) | Временный диск для бэкапа, chroot |
   | `/media` | Автоматическое | Системные службы (`udisks2`) | Вставленная USB-флешка, диск |

   **Типичная ошибка:** Монтировать сетевой NFS-ресурс прямо в корень `/media`, ломая структуру автодетекта съемных устройств.

   **Источник:** [FHS 3.0: Comparison of /mnt and /media](https://refspecs.linuxfoundation.org/FHS_3.0/)

87. Что хранится в /boot?

   **Ответ:** Каталог `/boot` содержит всё необходимое для начального этапа загрузки ОС до момента инициализации VFS ядра: сжатый бинарный образ ядра Linux (`vmlinuz`), образ начальной файловой системы RAM (`initramfs` / `initrd`), карту системных символов ядра (`System.map`) и конфигурацию загрузчика GRUB (`/boot/grub/grub.cfg`).

   **Пример:**

   ```bash
   ls /boot
   # config-6.8.0-31-generic  initrd.img-6.8.0-31-generic  vmlinuz-6.8.0-31-generic  grub

   ```

   **Типичная ошибка:** Переполнение раздела `/boot` старыми ядрами. Если `/boot` вынесен на отдельный небольшой раздел (например, 500 МБ), накопление старых версий ядер блокирует обновление системы из-за невозможности сгенерировать новый initramfs.

   **Источник:** [FHS 3.0: /boot : Static files of the boot loader](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s05.html)

88. Что такое initramfs?

   **Ответ:** Initramfs (initial RAM filesystem) — сжатый cpio-архив корневой файловой системы, который ядро распаковывает в rootfs при загрузке; внешний архив передаётся ядру загрузчиком. Он содержит минимальный набор драйверов (для контроллеров дисков NVMe/SATA, RAID, шифрования LUKS, LVM) и скриптов, необходимых для обнаружения и монтирования реального корневого раздела (`/`), после чего управление передается постоянному `/sbin/init`.

   **Пример:**

   ```bash
   lsinitramfs /boot/initrd.img-$(uname -r) | grep nvme

   ```

   **Типичная ошибка:** Полагать, что ядро Linux содержит драйверы для всех существующих дисковых контроллеров внутри файла `vmlinuz`. Ядро делают компактным, а драйверы контроллеров дисков выносят в модули внутри `initramfs`.

   **Источник:** [Linux Kernel Documentation: ramfs-rootfs-initramfs](https://docs.kernel.org/filesystems/ramfs-rootfs-initramfs.html)

89. Что лежит в /lib?

   **Ответ:** Исторически каталог `/lib` содержит критически важные разделяемые библиотеки (`libc.so`, динамический компоновщик `ld-linux.so`), необходимые для запуска бинарников из `/bin` и `/sbin`, а также каталог с модулями текущего ядра Linux (`/lib/modules/$(uname -r)/`).

   **Пример:**

   ```bash
   ls /lib/modules/$(uname -r)
   # Драйверы ядра (.ko), скомпилированные под текущую запущенную версию

   ```

   **Типичная ошибка:** Попытка вручную скопировать стороннюю библиотеку в `/lib` вместо использования стандартного `/usr/local/lib` или настройки `rpath`/`LD_LIBRARY_PATH`.

   **Источник:** [FHS 3.0: /lib : Essential shared libraries and kernel modules](https://refspecs.linuxfoundation.org/FHS_3.0/fhs/ch03s10.html)

90. Чем /lib отличается от /usr/lib?

   **Ответ:** В классическом FHS разделение строгое: в `/lib` располагаются библиотеки, жизненно необходимые для старта системы в аварийном режиме до монтирования раздела `/usr` (базовая `libc`, math library). В `/usr/lib` находятся библиотеки для остального прикладного ПО (`libcurl`, `libssl`, библиотеки GUI и фреймворков). В современных дистрибутивах (UsrMerge) `/lib` является символической ссылкой на `/usr/lib`.

   **Пример:**

   ```bash
   ls -ld /lib
   # lrwxrwxrwx 1 root root 7 ... /lib -> usr/lib

   ```

   **Типичная ошибка:** Полагаться в скриптах на физическую раздельность каталогов `/lib` и `/usr/lib` на современных дистрибутивах Linux.

   **Источник:** [The Case for the /usr Merge: Lennart Poettering](https://www.freedesktop.org/wiki/Software/systemd/TheCaseForTheUsrMerge/)

91. Что такое symbolic links внутри FHS?

   **Ответ:** Символическая ссылка (symlink) — специальный тип файла в VFS, содержащий в виде текста путь к целевому файлу или директории. Внутри FHS symlink активно используются для обеспечения обратной совместимости при переходе на новые схемы стандартов (например, ссылки на объединенный `/usr`, ссылки на версионированные библиотеки `libfoo.so -> libfoo.so.1.0`).

   **Пример:**

   ```bash
   ls -l /usr/lib/x86_64-linux-gnu/libz.so
   # lrwxrwxrwx ... libz.so -> libz.so.1.2.13

   ```

   **Типичная ошибка:** Создание циклических символических ссылок (`a -> b -> a`), вызывающее ошибку ядра `ELOOP` (Too many levels of symbolic links).

   **Источник:** [Linux man pages: symlink(7)](https://man7.org/linux/man-pages/man7/symlink.7.html)

92. Почему /bin иногда является symlink на /usr/bin?

   **Ответ:** Это результат реформы **UsrMerge**. Историческое разделение на `/bin` и `/usr/bin` было обусловлено маленьким размером жестких дисков в 1970-х годах. В современных системах все бинарники объединили в единый каталог `/usr/bin`, а `/bin` оставили в виде символической ссылки (`/bin -> usr/bin`), чтобы сохранить совместимость со старыми скриптами с жестко прописанным шебангом `#!/bin/sh` или `#!/bin/bash`.

   **Пример:**

   ```bash
   ls -ld /bin /sbin /lib /lib64
   # lrwxrwxrwx ... /bin -> usr/bin
   # lrwxrwxrwx ... /sbin -> usr/sbin
   # lrwxrwxrwx ... /lib -> usr/lib
   # lrwxrwxrwx ... /lib64 -> usr/lib64

   ```

   **Типичная ошибка:** Попытка удалить «дублирующийся» каталог `/bin`, что моментально уничтожает всю систему исполнения команд ОС.

   **Источник:** [Debian Wiki: UsrMerge](https://wiki.debian.org/UsrMerge)

93. Что произойдет, если удалить важный файл из /etc?

   **Ответ:** Зависит от файла:

   * Удаление `/etc/fstab`: система не сможет смонтировать файловые системы при следующем ребуте и свалится в Emergency Shell.
   * Удаление `/etc/passwd`: перестанет работать авторизация, команды `sudo`, `login` и определение владельцев процессов.
   * Удаление `/etc/resolv.conf`: перестанет резолвиться сетевые доменные имена (DNS).
   Однако работающие процессы не упадут немедленно, так как они уже загрузили настройки в память при старте.

   **Пример:**

   ```bash
   # Восстановление типовых конфигов из шаблонов пакетов (Debian/Ubuntu):
   sudo apt-get install --reinstall -o Dpkg::Options::="--force-confmiss" <package_name>

   ```

   **Типичная ошибка:** Редактировать важные файлы в `/etc` без создания резервной копии (`cp /etc/fstab /etc/fstab.bak`).

   **Источник:** [Linux Administration Handbook: Configuration files failure](https://www.pearson.com/)

94. Где обычно лежат system-wide config файлы?

   **Ответ:** Общесистемные конфигурации располагаются строго в каталоге `/etc/` или его поддиректориях (`/etc/ssh/sshd_config`, `/etc/nginx/nginx.conf`). Конфигурации по умолчанию, поставляемые разработчиками пакетов и не предназначенные для прямой правки администратором, часто хранятся в `/usr/lib/<package>/` (например, `/usr/lib/systemd/system/`).

   **Пример:**

   ```bash
   # Иерархия переопределения конфигурации systemd:
   # 1. /etc/systemd/system/ (высший приоритет — переопределение администратором)
   # 2. /usr/lib/systemd/system/ (низший приоритет — дефолт пакета)

   ```

   **Типичная ошибка:** Редактировать дефолтные файлы конфигураций пакетов в `/usr/lib/`, которые будут перезаписаны при первом же обновлении системы через `apt upgrade`.

   **Источник:** [systemd.unit(5) — Unit Load Path](https://www.freedesktop.org/software/systemd/man/systemd.unit.html)

95. Где обычно лежат user-specific config файлы?

   **Ответ:** Пользовательские конфигурационные файлы располагаются в домашней директории пользователя `$HOME`. Согласно современному стандарту **XDG Base Directory Specification**, они должны лежать в каталоге `~/.config/` (`$XDG_CONFIG_HOME`), а исторически располагаются в виде скрытых dot-файлов прямо в корне домашнего каталога (`~/.bashrc`, `~/.vimrc`).

   **Пример:**

   ```bash
   echo ${XDG_CONFIG_HOME:-$HOME/.config}
   # Каноническое место пользовательских конфигов: ~/.config/<app_name>/config

   ```

   **Типичная ошибка:** Жестко записывать конфиги в корень `$HOME/.myapp` в новых программах вместо поддержки спецификации XDG (`~/.config/myapp`).

   **Источник:** [XDG Base Directory Specification](https://specifications.freedesktop.org/basedir-spec/basedir-spec-latest.html)

96. Что такое hidden files в home directory?

   **Ответ:** Hidden files («скрытые файлы» или dotfiles) — файлы или директории, имя которых начинается с символа точки (`.`). Утилита `ls` и графические менеджеры по умолчанию скрывают их отображение при обычном листинге. Традиционно используются для хранения индивидуальных пользовательских настроек окружения, профилей и кэшей.

   **Пример:**

   ```bash
   ls -a ~
   # .bashrc  .profile  .ssh  .config  .local  .cache

   ```

   **Типичная ошибка:** Считать, что точка в начале имени файла обеспечивает безопасность или защиту данных. Это исключительно соглашение отображения в утилитах пользовательского пространства (`ls` пропускает файлы, начинающиеся с точки, если не передан флаг `-a`).

   **Источник:** [Rob Pike: A brief history of the hidden dotfiles bug](https://plus.google.com/)

97. Что такое ~/.bashrc?

   **Ответ:** `~/.bashrc` — командный скрипт, исполняемый оболочкой Bash при запуске каждого нового интерактивного non-login шелла (например, открытие нового окна терминала в графической среде или запуск подоболочки `bash`). В нем настраиваются алиасы (`alias`), персональный вид приглашения ввода (`PS1`), функции и специфичные переменные окружения.

   **Пример:**

   ```bash
   # Фрагмент ~/.bashrc:
   alias ll='ls -alF'
   export EDITOR=vim

   ```

   **Типичная ошибка:** Добавлять в `~/.bashrc` команды, генерирующие текстовый вывод в `stdout` (например, `echo "Hello"`). Это может нарушить работу утилит удаленного копирования `scp` и `sftp`, которые ожидают чистый поток данных при открытии сессии.

   **Источник:** [GNU Bash Manual: Bash Startup Files](https://www.gnu.org/software/bash/manual/html_node/Bash-Startup-Files.html)

98. Что такое ~/.profile?

   **Ответ:** `~/.profile` — скрипт конфигурации, выполняемый один раз при успешном входе пользователя в систему (login shell). Он предназначен для общих настроек всей пользовательской сессии, не привязанных к конкретной оболочке (запуск ssh-agent, глобальный экспорт переменных `$PATH`, локали).

   **Пример:**

   ```bash
   # Добавление пользовательских бинарников в PATH на уровне всей сессии в ~/.profile:
   if [ -d "$HOME/.local/bin" ] ; then
       PATH="$HOME/.local/bin:$PATH"
   fi

   ```

   **Типичная ошибка:** Настраивать shell-специфичные псевдонимы (`alias`) внутри `~/.profile`: при запуске последующих подоболочек этот файл повторно не считывается.

   **Источник:** [POSIX.1-2017: sh startup](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html)

99. Чем отличаются system config и user config?

   **Ответ:** Различие заключается в области действия и правах:

      1. **System Config (`/etc/`):** Задает глобальные параметры системы по умолчанию, применяется ко всем пользователям ОС и может редактироваться только пользователем `root`.

      2. **User Config (`~/.config/`, dotfiles):** Находится в домашней папке пользователя, управляется самим пользователем без прав `sudo` и переопределяет общесистемные параметры конкретно для его сессии.

   **Пример:**

   Глобальный конфиг Git: /etc/gitconfig (для всех учетных записей машины)
   Пользовательский Git:  ~/.gitconfig   (переопределяет user.name и user.email для текущего юзера)

   **Типичная ошибка:** Менять общесистемный конфиг в `/etc/` для решения локальной задачи одного пользователя, подвергая риску остальных пользователей машины.

   **Источник:** [Linux man pages: hier(7)](https://man7.org/linux/man-pages/man7/hier.7.html)

100. Почему важно понимать FHS разработчику C/C++?

   **Ответ:** Разработчик C/C++ взаимодействует со стандартом FHS на всех стадиях жизненного цикла ПО:

      1. **Сборка и линковка:** Понимание стандартных путей поиска заголовочных файлов (`/usr/include`, `/usr/local/include`) компилятором и библиотек компоновщиком (`/usr/lib`, `/usr/local/lib`).

      2. **Инсталляция:** Корректная настройка сборочных систем (CMake `GNUInstallDirs`, autotools) с разнесением бинарников (`bin`), библиотек (`lib`), заголовков (`include`) и документации (`share/man`).

      3. **Runtime архитектура:** Корректный выбор путей для сокетов IPC (`/run` или `/tmp`), lock-файлов, файлов конфигурации (`/etc`) и изменяемых данных (`/var/lib`).

      4. **Упаковка:** Создание deb/rpm пакетов, полностью совместимых с дистрибутивами Linux.

   **Пример:**

   ```cpp
   #include <cstdlib>
   #include <filesystem>

   // Пример корректного FHS-aware выбора пути конфигурации в C++:
   std::filesystem::path get_config_path() {
       const char* xdg = std::getenv("XDG_CONFIG_HOME");
       if (xdg && *xdg && std::filesystem::path(xdg).is_absolute()) return std::filesystem::path(xdg) / "my_app/app.conf";

       const char* home = std::getenv("HOME");
       if (home && *home) return std::filesystem::path(home) / ".config/my_app/app.conf";

       return "/etc/my_app/app.conf"; // Общесистемный fallback по FHS
   }

   ```

   **Типичная ошибка:** Размещение сгенерированных логов, баз данных SQLite или временных сокетов рядом с исполняемым бинарным файлом в `/usr/bin/` — в Unix-подобных ОС этот каталог доступен приложению исключительно на чтение (`Read-Only`).

   **Источник:** [CMake Documentation: GNUInstallDirs](https://cmake.org/cmake/help/latest/module/GNUInstallDirs.html)

### Basic Commands

101. Что делает команда ls?

   **Ответ:** Выводит список файлов и подкаталогов в указанной директории (по умолчанию в текущей).

   **Пример:**

   ```bash
   ls
   ls /var/log
   ```

   **Типичная ошибка:** Полагаться на порядок вывода `ls` при парсинге в скриптах вместо использования глоббинга или `find`.

   **Источник:** [man7: ls(1)](https://man7.org/linux/man-pages/man1/ls.1.html)

102. Чем ls отличается от ls -l?

   **Ответ:** Обычный `ls` выводит только имена файлов в виде колонок, а флаг `-l` включает подробный длинный формат (long listing): права доступа, количество жестких ссылок, владельца, группу, размер, дату изменения и имя.

   **Пример:**

   ```bash
   ls -l
   # -rw-r--r-- 1 user group 4096 May 10 12:00 main.cpp
   ```

   **Типичная ошибка:** Забывать, что размер каталога в выводе `ls -l` — это размер метаданных самой директории, а не сумма размеров файлов внутри неё.

   **Источник:** [man7: ls(1)](https://man7.org/linux/man-pages/man1/ls.1.html)

103. Что показывает ls -a?

   **Ответ:** Отображает абсолютно все файлы в директории, включая скрытые (имена которых начинаются с точки `.`), а также служебные записи `.` (текущая) и `..` (родительская).

   **Пример:**

   ```bash
   ls -a
   # .  ..  .bashrc  .git  main.cpp
   ```

   **Типичная ошибка:** Использовать шаблон `.*` для удаления скрытых файлов (`rm -rf .*`), что приведет к попытке рекурсивно удалить родительскую директорию `..`.

   **Источник:** [man7: ls(1)](https://man7.org/linux/man-pages/man1/ls.1.html)

104. Что показывает ls -h?

   **Ответ:** Используется в сочетании с `-l` для вывода размеров файлов в удобном для чтения формате (human-readable: K, M, G вместо количества байт).

   **Пример:**

   ```bash
   ls -lh
   # -rw-r--r-- 1 user group 1.5M May 10 12:00 libapp.so
   ```

   **Типичная ошибка:** Запуск `ls -h` без флага `-l`, из-за чего флаг игнорируется и вывод остается обычным списком имен.

   **Источник:** [man7: ls(1)](https://man7.org/linux/man-pages/man1/ls.1.html)

105. Что означает первый символ в выводе ls -l?

   **Ответ:** Первый символ указывает на тип сущности файловой системы (регулярный файл, директория, символическая ссылка, сокет, пайп и т.д.).

   **Пример:**

   ```bash
   # d -> directory, - -> regular file, l -> symlink, c -> char dev, b -> block dev
   ```

   **Типичная ошибка:** Путать тип файла с битами прав доступа (`rwx`).

   **Источник:** [man7: ls(1)](https://man7.org/linux/man-pages/man1/ls.1.html)

106. Что означает d в правах файла?

   **Ответ:** Буква `d` (directory) в первой позиции означает, что данная запись является каталогом.

   **Пример:**

   ```bash
   drwxr-xr-x 2 user group 4096 May 10 12:00 src
   ```

   **Типичная ошибка:** Пытаться открыть каталог системным вызовом `open()` с флагом записи `O_WRONLY`.

   **Источник:** [man7: ls(1)](https://man7.org/linux/man-pages/man1/ls.1.html)

107. Что означает - в начале строки ls -l?

   **Ответ:** Дефис `-` на первой позиции указывает, что объект является обычным регулярным файлом (regular file).

   **Пример:**

   ```bash
   -rw-r--r-- 1 user group 120 May 10 12:00 Makefile
   ```

   **Типичная ошибка:** Считать регулярным файлом именованный канал (FIFO) или сокет.

   **Источник:** [man7: ls(1)](https://man7.org/linux/man-pages/man1/ls.1.html)

108. Что означает l в начале строки ls -l?

   **Ответ:** Буква `l` (link) означает, что объект является символической ссылкой (symlink), указывающей на другой путь.

   **Пример:**

   ```bash
   lrwxrwxrwx 1 root root 7 May 10 12:00 libboost.so -> libboost.so.1.80
   ```

   **Типичная ошибка:** Полагать, что права `rwxrwxrwx` у symlink дают полный доступ: права всегда проверяются на целевом файле.

   **Источник:** [man7: symlink(7)](https://man7.org/linux/man-pages/man7/symlink.7.html)

109. Что делает команда cd?

   **Ответ:** Изменяет текущий рабочий каталог (current working directory) текущего процесса shell.

   **Пример:**

   ```bash
   cd /home/user/project
   ```

   **Типичная ошибка:** Пытаться запустить `cd` из дочернего процесса (например, скрипта) в надежде сменить директорию в родительском терминале.

   **Источник:** [POSIX: cd](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/cd.html)

110. Чем cd .. отличается от cd ~?

   **Ответ:** `cd ..` переходит в родительский каталог относительно текущего, а `cd ~` перемещает в домашний каталог текущего пользователя (`$HOME`).

   **Пример:**

   ```bash
   cd ..  # Подняться на уровень выше
   cd ~   # Перейти в /home/username
   ```

   **Типичная ошибка:** Забывать пробел между `cd` и `..` (команда `cd..` не существует в большинстве Linux-оболочек).

   **Источник:** [POSIX: cd](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/cd.html)

111. Что делает pwd?

   **Ответ:** Печатает абсолютный путь к текущему рабочему каталогу (print working directory).

   **Пример:**

   ```bash
   pwd
   # /home/user/cpp_project
   ```

   **Типичная ошибка:** Не учитывать разницу между логическим путем (`pwd`, учитывающим symlinks) и физическим (`pwd -P`).

   **Источник:** [man7: pwd(1)](https://man7.org/linux/man-pages/man1/pwd.1.html)

112. Что делает cat?

   **Ответ:** Объединяет (concatenate) файлы и выводит их содержимое в стандартный поток вывода (`stdout`).

   **Пример:**

   ```bash
   cat main.cpp
   cat file1.txt file2.txt > combined.txt
   ```

   **Типичная ошибка:** Useless Use of Cat (UUOC): выполнение `cat file | grep text` вместо прямого `grep text file`.

   **Источник:** [man7: cat(1)](https://man7.org/linux/man-pages/man1/cat.1.html)

113. Когда лучше использовать less вместо cat?

   **Ответ:** При просмотре больших файлов или логов, так как `less` загружает данные постранично по мере надобности без чтения файла целиком в память и поддерживает навигацию.

   **Пример:**

   ```bash
   less /var/log/syslog
   ```

   **Типичная ошибка:** Попытка вывести гигабайтный бинарный лог через `cat`, блокирующая терминал и забивающая буфер вывода.

   **Источник:** [man7: less(1)](https://man7.org/linux/man-pages/man1/less.1.html)

114. Что делает touch?

   **Ответ:** Обновляет временные метки доступа и модификации файла (atime и mtime), а если файл не существует — создает пустой файл.

   **Пример:**

   ```bash
   touch new_header.h
   ```

   **Типичная ошибка:** Использовать `touch` для изменения содержимого файла (он только обновляет метаданные или создает пустой файл).

   **Источник:** [man7: touch(1)](https://man7.org/linux/man-pages/man1/touch.1.html)

115. Что делает mkdir?

   **Ответ:** Создает одну или несколько директорий по указанным путям.

   **Пример:**

   ```bash
   mkdir build
   mkdir -p build/release/bin # Создает все промежуточные папки
   ```

   **Типичная ошибка:** Создание вложенной структуры папок без флага `-p`, что приводит к ошибке `No such file or directory`.

   **Источник:** [man7: mkdir(1)](https://man7.org/linux/man-pages/man1/mkdir.1.html)

116. Что делает rm?

   **Ответ:** Удаляет ссылки на файлы и сами файлы из файловой системы.

   **Пример:**

   ```bash
   rm temp.o
   rm -r build/
   ```

   **Типичная ошибка:** Удаление файлов без возможности восстановления (в Linux CLI нет встроенной «Корзины»).

   **Источник:** [man7: rm(1)](https://man7.org/linux/man-pages/man1/rm.1.html)

117. Почему rm -rf опасен?

   **Ответ:** Флаг `-r` рекурсивно удаляет каталоги и всё их содержимое, а `-f` форсирует удаление без предупреждений и игнорирует ошибки; опечатка в пути может удалить корень системы или данные пользователя.

   **Пример:**

   ```bash
   rm -rf /tmp/mybuild # Безопасно
   rm -rf / tmp/mybuild # Фатальная опечатка: пробел после слэша!
   ```

   **Типичная ошибка:** Подстановка неэкранированных или пустых переменных окружения (`rm -rf $VAR/*` при пустом `VAR`).

   **Источник:** [man7: rm(1)](https://man7.org/linux/man-pages/man1/rm.1.html)

118. Что делает cp?

   **Ответ:** Копирует файлы или директории из источника в место назначения.

   **Пример:**

   ```bash
   cp src/main.cpp src/main.cpp.bak
   cp -r include/ build/include/
   ```

   **Типичная ошибка:** Копирование директории без флага `-r` или `-a`, что приводит к пропуску каталога.

   **Источник:** [man7: cp(1)](https://man7.org/linux/man-pages/man1/cp.1.html)

119. Что делает mv?

   **Ответ:** Перемещает или переименовывает файлы и каталоги.

   **Пример:**

   ```bash
   mv old_name.cpp new_name.cpp
   mv *.o build/obj/
   ```

   **Типичная ошибка:** Случайная перезапись целевого файла существующим одноименным без ключа `-i` или `-n`.

   **Источник:** [man7: mv(1)](https://man7.org/linux/man-pages/man1/mv.1.html)

120. Что делает ln?

   **Ответ:** Создает ссылки (жесткие или символические) на существующие файлы.

   **Пример:**

   ```bash
   ln target.txt hardlink.txt
   ln -s target.txt symlink.txt
   ```

   **Типичная ошибка:** Перепутать порядок аргументов (сначала указывается исходный целевой файл, затем путь ссылки).

   **Источник:** [man7: ln(1)](https://man7.org/linux/man-pages/man1/ln.1.html)

121. Что такое hard link?

   **Ответ:** Дополнительное имя (запись в каталоге), указывающее на тот же самый индексный дескриптор (inode) файла в рамках одной файловой системы.

   **Пример:**

   ```bash
   ln main.cpp main_alias.cpp
   # Изменение данных в main_alias.cpp изменит и main.cpp: inode общий
   ```

   **Типичная ошибка:** Попытка создать hard link на каталог или между разными смонтированными разделами диска.

   **Источник:** [man7: link(2)](https://man7.org/linux/man-pages/man2/link.2.html)

122. Что такое symbolic link?

   **Ответ:** Специальный файл, содержимым которого является текстовая строка с путем к целевому файлу или директории (ярлык).

   **Пример:**

   ```bash
   ln -s /opt/lib/libtest.so ./libtest.so
   ```

   **Типичная ошибка:** Создание относительной символической ссылки без учета ее будущего местоположения относительно целевого файла.

   **Источник:** [man7: symlink(7)](https://man7.org/linux/man-pages/man7/symlink.7.html)

123. Чем hard link отличается от symlink?

   **Ответ:** Hard link указывает напрямую на inode (данные сохраняются, пока счетчик ссылок > 0), не может пересекать границы ФС и указывать на директории; Symlink хранит путь в виде строки, может указывать на каталоги и другие ФС, но ломается при перемещении цели.

   **Пример:**

   ```bash
   rm target.txt
   # hardlink.txt продолжает открываться, symlink.txt становится битой (dangling)
   ```

   **Типичная ошибка:** Думать, что удаление исходного файла освобождает память диска, если на его inode всё ещё есть живой hard link.

   **Источник:** [man7: symlink(7)](https://man7.org/linux/man-pages/man7/symlink.7.html)

124. Что делает grep?

   **Ответ:** Ищет строки, соответствующие заданному регулярному выражению или шаблону, в файлах или потоке ввода.

   **Пример:**

   ```bash
   grep "nullptr" main.cpp
   ```

   **Типичная ошибка:** Искать спецсимволы регулярных выражений (`*`, `.`, `[`), забывая экранировать их или использовать флаг `-F` (fixed strings).

   **Источник:** [man7: grep(1)](https://man7.org/linux/man-pages/man1/grep.1.html)

125. Что ищет grep по умолчанию?

   **Ответ:** По умолчанию ищет базовые регулярные выражения (BRE — Basic Regular Expressions), чувствительные к регистру символов.

   **Пример:**

   ```bash
   grep "main(" *.cpp
   ```

   **Типичная ошибка:** Использование метасимволов `+` или `?` в стандартном `grep` без экранирования `\+` и `\?`.

   **Источник:** [man7: grep(1)](https://man7.org/linux/man-pages/man1/grep.1.html)

126. Что делает grep -r?

   **Ответ:** Выполняет рекурсивный поиск по всем файлам во всех поддиректориях указанного пути.

   **Пример:**

   ```bash
   grep -r "class Server" src/
   ```

   **Типичная ошибка:** Запуск `grep -r` в корневой директории сборки, что приводит к поиску внутри тяжелых бинарных артефактов и папки `.git`.

   **Источник:** [man7: grep(1)](https://man7.org/linux/man-pages/man1/grep.1.html)

127. Что делает grep -n?

   **Ответ:** Префиксирует каждую совпавшую строку её порядковым номером в исходном файле.

   **Пример:**

   ```bash
   grep -n "TODO" src/*.cpp
   # src/parser.cpp:42: // TODO: fix memory leak
   ```

   **Типичная ошибка:** Попытка программно парсить строку `grep -n`, не учитывая, что само имя файла может содержать символ двоеточия.

   **Источник:** [man7: grep(1)](https://man7.org/linux/man-pages/man1/grep.1.html)

128. Что делает grep -i?

   **Ответ:** Игнорирует регистр символов при сопоставлении шаблона с текстом (case-insensitive).

   **Пример:**

   ```bash
   grep -i "error" output.log # Находит Error, ERROR, error
   ```

   **Типичная ошибка:** Полагать, что флаг `-i` ускоряет поиск: он требует дополнительных операций нормализации регистра.

   **Источник:** [man7: grep(1)](https://man7.org/linux/man-pages/man1/grep.1.html)

129. Что делает grep -v?

   **Ответ:** Инвертирует условие поиска: выводит только те строки, которые НЕ содержат заданный шаблон.

   **Пример:**

   ```bash
   grep -v "//" config.cfg # Показать строки без комментариев
   ```

   **Типичная ошибка:** Использование `-v` без понимания того, что пустые строки не будут отфильтрованы, если они не содержат шаблон.

   **Источник:** [man7: grep(1)](https://man7.org/linux/man-pages/man1/grep.1.html)

130. Чем grep отличается от egrep / grep -E?

   **Ответ:** `grep` использует базовые регулярные выражения (BRE), где `(`, `)`, `{`, `}`, `+`, `?` требуют экранирования; `grep -E` (или устаревший `egrep`) использует расширенные (ERE), где эти символы являются операторами по умолчанию.

   **Пример:**

   ```bash
   grep -E "int|double" types.h
   # в обычном grep: grep "int\|double" types.h
   ```

   **Типичная ошибка:** Использование вызова `egrep` в новых скриптах (утилита объявлена устаревшей в пользу `grep -E`).

   **Источник:** [man7: grep(1)](https://man7.org/linux/man-pages/man1/grep.1.html)

131. Что такое regex в grep?

   **Ответ:** Регулярное выражение — формальный синтаксис строковых шаблонов с использованием квантификаторов (`*`, `+`), якорей (`^`, `$`) и классов символов (`[...]`) для поиска текста.

   **Пример:**

   ```bash
   grep -E "^#include <.*>" main.cpp
   ```

   **Типичная ошибка:** Отсутствие кавычек вокруг regex в shell, из-за чего метасимволы вроде `*` раскрываются самой командной строкой до передачи в `grep`.

   **Источник:** [man7: regex(7)](https://man7.org/linux/man-pages/man7/regex.7.html)

132. Как найти все вхождения main в .cpp файлах?

   **Ответ:** Использовать рекурсивный `grep` с фильтром по шаблону включения файлов `--include`.

   **Пример:**

   ```bash
   grep -rn --include="*.cpp" "\bmain\b" .
   ```

   **Типичная ошибка:** Запуск `grep "main" *.cpp`, который ищет только в текущей директории и ломается при превышении лимита аргументов `ARG_MAX`.

   **Источник:** [man7: grep(1)](https://man7.org/linux/man-pages/man1/grep.1.html)

133. Что делает find?

   **Ответ:** Выполняет рекурсивный обход иерархии директорий и осуществляет поиск файлов и папок по атрибутам (имени, размеру, времени, типу, правам).

   **Пример:**

   ```bash
   find . -type f -name "*.hpp"
   ```

   **Типичная ошибка:** Попытка использовать `find` для поиска содержимого внутри файлов без комбинации с `grep` или `-exec`.

   **Источник:** [man7: find(1)](https://man7.org/linux/man-pages/man1/find.1.html)

134. Чем find отличается от grep?

   **Ответ:** `find` ищет файлы в дереве каталогов по их именам и метаданным; `grep` ищет текстовые строки внутри содержимого переданных ему файлов или потока.

   **Пример:**

   ```bash
   find src/ -name "*.cpp" | xargs grep "mutex"
   ```

   **Типичная ошибка:** Попытка искать файл на диске с помощью `grep / -r "file.txt"`.

   **Источник:** [man7: find(1)](https://man7.org/linux/man-pages/man1/find.1.html)

135. Как найти файл по имени через find?

   **Ответ:** С помощью предиката `-name` (с учетом регистра) или `-iname` (без учета регистра).

   **Пример:**

   ```bash
   find . -name "CMakeLists.txt"
   ```

   **Типичная ошибка:** Не экранировать шаблон с подстановочными знаками: `find . -name *.cpp` упадет, если в текущей папке есть несколько файлов `.cpp`.

   **Источник:** [man7: find(1)](https://man7.org/linux/man-pages/man1/find.1.html)

136. Как найти файлы по расширению через find?

   **Ответ:** Указать предикат типа `-type f` и маску расширения в `-name` в одинарных кавычках.

   **Пример:**

   ```bash
   find . -type f -name '*.cpp'
   ```

   **Типичная ошибка:** Игнорирование проверки типа `-type f`, из-за чего каталоги с расширением в имени (например, `dir.cpp`) также попадут в вывод.

   **Источник:** [man7: find(1)](https://man7.org/linux/man-pages/man1/find.1.html)

137. Как найти файлы больше определенного размера?

   **Ответ:** С помощью предиката `-size` с указанием суффикса (k, M, G) и знака плюс (`+` для "больше").

   **Пример:**

   ```bash
   find . -type f -size +50M # Больше 50 Мегабайт
   ```

   **Типичная ошибка:** Использование заглавной буквы `K` вместо строчной `k` (в GNU find килобайты обозначаются строчной `k`, а мегабайты заглавной `M`).

   **Источник:** [man7: find(1)](https://man7.org/linux/man-pages/man1/find.1.html)

138. Как найти файлы и удалить их через find?

   **Ответ:** Добавить действие `-delete` в конце команды `find` (либо использовать `-exec rm {} +`).

   **Пример:**

   ```bash
   find build/ -type f -name "*.o" -delete
   ```

   **Типичная ошибка:** Помещать `-delete` в начале команды до предикатов `-name`, что приведет к удалению всех файлов в каталоге подряд.

   **Источник:** [man7: find(1)](https://man7.org/linux/man-pages/man1/find.1.html)

139. Что делает -exec в find?

   **Ответ:** Выполняет указанную внешнюю команду для каждого найденного файла; синтаксис `{}` заменяется на путь к найденному объекту.

   **Пример:**

   ```bash
   find . -name "*.cpp" -exec clang-format -i {} \;
   ```

   **Типичная ошибка:** Забывать завершающий символ экранированной точки с запятой `\;` или плюса `+`.

   **Источник:** [man7: find(1)](https://man7.org/linux/man-pages/man1/find.1.html)

140. Чем -exec отличается от xargs?

   **Ответ:** `-exec \;` порождает отдельный процесс ОС на каждый найденный файл; `xargs` и `-exec +` собирают аргументы в пачки и вызывают утилиту один раз для сотен файлов, что на порядки производительнее.

   **Пример:**

   ```bash
   find . -name "*.o" -exec rm {} +
   find . -name "*.o" -print0 | xargs -0 rm
   ```

   **Типичная ошибка:** Использование `find | xargs` без флагов безопасного разделения пробелов (`-print0` и `xargs -0`).

   **Источник:** [man7: xargs(1)](https://man7.org/linux/man-pages/man1/xargs.1.html)

141. Что делает which?

   **Ответ:** Ищет абсолютный путь к исполняемому файлу команды в каталогах, перечисленных в переменной окружения `$PATH`.

   **Пример:**

   ```bash
   which g++
   # /usr/bin/g++
   ```

   **Типичная ошибка:** Использовать `which` для поиска встроенных команд оболочки (built-ins) вроде `cd` или псевдонимов (aliases) — для них нужен `type` или `command -v`.

   **Источник:** [man7: which(1)](https://man7.org/linux/man-pages/man1/which.1.html)

142. Что делает whereis?

   **Ответ:** Ищет бинарные исполняемые файлы, исходные коды и страницы справочника (man pages) для указанной утилиты в стандартных системных директориях.

   **Пример:**

   ```bash
   whereis clang
   # clang: /usr/bin/clang /usr/lib/clang /usr/share/man/man1/clang.1.gz
   ```

   **Типичная ошибка:** Ожидать от `whereis` поиска пользовательских скриптов, лежащих в нестандартных папках.

   **Источник:** [man7: whereis(1)](https://man7.org/linux/man-pages/man1/whereis.1.html)

143. Что делает file?

   **Ответ:** Определяет реальный тип файла путем анализа его сигнатур (магических чисел в заголовке, magic numbers), а не по расширению имени.

   **Пример:**

   ```bash
   file a.out
   # a.out: ELF 64-bit LSB pie executable, x86-64, dynamically linked...
   ```

   **Типичная ошибка:** Определять тип бинарного файла исключительно по расширению (`.exe`, `.bin`).

   **Источник:** [man7: file(1)](https://man7.org/linux/man-pages/man1/file.1.html)

144. Что делает stat?

   **Ответ:** Отображает подробные метаданные файла или файловой системы: размер, выделенные блоки, номер inode, количество жестких ссылок, права доступа, UID владельца, GID и временные метки (atime, mtime, ctime, btime).

   **Пример:**

   ```bash
   stat app.bin
   ```

   **Типичная ошибка:** Путать ctime (время изменения метаданных/индекса) со временем создания файла (btime/crtime).

   **Источник:** [man7: stat(1)](https://man7.org/linux/man-pages/man1/stat.1.html)

145. Что делает du?

   **Ответ:** Оценивает использование дискового пространства файлами и директориями (disk usage).

   **Пример:**

   ```bash
   du -sh build/
   # 340M    build/
   ```

   **Типичная ошибка:** Запуск `du` без флага `-s` (summary), приводящий к выводу размера каждой отдельной подпапки дерева.

   **Источник:** [man7: du(1)](https://man7.org/linux/man-pages/man1/du.1.html)

146. Что делает df?

   **Ответ:** Показывает информацию об общем, используемом и доступном дисковом пространстве на всех смонтированных файловых системах (disk free).

   **Пример:**

   ```bash
   df -h
   ```

   **Типичная ошибка:** Игнорирование проверки свободного места по inode (`df -i`), когда место есть, но дескрипторы исчерпаны.

   **Источник:** [man7: df(1)](https://man7.org/linux/man-pages/man1/df.1.html)

147. Чем du отличается от df?

   **Ответ:** `du` рекурсивно считает размер файлов через вызовы `stat()`, а `df` опрашивает метаданные суперблока файловой системы; если файл удален, но открыт процессом, `du` его не видит, а `df` считает место занятым.

   **Пример:**

   ```bash
   # Процесс пишет в удаленный лог-файл:
   # df показывает 100% full, а du не находит виновника
   ```

   **Типичная ошибка:** Искать утечку места через `du`, не проверив удаленные открытые дескрипторы через `lsof +L1`.

   **Источник:** [man7: df(1)](https://man7.org/linux/man-pages/man1/df.1.html)

148. Что делает head?

   **Ответ:** Выводит первые $N$ строк (по умолчанию 10) переданного файла или входного потока.

   **Пример:**

   ```bash
   head -n 5 Makefile
   ```

   **Типичная ошибка:** Передача флага в формате `head -5` (устаревший синтаксис, правильный стандартный вариант `-n 5`).

   **Источник:** [man7: head(1)](https://man7.org/linux/man-pages/man1/head.1.html)

149. Что делает tail?

   **Ответ:** Выводит последние $N$ строк (по умолчанию 10) файла или входного потока.

   **Пример:**

   ```bash
   tail -n 20 error.log
   ```

   **Типичная ошибка:** Чтение с конца огромного текстового потока пайпа (требует буферизации данных утилитой).

   **Источник:** [man7: tail(1)](https://man7.org/linux/man-pages/man1/tail.1.html)

150. Что делает tail -f?

   **Ответ:** Запускает режим непрерывного отслеживания (follow): процесс не завершается, а выводит новые строки по мере их дозаписи в файл процессом.

   **Пример:**

   ```bash
   tail -f /var/log/nginx/access.log
   ```

   **Типичная ошибка:** Использование `-f` вместо `-F` при мониторинге логов с ротацией (logrotate пересоздает файл, и `-f` перестает читать).

   **Источник:** [man7: tail(1)](https://man7.org/linux/man-pages/man1/tail.1.html)

151. Что делает wc?

   **Ответ:** Подсчитывает количество строк (`-l`), слов (`-w`), символов (`-m`) или байт (`-c`) в файле или стандартном вводе.

   **Пример:**

   ```bash
   wc -l main.cpp
   # 124 main.cpp
   ```

   **Типичная ошибка:** Считать, что `wc -l` считает переносы строк, забывая, что если последняя строка файла не имеет символа `\n`, она не будет учтена.

   **Источник:** [man7: wc(1)](https://man7.org/linux/man-pages/man1/wc.1.html)

152. Что делает sort?

   **Ответ:** Сортирует строки текстовых файлов или потока ввода по алфавиту или по численным значениям.

   **Пример:**

   ```bash
   sort -n numbers.txt # Числовая сортировка
   sort -u list.txt   # Сортировка с удалением дубликатов
   ```

   **Типичная ошибка:** Сортировать числа без флага `-n`, в результате чего число `100` окажется раньше, чем `2`.

   **Источник:** [man7: sort(1)](https://man7.org/linux/man-pages/man1/sort.1.html)

153. Что делает uniq?

   **Ответ:** Фильтрует или сообщает о повторяющихся строках во входных данных.

   **Пример:**

   ```bash
   uniq -c input.txt # Подсчитать частоту вхождений
   ```

   **Типичная ошибка:** Запуск `uniq` на неотсортированных данных: утилита сравнивает только соседние идущие подряд строки.

   **Источник:** [man7: uniq(1)](https://man7.org/linux/man-pages/man1/uniq.1.html)

154. Почему uniq часто используют вместе с sort?

   **Ответ:** Поскольку `uniq` удаляет только одинаковые строки, идущие непосредственно друг за другом, предварительный вызов `sort` группирует все одинаковые строки вместе.

   **Пример:**

   ```bash
   sort access.log | uniq -c
   ```

   **Типичная ошибка:** Ожидание, что `cat file | uniq` удалит дубликаты, разбросанные по всему файлу.

   **Источник:** [man7: uniq(1)](https://man7.org/linux/man-pages/man1/uniq.1.html)

155. Что делает cut?

   **Ответ:** Вырезает и извлекает определенные секции, символы или поля из каждой строки файла на основе разделителя.

   **Пример:**

   ```bash
   cut -d: -f1 /etc/passwd # Получить список логинов
   ```

   **Типичная ошибка:** Использовать `cut` для данных, где разделителем является произвольное число пробелов (в этом случае лучше использовать `awk`).

   **Источник:** [man7: cut(1)](https://man7.org/linux/man-pages/man1/cut.1.html)

156. Что делает awk на базовом уровне?

   **Ответ:** Текстовый процессор и язык сопоставления шаблонов, разбивающий строки на поля по пробельным разделителям (`$1`, `$2`, ...) и применяющий к ним блоки действий.

   **Пример:**

   ```bash
   awk '{print $1, $3}' data.txt
   ls -l | awk '{sum += $5} END {print sum}' # Сумма размеров
   ```

   **Типичная ошибка:** Путать синтаксис переменных shell `$VAR` и полей `$1` внутри тела кавычек скрипта AWK.

   **Источник:** [man7: gawk(1)](https://man7.org/linux/man-pages/man1/gawk.1.html)

157. Что делает sed на базовом уровне?

   **Ответ:** Потоковый редактор (stream editor), выполняющий построчную трансформацию текста, чаще всего поиск и замену по регулярным выражениям.

   **Пример:**

   ```bash
   sed 's/foo/bar/g' input.txt
   sed -i 's/OLD_FLAG/NEW_FLAG/g' config.h # Замена на месте
   ```

   **Типичная ошибка:** Запуск `sed 's/a/b/'` без флага `g` (global), из-за чего заменяется только первое совпадение в каждой строке.

   **Источник:** [man7: sed(1)](https://man7.org/linux/man-pages/man1/sed.1.html)

158. Что такое pipe (|) в shell?

   **Ответ:** Механизм межпроцессного взаимодействия (IPC), перенаправляющий стандартный вывод (`stdout`) левой команды в стандартный ввод (`stdin`) правой команды через анонимный системный пайп ядра.

   **Пример:**

   ```bash
   cat log.txt | grep "ERROR" | wc -l
   ```

   **Типичная ошибка:** Полагать, что команды в конвейере выполняются последовательно: они запускаются ядром параллельно в разных процессах.

   **Источник:** [man7: pipe(7)](https://man7.org/linux/man-pages/man7/pipe.7.html)

159. Как работает перенаправление > ?

   **Ответ:** Открывает целевой файл на запись с флагом `O_TRUNC`, обрезая его до нулевой длины, и перенаправляет поток `stdout` процесса в этот файл.

   **Пример:**

   ```bash
   ./app > output.log
   ```

   **Типичная ошибка:** Попытка одновременно читать и писать в один и тот же файл через конвейер (`cat f.txt | sort > f.txt`), что сразу затирает файл до пустых данных.

   **Источник:** [POSIX: Redirection](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html#tag_18_07)

160. Чем > отличается от >> ?

   **Ответ:** Оператор `>` перезаписывает файл (очищает перед записью), а `>>` открывает файл в режиме дозаписи в конец (append, флаг ядра `O_APPEND`).

   **Пример:**

   ```bash
   echo "Init" > run.log
   echo "Step 2" >> run.log
   ```

   **Типичная ошибка:** Случайный запуск `>` вместо `>>`, уничтожающий накопленный файл журнала.

   **Источник:** [POSIX: Redirection](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html#tag_18_07)

161. Что делает 2> ?

   **Ответ:** Перенаправляет файловый дескриптор 2 — стандартный поток ошибок (`stderr`) — в указанный файл или устройство.

   **Пример:**

   ```bash
   ./build.sh 2> errors.txt
   ```

   **Типичная ошибка:** Ожидать от `2>` фильтрации обычных информационных сообщений программы, которые пишутся в `stdout`.

   **Источник:** [POSIX: Redirection](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html#tag_18_07)

162. Как объединить stdout и stderr?

   **Ответ:** Использовать конструкцию перенаправления `> file 2>&1` или современный синтаксис Bash `&> file`.

   **Пример:**

   ```bash
   ./my_service > all.log 2>&1
   ```

   **Типичная ошибка:** Написание `2>&1 > file`, при котором `stderr` отправляется на консоль, а не в файл, из-за порядка разбора перенаправлений слева направо.

   **Источник:** [POSIX: Redirection](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html#tag_18_07)

163. Что такое wildcard в shell?

   **Ответ:** Специальные символы подстановки (метасимволы путей, globbing), используемые командной оболочкой для сопоставления имен файлов в каталогах.

   **Пример:**

   ```bash
   ls *.cpp
   rm -f test_?.o
   ```

   **Типичная ошибка:** Путать глоббинг файловой системы (`*.cpp`) с синтаксисом регулярных выражений regex (где `.` — любой символ, а `*` — повторитель).

   **Источник:** [man7: glob(7)](https://man7.org/linux/man-pages/man7/glob.7.html)

164. Чем * отличается от ? в shell patterns?

   **Ответ:** Метасимвол `*` соответствует любой последовательности символов любой длины (включая нулевую), а `?` соответствует ровно одному произвольному символу.

   **Пример:**

   ```bash
   ls file?.txt  # Найдет file1.txt, но пропустит file10.txt
   ls file*.txt  # Найдет и file1.txt, и file10.txt
   ```

   **Типичная ошибка:** Ожидать, что `*` захватит скрытые файлы, начинающиеся с точки (для них требуется явный шаблон `.*`).

   **Источник:** [man7: glob(7)](https://man7.org/linux/man-pages/man7/glob.7.html)

165. Что делает history?

   **Ответ:** Выводит список ранее введенных команд текущей интерактивной сессии оболочки с их порядковыми номерами.

   **Пример:**

   ```bash
   history | grep "cmake"
   !154 # Выполнить команду под номером 154
   ```

   **Типичная ошибка:** Полагаться на сохранность паролей или секретов, переданных в аргументах утилит (они сохраняются в открытом виде в `~/.bash_history`).

   **Источник:** [man7: history(3)](https://man7.org/linux/man-pages/man3/history.3.html)

166. Что делает ps?

   **Ответ:** Выводит снимок (snapshot) текущих активных процессов в системе с их PID, TTY, статусом и командной строкой.

   **Пример:**

   ```bash
   ps aux | grep "app_server"
   ps -ef
   ```

   **Типичная ошибка:** Путать синтаксис параметров BSD (`ps aux` без дефиса) и стандартный POSIX-синтаксис (`ps -ef`).

   **Источник:** [man7: ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)

167. Что делает top?

   **Ответ:** Запускает интерактивный динамический монитор процессов в реальном времени, отображая загрузку CPU, использование памяти, load average и список потоков.

   **Пример:**

   ```bash
   top -H -p $(pgrep my_app) # Мониторинг отдельных потоков конкретного процесса
   ```

   **Типичная ошибка:** Не учитывать разницу между виртуальной памятью (VIRT) и физически выделенной оперативной памятью (RES).

   **Источник:** [man7: top(1)](https://man7.org/linux/man-pages/man1/top.1.html)

168. Что делает kill?

   **Ответ:** Отправляет указанный операционной системой сигнал процессу по его идентификатору PID (по умолчанию посылает сигнал `SIGTERM` / 15).

   **Пример:**

   ```bash
   kill 1234
   kill -TERM 1234
   ```

   **Типичная ошибка:** Считать, что команда `kill` предназначена исключительно для немедленного уничтожения процесса; она отправляет любые сигналы.

   **Источник:** [man7: kill(1)](https://man7.org/linux/man-pages/man1/kill.1.html)

169. Чем kill отличается от kill -9?

   **Ответ:** Обычный `kill` посылает сигнал `SIGTERM` (15), который процесс может перехватить для корректного освобождения ресурсов (graceful shutdown); `kill -9` посылает `SIGKILL`, который не перехватывается, уничтожая процесс ядром мгновенно.

   **Пример:**

   ```bash
   kill -15 $PID # Позволяет C++ объектам вызвать деструкторы
   kill -9 $PID  # Ядро убивает процесс немедленно: файлы/БД могут быть повреждены
   ```

   **Типичная ошибка:** Использовать `kill -9` как первое средство остановки зависшей программы вместо предварительной попытки `SIGTERM`.

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

170. Что делает xargs?

   **Ответ:** Преобразует элементы стандартного потока ввода в аргументы командной строки для указанной исполняемой команды.

   **Пример:**

   ```bash
   cat targets.txt | xargs rm
   ```

   **Типичная ошибка:** Вызов без флага `-0` для списков, содержащих имена с пробелами или кавычками.

   **Источник:** [man7: xargs(1)](https://man7.org/linux/man-pages/man1/xargs.1.html)

171. Что делает man?

   **Ответ:** Форматирует и отображает системные справочные руководства (manual pages) по утилитам, системным вызовам ядра и функциям C-библиотеки.

   **Пример:**

   ```bash
   man 2 open  # Справка по системному вызову Linux
   man 3 printf # Справка по библиотечной функции glibc
   ```

   **Типичная ошибка:** Запуск `man open` без указания номера секции, что может открыть описание команды терминала вместо функции Си.

   **Источник:** [man7: man(1)](https://man7.org/linux/man-pages/man1/man.1.html)

172. Что делает echo?

   **Ответ:** Выводит переданные аргументы в стандартный поток вывода, разделяя их пробелами и завершая символом новой строки.

   **Пример:**

   ```bash
   echo "Build complete"
   echo -n "No newline"
   ```

   **Типичная ошибка:** Использовать управляющие последовательности (`\n`, `\t`) без обязательного флага `-e` в Bash.

   **Источник:** [man7: echo(1)](https://man7.org/linux/man-pages/man1/echo.1.html)

173. Что делает env?

   **Ответ:** Выводит список всех текущих экспортированных переменных окружения либо запускает программу в модифицированном окружении без изменения текущего shell.

   **Пример:**

   ```bash
   env
   env -i CXX=clang++ make # Запуск с чистым окружением
   ```

   **Типичная ошибка:** Использовать `env` для просмотра локальных неэкспортированных переменных shell (они видны через команду `set`).

   **Источник:** [man7: env(1)](https://man7.org/linux/man-pages/man1/env.1.html)

174. Что делает export?

   **Ответ:** Помечает переменную оболочки для автоматической передачи в окружение всех последующих дочерних процессов, порождаемых данным shell.

   **Пример:**

   ```bash
   export LD_LIBRARY_PATH=/usr/local/lib:$LD_LIBRARY_PATH
   ```

   **Типичная ошибка:** Объявление `VAR=value` без `export`, из-за чего дочерние программы не видят эту переменную.

   **Источник:** [POSIX: export](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html#export)

175. Как посмотреть PATH?

   **Ответ:** Вывести значение переменной через команду `echo $PATH`.

   **Пример:**

   ```bash
   echo $PATH
   # /usr/local/bin:/usr/bin:/bin
   ```

   **Типичная ошибка:** Модификация PATH с опечаткой без сохранения `$PATH` (`export PATH=/my/bin`), что лишает терминал доступа ко всем базовым утилитам (`ls`, `cp`).

   **Источник:** [man7: environ(7)](https://man7.org/linux/man-pages/man7/environ.7.html)

176. Почему PATH важен для запуска программ?

   **Ответ:** Он содержит упорядоченный список директорий, в которых операционная система последовательно ищет исполняемый файл, если команда вызвана без указания полного или относительного пути.

   **Пример:**

   ```bash
   gcc main.c # Оболочка найдет gcc в /usr/bin/gcc благодаря $PATH
   ```

   **Типичная ошибка:** Помещение текущей директории `.` в начало `$PATH` (серьезная уязвимость безопасности: троянский бинарник `ls` в рабочей папке выполнится вместо системного).

   **Источник:** [man7: exec(3)](https://man7.org/linux/man-pages/man3/exec.3.html)

177. Как shell находит исполняемый файл?

   **Ответ:** Если путь содержит `/`, shell пробует открыть файл напрямую; иначе последовательно перебирает каталоги из списка переменной `$PATH` слева направо до первого совпадения.

   **Пример:**

   ```bash
   # Поиск команды "make" по директориям /usr/local/bin -> /usr/bin
   ```

   **Типичная ошибка:** Установка двух версий компилятора и непонимание, почему запускается старая (каталог старой стоит раньше в `$PATH`).

   **Источник:** [POSIX: Command Execution](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html#tag_18_09_01_01)

178. Что произойдет, если текущая директория не в PATH?

   **Ответ:** Попытка запустить бинарник без указания пути (например, `a.out`) завершится ошибкой `command not found`.

   **Пример:**

   ```bash
   a.out   # bash: a.out: command not found
   ./a.out # Успешный запуск через явный относительный путь
   ```

   **Типичная ошибка:** Недоумение, почему скомпилированная программа не запускается по простому имени из текущей папки.

   **Источник:** [man7: exec(3)](https://man7.org/linux/man-pages/man3/exec.3.html)

179. Как найти все .h и .cpp файлы в проекте?

   **Ответ:** Использовать утилиту `find` с объединением условий через логический оператор `-o` (OR).

   **Пример:**

   ```bash
   find . -type f \( -name "*.cpp" -o -name "*.h" \)
   ```

   **Типичная ошибка:** Опускать экранированные круглые скобки `\( ... \)`. Без них условия связываются неверно из-за приоритета оператора AND.

   **Источник:** [man7: find(1)](https://man7.org/linux/man-pages/man1/find.1.html)

180. Как через grep найти использование malloc в проекте?

   **Ответ:** Использовать флаги `-r` (рекурсивно), `-n` (номера строк) и границы слова `\b`.

   **Пример:**

   ```bash
   grep -rnw "malloc" src/
   ```

   **Типичная ошибка:** Поиск без границы слова `\b`, что приведет к ложным срабатываниям на словах `my_malloc`, `kmalloc` или `malloc_stats`.

   **Источник:** [man7: grep(1)](https://man7.org/linux/man-pages/man1/grep.1.html)

### Permissions

181. Что такое права доступа в Linux?

   **Ответ:** Атрибуты метаданных inode файла (дискреционная модель DAC), определяющие, кому из субъектов системы разрешено читать, изменять или исполнять файл.

   **Пример:**

   ```bash
   -rwxr-xr-- 1 developer team 1024 May 10 12:00 script.sh
   ```

   **Типичная ошибка:** Предполагать, что права DAC защищают от администратора `root` (root игнорирует стандартные проверки rwx).

   **Источник:** [man7: inode(7)](https://man7.org/linux/man-pages/man7/inode.7.html)

182. Какие три базовые группы прав существуют?

   **Ответ:** Чтение (`r` — read), запись (`w` — write) и исполнение (`x` — execute).

   **Пример:**

   ```bash
   rwx # Чтение, запись, выполнение
   ```

   **Типичная ошибка:** Считать, что эти три бита имеют одинаковый смысл для обычных файлов и для каталогов.

   **Источник:** [man7: chmod(1)](https://man7.org/linux/man-pages/man1/chmod.1.html)

183. Что означает r?

   **Ответ:** Для файла — разрешение на чтение его содержимого; для директории — разрешение на просмотр списка имен файлов внутри нее (например, командой `ls`).

   **Пример:**

   ```bash
   cat secret.txt # Требует права 'r' на secret.txt
   ```

   **Типичная ошибка:** Забывать, что право `r` на директорию позволяет узнать имена файлов, но без права `x` прочитать их метаданные и содержимое нельзя.

   **Источник:** [man7: path_resolution(7)](https://man7.org/linux/man-pages/man7/path_resolution.7.html)

184. Что означает w?

   **Ответ:** Для файла — право на модификацию и усечение его содержимого; для директории — право создавать, удалять и переименовывать файлы внутри неё.

   **Пример:**

   ```bash
   echo "data" >> file.txt # Требует 'w' на файл
   ```

   **Типичная ошибка:** Считать, что для удаления файла нужно право записи на сам файл (удаление определяется правом записи на родительскую директорию).

   **Источник:** [man7: path_resolution(7)](https://man7.org/linux/man-pages/man7/path_resolution.7.html)

185. Что означает x?

   **Ответ:** Для файла — право передать его ядру на исполнение (`execve`); для директории — право входа (`cd`), сквозного прохода (traverse) и доступа к inode файлов внутри нее.

   **Пример:**

   ```bash
   chmod +x ./build.sh
   ```

   **Типичная ошибка:** Лишение каталога бита `x`, в результате чего никто не может зайти в него и открыть ни один файл внутри, даже зная точное имя.

   **Источник:** [man7: path_resolution(7)](https://man7.org/linux/man-pages/man7/path_resolution.7.html)

186. Для кого задаются права файла?

   **Ответ:** Права задаются для трех классов пользователей: владельца файла (User/Owner), группы владельца (Group) и всех остальных пользователей системы (Others).

   **Пример:**

   ```bash
   # user / group / others
   # [rwx]  [r-x]   [r--]
   ```

   **Типичная ошибка:** Считать, что проверки прав аддитивны: если процесс является владельцем файла, права группы и others для него игнорируются, даже если они шире.

   **Источник:** [man7: inode(7)](https://man7.org/linux/man-pages/man7/inode.7.html)

187. Что такое owner?

   **Ответ:** Конкретный идентификатор пользователя (UID), создавший файл или назначенный его владельцем, имеющий право изменять права доступа к нему через `chmod`.

   **Пример:**

   ```bash
   ls -l # Поле 3 показывает владельца: -rw-r--r-- 1 alex alex 100 ...
   ```

   **Типичная ошибка:** Полагать, что непривилегированный пользователь может отдать владение своим файлом другому пользователю через `chown` (в Linux это запрещено для предотвращения атак с квотами).

   **Источник:** [man7: chown(2)](https://man7.org/linux/man-pages/man2/chown.2.html)

188. Что такое group?

   **Ответ:** Идентификатор группы (GID), ассоциированный с файлом, определяющий права для всех пользователей, входящих в данную группу.

   **Пример:**

   ```bash
   chgrp developers src/
   ```

   **Типичная ошибка:** Забывать, что пользователь должен перелогиниться или выполнить `newgrp`, чтобы изменения в членстве групп вступили в силу.

   **Источник:** [man7: group(5)](https://man7.org/linux/man-pages/man5/group.5.html)

189. Что такое others?

   **Ответ:** Любые учетные записи в системе, чей UID не совпадает с UID владельца файла, и которые не входят в группу файла (весь остальной мир).

   **Пример:**

   ```bash
   chmod o-rwx sensitive.db # Закрыть доступ всем посторонним
   ```

   **Типичная ошибка:** Оставлять биты чтения/записи для others на сокетах и конфигурационных файлах с паролями.

   **Источник:** [man7: chmod(1)](https://man7.org/linux/man-pages/man1/chmod.1.html)

190. Как читать строку rwxr-xr--?

   **Ответ:** Строка разбивается на 3 триады: владелец имеет права `rwx` (чтение, запись, исполнение), группа имеет `r-x` (чтение и исполнение), остальные `r--` (только чтение).

   **Пример:**

   ```bash
   # rwx = 7, r-x = 5, r-- = 4 -> 754 в восьмеричной системе
   ```

   **Типичная ошибка:** Пропуск первой позиции типа файла (в строке `ls -l` всего 10 символов, первый символ — тип).

   **Источник:** [man7: ls(1)](https://man7.org/linux/man-pages/man1/ls.1.html)

191. Что делает chmod?

   **Ответ:** Изменяет биты режима доступа (права) к файлу или директории (change file mode).

   **Пример:**

   ```bash
   chmod 600 id_rsa
   chmod u+x run.sh
   ```

   **Типичная ошибка:** Попытка сменить права на файл, не являясь его владельцем или суперпользователем `root`.

   **Источник:** [man7: chmod(1)](https://man7.org/linux/man-pages/man1/chmod.1.html)

192. Что делает chown?

   **Ответ:** Изменяет пользователя-владельца и/или группу-владельца файла (change file owner).

   **Пример:**

   ```bash
   chown user:team server.cpp
   ```

   **Типичная ошибка:** Использование команды обычным пользователем: смена владельца UID в Linux доступна только процессу с правами `CAP_CHOWN` (суперпользователю).

   **Источник:** [man7: chown(1)](https://man7.org/linux/man-pages/man1/chown.1.html)

193. Чем chown отличается от chmod?

   **Ответ:** `chown` изменяет субъектов владения файлом (UID/GID), а `chmod` изменяет права доступа (чтение, запись, исполнение) для этих субъектов.

   **Пример:**

   ```bash
   chown nobody:nogroup app # Сменил владельца
   chmod 755 app            # Сменил права доступа
   ```

   **Типичная ошибка:** Пытаться дать доступ другому пользователю через `chown`, забирая при этом файл у текущего владельца, вместо настройки прав или ACL.

   **Источник:** [man7: chmod(1)](https://man7.org/linux/man-pages/man1/chmod.1.html)

194. Что делает chgrp?

   **Ответ:** Изменяет только группу-владельца файла (change group ownership).

   **Пример:**

   ```bash
   chgrp staff main.o
   ```

   **Типичная ошибка:** Попытка назначить файлу группу, в которой сам текущий непривилегированный пользователь не состоит.

   **Источник:** [man7: chgrp(1)](https://man7.org/linux/man-pages/man1/chgrp.1.html)

195. Что такое octal notation у chmod?

   **Ответ:** Восьмеричная запись прав доступа, где каждая триада представляется цифрой от 0 до 7, сформированной суммой весов установленных битов ($r=4, w=2, x=1$).

   **Пример:**

   ```bash
   # r-x = 4 + 0 + 1 = 5
   # rw- = 4 + 2 + 0 = 6
   # rwx = 4 + 2 + 1 = 7
   ```

   **Типичная ошибка:** Перепутать веса битов (например, считать, что $w=1$, а $x=2$).

   **Источник:** [man7: chmod(1)](https://man7.org/linux/man-pages/man1/chmod.1.html)

196. Что означает chmod 755?

   **Ответ:** Владелец получает полные права ($7 = rwx$), группа — чтение и запуск ($5 = r-x$), остальные — чтение и запуск ($5 = r-x$).

   **Пример:**

   ```bash
   chmod 755 my_executable
   ```

   **Типичная ошибка:** Установка 755 на конфигурационные файлы, содержащие пароли или приватные ключи.

   **Источник:** [man7: chmod(1)](https://man7.org/linux/man-pages/man1/chmod.1.html)

197. Что означает chmod 644?

   **Ответ:** Стандартные права для обычных файлов: владелец может читать и писать ($6 = rw-$), группа и весь мир — только читать ($4 = r--$).

   **Пример:**

   ```bash
   chmod 644 source.cpp
   ```

   **Типичная ошибка:** Установка 644 на исполняемый скрипт, что лишает его права на запуск напрямую через `./script.sh`.

   **Источник:** [man7: chmod(1)](https://man7.org/linux/man-pages/man1/chmod.1.html)

198. Что означает chmod 700?

   **Ответ:** Полный монопольный доступ только для владельца ($7 = rwx$); группе и всем остальным доступ полностью закрыт ($0 = ---$).

   **Пример:**

   ```bash
   chmod 700 ~/.ssh
   ```

   **Типичная ошибка:** Установка 700 на общие системные библиотеки или заголовки, из-за чего другие процессы не смогут их скомпилировать или загрузить.

   **Источник:** [man7: chmod(1)](https://man7.org/linux/man-pages/man1/chmod.1.html)

199. Почему 755 часто используют для исполняемых файлов?

   **Ответ:** Владелец сохраняет возможность обновлять и компилировать бинарник (`w`), а все остальные пользователи системы могут его гарантированно запускать (`x`) и читать код (`r`), не имея возможности его повредить.

   **Пример:**

   ```bash
   # Права на /usr/bin/gcc обычно выставлены в 755
   ```

   **Типичная ошибка:** Добавление бита записи для группы или others (`chmod 777`), позволяющее посторонним подменить бинарник.

   **Источник:** [man7: chmod(1)](https://man7.org/linux/man-pages/man1/chmod.1.html)

200. Почему 644 часто используют для обычных файлов?

   **Ответ:** Это баланс безопасности и доступности: владелец может свободно редактировать файл, а все процессы имеют возможность безопасно считывать данные без риска несанкционированной перезаписи.

   **Пример:**

   ```bash
   # Исходники ядра или заголовки /usr/include/*.h имеют маску 644
   ```

   **Типичная ошибка:** Выдача обычному файлу с кодом бита `x` без необходимости.

   **Источник:** [man7: chmod(1)](https://man7.org/linux/man-pages/man1/chmod.1.html)

201. Что будет, если убрать x у исполняемого файла?

   **Ответ:** Системный вызов `execve()` вернет ошибку `EACCES`, а командный интерпретатор shell выдаст сообщение `Permission denied`.

   **Пример:**

   ```bash
   chmod -x a.out
   ./a.out # bash: ./a.out: Permission denied
   ```

   **Типичная ошибка:** Считать файл поврежденным, когда дело лишь в сброшенном флаге исполнения в правах.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

202. Можно ли читать файл без x?

   **Ответ:** Да. Бит `x` нужен исключительно для передачи файла ядру на запуск; чтение файла утилитами (`cat`, текстовыми редакторами, компилятором) требует только бита `r`.

   **Пример:**

   ```bash
   # Файл с правами 644 (rw-r--r--) читается через cat без проблем
   ```

   **Типичная ошибка:** Установка бита `x` на текстовые файлы или исходный код `.cpp` ради возможности их «открыть».

   **Источник:** [man7: open(2)](https://man7.org/linux/man-pages/man2/open.2.html)

203. Можно ли зайти в директорию без x?

   **Ответ:** Нет. Бит `x` на директории означает право перехода (search/traverse); без него вызов `chdir()` завершится ошибкой `Permission denied`.

   **Пример:**

   ```bash
   chmod 644 my_dir/
   cd my_dir/ # bash: cd: my_dir/: Permission denied
   ```

   **Типичная ошибка:** Рекурсивный `chmod -R 644` на папку проекта, блокирующий доступ к любым каталогам внутри.

   **Источник:** [man7: path_resolution(7)](https://man7.org/linux/man-pages/man7/path_resolution.7.html)

204. Зачем директории нужен execute bit?

   **Ответ:** Он разрешает ядру транслировать пути через эту директорию, открывать и читать метаданные inode файлов внутри нее.

   **Пример:**

   ```bash
   # Если на папку нет 'x', то даже зная точный путь 'dir/file.txt', прочитать file.txt нельзя
   ```

   **Типичная ошибка:** Думать, что для доступа к известному файлу внутри папки достаточно права `r` на саму папку.

   **Источник:** [man7: path_resolution(7)](https://man7.org/linux/man-pages/man7/path_resolution.7.html)

205. Что означает write bit для директории?

   **Ответ:** Дает право создавать, переименовывать и удалять записи в таблице этой директории (добавлять и удалять имена файлов).

   **Пример:**

   ```bash
   touch dir/new.txt # Требует 'w' и 'x' на каталог dir/
   ```

   **Типичная ошибка:** Думать, что право `w` на директорию позволяет редактировать содержимое уже созданных файлов внутри неё.

   **Источник:** [man7: path_resolution(7)](https://man7.org/linux/man-pages/man7/path_resolution.7.html)

206. Можно ли удалить файл без прав на сам файл?

   **Ответ:** Да. Удаление файла — это модификация родительского каталога (вызов системного вызова `unlink()`), поэтому оно требует права записи `w` и перехода `x` на директорию, а не на сам файл.

   **Пример:**

   ```bash
   chmod 000 file.txt # На файл прав нет вовсе!
   rm file.txt        # Файл успешно удален, если есть 'w' на каталог
   ```

   **Типичная ошибка:** Полагать, что снятие всех прав с файла защитит его от удаления другими пользователями в общей папке.

   **Источник:** [man7: unlink(2)](https://man7.org/linux/man-pages/man2/unlink.2.html)

207. От чего реально зависит удаление файла?

   **Ответ:** От наличия бита записи (`w`) и исполнения (`x`) на родительский каталог, а также от отсутствия ограничений Sticky Bit на каталоге.

   **Пример:**

   ```bash
   # unlink() удаляет имя из директории и уменьшает nlink в inode
   ```

   **Типичная ошибка:** Попытка запретить удаление файла, меняя атрибуты самого файла через `chmod` вместо защиты прав родительского каталога.

   **Источник:** [man7: unlink(2)](https://man7.org/linux/man-pages/man2/unlink.2.html)

208. Что такое umask?

   **Ответ:** Маска режима создания пользовательских файлов процесса: битовая маска, определяющая, какие права должны быть автоматически СБРОШЕНЫ (запрещены) при создании новых файлов и папок.

   **Пример:**

   ```bash
   umask 022 # Запретить запись для group и others
   ```

   **Типичная ошибка:** Путать umask с прямыми правами (umask вычитает биты из базовой маски $666$ для файлов и $777$ для каталогов).

   **Источник:** [man7: umask(2)](https://man7.org/linux/man-pages/man2/umask.2.html)

209. Как umask влияет на права новых файлов?

   **Ответ:** Результирующие права вычисляются побитовой операцией: `mode & ~umask`. При базовых правах на файл `666` и `umask 022` файл получит права `644`.

   **Пример:**

   ```bash
   # Базовый: 0666 (rw-rw-rw-)
   # umask:   0022 (----w--w-)
   # Итог:    0644 (rw-r--r--)
   ```

   **Типичная ошибка:** Попытка создать исполняемый файл через системный вызов `creat()` без явного `chmod` (базовая маска файлов всегда $666$, бит `x` не ставится по умолчанию).

   **Источник:** [man7: umask(2)](https://man7.org/linux/man-pages/man2/umask.2.html)

210. Почему новые файлы обычно не создаются с 777?

   **Ответ:** В целях базовой безопасности системы: программы не должны быть по умолчанию исполняемыми и перезаписываемыми всеми пользователями системы.

   **Пример:**

   ```bash
   # Стандартный umask дистрибутивов 0022 или 0027 предотвращает создание файлов с правами 777
   ```

   **Типичная ошибка:** Установка `umask 000` в производственных сервисах.

   **Источник:** [man7: umask(1)](https://man7.org/linux/man-pages/man1/umask.1.html)

211. Что такое SUID?

   **Ответ:** Специальный бит права (Set User ID, вес 4000), при установке которого исполняемый файл выполняется с правами владельца этого файла, а не с правами запустившего его пользователя.

   **Пример:**

   ```bash
   ls -l /usr/bin/passwd
   # -rwsr-xr-x 1 root root ... passwd
   ```

   **Типичная ошибка:** Установка бита SUID на shell-скрипты (современные ядра Linux игнорируют SUID для интерпретируемых скриптов из соображений безопасности).

   **Источник:** [man7: setuid(2)](https://man7.org/linux/man-pages/man2/setuid.2.html)

212. Что такое SGID?

   **Ответ:** Бит Set Group ID (вес 2000): для бинарника запускает процесс с правами группы файла; для директории — заставляет все новые файлы внутри неё автоматически наследовать группу этой директории, а не основную группу создателя.

   **Пример:**

   ```bash
   chmod g+s shared_folder/ # Идеально для совместных директорий разработки
   ```

   **Типичная ошибка:** Ожидать от SGID на обычном текстовом файле какого-либо эффекта.

   **Источник:** [man7: chmod(1)](https://man7.org/linux/man-pages/man1/chmod.1.html)

213. Что такое sticky bit?

   **Ответ:** Специальный бит защиты директории (вес 1000): запрещает пользователям удалять и переименовывать чужие файлы внутри этой директории, даже если на саму директорию есть права записи `777`.

   **Пример:**

   ```bash
   chmod +t my_shared_dir/
   ```

   **Типичная ошибка:** Полагать, что sticky bit запрещает владельцу файла удалять собственный файл.

   **Источник:** [man7: stat(2)](https://man7.org/linux/man-pages/man2/stat.2.html)

214. Где часто используется sticky bit?

   **Ответ:** В общедоступных временных каталогах операционной системы (`/tmp`, `/var/tmp`), куда любой процесс может писать свои временные данные.

   **Пример:**

   ```bash
   ls -ld /tmp
   # drwxrwxrwt ... /tmp
   ```

   **Типичная ошибка:** Создание общей папки для команды разработчиков с правами `777` без sticky bit (пользователи случайно затирают файлы коллег).

   **Источник:** [man7: chmod(1)](https://man7.org/linux/man-pages/man1/chmod.1.html)

215. Почему /tmp обычно имеет sticky bit?

   **Ответ:** Чтобы изолировать пользователей друг от друга: любой локальный пользователь или сервис может создавать файлы в `/tmp`, но никто посторонний не может удалить или подменить чужой временный файл.

   **Пример:**

   ```bash
   # Предотвращает DoS-атаки через удаление чужих сокетов и lock-файлов в /tmp
   ```

   **Типичная ошибка:** Случайный сброс sticky bit командой `chmod 777 /tmp` вместо `chmod 1777 /tmp`.

   **Источник:** [man7: chmod(1)](https://man7.org/linux/man-pages/man1/chmod.1.html)

216. Как выглядит sticky bit в ls -l?

   **Ответ:** Отображается буквой `t` (или заглавной `T`, если базовый бит `x` для others отсутствует) на последней позиции строки прав.

   **Пример:**

   ```bash
   drwxrwxrwt 15 root root 4096 May 10 12:00 /tmp
   ```

   **Типичная ошибка:** Считать, что заглавная `T` означает «усиленный режим»; она лишь указывает на ошибку настройки — флаг sticky включен, но бит исполнения `x` для others снят.

   **Источник:** [man7: ls(1)](https://man7.org/linux/man-pages/man1/ls.1.html)

217. Что означает s в правах файла?

   **Ответ:** Наличие установленного флага SUID (в первой триаде `rws`) или SGID (во второй триаде `rws`), показывающего выполнение процесса с повышенными привилегиями владельца или группы.

   **Пример:**

   ```bash
   -rwsr-xr-x 1 root root 50000 /usr/bin/sudo
   ```

   **Типичная ошибка:** Заглавная буква `S` сигнализирует о том, что SUID выставлен, но бит исполнения `x` для владельца забыли выставить (`rwS`).

   **Источник:** [man7: ls(1)](https://man7.org/linux/man-pages/man1/ls.1.html)

218. Что произойдет при запуске SUID binary?

   **Ответ:** Ядро создает процесс, у которого эффективный пользователь (`euid`) устанавливается равным владельцу этого бинарного файла, а не тому пользователю, который его запустил.

   **Пример:**

   ```bash
   # Обычный пользователь запускает 'passwd' (owner: root) -> процесс получает euid = 0 (root)
   ```

   **Типичная ошибка:** Запуск непроверенных самописных бинарников с правами SUID root.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

219. Почему SUID может быть опасен?

   **Ответ:** Любая уязвимость переполнения буфера, форматной строки или небезопасный системный вызов (`system()`) внутри SUID-программы позволяет обычному пользователю немедленно получить root-доступ к операционной системе.

   **Пример:**

   ```cpp
   // SUID бинарник, вызвавший system("ls") без полного пути, уязвим к подмене $PATH
   ```

   **Типичная ошибка:** Использование внешних переменных окружения внутри C/C++ приложений, работающих с SUID битом.

   **Источник:** [man7: environ(7)](https://man7.org/linux/man-pages/man7/environ.7.html)

220. Что такое executable permission для directory?

   **Ответ:** Право доступа к содержимому каталога и возможность разрешения путей к файлам внутри него (вход через системный вызов `chdir` и поиск по именам).

   **Пример:**

   ```bash
   chmod 711 public_html/ # Позволяет веб-серверу открыть файл внутри, не позволяя просмотреть весь список
   ```

   **Типичная ошибка:** Выдавать каталогам только права `r` без `x`, блокируя работу любых вложенных программ.

   **Источник:** [man7: path_resolution(7)](https://man7.org/linux/man-pages/man7/path_resolution.7.html)

221. Как проверить владельца файла?

   **Ответ:** С помощью утилиты `ls -l` или более подробного инструмента `stat`.

   **Пример:**

   ```bash
   stat -c "%U %G" main.cpp
   # alex developers
   ```

   **Типичная ошибка:** Ориентироваться на числовые UID вместо имен пользователей при переносе файлов на другую ОС.

   **Источник:** [man7: stat(1)](https://man7.org/linux/man-pages/man1/stat.1.html)

222. Как рекурсивно поменять владельца директории?

   **Ответ:** Использовать `chown` с флагом `-R` (рекурсивно) от имени учетной записи суперпользователя.

   **Пример:**

   ```bash
   sudo chown -R www-data:www-data /var/www/project
   ```

   **Типичная ошибка:** Запуск `chown -R` по символическим ссылкам без флагов контроля обхода ссылок (`-h`), что может случайно изменить владельца системных файлов за пределами каталога.

   **Источник:** [man7: chown(1)](https://man7.org/linux/man-pages/man1/chown.1.html)

223. Что делает chmod -R?

   **Ответ:** Рекурсивно применяет заданные права доступа ко всем файлам и каталогам внутри указанного пути.

   **Пример:**

   ```bash
   chmod -R 755 ./scripts
   ```

   **Типичная ошибка:** Выполнение `chmod -R 777 .`, что ломает модель безопасности проекта и может испортить репозиторий Git.

   **Источник:** [man7: chmod(1)](https://man7.org/linux/man-pages/man1/chmod.1.html)

224. Почему chmod -R может быть опасен?

   **Ответ:** Ошибочное выставление одинаковых восьмеричных прав (например, `644`) на папки лишит их флага `x`, сделав каталог недоступным; а выставление `777` открывает критические файлы для изменения любыми локальными сервисами.

   **Пример:**

   ```bash
   # Безопасное разделение файлов и каталогов:
   find . -type d -exec chmod 755 {} +
   find . -type f -exec chmod 644 {} +
   ```

   **Типичная ошибка:** Использование `chmod -R 644 *`, после чего ни в один подкаталог больше нельзя зайти.

   **Источник:** [man7: chmod(1)](https://man7.org/linux/man-pages/man1/chmod.1.html)

225. Что такое access control на уровне POSIX?

   **Ответ:** Стандартизованный механизм ядра проверки привилегий вызывающего процесса (real/effective UID/GID) против режима доступа (mode/DAC) запрашиваемого файла в файловой системе.

   **Пример:**

   ```c
   access("data.bin", R_OK | W_OK); // Проверка прав через POSIX API
   ```

   **Типичная ошибка:** Возникновение состояния гонки TOCTOU (Time-of-Check to Time-of-Use) при проверке прав через `access()` перед вызовом `open()`.

   **Источник:** [man7: access(2)](https://man7.org/linux/man-pages/man2/access.2.html)

226. Что такое ACL на базовом уровне?

   **Ответ:** Access Control Lists (списки контроля доступа) — расширение стандартной модели прав, позволяющее гранулярно назначать индивидуальные права доступа произвольным конкретным пользователям и группам.

   **Пример:**

   ```bash
   setfacl -m u:ci_runner:rwx build/
   getfacl build/
   ```

   **Типичная ошибка:** Потеря настроек ACL при архивации или копировании стандартными утилитами без соответствующих флагов сохранения атрибутов (нужен флаг `tar --acls` или `cp -a`).

   **Источник:** [man7: acl(5)](https://man7.org/linux/man-pages/man5/acl.5.html)

227. Чем ACL отличается от обычных rwx прав?

   **Ответ:** Обычные права Linux ограничены ровно одной тройкой "один владелец, одна группа, остальные"; ACL позволяет задать десятки независимых правил для разных пользователей на один и тот же файл.

   **Пример:**

   ```bash
   # В ls -l наличие расширенного ACL обозначается символом '+' в конце прав:
   # -rw-r--r--+ 1 user group ...
   ```

   **Типичная ошибка:** Не заметить знак `+` в выводе `ls -l` и удивляться, почему пользователь имеет доступ, которого нет в стандартных битах.

   **Источник:** [man7: getfacl(1)](https://man7.org/linux/man-pages/man1/getfacl.1.html)

228. Как права применяются к symbolic link?

   **Ответ:** Права на саму символическую ссылку в Linux полностью игнорируются (в `ls -l` они всегда `lrwxrwxrwx`); права доступа всегда проверяются ядром исключительно на целевом объекте, на который она указывает.

   **Пример:**

   ```bash
   chmod 777 symlink_file # На самом деле изменит права у целевого файла!
   ```

   **Типичная ошибка:** Попытка закрыть доступ к секретному файлу через изменение прав на симлинк.

   **Источник:** [man7: symlink(7)](https://man7.org/linux/man-pages/man7/symlink.7.html)

229. Проверяются ли права symlink или target?

   **Ответ:** Ядро операционной системы проверяет права доступа строго у целевого файла (`target`); ссылка служит лишь указателем пути.

   **Пример:**

   ```bash
   # Целевой файл target.txt имеет режим 000.
   # Попытка прочитать cat my_symlink вернет: Permission denied
   ```

   **Типичная ошибка:** Думать, что создание симлинка позволяет обойти ограничения прав доступа целевого файла.

   **Источник:** [man7: symlink(7)](https://man7.org/linux/man-pages/man7/symlink.7.html)

230. Почему root может обойти многие ограничения?

   **Ответ:** Процессы с `UID 0` обладают системным набором Linux Capabilities (например, `CAP_DAC_OVERRIDE` и `CAP_DAC_READ_SEARCH`), которые инструктируют ядро полностью пропускать стандартные проверки прав DAC.

   **Пример:**

   ```bash
   # root может прочитать файл с правами 000 (---------)
   ```

   **Типичная ошибка:** Полагать, что даже `root` может выполнить файл, если ни у одной из категорий не выставлен хотя бы один бит `x` (для `execve` бит `x` обязателен даже суперпользователю).

   **Источник:** [man7: capabilities(7)](https://man7.org/linux/man-pages/man7/capabilities.7.html)

231. Может ли процесс открыть файл без прав пользователя?

   **Ответ:** Нет, если только процесс не обладает специальными привилегиями (Capabilities вроде `CAP_DAC_OVERRIDE`) или не запущен от суперпользователя.

   **Пример:**

   ```c
   int fd = open("/etc/shadow", O_RDONLY); // Обычный процесс получит -1 (EACCES)
   ```

   **Типичная ошибка:** Предполагать, что C++ приложение само может запросить у ядра доступ к защищенному файлу в обход прав ОС.

   **Источник:** [man7: open(2)](https://man7.org/linux/man-pages/man2/open.2.html)

232. Как effective UID влияет на доступ?

   **Ответ:** Именно эффективный идентификатор пользователя (`euid`) проверяется ядром при выполнении системных вызовов открытия файлов (`open`), отправки сигналов и создания сокетов.

   **Пример:**

   ```c
   // Процесс имеет ruid=1000, но euid=0: доступ разрешен как для root
   ```

   **Типичная ошибка:** Путать права запустившего терминала и реальный `euid` сервиса.

   **Источник:** [man7: credentials(7)](https://man7.org/linux/man-pages/man7/credentials.7.html)

233. Что такое real UID и effective UID?

   **Ответ:** Real UID (`ruid`) — идентификатор пользователя, фактически запустившего процесс; Effective UID (`euid`) — рабочий идентификатор, который ядро использует для проверки прав доступа ко всем ресурсам.

   **Пример:**

   ```c
   #include <unistd.h>
   uid_t r = getuid();  // Real UID
   uid_t e = geteuid(); // Effective UID
   ```

   **Типичная ошибка:** Полагаться на `getuid()` для проверки прав на открытие файлов вместо `geteuid()`.

   **Источник:** [man7: geteuid(2)](https://man7.org/linux/man-pages/man2/geteuid.2.html)

234. Как права доступа связаны с open()?

   **Ответ:** При вызове `open()` ядро сверяет флаги доступа (`O_RDONLY`, `O_WRONLY`, `O_RDWR`) с битами прав на файл и каталоги пути; если соответствия нет, возвращается дескриптор `-1` и выставляется `errno = EACCES`.

   **Пример:**

   ```c
   int fd = open("log.txt", O_WRONLY);
   if (fd < 0) { perror("open failed"); }
   ```

   **Типичная ошибка:** Не обрабатывать возвращаемое значение `open()`, продолжая передавать невалидный дескриптор в `read()`/`write()`.

   **Источник:** [man7: open(2)](https://man7.org/linux/man-pages/man2/open.2.html)

235. Когда проверяются права — при open() или read()?

   **Ответ:** Права доступа проверяются строго в момент выполнения системного вызова `open()`. После того как файл успешно открыт, последующие операции `read()` и `write()` права заново не проверяют.

   **Пример:**

   ```c
   int fd = open("file.txt", O_RDWR); // Права проверены тут
   // Позже права файла на диске могут измениться на 000,
   // но write(fd, ...) продолжит успешно работать!
   ```

   **Типичная ошибка:** Ожидание, что изменение прав файла на лету немедленно заблокирует работу уже запущенных процессов, читающих этот файл.

   **Источник:** [man7: open(2)](https://man7.org/linux/man-pages/man2/open.2.html)

236. Почему file descriptor сохраняет доступ после открытия файла?

   **Ответ:** Файловый дескриптор указывает на системную структуру открытого файла в ядре (`struct file`), в которой уже зафиксированы разрешенные режимы доступа, полученные при успешном вызове `open()`.

   **Пример:**

   ```c
   // Ядро проверяет только биты структуры открытого файла процесса (f_mode)
   ```

   **Типичная ошибка:** Попытка оборвать чтение лог-файла сторонним процессом с помощью команды `chmod 000 log.txt`.

   **Источник:** [man7: open(2)](https://man7.org/linux/man-pages/man2/open.2.html)

237. Что произойдет, если убрать права после успешного open()?

   **Ответ:** Процесс продолжит беспрепятственно читать и писать в уже открытый файловый дескриптор; новые вызовы `open()` для этого файла другими процессами будут блокироваться.

   **Пример:**

   ```bash
   # Процесс открыл /data/state.bin -> администратор сделал chmod 000 /data/state.bin
   # Работа процесса никак не прервется.
   ```

   **Типичная ошибка:** Уверенность в том, что отзыв прав в файловой системе немедленно защищает данные от уже запущенных процессов.

   **Источник:** [man7: open(2)](https://man7.org/linux/man-pages/man2/open.2.html)

238. Как права Linux влияют на безопасность C/C++ приложений?

   **Ответ:** Они ограничивают область возможной компрометации (blast radius): если сервис взломан, злоумышленник получит доступ только к тем ресурсам ОС, на которые у процесса есть права DAC.

   **Пример:**

   ```bash
   # Запуск демона от непривилегированного пользователя c_app:
   # взломщик не сможет перезаписать системные бинарники в /bin или прочитать /etc/shadow
   ```

   **Типичная ошибка:** Запуск продакшн-демонов от имени суперпользователя `root` «чтобы не было проблем с правами».

   **Источник:** [man7: credentials(7)](https://man7.org/linux/man-pages/man7/credentials.7.html)

239. Почему опасно запускать сервер от root?

   **Ответ:** Любая уязвимость C/C++ (выход за границы буфера, RCE, внедрение шеллкода) дает взломщику неограниченный контроль над всей операционной системой и всеми аппаратными ресурсами.

   **Пример:**

   ```bash
   sudo ./my_http_server # Опасная практика!
   ```

   **Типичная ошибка:** Разрешение веб-серверу слушать порт 80/443 только через запуск из-под root (вместо использования Linux capabilities: `setcap 'cap_net_bind_service=+ep' my_http_server`).

   **Источник:** [man7: capabilities(7)](https://man7.org/linux/man-pages/man7/capabilities.7.html)

240. Какие минимальные права стоит давать приложению?

   **Ответ:** Принцип наименьших привилегий (Principle of Least Privilege): отдельный системный пользователь без оболочки входа (`/sbin/nologin`), доступ только к рабочей папке (read-only для бинарника/библиотек, write только для логов и сокетов).

   **Пример:**

   ```bash
   useradd -r -s /bin/false appuser
   chown -R root:root /opt/app/bin
   chmod 755 /opt/app/bin/server
   ```

   **Типичная ошибка:** Предоставление прав на запись в директорию с исполняемым кодом серверного приложения.

   **Источник:** [man7: useradd(8)](https://man7.org/linux/man-pages/man8/useradd.8.html)

### Linux Basics for C/C++ Developers

241. Как запустить скомпилированную программу из текущей директории?

   **Ответ:** Указать явный относительный путь, добавив префикс `./` перед именем исполняемого файла.

   **Пример:**

   ```bash
   g++ main.cpp -o app
   ./app
   ```

   **Типичная ошибка:** Попытка запуска по голому имени `app` в надежде, что текущая папка по умолчанию опрашивается shell.

   **Источник:** [POSIX: Command Execution](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html#tag_18_09_01_01)

242. Почему ./a.out работает, а a.out — нет?

   **Ответ:** По умолчанию текущий каталог `.` намеренно исключен из переменной `$PATH` ради безопасности; префикс `./` явно указывает shell искать файл в текущей папке, минуя `$PATH`.

   **Пример:**

   ```bash
   ./a.out # Запускает файл прямо из текущей директории
   ```

   **Типичная ошибка:** Добавление `export PATH=.:$PATH`, что позволяет подсунуть поддельные бинарники команд.

   **Источник:** [man7: exec(3)](https://man7.org/linux/man-pages/man3/exec.3.html)

243. Что такое shebang?

   **Ответ:** Первая строка скрипта вида `#!/path/to/interpreter`, сообщающая ядру Linux, какой интерпретатор необходимо вызвать для выполнения данного файла.

   **Пример:**

   ```bash
   #!/usr/bin/env bash
   #!/usr/bin/python3
   ```

   **Типичная ошибка:** Пропуск символа восклицательного знака (`# /bin/bash`), из-за чего строка воспринимается как обычный комментарий.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

244. Почему shell script должен иметь execute bit?

   **Ответ:** При прямом вызове (`./script.sh`) ядро через системный вызов `execve()` проверяет наличие бита `x`; если его нет, ядро отказывается анализировать файл и возвращает ошибку `EACCES`.

   **Пример:**

   ```bash
   chmod +x build.sh
   ./build.sh
   ```

   **Типичная ошибка:** Считать, что shebang `# !/bin/sh` заменяет необходимость выдачи права исполнения `x`.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

245. Как shell понимает, чем открыть файл?

   **Ответ:** Ядро читает первые байты файла (магические числа): если это `\x7fELF`, файл загружается как бинарник; если `#!`, запускается интерпретатор из shebang; в иных случаях возвращается ошибка.

   **Пример:**

   ```bash
   # Заголовок ELF бинарника: 7f 45 4c 46 (.ELF)
   ```

   **Типичная ошибка:** Попытка запустить текстовый файл без shebang как самостоятельную программу.

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

246. Что делает ldd?

   **Ответ:** Выводит список всех разделяемых динамических библиотек (shared libraries), необходимых для запуска указанного исполняемого файла, и пути к ним.

   **Пример:**

   ```bash
   ldd ./app
   # linux-vdso.so.1 => (0x00007fff...)
   # libstdc++.so.6 => /lib/x86_64-linux-gnu/libstdc++.so.6
   ```

   **Типичная ошибка:** Запуск `ldd` на непроверенных сторонних бинарниках: `ldd` может вызывать загрузчик напрямую и исполнить вредоносный код из файла.

   **Источник:** [man7: ldd(1)](https://man7.org/linux/man-pages/man1/ldd.1.html)

247. Как проверить, от каких shared libraries зависит бинарник?

   **Ответ:** Безопасно проверить зависимости можно через `objdump -p <binary> | grep NEEDED`, `readelf -d <binary> | grep NEEDED` или через команду `ldd`.

   **Пример:**

   ```bash
   readelf -d ./app | grep NEEDED
   ```

   **Типичная ошибка:** Полагаться только на `ldd` при кросс-компиляции (нужно анализировать заголовки ELF через `readelf`).

   **Источник:** [man7: readelf(1)](https://man7.org/linux/man-pages/man1/readelf.1.html)

248. Что такое ELF?

   **Ответ:** Executable and Linkable Format — стандартный формат двоичных исполняемых файлов, объектных модулей, разделяемых библиотек и core dump в операционных системах Linux.

   **Пример:**

   ```bash
   readelf -h ./app # Просмотр заголовка ELF файла
   ```

   **Типичная ошибка:** Перенос собранного ELF-бинарника на платформу с другой архитектурой или несовместимой версией ABI `glibc`.

   **Источник:** [man7: elf(5)](https://man7.org/linux/man-pages/man5/elf.5.html)

249. Как посмотреть тип файла бинарника?

   **Ответ:** Использовать утилиту `file` для получения детальной информации об архитектуре CPU, битности и типе компоновки.

   **Пример:**

   ```bash
   file ./app
   # ./app: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked...
   ```

   **Типичная ошибка:** Ориентироваться на расширение `.so` или отсутствие расширения для идентификации назначения файла.

   **Источник:** [man7: file(1)](https://man7.org/linux/man-pages/man1/file.1.html)

250. Что делает nm?

   **Ответ:** Извлекает и выводит таблицу символов (имена функций, глобальных переменных, внешних ссылок) из скомпилированного объектного файла или библиотеки.

   **Пример:**

   ```bash
   nm -C ./app # Флаг -C включает demangling C++ имен
   nm -D libmath.so # Просмотр динамических символов
   ```

   **Типичная ошибка:** Попытка найти приватные символы в стрипнутом (stripped) бинарнике, откуда удалена отладочная таблица символов.

   **Источник:** [man7: nm(1)](https://man7.org/linux/man-pages/man1/nm.1.html)

251. Что делает objdump?

   **Ответ:** Отображает исчерпывающую низкоуровневую информацию об объектных файлах и библиотеках, включая дизассемблирование машинного кода в ассемблерный листинг (`-d`).

   **Пример:**

   ```bash
   objdump -d -M intel ./app # Дизассемблировать машинный код в Intel-синтаксисе
   ```

   **Типичная ошибка:** Дизассемблирование без флага демонглинга (`-C`), из-за чего имена методов C++ остаются зашифрованными строками (mangled names).

   **Источник:** [man7: objdump(1)](https://man7.org/linux/man-pages/man1/objdump.1.html)

252. Что делает strings?

   **Ответ:** Сканирует любой (в том числе бинарный) файл и выводит все последовательности печатных символов длиной от 4 символов и более.

   **Пример:**

   ```bash
   strings ./app | grep "Build version"
   ```

   **Типичная ошибка:** Хранение паролей и токенов в виде строковых литералов в коде C++: `strings` извлекает их из бинарника за доли секунды.

   **Источник:** [man7: strings(1)](https://man7.org/linux/man-pages/man1/strings.1.html)

253. Как узнать, почему программа не запускается?

   **Ответ:** Запустить её в терминале для просмотра exit code и вывода ошибок, проверить зависимости через `ldd`, проверить права доступа через `ls -l` или запустить под трассировкой `strace ./app`.

   **Пример:**

   ```bash
   strace -o trace.log ./app
   ```

   **Типичная ошибка:** Гадание по логам вместо прямого запуска утилиты трассировки системных вызовов `strace`.

   **Источник:** [man7: strace(1)](https://man7.org/linux/man-pages/man1/strace.1.html)

254. Что значит “Permission denied” при запуске бинарника?

   **Ответ:** Означает, что на самом исполняемом файле отсутствует бит исполнения `x`, либо на одну из родительских папок пути нет права `x`, либо файловая система смонтирована с опцией `noexec`.

   **Пример:**

   ```bash
   chmod +x ./my_binary
   ```

   **Типичная ошибка:** Игнорирование проверки опций монтирования диска в `/etc/fstab` (диск смонтирован с опцией `noexec`).

   **Источник:** [man7: execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)

255. Что значит “No such file or directory” для существующего ELF?

   **Ответ:** Означает, что ядро не смогло найти динамический компоновщик/загрузчик (dynamic loader, например `/lib64/ld-linux-x86-64.so.2`), указанный в заголовке `.interp` этого бинарника.

   **Пример:**

   ```bash
   readelf -l ./app | grep interpreter
   # [Requesting program interpreter: /lib64/ld-linux-x86-64.so.2]
   ```

   **Типичная ошибка:** Попытка запустить бинарник, скомпилированный под стандартный Linux glibc, внутри окружения Alpine Linux на базе musl libc.

   **Источник:** [man7: ld.so(8)](https://man7.org/linux/man-pages/man8/ld.so.8.html)

256. Почему отсутствие dynamic loader может давать “No such file or directory”?

   **Ответ:** Системный вызов `execve()` пытается загрузить файл интерпретатора, прописанного в секции `.interp`; если файла загрузчика нет на диске, вызов завершается с ошибкой `ENOENT`, что транслируется оболочкой как "No such file".

   **Пример:**

   ```bash
   # Интерпретатор не найден на диске: ядро сообщает об ошибке отсутствия файла
   ```

   **Типичная ошибка:** Долгий поиск опечатки в имени самого бинарника вместо проверки наличия dynamic linker.

   **Источник:** [man7: ld.so(8)](https://man7.org/linux/man-pages/man8/ld.so.8.html)

257. Что делает strace на базовом уровне?

   **Ответ:** Перехватывает и протоколирует все системные вызовы (syscalls), которые процесс совершает к ядру ОС, а также сигналы, которые процесс получает.

   **Пример:**

   ```bash
   strace ./my_app
   ```

   **Типичная ошибка:** Запуск `strace` в продакшене под высокой нагрузкой без учета того, что механизм `ptrace` замедляет работу приложения в десятки раз.

   **Источник:** [man7: strace(1)](https://man7.org/linux/man-pages/man1/strace.1.html)

258. Как через strace увидеть open/read/write?

   **Ответ:** Запустить `strace` с фильтром по именам системных вызовов через флаг `-e trace=...`.

   **Пример:**

   ```bash
   strace -e trace=openat,read,write ./my_app
   ```

   **Типичная ошибка:** Фильтрация только по устаревшему вызову `open`, в то время как современный Linux использует вызов `openat`.

   **Источник:** [man7: strace(1)](https://man7.org/linux/man-pages/man1/strace.1.html)

259. Что делает ltrace?

   **Ответ:** Перехватывает и выводит вызовы динамических библиотечных функций пространств пользователя (вызовы из libc и разделяемых `.so` библиотек), а не системные вызовы ядра.

   **Пример:**

   ```bash
   ltrace ./my_app # Покажет вызовы malloc, free, strcmp и т.д.
   ```

   **Типичная ошибка:** Попытка отследить с помощью `ltrace` функции, которые были слинкованы статически или заинлайнены компилятором.

   **Источник:** [man7: ltrace(1)](https://man7.org/linux/man-pages/man1/ltrace.1.html)

260. Как найти утечку файловых дескрипторов?

   **Ответ:** Проверить содержимое виртуальной директории `/proc/<pid>/fd/`, использовать утилиту `lsof -p <pid>` или запустить процесс под `strace -e trace=openat,close`.

   **Пример:**

   ```bash
   ls -l /proc/$(pgrep my_app)/fd | wc -l
   ```

   **Типичная ошибка:** Постоянный рост числа дескрипторов из-за забытых вызовов `close()` или `fclose()` при возникновении C++ исключений.

   **Источник:** [man7: proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html)

261. Что такое core dump?

   **Ответ:** Образ (аварийный дамп) оперативной памяти процесса, записываемый ядром на диск в момент аварийного завершения (Segmentation fault, Abort) для посмертной отладки.

   **Пример:**

   ```bash
   gdb ./my_app core.1234
   (gdb) bt # Показывает стек падения
   ```

   **Типичная ошибка:** Удаление файлов `core` без анализа причин аварии через GDB.

   **Источник:** [man7: core(5)](https://man7.org/linux/man-pages/man5/core.5.html)

262. Как включить core dump?

   **Ответ:** Снять ограничение на максимальный размер файла дампа командой `ulimit -c unlimited` и настроить шаблон пути в `/proc/sys/kernel/core_pattern`.

   **Пример:**

   ```bash
   ulimit -c unlimited
   ./crashing_app # Теперь создаст файл core
   ```

   **Типичная ошибка:** Ожидание генерации `core` dump при падении процесса, когда `ulimit -c` выставлен в 0.

   **Источник:** [man7: core(5)](https://man7.org/linux/man-pages/man5/core.5.html)

263. Что такое ulimit?

   **Ответ:** Встроенная команда shell для управления лимитами системных ресурсов, выделяемых процессам (размер стека, лимит дескрипторов, размер файлов, память).

   **Пример:**

   ```bash
   ulimit -n 65535 # Увеличить лимит открытых файловых дескрипторов
   ulimit -s 16384 # Задать размер стека 16 МБ
   ```

   **Типичная ошибка:** Превышение жесткого лимита (hard limit) непривилегированным пользователем.

   **Источник:** [POSIX: ulimit](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/ulimit.html)

264. Что такое exit code процесса?

   **Ответ:** Целочисленное значение (от 0 до 255), передаваемое завершающимся процессом операционной системе через системный вызов `exit_group()` или оператор `return` функции `main()`.

   **Пример:**

   ```cpp
   int main() {
       return 0; // Exit code 0 (успех)
   }
   ```

   **Типичная ошибка:** Возврат отрицательного числа (например, `return -1;`), которое ядро преобразует в значение по модулю 256 (код станет равен `255`).

   **Источник:** [man7: exit(3)](https://man7.org/linux/man-pages/man3/exit.3.html)

265. Как получить код завершения в shell?

   **Ответ:** Прочитать специальную переменную оболочки `$?` сразу после завершения интересующей команды.

   **Пример:**

   ```bash
   ./app
   echo $?
   # 0
   ```

   **Типичная ошибка:** Выполнение промежуточной команды (например, другого `echo`) до проверки `$?`, из-за чего значение `$?` перезаписывается статусом этой новой команды.

   **Источник:** [POSIX: Special Parameters](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html#tag_18_05_02)

266. Почему важно возвращать корректный exit code из C++ программы?

   **Ответ:** Системы CI/CD, сценарии сборки, шедулеры и терминалы опираются на exit code для автоматического определения успешности или ошибки выполнения этапа.

   **Пример:**

   ```cpp
   if (!init_database()) {
       return 1; // Сигнал сборочному скрипту о критической ошибке
   }
   ```

   **Типичная ошибка:** Возврат `0` при аварийных ситуациях, из-за чего сборочный пайплайн считает упавшую задачу завершившейся успешно.

   **Источник:** [POSIX: exit code conventions](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html)

267. Что означает код 0?

   **Ответ:** Общепринятый стандарт успешного завершения программы (Success / `EXIT_SUCCESS`).

   **Пример:**

   ```cpp
   #include <cstdlib>
   return EXIT_SUCCESS;
   ```

   **Типичная ошибка:** Возвращать 1 при успехе по аналогии с boolean `true`.

   **Источник:** [man7: exit(3)](https://man7.org/linux/man-pages/man3/exit.3.html)

268. Что означает ненулевой код выхода?

   **Ответ:** Сигнал об ошибке или нештатном завершении работы приложения (конкретный код от 1 до 255 часто указывает на тип произошедшей ошибки).

   **Пример:**

   ```bash
   # 127 -> Command not found
   # 139 -> Процесс убит по сигналу SIGSEGV (128 + 11)
   ```

   **Типичная ошибка:** Возврат случайного мусора из функции `main` при отсутствии инструкции `return` (хотя в стандарте C++98/11+ отсутствие return в main неявно возвращает 0, в обычных функциях это UB).

   **Источник:** [POSIX: Exit status for commands](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html#tag_18_08_02)

269. Как shell использует exit code в scripting?

   **Ответ:** Для условных операторов `if`, `while` и логических операторов цепочек: `&&` выполняет следующую команду только при коде 0, а `||` — только при ненулевом коде.

   **Пример:**

   ```bash
   make && ./run_tests || echo "Pipeline failed"
   ```

   **Типичная ошибка:** Пропуск проверки exit code в скриптах без флага `set -e`, из-за чего скрипт продолжает исполняться после фатальных сбоев.

   **Источник:** [POSIX: Compound Commands](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html#tag_18_09_04)

270. Что делает gdb на базовом уровне?

   **Ответ:** GNU Debugger позволяет контролировать исполнение C/C++ программы: устанавливать точки останова (breakpoints), инспектировать значения переменных, просматривать стек вызовов и исследовать дампы памяти.

   **Пример:**

   ```bash
   gdb ./app
   (gdb) run
   (gdb) backtrace
   ```

   **Типичная ошибка:** Компиляция без отладочных символов `-g`, из-за чего GDB не может сопоставить машинный код со строками исходных файлов `.cpp`.

   **Источник:** [man7: gdb(1)](https://man7.org/linux/man-pages/man1/gdb.1.html)

271. Как посмотреть map памяти процесса в Linux?

   **Ответ:** Прочитать виртуальный файл `/proc/<PID>/maps` или воспользоваться консольной утилитой `pmap <PID>`.

   **Пример:**

   ```bash
   cat /proc/self/maps
   pmap -x 1234
   ```

   **Типичная ошибка:** Игнорирование проверки защиты страниц памяти (rwxp) при поиске проблем с перезаписью исполняемого кода.

   **Источник:** [man7: proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html)

272. Что можно узнать из /proc/<pid>/maps?

   **Ответ:** Карту виртуального адресного пространства процесса: адреса начала и конца сегментов, права на память (чтение, запись, исполнение, разделяемая/приватная), смещения, а также связанные файлы (стек, куча, бинарники, библиотеки `.so`).

   **Пример:**

   ```bash
   # 00400000-0040b000 r-xp 00000000 ... /usr/bin/cat (сегмент кода)
   # 0060a000-0060b000 rw-p 0000a000 ... /usr/bin/cat (сегмент данных)
   ```

   **Типичная ошибка:** Считать, что весь диапазон виртуальной памяти из `maps` физически выделен в RAM.

   **Источник:** [man7: proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html)

273. Что можно узнать из /proc/<pid>/fd?

   **Ответ:** Список всех файловых дескрипторов, открытых процессом в данный момент; каждая запись является символической ссылкой на реальный файл, сокет, пайп или устройство.

   **Пример:**

   ```bash
   ls -l /proc/1234/fd/
   # lrwx------ 1 user user 64 ... 0 -> /dev/pts/1
   # lrwx------ 1 user user 64 ... 3 -> socket:[23451]
   ```

   **Типичная ошибка:** Пытаться закрыть дескриптор, удаляя симлинк из `/proc/<pid>/fd` командой `rm` (это действие запрещено ядром).

   **Источник:** [man7: proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html)

274. Как посмотреть текущий working directory процесса?

   **Ответ:** Прочитать символическую ссылку `/proc/<PID>/cwd`.

   **Пример:**

   ```bash
   readlink /proc/1234/cwd
   # /home/user/project
   ```

   **Типичная ошибка:** Путать директорию, где лежит исполняемый бинарник (`/proc/<PID>/exe`), с текущим рабочим каталогом процесса (`/proc/<PID>/cwd`).

   **Источник:** [man7: proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html)

275. Что можно узнать из /proc/self?

   **Ответ:** `/proc/self` — это магическая ссылка ядра, которая всегда указывает на директорию `/proc/<PID>` того процесса, который в данный момент обращается к этой ссылке.

   **Пример:**

   ```cpp
   // Узнать путь к собственному исполняемому файлу в C++:
   char path[1024];
   ssize_t len = readlink("/proc/self/exe", path, sizeof(path) - 1);
   ```

   **Типичная ошибка:** Полагать, что `/proc/self` одинаков для всех процессов в системе (он строго изолирован и персонализирован для каждого читающего).

   **Источник:** [man7: proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html)

276. Что такое stdin/stdout/stderr на уровне FD?

   **Ответ:** Стандартные файловые дескрипторы POSIX, автоматически открываемые для процесса при старте: 0 — стандартный ввод (stdin), 1 — стандартный вывод (stdout), 2 — стандартный поток ошибок (stderr).

   **Пример:**

   ```c
   write(1, "Hello\n", 6); // Прямая запись в stdout через syscall
   ```

   **Типичная ошибка:** Закрытие дескриптора 0, после чего первый же открытый процессом файл получает дескриптор 0, ломая ввод-вывод стандартных функций.

   **Источник:** [man7: stdin(3)](https://man7.org/linux/man-pages/man3/stdin.3.html)

277. Почему printf пишет в stdout, а perror — в stderr?

   **Ответ:** Это разделение информационных данных от сообщений о сбоях: поток `stderr` является небуферизованным для немедленного вывода при авариях, а также позволяет перенаправлять чистые данные без загрязнения их логами ошибок.

   **Пример:**

   ```c
   printf("42\n");        // stdout: полезный результат для пайплайна
   perror("file error");  // stderr: диагностическое сообщение
   ```

   **Типичная ошибка:** Вывод ошибок через обычный `printf`, из-за чего сообщения об ошибках попадают во входные данные следующей утилиты конвейера.

   **Источник:** [man7: perror(3)](https://man7.org/linux/man-pages/man3/perror.3.html)

278. Как перенаправить stdout программы в файл?

   **Ответ:** Использовать символ перенаправления `>` или `1>`.

   **Пример:**

   ```bash
   ./my_tool > result.txt
   ```

   **Типичная ошибка:** Ожидание, что ошибки программы попадут в этот же файл (ошибки продолжат выводиться в консоль через `stderr`).

   **Источник:** [POSIX: Redirection](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html#tag_18_07)

279. Как перенаправить stderr отдельно?

   **Ответ:** Использовать оператор перенаправления с указанием дескриптора `2>`.

   **Пример:**

   ```bash
   ./app > output.log 2> errors.log
   ```

   **Типичная ошибка:** Отправка логов в файл с игнорированием `2>`, из-за чего критические сообщения об ошибках теряются.

   **Источник:** [POSIX: Redirection](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html#tag_18_07)

280. Как собрать stdout и stderr вместе?

   **Ответ:** С помощью конструкции `> all.log 2>&1` или оператора `&> all.log`.

   **Пример:**

   ```bash
   ./compiler_wrapper &> build.log
   ```

   **Типичная ошибка:** Неправильный порядок: `2>&1 > all.log` приведет к тому, что stderr уйдет в терминал, а не в файл.

   **Источник:** [POSIX: Redirection](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html#tag_18_07)

281. Что такое background process?

   **Ответ:** Процесс, запущенный в асинхронном фоновом режиме: он не блокирует командную строку терминала и не считывает ввод с клавиатуры.

   **Пример:**

   ```bash
   ./long_task &
   ```

   **Типичная ошибка:** Попытка фонового процесса прочитать данные из `stdin`, что приводит к автоматической остановке процесса ядром через сигнал `SIGTTIN`.

   **Источник:** [POSIX: Asynchronous Lists](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html#tag_18_09_03)

282. Что делает & в shell?

   **Ответ:** Символ `&` в конце команды предписывает командной оболочке запустить указанную задачу асинхронно в фоне и немедленно вернуть управление пользователю.

   **Пример:**

   ```bash
   cmake --build . &
   ```

   **Типичная ошибка:** Путать одинарный `&` (фоновый запуск) с двойным `&&` (условное логическое И).

   **Источник:** [POSIX: Asynchronous Lists](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html#tag_18_09_03)

283. Что такое job control?

   **Ответ:** Механизм shell, позволяющий интерактивно приостанавливать, возобновлять, переводить в фоновый режим и возвращать на передний план отдельные группы процессов (jobs).

   **Пример:**

   ```bash
   jobs # Список текущих заданий сессии
   ```

   **Типичная ошибка:** Путать идентификатор задания в оболочке `%1` с системным идентификатором процесса PID `1234`.

   **Источник:** [POSIX: Job Control](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/V3_chap02.html#tag_18_11)

284. Что делают fg и bg?

   **Ответ:** `fg` (foreground) переводит фоновое или остановленное задание на передний план терминала; `bg` (background) возобновляет выполнение остановленной задачи в фоновом режиме.

   **Пример:**

   ```bash
   # Нажали Ctrl+Z -> процесс остановился (SIGTSTP)
   bg %1 # Продолжить работу в фоне
   fg %1 # Вернуть процесс в интерактивный режим
   ```

   **Типичная ошибка:** Завершение сессии терминала с процессами, работающими через `bg`, без применения `nohup` или `disown` (они завершатся по `SIGHUP`).

   **Источник:** [POSIX: fg](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/fg.html)

285. Что происходит с дочерним процессом после Ctrl+C?

   **Ответ:** Драйвер терминала генерирует и отправляет сигнал `SIGINT` (сигнал прерывания 2) всей группе процессов переднего плана (foreground process group), что по умолчанию завершает процесс.

   **Пример:**

   ```bash
   # Вызов Ctrl+C прерывает бесконечный цикл программы
   ```

   **Типичная ошибка:** Полагать, что `Ctrl+C` убивает процессы, работающие в фоне (`&`): фоновые процессы игнорируют сигналы клавиатуры терминала.

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

286. Как signal SIGINT влияет на программу?

   **Ответ:** По умолчанию приводит к немедленному завершению процесса с exit code `130` (128 + 2); программа на C++ может перехватить сигнал через `sigaction()` для корректной остановки.

   **Пример:**

   ```cpp
   #include <csignal>
   void handler(int) { g_running = false; }
   signal(SIGINT, handler);
   ```

   **Типичная ошибка:** Вызов сложных небезопасных функций (вроде `malloc`, `printf`, `new`) внутри обработчика сигнала (они не являются async-signal-safe).

   **Источник:** [man7: signal-safety(7)](https://man7.org/linux/man-pages/man7/signal-safety.7.html)

287. Что будет, если C++ программа игнорирует SIGTERM?

   **Ответ:** Программа продолжит работать, когда внешняя система (systemd, Docker, Kubernetes) попытается ее штатно остановить; по истечении таймаута среда принудительно убьет ее сигналом `SIGKILL` (kill -9).

   **Пример:**

   ```cpp
   signal(SIGTERM, SIG_IGN); // Игнорирование SIGTERM
   ```

   **Типичная ошибка:** Игнорировать `SIGTERM`, лишая контейнер или сервис возможности штатно сбросить кэши на диск перед выключением машины.

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

288. Чем kill -15 отличается от kill -9 для сервиса?

   **Ответ:** `kill -15` (`SIGTERM`) запрашивает вежливую остановку (приложение закрывает соединения, сокеты, файлы и выходит штатно); `kill -9` (`SIGKILL`) уничтожает процесс немедленно силами ядра без шанса выполнить деструкторы.

   **Пример:**

   ```bash
   # Рекомендуемый алгоритм:
   kill -15 $PID
   # Ждем завершения, и только если завис -> kill -9 $PID
   ```

   **Типичная ошибка:** Использование `kill -9` в скриптах автодеплоя, приводящее к повреждению баз данных и lock-файлов на диске.

   **Источник:** [man7: signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)

289. Как посмотреть переменные окружения процесса?

   **Ответ:** Прочитать виртуальный файл `/proc/<PID>/environ`, разделяя записи по нулевому байту (`\0`).

   **Пример:**

   ```bash
   tr '\0' '\n' < /proc/1234/environ
   ```

   **Типичная ошибка:** Обычный просмотр `cat /proc/1234/environ` сливает все переменные в одну нечитаемую строку, так как разделителем служит `\0`, а не `\n`.

   **Источник:** [man7: proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html)

290. Почему знание Linux Basics критично для системного C/C++ разработчика?

   **Ответ:** Код C/C++ выполняется непосредственно поверх системных интерфейсов ОС; понимание модели процессов, файловых дескрипторов, виртуальной памяти (`/proc`), сигналов и прав доступа необходимо для написания безопасных, отказоустойчивых и производительных приложений.

   **Пример:**

   ```cpp
   // Обработка ошибок POSIX-вызовов (EACCES, ENOENT, EINTR)
   // невозможна без знания механики ядра Linux
   ```

   **Типичная ошибка:** Попытка отлаживать системные сбои (Segfault, Deadlock, FD Leaks) вслепую без применения системных инструментов анализа (`strace`, `gdb`, `procfs`, `ulimit`).

   **Источник:** [man7: intro(2)](https://man7.org/linux/man-pages/man2/intro.2.html)
