# ABI, бинарные файлы и системный интерфейс

Цель — проследить путь от скомпилированной функции до работающего процесса и отделить аппаратный механизм перехода от соглашений компилятора и ОС. Предварительно разберите [ISA](./03_isa_and_assembly.md) и [виртуальную память](./07_virtual_memory.md). Для практики выберите Linux и конкретный ABI, например System V AMD64 или AAPCS64; выводы для одного ABI нельзя автоматически переносить на другой.

## Лёгкий уровень

1. Что определяет ISA, что определяет ABI, а что остаётся частью API библиотеки? Разберите вызов функции из отдельно собранного объектного файла: какие договорённости нужны компилятору, линкеру и процессору?

   **Ответ:** ISA задаёт инструкции, регистры и их архитектурное поведение. ABI задаёт бинарный контракт: размеры и layout типов, передачу аргументов, сохранение регистров, формат объектов и relocations. API описывает доступные функции и смысл операций. Компилятор создаёт вызов по ABI, линкер сопоставляет символы и исправляет адреса, CPU исполняет полученные инструкции; сам процессор не проверяет соответствие прототипов.

   **Пример:** Для `long f(long)` на Linux AMD64 аргумент находится в `RDI`, результат — в `RAX`; смысл `f` остаётся частью API.

   **Типичная ошибка:** Считать, что одинаковая ISA автоматически делает библиотеки бинарно совместимыми.

   **Источник:** [System V AMD64 psABI, §3.2 Function Calling Sequence](https://gitlab.com/x86-psABIs/x86-64-ABI); [ELF gABI, главы 3–8](https://gabi.xinuos.com/).

2. Зачем нужно соглашение о вызовах (calling convention)? На примере функции с целыми аргументами и результатом объясните, кто выбирает регистры, где размещаются остальные аргументы и как вызывающий код узнаёт результат.

   **Ответ:** Calling convention позволяет независимо скомпилированным частям согласовать размещение аргументов, результата, стека и ответственность за регистры. Для System V AMD64 первые шесть целочисленных аргументов идут в `RDI, RSI, RDX, RCX, R8, R9`, следующие — в области аргументов стека; обычный целочисленный результат — в `RAX`. Расположение выбирает ABI, а компилятор реализует его с обеих сторон вызова.

   **Пример:** `long add(long a, long b)` может состоять из `lea (%rdi,%rsi), %rax; ret`.

   **Типичная ошибка:** Переносить этот список регистров на Windows x64, где другое соглашение.

   **Источник:** [System V AMD64 psABI, §3.2 Function Calling Sequence](https://gitlab.com/x86-psABIs/x86-64-ABI).

3. Чем регистры caller-saved отличаются от callee-saved в выбранном ABI? Проследите сохранение значения, которое должно пережить вызов другой функции, и объясните, почему наличие регистра в ISA ещё не задаёт правило его сохранения.

   **Ответ:** Caller-saved разрешено изменить вызываемой функции; вызывающий сохраняет в памяти или переносит в callee-saved только нужные после вызова значения. Callee-saved функция обязана восстановить, если использовала их. В System V AMD64 сохраняются `RBX, RBP, R12–R15` и восстанавливается `RSP`; например, `RAX` и `RDI` сохранения не обещают. ISA определяет действие `call`, но список сохраняемых регистров — соглашение ПО.

   **Пример:** Живое значение в `RAX` перед `call g` можно сохранить в `RBX`; использующая `RBX` внешняя функция сама сохраняет его прежнее значение в прологе.

   **Типичная ошибка:** Сохранять значение в `R10` и ожидать, что любой вызов его оставит.

   **Источник:** [System V AMD64 psABI, §3.2 Function Calling Sequence](https://gitlab.com/x86-psABIs/x86-64-ABI).

4. Какую задачу решает стек вызовов и что может входить в stack frame? Объясните роль адреса возврата, локальных данных и сохранённых регистров; выясните, обязана ли каждая функция создавать отдельный кадр и использовать frame pointer.

   **Ответ:** Стек хранит данные активных вызовов с вложенным временем жизни. Кадр может содержать адрес возврата, spill slots, локальные объекты, сохранённые регистры и исходящие аргументы. На x86 `call` кладёт адрес возврата в стек, `ret` извлекает его. Оптимизированная leaf-функция может обойтись регистрами и red zone System V AMD64, без изменения `RSP`; `RBP` как frame pointer необязателен. Inlining и tail call могут убрать отдельный кадр.

   **Типичная ошибка:** Предполагать цепочку `RBP` у каждой функции и переносить пользовательскую red zone в код ядра.

   **Источник:** [System V AMD64 psABI, §3.2 Function Calling Sequence](https://gitlab.com/x86-psABIs/x86-64-ABI), §3.2.2 The Stack Frame.

5. Чем исходный файл, объектный файл, исполняемый файл и разделяемая библиотека отличаются по назначению? Проследите, какие сведения о символах и адресах ещё могут быть неизвестны на каждом этапе сборки.

   **Ответ:** Исходник задаёт программу на языке. Объектный `ET_REL` содержит машинный код, символы и relocations, но адрес внешнего символа ещё может быть неизвестен. Линкер собирает исполняемый образ (`ET_EXEC` либо PIE типа `ET_DYN`) или библиотеку `ET_DYN`. Для динамического образа часть символов и адресов разрешается загрузчиком при запуске или позднее. Окончательные виртуальные адреса зависят также от размещения и ASLR.

   **Пример:** `cc -c a.c -o a.o` создаёт relocatable object; `cc a.o -o app` добавляет связывание и стартовый код.

   **Типичная ошибка:** Называть любой `ET_DYN` только библиотекой, забывая PIE.

   **Источник:** [ELF gABI, главы 3–8](https://gabi.xinuos.com/), ELF Header и Dynamic Linking.

6. Какие задачи решают sections и segments в ELF? Найдите `.text`, `.data`, `.bss` и записи `PT_LOAD` в небольшом бинарном файле; объясните, какие представления нужны линкеру, а какие загрузчику.

   **Ответ:** Sections описывают логические части для линкера и инструментов: `.text` — код, `.data` — инициализированные изменяемые данные, `.bss` — данные с нулевой начальной инициализацией типа `SHT_NOBITS`. Program headers описывают загрузку: `PT_LOAD` задаёт файловые байты, виртуальный адрес, размер в памяти и права. Один segment может включать несколько sections. Для `.bss` место в памяти требуется, но соответствующие нулевые байты в файле не хранятся.

   **Пример:** В Linux собрать `int x=7; int z[1024]; int main(void){return x+z[0];}`, затем выполнить `readelf -S app` и `readelf -l app`: вторая команда показывает также mapping sections→segments. Адреса зависят от линкера.

   **Типичная ошибка:** Считать section headers обязательными для загрузки ELF: загрузчик использует program headers.

   **Источник:** [ELF gABI, главы 3–8](https://gabi.xinuos.com/), Sections и Program Loading.

7. Чем обычный вызов функции отличается от системного вызова? На примере чтения файла разграничьте библиотечную обёртку, аппаратную инструкцию перехода и работу ядра; выясните, всегда ли вызов библиотечной функции требует входа в ядро.

   **Ответ:** Обычный вызов сохраняет текущий уровень привилегий. Syscall обращается к сервису ядра через архитектурный вход и отдельный syscall ABI. При `read(fd, buf, n)` libc подготавливает номер и аргументы, процессор передаёт управление точке входа ядра, ядро проверяет дескриптор и диапазон пользователя, выполняет чтение и возвращает результат. Обёртка преобразует ошибку в `-1` и `errno`. Не всякая библиотечная функция вызывает ядро: `strlen` обычно работает в user mode, `fread` может обслужиться из буфера.

   **Типичная ошибка:** Считать имя функции libc доказательством выполненного syscall.

   **Источник:** [syscall(2), архитектурные соглашения](https://man7.org/linux/man-pages/man2/syscall.2.html); [read(2)](https://man7.org/linux/man-pages/man2/read.2.html).

8. Что такое переключение контекста потока и чем оно отличается от перехода user → kernel? Опишите случай, когда системный вызов завершился в том же потоке, и случай, когда ожидание ввода-вывода привело к запуску другого потока.

   **Ответ:** Переключение контекста передаёт CPU другому планируемому потоку и сохраняет/восстанавливает нужное состояние: регистры, стек ядра и, при необходимости, адресное пространство и расширенное состояние CPU. Переход в ядро меняет уровень привилегий, но может продолжать тот же поток. Чтение уже готовых данных способно вернуться в него без переключения; блокирующее чтение усыпляет поток, и scheduler запускает другой. При возврате ожидавшего потока его контекст восстанавливается.

   **Типичная ошибка:** Считать каждый syscall одним context switch и оценивать эту стоимость по числу syscalls.

   **Источник:** [Linux scheduler, контекст задачи](https://docs.kernel.org/scheduler/sched-design-CFS.html); [getrusage(2), voluntary/involuntary context switches](https://man7.org/linux/man-pages/man2/getrusage.2.html).

## Средний уровень

9. Исследуйте дизассемблирование функции с восемью целыми аргументами для выбранного ABI. Где оказываются аргументы и результат, как соблюдается выравнивание стека и какие изменения появятся, если добавить аргумент с плавающей точкой?

   **Ответ:** Возьмём System V AMD64 и `long sum8(long a,long b,long c,long d,long e,long f,long g,long h)`. Первые шесть аргументов находятся в целочисленных регистрах; при входе `g` — в `[RSP+8]`, `h` — в `[RSP+16]`, поскольку `[RSP]` содержит return address. Результат возвращается в `RAX`. Непосредственно перед `call` стек выровнен на 16 байт; сразу после обычного входа `(RSP+8) % 16 == 0`. Добавленный `double` использует независимую очередь SSE-регистров, начиная с `XMM0`, а не вытесняет один из шести integer arguments.

   **Пример:** Проверка кросс-компиляцией `clang --target=x86_64-unknown-linux-gnu -O2 -c abi.c` и `llvm-objdump -d abi.o` дала для последних аргументов `addq 0x8(%rsp), %rax` и `addq 0x10(%rsp), %rax`. Leaf-функция не меняла стек. Это результат компиляции, время исполнения не измерялось.

   **Типичная ошибка:** Брать смещения после пролога и выдавать их за смещения при входе.

   **Источник:** [System V AMD64 psABI, §3.2 Function Calling Sequence](https://gitlab.com/x86-psABIs/x86-64-ABI).

10. Как ABI определяет передачу структуры по значению и возврат большой структуры? Сравните две структуры разного состава и проверьте по документации и дизассемблированию, передаются ли они в регистрах, через стек или с использованием скрытого указателя.

    **Ответ:** В System V AMD64 классификация зависит от размера, состава, выравнивания и специальных правил C++. Для простых C-структур `struct Pair { long a,b; }` занимает два INTEGER eightbytes: аргумент — `RDI/RSI`, результат — `RAX/RDX`. У `struct Mixed { double x; long n; }` части SSE и INTEGER: аргумент — `XMM0/RDI`, результат — `XMM0/RAX`. `struct Big { long a,b,c; }` передаётся в памяти на стеке; для возврата вызывающий передаёт скрытый указатель в `RDI`, а функция возвращает его в `RAX`. Эти выводы предполагают обычное выравнивание и свободные регистры аргументов.

    **Пример:** Кросс-компиляция функций, увеличивающих одно поле, с `clang --target=x86_64-unknown-linux-gnu -O2 -fPIC -c abi.c` подтвердила регистры для Pair/Mixed; для Big — чтение `[RSP+8]` и запись через `RDI`.

    **Типичная ошибка:** Определять передачу только по `sizeof`, игнорируя состав полей и доступность регистров.

    **Источник:** [System V AMD64 psABI, §3.2 Function Calling Sequence](https://gitlab.com/x86-psABIs/x86-64-ABI), Parameter Passing / Returning of Values.

11. Почему одинаковое объявление функции в двух исходных файлах ещё не гарантирует бинарную совместимость? Разберите влияние packing, размеров типов, ABI C++, name mangling и настроек компилятора; предложите проверку границы C/C++.

    **Ответ:** Объявления могут совпасть текстом, но типы иметь другой layout: `long` различается между LP64/LLP64, `#pragma pack` меняет offsets, версии C++ ABI и стандартной библиотеки меняют представление объектов и символы. `extern "C"` убирает C++ mangling функции, но не делает `std::string` переносимым бинарным типом. Стабильную границу строят на C ABI, opaque handles, фиксированных целых типах, явной длине и правилах выделения/освобождения памяти; версионируют контракт.

    **Пример:** С обеих сторон проверить `sizeof`, `alignof`, `offsetof` общей C-структуры и экспорт через `nm -D`; загрузочный тест должен проверять версию ABI до передачи данных.

    **Типичная ошибка:** Передавать STL-объект между несовместимыми runtime и освобождать его другим allocator.

    **Источник:** [GCC, -fpack-struct и бинарная совместимость](https://gcc.gnu.org/onlinedocs/gcc/Code-Gen-Options.html); [Itanium C++ ABI](https://itanium-cxx-abi.github.io/cxx-abi/abi.html).

12. Зачем объектному файлу таблица символов и relocations? Скомпилируйте обращение к внешней функции и глобальной переменной, затем с помощью `readelf` и `objdump` проследите, какие адреса уточняет линкер или динамический загрузчик.

    **Ответ:** Symbol table связывает имя с определением/внешней ссылкой, binding, видимостью и размером. Relocation задаёт, где и по какой формуле подставить значение после выбора адресов. Для `extern long ext(long); extern long global; long use(long x){return ext(x)+global;}` PIC-объект ещё не знает окончательные адреса `ext` и `global`. Статический линкер разрешает часть ссылок, а динамические relocations оставляет загрузчику.

    **Пример:** `clang --target=x86_64-unknown-linux-gnu -O2 -fPIC -c abi.c` и `llvm-objdump -dr abi.o` показали `R_X86_64_PLT32 ext-4` у `call` и `R_X86_64_REX_GOTPCRELX global-4` у RIP-relative load. В Linux `readelf -Ws -r abi.o` показывает те же символы и relocations. Конкретные типы меняются с флагами/оптимизацией.

    **Типичная ошибка:** Читать нулевое поле смещения в `.o` как окончательный адрес функции.

    **Источник:** [ELF gABI, главы 3–8](https://gabi.xinuos.com/), Symbol Table и Relocation; [AMD64 psABI, Relocation Types](https://gitlab.com/x86-psABIs/x86-64-ABI).

13. Как position-independent code связан с GOT, PLT и динамической линковкой в выбранном ELF ABI? Сравните вызов внешней функции и доступ к локальному символу; выясните, какие механизмы зависят от ISA, флагов сборки и видимости символа.

    **Ответ:** PIC позволяет разместить код по разным адресам, не переписывая каждую инструкцию. На AMD64 локальные доступные символы часто адресуются относительно `RIP`. GOT хранит адреса, уточняемые при связывании/загрузке; PLT обеспечивает переход к внешней функции и при выбранной конфигурации lazy binding. Вызов может идти через PLT, через GOT при `-fno-plt` или напрямую после локального разрешения. Hidden visibility, interposition, PIE и linker relaxation меняют путь; PIC не означает обязательную PLT для всех вызовов.

    **Пример:** Сравнить `objdump -dr lib.o` для `-fPIC` и `-fPIC -fno-plt`, затем уже связанный `.so`, где линкер мог упростить обращения.

    **Типичная ошибка:** Приписывать каждому вызову внешней функции динамическое разрешение заново.

    **Источник:** [AMD64 psABI, GOT/PLT и Position-Independent Function Prologue](https://gitlab.com/x86-psABIs/x86-64-ABI); [ld.so(8), LD_BIND_NOW](https://man7.org/linux/man-pages/man8/ld.so.8.html).

14. Как TLS позволяет разным потокам иметь разные значения одной thread-local переменной? Сопоставьте адреса переменной в двух потоках и исследуйте машинный код обращения; отделите модель хранения от конкретного регистра и модели TLS выбранной платформы.

    **Ответ:** TLS создаёт отдельный экземпляр переменной для каждого потока, а runtime выделяет/инициализирует его и поддерживает доступ. На Linux AMD64 thread pointer связан с `FS.base`; конкретная последовательность зависит от TLS model: local-exec/initial-exec используют смещения, general-dynamic может вызвать `__tls_get_addr`, возможны TLSDESC и relaxation. Модель хранения не требует одного и того же регистра на всех ISA.

    **Пример:** Для `__thread long tls; long tls_get(void){return tls;}` кросс-компиляция AMD64 ELF с `-O2 -fPIC` дала `R_X86_64_TLSGD tls` и вызов `__tls_get_addr`. В Linux два потока публикуют свои `&tls` в общий массив через барьер/handshake; адреса сравнивают, пока оба потока ещё живы и TLS-объекты существуют. Адреса экземпляров различаются. Сами адреса здесь не измерялись.

    **Типичная ошибка:** Называть TLS обычной общей глобальной переменной, защищённой lock.

    **Источник:** [Ulrich Drepper, ELF Handling For Thread-Local Storage, x86-64](https://www.akkadia.org/drepper/tls.pdf).

15. Как восстанавливается цепочка вызовов, если компилятор опустил frame pointer? Разберите роль unwind metadata, inlining и tail calls; объясните, почему результат отладчика может отличаться от простого обхода указателей по стеку.

    **Ответ:** Unwinder применяет правила CFI из `.eh_frame`/`.debug_frame`: как вычислить CFA и где найти прежние регистры и адрес возврата в каждой точке кода. Frame pointer для этого не обязателен, но metadata должны соответствовать прологу/эпилогу. Отладочная информация позволяет показать inline-функции как логические кадры; tail call может убрать физический кадр. Ошибочные metadata, повреждённый стек или stripped debug info ограничивают восстановление.

    **Пример:** Сравнить `readelf --debug-dump=frames app` и backtrace сборок с `-fomit-frame-pointer` и `-fno-omit-frame-pointer`, сохранив unwind tables и debug info.

    **Типичная ошибка:** Считать отсутствие цепочки `RBP` доказательством невозможности stack unwind.

    **Источник:** [GNU as, CFI directives](https://sourceware.org/binutils/docs/as/CFI-directives.html); [DWARF 5, §6.4 Call Frame Information](https://dwarfstd.org/dwarf5std.html).

16. Проследите путь от `execve` до `main` для динамически связанного ELF на Linux. Кто создаёт отображения памяти и начальный стек, как участвуют ELF interpreter и runtime и почему точка входа программы обычно отличается от `main`?

    **Ответ:** `execve` заменяет образ текущего процесса. Ядро проверяет ELF, создаёт отображения `PT_LOAD` и стек с `argc`, `argv`, environment и auxiliary vector; для динамического ELF отображает interpreter из `PT_INTERP` и начинает с его entry point. Динамический загрузчик находит зависимости, выполняет relocations и подготовку TLS, затем передаёт управление entry point приложения. Стартовый runtime (`_start`, далее libc startup) организует инициализацию, вызов `main` и завершение. `main` — языковая точка входа, обычно не адрес из `e_entry`.

    **Типичная ошибка:** Рисовать `execve → main` без загрузчика и runtime либо считать `execve` созданием нового PID.

    **Источник:** [execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html); [ELF gABI, Program Loading / Dynamic Linking](https://gabi.xinuos.com/); [glibc, x86-64 start.S](https://github.com/bminor/glibc/blob/master/sysdeps/x86_64/start.S).

## Сложный уровень

17. Нужно вызвать функцию из вручную написанного ассемблерного кода. Как составить проверяемый контракт для аргументов, результата, выравнивания стека, сохраняемых регистров и unwind; какие тестовые функции выявят нарушение каждого правила выбранного ABI?

    **Ответ:** Для System V AMD64 письменно зафиксировать C-прототип и classification всех аргументов/результата, состояние стека перед `call`, clobbers, callee-saved и unwind rules. В ассемблерном прологе сохранить используемые `RBX/RBP/R12–R15`, выровнять стек, описать изменения CFI и симметрично восстановить всё на выходе. Проверять конечный объект: inline asm имеет ещё и отдельный контракт clobbers с компилятором.

    **Пример:** Функция с 8 integer arguments проверяет регистры и стек; mixed struct — SSE/INTEGER; большой return — скрытый указатель. Обёртка с известными значениями callee-saved выявляет порчу, функция с выровненным stack spill — alignment, `backtrace` и C++ throw через кадр — CFI. Тестировать разные уровни оптимизации и все пути выхода.

    **Типичная ошибка:** Проверить только сумму двух чисел, когда ошибка проявляется лишь на stack arguments или unwinding.

    **Источник:** [System V AMD64 psABI, §3.2 Function Calling Sequence](https://gitlab.com/x86-psABIs/x86-64-ABI); [GNU as, CFI directives](https://sourceware.org/binutils/docs/as/CFI-directives.html).

18. Почему C++-исключение через границу библиотек требует согласованных ABI и runtime? Разберите путь раскрутки стека через C++ и ассемблерный кадр; какие ограничения нужны, если модуль собран другим компилятором или должен предоставлять стабильный C API?

    **Ответ:** Исключение требует согласованных представления exception object, RTTI, personality routines, unwind tables и runtime. Поиск обработчика и cleanup проходят через каждый кадр: C++-кадры описывают destructors, ассемблерный кадр обязан дать корректную CFI; при собственных cleanup нужны также language-specific metadata. Один mangling не гарантирует совместимость двух toolchain/runtime. Для стабильного C API исключения перехватывают внутри границы и возвращают error code; освобождение объектов выполняет их владелец.

    **Пример:** Проверять `throw` через ассемблерную обёртку с RAII-объектами по обе стороны: должны исполниться все предусмотренные destructors и сохраниться регистры. При несовместимой среде такой переход исключения запрещают контрактом.

    **Типичная ошибка:** Разрешать исключению выйти в чужой C ABI, полагаясь на успешную загрузку `.so`.

    **Источник:** [Itanium C++ ABI, Exception Handling, Level I/II](https://itanium-cxx-abi.github.io/cxx-abi/abi-eh.html).

19. Сравните обычный вызов функции, Linux syscall и доступ к поддерживаемой функции через vDSO. Какие переходы и проверки происходят в каждом случае, как проверить фактический путь и почему нельзя назначить им универсальную стоимость в тактах?

    **Ответ:** Обычный вызов меняет control flow в user mode. Syscall использует привилегированную точку входа, syscall ABI, проверки ядра и путь возврата. Поддерживаемая vDSO-функция вызывается как пользовательская ELF-функция и может прочитать публикуемые ядром данные без входа в него; для неподдержанного clock id/условий возможен fallback. Стоимость зависит от CPU, mitigations, cache state и реально выполненного сервиса.

    **Пример:** Сравнить libc `clock_gettime` с принудительным `syscall(SYS_clock_gettime, ...)`, посмотреть `[vdso]` в maps и `strace`; vDSO-путь в syscall trace отсутствует. Измерять серии, вычитая оценённый overhead таймера; трассировку выполнять отдельно от timing.

    **Типичная ошибка:** Считать отсутствие записи `strace` доказательством, что библиотечная функция вообще не исполнялась.

    **Источник:** [vdso(7)](https://man7.org/linux/man-pages/man7/vdso.7.html); [syscall(2)](https://man7.org/linux/man-pages/man2/syscall.2.html).

20. При профилировании частые системные вызовы оказались дорогими. Как отделить стоимость перехода привилегий от копирования, проверки аргументов, ожидания и переключений контекста; каким экспериментом проверить пользу batching, сохранив семантику обработки ошибок?

    **Ответ:** Сначала локализовать время: wall/CPU time, syscall counts, off-CPU intervals, context switches, объём копирования. Минимальный syscall оценивает вход и dispatch только приближённо: он имеет другое тело и cache behavior. Сравнить одинаковый сервис с нулевым/разным payload и готовыми/блокирующими данными, затем профиль ядра покажет проверки, copying и ожидание. Batching проверять на одинаковом числе логических операций, порядке, latency и обработке частичного результата.

    **Пример:** Для отправки сообщений сравнить одиночные вызовы с `sendmmsg`, контролируя partial send, `EINTR`, `EAGAIN`, фактическое число сообщений и размер batch; измерить throughput, CPU на сообщение и p99.

    **Типичная ошибка:** Приписать всю длительность блокирующего `read` аппаратному переходу привилегий.

    **Источник:** [sendmmsg(2)](https://man7.org/linux/man-pages/man2/sendmmsg.2.html); [perf sched](https://man7.org/linux/man-pages/man1/perf-sched.1.html).

21. Как Linux-доставка сигнала взаимодействует с сохранённым контекстом, пользовательским стеком и возвратом из обработчика? Разберите, что нужно восстановить при `sigreturn`, и почему обработчик не является обычным вызовом, который программа сделала сама.

    **Ответ:** При доставке ядро сохраняет user context в signal frame на обычном или alternate stack: регистры, адрес продолжения, signal mask и архитектурное расширенное состояние. Оно подготавливает вход в handler и путь через trampoline/restorer. `rt_sigreturn` восстанавливает контекст и mask из кадра, после чего исполнение продолжается по правилам прерванной операции и `SA_RESTART`. Сигнал может появиться в произвольной допустимой точке, без исходного `call`, поэтому handler ограничен async-signal-safe действиями.

    **Типичная ошибка:** Вызывать `printf` или брать произвольный mutex в обработчике: прерванный поток мог уже владеть внутренней блокировкой.

    **Источник:** [signal(7), Execution of signal handlers](https://man7.org/linux/man-pages/man7/signal.7.html); [sigreturn(2)](https://man7.org/linux/man-pages/man2/sigreturn.2.html); [signal-safety(7)](https://man7.org/linux/man-pages/man7/signal-safety.7.html).

22. Плагин успешно загружается, но вызов функции иногда повреждает стек. Как проверить ABI, прототип, varargs, выравнивание, владение переданными объектами и версии библиотек; какие наблюдения позволят отличить ошибку контракта от аппаратной неисправности?

    **Ответ:** Зафиксировать точные бинарники/версии и минимальный воспроизводитель. Сверить typedef функции с экспортируемым прототипом, calling convention, aggregate return, varargs и packing; на AMD64 у variadic call важен также `AL` с верхней границей числа использованных vector registers (0–8). Проверить stack alignment, callee-saved, symbol version и фактические библиотеки загрузчика. Затем lifetime, размеры буферов и allocator ownership, ASan/UBSan и disassembly границы вызова.

    **Пример:** Заполнение стека guard bytes и проверка регистров до/после вызова помогают локализовать порчу; воспроизводимость на одном конкретном прототипе указывает на контракт. Аппаратную гипотезу подкрепляют независимые ошибки, RAS/MCE и воспроизводимость вне плагина, а не один crash.

    **Типичная ошибка:** Привести `void*` из `dlsym` к произвольной сигнатуре и принять успешный `dlopen` за проверку ABI.

    **Источник:** [dlsym(3)](https://man7.org/linux/man-pages/man3/dlsym.3.html); [AMD64 psABI, Variable Argument Lists](https://gitlab.com/x86-psABIs/x86-64-ABI).

23. Разработайте эксперимент для сравнения static linking, dynamic linking и первого/повторного вызова внешней функции. Как разделить время запуска и steady state, учесть lazy binding, page faults и кеши и проверить, какой путь вызова фактически сгенерирован?

    **Ответ:** Собрать один исходник с сопоставимыми оптимизациями и отключить LTO/inlining тестовой внешней функции. Отдельно измерить запуск многих процессов и длинный цикл внутри процесса. Для dynamic сравнить lazy binding и `LD_BIND_NOW=1`/`-Wl,-z,now`, отдельно первый и последующие вызовы. Собирать faults, размер бинарника, время loader и распределения длительностей; cold page cache выделять в отдельный явно описанный опыт. Static может изменить объём/раскладку кода, а не только linking cost.

    **Пример:** `readelf -d app` проверяет `NEEDED`/`BIND_NOW`, disassembly — PLT/GOT/direct call; `LD_DEBUG=bindings` объясняет разрешение, но не используется в timing run. Результаты не подменять универсальным утверждением «static быстрее».

    **Типичная ошибка:** Смешать время загрузки процесса с steady-state вызовом и назвать разницу ценой PLT.

    **Источник:** [ld.so(8), LD_BIND_NOW / LD_DEBUG](https://man7.org/linux/man-pages/man8/ld.so.8.html); [GNU ld, -z now](https://sourceware.org/binutils/docs/ld/Options.html).

24. Нарисуйте сквозной путь `приложение → библиотека → syscall → драйвер → устройство → завершение → приложение`. Какие ABI, адресные пространства и владельцы ресурсов меняются на границах; где возможны ожидание и переключение потока и как связать схему с наблюдениями `strace` и профиля?

    **Ответ:** Для чтения с устройства схема: `user code → libc read → syscall ABI → VFS/драйвер → DMA queue/device → completion IRQ или polling → wakeup → возврат read → user code`. API библиотеки задаёт смысл вызова, function ABI — аргументы libc, syscall ABI — границу ядра, device protocol — descriptors и MMIO. User VA проверяется ядром; DMA использует mapping/IOVA, а не произвольный user pointer. Файл/дескриптор, request и buffer имеют разных владельцев и сроки жизни; до завершения DMA буфер нельзя освобождать.

    **Пример:** Поток может заснуть в ожидании, другой поток будет запущен, IRQ обработает иное ядро. `strace -T` показывает syscall и elapsed time, sampling/off-CPU profile — CPU work и ожидание, tracepoints — request/completion. Кешированный `read` способен завершиться без устройства, поэтому путь проверяют по наблюдениям.

    **Типичная ошибка:** Считать IRQ возвратом непосредственно в исходное приложение или принимать kernel VA за DMA address.

    **Источник:** [Linux DMA API HOWTO](https://docs.kernel.org/core-api/dma-api-howto.html); [read(2)](https://man7.org/linux/man-pages/man2/read.2.html).
