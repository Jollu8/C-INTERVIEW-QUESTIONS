# Когерентность кэшей, порядок памяти и атомарные операции

Цель — различать согласование копий одной строки, порядок наблюдения разных обращений и гарантии языка программирования. MESI ниже служит учебной моделью протокола, а задачи о C++ предполагают C++20, обычную оперативную память и отсутствие неуказанных способов синхронизации.

Предпосылки: [микроархитектура CPU](04_cpu_microarchitecture.md), [иерархия кэшей](05_cache_hierarchy.md), [виртуальная память](07_virtual_memory.md). Основы языка можно повторить в [многопоточности C++](../03_concurrency/01_base.md).

## Лёгкий уровень

1. Чем когерентность кэшей отличается от модели согласованности памяти? Сформулируйте отдельные вопросы о порядке записей в один адрес и о порядке наблюдения записей в два разных адреса, которые выполняет другой поток.

   **Ответ:** Когерентность описывает согласование копий одного адреса/блока: как записи к нему упорядочиваются и когда новая запись исключает использование старой копии. Модель памяти задаёт допустимый порядок наблюдения нескольких обращений, в том числе к разным адресам. Отдельные вопросы: «могут ли ядра видеть записи `x=1`, `x=2` в несовместимом порядке?» и «гарантирует ли наблюдение `flag=1`, что уже виден предшествующий `data=42`?». Второе не следует из одного лишь согласования каждой строки. Модель C++ дополнительно ограничивает преобразования компилятора и определяет data race.

   **Типичная ошибка:** Из когерентности `data` и `flag` выводить корректность их публикации без синхронизации.

   **Источник:** [Intel SDM, т. 3A, §9.2 «Memory Ordering» и гл. «Memory Cache Control»](https://cdrdv2-public.intel.com/671190/253668-sdm-vol-3a.pdf); [C++20 N4861, [intro.races]](https://timsong-cpp.github.io/cppwp/n4861/intro.races).

2. Почему протокол когерентности обычно работает с блоками данных, а исходная программа обращается к отдельным объектам? Для двух разных полей структуры в одной учебной строке 64 байта объясните, какие аппаратные взаимодействия возможны даже без обращения потоков к одному полю.

   **Ответ:** Аппаратная часть отслеживает теги и права на блок целиком: побайтовый протокол потребовал бы гораздо больше метаданных и сообщений. Поэтому запись одного поля строки может отозвать копию, в которой другое ядро использует соседнее поле. Если два потока изменяют разные поля, они способны постоянно передавать владение строкой друг другу, даже без логически общих данных. При чтениях обоими ядрами строка обычно разделяется без такой передачи.

   **Пример:** При полях по смещениям 0 и 8 в одной строке 64 байта записи разных потоков могут вызвать invalidation одной и той же строки. В C++ разные обычные скалярные поля обычно являются разными memory locations; аппаратный false sharing сам по себе не означает data race.

   **Источник:** [Linux, «False Sharing», «What is False Sharing»](https://docs.kernel.org/kernel-hacking/false-sharing.html).

3. Где может находиться самая новая версия данных при использовании write-back кэшей? Разберите ситуацию, когда одно ядро изменило строку, а другое хочет её прочитать, и объясните, почему ответ «нужно просто прочитать DRAM» требует дополнительных условий.

   **Ответ:** Самая новая версия может находиться в грязной строке частного кэша владельца, а DRAM и некоторые нижние уровни содержать старые данные. Когда другое ядро запрашивает чтение, протокол находит владельца и обеспечивает передачу актуальной версии, непосредственно либо через промежуточный уровень. В учебном MESI владелец `M` при разделяемом чтении перестаёт быть единственным владельцем; грязные данные должны быть согласованы с нижним уровнем согласно протоколу. Читать DRAM без участия когерентности допустимо только при гарантии, что она содержит актуальную версию, например после требуемой обратной записи.

   **Типичная ошибка:** Считать DRAM неизменно главным источником самого нового значения при write-back.

   **Источник:** [gem5, «MESI Two Level», «Protocol Overview» и состояния M/E/S/I](https://www.gem5.org/documentation/general_docs/ruby/MESI_Two_Level/).

4. Какие состояния выделяет учебный протокол MESI и какие сведения о строке они выражают? Сопоставьте допустимость чтения, необходимость получения права на запись и наличие актуальной копии в памяти, отдельно указав, почему эта схема не описывает все реальные протоколы.

   **Ответ:** `M` (Modified) — единственная действительная копия, изменена относительно нижнего уровня; чтение и запись разрешены. `E` (Exclusive) — единственная чистая копия, запись может локально перевести её в M. `S` (Shared) — чистая разделяемая копия; читать можно, для записи требуется получить исключительное право и убрать чужие копии. `I` (Invalid) — действительной копии нет, нужен запрос. В простой модели память актуальна для E/S, для M может отставать. Реальные протоколы добавляют состояния вроде Owned/Forward, переходные состояния, directory и особенности многоуровневой иерархии.

   **Типичная ошибка:** Считать E грязным состоянием либо ожидать, что четырёх стабильных состояний достаточно для описания сообщений в полёте.

   **Источник:** [gem5, «MESI Two Level», описание стабильных состояний](https://www.gem5.org/documentation/general_docs/ruby/MESI_Two_Level/).

5. Что должно произойти, если два ядра читают одну строку, а затем одно начинает её изменять? Проследите запрос права на запись и судьбу чужой копии в учебной invalidation-модели, не предполагая мгновенную доставку сообщений между ядрами.

   **Ответ:** После чтений у обоих ядер могут быть копии S. Пишущее ядро запрашивает исключительное владение, а протокол отправляет invalidation держателям других копий. Получатель делает свою копию недействительной и подтверждает это; запись должна войти в согласованный порядок после получения необходимых разрешений. До завершения процедуры ядро может находиться в переходном состоянии, а сама запись — ожидать в store buffer. Чужое ядро после отзыва копии должно заново запросить строку при следующем обращении.

   **Типичная ошибка:** Представлять invalidation как мгновенное «обновление всех кэшей» или считать, что уже выданная команда записи немедленно видна всем ядрам.

   **Источник:** [gem5, MESI L1 controller, состояния SM/IM и обработка invalidation](https://gem5.googlesource.com/public/gem5/+/3f835d88a337c74869393b76ef3c398c324754cc/src/mem/protocol/MESI_Two_Level-L1cache.sm).

6. Чем false sharing отличается от одновременного изменения одного общего счётчика? Сравните два потока, увеличивающих разные атомарные счётчики в одной строке, с двумя потоками, увеличивающими один атомарный счётчик, и сформулируйте разные причины потери производительности.

   **Ответ:** При разных атомарных счётчиках в одной строке данные логически независимы, но протокол передаёт право записи на общий блок: это false sharing. Разнесение по строкам может устранить такую конкуренцию. При одном общем счётчике есть настоящая логическая конкуренция: все увеличения должны атомарно войти в один modification order; выравнивание не устраняет необходимость сериализации. Здесь помогают уменьшение числа общих обновлений, локальные счётчики с последующим объединением или иная структура алгоритма.

   **Типичная ошибка:** Называть любой медленный общий атомик false sharing и пытаться исправить его одним padding.

   **Источник:** [Linux, «False Sharing», «What is False Sharing» и «How to avoid False Sharing»](https://docs.kernel.org/kernel-hacking/false-sharing.html).

7. Почему аппаратная когерентность не делает корректной программу C++, где один поток пишет обычный `int`, а другой читает его без синхронизации? Назовите условия data race на уровне языка и объясните, почему эксперимент на одном CPU не доказывает допустимость такой программы.

   **Ответ:** Data race возникает при потенциально конкурентных конфликтующих действиях разных потоков, когда хотя бы одно неатомарно и ни одно не happens-before другого. Запись обычного `int` и чтение этого же объекта без синхронизации удовлетворяют этим условиям; поведение программы неопределено. Когерентность CPU не ограничивает все оптимизации компилятора: загрузка может быть вынесена из цикла, а код преобразован исходя из отсутствия гонок. Наблюдение ожидаемого значения в миллионе запусков не создаёт недостающей гарантии языка.

   **Типичная ошибка:** «На моём x86 выровненный int читается одним MOV, значит программа C++ корректна». Одной аппаратной неделимости недостаточно.

   **Источник:** [C++20 N4861, [intro.races], конфликтующие действия, happens-before и data race](https://timsong-cpp.github.io/cppwp/n4861/intro.races).

8. Чем неделимость отдельной операции отличается от порядка её выполнения относительно других операций? Сравните атомарную загрузку, атомарное увеличение и пару отдельных атомарных операций, затем укажите, какие сведения нужны для проверки lock-free реализации выбранного типа.

   **Ответ:** Atomic load неделимо получает значение, atomic RMW вроде `fetch_add` неделимо связывает чтение и изменение. Но пара `load(); store(old+1);` остаётся двумя атомарными операциями: другой поток способен вклиниться, и обновление потеряется. Порядок относительно других объектов зависит от `memory_order`; даже relaxed RMW остаётся неделимой. Lock-free означает отсутствие блокировки в реализации выбранной операции, а не отсутствие конкуренции. Проверяют тип, размер, выравнивание, ABI, ISA, `std::atomic<T>::is_always_lock_free` и при необходимости `is_lock_free()` у конкретного объекта.

   **Типичная ошибка:** Считать составной алгоритм атомарным или wait-free только потому, что каждая отдельная загрузка атомарна.

   **Источник:** [C++20 N4861, [atomics.types.operations]](https://timsong-cpp.github.io/cppwp/n4861/atomics.types.operations); [atomics.lockfree](https://timsong-cpp.github.io/cppwp/n4861/atomics.lockfree).

## Средний уровень

9. Как изменяются состояния строки при последовательности действий разных ядер? В учебной write-back/write-allocate MESI-модели с изначально пустыми кэшами проследите `A читает → B читает → A пишет → B читает`, указав состояния, запросы и необходимость передачи актуальных данных, но не навязывая конкретный маршрут по межсоединению.

   **Ответ:** В принятой модели состояния `(A,B)` таковы: начально `(I,I)`; A читает — запрос разделяемого чтения, при отсутствии иных копий получает `(E,I)`; B читает — A теряет исключительность, получается `(S,S)`. A пишет — запрашивает upgrade/исключительное владение, B инвалидируется, после необходимых подтверждений `(M,I)`. B снова читает — необходима актуальная версия от M-владельца с требуемым согласованием нижнего уровня, после завершения `(S,S)`. Переходы проходят через временные состояния. Путь данных может идти через владельца, домашний агент или общий кэш; MESI сам по себе не фиксирует физический маршрут.

   **Типичная ошибка:** На последнем шаге выдавать B старую строку из DRAM, игнорируя M у A.

   **Источник:** [gem5, «MESI Two Level», «Protocol Overview»](https://www.gem5.org/documentation/general_docs/ruby/MESI_Two_Level/).

10. Чем snooping-подход отличается от протокола с directory? Для системы с 4, а затем с 64 ядрами сравните, кто определяет держателей строки и кому отправляются запросы, учитывая стоимость широковещательных сообщений, хранения метаданных и подтверждений invalidation.

    **Ответ:** В snooping-схеме запрос видят участвующие кэши и сами проверяют, держат ли строку; общая среда или сеть обеспечивает необходимую координацию. Directory хранит сведения о владельце и возможных держателях и направляет запросы нужным участникам. Для четырёх ядер широковещательный обмен может быть относительно прост, для 64 возрастает цена доставки и проверки каждого запроса всеми. Directory уменьшает ненужные snoops, но требует места под метаданные, доступа к домашнему агенту и учёта подтверждений invalidation. Точные bit vectors на 64 держателя дороже, сжатые представления иногда дают ложных кандидатов и дополнительные запросы.

    **Типичная ошибка:** Считать directory бесплатным или приравнивать snooping к единственно возможной общей физической шине.

    **Источник:** [gem5, «Cache Coherence Protocols», snooping/directory](https://www.gem5.org/documentation/general_docs/ruby/cache-coherence-protocols/); [«MESI Two Level», directory co-located with L2](https://www.gem5.org/documentation/general_docs/ruby/MESI_Two_Level/).

11. Как store buffer может влиять на наблюдаемый порядок независимых обращений? Для атомарных `x = 0` и `y = 0` разберите два потока: первый выполняет relaxed-запись `x = 1` и relaxed-чтение `y`, второй — relaxed-запись `y = 1` и relaxed-чтение `x`; исследуйте результат двух нулей отдельно в C++ и в выбранной модели ISA.

    **Ответ:** В C++20 relaxed-доступы к двум атомикам не задают межпоточное happens-before и не создают единого порядка всех операций; результат двух нулей допустим. В x86-64 с обычной WB-памятью и обычными `MOV` он также разрешён: каждое ядро помещает свою запись в store buffer, затем читает другую строку до глобальной видимости чужой записи. Оба могут прочитать начальный ноль, хотя видят собственные предшествующие записи через forwarding. При замене всех четырёх операций C++ на `seq_cst` такой результат запрещён; компилятор должен обеспечить нужные аппаратные ограничения.

    **Типичная ошибка:** Из сохранения порядка записей x86 выводить запрет Store→Load эффекта для разных адресов.

    **Источник:** [C++20 N4861, [atomics.order]](https://timsong-cpp.github.io/cppwp/n4861/atomics.order); [Intel SDM, т. 3A, §9.2.3.4 «Loads May Be Reordered with Earlier Stores to Different Locations»](https://cdrdv2-public.intel.com/671190/253668-sdm-vol-3a.pdf).

12. Почему `memory_order_relaxed` не устраняет стоимость передачи права на запись строки? Спроектируйте сравнение двух атомарных счётчиков в одной строке и в разных строках, сохранив число операций и привязку потоков, затем объясните, почему одно только выравнивание начала всей структуры может оказаться недостаточным.

    **Ответ:** Relaxed убирает часть требований порядка для других объектов, но RMW всё равно требует неделимого обновления и исключительного права на строку. В опыте два закреплённых потока выполняют одинаковое число `fetch_add(1, relaxed)` каждый на своём счётчике; сравнивают соседние атомики и отдельные структуры, чей размер и выравнивание соответствуют разнесению по строкам. Прогревают, проверяют адреса и размещение, считают операции/с и coherence/HITM-подобные события. `alignas(64)` только у начала структуры с двумя соседними полями выравнивает структуру, но оба счётчика остаются в одной строке; нужны отдельные блоки и подходящий stride.

    **Типичная ошибка:** Ожидать устранения ping-pong сменой `seq_cst` на relaxed без изменения размещения данных.

    **Источник:** [Linux, «False Sharing», «How to avoid False Sharing»](https://docs.kernel.org/kernel-hacking/false-sharing.html).

13. Когда release-запись и acquire-чтение позволяют передать обычные данные между потоками? Для однократной публикации структуры через атомарный флаг, изначально равный `false`, сформулируйте условия на порядок заполнения структуры, значение, прочитанное потребителем, и отсутствие дальнейших несинхронизированных изменений.

    **Ответ:** Производитель полностью заполняет структуру, затем выполняет `ready.store(true, release)`. Потребитель обращается к обычным полям только после `ready.load(acquire)`, который прочитал `true` именно от этой публикации или подходящей release sequence. Тогда release synchronizes-with acquire, и предшествующие записи полей happens-before последующих чтений. Объект и флаг должны быть корректно созданы до использования, а структура не должна дальше изменяться без новой синхронизации. Это схема однократной публикации, а не готовый протокол повторного использования буфера.

    **Пример:** `payload.value = 42; ready.store(true, std::memory_order_release);` и `if (ready.load(std::memory_order_acquire)) use(payload.value);`.

    **Типичная ошибка:** Читать поля до проверки флага или повторно менять их, пока потребитель ещё читает.

    **Источник:** [C++20 N4861, [atomics.order]/2](https://timsong-cpp.github.io/cppwp/n4861/atomics.order#2) и [intro.races](https://timsong-cpp.github.io/cppwp/n4861/intro.races).

14. Чем `compare_exchange_weak` отличается от `compare_exchange_strong` на уровне контракта C++? Разберите цикл изменения атомарного значения, включая обновление `expected` после неудачи, возможный ложный отказ и допустимые порядки памяти для успешного и неуспешного пути.

    **Ответ:** Weak может ложно вернуть `false` при совпавшем представлении значения; strong не имеет такого разрешения. После неудачи `expected` получает фактически прочитанное значение, поэтому `desired` пересчитывают. Успех — RMW, неуспех — load. Для числового счётчика без публикации полезных данных достаточно relaxed на обоих путях. Для C++20 N4861 failure не может быть release или acq_rel; success выбирают по необходимой синхронизации. В одноаргументной форме failure равен success, кроме release→relaxed и acq_rel→acquire. Не следует без проверки переносить в C++20 формулировки ограничений старых стандартов.

    **Пример:** Для `std::atomic<unsigned> x{0}`: `auto e = x.load(std::memory_order_relaxed); while (!x.compare_exchange_weak(e, e + 1, std::memory_order_relaxed, std::memory_order_relaxed)) {}`. `e+1` пересчитывается при каждой попытке.

    **Типичная ошибка:** После отказа продолжать записывать `desired`, вычисленное из старого `expected`.

    **Источник:** [C++20 N4861, [atomics.types.operations]/21–28](https://timsong-cpp.github.io/cppwp/n4861/atomics.types.operations#21).

15. Как связка load-linked/store-conditional отличается от сравнения и обмена по значению? На примере выбранной ISA объясните, что отслеживает reservation, почему условная запись может не состояться и какие ограничения нужно проверить при построении цикла атомарного увеличения.

    **Ответ:** CAS сравнивает текущее представление значения с ожидаемым. AArch64 `LDXR` устанавливает reservation для области памяти, а `STXR` пытается записать новое значение при сохранённом разрешении и возвращает статус: 0 — успех, ненулевой — отказ без записи. Между ними другое ядро может изменить область, даже вернув исходное значение: CAS тогда может не заметить изменение, а reservation теряется. Возможны и другие причины сброса monitor. Проверяют одинаковые адрес и размер пары, выравнивание, memory attributes, короткую последовательность без посторонних обращений и требуемый порядок памяти.

    **Пример:** Схема увеличения: `retry: LDXR w0,[x1]; ADD w0,w0,#1; STXR w2,w0,[x1]; CBNZ w2,retry`. Для публикации нужны соответствующие acquire/release варианты, например LDAXR/STLXR.

    **Типичная ошибка:** Считать неуспешный STXR доказательством изменения самого значения счётчика.

    **Источник:** [Arm, «Synchronization Primitives in A64», §3 «Exclusives», §3.1–3.2](https://documentation-service.arm.com/static/68c223238a337a2bc6645c0a).

16. Почему одинаковые acquire/release-операции C++ могут давать разные инструкции на x86-64 и AArch64? Для выровненного атомарного целого в обычной кэшируемой памяти сравните вывод компилятора для relaxed, acquire, release и `seq_cst`, отделяя ограничения компилятора от гарантий используемых инструкций и типов памяти.

    **Ответ:** C++ задаёт результат и порядок, а компилятор выбирает инструкции с подходящими ISA-гарантиями. Проверка Clang 22.1.2, C++20, `-O2 -S`, для отдельных `std::atomic<int>` load/store, с целями `x86_64-apple-macos13` и `arm64-apple-macos13 -mcpu=generic -march=armv8-a` дала:

    | Операция | x86-64 | AArch64, Armv8-A |
    |---|---|---|
    | load relaxed | `MOV` | `LDR` |
    | load acquire | `MOV` | `LDAR` |
    | load seq_cst | `MOV` | `LDAR` |
    | store relaxed | `MOV` | `STR` |
    | store release | `MOV` | `STLR` |
    | store seq_cst | `XCHG` | `STLR` |

    Для AArch64 без `-mcpu=generic` выбранная конфигурация Clang выдала `LDAPR` для acquire, сохранив `LDAR` для seq_cst. Это зависит от доступности RCpc. Одинаковый `MOV` для relaxed/acquire не означает одинаковую свободу компилятора: требования C++ запрещают соответствующие перемещения соседних операций. Таблица относится к выровненному 32-битному типу и обычной кэшируемой RAM; MMIO и NT stores требуют другого анализа.

    **Типичная ошибка:** Переносить один дизассемблированный вариант на все типы, CPU и параметры компиляции.

    **Источник:** [Sewell et al., «C/C++11 mappings to processors», x86 и ARMv8](https://www.cl.cam.ac.uk/~pes20/cpp/cpp0xmappings.html); [Arm, «Enabling the LDAPR instructions for C/C++ compilers»](https://developer.arm.com/community/arm-community-blogs/b/tools-software-ides-blog/posts/enabling-rcpc-in-gcc-and-llvm). Таблица дополнительно проверена указанной компиляцией.

## Сложный уровень

17. Как изменится корректность однократной публикации, если потребитель использует relaxed-чтение флага вместо acquire? Сначала рассмотрите обычные поля полезной нагрузки и проверьте отсутствие data race, затем замените каждое поле атомарным с relaxed-доступом и отдельно исследуйте допустимые значения без предположения о случайно наблюдаемом порядке CPU.

    **Ответ:** Если потребитель читает `true` relaxed и затем обычные поля, synchronizes-with не возникает. Между записями производителя и чтениями потребителя нет happens-before, поэтому программа содержит data race и имеет неопределённое поведение; рассуждать о разрешённых «старых значениях» для неё некорректно. Если поля заменить заранее созданными атомиками и обращаться relaxed, гонки на этих полях исчезнут, но публикация всё равно не упорядочит их значения относительно флага. При начальном значении 0 и однократной записи 42 потребитель может прочитать 0 или 42 для каждого поля, включая смеси, если нет дополнительных связей порядка.

    **Типичная ошибка:** Объяснять первый вариант только «устаревшим кэшем» вместо признания UB или считать relaxed-флаг достаточным для остальных атомиков.

    **Источник:** [C++20 N4861, [intro.races], modification order и data race](https://timsong-cpp.github.io/cppwp/n4861/intro.races); [atomics.order](https://timsong-cpp.github.io/cppwp/n4861/atomics.order).

18. При каких условиях release fence и acquire fence могут синхронизировать передачу данных через relaxed-атомик? Разберите порядок «запись полезных данных → release fence → relaxed-запись флага» у производителя и «relaxed-чтение флага → acquire fence → чтение полезных данных» у потребителя, явно указав, какое значение должен прочитать потребитель и почему двух произвольных fences недостаточно.

    **Ответ:** Release fence производителя синхронизируется с acquire fence потребителя, если существует связывающий атомарный объект: release fence sequenced-before записи флага X, чтение Y sequenced-before acquire fence, и Y прочитало значение X либо подходящей гипотетической release sequence. Тогда записи полезных данных до первого fence happens-before чтений после второго. Для однократного флага false→true потребитель должен прочитать true от нужного производителя и лишь затем выполнять acquire fence и читать данные. Если прочитан исходный false, связи нет. Fences в произвольных местах без такого reads-from ребра не синхронизируют потоки.

    **Типичная ошибка:** Поставить acquire fence до чтения флага или после чтения полезных данных и ожидать то же доказательство.

    **Источник:** [C++20 N4861, [atomics.fences]/2, fence–fence synchronization](https://timsong-cpp.github.io/cppwp/n4861/atomics.fences#2).

19. Как различить индивидуальную когерентность атомиков и единый порядок `seq_cst`? Для двух атомарных переменных, двух потоков-писателей и двух читателей, читающих переменные в противоположном порядке, постройте наблюдение, которое нужно проверить при acquire/release и при замене всех операций на `seq_cst`, обосновав вывод по выбранной версии стандарта.

    **Ответ:** Пусть `x=y=0` до запуска потоков. Писатели независимо делают `x.store(1, release)` и `y.store(1, release)`. Читатель R1 читает acquire сначала x, затем y; R2 — сначала y, затем x. Наблюдение R1=`(1,0)`, R2=`(1,0)` допустимо в абстрактной модели C++20 acquire/release: каждый атомик имеет свой modification order, а прочитанная единица синхронизирует только с соответствующим писателем. При замене всех операций на seq_cst результат запрещён. Для единого порядка S из результатов следуют `Wx < R1x < R1y < Wy < R2y < R2x < Wx`, то есть цикл. Допустимость в C++ не означает воспроизводимость на любой ISA.

    **Типичная ошибка:** Приписывать acquire/release единый глобальный порядок всех независимых атомиков либо доказывать запрет одним поведением x86.

    **Источник:** [C++20 N4861, [intro.races]/4](https://timsong-cpp.github.io/cppwp/n4861/intro.races#4) и [[atomics.order]/4–7](https://timsong-cpp.github.io/cppwp/n4861/atomics.order#4).

20. Почему цикл с CAS может плохо масштабироваться, даже если каждая отдельная операция lock-free? Для общего счётчика сравните CAS-loop и `fetch_add` при росте числа ядер, учитывая неудачные попытки, передачу владения строкой, возможность откладывания одного участника и различие lock-free и wait-free гарантий алгоритма.

    **Ответ:** В CAS-loop несколько потоков читают одно старое значение, но успешно меняет его один; остальные обновляют expected, пересчитывают результат и повторяют попытку. С ростом числа ядер растут повторы, передачи строки, нагрузка на межсоединение и вероятность долгого ожидания конкретного потока. `fetch_add` часто использует прямой аппаратный RMW и избегает программных повторов, но общий счётчик всё равно сериализует обновления; на ISA без прямой операции он сам может быть LL/SC-loop. В измерении фиксируют число успешных увеличений, placement и memory order, считают также неудачные CAS. Lock-free допускает продвижение других при задержке одного участника; wait-free требует ограниченного числа шагов каждого, чего обычный CAS-loop не обещает.

    **Типичная ошибка:** Считать lock-free синонимом «быстро при любом contention» или «никто не голодает».

    **Источник:** [C++20 N4861, [intro.progress]/2](https://timsong-cpp.github.io/cppwp/n4861/intro.progress#2); [Arm, «Synchronization Primitives in A64», §2, LSE](https://documentation-service.arm.com/static/68c223238a337a2bc6645c0a).

21. В чём состоит проблема ABA при сравнении указателя и обмене? Постройте последовательность, в которой значение указателя вернулось к исходному, но состояние структуры или время жизни узла изменилось, затем разделите задачи обнаружения изменения, безопасного освобождения памяти и защиты от повторного использования адреса.

    **Ответ:** Пусть стек начинается `A→B→C`. T1 читает `head=A` и `A.next=B`, затем останавливается. T2 удаляет A и B, после чего возвращает A в стек уже как `A→C`. CAS T1 по одному значению указателя `A→B` может успешно установить устаревший B, хотя структура изменилась; при освобождении B это ещё и доступ к закончившему жизнь объекту. Счётчик версии рядом с указателем помогает обнаружить изменение, если пара обновляется атомарно и учтено переполнение. Но он не обеспечивает безопасного разыменования старых узлов. Hazard pointers, epochs/RCU и другие схемы управляют временем освобождения и повторного использования; корректность каждой требует отдельного доказательства.

    **Типичная ошибка:** Исправить сравнение тегом, но продолжить читать `next` узла, который другой поток уже мог освободить.

    **Источник:** [Michael, «Hazard Pointers: Safe Memory Reclamation for Lock-Free Objects», проблема ABA и reclamation](https://research.ibm.com/publications/hazard-pointers-safe-memory-reclamation-for-lock-free-objects).

22. Какие детали ISA важны при замене CAS-loop на LL/SC-loop? Для выбранного AArch64-процессора исследуйте размер области reservation, ограничения последовательности и влияние посторонних записей, после чего объясните, почему нельзя переносить вывод о ложных отказах и прогрессе на все реализации либо считать LL/SC готовым решением освобождения узлов.

    **Ответ:** Для Cortex-A76 r4p1 TRM указывает `CTR_EL0.ERG=4`, то есть `2⁴` 32-битных слова = 64 байта; внутренний exclusive monitor отслеживает строку такого размера. Запись другого ядра в соседний объект этой области может сорвать STXR без изменения нужного слова. Проверяют адрес, размер и выравнивание LDXR/STXR, атрибуты coherent shareable memory, сброс monitor через CLREX/возврат из исключения и ограничения конкретной ISA для прогресса. Между парой сохраняют короткую вычислительную последовательность без посторонних обращений и cache maintenance; рекомендуемую близость нельзя подменять универсальной гарантией числа попыток. На другом CPU гранула и причины отказов могут отличаться. LL/SC обнаруживает вмешательство в reservation, но не продлевает жизнь узла, разыменованного до её установки или после потери reservation.

    **Типичная ошибка:** Выводить wait-free из отсутствия сравнения по значению либо использовать LL/SC вместо схемы освобождения узлов.

    **Источник:** [Arm Cortex-A76 TRM r4p1, §A6.4.2 «Internal exclusive monitor», §B2.39 «CTR_EL0»](https://documentation-service.arm.com/static/5f562083235b3560a01e03bc); [Arm, «Synchronization Primitives in A64», §3](https://documentation-service.arm.com/static/68c223238a337a2bc6645c0a).

23. Как измерить стоимость передачи строки между ядрами и отличить её от стоимости обращения к DRAM? Спроектируйте опыт с передачей атомарного флага или маркера между двумя закреплёнными потоками, затем сравните пары ядер и укажите, как синхронизация, топология, частота CPU и используемые счётчики ограничивают вывод о самом протоколе.

    **Ответ:** Два закреплённых потока многократно передают очередь через отдельный атомарный маркер: A ждёт свою очередь acquire и отдаёт её release, B делает обратное. Маркер выровнен, лишние изменяемые данные вынесены в другие строки; после прогрева измеряют много полных round trips и распределение задержек. Половина round trip — лишь приближение односторонней стоимости при симметрии: в неё входят polling, инструкции и синхронизация. Сравнивают SMT-соседей, разные ядра одного кластера/сокета и разные сокеты, фиксируя частоты и NUMA. Малый горячий набор и счётчики cache-to-cache/HITM при низком DRAM-трафике отличают передачу владения от DRAM; отдельный зависимый холодный тест даёт контроль памяти.

    **Типичная ошибка:** Назвать полученный ping-pong latency чистой ценой одного сообщения MESI или одного обращения к DRAM.

    **Источник:** [Linux, «False Sharing», `perf c2c` и анализ обмена строками](https://docs.kernel.org/kernel-hacking/false-sharing.html); [Intel PerfMon, модельные HITM/remote response events](https://perfmon-events.intel.com/).

24. Почему доказательства корректности обмена между потоками C++ недостаточно для публикации буфера DMA-устройству? Для сценария «заполнить буфер → записать MMIO doorbell» перечислите отдельно требования к DMA-когерентности, cache maintenance, доступу к регистрам и платформенным барьерам, объяснив, почему `atomic_thread_fence`, `volatile` и протокол CPU-кэшей нельзя считать взаимозаменяемыми средствами.

    **Ответ:** C++ happens-before описывает потоки языка, но не задаёт протокол DMA и MMIO. Драйвер должен получить корректный DMA-адрес и mapping/IOMMU-настройки, знать, участвует ли устройство в когерентности, и передать ему владение буфером. Для некогерентной streaming DMA нужны предусмотренные API clean/flush/sync до чтения устройством, а при обратном направлении — нужное invalidation/sync перед CPU-чтением. Даже coherent DMA требует упорядочивания данных и дескрипторов перед передачей владения. Doorbell записывают платформенным MMIO accessor с нужными барьерами и при необходимости учитывают posted writes. В Linux это DMA API, `dma_wmb()` для соответствующего протокола дескрипторов и правильный `writel()`/иной accessor. `volatile` не обеспечивает cache maintenance, а `atomic_thread_fence` сам не заменяет контракт драйверного API.

    **Типичная ошибка:** Заменять `dma_map/sync` и MMIO-accessor одной C++ seq_cst fence либо писать в регистр как в обычный атомик RAM.

    **Источник:** [Linux, «Dynamic DMA mapping Guide», coherent/streaming mappings](https://docs.kernel.org/core-api/dma-api-howto.html); [«Linux kernel memory barriers», «DMA barriers» и «Kernel I/O barrier effects»](https://docs.kernel.org/core-api/wrappers/memory-barriers.html).
