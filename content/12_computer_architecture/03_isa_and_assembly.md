# Набор команд, регистры и чтение ассемблера

Цель — научиться связывать простую программу с машинными инструкциями и отличать архитектурные гарантии от деталей реализации процессора. Предпосылки: [цифровые основы](01_digital_foundations.md) и [представление данных](02_data_representation.md); для практики нужен компилятор C/C++ с выводом ассемблера или дизассемблер.

## Лёгкий уровень

1. Что определяет архитектура набора команд — ISA, а что относится к микроархитектуре? Сравните совместимость двух процессоров, исполняющих один набор команд, и объясните, почему одинаковая программа на них может работать с разной скоростью.

   **Ответ:** ISA задаёт доступные программному обеспечению инструкции, регистры, типы операндов, кодировки, исключения и правила памяти. Микроархитектура реализует этот контракт: конвейер, исполнительные устройства, кэши, переименование, предсказание переходов. Два процессора совместимы с одним двоичным кодом, если поддерживают используемые инструкции, режим и требования среды выполнения; одинакового названия семейства ISA недостаточно без нужных расширений и ABI.

   **Пример:** Одинаковая скалярная программа x86-64 может исполняться на разных ядрах Intel/AMD, но разный размер кэша и число исполнительных портов изменят время. Программа с AVX2 потребует AVX2 и поддержки сохранения соответствующего состояния ОС.

   **Типичная ошибка:** Принимать число инструкций за число тактов или считать все расширения x86-64 обязательными.

   **Источник:** [Intel SDM, том 1, Introduction и Basic Execution Environment](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html).

2. Из каких частей состоит машинная инструкция и чем её кодировка отличается от ассемблерной записи? На примере операции сложения выделите операцию, операнды и способ получения каждого операнда, не предполагая, что каждой строке исходного C++ соответствует одна инструкция.

   **Ответ:** Инструкция кодирует операцию, источники/назначение и способы получения операндов: регистр, непосредственная константа, память и т. п. Машинная кодировка — биты, которые декодирует процессор; ассемблерная запись — символический текст с мнемониками, именами и иногда псевдоинструкциями.

   **Пример:** В RISC-V `add x3,x1,x2` означает `x3←x1+x2` по модулю `2^XLEN`: поля rd/rs1/rs2 выбирают регистры, opcode/funct — ADD. `addi x3,x1,5` получает второе слагаемое из непосредственного поля. Одно выражение C++ может превратиться в несколько команд, исчезнуть или объединиться с соседними.

   **Типичная ошибка:** Считать метку или директиву `.globl` исполняемой инструкцией.

   **Источник:** [RISC-V RV32I, Base Instruction Formats и Integer Computational Instructions](https://docs.riscv.org/reference/isa/v20260120/unpriv/rv32.html).

3. Чем архитектурный регистр отличается от ячейки оперативной памяти? Составьте короткую последовательность «загрузить два значения, сложить, сохранить результат» и укажите, где находится каждое промежуточное значение.

   **Ответ:** Архитектурный регистр именуется полем инструкции и является частью состояния CPU; память выбирается адресом, имеет гораздо больший объём и иной механизм доступа. В load/store ISA арифметика получает значения из регистров, а память читают/пишут отдельные инструкции.

   **Пример:** AArch64, 32-битные значения, адреса в x0/x1/x2:

   ```asm
   ldr w3, [x0]       // первое значение: память → w3
   ldr w4, [x1]       // второе: память → w4
   add w5, w3, w4     // сумма modulo 2^32 находится в w5
   str w5, [x2]       // сумма → память
   ```

   Адреса остаются в 64-битных x-регистрах; w3/w4/w5 — значения, а не адреса.

   **Типичная ошибка:** Называть запись в регистр записью в RAM или путать указатель с прочитанными по нему данными.

   **Источник:** [Arm A64 Instruction Set Reference, LDR, ADD, STR](https://documentation-service.arm.com/static/6245c734b059dc5ff9a8bdab).

4. Что хранит счётчик команд и как определяется адрес следующей инструкции? Проследите выполнение трёх последовательных инструкций и одного перехода, затем объясните, почему длина кодировки инструкции важна при чтении адресов в дизассемблере.

   **Ответ:** Счётчик команд определяет место исполнения в потоке инструкций. При последовательном исполнении следующая инструкция находится по адресу текущей плюс длина кодировки; переход, вызов, возврат или исключение задают другой адрес. На конвейерном CPU одновременно существуют несколько внутренних адресов разных стадий, поэтому архитектурную модель нельзя отождествлять с единственным физическим регистром выборки.

   **Пример:** В A64 три команды по 4 байта идут по `0x1000,0x1004,0x1008`; переход в `0x1008` на `0x2000` делает следующим адресом `0x2000`, а не `0x100C`. В x86 длина переменная, поэтому прибавлять четыре к каждому адресу нельзя.

   **Типичная ошибка:** Читать произвольный байт внутри x86-инструкции как начало следующей.

   **Источник:** [Intel SDM, том 1, Instruction Pointer](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html); [RISC-V ISA, Base Instruction-Length Encoding](https://riscv.github.io/riscv-isa-manual/snapshot/spec/).

5. Какие различия есть между непосредственным значением, значением в регистре и значением по адресу в памяти? На примере прибавления пяти к счётчику объясните, какую работу должен выполнить процессор в каждом варианте расположения исходного счётчика.

   **Ответ:** Immediate — константа в кодировке команды; регистровый операнд — текущее содержимое регистра; операнд памяти — данные после вычисления адреса и чтения. Расположение счётчика и расположение прибавляемой пятёрки — разные вопросы.

   **Пример:** x86-64 Intel-синтаксис: `add eax,5` увеличивает счётчик в EAX, а 5 берёт из инструкции. `add eax,ecx` требует заранее поместить 5 в ECX. `add eax,dword ptr [rdi]` читает слагаемое из памяти. Если сам счётчик в памяти, `add dword ptr [rdi],5` читает, изменяет и записывает его; это не делает операцию атомарной относительно других потоков без дополнительных условий.

   **Типичная ошибка:** Принимать `mov eax,5` за чтение ячейки по адресу 5.

   **Источник:** [Intel SDM, том 1, Operand Addressing; том 2, ADD](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html).

6. Чем загрузка значения из памяти отличается от вычисления его адреса? Для массива 32-битных элементов с базовым адресом `B` выразите адрес элемента с индексом `i` и укажите, на каком шаге реально требуется чтение памяти.

   **Ответ:** Для массива 32-битных элементов при восьмибитном байте адрес элемента `EA=B+4·i`. Вычислить EA — выполнить арифметику над адресами; загрузить элемент — прочитать четыре байта по EA и интерпретировать их по правилам формата/инструкции.

   **Пример:** x86-64: `lea rax,[rdi+rsi*4]` вычисляет адрес без чтения массива, `mov eax,[rdi+rsi*4]` читает значение. При `B=0x1000,i=3` адрес `0x100C`; содержимое может быть любым. Корректность C++-адресации дополнительно требует допустимого индекса и живого объекта массива.

   **Типичная ошибка:** Считать, что LEA всегда обращается к памяти, потому что использует квадратные скобки.

   **Источник:** [Intel SDM, том 2, LEA и MOV](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html).

7. Как условный переход связывается с результатом сравнения? Переведите простое условие `if (a < b)` в последовательность сравнения и переходов для выбранной ISA и отдельно уточните, являются ли сравниваемые числа знаковыми.

   **Ответ:** В x86 CMP выполняет вычитание для установки флагов, не сохраняя разность; Jcc проверяет нужное условие. Для signed 32-bit `a<b` используются `JL` (`SF≠OF`), для unsigned — `JB` (`CF=1`). Равенство определяется одинаково, порядок — по-разному.

   **Пример:** При a в EDI, b в ESI:

   ```asm
   cmp edi, esi
   jl  less          // знаковое a < b
   // ветвь a >= b
   jmp done
   less:
   // ветвь a < b
   done:
   ```

   Для unsigned заменить `jl` на `jb`. Шаблон `0xFFFFFFFF` меньше 1 как −1, но больше 1 как 4294967295.

   **Типичная ошибка:** Использовать JL для размера массива unsigned, потому что «это переход меньше».

   **Источник:** [Intel SDM, том 2, CMP и Jcc: signed/unsigned conditions](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html).

8. Зачем программе стек и указатель стека? Проследите сохранение временного значения и его восстановление в абстрактной модели стека, явно задав направление роста и размер сохраняемого элемента.

   **Ответ:** Стек обеспечивает LIFO-хранение временных значений, адресов возврата и данных вызовов; SP указывает принятую соглашением границу стека. Зададим рост к меньшим адресам и 8-байтовые элементы: push сначала уменьшает SP на 8 и сохраняет значение, pop читает по SP и затем увеличивает SP на 8.

   **Пример:** Начало `SP=0x1000`; push 42 даёт `SP=0xFF8,M[0xFF8]=42`; push 7 — `SP=0xFF0`; два pop вернут сначала 7, затем 42 и исходный SP. Конкретный ABI дополнительно задаёт выравнивание и правила сохранения регистров.

   **Типичная ошибка:** Восстанавливать значения в порядке сохранения или считать направление роста универсальным для любой архитектуры.

   **Источник:** [MIT, §16.2.3: Stacks](https://computationstructures.org/notes/stacks/notes.html).

## Средний уровень

9. Какие различия между x86-64, AArch64 и RISC-V важны при первом чтении ассемблера? Сравните доступ к памяти в арифметических инструкциях, способы условного перехода и кодирование инструкций, уточняя базовый набор и расширения там, где от них зависит ответ.

   **Ответ:** x86-64 имеет переменную длину команд (до 15 байтов), арифметику с одним операндом памяти и флаги для Jcc; два обычных явных операнда памяти ADD не допускает. A64 использует 32-битные инструкции и load/store модель, условные B.cond по NZCV, также CBZ/TBZ. Базовые RV32I/RV64I — load/store, команды по 32 бита, сравнение регистров внутри BLT/BLTU/BEQ без отдельного регистра флагов; расширение C добавляет 16-битные кодировки.

   **Пример:** Сложение с памятью: x86 `add eax,[rdi]`; A64 `ldr w2,[x0]; add w1,w1,w2`; RV64I `lw t0,0(a0); addw a1,a1,t0`. Для unsigned результата 32 бит достаточно младших битов; для дальнейшей 64-битной интерпретации требуется проверить расширение загрузки/ADDW.

   **Типичная ошибка:** Обобщать фиксированную длину базового RISC-V на набор с C или путать AArch64 с A32/Thumb.

   **Источник:** [RISC-V, RV32I и RV64I](https://riscv.github.io/riscv-isa-manual/snapshot/spec/); [Arm A64 Instruction Set Reference](https://documentation-service.arm.com/static/6245c734b059dc5ff9a8bdab); [Intel SDM, том 2, Instruction Format](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html).

10. Почему архитектурные имена регистра могут обозначать разные части одного хранилища? Для x86-64 сопоставьте `RAX`, `EAX`, `AX` и `AL`, затем по документации определите, какие старшие биты сохраняются или изменяются при записи в каждый из этих операндов.

    **Ответ:** В x86-64 RAX — 64 бита, EAX — младшие 32, AX — младшие 16, AL — младшие 8. Обычная запись RAX заменяет все 64 бита; запись EAX заменяет младшие 32 и обнуляет старшие 32; записи AX/AL сохраняют остальные разряды. Это правило размера результата не следует переносить на инструкции с другой семантикой назначения.

    **Пример:** Если `RAX=0x1122334455667788`, то `mov al,0xAA` даёт `0x11223344556677AA`; `mov ax,0xBBBB` — `0x112233445566BBBB`; `mov eax,0xCCCCCCCC` — `0x00000000CCCCCCCC` (каждый пример от исходного RAX).

    **Типичная ошибка:** Ожидать сохранения старших 32 бит после MOV EAX или их очистки после MOV AX.

    **Источник:** [Intel SDM, том 1, §3.4.1.1: General-Purpose Registers in 64-Bit Mode](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html).

11. Как формируется эффективный адрес и какие ограничения накладывает конкретная ISA? Для выражения `a[i]` и поля структуры разберите базу, смещение и масштаб индекса, затем сравните возможные последовательности вычисления адреса в x86-64 и AArch64.

    **Ответ:** Эффективный адрес объединяет базу, индекс с масштабом и смещение в пределах поддерживаемой формы. В x86 обычная форма `base+index*scale+disp`, scale∈{1,2,4,8}; конкретные регистры/кодировки имеют ограничения. В A64 LDR поддерживает базу с immediate либо регистровым индексом и разрешённым сдвигом/расширением, но не произвольную сумму всех компонентов в одной команде.

    **Пример:** `uint32_t a[]`: x86 `mov eax,[rdi+rsi*4]`, A64 `ldr w2,[x0,x1,lsl #2]`. Для массива структур размером 16 байт и поля по смещению 8: x86 сначала `shl rsi,4`, затем `[rdi+rsi+8]`; A64 `add x2,x0,x1,lsl #4; ldr w3,[x2,#8]`. Размер и offset берутся из ABI/offsetof, не из суммы размеров полей на глаз.

    **Типичная ошибка:** Использовать x86 scale=16 или одновременно вписать в A64 LDR несовместимые формы адресации.

    **Источник:** [Intel SDM, том 1, Specifying an Offset](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html); [Arm, LDR register/immediate addressing](https://documentation-service.arm.com/static/6245c734b059dc5ff9a8bdab).

12. Как различить в дизассемблере знаковое и беззнаковое сравнение? Скомпилируйте две функции сравнения одинаковых по ширине целых типов с разной знаковостью и объясните выбранные условия перехода на граничных битовых шаблонах.

    **Ответ:** Знаковость видна по условию, использующему результат CMP, а не по CMP самому. Проверены функции `int lt_s(int a,int b){return a<b;}` и `int lt_u(unsigned a,unsigned b){return a<b;}`: Clang 22.1.2, `-target x86_64-unknown-linux-gnu -O2 -S -masm=intel` генерирует для обеих `xor eax,eax; cmp edi,esi`, затем соответственно `setl al` и `setb al`, `ret`. Для ветвящегося потребителя аналогичны JL и JB.

    **Пример:** `a=0x80000000,b=0`: signed a=−2147483648 → true, unsigned a=2147483648 → false. SETL анализирует SF/OF, SETB — CF; одни и те же биты требуют разного условия.

    **Типичная ошибка:** Определять знаковость по MOV или считать любое сравнение с нулём знаковым.

    **Источник:** [Intel SDM, том 2, SETcc/Jcc](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html); [Clang, target и -S](https://clang.llvm.org/docs/UsersManual.html).

13. Как цикл `for` превращается в инициализацию, тело, проверку условия и переход? Разберите ассемблер суммирования короткого массива без оптимизации и с оптимизацией, отмечая, какие изменения сохраняют смысл программы и какие предположения о входных данных необходимы.

    **Ответ:** Для `unsigned sum(const unsigned*a,unsigned long n){unsigned s=0;for(unsigned long i=0;i<n;++i)s+=a[i];return s;}` на x86-64 Linux unsigned имеет 32 бита, unsigned long — 64. Проверенная сборка Clang 22.1.2 `-O0` хранит a,n,s,i в стеке: инициализация s/i, блок `cmp i,n; jae exit`, загрузка `a[i]`, сложение, запись s, увеличение i и обратный JMP. При `-O2 -fno-vectorize -fno-slp-vectorize -fno-unroll-loops` s/i остаются в регистрах.

    **Пример:** Оптимизированное ядро: `xor eax,eax; test rsi,rsi; je done; xor ecx,ecx; loop: add eax,[rdi+rcx*4]; inc rcx; cmp rsi,rcx; jne loop; done: ret`. Пустой массив возвращает 0; `{1,2,3}` — 6. Массив должен содержать n доступных элементов; сложение unsigned даёт modulo `2^32`. Векторизация тоже может сохранять этот результат.

    **Типичная ошибка:** Удалить начальную проверку n и получить чтение a[0] при n=0.

    **Источник:** [Clang, Optimization Levels и Loop Vectorization](https://clang.llvm.org/docs/UsersManual.html); [C++ basic.fundamental: unsigned arithmetic](https://eel.is/c++draft/basic.fundamental).

14. Как инструкция вызова и возврата передаёт управление между функциями? Сравните концепцию адреса возврата в стеке и в регистре связи, затем проследите два вложенных вызова и объясните, какие данные необходимо сохранить, чтобы вернуться в правильные места.

    **Ответ:** CALL сохраняет адрес продолжения и передаёт управление, RET возвращается по нему. В x86-64 near CALL помещает адрес следующей инструкции на стек; RET забирает его. В AArch64 BL записывает адрес следующей инструкции в x30 (LR), RET обычно переходит по x30; сама BL не сохраняет старое значение LR.

    **Пример:** A вызывает B, B вызывает C: у x86 на стеке два разных адреса возврата. У A64 B должен до BL C сохранить свой входной LR, например `stp x29,x30,[sp,#-16]!`, затем восстановить его перед RET. Также сохраняют необходимые значения caller/callee-saved регистров по ABI; C может не иметь кадра, если она leaf-функция.

    **Типичная ошибка:** Вложенно вызвать функцию через BL и затем RET без сохранения входного LR.

    **Источник:** [AAPCS64, §6.1: Machine Registers и §6.5: Subroutine Calls](https://github.com/ARM-software/abi-aa/blob/main/aapcs64/aapcs64.rst); [Intel SDM, том 2, CALL/RET](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html).

15. Почему локальная переменная исходной программы не обязана иметь отдельную ячейку в стеке? Сравните ассемблер маленькой функции при разных уровнях оптимизации и определите, какие значения остаются в регистрах, вычисляются заново или исчезают после упрощения выражений.

    **Ответ:** Переменная языка — абстрактное значение/объект; если наблюдаемое поведение не требует отдельного адресуемого хранения, компилятор может держать его в регистре, пересчитать или удалить. Проверенная функция `unsigned local(unsigned x){unsigned a=x+3;unsigned b=a*2;return b;}` при Clang 22.1.2 x86-64 `-O0` записывает x,a,b в разные слоты стека. При `-O2` остаётся `lea eax,[2*rdi+6]; ret`.

    **Пример:** x поступает в EDI; a и b не имеют отдельных ячеек, их выражения объединены. Константная локальная, используемая только в свёрнутом выражении, может исчезнуть полностью; значение, нужное после уничтожения регистра, компилятор может вычислить повторно. Это возможности оптимизатора, а не обещание для каждой функции.

    **Типичная ошибка:** Считать наличие переменной в исходнике доказательством обращения к стеку или использовать -O0 для выводов о скорости production-сборки.

    **Источник:** [C++ intro.abstract: observable behavior/as-if](https://eel.is/c++draft/intro.abstract); [Clang, Controlling Code Generation](https://clang.llvm.org/docs/UsersManual.html).

16. Чем различаются текст ассемблера от компилятора и дизассемблирование объектного или исполняемого файла? Выберите короткую функцию, найдите её символ и инструкции в обоих представлениях и объясните роль меток, адресов и ещё не разрешённых ссылок на внешние символы.

    **Ответ:** `clang -S` показывает символический текст до окончательной компоновки: метки, директивы, внешние символы. `llvm-objdump -d -r` декодирует реальные байты объекта, показывает смещения и релокации; адреса объекта ещё не обязательно адреса загрузки. После линковки/загрузки ссылки разрешаются, хотя часть может оставаться динамической.

    **Пример:** Проверено для `extern unsigned external(unsigned); unsigned caller(unsigned x){return external(x)+1;}` при x86-64 Linux -O2. В `.s` — `push rax; call external@PLT; inc eax; pop rcx; ret`. В `.o` CALL имеет байты `e8 00 00 00 00`; `-r` показывает `R_X86_64_PLT32 external-4`, без неё нулевое смещение можно ошибочно принять за фактическую цель. Имя caller находится в таблице символов; локальные метки связывают блоки, но не являются командами.

    **Типичная ошибка:** Считать нули в ещё не разрешённом операнде окончательным адресом external.

    **Источник:** [LLVM llvm-objdump, --disassemble и --reloc](https://llvm.org/docs/CommandGuide/llvm-objdump.html); [GNU as, Symbols](https://sourceware.org/binutils/docs/as/Symbols.html).

## Сложный уровень

17. Почему число ассемблерных инструкций само по себе плохо предсказывает стоимость фрагмента? Сравните две реализации вычисления адреса и загрузки значения, выделив зависимости, обращения к памяти и возможное разбиение инструкций на внутренние операции; укажите, каких сведений о микроархитектуре не хватает для вывода о скорости.

    **Ответ:** Стоимость зависит от графа зависимостей, внутренних операций, исполнительных портов, адресной генерации и попадания памяти. Одна команда с операндом памяти может выполнять и загрузку, и арифметику; некоторые реализации сохраняют их слияние лишь на части стадий.

    **Пример:** A: `mov eax,[rdi+rsi*4+8]`; B: `lea rdx,[rdi+rsi*4+8]; mov eax,[rdx]`. Обе читают одно и то же 32-битное значение при допустимом адресе, но B добавляет зависимость `LEA→load`, занимая АЛУ/порт LEA. A может иметь ограничения сложного адреса на конкретном AGU. Ещё пример `add eax,[rdi]` объединяет запись ассемблера, но не отменяет загрузку и зависимость суммы от неё. Нужны модель CPU, latency/throughput, порты, cache/TLB, surrounding code и частота.

    **Типичная ошибка:** Объявить A быстрее ровно вдвое по количеству строк или сравнивать горячую и холодную память как равные условия.

    **Источник:** [Intel Optimization Reference Manual, §3.5: инструкции, зависимости и порты](https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf).

18. Как чтение или запись части регистра может повлиять на зависимости следующей инструкции? Постройте два коротких примера для выбранного x86-64 процессора и отделите требуемый ISA результат от возможной стоимости объединения частей регистра на этой реализации.

    **Ответ:** ISA требует сохранить не записанные части регистра, поэтому чтение полного регистра после частичной записи может зависеть и от старых старших битов. Пример A: `mov al,[rdi]; add rax,rbx` использует новый AL и прежние биты 63:8. Пример B: `movzx eax,byte ptr [rdi]; add rax,rbx` обнуляет биты 63:8 и устраняет зависимость от прежнего RAX; результаты A/B совпадают только при соответствующем условии на старшие биты.

    **Пример:** Выбран Intel Skylake: согласно Optimization Manual §3.5.2.3, объединение частичных записей выполняется аппаратно без вставки специальной merge-uop, применявшейся в более ранних реализациях. AH/BH/CH/DH всё ещё имеют отдельные ограничения портов/задержек; из одной лишь семантики AL нельзя вывести их стоимость. `mov eax,[rdi]; mov cl,al` читает часть уже готовой полной версии и не требует объединения разных записей.

    **Типичная ошибка:** Приписывать всем x86 один исторический штраф partial-register stall или заменять MOV AL на MOVZX без проверки нужных старших битов.

    **Источник:** [Intel Optimization Reference Manual, §3.5.2.3: Partial Register Stalls, Skylake](https://cdrdv2-public.intel.com/821612/248966-Optimization-Reference-Manual-V1-050.pdf); [Intel SDM, §3.4.1.1](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html).

19. Как восстановить смысл функции по дизассемблеру, если имена локальных переменных отсутствуют? Возьмите функцию с одним циклом и двумя ветвями, постройте граф базовых блоков и определите входы, выходы и инвариант цикла, помечая выводы, которые нельзя сделать однозначно.

    **Ответ:** Сначала находят входы по ABI, границы базовых блоков по целям/продолжениям переходов, затем def-use регистров, обращения к памяти, обратные рёбра и выходы. Пример функции: `unsigned f(const unsigned*a,unsigned long n){unsigned s=0;for(unsigned long i=0;i<n;i++){if(a[i]&1)s+=a[i];else s-=a[i];if(s>100)s=0;}return s;}`. В проверенном Clang -O0 видны проверка `i<n`, тест младшего бита, ADD/SUB и unsigned-проверка `s>100`.

    **Пример:** Граф: `entry→test`; `test(false)→exit`, `test(true)→parity`; `parity→add/sub→limit`; `limit(true)→reset→inc`, `limit(false)→inc`; `inc→test`. Инвариант: `0≤i≤n`, s — результат обработки первых i элементов по рекуррентному правилу «±элемент modulo 2^32, затем сброс при >100»; после каждой полной итерации `s≤100`. Входы — a,n, выход — s в EAX. Имена, typedef, исходный вид for/while и назначение массива однозначно не восстанавливаются; оптимизация может заменить ветвь CMOV.

    **Типичная ошибка:** Считать все обратные переходы отдельными циклами или восстанавливать исходные имена из роли регистра.

    **Источник:** [LLVM Language Reference, basic blocks и terminator instructions](https://llvm.org/docs/LangRef.html#function-structure); [x86-64 psABI, передача аргументов/результатов](https://gitlab.com/x86-psABIs/x86-64-ABI).

20. Как распознать вычисление, заменившее условный переход выбором значения, маской или условной инструкцией? Скомпилируйте функцию минимума двух чисел для двух ISA и объясните, почему одинаковая семантика не гарантирует одинаковую последовательность команд или одинаковую скорость.

    **Ответ:** Проверена функция `int minimum(int a,int b){return a<b?a:b;}` с Clang 22.1.2, `-O2`, отдельно `-target x86_64-unknown-linux-gnu -masm=intel` и `-target aarch64-unknown-linux-gnu`. Результат x86: `mov eax,esi; cmp edi,esi; cmovl eax,edi; ret`. A64: `cmp w0,w1; csel w0,w0,w1,lt; ret`. Обе выбирают минимум signed 32-bit для всех входов, включая INT_MIN/INT_MAX.

    **Пример:** Условный выбор узнаётся по CMOV/CSEL, булевому 0/1 с последующей маской либо эквивалентной арифметике. Отсутствие Jcc не означает отсутствия зависимости: выбор ждёт флаги и нужные операнды. Стоимость зависит от латентности, портов и предсказуемости альтернативной ветви; нельзя переносить скорость между ISA по числу команд.

    **Типичная ошибка:** Писать `b+((a-b)&mask)` для signed без проверки переполнения `a-b`.

    **Источник:** [Arm armasm Reference, §5.53 CSEL](https://documentation-service.arm.com/static/5f3fa899428f7a6b3328fd44); [Intel SDM, том 2, CMOVcc](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html).

21. Что произойдёт при выполнении инструкции, отсутствующей в поддерживаемом процессором наборе или недоступной на текущем уровне привилегий? Сопоставьте случаи неподдерживаемого расширения, привилегированной операции и обычной ошибки адресации, затем укажите, какие сведения об ОС нужны для описания наблюдаемой реакции программы.

    **Ответ:** На x86-64 неподдерживаемая/недопустимая кодировка обычно вызывает `#UD`; привилегированная команда вроде CLI при недостаточных правах — `#GP`; загрузка с отсутствующей страницы — `#PF`, а неканонический адрес может дать `#GP`. Неподдерживаемое расширение и расширение, состояние которого не включила ОС, также требуют различать по документации инструкции.

    **Пример:** В пользовательском процессе Linux необработанный #UD обычно становится SIGILL, #GP и неустранимый #PF — SIGSEGV. Но demand paging может обработать #PF и продолжить исполнение, а ОС/гипервизор может эмулировать отдельные инструкции. Нужны ОС, режим привилегий, настройки расширений, обработчики сигналов/исключений и конкретный адрес доступа.

    **Типичная ошибка:** Называть любое исключение CPU «segmentation fault» или считать каждый page fault аварией программы.

    **Источник:** [Intel SDM, том 3, Interrupt and Exception Handling: #UD/#GP/#PF](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html).

22. Какие ограничения необходимо учитывать при размещении изменяемых данных рядом с машинным кодом? На примере дизассемблирования смешанного участка объясните, почему правдоподобная декодировка байтов ещё не доказывает, что они являются исполняемыми инструкциями, и предложите признаки для восстановления границ кода.

    **Ответ:** Права памяти обычно задаются страницами: смешивание изменяемых данных и кода усложняет W^X, защиту от исполнения данных и синхронизацию модификаций кода. Обновление исполняемых байтов дополнительно требует правил ISA по видимости записей для выборки инструкций и безопасного взаимодействия с другими потоками; для обычных данных рядом с неизменным кодом это не требуется.

    **Пример:** `jmp after; .byte 0x90,0xc3; after: ...` содержит байты данных, которые x86-дизассемблер правдоподобно покажет как NOP/RET при линейном обходе. Признаки границ: entry points, символы/размеры функций, релокации, прямые цели ветвей, достижимость, таблицы переходов и обращения как к данным. Косвенные переходы, stripped-символы и встроенные таблицы оставляют неоднозначность.

    **Типичная ошибка:** Считать любой успешно декодированный участок исполняемым или выводить права страницы только из имени `.text`.

    **Источник:** [GNU as, .section: writable/executable flags](https://sourceware.org/binutils/docs/as/Section.html); [Intel SDM, том 3, Self-Modifying and Cross-Modifying Code](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html).

23. Как убедиться, что компилятор сохранил именно исследуемую операцию в маленьком эксперименте? Подготовьте функцию с входом, известным только во время выполнения, и наблюдаемым результатом, затем проверьте дизассемблер на удаление вычисления, свёртку констант и встраивание; объясните, зачем фиксировать ISA, её расширения и опции компиляции.

    **Ответ:** Поместить исследуемую функцию в отдельную единицу трансляции без LTO, дать runtime-вход и использовать возвращённое значение в выводе. Затем проверить именно конечный бинарный код: функция присутствует, вызов не встроен, операция зависит от входа и не сведена к константе. `noinline` помогает, но не запрещает оптимизацию тела и само по себе не обеспечивает наблюдаемый результат.

    **Пример:** `extern "C" __attribute__((noinline)) unsigned probe(unsigned x,unsigned y){return x*y+3u;}`; отдельный main читает x/y из аргументов командной строки, вызывает probe и печатает результат. Сборка `clang++ -O2 -fno-lto -target x86_64-unknown-linux-gnu -c probe.cpp`, затем линковка с main и `llvm-objdump -d --x86-asm-syntax=intel` конечного файла. Искать IMUL/эквивалент и ADD/LEA, проверить вызов. Зафиксировать версию, target, -march/-mcpu и расширения: они меняют доступные инструкции и выбор преобразований.

    **Типичная ошибка:** Возвращать неиспользуемый результат либо считать `volatile` универсальным запретом оптимизации всех окружающих вычислений.

    **Источник:** [Clang, noinline и управление оптимизацией](https://clang.llvm.org/docs/AttributeReference.html#noinline); [LLVM llvm-objdump](https://llvm.org/docs/CommandGuide/llvm-objdump.html).

24. Как перенести небольшой ассемблерный алгоритм между x86-64 и AArch64 или RISC-V, сохранив результат на всех допустимых входах? Возьмите суммирование массива с заданной шириной беззнаковых элементов и явно заданным переполнением по модулю, составьте версии для двух ISA и проверьте адресную арифметику, расширение загрузок и завершение цикла на пустом массиве.

    **Ответ:** Контракт: n — 64-битное беззнаковое число элементов; a указывает на n доступных uint32_t, адреса не переполняются; результат — сумма modulo `2^32`, для n=0 чтений нет. Следующие скалярные варианты соответствуют SysV x86-64 и AAPCS64 и используют только caller-saved регистры. Проверены ассемблированием для обоих target.

    **Пример:** x86-64, Intel-синтаксис, a=RDI,n=RSI, результат EAX:

    ```asm
    sum32:
        xor eax, eax
        test rsi, rsi
        je .done
    .loop:
        add eax, dword ptr [rdi]
        add rdi, 4
        dec rsi
        jne .loop
    .done:
        ret
    ```

    AArch64, a=x0,n=x1, результат w0:

    ```asm
    sum32:
        mov w2, wzr
        cbz x1, .done
    .loop:
        ldr w3, [x0], #4
        add w2, w2, w3
        subs x1, x1, #1
        b.ne .loop
    .done:
        mov w0, w2
        ret
    ```

    В обоих случаях адрес увеличивается на 4 байта, 32-битное сложение отбрасывает перенос. Запись EAX/w2 и загрузка w3 обнуляют верхнюю половину соответствующего 64-битного регистра; знаковое расширение не используется. Инвариант: после k итераций сумма равна сумме первых k элементов modulo `2^32`, указатель сдвинут на 4k, осталось n−k. Проверки: пустой массив→0, `{1}→1`, `{0xFFFFFFFF,1}→0`, `{1,2,3}→6`.

    **Типичная ошибка:** Взять 64-битную загрузку, шаг 1 вместо 4 или цикл do-while без проверки n=0; менять сумму на signed C++ при проверке эталоном.

    **Источник:** [Intel SDM, том 2, ADD/MOV](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html); [Arm A64, LDR/ADD/SUBS](https://documentation-service.arm.com/static/6245c734b059dc5ff9a8bdab); [AAPCS64, §6.1](https://github.com/ARM-software/abi-aa/blob/main/aapcs64/aapcs64.rst).
